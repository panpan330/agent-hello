# 当前阶段工作约定

最后更新：2026-07-31

## 文档目的

这个文档记录当前 Java + Python + AI 学习项目里的协作约定。

后续继续学习时，如果上下文变长、切换模型、换新对话，优先按本文档执行，避免反复确认。

当前主线：

```text
阶段 10：AI 应用生产化与可运营能力
```

但本文档里的大部分约定也适用于后续阶段。

## 总目标

学习目标永远优先于单纯赶进度。

核心要求：

```text
不只是会用，还要真正理解。
以后开发、工作、面试、给别人讲解时，都能说清楚这个技术为什么这样设计、能解决什么问题、有什么边界。
```

所以每节学习要兼顾：

```text
基础概念
系统理解
工程落地
代码实践
测试验证
复盘表达
```

## 教学要求

每节笔记必须保证高质量，不能写薄。

尤其要保证：

```text
基础知识铺垫
本节主题系统讲解
```

这两部分是学习质量核心，不能因为省 token 模式而明显缩水。

笔记应该做到：

```text
从基础讲起。
解释为什么要学。
解释它解决什么问题。
解释它在真实项目中的位置。
解释它和前后知识点的关系。
解释边界和局限。
提供练习题和自测题。
练习题和自测题答案放在对应题目下面，方便阅读。
```

笔记结构权重：

```text
“本节定位”要短，只交代本节学什么和接在哪。
“本节学习目标”要精炼，不写过长清单。
“本节新增和修改”要简洁列文件，不展开太多解释。
“一句话先讲透”要短，不扩展成大段说明。
“基础知识铺垫”要明显增多，这是学习理解的重点。
“本节主题系统讲解”也要保持充分，但不要挤占基础知识铺垫。
```

栏目边界：

```text
“基础知识铺垫”：负责讲前置概念、核心术语、为什么重要、基础原理、真实项目背景，以及初学者容易缺失的理解。
“本节主题系统讲解”：负责讲本节主题在系统里的位置、整体流程、模块边界、设计取舍、和前后知识点的关系，以及真实项目里怎么判断该不该这样做；它不能变成代码逐行讲解。
“本节代码讲解”：只讲和本节学习目标直接相关的核心代码，重点解释为什么加、解决什么问题、关键字段或函数如何映射到本节主题、和已有模块怎么协作、有什么边界；避免大量贴代码、逐行解释、重复解释模板代码。
“常见误区”：后续应作为常规栏目保留，尤其是概念、工程边界、安全边界、真实项目取舍类课程，用来集中纠正常见错误理解。
```

## 省 token 模式

当用户说：

```text
省 token 模式
```

执行以下规则。

### 保留的内容

这些不能省：

```text
高质量笔记。
基础知识铺垫。
本节主题系统讲解。
关键代码实现。
关键测试。
学习进度更新。
必要的 README 或模块索引更新。
必要的 git diff --check。
```

### 减少的内容

这些要减少：

```text
重复以前已经讲过且几乎一样的内容。
无关文件扫描。
大范围项目阅读。
冗长中途解释。
无关测试输出。
非必要全量测试。
非必要手动测试文档。
非必要 README 更新。
非必要敏感信息扫描。
```

省 token 模式不是降低学习质量，而是减少低价值消耗。

## 极省 token 模式

当用户明确说：

```text
极省 token 模式
```

可以进一步压缩执行范围：

```text
只读最必要文件。
只写本节核心笔记。
只做最小代码和最小测试。
只跑本节测试和 git diff --check。
最终总结极短。
```

但如果某节是全新重要概念，不建议长期使用极省 token 模式。

## 代码讲解要求

代码是辅助学习的，不是为了堆解释。

新增、修改、删除的非测试代码，如果对本节学习有帮助，需要讲清楚：

```text
为什么要加。
解决什么问题。
关键字段或函数是什么意思。
它在链路里的位置。
它和已有模块的关系。
它有什么边界和局限。
```

不需要大篇幅讲：

```text
机械样板代码。
重复 Pydantic 字段。
普通测试辅助代码。
和本节核心知识关系不大的细节。
```

## 测试要求

平时默认只跑：

```text
本节新增测试。
受影响的相邻测试。
git diff --check。
```

不默认跑全量测试。

只有在以下情况才扩大测试范围：

```text
改动跨多个核心模块。
影响共享接口或主流程。
测试失败需要排查。
用户要求跑全量测试。
准备上传 GitHub 前需要更完整检查。
```

测试讲解只讲重要测试点，不逐行解释测试代码。

## 手动验证和手动文档

纯知识点节默认不写手动测试文档。

只有涉及下面内容时，才考虑写 manual tasks 或手动验证说明：

```text
真实服务启动。
真实 API 调用。
curl 命令。
数据库。
Redis。
Docker。
Qdrant。
Milvus。
VMware Ubuntu。
本机 .env 配置。
IDEA / VS Code 手动运行。
```

如果用户愿意手动执行命令，用户贴出结果后，只需要判断结果、解释原因、指导下一步，不重复生成大量手动验证文档。

## README 和索引更新

默认不每节更新顶层 README。

默认不更新：

```text
projects/java-business-service/README.md
```

除非用户明确要求，或者该阶段确实发生重大结构变化。

可以更新：

```text
projects/ai-service/app/rag/README.md
docs/learning-progress.md
```

但也要控制范围，只记录当前节新增模块和进度。

## GitHub 上传约定

平时学习完成后：

```text
不自动提交。
不自动推送。
不自动做敏感扫描。
```

只有用户明确说：

```text
上传 GitHub
提交 GitHub
推送 GitHub
```

才执行：

```text
检查 git status。
做敏感信息扫描。
运行必要测试。
暂存相关文件。
提交。
推送。
```

上传时要注意不要把 `.env`、API Key、token、密码等敏感信息提交到仓库。

## 敏感信息扫描约定

平时不做敏感扫描。

上传 GitHub 前必须做敏感扫描。

重点检查：

```text
API Key
Authorization Bearer
sk- 开头的密钥
数据库密码
Redis 密码
.env 文件
真实 token
私钥
```

## 中文乱码判断约定

如果在 PowerShell 输出里看到中文乱码，优先怀疑：

```text
PowerShell 输出编码显示 UTF-8 中文时出了问题。
```

不要立刻误判为文件内容真的坏了。

除非通过更可靠方式确认文件本身确实乱码，否则不要做大范围编码修复。

## 虚拟机和外部服务约定

如果下一节需要：

```text
VMware Ubuntu
Docker
Qdrant
Milvus
Redis
MySQL
真实模型 API
```

开始前要明确告诉用户是否需要打开虚拟机或启动服务。

如果本节不需要，就不要让用户额外启动服务。

## 每节默认流程

默认按这个节奏执行：

```text
1. 简短说明本节要做什么。
2. 只读取本节必要文件。
3. 实现最小但完整的代码或文档改动。
4. 编写高质量学习笔记。
5. 更新必要索引和学习进度。
6. 运行本节相关测试和 git diff --check。
7. 简短总结产出、测试结果、下一节主题。
```

## 最终总结格式

每节完成后的最终回复尽量简洁，只包含：

```text
本节完成了什么。
新增/修改的关键文件路径。
测试结果。
是否提交/推送。
下一节是什么。
```

不重复整节笔记内容。

## 后续维护

如果用户对学习方式提出新要求，应优先更新本文档。

比如：

```text
笔记变薄了。
基础知识铺垫不够。
代码讲解太多。
测试讲解太细。
生成速度太慢。
需要减少某类文档。
```

这类长期规则都应该记录到本文档，避免后续忘记。
