# 阶段 11：完整智能工单系统项目化范围与真实化标准

## 1. 文档目的

阶段 11 的目标不是继续零散学习单个技术点，而是把已经学过的 Java、Python、AI、RAG、Agent、MCP、MySQL、Redis、向量数据库和生产化能力整合成一个完整项目。

这个文档用于固定阶段 11 的项目边界：

- 这个系统面向谁。
- 要做哪些业务功能。
- 哪些链路必须使用真实组件。
- 哪些能力可以后续扩展。
- 前端、Java 服务、Python AI 服务、数据库、Redis、向量库、模型分别负责什么。
- 阶段 11 做完后，如何判断这个项目已经达到“完整简历项目 / 作品项目”的标准。

后续开发时，如果出现“要不要加这个功能”“这个地方该不该真实化”“这个是不是阶段 11 范围内”的问题，优先回到这份文档判断。

## 2. 项目定位

项目名称暂定：

```text
AI 客服与智能工单系统
```

项目定位：

```text
一个面向电商/售后客服场景的 AI 应用系统。它用 Java Spring Boot 承载真实业务数据和工单流程，用 Python FastAPI 承载 LLM、RAG、Tool Calling 和 Agent 编排，用前端提供客服工作台和管理页面，让用户可以通过 AI 完成知识问答、订单查询、工单创建、工单跟进和人工处理。
```

项目不是简单聊天机器人，也不是只调用大模型 API 的 demo。

它要体现三类能力：

- 传统后端能力：用户、订单、工单、权限、数据库、缓存、接口契约。
- AI 应用能力：LLM、RAG、embedding、rerank、Tool Calling、Agent 编排。
- 工程化能力：配置、日志、trace_id、测试、评估、安全、限流、降级、部署和演示。

## 3. 阶段 11 的真实化标准

阶段 11 默认尽量使用真实组件。

这里的“真实”不是指必须达到大厂生产规模，而是指核心链路不能只停留在假数据、mock 逻辑或脚本演示。

### 3.1 必须真实化

| 类型 | 真实化标准 |
| --- | --- |
| 前端 | 有真实页面，用户能在浏览器里完成核心操作 |
| Java 后端 | 使用真实 Spring Boot 服务，而不是 mock service |
| 数据库 | 使用真实 MySQL 保存用户、订单、工单、知识库配置等业务数据 |
| Redis | 用于真实缓存、幂等、限流或会话辅助能力 |
| Python AI 服务 | 使用真实 FastAPI 服务承载 AI 接口 |
| LLM | 使用真实兼容 OpenAI API 的模型调用 |
| Embedding | 使用真实 embedding 模型生成向量 |
| Rerank | 使用真实 rerank 模型对候选文档排序 |
| 向量数据库 | 优先使用真实 Qdrant；Milvus 保留为对比或可选扩展 |
| RAG 数据 | 使用真实项目知识文档入库，而不是只写死几条字符串 |
| Tool 调用 | Python 通过受控 client 调用 Java 真实业务接口 |
| 配置 | 使用 `.env` / 环境变量区分本地配置和密钥 |
| 演示 | 能用一套步骤跑通前端到 AI、Java、MySQL、Redis、向量库的主链路 |

### 3.2 可以先简化

| 类型 | 简化原则 |
| --- | --- |
| 用户登录 | 可以先做本地账号密码登录，不急着接企业 SSO |
| 权限模型 | 先做角色和资源范围，不做复杂组织架构 |
| 支付/短信/邮件 | 暂不接真实第三方服务，必要时预留接口 |
| 大规模并发 | 不做压测平台，先保证本地和小规模演示稳定 |
| CI/CD | 可先做本地脚本和部署说明，后续再接 GitHub Actions |
| Kubernetes | 阶段 11 不强制做，Docker Compose 足够 |
| 企业级监控平台 | 先保留指标、日志、Runbook 和本地验证，后续可接 Prometheus/Grafana |

## 4. 目标用户和角色

阶段 11 先设计 4 类角色。

### 4.1 普通客户

普通客户关注：

- 查询订单状态。
- 询问退款、退货、物流、账号安全等政策。
- 创建售后工单。
- 查看自己提交的工单进度。

客户不应该看到：

- 其他用户订单。
- 内部工单处理备注。
- AI 工具调用细节。
- 系统 prompt、内部错误、密钥、调试信息。

### 4.2 客服人员

客服人员关注：

- 查看分配给自己的工单。
- 查看用户订单和历史沟通。
- 使用 AI 辅助总结用户问题。
- 回复用户或更新工单状态。
- 将问题升级给主管。

客服人员可以看到部分业务信息，但仍然受权限限制。

### 4.3 客服主管 / 运营管理员

主管或运营管理员关注：

- 查看工单列表和统计。
- 分配工单。
- 管理知识库文档。
- 查看 AI 处理效果。
- 查看 bad case 和评估结果。
- 调整部分运营配置。

### 4.4 系统管理员

系统管理员关注：

- 用户和角色管理。
- 服务运行配置。
- 模型配置。
- 系统日志和关键运行状态。
- 部署、密钥和环境变量。

阶段 11 不需要把管理员做得过重，但要保留清晰扩展空间。

## 5. 核心业务模块

阶段 11 的完整项目至少包含以下模块。

### 5.1 用户与权限模块

目标：

- 支持用户登录。
- 区分客户、客服、主管、管理员。
- 后端根据当前用户身份控制数据访问范围。

最小功能：

- 登录。
- 获取当前用户信息。
- 基于角色控制菜单和接口权限。
- 客户只能访问自己的订单和工单。
- 客服只能访问有权限处理的工单。

### 5.2 订单模块

目标：

- 提供真实订单数据。
- 支持 AI 工具查询订单。
- 支持前端查看订单详情。

最小功能：

- 订单列表。
- 订单详情。
- 根据订单号查询订单。
- 订单归属用户校验。

订单数据可以用初始化 SQL 提供一批演示数据，但查询必须走真实数据库。

### 5.3 工单模块

目标：

- 支持用户创建售后工单。
- 支持客服处理工单。
- 支持 AI Agent 根据用户描述辅助创建工单。

最小功能：

- 创建工单。
- 工单列表。
- 工单详情。
- 工单状态流转。
- 工单事件记录。
- 幂等创建。
- 关联订单。

建议状态：

```text
OPEN
IN_PROGRESS
WAITING_USER
RESOLVED
CLOSED
CANCELLED
```

### 5.4 知识库模块

目标：

- 管理客服知识文档。
- 支持真实 embedding 入库。
- 支持 RAG 检索问答。

最小功能：

- 知识文档列表。
- 文档详情。
- 文档启用/停用。
- 文档入库状态。
- 支持重新入库。
- 支持按业务域检索，如退款、物流、账号安全、内部 SOP。

阶段 11 可以先使用 Markdown 文档作为知识源，但入库和检索要走真实向量数据库。

### 5.5 AI 对话模块

目标：

- 提供用户可见的 AI 客服入口。
- 支持普通问答、RAG 问答、订单查询、工单创建。

最小功能：

- AI 对话页面。
- 普通聊天。
- RAG 知识库问答。
- 查询订单工具调用。
- 创建工单工具调用。
- 工单创建前确认。
- 流式输出可选。
- 展示引用来源。
- 展示必要的安全拒答。

### 5.6 AI 运营与评估模块

目标：

- 让项目不只是“能回答”，还要能观察回答质量。

最小功能：

- 查看评测集。
- 查看评测结果摘要。
- 查看 bad case 列表。
- 标记 bad case 状态。
- 查看生产化指标文档或简化看板。

这部分可以先做轻量前端页面，不急着接复杂监控平台。

## 6. 前端页面范围

阶段 11 必须做真实前端。

前端固定技术栈：

```text
Vue3 + TypeScript + Vite + Element Plus
Vue Router + Pinia + Axios
```

选择原因：

- 这套技术更贴近你熟悉的前后端分离后台项目开发方式。
- Element Plus 适合表格、表单、弹窗、分页、菜单、工单详情和配置页面。
- Vue3 + Vite 本地开发速度快，适合阶段 11 快速做出真实工作台。

建议页面：

| 页面 | 使用者 | 说明 |
| --- | --- | --- |
| 登录页 | 全部角色 | 输入账号密码登录 |
| AI 客服对话页 | 客户 | 提问、查订单、创建工单、查看引用来源 |
| 我的订单页 | 客户 | 查看自己的订单 |
| 我的工单页 | 客户 | 查看自己创建的工单 |
| 工单工作台 | 客服 | 查看、处理、更新工单 |
| 工单详情页 | 客服/客户 | 根据角色展示不同信息 |
| 知识库管理页 | 主管/管理员 | 查看文档、触发入库、管理业务域 |
| AI 评估与 bad case 页 | 主管/管理员 | 查看评估结果和坏例 |
| 系统配置页 | 管理员 | 查看模型和服务配置摘要，不展示密钥原文 |

前端风格应该偏工作台，而不是营销落地页。

也就是说：

- 信息密度适中。
- 操作入口清晰。
- 页面适合反复使用。
- 不做花哨的宣传首页。

## 7. 系统边界

阶段 11 继续保持清晰边界。

```text
前端
-> 调 Java 业务 API
-> 调 Python AI API

Python AI 服务
-> 调 LLM / embedding / rerank
-> 调 Qdrant
-> 通过 Java client 调 Java 内部接口

Java 业务服务
-> 管用户、订单、工单、权限、MySQL、Redis
```

### 7.1 前端职责

前端负责：

- 页面展示。
- 表单输入。
- 调用后端接口。
- 展示加载、错误、空状态。
- 展示 AI 回答、引用来源和工单状态。

前端不负责：

- 判断用户是否有权访问订单。
- 直接调用数据库。
- 保存密钥。
- 自己拼接 AI 工具调用。

### 7.2 Java 服务职责

Java 服务负责传统业务：

- 用户身份。
- 角色权限。
- 订单数据。
- 工单数据。
- 工单状态流转。
- 幂等。
- Redis 缓存和限流。
- MySQL 持久化。
- 面向 Python AI 服务的内部 API。

Java 服务是业务事实来源。

### 7.3 Python AI 服务职责

Python AI 服务负责 AI 能力：

- LLM 调用。
- RAG 检索问答。
- embedding。
- rerank。
- Agent 编排。
- Tool Calling。
- AI 安全边界。
- AI 评估和 bad case。
- 调用 Java 内部 API。

Python AI 服务不能绕过 Java 服务直接写业务表。

### 7.4 向量数据库职责

向量数据库负责：

- 保存知识文档 chunks 的向量。
- 支持相似度检索。
- 支持 metadata filter。
- 为 RAG 提供候选上下文。

向量数据库不是业务数据库。

订单、工单、用户不应该只存在向量库里。

## 8. 关键业务流程

### 8.1 用户知识库问答

```text
客户输入政策问题
-> 前端调用 Python AI 服务
-> Python 做安全检查
-> Python 判断需要 RAG
-> Python 改写/路由查询
-> embedding 生成查询向量
-> Qdrant 检索候选 chunks
-> rerank 重新排序
-> 引用来源校验
-> LLM 基于上下文生成回答
-> 前端展示答案和引用来源
```

### 8.2 用户查询订单

```text
客户输入“帮我查 A1001 的物流”
-> Python AI 服务识别工具意图
-> 模型请求 query_order
-> 后端校验工具名和参数
-> Python 调 Java 内部订单接口
-> Java 校验用户身份和订单归属
-> Java 从 MySQL 查询订单
-> Java 返回白名单字段
-> Python 让模型总结成用户可读回答
-> 前端展示结果
```

### 8.3 用户创建工单

```text
客户描述问题
-> Python Agent 提取工单字段
-> 如果字段不足，追问
-> 如果字段完整，生成待确认工单草稿
-> 用户确认
-> Python 调 Java 创建工单接口
-> Java 校验权限、幂等、订单关系
-> Java 写入 tickets 和 ticket_events
-> Python 返回创建结果
-> 前端展示工单编号和状态
```

### 8.4 客服处理工单

```text
客服登录
-> 查看工单工作台
-> 打开工单详情
-> 查看用户问题、订单、AI 摘要、事件记录
-> 更新状态或回复
-> Java 写入工单事件
-> 用户在前端看到状态变化
```

### 8.5 知识库更新入库

```text
管理员上传或维护 Markdown 文档
-> Java 或前端记录知识库元信息
-> Python 读取文档内容
-> 文档切分 chunks
-> 真实 embedding 生成向量
-> 写入 Qdrant
-> 更新入库状态
-> RAG 问答使用新知识
```

## 9. 数据模型范围

阶段 11 初版建议包含这些核心表。

### 9.1 Java MySQL 业务表

建议表：

- `users`
- `roles`
- `user_roles`
- `orders`
- `order_items`
- `tickets`
- `ticket_events`
- `ticket_assignments`
- `knowledge_documents`
- `ai_conversations`
- `ai_messages`

不一定第一节就全部建完，但最终完整项目应该覆盖这些方向。

### 9.2 Python AI 侧数据

Python AI 服务可以保留：

- evaluation datasets。
- bad cases。
- RAG 文档处理结果。
- AI 运行配置。

如果数据属于核心业务，例如订单和工单，应该归 Java 和 MySQL 管。

## 10. 外部真实资源需求

阶段 11 会按需提醒你准备真实资源。

预计需要：

| 资源 | 用途 | 何时需要 |
| --- | --- | --- |
| LLM API Key | 普通聊天、工具总结、Agent 节点 | AI 主链路真实化时 |
| Embedding API Key | 文档入库和查询向量化 | 知识库真实入库时 |
| Rerank API Key | 检索候选重排 | RAG 检索质量提升时 |
| Qdrant | 向量检索 | RAG 主链路开始时 |
| MySQL | 业务数据 | Java 业务模块开始时 |
| Redis | 缓存、幂等、限流 | 登录/工单/限流开始时 |
| Node.js | 前端开发 | 前端项目创建时 |

当前第 1 节不需要注册新东西，不需要打开虚拟机。

## 11. 阶段 11 验收标准

阶段 11 完成后，至少要满足这些标准。

### 11.1 功能验收

- 用户可以登录。
- 用户可以在前端进行 AI 对话。
- 用户可以查看自己的订单。
- 用户可以通过 AI 查询订单。
- 用户可以通过 AI 创建工单。
- 客服可以查看和处理工单。
- 管理员可以查看知识库文档。
- RAG 可以基于真实向量库回答知识问题。
- AI 回答能展示引用来源。

### 11.2 技术验收

- 前端是真实项目。
- Java 服务使用 MySQL / Redis。
- Python 服务使用真实 LLM。
- RAG 使用真实 embedding 和 Qdrant。
- rerank 使用真实 rerank 模型。
- Python 调 Java 走真实 HTTP client。
- 密钥不进入 GitHub。
- 配置通过 `.env` 或环境变量管理。

### 11.3 工程验收

- 有运行说明。
- 有接口说明。
- 有数据库说明。
- 有演示脚本。
- 有关键测试或手动验证清单。
- 有简历表达材料。
- 有项目边界说明。

### 11.4 展示验收

别人看项目时，能在 5-10 分钟内理解：

- 这个系统解决什么问题。
- 前端、Java、Python、RAG、LLM 怎么协作。
- 为什么它不是简单模型套壳。
- 哪些地方体现真实后端经验。
- 哪些地方体现 AI 应用工程化能力。

## 12. 阶段 11 不做什么

为了避免项目范围失控，阶段 11 暂时不做：

- Kubernetes。
- 大规模压测平台。
- 企业 SSO。
- 支付、短信、邮件真实第三方接入。
- 复杂多租户计费。
- 模型微调。
- 自研向量数据库。
- 多 Agent 平台化。
- 完整商业 SaaS 运营后台。

这些不是没价值，而是不适合在当前阶段抢主线。

阶段 11 的主线是：

```text
把智能工单系统做成完整、真实、可运行、可演示、可写简历的项目。
```
