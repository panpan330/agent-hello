# 阶段 10 第 1 节：AI 应用生产化总览

## 本节定位

这是阶段 10 的第一节。

阶段 10 的主题是：

```text
AI 应用生产化与可运营能力
```

本节不写复杂代码。


## 一句话先讲透

AI 应用生产化，就是让一个会调用模型的功能，变成稳定、安全、可追踪、可评估、可控成本、可灰度上线、出问题能排查和回滚的真实工程系统。

## 基础知识铺垫

### 1. 什么是“生产化”

先不要急着把“生产化”等同于“部署到服务器”。

部署只是生产化的一部分。

生产化更完整的意思是：

```text
一个系统不只是在开发者电脑上能跑，而是能被真实用户长期使用，并且在失败、变慢、变贵、变危险、变复杂时，团队仍然能控制它。
```

传统后端系统生产化通常关注：

```text
服务能不能稳定启动
接口能不能承受流量
数据库连接是否稳定
缓存是否命中
错误是否能被捕获
日志是否能排查问题
权限是否正确
事务是否一致
接口是否有测试
上线失败能不能回滚
```

AI 应用也需要这些。

但 AI 应用还会多出一批新的问题：

```text
模型回答不稳定
模型 API 依赖外部服务
token 成本可能失控
上下文可能泄露敏感信息
Prompt Injection 可能改变模型行为
RAG 检索质量会影响回答
Agent 工具调用可能产生真实业务后果
流式输出中途失败时用户已经看到部分内容
评估质量不能只靠接口状态码
```

所以 AI 应用生产化不是一个小主题，而是一整套运行治理能力。

### 2. “能跑通”和“能上线”的区别

能跑通通常意味着：

```text
本地接口能启动。
手动请求能返回结果。
模型能给出看起来合理的回答。
主要流程能走完。
```

能上线至少意味着：

```text
请求失败时有清晰错误处理。
请求慢时有超时和降级。
请求多时有限流。
模型失败时有 fallback 或兜底。
日志能排查问题。
日志不泄露敏感内容。
成本能统计和限制。
质量能评测和回归。
权限边界能保证。
新版本能灰度和回滚。
出现故障时有 runbook。
```

这两者差距很大。

一个本地 demo 可以没有监控。
一个真实系统不行。

一个学习脚本可以失败后重新跑。
一个线上服务失败时，用户正在等结果。

一个手动测试可以只问三个问题。
一个真实 AI 应用需要评测集、bad case 回归和线上反馈。

### 3. 什么是“可运营”

生产化强调系统能上线。
可运营强调系统上线后能持续管理。

可运营包含：

```text
能观察：知道系统现在发生了什么。
能分析：知道问题出在哪一层。
能控制：能限制流量、成本和风险。
能调整：能切模型、改 prompt、改参数、灰度新版本。
能恢复：出问题后能降级、回滚、按 runbook 处理。
能复盘：把 bad case 和事故沉淀为测试、文档和改进项。
```

AI 应用尤其需要可运营。

原因是模型不是传统意义上的确定性函数。

同样的问题，不同模型、不同 prompt、不同上下文、不同检索结果，都可能导致不同回答。

如果没有运营能力，系统上线后只能靠“感觉”维护。

这会很危险。

### 4. AI 应用比传统后端多出来的风险

你有传统 Java 后端基础，所以可以先从对比理解。

传统后端接口通常是：

```text
请求参数
-> 业务逻辑
-> 数据库 / Redis
-> 明确响应
```

AI 应用可能是：

```text
用户自然语言
-> prompt 构造
-> RAG 检索
-> rerank
-> 上下文压缩
-> LLM 调用
-> Tool Calling
-> Agent 决策
-> Java 后端读写
-> 模型总结
-> 流式输出
```

链路更长，风险也更多。

主要多出来这些：

```text
不确定性：模型输出不是完全固定的。
外部依赖：模型 API、embedding API、rerank API 可能超时或限流。
成本变量：token、重试、rerank、embedding 都会产生费用。
上下文风险：塞给模型的内容可能包含隐私、密钥、无权文档。
注入风险：用户或文档可能诱导模型忽略系统规则。
工具风险：模型可能请求执行真实业务操作。
评估困难：HTTP 200 不代表答案正确。
排查困难：失败可能发生在 query、retrieval、rerank、prompt、model、tool、Java 后端任意一层。
```

这就是阶段 10 要补的内容。

### 5. 为什么 AI 应用不能只看 HTTP 状态码

传统接口里，`200` 通常表示请求成功。

AI 应用里，`200` 只能表示接口成功返回了一个响应。

但响应可能是：

```text
答案事实错误。
引用来源不匹配。
没有资料却强行回答。
用户无权限却泄露内容。
模型被 prompt injection 影响。
工具调用参数错了。
成本过高。
响应太慢。
回答语气不符合业务要求。
```

所以 AI 应用的“成功”要看更多维度：

```text
接口是否成功
回答是否正确
证据是否可信
权限是否正确
安全策略是否生效
耗时是否可接受
成本是否可接受
是否可追踪
是否可复现和回归
```

这也是为什么阶段 10 会继续学 tracing、评估、监控、告警和 runbook。

### 6. Tracing、日志、指标、评估分别解决什么

这几个词后面会详细学，本节先建立直觉。

日志解决：

```text
某次请求发生了什么。
```

Tracing 解决：

```text
某次请求经过了哪些阶段，每个阶段用了多久，在哪里失败。
```

指标解决：

```text
一段时间内整体表现怎么样。
例如请求量、错误率、平均耗时、P95 延迟、token 成本、fallback 次数。
```

评估解决：

```text
回答质量好不好，改动有没有让效果变好。
```

告警解决：

```text
系统异常时，是否能及时通知人处理。
```

它们不是一个东西。

简单记：

```text
日志看单点细节。
Tracing 看单次链路。
指标看整体趋势。
评估看回答质量。
告警看是否需要人介入。
```

### 7. 为什么成本是 AI 应用的一等问题

传统后端也有成本。
但 AI 应用的成本更容易随着请求内容变化。

一次 AI 请求的成本可能来自：

```text
LLM 输入 token
LLM 输出 token
embedding 调用
rerank 调用
多模型 fallback
失败重试
RAG 检索上下文过长
Agent 多轮工具调用
```

如果没有成本统计，你只知道系统在跑。
但你不知道：

```text
哪个接口最贵。
哪个用户最贵。
哪个模型最贵。
哪种场景最贵。
重试带来了多少额外成本。
上下文是不是塞太多。
```

所以阶段 10 会专门学 token 成本统计和成本控制。

### 8. 为什么稳定性不能只靠“模型质量”

模型质量好，不代表系统稳定。

系统可能因为这些原因失败：

```text
模型 API 超时。
模型 API 被限流。
网络抖动。
向量库响应慢。
rerank 服务失败。
Java 后端返回业务错误。
Redis 连接失败。
MySQL 慢查询。
SSE 连接中断。
用户重复提交写操作。
```

所以生产化要补：

```text
超时
重试
fallback
降级
限流
幂等
缓存
监控
告警
回滚
```

这些是后端工程的老问题，但在 AI 链路里会变得更复杂。

### 9. 为什么安全和隐私在 AI 应用里更敏感

AI 应用经常需要把数据放进 prompt。

这些数据可能包括：

```text
用户问题
用户身份
订单信息
工单内容
知识库片段
检索结果
工具返回
历史对话
```

如果不处理好，可能出现：

```text
日志记录了完整隐私内容。
错误信息暴露内部系统细节。
模型回答泄露无权数据。
prompt 中混入 API Key。
知识库文档诱导模型忽略安全规则。
工具调用绕过权限和确认。
```

所以阶段 10 会继续强化：

```text
日志脱敏
密钥管理
权限控制
Prompt Injection 防护
模型输出安全
隐私保护
```

### 10. 灰度和回滚为什么对 AI 应用很重要

AI 应用的“版本”不只是代码。

这些东西都可能是版本：

```text
Prompt
模型
RAG 参数
rerank 开关
score_threshold
top_k
多模型路由规则
安全策略
工具描述
知识库数据
```

修改一行 prompt，可能让某些回答变好，也可能让另一些回答变差。

所以不能每次都直接全量上线。

真实项目里更稳的方式是：

```text
小流量灰度
观察指标
收集 bad case
确认没有明显回归
逐步扩大
出问题能快速回滚
```

这也是阶段 10 后面要学灰度发布与回滚的原因。

### 11. Runbook 是什么

Runbook 可以理解为故障处理手册。

它不是理论文档。
它是系统出问题时，值班人员按步骤执行的排查和恢复说明。

例如：

```text
如果模型错误率突然升高，先看模型 provider 状态，再看 fallback 是否生效，再看最近是否切换模型或 prompt。
如果 RAG 无资料率突然升高，先看向量库是否可用，再看入库任务是否失败，再看 metadata filter 是否过严。
如果 token 成本突然升高，先看请求量、平均输入 token、输出 token、重试次数和是否开启了高成本模型。
```

Runbook 的价值是：

```text
出问题时不靠临时猜，而是按已知路径排查。
```

对初学者来说，理解 Runbook 会让你更接近真实工程视角。

### 12. AI 应用生产化成熟度可以分几层

生产化不是只有“没上线”和“已上线”两种状态。

更适合按成熟度分层理解：

| 层级 | 状态 | 特点 |
| --- | --- | --- |
| Demo | 演示可用 | 本地能跑，流程能走通，主要靠人工观察效果 |
| Internal Alpha | 内部试用 | 小范围使用，有基础日志和错误处理，但评估、成本、告警还不完整 |
| Project v1 | 简历级完整项目 | 真实服务、真实数据库、真实模型、RAG/Agent 主链路、测试、文档、演示基本齐全 |
| Production Ready | 可上线版本 | 有 tracing、监控、告警、限流、超时、fallback、成本统计、安全策略、灰度回滚 |
| Operated System | 可持续运营系统 | 能持续收集 bad case、做评测回归、看成本趋势、优化模型和策略、按 runbook 处理故障 |

你现在的项目大致已经具备：

```text
Project v1 的基础能力
```

阶段 10 要继续补的是：

```text
Production Ready 和 Operated System 方向的能力
```

这不代表马上要做成商业公司全量生产系统。
它代表你要开始理解真实生产系统需要哪些工程控制点。

### 13. 什么叫“最小可生产化标准”

不是所有项目一开始都要做到大厂级平台。

但一个 AI 应用如果想从 demo 走向真实项目，至少要有一个最小标准。

可以先记这 10 条：

```text
1. 有清晰配置管理，密钥不进代码库。
2. 有统一 trace_id，能串起一次请求。
3. 有安全日志，能排查但不泄露隐私。
4. 有超时，不能无限等待模型或外部服务。
5. 有错误处理，不能把内部异常直接暴露给用户。
6. 有成本统计，知道 token 和模型调用成本。
7. 有限流或基本保护，避免单用户拖垮系统。
8. 有评测集，能判断改动有没有质量回归。
9. 有灰度或开关，重要策略不能直接全量硬切。
10. 有回滚和故障处理说明，出问题知道怎么恢复。
```

这 10 条不是终点，但可以作为学习阶段判断项目是否足够完整的底线。

对于简历项目来说，如果你能讲清楚这些，项目可信度会明显提高。

### 14. AI 应用上线前、上线中、上线后分别关注什么

生产化要按生命周期看。

上线前关注：

```text
功能是否完整
评测是否通过
权限是否正确
Prompt Injection 是否有防护
成本是否估算
超时和 fallback 是否设计
日志是否脱敏
灰度和回滚方案是否准备
```

上线中关注：

```text
灰度流量比例
错误率
延迟
token 消耗
fallback 次数
用户反馈
bad case 数量
是否出现安全拦截
```

上线后关注：

```text
长期质量趋势
成本趋势
用户使用分布
高频失败原因
新增 bad case 是否进入评测集
知识库和 prompt 是否需要更新
runbook 是否需要补充
```

所以生产化不是上线那一天的事。

更准确地说：

```text
上线前是准备。
上线中是控制风险。
上线后是持续运营和改进。
```

### 15. AI 应用的风险矩阵怎么理解

真实项目里，风险不能只按“有没有 bug”来判断。

AI 应用常见风险可以按两个维度看：

```text
发生概率
影响程度
```

例如：

| 风险 | 发生概率 | 影响程度 | 处理优先级 |
| --- | --- | --- | --- |
| 模型偶尔答得不够好 | 中 | 中 | 用评测和 bad case 回归持续优化 |
| 模型 API 超时 | 中 | 高 | 必须有超时、fallback、降级 |
| 日志泄露 API Key | 低 | 极高 | 必须提前防护，不能等发生 |
| 用户看到无权数据 | 低到中 | 极高 | 权限过滤必须作为上线阻断项 |
| token 成本突然升高 | 中 | 高 | 要有成本统计、限额和告警 |
| Prompt Injection 诱导工具调用 | 中 | 高 | 要有工具权限、确认和安全策略 |

这张表说明一件事：

```text
有些问题即使发生概率不高，也必须提前防，因为影响太大。
```

这也是为什么安全、权限、密钥、写操作确认不能等上线后再补。

## 本节主题系统讲解

### 1. 阶段 10 的核心问题

阶段 10 的核心问题可以概括成一句：

```text
如何让 AI 应用从“功能可用”变成“系统可运营”。
```

功能可用关注：

```text
能不能回答。
能不能检索。
能不能调用工具。
能不能创建工单。
```

系统可运营关注：

```text
出了问题能不能定位。
变慢能不能发现。
成本升高能不能控制。
质量变差能不能评估。
风险请求能不能拦住。
新版本能不能灰度。
上线失败能不能回滚。
故障发生能不能按步骤恢复。
```

这就是阶段 10 和前面阶段的区别。

### 2. 当前项目已经具备的基础

你当前项目已经不是从零开始。

已有基础包括：

```text
FastAPI AI 服务
Java Spring Boot 业务服务
MySQL / Redis
LLM API 调用
Structured Output
Tool Calling
LangGraph Agent
RAG
Qdrant / Milvus
MCP
trace_id 基础
错误码基础
幂等基础
RAG 评测基础
可观测事件基础
生产化验收清单基础
```

这些是阶段 10 的地基。

阶段 10 不是推翻重做，而是继续往上补：

```text
更系统的 tracing
更安全的日志
更完整的成本统计
更明确的限流、重试、超时、fallback
更接近生产的 SSE
更完整的安全和隐私边界
更持续的自动化评估和 bad case 回归
更明确的监控、告警、灰度、回滚和 runbook
```

### 3. 阶段 10 的 28 节可以分成六组

不要把 28 节看成零散知识。

可以分成六组：

```text
可追踪：1-6
可控成本和性能：7-15
可用体验：16-17
安全边界：18-20
质量评估：21-23
线上运营：24-28
```

对应关系：

| 分组 | 节 | 重点 |
| --- | --- | --- |
| 可追踪 | 1-6 | 生产化总览、Tracing、trace/span/event/metric、Python/Java 链路、LLM 日志安全 |
| 可控成本和性能 | 7-15 | 配置密钥、token 成本、耗时拆解、多模型路由、fallback、成本控制、限流、重试、超时 |
| 可用体验 | 16-17 | SSE 流式输出、流式错误和中断 |
| 安全边界 | 18-20 | Prompt Injection、权限控制、隐私和安全输出 |
| 质量评估 | 21-23 | 自动化评估、评测集版本、Bad Case 回归 |
| 线上运营 | 24-28 | 监控指标、告警、灰度回滚、SLO/SLA/Runbook、面试表达 |

这样理解阶段 10，会比背目录更清晰。

### 4. 一次真实 AI 请求的生产化视角

假设用户问：

```text
我的订单 A1001 物流一直没更新，能帮我看看吗？
```

功能视角只会看：

```text
模型是否理解问题。
是否调用订单或物流工具。
是否返回回答。
```

生产化视角还会看：

```text

是否触发了 fallback？
是否包含敏感字段？

总耗时是否超过阈值？
如果失败，用户看到的错误是否安全？
这次 bad case 是否要进入评测集？
```

这就是生产化思维。

同一个功能，关注层次完全不同。

### 10. 阶段 10 在当前项目里的落地顺序

阶段 10 不会一次性把所有生产化能力都塞进项目。

更合理的落地顺序是：

```text
先让问题能被看见。
再让问题能被控制。
再让质量能被评估。
最后让上线和故障处理可管理。
```

对应到项目里：

```text
Tracing / 日志安全
-> 成本统计 / 耗时拆解
-> fallback / 限流 / 重试 / 超时
-> SSE 生产化
-> 安全和权限强化
-> 自动化评估和 bad case 回归
-> 监控告警
-> 灰度回滚
-> SLO / SLA / Runbook
```

为什么这样排？

因为如果系统没有 tracing 和日志，你连问题在哪里都不知道。
如果没有成本和耗时统计，你不知道系统贵在哪里、慢在哪里。
如果没有超时、fallback、限流，系统遇到外部失败时就只能硬失败。
如果没有评估和 bad case 回归，改动好坏只能靠感觉。
如果没有监控告警和 runbook，上线后出问题就靠临场发挥。

### 12. 阶段 10 每类能力的判断标准

学阶段 10 时，不要只问“代码写了吗”。

更应该问：

| 能力 | 判断标准 |
| --- | --- |
| Tracing | 一次请求失败时，能否看到经过哪些阶段、每阶段耗时、失败原因 |
| 日志安全 | 日志是否能排查问题，同时不暴露密钥、隐私、完整 prompt 和敏感工具结果 |
| 成本统计 | 能否按请求、用户、模型、接口统计 token 和大致成本 |
| 耗时拆解 | 能否知道慢在 LLM、RAG、rerank、Tool 还是 Java 后端 |
| fallback | 主模型失败时是否有明确备用策略，且输出契约仍然稳定 |
| 限流 | 单个用户或接口异常流量是否会被限制 |
| 重试 | 是否只对安全可重试场景重试，写操作是否有幂等保护 |
| 超时 | 是否有总超时和分阶段超时，避免请求无限挂住 |
| 安全 | Prompt Injection、权限、隐私、工具调用是否有系统侧边界 |
| 评估 | 改动后是否能通过评测集判断有没有回归 |
| 监控告警 | 关键错误、成本、延迟、fallback、限流是否能被发现 |
| 灰度回滚 | 新 prompt、新模型、新参数是否能小流量验证并快速回退 |

这张表是阶段 10 的学习标尺。

以后每学一节，都要能把它放回这张表里。


不需要一开始就做复杂账单系统。

```text

```

## 常见误区

### 误区 1：生产化就是部署上线

不对。

部署只是把服务放到运行环境。
生产化还包括稳定性、安全、可观测性、成本、评估、灰度、回滚和故障处理。

### 误区 2：AI 应用只要模型好就稳定

不对。

模型质量只是其中一部分。
系统还依赖网络、模型服务、向量库、Java 后端、Redis、MySQL、prompt、RAG 数据和工具调用。

### 误区 3：接口返回 200 就代表 AI 回答成功

不对。

AI 接口 `200` 只说明接口返回了内容。
回答可能仍然事实错误、引用错误、越权、成本过高或被注入影响。

### 误区 4：日志越详细越好

不对。

AI 应用日志如果记录完整 prompt、用户隐私、订单信息、API Key 或工具结果，可能带来严重泄露风险。
日志要足够排查，但必须脱敏和控制范围。

### 误区 5：重试总能提高成功率

不一定。

读操作遇到短暂网络失败可以考虑重试。
写操作如果没有幂等保护，重试可能造成重复创建工单、重复扣费、重复提交。

### 误区 6：fallback 就是失败后随便换个模型

不对。

fallback 要考虑任务类型、成本、质量、安全和输出格式。
备用模型也必须符合接口契约和业务边界。

### 误区 7：灰度发布只适用于代码

不对。

AI 应用里的 prompt、模型、RAG 参数、rerank 开关、多模型路由规则、安全策略都可能需要灰度。

### 误区 8：评估只在开发阶段有用

不对。

上线后更需要评估。
线上 bad case 应该进入评测集，形成回归测试，防止问题反复出现。

### 误区 9：生产化能力一定要等项目很大才需要

不对。

越早建立基本生产化意识，后面越不容易返工。

小项目不一定要做复杂平台，但可以先做最小版本：

```text
trace_id
日志脱敏
超时
成本统计
基础限流
评测集
错误兜底
回滚说明
```

这些能力不会让项目变复杂太多，但会显著提高项目可信度。

### 误区 10：只要有测试，就等于有评估

不完全对。

测试主要验证：

```text
代码逻辑是否符合预期。
接口契约是否稳定。
异常分支是否被处理。
```

评估更关注：

```text
模型回答是否正确。
RAG 证据是否匹配。
拒答是否合理。
质量有没有回归。
```

AI 项目通常既需要测试，也需要评估。

### 误区 11：生产化就是后端工程师的事，和 AI 无关

不对。

AI 应用生产化既包含后端工程能力，也包含 AI 特有风险。

例如：

```text
token 成本
prompt 版本
模型 fallback
RAG 检索质量
Prompt Injection
上下文隐私
LLM-as-judge 或自动化评估
```

这些不是纯传统后端问题。

所以后端 AI 工程师要能把两边结合起来。

### 误区 12：生产化学习会拖慢做项目

短期看，确实会多写一些日志、测试、文档和保护逻辑。

但长期看，它是在减少返工。

如果没有 tracing，后面一次复杂 bug 可能排查很久。
如果没有评测集，改 prompt 后不知道有没有破坏旧问题。
如果没有成本统计，流量上来后才发现账单失控。
如果没有权限和日志脱敏，安全问题可能直接变成严重事故。

所以生产化不是额外负担，而是让项目能继续变大的基础。

## 自测题

### 自测 1：生产化和部署有什么区别？

答案：

部署是把服务放到运行环境。
生产化是让系统能长期稳定、安全、可观测、可评估、可控成本地被真实用户使用，并且支持灰度、回滚和故障处理。

### 自测 2：可运营是什么意思？

答案：

可运营是指系统上线后能被持续观察、分析、控制、调整、恢复和复盘。
例如能看日志、trace、指标，能控制成本和流量，能发现质量下降，能处理故障并沉淀 bad case。

### 自测 3：为什么 AI 应用要特别关注日志安全？

答案：

因为 AI 应用日志可能包含用户问题、历史对话、知识库片段、工具结果、订单信息、模型输入输出甚至密钥。
如果完整记录，可能泄露隐私、业务数据或系统内部信息。

### 自测 4：阶段 10 为什么要学成本控制？

答案：

因为 AI 应用成本和 token、模型、embedding、rerank、重试、fallback、上下文长度、Agent 多轮调用有关。
如果不统计和限制，流量上来后成本可能快速失控。

### 自测 5：为什么灰度和回滚对 AI 应用重要？

答案：

因为 AI 应用的 prompt、模型、RAG 参数、路由策略、安全策略都会影响输出质量。
直接全量上线风险大，灰度可以小范围观察，回滚可以在出问题时快速恢复。

### 自测 6：阶段 10 学完后，你的项目表达应该提升在哪里？

答案：

不再只说“我做过 RAG / Agent / LLM 调用”，而是能说：

```text
我知道 AI 应用上线后如何做 tracing、日志安全、token 成本统计、耗时拆解、多模型路由、fallback、限流、重试、超时、SSE 流式输出、安全防护、自动化评估、bad case 回归、监控告警、灰度回滚和 runbook。
```
