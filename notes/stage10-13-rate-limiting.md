# 阶段 10 第 13 节：限流

## 本节定位

这一节学习 AI 应用生产化里的限流。

前面第 12 节学的是成本控制，它关心：

```text
单次请求预计会消耗多少 token 或多少钱。
```

这一节学的限流关心：

```text
单位时间内允许多少请求通过。
```

两者都是生产系统的保护能力，但保护的角度不同。

## 本节学习目标

- 理解什么是限流，为什么 AI 应用更需要限流。
- 理解限流和成本控制、权限控制、超时、重试的区别。
- 理解 429、Retry-After、X-RateLimit-* 响应头。
- 理解固定窗口、滑动窗口、令牌桶、漏桶的基本思想。
- 理解用户级、接口级、AI 路由级、工具级限流。
- 理解为什么本节先用内存限流，为什么真实生产通常会用 Redis、网关或专门限流组件。
- 看懂本节新增的 `rate_limit.py`、`rate_limit` middleware 和对应测试。

## 本节新增和修改

- 新增 `app/core/rate_limit.py`。
- 新增 `app/middleware/rate_limit.py`。
- 修改 `app/main.py`，注册限流中间件。
- 修改 `config.py`、`.env.example`、配置安全快照。
- 新增 `tests/test_rate_limit.py`，补充配置相关测试。

## 一句话先讲透

限流就是在请求进入业务逻辑之前，按用户、接口或功能维度计数，如果短时间请求太多，就直接返回 429，让系统、模型额度、数据库和下游服务不被高频请求打满。

## 基础知识铺垫

### 1. 什么是限流

限流的英文通常叫：

```text
Rate Limiting
```

它的核心问题是：

```text
在一段时间内，最多允许多少请求通过？
```

例如：

```text
同一个用户每分钟最多 60 次 AI 对话。
同一个 IP 每分钟最多 120 次请求。
同一个工具接口每分钟最多 30 次调用。
同一个租户每天最多 10000 次模型请求。
```

当超过限制时，系统不继续执行业务逻辑，而是直接返回错误。

最常见的状态码是：

```text
429 Too Many Requests
```

它的含义是：

```text
你请求得太频繁了，请稍后再试。
```

### 2. AI 应用为什么更需要限流

传统后端也需要限流，比如防止登录接口被爆破、防止短信接口被刷、防止数据库被压垮。

AI 应用更需要限流，因为一次 AI 请求背后可能不只是一次普通 HTTP 处理。

它可能包含：

```text
调用大模型
生成 embedding
检索向量数据库
调用 rerank 模型
执行工具调用
调用 Java 业务服务
发起多轮 Agent Loop
触发 fallback
触发重试
流式输出占用连接
```

也就是说，用户看起来只是点了一次发送，但系统内部可能发生多次昂贵操作。

如果没有限流，风险包括：

```text
模型额度被快速耗尽
账单异常增加
QPS 超过模型供应商限制
Java 后端被 AI 服务打满
向量数据库被高频查询打满
Redis/MySQL 连接被耗尽
SSE 长连接过多
正常用户被异常流量挤掉
```

所以限流不是锦上添花，而是生产 AI 应用的基本保护层。

### 3. 限流和成本控制的区别

第 12 节的成本控制回答：

```text
这一次请求预计贵不贵？
```

第 13 节的限流回答：

```text
这段时间请求次数多不多？
```

举例：

```text
用户 1 分钟请求 1 次，但一次输入 10 万字。
```

这不是高频请求，但单次请求可能很贵，所以需要成本控制。

再比如：

```text
用户每秒请求 20 次，每次问题都很短。
```

每次都不贵，但请求频率很高，所以需要限流。

生产系统通常两者都要有：

```text
成本控制管单次消耗。
限流管单位时间请求数量。
```

### 4. 限流和权限控制的区别

权限控制回答：

```text
你有没有资格做这件事？
```

限流回答：

```text
你做这件事的频率是不是太高？
```

一个用户可能有权限调用 `/tool-chat`，但如果一分钟调用 1000 次，仍然应该被限流。

反过来，一个用户请求频率很低，但没有权限访问某个订单，也必须被权限控制拒绝。

它们的典型顺序可以理解为：

```text
认证：你是谁？
权限：你能不能做？
限流：你做得是不是太频繁？
业务：真正执行。
```

实际中间件顺序会根据系统设计调整，但概念上一定要分清。

### 5. 限流和超时、重试的关系

超时回答：

```text
这次请求最多等多久？
```

重试回答：

```text
失败后是否再试一次？
```

限流回答：

```text
短时间内是否允许继续请求？
```

它们之间会互相影响。

例如：

```text
系统超时太长，会导致并发请求堆积。
重试次数太多，会放大请求量。
没有限流，重试风暴可能把下游服务打满。
```

所以后续学习重试时，必须记住一个原则：

```text
重试会增加请求次数，限流要能防住重试带来的放大效应。
```

### 6. 什么是 429

HTTP 429 的完整含义是：

```text
Too Many Requests
```

它不是业务失败，不是参数错误，也不是服务器崩了。

它表示：

```text
请求格式可能正确，用户也可能有权限，但请求频率超过了系统允许范围。
```

常见响应类似：

```json
{
  "success": false,
  "code": "RATE_LIMITED",
  "message": "请求过于频繁，请稍后重试。",
  "data": null,
  "trace_id": "..."
}
```

429 的好处是语义明确。前端、客户端、网关、SDK 都能理解：

```text
不是立刻疯狂重试，而是等一会儿。
```

### 7. Retry-After 是什么

`Retry-After` 是一个响应头。

它告诉客户端：

```text
建议等多少秒以后再试。
```

例如：

```text
Retry-After: 18
```

意思是：

```text
18 秒后再请求更合适。
```

没有 `Retry-After`，客户端只能猜什么时候重试。真实项目里，这会导致客户端不断试探，反而增加系统压力。

### 8. X-RateLimit-* 响应头是什么

很多系统会返回额外的限流响应头，让客户端更清楚当前限制状态。

本节新增了：

```text
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset-After
X-RateLimit-Scope
```

它们分别表示：

```text
本窗口最多允许多少次。
本窗口还剩多少次。
距离窗口重置还有多少秒。
是哪一种限流命中，例如 client、route、ai、tool。
```

这些响应头不仅方便前端做提示，也方便排查问题。

例如用户说：

```text
为什么我刚才不能提问？
```

日志和响应头能帮助你判断是：

```text
用户级限流
接口级限流
AI 路由限流
工具调用限流
```

### 9. 常见限流维度

限流不是只能按 IP。

真实项目常见维度有：

```text
IP 维度
用户维度
租户维度
接口维度
模型维度
工具维度
业务动作维度
全局维度
```

#### IP 维度

适合未登录场景，比如登录页、公开接口。

缺点是：

```text
公司、学校、网吧可能很多人共用一个出口 IP。
攻击者也可能切换 IP。
```

#### 用户维度

适合登录后的系统。

它比 IP 更接近真实身份。

本节优先使用：

```text
X-User-Id
```

如果没有用户 ID，再退回 IP。

#### 接口维度

接口维度限制某个路径的总体请求量。

例如：

```text
POST /chat 每分钟最多 120 次。
```

它可以保护某个热点接口。

#### AI 路由维度

不是所有接口成本都一样。

`/health` 很轻，`/chat` 很重，`/rag/query` 可能更重。

所以本节把 AI 相关路径归为：

```text
ai scope
```

这样可以对 AI 请求设置更严格的限制。

#### 工具维度

Tool Calling 可能会访问真实业务系统，尤其要谨慎。

例如：

```text
查询订单
创建工单
调用 Java 服务
```

工具请求不只是模型调用，还会触达业务系统，所以本节单独加了：

```text
tool scope
```

### 10. 固定窗口算法

本节实现的是固定窗口限流。

它的思想很简单：

```text
把时间切成一段一段的窗口。
每个窗口内计数。
超过上限就拒绝。
窗口切换后重新计数。
```

例如窗口是 60 秒，限制是 3 次：

```text
00:00 - 00:59 允许 3 次
01:00 - 01:59 再允许 3 次
```

优点：

```text
实现简单。
容易理解。
适合教学和本地单进程服务。
```

缺点：

```text
窗口边界可能出现突刺。
多进程、多机器时内存计数不共享。
不适合直接当成完整生产方案。
```

窗口边界突刺指的是：

```text
用户在 00:59 请求 3 次，又在 01:00 请求 3 次。
从窗口看都合法，但 2 秒内实际发生了 6 次。
```

### 11. 滑动窗口算法

滑动窗口不是按固定整分钟切，而是看当前时刻往前推一段时间。

例如：

```text
任意连续 60 秒内最多 100 次。
```

它比固定窗口更平滑。

缺点是实现更复杂，通常需要记录更多时间戳或做桶聚合。

真实项目里，如果想减少固定窗口边界突刺，可以考虑滑动窗口。

### 12. 令牌桶算法

令牌桶可以理解成：

```text
系统按固定速度往桶里放令牌。
每个请求要拿一个令牌。
有令牌就放行，没令牌就拒绝或等待。
```

它的特点是：

```text
允许短时间突发，但长期平均速率受限制。
```

比如系统每秒放 10 个令牌，桶最多存 100 个令牌。

如果一段时间没人请求，桶里会积累令牌。突然来一批请求时，可以用积累的令牌处理一部分突发流量。

令牌桶常用于网关和 API 限流。

### 13. 漏桶算法

漏桶可以理解成：

```text
请求先进入桶，系统按固定速度往外处理。
桶满了就拒绝新请求。
```

它的特点是：

```text
输出更平稳。
```

令牌桶更偏向允许突发，漏桶更偏向平滑处理。

你暂时不用急着掌握算法细节，但要知道生产里不是只有一种限流算法。

### 14. 内存限流和 Redis 限流的区别

本节使用内存限流。

内存限流的意思是：

```text
计数存在当前 Python 进程内存里。
```

优点：

```text
简单。
不需要安装 Redis。
适合教学。
适合单进程本地开发。
```

缺点：

```text
服务重启后计数清零。
多个 worker 之间计数不共享。
多台机器之间计数不共享。
无法做全局用户限流。
不适合直接当作分布式生产限流方案。
```

Redis 限流的意思是：

```text
计数存在 Redis 里，多个服务实例共享同一份计数。
```

真实生产系统更常见的是：

```text
网关限流 + Redis/集中式限流 + 应用内保护
```

本节先学内存限流，是因为你要先理解限流的业务含义和代码结构，再学 Redis 版本会更稳。

### 15. 为什么 health 和 ready 默认排除

本节默认排除：

```text
/health
/ready
```

原因是它们通常用于健康检查。

如果健康检查也被限流，可能出现奇怪问题：

```text
服务其实还活着，但健康检查被 429。
部署平台误以为服务不可用。
监控系统误报服务故障。
```

所以健康检查一般不放进普通用户限流规则。

### 16. 限流的日志原则

限流日志要记录足够排查的信息，但不能泄露敏感内容。

适合记录：

```text
scope
key
path
limit
retry_after
trace_id
```

不应该记录：

```text
用户原始问题
prompt 全文
API Key
工具返回的敏感字段
身份证、手机号、地址等隐私信息
```

这和前面学过的 LLM 调用日志安全是一致的。

## 本节主题系统讲解

### 1. 本节在系统里的位置

请求进入 FastAPI 后，当前系统的大致链路是：

```text
HTTP 请求进入 FastAPI
-> trace_id 中间件
-> rate limit 中间件
-> CORS 中间件
-> router
-> service
-> LLM / RAG / Tool / Java 服务
```

限流越早做越好。

原因是：

```text
如果请求已经进入 LLM、RAG、Java 服务再限流，就已经消耗了资源。
```

所以本节把限流放在中间件层。

### 2. 本节采用的限流策略

本节不是只做一个简单的全局限流，而是做四类规则：

```text
client：同一个用户或 IP 的总请求频率。
route：同一个接口路径的请求频率。
ai：AI 相关接口的请求频率。
tool：工具相关接口的请求频率。
```

这样做的好处是：

```text
用户刷接口会被 client 限制。
某个热点路径流量过大，会被 route 限制。
AI 相关能力更贵，会被 ai 限制。
工具调用可能触达业务系统，会被 tool 限制。
```

### 3. 为什么不是所有接口同一个限制

不同接口的成本不一样。

例如：

```text
GET /health 几乎不消耗业务资源。
POST /chat 会调用模型。
POST /tool-chat 可能调用模型和工具。
POST /rag/query 可能调用 embedding、向量数据库和模型。
```

如果所有接口统一限流，会出现两类问题：

```text
轻接口被限制得太严格。
重接口被限制得太宽松。
```

所以生产系统经常按接口、业务动作、模型能力分级限流。

### 4. 客户端身份怎么确定

本节按以下顺序识别客户端：

```text
优先 X-User-Id。
没有用户 ID 时使用 X-Forwarded-For 的第一个 IP。
再没有就使用 request.client.host。
最后兜底 ip:unknown。
```

为什么优先用户 ID？

因为登录后的 AI 系统里，用户 ID 比 IP 更稳定。

为什么还要支持 IP？

因为有些请求可能还没有登录，或者本地测试时没有用户体系。

### 5. 多条限流规则同时命中怎么办

一个 `/tool-chat` 请求可能同时经过：

```text
client 限流
route 限流
ai 限流
tool 限流
```

本节策略是：

```text
按顺序检查，第一条拒绝的规则直接返回 429。
```

这叫短路。

好处是简单明确，避免一次请求返回多个错误。

如果以后要做更完整的观测，也可以把所有规则都检查一遍，记录最紧张的规则。但当前教学项目先保持清晰。

### 6. 429 返回格式为什么复用统一错误结构

本项目前面已经有统一异常和错误响应。

限流虽然发生在 middleware 层，但返回格式仍然应该和业务错误一致。

所以本节返回：

```text
success=false
code=RATE_LIMITED
message=请求过于频繁，请稍后重试。
data=null
trace_id=...
```

这样前端和调用方不需要为限流单独写一套解析逻辑。

### 7. 本节暂时不做什么

本节不做：

```text
Redis 分布式限流
网关层限流
租户级限流
模型供应商额度同步
按用户套餐动态限流
按 token 消耗累计限流
滑动窗口/令牌桶真实实现
数据库持久化限流记录
后台管理页面
```

不是这些不重要，而是它们适合在你理解基本限流链路后再做。

当前目标是：

```text
先让 AI 服务具备清晰的本地限流边界。
```

## 本节代码讲解

### 1. `RateLimitRule`

`RateLimitRule` 表示一条限流规则。

它包含：

```text
scope：规则类型，例如 client、route、ai、tool。
limit：窗口内最多允许多少次。
window_seconds：窗口长度。
```

它还有一个 `enabled` 属性。

当前约定是：

```text
limit > 0 并且 window_seconds > 0 才启用。
```

所以你可以把某个限制配置成 `0`，表示关闭这一类限制。

### 2. `RateLimitCheck`

规则本身还不够，还要知道这条规则限制谁。

例如：

```text
client 限制 user:u1001
route 限制 POST:/chat
ai 限制 user:u1001
tool 限制 user:u1001
```

`RateLimitCheck` 就是：

```text
规则 + 身份。
```

它生成的 key 类似：

```text
client:user:u1001
route:POST:/chat
```

这个 key 会被拿去计数。

### 3. `RateLimitDecision`

`RateLimitDecision` 是一次限流检查的结果。

它回答：

```text
是否允许？
是哪种 scope？
当前 key 是什么？
limit 是多少？
还剩多少？
多久后重置？
如果被拒绝，建议多久后重试？
```

它的 `to_headers()` 会转换成 HTTP 响应头。

这样 middleware 不需要关心内部计数细节，只需要把结果返回给客户端。

### 4. `InMemoryFixedWindowRateLimiter`

这是本节的核心计数器。

它内部保存：

```text
key -> 当前窗口开始时间和计数
```

每次请求进来时：

```text
1. 根据当前时间算出窗口开始时间。
2. 找到这个 key 的计数器。
3. 如果窗口变了，就重新计数。
4. 如果 count >= limit，就拒绝。
5. 否则 count + 1，并返回剩余次数。
```

这里使用了线程锁：

```text
threading.Lock
```

原因是 Web 服务可能并发处理请求。

虽然当前只是教学项目，但涉及共享内存计数时，至少要避免同一个进程内的明显并发计数问题。

### 5. `build_rate_limit_checks`

这个函数负责根据请求构造需要检查的规则。

它会先判断：

```text
总开关是否开启。
当前路径是否在排除列表。
```

然后构造：

```text
client check
route check
ai check
tool check
```

其中 `ai` 和 `tool` 不是所有接口都有。

只有路径属于 AI 或工具相关接口时才添加。

### 6. `register_rate_limit_middleware`

这个 middleware 做的事情是：

```text
1. 创建一个内存限流器，放到 app.state.rate_limiter。
2. 每个请求进来时解析 trace_id。
3. 解析客户端身份。
4. 构造限流检查列表。
5. 逐条检查。
6. 如果被拒绝，记录安全日志并返回 429。
7. 如果全部放行，继续 call_next。
```

这就是限流中间件的基本结构。

注意：

```text
限流被拒绝时，不会进入 router，也不会调用模型、RAG、工具或 Java 服务。
```

这正是限流的价值。

## 关键测试说明

本节测试重点不是为了测试 FastAPI 本身，而是固定我们自己的限流边界。

重点验证：

```text

排除路径不会生成限流规则。
不同用户 ID 使用不同计数 key。

```

## 常见误区

### 误区 1：有了成本控制就不需要限流

不对。

成本控制管单次请求是否太贵。

限流管单位时间请求是否太多。

大量低成本请求仍然可能把系统打满。

### 误区 2：只按 IP 限流就够了

不够。

登录系统更应该按用户、租户或业务身份限流。

IP 只能作为兜底维度。

### 误区 3：健康检查接口也应该一起限流

一般不应该。

健康检查被限流可能导致部署平台或监控误判服务不可用。

所以 `/health` 和 `/ready` 默认排除。

### 误区 4：内存限流就是生产限流

不是。

内存限流适合教学和单进程本地开发。

生产多实例服务通常需要 Redis、网关或专门限流系统来共享计数。

### 误区 5：429 是系统异常

不是。

429 是系统按规则主动保护自己。

它表示请求太频繁，不表示服务崩溃。

### 误区 6：重试可以解决 429

不能立刻重试。

429 通常意味着你应该根据 `Retry-After` 等一段时间。

盲目重试会让限流更严重。

### 误区 7：限流日志越详细越好

不是。

限流日志要能排查问题，但不能记录 prompt、用户原文、密钥或隐私。

## 本节练习

### 练习 1：解释限流和成本控制的区别

参考答案：

```text
限流控制单位时间内允许多少请求通过，例如每分钟最多 60 次。
成本控制控制单次请求或累计请求预计消耗多少 token 或金额。
限流解决高频问题，成本控制解决高消耗问题，两者都需要。
```

### 练习 2：为什么 AI 应用里的 `/tool-chat` 比普通健康检查更应该严格限流

参考答案：

```text
因为 /tool-chat 可能调用模型、解析工具请求、执行工具、访问 Java 业务服务，成本和风险都更高。
/health 通常只是轻量健康检查，主要给部署平台和监控使用，一般不应该被普通限流影响。
```

### 练习 3：固定窗口限流有什么优点和缺点

参考答案：

```text
优点是实现简单、容易理解、适合本地单进程教学项目。
缺点是窗口边界可能出现突刺，并且内存计数无法在多进程、多机器之间共享。
```

### 练习 4：为什么本节要返回 Retry-After

参考答案：

```text
Retry-After 告诉客户端建议等待多少秒后再请求。
如果没有它，客户端可能频繁试探重试，反而继续增加系统压力。
```

### 练习 5：为什么不同用户 ID 应该有不同计数 key

参考答案：

```text
因为限流应该尽量限制真正发起请求的身份。
如果所有用户共用同一个 key，一个用户的高频请求可能影响其他正常用户。
```

### 练习 6：为什么生产环境通常不用单机内存限流作为唯一方案

参考答案：

```text
因为生产服务常常有多个 worker 或多台机器，单机内存计数无法共享。
服务重启后计数也会丢失。
如果要做全局用户、租户或接口限流，通常需要 Redis、网关或集中式限流服务。
```

## 自测题

### 自测 1：HTTP 429 表示什么

参考答案：

```text
表示请求过于频繁。请求格式可能正确，用户也可能有权限，但当前请求频率超过系统允许范围。
```

### 自测 2：client、route、ai、tool 四种 scope 分别解决什么问题

参考答案：

```text
client 限制某个用户或 IP 的总体请求频率。
route 限制某个接口路径的请求频率。
ai 限制 AI 相关接口的请求频率。
tool 限制工具相关接口的请求频率，保护后端业务系统和工具执行链路。
```

### 自测 3：为什么限流应该尽量放在业务逻辑之前

参考答案：

```text
因为限流的目的是在消耗昂贵资源之前拦截高频请求。
如果等到模型、RAG、工具或数据库已经执行后再限流，保护效果就很差。
```

### 自测 4：固定窗口为什么可能出现边界突刺

参考答案：

```text
因为用户可以在一个窗口末尾发满限制次数，又在下一个窗口开头继续发满限制次数。
从每个窗口看都合法，但短时间内实际请求量可能很高。
```

### 自测 5：为什么不能把 429 当成普通系统异常来疯狂重试

参考答案：

```text
429 表示系统已经认为请求太频繁。
如果客户端立刻疯狂重试，会进一步增加系统压力。
正确做法是读取 Retry-After，等待一段时间后再试。
```

### 自测 6：限流日志应该记录哪些信息，不应该记录哪些信息

参考答案：

```text
应该记录 scope、key、path、limit、retry_after、trace_id 等排查必要信息。
不应该记录用户原始问题、prompt 全文、API Key、工具敏感返回、身份证手机号等隐私数据。
```

## 本节小结

这一节你要记住：

```text
限流不是判断一次请求贵不贵，而是判断一段时间内请求是不是太频繁。
```

当前项目已经具备：

```text
内存固定窗口限流
client / route / ai / tool 四类 scope
X-User-Id 优先的客户端身份识别
/health 和 /ready 默认排除
429 统一错误响应
Retry-After 和 X-RateLimit-* 响应头
限流安全日志
自动化测试覆盖
```

下一节学习：

```text
重试。
```

也就是在请求失败时，系统什么时候可以再试一次，什么时候绝对不能重试，以及写操作为什么必须考虑幂等。
