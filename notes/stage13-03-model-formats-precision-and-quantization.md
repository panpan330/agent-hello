# M13 第 3 节：模型格式、精度与量化

## 本节定位

上一节已经知道：模型权重、KV Cache、临时计算和运行时开销共同占用内存/显存；模型参数越多、每个参数占用字节越多，部署门槛越高。本节解决一个直接影响部署选择的问题：为什么同一个模型会出现 FP32、FP16、BF16、INT8、8-bit、4-bit 等版本？它们是不同模型吗？为什么有的模型文件更小却还能使用？

核心答案是：模型参数原本是大量数值，而不同数值表示方式会在**数值精度、存储空间、计算速度、硬件支持和任务质量**之间做权衡。量化（quantization）就是将部分高精度数值以更低位数表示或计算，使模型能在更少资源中运行。

量化是本地模型、自部署推理和成本优化中非常常见的技术，但不应被理解为“把模型随便压缩一下”。不同模型、任务、硬件、量化方法和推理引擎会产生不同结果。正确做法是理解原理、明确权衡、通过评估验证，再选择部署版本。

## 本节学习目标

学完后，你应当能：

1. 解释数值精度、位（bit）、字节（byte）与参数存储大小的关系。
2. 区分 FP32、FP16、BF16、INT8、4-bit 等常见表示的基本含义。
3. 理解量化的目标、基本思想和为什么它能减少模型资源需求。
4. 区分权重量化、激活量化、KV Cache 量化和训练/推理量化的概念。
5. 说明量化可能影响哪些能力，以及为什么不能只看模型文件大小。
6. 理解模型格式、量化格式、推理引擎和硬件支持之间的匹配关系。
7. 能为“是否使用某个量化模型”设计基本的评估与选择流程。

## 一句话先讲透

> 量化的本质是用更少 bit 表示模型中的大量数值，以降低权重和运行状态的存储与带宽压力；它让更多模型能够在有限硬件上运行，但会引入近似误差，实际速度和质量取决于量化对象、算法、硬件和推理引擎，必须用真实任务评估而不是只看文件变小。

## 基础知识铺垫

### 1. bit、byte 与数值表示

计算机中的数据由 bit（比特）组成。一个 bit 只有两种状态：0 或 1。8 个 bit 组成 1 个 byte（字节）：

```text
1 byte = 8 bits
```

模型参数本质上是数值。为了在计算机中保存一个数，需要选择一种数值表示格式。不同格式使用不同 bit 数，能表达的范围和精度也不同。

| 名称 | 常见 bit 数 | 理想存储占用 | 直觉 |
| --- | --- | --- | --- |
| FP32 | 32 bit | 4 byte | 数值精细、占用较大 |
| FP16 / BF16 | 16 bit | 2 byte | 更省资源，深度学习常用 |
| INT8 | 8 bit | 1 byte | 更紧凑，需要量化映射 |
| 4-bit | 4 bit | 0.5 byte | 更紧凑，近似与元数据更重要 |

“理想存储占用”只用于初步估算。真实量化模型还需要缩放因子、分组元数据、格式头等额外信息，因此文件/运行时大小不会永远严格等于参数数乘以理论字节数。

### 2. 什么是浮点数（Floating Point）

模型权重和中间计算经常需要表示小数、很大或很小的数。浮点数是一种在有限 bit 内近似表示实数的方式，通常由符号、指数和有效数字等部分组成。

你不需要背每种格式的位布局，但要理解两个维度：

```text
数值范围：能表示多大/多小的数
数值精度：能区分多细微的差异
```

不同浮点格式在范围与精度上有所取舍。模型训练和推理会涉及大量数值运算，因此格式选择会影响是否容易出现数值溢出、舍入误差、显存占用和硬件加速效率。

### 3. FP32：传统高精度基准

FP32（32-bit floating point）通常占 4 字节，是深度学习早期和通用科学计算中常见的数值格式。

优点：

- 数值精度和范围相对充足；
- 算法行为较稳定，常作为对照基准；
- 广泛被硬件和软件支持。

缺点：

- 权重占用大；
- 训练时梯度、优化器等还会进一步放大内存消耗；
- 推理时常比低精度方案占用更多显存和带宽；
- 在适合低精度计算的硬件上不一定是最高效选择。

对大语言模型推理而言，FP32 通常资源开销较高。它并非“永远最好”，而是一个相对高精度的参考点。

### 4. FP16：半精度的基本思想

FP16（16-bit floating point）通常占 2 字节，约为 FP32 的一半。将权重从 FP32 转为 FP16，理想情况下可显著降低存储和显存占用。

它的优势：

- 权重更小；
- 显存带宽压力降低；
- 许多现代 GPU 对半精度矩阵计算有较好支持；
- 对许多推理任务，质量可保持在可接受范围。

它的挑战：

- 可表示的数值范围和精度低于 FP32；
- 某些计算可能出现上溢、下溢或舍入问题；
- 不是所有硬件/软件路径都能同样高效支持。

FP16 是理解“混合精度”和“半精度推理”的基础。它不是把模型逻辑变了，而是用更紧凑方式表示数值。

### 5. BF16：范围与精度的不同取舍

BF16（bfloat16）也是 16 bit 浮点表示，但与 FP16 的位分配方式不同。概念上可以记住：

```text
BF16 更接近 FP32 的数值范围特性，
但有效精度较低；
FP16 的有效精度特性不同，数值范围相对更受限。
```

这使 BF16 在许多深度学习训练/推理场景中很受欢迎，尤其当硬件和框架对其有良好支持时。它不是“BF16 一定优于 FP16”，而是不同格式在数值稳定性、硬件支持和性能上各有适用场景。

对于应用工程师，最实用的结论是：看到 FP16/BF16 时，应理解它们都是降低资源使用的半精度选择；具体该选哪种，通常要看模型官方建议、目标硬件、推理引擎支持和实际评估结果。

### 6. 整数（Integer）与 INT8 的直觉

INT8 使用 8 bit 表示整数。模型原始权重通常是连续的小数，而不是天然整数。要将它们存为 INT8，需要建立映射关系：

```text
原始浮点范围
<-> 有限的整数值范围
```

常见概念形式是：

```text
近似浮点值 ≈ scale × (integer_value - zero_point)
```

其中 `scale`（缩放因子）和可选的 `zero_point` 用于把整数空间映射回原浮点数范围。你不需要在这一阶段手算每个参数，但要理解：INT8 并不是简单截断小数，而是通过规则将原数值近似编码为较少 bit 的整数，并在计算时按相应规则恢复/计算。

### 7. 4-bit：为什么还能进一步压缩

4-bit 只有 16 种可表示值（从 bit 组合角度看），远少于 FP16 或 INT8 能表示的数值。为了让 4-bit 仍可用于大模型，量化方法通常会使用：

- 分组（grouping）：将一小组权重共享某些量化参数；
- 缩放因子（scales）：记录该组数值范围；
- 特定码本/非均匀映射：让有限表示更适合权重分布；
- 更精细的逐通道/逐组策略；
- 在部分计算中保留较高精度。

因此“4-bit 模型”不是只有每参数 4 个 bit 的孤立数据，还会有额外量化元数据和运行时策略。4-bit 的价值是让较大模型有机会在较小显存/内存设备运行；代价是近似误差、格式兼容、性能实现和任务质量都更需要验证。

### 8. 精度、范围、误差与任务质量

降低 bit 数会引入近似误差。可以用一个简单类比：

```text
高精度刻度尺：能区分毫米甚至更细差别
低精度刻度尺：可能只能区分厘米
```

模型中的每个权重误差看似很小，但经过多层计算和大量 token 生成后，可能影响输出。影响大小不是固定的：

- 有些模型/层/任务对量化非常鲁棒；
- 有些任务对长上下文、数学、代码、结构化输出或多语言更敏感；
- 有些量化算法和格式比简单低位截断保留得更好；
- 有些硬件/引擎会在计算中使用更高精度累积，减轻误差；
- 有些问题本来由 RAG、Prompt 或工具控制，模型量化影响可能不明显。

所以量化效果必须在目标任务上评估，不能只凭“位数更低”断言模型一定不可用，也不能凭“日常聊天看着正常”断言生产任务完全无损。

## 本节主题系统讲解

### 1. 量化（Quantization）到底是什么

量化可以理解为：将模型中的某些高精度连续数值，映射到更低 bit 的有限表示，以减少存储、显存、带宽或计算成本。

概念流程：

```text
原始 FP16/FP32 权重
-> 按某种量化规则分组、测量范围/分布
-> 将每个权重映射到低 bit 编码
-> 保存必要的 scale/zero point/码本等元数据
-> 推理时由引擎使用低位表示计算或恢复近似数值
```

量化的目标通常不是追求数学上完全相同，而是在资源显著降低的前提下，让任务质量下降保持可接受。

### 2. 量化解决的资源问题

量化可能改善多个资源维度：

| 资源维度 | 为什么可能改善 |
| --- | --- |
| 磁盘存储 | 权重文件更小，下载/分发更容易 |
| RAM/VRAM | 权重占用降低，可运行更大模型或留更多 KV Cache |
| 显存带宽 | 读取权重的数据量减少，部分场景有利于生成速度 |
| 部署成本 | 可能用更小实例/更少 GPU 承载相同模型 |
| 启动时间 | 模型文件更小，加载/传输可能更快 |
| 本地可用性 | 让资源有限设备也能尝试运行模型 |

这里所有用词都应是“可能”。例如低位权重需要反量化或特定计算内核，若硬件/引擎支持不好，速度未必提升；KV Cache 仍可能成为主要显存占用；质量评估和工程维护也有成本。

### 3. 权重量化（Weight Quantization）

权重量化是最常见概念：将模型参数本身从高精度存储表示改为低位表示。

优点：

- 直接减少最主要的固定显存部分；
- 模型文件更小；
- 对部署可行性影响最直观。

局限：

- 只降低权重，不会自动降低每个请求的 KV Cache；
- 某些层或模型对低位误差敏感；
- 引擎必须支持对应格式和高效内核；
- 不同权重量化格式不可随意互换。

当你看到“某模型 4-bit 版本”，多数情况下首先指权重量化，但仍应查看该版本文档或模型卡确认具体做了什么。

### 4. 激活量化（Activation Quantization）

激活（activation）可以粗略理解为模型在处理当前输入时各层产生的中间数值。它们不是固定模型权重，而是随请求、token、batch 变化。

激活量化是将这些运行时中间值也使用更低精度表示/计算。它可能进一步降低计算或内存成本，但挑战通常更大，因为激活值的范围和分布会随输入变化。

对推理工程师而言，知道它的存在即可：

- “量化”不只可能发生在权重；
- 量化方案的质量/性能要看它量化了什么；
- 权重低位不代表所有计算都低位；
- 有些方案会在关键算子中使用更高精度累积以保持稳定。

### 5. KV Cache 量化

上一节学习过 KV Cache 随上下文、输出和并发增长。即使权重已经量化，长上下文高并发时 KV Cache 仍可能吃掉大量显存。

KV Cache 量化是对缓存中的键/值状态采用更紧凑表示，以降低每个 token、每个并发请求的缓存占用。

它的潜在价值：

- 增加可支持的上下文长度；
- 增加并发请求数量；
- 缓解长会话/长文档 Agent 的显存压力。

它的挑战：

- 可能影响注意力计算质量；
- 需要引擎和硬件支持；
- 对不同模型/任务的影响需测试；
- 不能替代上下文工程和并发控制。

这说明资源优化不能只盯权重。部署长上下文 Agent 时，权重与 KV Cache 都是显存账本的重要部分。

### 6. PTQ 与 QAT：何时发生量化

按量化发生时机，常见有两类概念：

#### 6.1 PTQ（Post-Training Quantization，训练后量化）

先有已经训练好的模型，再将其转换为低精度版本。它的优点是相对容易、成本低，适合大量已有开源模型或部署场景。

```text
训练好的模型
-> 选择量化算法/配置
-> 使用少量校准数据（某些方法需要）
-> 生成量化模型
-> 评估与部署
```

#### 6.2 QAT（Quantization-Aware Training，量化感知训练）

在训练或微调过程中模拟/考虑低精度误差，让模型参数适应未来量化表示。它潜在质量更好，但训练流程更复杂、成本更高。

对大多数应用团队，自部署推理时更常先接触 PTQ；QAT 属于更深入模型工程主题。理解二者的区别即可，不必现在自行实现。

### 7. 对称、非对称与分组量化的直觉

不同量化算法会决定如何将浮点数映射到低位整数/码本。常见设计思想包括：

- **对称量化**：围绕 0 对称映射，通常概念较简单；
- **非对称量化**：通过零点等机制处理不对称数值范围；
- **逐张量量化**：整块张量共用一组参数，简单但可能误差较大；
- **逐通道量化**：不同通道分别缩放，通常更细致；
- **逐组量化（group-wise）**：按小组共享 scale 等参数，在质量与元数据开销间折中；
- **非均匀量化/码本量化**：用更适合权重分布的有限值表示。

这里的核心思想是：量化不是只有“把小数四舍五入”。高质量量化会尽力让有限 bit 资源优先表示对模型更重要、更常见的数值范围和结构。

### 8. 模型格式与量化格式不是同一个层次

“模型格式”可能指多种东西：

| 维度 | 例子（概念） | 它解决什么 |
| --- | --- | --- |
| 权重存储格式 | 某框架原生权重文件、张量文件 | 权重如何在磁盘保存 |
| 量化表示格式 | INT8、4-bit、特定量化布局 | 参数如何低位编码 |
| 推理运行格式 | 某引擎可加载的优化产物 | 引擎如何高效执行 |
| 模型配置格式 | 网络结构/tokenizer/generation 配置 | 如何构建和使用模型 |
| API 协议格式 | OpenAI 兼容 JSON 等 | 应用如何调用服务 |

同一个模型可以有多种权重格式和量化版本；某个推理引擎可能只支持其中一部分；某个硬件可能对某些精度更高效。

因此不要看到“4-bit”就只问“这个模型能不能下载”。还要问：

```text
该权重格式能否被目标推理引擎加载？
引擎是否在目标硬件上支持这种量化？
能否支持需要的上下文、并发、工具调用和 API？
量化版本是否经过目标任务评估？
```

### 9. 硬件支持会影响实际性能

同样是 INT8 或 4-bit，在不同硬件上可能表现不同。原因包括：

- 某些 GPU 对 FP16/BF16 矩阵运算特别优化；
- 某些硬件对 INT8/低位计算有专用单元；
- 某些低位格式需要额外解码/反量化操作；
- 内存带宽、缓存、驱动和编译器优化不同；
- 推理引擎是否有对应高效 kernel。

所以不能从“4-bit 比 FP16 小 4 倍”直接推导“4-bit 必然快 4 倍”。在某些场景中，量化主要带来容量收益；在另一些场景中还会带来吞吐提升；也可能因格式不匹配或反量化成本而表现不佳。

### 10. 量化对模型质量可能产生什么影响

量化误差可能影响：

- 一般对话的连贯性和细节；
- 长上下文信息利用；
- 复杂推理、数学、代码和多步骤任务；
- 多语言/低资源语言表现；
- 结构化输出稳定性；
- 工具参数准确性；
- RAG 引用精度；
- 重复、幻觉或边界案例表现。

重要的是：影响并不一定均匀。某个 4-bit 模型日常聊天看起来很好，不代表它在你的 Agent 工具参数、中文政策问答、长文档或关键业务任务中同样稳定。

因此评估应覆盖你真正关心的任务，而不是只问几个通用问题。

### 11. 量化不会自动解决哪些问题

量化可以缓解资源压力，但不能自动解决：

- RAG 检索错了；
- 用户没有权限；
- Prompt Injection；
- Agent Loop 无限循环；
- 工具调用越权或参数错误；
- 模型本身不具备某类能力；
- 长任务没有 checkpoint；
- 服务没有限流、队列、监控和成本控制；
- 业务事实过期或工具不可用。

不要因为量化让模型能运行，就误以为 AI 应用已经具备生产能力。量化解决的是模型运行资源和部分性能问题。

### 12. 量化与训练的区别

量化通常是在表示/运行层压缩已有模型数值；训练和微调是在学习层调整模型参数。二者的目标不同：

| 技术 | 是否改变模型学习到的能力模式 | 主要目的 |
| --- | --- | --- |
| Prompt/RAG | 不改变权重 | 改变当前上下文与外部知识 |
| 微调 | 改变/新增参数或适配器 | 强化某类稳定任务行为 |
| 量化 | 近似表示已有参数/状态 | 降低资源与部署成本 |

量化有时会带来质量变化，但这不是有目的地让模型学习新知识或新格式。不要把“量化版本输出不同”误认为完成了微调。

### 13. 量化与 LoRA/QLoRA 的关系

后续微调课程会学习 LoRA 和 QLoRA。现在先建立概念边界：

- **LoRA**：通常是参数高效微调方法，通过训练较小的适配器参数来适应任务；
- **QLoRA**：在较低位量化的基础模型上进行高效微调的一类思路，目的是降低微调时的资源要求；
- **推理量化**：主要让已经可用的模型以更少资源部署和推理。

三者可以组合，但不应混为一谈。你将在 M13-14 专门学习它们。

### 14. 量化模型的选择流程

面对多个量化版本，不建议只按“最小文件”选择。可以按以下步骤：

1. 明确目标任务：聊天、RAG、结构化输出、Agent、代码还是离线批处理？
2. 明确资源约束：VRAM/RAM、CPU/GPU、上下文、并发、预算。
3. 确认许可证、来源、权重/配置/tokenizer 完整性。
4. 确认目标推理引擎和硬件是否原生支持该格式。
5. 做加载与基础性能测试：是否能稳定启动，TTFT/输出速度如何。
6. 在真实评估集上比较质量：正确性、引用、格式、工具选择、边界案例。
7. 做并发与长上下文测试：KV Cache、OOM、排队、错误率。
8. 选择能满足质量门槛的最低资源方案，而不是绝对最小位数。
9. 记录模型、量化、引擎、参数和评估版本，以便回滚。

这套流程体现一个工程原则：资源优化必须受质量底线约束。

### 15. 一个近似资源比较例子

假设同一个约 7B 参数模型有多种表示版本。仅看理想权重占用：

| 表示 | 每参数理想字节 | 理想权重规模 | 部署含义 |
| --- | --- | --- | --- |
| FP32 | 4 | 约 28GB | 高资源基准，通常不适合资源有限推理 |
| FP16/BF16 | 2 | 约 14GB | 常见高质量推理起点 |
| INT8 | 1 | 约 7GB | 更省显存，需看引擎/质量 |
| 4-bit | 0.5 | 约 3.5GB | 更适合资源有限环境，需重点评估 |

真实部署绝不能只用这张表做决定。还需加上 KV Cache、临时空间、元数据、运行时和安全余量。若目标是长上下文多并发 Agent，量化后节省出的显存可能主要用来承载更多 KV Cache，而不是单纯“把模型放进更小显卡”。

### 16. 一个实际走读：为什么 4-bit 模型能跑但服务仍然不稳定

假设团队将一个模型从 FP16 换成 4-bit，模型终于能加载到某张 GPU。测试中却发现高并发长对话仍会 OOM，部分结构化输出失败。

分析路径：

```text
权重：4-bit 后显著变小，加载问题缓解
KV Cache：仍随长上下文和并发增长，可能成为新主要显存消费者
输出质量：量化误差可能让格式/工具参数边界案例变差
并发：更多请求同时活跃，临时空间和缓存增加
服务：若无 token/上下文/队列控制，仍会资源耗尽
```

合理改进可能包括：限制每请求上下文/输出、压缩历史和 RAG、设置并发/队列、评估更合适量化格式或模型、优化结构化输出校验与重试。不能只把问题归结为“4-bit 不行”或“再降到更低 bit”。

### 17. 质量评估应怎么比较量化版本

量化评估至少应包含：

| 维度 | 示例问题 |
| --- | --- |
| 任务正确性 | 对真实问题的答案是否达标？ |
| RAG 引用 | 是否引用正确文档/段落，是否误用过期内容？ |
| 结构化输出 | JSON/schema 是否稳定，字段语义是否正确？ |
| 工具调用 | 工具选择、参数、边界和拒绝行为是否变化？ |
| 长上下文 | 长会话/长文档下是否遗漏关键条件？ |
| 多语言 | 目标语言，特别是中文等是否稳定？ |
| 安全 | 注入、权限、拒绝策略是否退化？ |
| 性能 | TTFT、输出速度、吞吐、显存、OOM、重试率 |
| 成本 | 单请求、单位 token、所需硬件/实例成本 |

对高风险业务，不应仅凭少数人工主观体验就将量化版本直接上线。需要基准版本比较、灰度、观测和回滚。

### 18. 量化后的版本治理

量化模型应视为独立可部署版本，至少记录：

```text
基础模型与原始权重版本
量化算法/格式/bit 数/分组配置
使用的校准数据（若适用）
tokenizer 与模型配置版本
推理引擎、硬件、运行参数
评估集与评估结果
已知限制、适用场景和回滚目标
```

不要只在配置中写 `model=xxx-4bit` 却没有任何来源和评估记录。模型、量化格式和引擎共同决定行为，任何一项变化都可能引起质量或性能回归。

### 19. 应用层如何配合量化部署

即使模型服务的量化由平台团队负责，应用团队仍应：

- 通过评估确认关键任务没有明显退化；
- 对结构化输出、工具调用和引用保持服务端校验；
- 为模型设置合理上下文、输出和 Agent 预算；
- 用网关记录实际模型/量化版本、token、延迟和失败；
- 对高风险路径保留更强模型或人工回退；
- 支持灰度比较与快速回滚；
- 不将硬件资源优化误当成业务安全机制。

量化改变的是模型服务底层能力边界，应用层的权限、任务、工具和评估责任仍然存在。

## 常见误区

### 误区 1：4-bit 就是把模型大小精确缩小到 FP16 的四分之一

不完全正确。理论参数位数更低，但真实文件和运行时还含有分组、scale、格式头和其他元数据；KV Cache、临时空间和引擎开销也不会按同样比例缩小。

### 误区 2：量化后的模型就是一个完全不同、重新训练过的模型

通常不是。推理量化主要近似表示已有权重以降低资源；它不是用新数据让模型学习任务模式。微调与量化的目的不同。

### 误区 3：量化越低 bit 越好

低 bit 能省资源，但可能带来质量、兼容或性能问题。正确目标是在满足任务质量和稳定性门槛下选择资源合适的版本，而不是追求最小数字。

### 误区 4：权重量化后，长上下文和高并发就不再占显存

不对。KV Cache 与临时空间仍会随上下文、输出和并发增长。权重量化可能释放显存，但不能替代上下文预算、并发限制和队列。

### 误区 5：INT8/4-bit 一定比 FP16 更快

不一定。速度依赖硬件支持、推理内核、带宽、反量化开销、batch 和模型结构。有时量化主要提升可部署性，实际速度增益有限或需要特定引擎。

### 误区 6：量化模型日常聊天正常，就可以直接用于所有生产任务

不对。结构化输出、工具调用、长上下文、代码、中文、RAG 引用和安全边界都可能有不同敏感度。应使用真实评估集和灰度验证。

### 误区 7：量化解决了 Prompt Injection、权限和业务错误

量化只处理模型数值表示和资源问题。安全、权限、工具校验、HITL、任务状态和 RAG 质量仍由应用系统负责。

## 本节练习

### 练习 1：估算与判断

一个约 13B 参数模型有 FP16 和 INT8 两个版本。按理想字节数估算，二者权重分别约多大？实际显存为何不能只按这个数值判断？

答案：FP16 约 `13B × 2 bytes = 26GB`，INT8 约 `13B × 1 byte = 13GB`。这只是理想权重规模；实际还要包含量化元数据、KV Cache、临时计算空间、运行时开销、显存碎片和并发余量，因此不能将该数值直接当成最小显存要求。

### 练习 2：区分技术目的

下面情况更适合使用 Prompt/RAG、微调还是量化？

1. 公司退款政策每周更新。
2. 需要让模型在固定抽取任务上长期稳定输出一种特定格式，且 Prompt 已难以满足。
3. 模型质量已达标，但当前 GPU 显存不足以加载。

答案：1 更适合 RAG/受控知识库，因为需要频繁更新、引用和版本控制。2 可评估微调，但仍应先验证 Structured Output、Prompt 和工作流是否足够。3 更适合量化、换更小模型、扩显存或调整部署资源；量化不用于学习新知识。

### 练习 3：分析性能误解

团队将模型换成 4-bit 后，模型文件变小，但生成速度没有明显提升。请给出三个可能原因。

答案：目标硬件或推理引擎对该低位格式没有高效 kernel，反量化开销抵消收益；当前瓶颈在 CPU、网络、tokenizer、队列或小 batch，而非权重带宽；长上下文并发导致 KV Cache/临时空间成为主要压力；也可能模型原本已经受其他服务限制。文件变小不自动等于端到端速度提升。

### 练习 4：设计评估

若要把客服 Agent 的 FP16 模型切换为量化版本，至少应比较哪些质量和系统指标？

答案：应比较真实客服任务正确性、RAG 引用、中文表现、结构化输出、工具选择/参数、权限/拒绝边界、长上下文情况；系统指标包括 TTFT、输出速度、吞吐、显存、OOM、错误率和单任务成本。高风险路径还应评估人工介入率和回滚条件。

## 自测题

### 自测 1：量化的核心目标是什么？

答案：用更少 bit 近似表示模型权重、激活或缓存等数值，以降低磁盘、内存/显存、带宽或计算资源需求，使模型更容易部署或提高资源效率，同时将任务质量损失控制在可接受范围。

### 自测 2：FP16 和 BF16 有什么共同点与差异？

答案：共同点是都使用 16 bit，通常比 FP32 更省资源；差异在于数值范围和有效精度的位分配不同，因而数值稳定性、硬件支持和适用场景可能不同。具体选择应看模型、硬件、引擎和评估，而不是简单判断谁绝对更好。

### 自测 3：为什么量化模型需要匹配推理引擎和硬件？

答案：量化格式决定权重如何编码和计算，推理引擎必须能正确加载并提供高效 kernel；硬件对不同精度的计算支持和带宽不同。格式或硬件不匹配可能无法加载、性能差或行为不符合预期。

### 自测 4：权重量化与 KV Cache 量化分别解决什么问题？

答案：权重量化降低模型固定参数的存储/显存占用；KV Cache 量化降低随上下文、输出和并发增长的请求状态占用。长上下文高并发服务可能同时需要关注两者。

### 自测 5：选择量化版本时最重要的工程原则是什么？

答案：先明确任务质量和安全底线，再在目标硬件、上下文、并发和成本约束下比较候选量化版本；通过真实评估、性能测试、灰度和可回滚发布，选择满足质量门槛的最低资源方案，而不是只选位数最低或文件最小的版本。

## 本节小结

本节解释了模型数值表示与量化的基本逻辑。FP32、FP16、BF16、INT8、4-bit 等版本本质上是在数值精度、存储、显存、带宽和计算之间做不同权衡；量化可以作用于权重、激活或 KV Cache，并需要与模型格式、推理引擎和硬件匹配。量化的价值必须通过真实任务的质量、性能、稳定性和成本评估来证明。
