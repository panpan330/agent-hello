# M11 第 5 节：RAG 元数据设计：来源、页码、版本与权限

## 本节定位

正文 `content` 只能说明“这段话写了什么”。企业 RAG 还必须回答：它来自哪里？是哪一版？现在是否有效？适用于谁？当前用户能否看到？系统怎样删除或重建它？

这些问题都由元数据解决。本节不把元数据当作附属 JSON，而把它当作知识系统的身份、时间、边界和治理模型。

## 本节学习目标

1. 理解元数据为什么决定引用、权限和生命周期。
2. 区分知识库、文档、文档版本、页面、结构块、检索块与索引版本。
3. 设计来源、章节、页码、版本、有效期、状态、权限和内容指纹。
4. 区分硬过滤、软排序、展示字段和治理字段。
5. 理解字段契约、数据最小化和元数据演进。

## 一句话先讲透

**没有元数据的文本块只是无来历文字；正确元数据让它成为可引用、可过滤、可授权、可更新、可审计的企业证据。**

## 基础知识铺垫

### 1. 元数据是什么

元数据就是描述数据的数据。正文写“退款时限为 7 天”；元数据说明这段话来自哪份文件、第几页、哪一章、哪个版本、对谁有效、谁能看。

```text
content：说了什么。
metadata：它是谁、从哪里来、是否有效、能给谁看、怎样管理。
```

没有后者，系统无法区分普通商品规则与活动商品规则，也无法区分当前政策与已失效政策。

### 2. 元数据不是越多越好

每个字段都应有明确用途：检索过滤、来源引用、版本治理、权限控制、排错或展示。无用途字段增加维护与泄露风险；把敏感信息复制到每个向量 payload，还会扩大日志、索引和调试的暴露面。

## 本节主题系统讲解

### 1. 先建领域对象，再设计字段

```text
知识库：受管理、受授权的资料范围。
文档：一份逻辑资料，例如“售后政策”。
文档版本：某次内容快照，例如 2026.08。
页面/区域：原始证据定位单位。
结构块：标题、正文、表格、脚注等解析结果。
检索块：向量检索的语义单位。
索引版本：用某套 pipeline 和 embedding 生成的派生索引。
```

关系并不简单：一个文档有多个版本；一个版本有多页、多块；同一版本也可因 embedding 或分块策略升级产生多套索引。先理解这些对象，才能避免把文件名、版本和块 ID 混成一个字段。

### 2. 稳定标识的职责

| 标识 | 表达什么 | 应保持稳定到何时 |
| --- | --- | --- |
| knowledge_base_id | 哪个知识范围 | 知识库存在期间 |
| document_id | 哪份逻辑文档 | 文件改名和重建后仍稳定 |
| document_version_id | 哪次内容快照 | 分块和模型升级后仍可追溯 |
| chunk_id | 哪个可引用检索块 | 在内容与边界不变时稳定 |
| index_version | 哪套派生索引 | pipeline/embedding 改变时更新 |

文件名适合展示，不适合当唯一 ID；每次重建随机生成块 ID，会让删除、评测、引用和 bad case 关联失效。

### 3. 来源与结构字段

```text
file_name / source_uri：让用户找到可信原件。
page_number / page_range：定位原始页面。
section_path：保留章节语义地址。
chunk_index：恢复块顺序。
content_type：正文、FAQ、表格行、脚注、图注等。
parent_chunk_id：支持父子上下文补全。
```

页码只保存在文档级不够，因为引用的是具体证据。章节路径也不是展示装饰，它常决定一句规则属于哪种商品、哪个流程或哪个例外。

### 4. 时间、版本与状态字段

至少区分三种时间：

```text
业务生效时间：政策从何时适用。
系统处理时间：文件何时解析和入库。
用户查询时间：用户问的是现在还是某个历史时点。
```

`ingested_at` 不等于 `effective_from`。旧政策今天入库，不能因入库新就变成当前规则。

状态可包括：draft、parsing、needs_review、ready、disabled、archived、failed。在线检索通常只允许 `ready` 且在目标业务时间有效的版本参与。

### 5. 权限字段与硬过滤

常见字段：

```text
tenant_id：所属租户。
permission_group：允许访问的角色/组。
visibility：公开、内部、受限。
department_id、region：细粒度范围。
data_classification：公开、内部、敏感等分级。
```

它们不是给模型看的提醒，而是检索前硬过滤输入。无权块不召回、不重排、不放进上下文。权限字段应来自可信身份与管理流程，不能相信用户请求或文档正文自己声明的值。

### 6. 字段的四种使用方式

| 类别 | 示例 | 用法 |
| --- | --- | --- |
| 硬过滤 | 租户、权限、状态、有效期 | 不满足绝不召回 |
| 软偏好 | 官方发布、可信等级、语言、业务域 | 都可见时优先排序 |
| 引用展示 | 文件名、版本、页码、章节 | 让用户核验 |
| 治理排错 | hash、pipeline_version、ingested_at | 重建、去重、诊断 |

把硬约束做成模型 prompt 会造成安全漏洞；把软偏好做成硬过滤会造成不必要漏召回。

### 7. 继承与覆盖规则

文档级权限、版本、生效期常需要被块继承，但块也可能更严格。例如整份文档对客服可见，某个内部定价附录只允许主管。安全原则是：

```text
下级可以收紧上级范围。
下级不能绕过上级范围放宽。
```

这说明权限不应只放在文件说明里；块级也必须能表达局部限制。

### 8. 内容指纹与数据契约

```text
file_hash：原始文件字节是否变化。
content_hash：规范化内容是否变化。
pipeline_version：解析、清洗、分块规则版本。
embedding_model/dimension：向量空间配置。
```

重要字段还需数据字典：类型、必填性、允许值、写入者、缺失处理、是否敏感。比如权限缺失应默认不可发布，而不是默认公开；状态应是受控枚举，不能任意写 `active` 或 `ok`。

### 9. 元数据演进

系统以后可能增加多租户、地区、历史查询或权威等级。演进时要问：旧数据缺字段时安全吗？是否要重建索引？历史引用还能否使用？新默认值是否意外放宽权限？

安全字段缺失时宁可进入待补全、不可检索状态，也不能因为兼容方便而默认放行。

## 常见误区

### 误区 1：向量和正文足够，元数据可后补

不对。没有来源、版本和权限，文本从一开始就不具备企业可用性。

### 误区 2：文件名可当唯一文档 ID

不对。同名、重命名和版本变化很常见，展示名与稳定标识应分离。

### 误区 3：只在前端隐藏敏感资料

不对。后端检索与引用接口都必须基于可信权限硬过滤。

### 误区 4：元数据越丰富越专业

不对。应数据最小化，避免将个人信息、订单细节、密钥或自由文本备注复制进可检索索引。

## 本节练习

### 练习 1：为什么 document_id、document_version_id 与 chunk_id 要分开？

答案：它们分别标识逻辑文档、具体内容快照和一个可引用块，生命周期不同。混用会使版本、删除、引用和索引重建无法稳定管理。

### 练习 2：哪些字段应在检索前硬过滤？

答案：例如 tenant_id、permission_group、status、有效期、知识库范围。它们决定当前用户与当前时间允许访问哪些证据。

### 练习 3：为什么入库时间不能替代生效时间？

答案：文件可能晚上传、提前发布或用于历史查询。业务适用性应由有效期决定，不能按系统处理时间猜测。

## 自测题

### 自测 1：元数据在 RAG 中承担哪些核心职责？

答案：来源追溯、权限过滤、版本与生命周期治理、上下文补全、展示引用、去重与排错。

### 自测 2：为什么元数据也需要权限和质量控制？

答案：它可能暴露敏感身份、部门或业务信息，并直接影响过滤、引用和版本判断。错误元数据会造成越权、旧知识和错误引用。

### 自测 3：本节最重要的结论是什么？

答案：正文说明内容，元数据决定内容是否可信、适用、可访问和可维护；企业 RAG 的可靠性很大程度来自元数据设计。
