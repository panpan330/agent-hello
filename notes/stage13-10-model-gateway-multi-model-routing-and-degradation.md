# M13 第 11 节：模型网关、多模型路由与降级

## 本节定位

前几节已经建立了模型服务、推理引擎和部署环境的概念。真实系统一旦同时使用多个云模型、自部署模型、Embedding 模型、Rerank 模型或不同版本的同类模型，就会出现一个新的问题：业务系统到底该如何选择、调用、切换、限制和观察这些能力？

最直接的写法是让每个业务模块自己判断 `if provider == ...`。短期很快，长期会产生密钥分散、模型名混乱、成本不可见、回退不一致、测试困难和安全策略漂移。模型网关与路由层的价值，就是把这些跨业务的共同问题集中在一个清晰边界中处理。

本节讲的是设计思想，不要求搭建网关、购买服务或修改代码。

## 本节学习目标

学完后，你应当能够：

1. 解释模型网关、模型适配层、负载均衡器和业务 AI 服务的职责差异。
2. 理解“逻辑模型名”“实际模型部署”“模型能力矩阵”三者的关系。
3. 区分静态路由、规则路由、能力路由、质量路由、成本路由和健康路由。
4. 解释模型回退、熔断、限流、重试和降级之间的区别与顺序。
5. 说明为什么降级不只是“换一个便宜模型”，还涉及质量、安全、数据和业务承诺。
6. 设计多模型系统中最小但可用的配置、审计和观测信息。
7. 识别自动路由常见的循环、成本失控、语义不兼容和质量退化风险。
8. 能为不同任务提出可解释的模型选择策略，而不是只按模型名硬编码。

## 一句话先讲透

**模型网关把“调用哪个模型、能不能调用、失败后怎么办、花了多少、是否符合治理要求”从业务代码中抽离出来；多模型路由的目标不是永远选到最强模型，而是在明确约束下选到足够好、可用、可控且可追责的路径。**

## 基础知识铺垫

### 1. 一个系统为什么会有多个模型

多模型不一定意味着追求复杂。它往往来自自然分工：

- 对话生成模型：回答问题、总结、生成结构化草稿；
- Embedding 模型：将文本变成向量，用于检索；
- Rerank 模型：对候选文档重新排序；
- 视觉模型：理解图片、扫描件或图表；
- 小模型：做分类、路由、轻量抽取或低成本任务；
- 大模型：处理复杂推理、长文本、工具编排或高质量回答；
- 云模型：快速获得能力或承载峰值；
- 自部署模型：满足数据边界、稳定成本或特定控制需求；
- 不同版本：灰度验证、回滚、A/B 对比。

因此，“只有一个模型”不是架构成熟的标志，“模型越多”也不是能力强的标志。关键是每增加一个模型，是否有明确的任务边界、质量验收、成本收益和治理方式。

### 2. 物理模型名与逻辑模型名

供应商实际模型 ID 往往带有平台和版本特征，例如：

```text
provider-a-model-x
provider-b-model-y-2026-01
self-hosted-model-z-q4
```

如果业务代码直接依赖这些名字，就会把供应商和部署细节扩散到各处。更稳健的做法是定义内部的**逻辑模型名**：

```text
support_chat_default
support_chat_high_quality
knowledge_embedding_zh
policy_rerank_default
document_vision_extract
```

然后由模型配置或网关把逻辑名解析为当前实际模型和接入方式：

```text
support_chat_default
  -> 云模型 A 的实际 ID（主）
  -> 自部署模型 B（备用）
```

逻辑名不是为了隐藏所有信息，而是为了让业务表达“我要客服默认能力”，而不是“我要某厂商某版本字符串”。模型更换、灰度和回退就能在集中配置中完成。

### 3. 路由、负载均衡、回退、重试和降级不是同义词

这些概念经常混用，必须分开：

- **路由（routing）**：在请求开始前，根据策略选择目标模型或提供方。
- **负载均衡（load balancing）**：在同一模型的多个健康副本中选择一个实例。
- **重试（retry）**：同一路径因可能短暂的失败再次尝试，通常有次数和退避上限。
- **回退（fallback）**：当前模型/提供方不可用或不适合时，切换到预先定义的替代路径。
- **熔断（circuit breaking）**：发现某依赖持续失败后，暂时停止向它继续发请求，避免重试风暴和无谓等待。
- **降级（degradation）**：资源或依赖受限时，主动降低非关键能力、质量、输出长度或交互方式，以保证核心服务仍可用。

示例：

```text
路由：普通问答先选 support_chat_default
负载均衡：在该模型的 3 个副本中选副本 2
重试：网络读超时后等待 200ms 再试一次
熔断：该提供方连续错误过多，30 秒内不再选它
回退：切到备用云模型或自部署模型
降级：将“深度分析 + 多轮工具”改为“简短说明 + 人工入口”
```

正确区分它们，才能避免故障时出现“重试后回退，回退后又重试，循环切换”的混乱行为。

### 4. 模型能力不是单一“强弱分数”

很多选择失败，是因为只用“这个模型更聪明/更便宜”描述能力。实际上能力至少包含：

- 文本语言与领域质量；
- 上下文窗口与长文本稳定性；
- 结构化输出和 JSON Schema 支持；
- 工具调用、并行调用、视觉/音频等多模态能力；
- Embedding 维度、语言覆盖和检索效果；
- Rerank 的相关性与延迟；
- 流式支持、TTFT、吞吐和并发上限；
- 数据地域、保留政策、许可证；
- 价格、配额、可用性和供应商支持；
- API 兼容程度、错误语义与观测能力。

因此一个模型的“最好”只能相对于某类任务、约束和指标而言。多模型路由的输入不是情绪化偏好，而是结构化能力与业务约束。

### 5. 决策必须可解释

若用户问“为什么这次回答变慢/变短/质量不同”，系统应该能解释至少一部分事实：

- 请求使用了哪个逻辑模型和实际版本；
- 路由命中了哪条规则；
- 是否因限流、熔断或成本策略发生回退；
- 是否存在缩短输出、关闭工具、异步化等降级；
- 请求是否被安全或权限策略限制；
- 哪个追踪 ID 可用于进一步排查。

这不意味着要向普通用户暴露内部供应商与安全规则细节，而是系统内部必须保留可审计依据。不可解释的智能路由会让调试、成本控制和责任划分都很困难。

## 本节主题系统讲解

### 1. 模型网关、应用适配层与业务服务的边界

可以从请求流理解：

```text
业务 API / AI 应用
  负责：用户身份、权限、领域数据、Prompt、RAG、工具语义
       |
       v
模型适配层或模型网关
  负责：逻辑模型解析、协议适配、密钥、配额、路由、观测、回退
       |
       v
模型提供方 / 自部署模型服务
  负责：实际推理、模型实例、GPU、基础 API
```

**应用内适配层**适合早期或调用方不多时使用。它可以把请求和响应标准化，但仍与具体应用一起部署。

**独立模型网关**适合多个业务服务共用模型、供应商/模型较多、成本/配额/审计需要集中治理的阶段。它将共性策略独立出来。

无论采用哪种形式，以下原则不变：

- 业务服务不应到处保存外部供应商密钥；
- 模型网关不应代替领域授权和业务规则；
- 适配层应保留提供方差异，而不是假装所有能力完全相同；
- 路由规则应可配置、可审计、可测试，不能只散落在 if/else 中。

### 2. 最小模型目录（model catalog）

多模型系统需要一份受版本管理的模型目录。它可以是配置、数据库表或平台资源，但概念上至少包含：

| 字段类别 | 典型内容 |
| --- | --- |
| 身份 | 逻辑模型名、实际模型 ID、提供方、部署区域、版本 |
| 用途 | chat、embedding、rerank、vision、classification 等 |
| 能力 | 流式、工具、JSON Schema、视觉、最大上下文、最大输出 |
| 性能 | 预期 TTFT、吞吐、并发、超时预算、健康状态 |
| 成本 | 输入/输出计价或内部单位成本、预算标签 |
| 治理 | 数据边界、许可、允许的环境/租户、审计级别 |
| 生命周期 | draft、canary、active、deprecated、disabled |
| 回退 | 主路径、备用路径、禁止回退的场景 |

模型目录不是文档摆设。路由、启动校验、能力检查、成本聚合、发布和回滚都应以它为事实来源或至少与它保持一致。

### 3. 能力矩阵：先判断“能不能”，再判断“选哪个”

一个简单能力矩阵可表示为：

| 逻辑模型 | 任务 | 工具调用 | JSON Schema | 流式 | 视觉 | 数据可外发 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| support_chat_default | chat | 是 | 是 | 是 | 否 | 可 | active |
| support_chat_private | chat | 部分 | 是 | 是 | 否 | 不可 | active |
| knowledge_embedding_zh | embedding | 不适用 | 不适用 | 不适用 | 否 | 可 | active |
| doc_vision_extract | vision | 否 | 部分 | 否 | 是 | 受限 | canary |

某个请求要求“上传图片 + 工具调用 + 数据不得外发”时，路由第一步不是比较价格，而是过滤掉能力和治理不满足的模型。否则可能把请求送到根本不能处理图片、没有工具协议或不允许处理敏感数据的服务。

### 4. 静态路由：最简单也最常用的起点

静态路由由开发或配置人员事先指定：

```text
客服聊天 -> support_chat_default
中文 Embedding -> knowledge_embedding_zh
政策文档重排 -> policy_rerank_default
```

它的优点：

- 易于理解、测试和审计；
- 输出行为相对稳定；
- 成本可预测；
- 对少量任务足够。

缺点：面对不同难度、不同租户、不同数据边界或供应商故障时不够灵活。

建议：即使未来会引入智能路由，也先把静态主路径、回退路径和禁止条件写清楚。没有稳定基线的“自动优化”无法判断是否真的变好。

### 5. 规则路由：把业务约束显式化

规则路由根据可解释条件选择路径，例如：

```text
若数据等级 = confidential
  -> 只允许 private/self-hosted 模型

若任务 = embedding
  -> 选择 embedding 模型，不可走 chat 模型

若请求需要 JSON Schema
  -> 只从 supports_json_schema = true 的候选中选

若用户为免费层且任务是低风险摘要
  -> 使用经济型模型，限制最大输出

若会话进入人工接管
  -> 不再调用生成模型，只返回状态与人工流程
```

规则本质上是一种业务政策。它应该使用明确、可测试的输入字段，而不是让模型在运行时“猜该用哪个模型”。对数据外发、安全能力、任务类型等硬约束，规则通常比学习式路由更可靠。

### 6. 质量路由：难度、风险和质量门槛

质量路由试图让简单任务用轻量模型，复杂或高风险任务用更强模型。可能依据：

- 任务类型：分类、抽取、摘要、复杂问答、代码、Agent；
- 输入长度与结构；
- 是否需要工具、结构化输出、多语言或视觉；
- 规则打分或小模型分类结果；
- 置信度、验证器结果、RAG 引用充分性；
- 用户等级、业务风险、人工复核要求。

合理示例：

```text
固定标签分类 -> 小模型或规则
短 FAQ 且检索命中充分 -> 经济型聊天模型
涉及退款承诺或复杂订单异常 -> 高质量模型 + 引用/人工规则
需要写操作工具 -> 满足工具/结构化能力的模型 + 确认链路
```

质量路由的最大风险是错误分类：把难题误送给弱模型，用户得到低质量答案且系统可能毫无察觉。因此要有保守边界、离线评测、线上抽样和升级路径，不能仅因为“模型路由器预测简单”就降低高风险任务质量。

### 7. 成本路由：成本是约束，不是唯一目标

成本路由通常考虑：

- 不同模型输入/输出 Token 成本；
- 自部署 GPU 的固定成本、利用率和边际成本；
- 长上下文、工具定义、RAG 文档带来的 Token 放大；
- 重试、回退、多轮 Agent 导致的调用次数；
- 用户、租户、任务或环境的预算；
- 缓存命中、批处理和异步化带来的节省。

简单策略可能是“预算低就选便宜模型”，但这常导致质量债务。更健康的顺序是：

1. 先确保安全、数据边界和最低质量门槛；
2. 在满足门槛的候选中比较成本与性能；
3. 控制无效 Token，例如过长历史、重复 Prompt、无意义重试；
4. 对高成本任务建立预算、告警、采样复核和人工升级；
5. 评估端到端业务成本，而不只看单次模型价格。

例如一个便宜模型若经常答错，导致重复提问、人工介入和工单升级，整体成本可能高于一次使用更适合模型。

### 8. 健康路由与回退链路

健康路由依据实时或近实时信号避开异常路径：

- 持续 5xx、连接失败、超时；
- 429 限流或配额不足；
- P95 TTFT 显著变差；
- 自部署副本不就绪、队列过长、显存紧张；
- 特定模型版本质量回归或结构化输出失败率异常。

一个概念性的回退树：

```text
support_chat_default
  -> 主：云模型 A
  -> 备用 1：自部署模型 B
  -> 备用 2：云模型 C
  -> 最终降级：返回简短模板 + 人工入口
```

但回退不是越多越好。每一级都必须验证：

- 它是否满足数据与区域约束；
- 它是否支持当前请求所需能力；
- 输出是否可被后续解析/工具链使用；
- 切换是否会造成重复副作用；
- 它的成本是否可能在故障时暴涨；
- 对用户是否需要提示服务正在降级。

### 9. 熔断：让坏路径暂时停止被选择

若某提供方连续超时，所有请求都先等待超时、重试、再回退，会使用户延迟急剧增加，也会给故障服务施加更多压力。

熔断器可以有三个简化状态：

```text
Closed（关闭）：正常放行并统计错误
Open（打开）：暂时直接拒绝/绕过该路径，不再真实调用
Half-open（半开）：间隔性放少量探测请求，判断是否恢复
```

熔断的关键不是“遇到一次错误就永远禁用”，而是基于一段时间内的失败率、超时率、连续错误或延迟阈值做受控判断，并设置恢复探测。阈值过低会造成误切换；阈值过高则不能及时保护用户。

熔断应按合理粒度设计，例如按提供方、区域、模型版本或特定端点。若一个 Embedding 端点异常，不一定要熔断同提供方的所有聊天模型；反之若网络出口整体失效，过细粒度也无意义。

### 10. 重试与回退的正确顺序

不存在所有情况通用的固定顺序，但可用以下原则：

1. 先判断是否是不可重试错误：参数、权限、上下文超限、能力不支持通常不应重试。
2. 对可能瞬态的错误，做极少次数、带退避和总时间预算的重试。
3. 若错误表明当前路径不健康、容量不足或预算耗尽，触发回退/熔断评估。
4. 回退前再次验证候选模型能力、数据边界和副作用风险。
5. 达到最终降级路径时，明确返回受控结果，而不是无限循环。

例如：

```text
请求主模型
-> 连接瞬断：最多重试一次
-> 仍失败且健康信号恶化：熔断主路径
-> 选择满足约束的备用模型
-> 备用模型不支持当前 JSON Schema：不能使用，改走受控失败/人工路径
```

必须设置“总尝试次数”和“端到端截止时间”。否则多层 SDK、网关、应用各自重试一次，就会叠加成大量隐藏调用。

### 11. 降级的层次：不是只有换模型

当系统受限时，降级可以发生在多个层面：

| 层次 | 例子 | 主要风险 |
| --- | --- | --- |
| 交互 | 从实时流式改为异步任务 | 用户等待与状态感知 |
| 输出 | 限制最大输出、减少格式化 | 信息不足、体验下降 |
| 上下文 | 减少历史、缩短检索候选 | 事实性和上下文丢失 |
| 模型 | 切到更轻量/备用模型 | 质量、工具/Schema 能力差异 |
| Agent | 关闭多轮反思或非关键工具 | 完成度下降 |
| 业务 | 转人工、返回模板化说明 | 人工成本、用户体验 |

降级应该按业务风险分级。对于“帮我总结一篇公开文章”，缩短输出可能可以接受；对于“是否给用户退款”或“执行写操作”，不能因为模型服务压力大就跳过权限、确认或审计。

### 12. 多模型路由中的数据治理

模型路由不能只看能力和价格，还要在请求进入外部服务前检查数据规则：

- 这段数据是否包含个人信息、订单信息、源代码、合同或内部文档？
- 当前用户/租户是否允许数据离开指定地域或私有网络？
- 供应商是否会保留、训练或审计请求内容？
- 是否需要脱敏、最小化、摘要化或字段过滤？
- 回退模型是否有同样的数据处理许可？

最危险的情况是：主模型是私有部署，故障时自动回退到外部云模型，却没有重新判断数据外发策略。回退路径与主路径一样是数据治理对象，不能被当作“技术细节”。

### 13. 路由与 Prompt/输出契约的兼容性

不同模型可能使用不同 Tokenizer、聊天模板、结构化输出机制和工具调用格式。即使 API 是 OpenAI 兼容，也要检查：

- 系统提示与角色消息的支持是否一致；
- JSON Schema/response format 的严格性是否相同；
- `tool_calls`、调用 ID、参数增量的格式是否可被后续链路处理；
- 上下文窗口和最大输出是否满足当前 Prompt；
- 安全过滤或推理模式是否改变输出；
- 流式结束事件、usage 和错误语义是否可兼容。

因此，多模型系统通常需要一个**内部统一结果模型**。它不必抹平所有差异，而是至少把应用真正依赖的字段（文本、结构化对象、工具调用、usage、finish reason、trace、错误分类）标准化，并把无法统一的能力显式标识。

### 14. 路由策略的测试与评估

路由策略本身也是生产逻辑，需要测试。至少应覆盖：

- 给定任务/数据等级/能力要求，是否选到允许模型；
- 高风险任务是否绝不会落入低保障路径；
- 主路径失败时是否按预期回退，而不是循环；
- 回退路径能否真正处理当前 Schema、工具或上下文；
- 熔断阈值触发和恢复是否正确；
- 预算达到阈值时是否按策略限额或降级；
- 日志、Trace 和成本标签是否完整；
- 新模型/新规则灰度时的质量、延迟和成本是否达标。

模型路由还需结合离线数据集与线上观察。只测试“能否返回 200”不够，因为最危险的问题往往是返回了 200 却使用了不合格模型、错误回退或质量明显变差。

### 15. 防止路由复杂度失控

多模型策略很容易变成难以维护的规则迷宫。可采用以下约束：

1. 先按任务类型建立少量稳定的逻辑模型名。
2. 将不可违反的规则（数据、能力、安全）与可优化规则（成本、延迟）分开。
3. 每个逻辑模型保留简短、明确、经过验证的回退链，而不是无限候选。
4. 把模型版本、能力和价格集中记录，不在业务代码中复制。
5. 路由变更同样需要评审、灰度、指标和回滚。
6. 定期清理已下线模型、过期规则和从未命中的回退路径。
7. 为每次实际决策记录结构化原因码，而不是只记录一段自然语言日志。

好路由不是规则最多，而是在系统当前复杂度下最少且足够的规则。

### 16. 一个客服 AI 的概念性策略

假设有以下逻辑模型：

```text
support_chat_standard
support_chat_sensitive
support_embedding
support_rerank
```

可能的策略如下：

```text
任务是检索：固定使用 support_embedding + support_rerank

任务是普通 FAQ：
  数据可外发、工具不需要、风险低
  -> support_chat_standard 的主模型

任务涉及订单详情或退款：
  先由业务层做权限和数据过滤
  若数据不可外发 -> support_chat_sensitive 的私有路径
  若要创建工单 -> 必须选择支持结构化工具调用的模型

主模型出现短暂网络错误：
  在总预算内有限重试
  若健康熔断 -> 选择满足相同数据/能力条件的备用模型
  若无合格备用 -> 提供人工入口，不把敏感数据发到不允许的服务
```

注意其中最关键的一句不是“选哪个模型”，而是“先由业务层做权限和数据过滤”。网关可选择模型，但不能替代业务可信边界。

### 17. 需要记录的路由审计事件

为了复盘和治理，一次模型调用可记录（按隐私最小化原则）：

- 请求/Trace ID；
- 调用服务、租户/业务场景标签；
- 逻辑模型名；
- 主候选与最终实际模型/版本/区域；
- 需要的能力与路由命中规则 ID；
- 是否命中缓存、重试、熔断、回退或降级；
- 输入/输出 Token、耗时、TTFT、状态和错误类别；
- 成本或配额扣减；
- 数据等级/脱敏是否执行；
- 工具/结构化输出是否成功。

不要默认记录完整 Prompt 或全部模型输出。审计应服务于定位、合规和成本，而不是制造新的敏感数据副本。

## 常见误区

### 误区 1：模型网关就是一个转发代理

纠正：最小网关可以只是转发，但它的工程价值在于统一模型名、密钥、能力检查、限流、路由、审计、成本和回退。若只转发而没有策略边界，可能只是多了一跳网络。

### 误区 2：多模型路由就是让模型自己决定调用哪个模型

纠正：高风险约束，例如数据外发、权限、能力和预算，必须由确定性规则或受控策略处理。模型可辅助分类或提出建议，但不能成为唯一裁决者。

### 误区 3：主模型失败就随便换任意可用模型

纠正：备用模型必须满足当前任务的能力、数据地域、结构化输出、工具协议、质量和成本约束。无合格备用时，受控失败或转人工比错误回退更安全。

### 误区 4：回退链越长，可用性越高

纠正：过长链路会增加延迟、成本、语义不兼容和调试难度，还可能产生循环。应保持短而经过验证的回退树，并设总尝试预算。

### 误区 5：按单价选最便宜模型就是成本优化

纠正：端到端成本还包含失败重试、人工介入、用户重复提问、长上下文、工具链和质量损失。应先满足最低质量与安全门槛，再比较成本。

### 误区 6：熔断就是永久禁用一个模型

纠正：熔断通常是临时保护机制，包含关闭、打开和半开探测状态。它应根据可观测信号自动或受控恢复，而不是一次错误永久下线。

### 误区 7：模型 API 兼容就不需要适配层

纠正：基础调用可复用 SDK，但模型名、能力、错误、流式、用量、数据政策和性能仍有差异。适配层负责把应用真正依赖的语义稳定下来。

## 本节练习

### 练习 1：区分概念

某模型服务返回 503，系统等待 300ms 后又调用同一模型一次；仍失败后，将后续请求在 1 分钟内改发备用模型；同时把这段时间的长文档任务改为异步。请分别指出重试、熔断/回退、降级的部分。

答案：等待 300ms 后再次调用同一模型是重试；在持续失败后短时间不再选择主模型、改发备用模型，包含熔断与回退；把长文档任务从同步改为异步是交互层降级。它们解决的问题不同，应分别记录和配置。

### 练习 2：设计能力过滤

某请求包含敏感订单信息，需要严格 JSON Schema 输出，并且可能要求工具调用。请列出在比较价格和延迟之前，候选模型必须满足的至少四项条件。

答案：数据处理政策/地域允许处理该敏感数据；支持当前所需的 JSON Schema 或等价可靠结构化输出机制；支持工具调用及当前工具协议；上下文窗口足以容纳 Prompt、订单信息、Schema 和预期输出；当前凭证/租户有权限调用；服务健康且未被熔断。满足这些硬条件后才适合比较质量、延迟和成本。

### 练习 3：分析错误回退

主模型是私有部署，备用模型是外部云服务。系统在私有模型故障时直接把原始用户请求转发给外部云模型。这个设计至少有什么风险？

答案：可能违反敏感数据不可外发、地域或合同约束；外部模型可能不支持相同工具/Schema/上下文；用户未必被告知处理路径变化；成本可能在故障时飙升；原始请求可能包含不应写入外部日志的内容。回退前必须重新做数据、能力和业务风险检查；无合格路径时应受控失败或转人工。

### 练习 4：写一个最小逻辑模型目录条目

为 `support_chat_default` 写出至少八项应该记录的字段。

答案：可包括逻辑模型名、实际模型 ID、提供方、区域、模型版本、任务类型、最大上下文/输出、是否支持流式、是否支持工具、是否支持 JSON Schema、状态、主/备用路径、超时预算、并发/配额、成本标签、允许的数据等级、上线时间和负责人。字段应服务实际路由和治理。

### 练习 5：为什么路由需要审计原因码

为什么只在日志里写“selected model B”不够？

答案：你还需要知道为什么没有选主模型，是否因为能力过滤、预算、租户规则、灰度、熔断、超时或数据策略；也需要知道是否发生降级。结构化原因码可以支持聚合、告警、成本复盘、质量对比和责任追溯，而自然语言日志难以稳定分析。

## 自测题

### 自测 1：逻辑模型名有什么价值？

答案：它让业务表达稳定的能力需求，而不是绑定供应商和物理部署细节。模型升级、切换、灰度和回退可在集中配置或网关完成，减少业务代码中的散落字符串和迁移成本。

### 自测 2：模型能力矩阵为什么应先于成本路由？

答案：如果模型不支持任务所需的工具、JSON Schema、上下文、数据边界或权限，再便宜也不能使用。能力和治理是硬约束；成本通常是在合格候选集内的优化维度。

### 自测 3：什么情况下不应该重试？

答案：请求参数非法、身份凭证无效、权限不足、上下文超限、模型不支持所需能力等确定性错误通常不应原样重试。对可能已有副作用或服务端可能已执行的请求也需谨慎，避免重复操作。

### 自测 4：为什么要给回退链设置总时间和次数预算？

答案：避免应用、SDK、网关和提供方多层重试叠加，造成用户等待过长、成本激增、故障放大和循环路由。预算让系统在有限时间内做出明确的成功、回退或受控失败决定。

### 自测 5：模型网关不能替代什么？

答案：不能替代业务身份认证、领域权限、数据所有权判断、RAG 权限过滤、工具副作用确认、订单规则和人工审批。它处理通用模型治理，业务/AI 应用层处理领域语义与可信边界。

## 本节小结

本节建立了多模型治理的核心框架：用逻辑模型名和模型目录隔离业务与物理模型，用能力矩阵先过滤不合格候选，再在质量、延迟和成本之间做可解释路由；用有限重试、健康检查、熔断、回退和多层降级应对故障与容量压力。

模型网关的目标不是制造一层万能代理，而是集中跨应用的密钥、配额、版本、路由、审计和成本控制。无论网关是应用内模块还是独立服务，安全数据边界、业务权限、工具确认和领域规则都必须留在正确的业务层。
