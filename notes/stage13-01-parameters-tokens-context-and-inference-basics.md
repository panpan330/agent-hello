# M13 第 1 节：模型参数、Token、上下文窗口与推理基础

## 本节定位

上一节建立了模型生命周期全景：模型权重由训练得到，推理引擎加载权重，模型服务把能力提供给应用。本节进一步进入一次模型请求的内部视角：当你发送一段文本给聊天模型时，文本如何进入模型？模型怎样一点点生成回答？为什么输入很长会更贵更慢？为什么 `max_tokens`、上下文窗口、temperature、stop 等参数会影响结果？

这些概念不仅是调用 API 时的参数说明。它们解释了后续许多工程现象：

```text
为什么长 RAG 上下文会拖慢响应；
为什么流式输出能更快让用户看到首字；
为什么不同语言的同样长度文本成本不同；
为什么模型会因为上下文太长而报错、截断或“忘记”早期内容；
为什么并发推理和 KV Cache 与 token 强相关；
为什么同一个问题多问几次，回答可能不同。
```

本节不要求你推导深度学习数学，也不把模型描述成不可理解的魔法。你要建立的是足够准确的工程模型：文本先被编码为 token，模型在固定上下文容量内依据参数计算下一个 token 的概率，再按解码规则逐步生成，直到满足停止条件。

## 本节学习目标

学完后，你应当能：

1. 解释参数量、权重、token、token ID、词表和 tokenizer 的关系。
2. 理解文本为什么要先被切分为 token，而 token 不等于字或单词。
3. 描述生成模型“逐 token 预测”的基本过程。
4. 区分输入 token、输出 token、上下文窗口和输出上限。
5. 判断上下文过长、输出截断、长 Prompt 成本高等现象的原因。
6. 理解 temperature、top-p、top-k、max tokens、stop 等常见生成控制概念。
7. 知道哪些模型行为由概率决定，哪些必须由应用系统和工具校验保证。

## 一句话先讲透

> 生成式语言模型并不是一次性写完整答案，而是在有限上下文中，利用固定参数反复计算“下一个 token 最可能是什么”；输入、历史、RAG、工具结果和已生成文本都会占用上下文与计算资源，因此 token 和上下文设计直接决定模型质量、速度与成本。

## 基础知识铺垫

### 1. 参数量到底表示什么

上一节说过，模型参数是训练得到的大量数值。现在进一步建立工程直觉。

假设一个模型有 `7B` 参数，大意是它的神经网络中约有 70 亿个可学习数值。这些数值分布在不同层和矩阵中，共同决定模型遇到某段 token 序列时会给下一个 token 分配怎样的概率。

参数量会影响：

- 模型文件大小；
- 加载模型所需内存/显存；
- 每次推理需要的计算量；
- 可表达和学习到的模式容量；
- 部署成本和可支持并发。

但参数量**不直接等于**：

- 模型精确记住了多少篇文章；
- 模型一定更懂某个专业领域；
- 模型上下文窗口一定更长；
- 模型回答一定更可靠、更安全；
- 模型运行一定更慢或一定更快。

模型质量由参数量、架构、训练数据、训练方法、推理方式、对齐、上下文、工具和应用控制共同决定。参数量是重要指标，但不能单独作为选型结论。

### 2. 从字符到 token：为什么不能把文本直接喂给模型

计算机内部处理的是数值。自然语言文本需要先变为模型可计算的整数序列。Tokenizer 完成的就是：

```text
文本
-> 按某种词表与规则拆分
-> token 片段
-> 每个片段映射为 token ID（整数）
```

概念例子：

```text
"订单 A1001 已发货。"
-> ["订单", " A", "100", "1", " 已", "发货", "。"]
-> [id_1, id_2, id_3, id_4, id_5, id_6, id_7]
```

这只是示意，不代表任何具体模型一定按这样切分。不同 tokenizer 对同一文本的 token 数可能不同。

Tokenizer 的存在有三个主要原因：

1. 词表把可处理符号限制在有限集合内；
2. token 比单字符或完整单词更适合在通用语言、代码、数字和罕见词之间平衡；
3. 模型可以对 token ID 序列进行统一数学计算。

### 3. Token 不等于字，不等于词，也不等于字符数

这是 AI 工程里必须牢牢记住的一点。

| 单位 | 描述 | 与 token 的关系 |
| --- | --- | --- |
| 字符 | 一个汉字、字母、数字、标点或空格 | 一个 token 可包含一个或多个字符 |
| 单词 | 自然语言中的词汇单位 | 一个单词可能被拆成多个 token，也可能与其他片段合并 |
| 字节 | 计算机编码存储单位 | 与 token 没有固定比例 |
| token | tokenizer 定义的模型输入/输出单位 | 由具体模型 tokenizer 决定 |

例如：

- 常见英文单词可能是一个 token，也可能因前导空格、词形变化而不同；
- 少见英文词、长数字串、URL、代码标识符通常可能被拆成多个 token；
- 中文一句话中的一个汉字可能对应一个或多个 token，也可能与相邻字符形成片段；
- 表情、标点、换行、空格和特殊字符都会影响 token 数。

因此，不能用“500 个汉字一定等于 500 token”或“英文一个单词一定一个 token”做精确估算。真实系统应使用目标模型的 tokenizer 或供应商返回的 usage 数据统计。

### 4. 词表（Vocabulary）是什么

词表是 tokenizer 能识别和映射的一组 token 单位。可以把它理解为一个映射表：

```text
token 片段 <-> token ID
```

词表大小是模型设计的一部分。词表较大时，可能能用较少 token 表示常见片段；词表较小时，表示稀有内容可能需要更多拆分。两者还会影响 embedding 矩阵大小、训练和推理成本。

对应用工程师而言，最重要的不是背某个模型的词表数量，而是知道：

- tokenizer 与模型必须匹配；
- token 计数是成本、上下文和限额的基础；
- 特殊 token 往往控制消息边界、角色、开始/结束等语义；
- 不要自己随意拼接底层 token ID 或假设某段字符串必定只占一个 token。

### 5. 特殊 token：模型并不只处理普通文本

模型的 token 序列中常存在特殊标记，用于表达：

- 文本开始与结束；
- 消息角色边界，例如 system/user/assistant；
- 工具调用或结构化输出边界；
- 填充（padding）和批处理长度对齐；
- 文本片段、文件/图像等多模态边界（具体取决于模型）。

这意味着你看到的聊天消息：

```text
system: ...
user: ...
assistant: ...
```

在模型真正看到的内部序列中，通常会被格式化成包含特殊 token 的统一模板。不同模型的聊天模板不同，因此不能假设任意模型都能理解同一种手写格式。

对于 SDK/API 使用者，通常由供应商或框架完成这些格式化。但理解其存在有助于你知道：系统提示、角色消息、工具定义本身也会占用上下文 token。

### 6. 上下文（Context）是什么

上下文是模型在当前一次推理中能够读取的 token 序列。对聊天/Agent 请求，它可能包括：

```text
系统提示
+ 开发者/应用规则
+ 历史用户与助手消息
+ 当前用户输入
+ RAG 检索片段
+ 工具定义/schema
+ 工具调用结果 observation
+ 已生成的输出 token
```

上下文并不是只指“用户问的问题”。任何放进模型请求的内容都可能占用上下文预算。

可以把一次请求写成：

```text
total_context_tokens
= input_tokens
+ generated_output_tokens
```

模型最大允许的 `total_context_tokens` 被称为上下文窗口（context window）。不同模型和服务配置的窗口大小可能不同。

### 7. 输入 token、输出 token 与总上下文

理解这三个概念是后续所有性能和成本讨论的基础。

#### 7.1 输入 token（Input / Prompt Tokens）

输入 token 是模型在开始生成前需要读取的全部内容：系统提示、历史、用户问题、工具 schema、RAG 片段等。

输入越长，通常意味着：

- 需要更多预处理计算；
- 可能花费更多 token 成本；
- 留给输出的上下文空间更少；
- 更容易把模型注意力分散到无关信息上。

#### 7.2 输出 token（Output / Completion Tokens）

输出 token 是模型逐步生成的结果。它包括最终自然语言，也可能包括结构化 JSON、工具调用参数或思考/推理相关输出（取决于模型和 API 行为）。

输出越长，通常意味着：

- 用户等待完整结果的时间更长；
- 成本更高；
- 占用服务并发资源更久；
- 更容易出现跑题、重复或格式漂移。

#### 7.3 总上下文预算

模型需要同时容纳输入和输出：

```text
输入 token + 最大可能输出 token <= 上下文窗口
```

若输入已经很长，却还请求很大的输出上限，服务可能拒绝请求、自动缩短可生成长度，或在生成中截断。不同供应商的行为不同，但应用应主动管理预算，而不是把它交给偶然结果。

### 8. 上下文窗口不是“无限记忆”

大上下文窗口让单次请求能携带更多内容，但它不等于模型拥有永久记忆，也不保证模型会同样重视窗口内每一段信息。

重要区别：

| 概念 | 它解决什么 | 它不保证什么 |
| --- | --- | --- |
| 上下文窗口 | 单次请求最多能放多少 token | 内容正确、相关、被充分利用 |
| 会话记忆 | 跨轮次保存和挑选历史 | 自动拥有权威事实 |
| RAG | 从外部知识中检索相关内容 | 检索结果一定正确或有权限 |
| 任务状态 | 长任务当前运行到哪里 | 模型天然记住全部过程 |

把整个数据库、所有历史聊天和所有工具日志都塞入长上下文，通常不是好设计。你在 M12 学过的记忆准入、RAG 检索、artifact 引用、工作记忆和最小上下文原则，在模型推理层同样适用。

### 9. 什么是“下一个 token 预测”

生成式语言模型的核心任务可以简化为：给定已出现的 token 序列，预测下一个 token 的概率分布。

```text
已有序列： [t1, t2, t3, ... tn]
模型输出：词表中每个候选 token 的概率
选择一个 token：t(n+1)
将 t(n+1) 加回序列
继续预测下一个 token
```

例如模型已看到：

```text
“中国的首都是”
```

它会给不同候选 token 分配不同概率，`“北京”`相关 token 的概率通常较高。模型最终输出什么，还会受采样/解码策略影响。

这并不意味着模型只是简单查表。模型会通过多层网络计算上下文中 token 的关系。但从应用工程角度，逐 token 生成足以解释延迟、流式和输出长度等行为。

### 10. 概率分布与“模型会不会胡说”

模型每一步输出的是“在当前上下文下什么 token 更可能出现”，而不是一个外部世界事实验证器。即使某段文本很流畅，仍可能：

- 使用了过期的训练知识；
- 在缺少事实时补全了看似合理内容；
- 误解用户问题；
- 忽略了 RAG 中关键限定条件；
- 生成格式不完整；
- 被不可信上下文诱导。

因此：

```text
高概率文本
≠ 已验证事实
≠ 有权限执行的动作
≠ 符合业务状态的结果
```

这也是为什么之前阶段反复强调：权威事实来自业务工具/RAG 来源，工具调用由服务端校验，写操作需确认和幂等，最终质量需要评估。

## 本节主题系统讲解

### 1. 一次聊天生成请求的完整过程

下面用一个简化但完整的过程说明用户问问题后发生什么：

```text
1. 应用准备请求
2. 聊天模板与工具定义被编码
3. tokenizer 产生输入 token IDs
4. 服务检查上下文、权限、限流、预算
5. 推理引擎处理输入 token（prefill）
6. 模型生成第一个输出 token
7. 重复生成后续 token（decode）
8. 满足停止条件
9. tokenizer 解码输出
10. 服务返回非流式结果或持续流式发送 token
```

下面逐步理解。

#### 第 1 步：应用准备请求

应用决定哪些内容真正进入模型：系统规则、当前用户问题、必要历史、RAG 片段、工具列表、任务状态摘要等。这一步决定模型的可见世界。

应用不应把所有可获得信息都塞进去。它要完成权限过滤、来源标记、长度控制、敏感字段去除和任务相关性选择。

#### 第 2 步：格式化消息

模型通常需要某种聊天模板来区分系统、用户、助手、工具等角色。SDK/服务会将逻辑消息格式化为适合该模型的 token 序列。

这一步解释了为什么“同样的文字，放在 system 与 user 中效果不同”，也解释了为什么工具 schema 和角色提示会消耗 token。

#### 第 3 步：Tokenization

格式化后的文本被 tokenizer 编码为 token IDs。服务可由此统计输入 token 数，并检查是否超过模型上下文限制或调用方预算。

#### 第 4 步：策略与容量检查

在企业系统中，模型服务或网关还应检查：

- 认证与模型调用权限；
- 每用户/租户速率限制；
- 输入大小和上下文预算；
- 是否允许请求的模型/参数；
- 当前并发、队列与成本预算；
- 内容/安全策略（按场景）。

这些检查通常在模型真正开始计算之前发生。

#### 第 5 步：Prefill（处理输入上下文）

推理引擎先读取整个输入 token 序列，计算模型内部状态。工程上常把这段称为 prefill 或 prompt processing。

输入很长时，prefill 往往是首字延迟（用户等待第一个 token）的重要来源之一。后续学习 KV Cache 时会进一步解释为什么这一步的结果可被用于后续逐 token 生成。

#### 第 6-7 步：Decode（逐 token 生成）

模型基于当前上下文计算下一个 token 概率，按照解码策略选择 token，再继续计算下一个。这是一个重复过程。

```text
当前上下文 -> 生成 token 1
上下文 + token 1 -> 生成 token 2
上下文 + token 1 + token 2 -> 生成 token 3
...
```

输出越长，decode 循环次数越多。流式输出通常能在第一个或前几个 token 生成后立即发送给客户端，无需等到整段完成。

#### 第 8 步：停止

模型不会无限生成。服务通常在满足某种停止条件后结束，后面会详细讲。

#### 第 9-10 步：解码与返回

token IDs 被 tokenizer 转回文本，服务再将其包装为 API 响应、SSE 流片段或结构化输出。业务应用还应进行 schema、引用、安全和工具协议等后处理。

### 2. Prefill 与 Decode：理解延迟的第一把钥匙

一次生成大致有两个性能阶段：

| 阶段 | 做什么 | 主要影响 |
| --- | --- | --- |
| Prefill | 处理全部输入上下文 | 首 token 时间、长 prompt 成本 |
| Decode | 一个个生成输出 token | 输出速度、完整响应时间 |

可以用两个常见指标理解：

```text
TTFT（Time To First Token）：从请求开始到用户看到第一个 token 的时间
TPOT（Time Per Output Token）：后续每个输出 token 的平均生成时间
```

即使最终答案很短，若输入包含极长历史、RAG 文档和工具 schema，TTFT 仍可能很高；即使首字很快，若要求生成很长报告，完整完成时间仍会很长。

这对用户体验有直接影响：聊天场景常重视 TTFT，离线报告场景更重视总吞吐与任务完成时间。

### 3. 上下文窗口如何分配

设某模型上下文窗口为 `C`，当前输入 token 为 `I`，你希望最多生成 `O` token，那么必须满足：

```text
I + O <= C
```

但实际设计还应留出余量：

- 工具调用后可能新增 observation；
- Agent Loop 后续轮次会追加消息；
- 结构化输出可能比自然语言更长；
- 供应商可能对请求/输出另有内部限制；
- 你可能需要安全提示、引用和错误恢复文本。

因此合理策略不是每次都把窗口塞满，而是为不同内容设预算：

| 内容 | 示例策略 |
| --- | --- |
| 系统规则 | 稳定、精炼，避免重复冗长说明 |
| 会话历史 | 保留最近轮次 + 结构化摘要 |
| RAG 内容 | 检索、重排、去重、限制 chunk 数和长度 |
| 工具 schema | 只暴露当前任务需要的工具 |
| 工具结果 | 字段白名单、摘要、artifact 引用 |
| 输出 | 按任务类型设置合理上限 |

这就是上下文工程（context engineering）的核心思想之一：不是“写更长 prompt”，而是管理模型每一轮真正需要看到的可靠信息。

### 4. 上下文过长时会发生什么

不同模型/服务有不同策略，但常见结果包括：

- 请求直接被拒绝，提示超出上下文窗口；
- 服务自动截断早期消息或某些内容；
- 可生成输出长度被压缩；
- 应用在本地先截断历史/RAG；
- 请求可通过但延迟和成本显著增加；
- 模型在很长内容中忽略关键细节，质量下降。

最后一种特别容易被忽略。即使技术上“能放下”，也不代表模型会稳定利用所有内容。长上下文中常见信息问题：

- 重要规则被大量无关文本淹没；
- 多个文档相互矛盾；
- 早期事实已经过期；
- 不可信内容增加 prompt injection 风险；
- 模型难以定位真正相关片段。

所以你已学的 RAG rerank、metadata filter、引用、记忆准入和 Agent 工作记忆，都是控制上下文质量的手段。

### 5. 输出上限：`max_tokens` / `max_output_tokens` 的含义

不同 API 的字段名称可能略有不同，但核心是限制本次生成允许产生的最大输出 token 数。

它通常用于：

- 防止模型生成过长文本；
- 控制成本和延迟；
- 为上下文窗口预留空间；
- 约束结构化输出的最大规模；
- 防止异常循环或错误提示导致冗长回答。

输出上限不是“要求模型一定生成这么多 token”。模型可能因完成、stop token、结构化结束或其他停止条件提前结束。

如果上限太小，可能出现：

- 回答被截断；
- JSON 缺少闭合括号；
- 工具调用参数不完整；
- 长文没有写完；
- 模型还未给结论就停止。

如果上限太大，则可能增加成本、延迟和跑题风险。应按任务类型配置，例如分类结果通常很短，详细报告需要更大预算，Agent 工具决策应尽量短而结构化。

### 6. 停止条件：模型何时停止生成

常见停止原因包括：

| 停止原因 | 含义 |
| --- | --- |
| EOS（End Of Sequence） | 模型生成了内部结束标记 |
| 达到输出上限 | 生成 token 数达到 max limit |
| 命中 stop sequence | 输出出现调用方设置的停止字符串/标记 |
| 工具调用/结构化协议结束 | 模型完成指定工具或结构化响应 |
| 服务端中断 | 超时、取消、内容策略、连接终止等 |

应用应关注“为什么停止”。如果因为达到输出上限而结束，结果可能不完整；如果因为工具调用协议结束，后续通常需要由 Agent 控制层执行工具再开启新一轮；如果用户取消，应阻止继续产生新副作用。

不能只检查“有返回文本”，还要检查完成原因、结构完整性和业务完成条件。

### 7. 解码（Decoding）与采样：从概率到具体输出

模型计算出候选 token 概率后，还需要一个策略选择具体 token。常见策略可分为更确定和更随机两类。

#### 7.1 贪心解码（Greedy Decoding）

每次都选概率最高的 token：

```text
候选概率最高 -> 直接选它
```

优点是可预测、结果更稳定；缺点是可能过于机械、重复或错过次优但整体更好的表达。在某些结构化/确定性任务中，这种低随机性思路有价值。

#### 7.2 采样（Sampling）

采样会在多个高概率候选中按概率随机选择，使输出更多样。它适合创意、对话、改写等需要变化的场景，但也增加不确定性。

这里要理解：随机性不是“模型突然失控”，而是解码策略有意允许概率较高的多个候选被选中。

### 8. Temperature：调整概率分布的尖锐程度

temperature（温度）是最常见的生成参数之一。概念上：

- 较低 temperature：高概率候选更占优势，输出更稳定、保守；
- 较高 temperature：概率分布更平，更多候选有机会被选中，输出更发散、多样。

可以用直觉图示：

```text
低温度：  北京 0.90，上海 0.05，广州 0.03，其他 0.02
高温度：  北京 0.50，上海 0.20，广州 0.15，其他 0.15
```

真实模型分布比示例复杂得多，但直觉正确。

适用原则：

| 任务 | 通常更倾向 |
| --- | --- |
| 分类、抽取、结构化工具参数 | 低随机性 |
| 事实解释、客服答复 | 较低到中等随机性 |
| 创意写作、多方案头脑风暴 | 可提高随机性 |
| 高风险决策 | 不能只靠降低温度，应加强规则与人工控制 |

低 temperature 不能保证真实正确，也不能防止 prompt injection 或工具越权。它只是减少解码层的随机性。

### 9. Top-k 与 Top-p：限制采样候选范围

除了 temperature，常见还有 top-k 与 top-p。

#### 9.1 Top-k

只从概率最高的 `k` 个候选 token 中选择。例如 top-k = 10，意味着低于前 10 名的候选不会被采样。

#### 9.2 Top-p（Nucleus Sampling）

选择概率累计达到 `p` 的最小候选集合，再在其中采样。例如 top-p = 0.9，大意是只保留累计概率覆盖约 90% 的候选。

它们都在控制“采样从多大范围中选”。实际 API 可能提供其中一个、两个都提供，或有不同默认值。使用时不必机械同时调很多参数；通常先按任务确定较保守或较开放的风格，再用评估集验证。

过度调参而没有任务评估，容易产生一种错觉：好像找到了“万能参数组合”。模型行为仍取决于任务、上下文、版本和工具链。

### 10. 随机种子（Seed）与可复现性

有些服务允许设置随机种子，用于在相同模型、相同输入、相近服务条件下尽量得到可复现的采样结果。它对调试和评估有帮助，但不能被理解为绝对承诺：

- 底层服务版本或并行计算可能变化；
- 服务端实现可能不同；
- 工具/RAG 返回内容可能变化；
- 浮点计算、调度和缓存也可能带来差异。

生产评估应记录完整条件：模型版本、参数、prompt、工具/知识数据版本、时间、seed（如适用），而不只记录“同一个问题”。

### 11. 为什么同一个问题多问几次可能不同

原因可能包括：

1. sampling/temperature 带来的随机性；
2. 历史对话、记忆或 RAG 检索结果发生变化；
3. 工具实时返回的数据不同；
4. 服务端模型版本或路由发生变化；
5. 不同请求的系统提示、工具 schema、上下文裁剪不同；
6. 并发/服务实现导致极小数值差异在逐 token 生成中被放大。

对高稳定性任务，应用应减少不必要随机性、使用结构化输出、固定关键上下文、强化确定性校验，并通过评估观察稳定性。不能只对模型说“每次必须完全一样”。

### 12. Token 与成本：为什么“短问题”未必便宜

用户输入只有一句话，不代表整次调用 token 少。真正成本通常包含：

```text
系统提示
+ 历史消息
+ RAG 内容
+ 工具 schema
+ 工具结果
+ 用户问题
+ 模型输出
```

例如用户只问“那怎么办？”，但系统带入 20 轮历史、10 个 RAG chunk 和多个工具定义，输入 token 仍可能很大。

因此成本优化常常不是让用户少说话，而是：

- 减少重复冗长系统提示；
- 使用会话摘要代替全量历史；
- 做 RAG 检索、rerank 与长度裁剪；
- 按任务暴露最少工具；
- 对工具结果做字段白名单和摘要；
- 为输出设置任务匹配的上限；
- 用更适合的模型/路由处理不同任务。

这也是为什么上下文工程是 AI 应用工程的重要能力。

### 13. Token 与延迟：输入和输出影响不同

输入 token 与输出 token 都会消耗资源，但行为不同：

| 类型 | 主要影响 | 用户体验现象 |
| --- | --- | --- |
| 输入 token 很多 | prefill 计算变重 | 首字出现慢 |
| 输出 token 很多 | decode 循环变长 | 整体完成慢、流持续更久 |
| 两者都很多 | 上下文和计算压力都大 | 又慢又贵，还可能超窗口 |

因此优化方案也不同：

- 首字慢：先看系统提示、历史、RAG、工具 schema 是否过长；
- 输出慢：看输出上限、回答风格、推理模型、流式体验和生成速度；
- 并发慢：看队列、批处理、KV Cache、GPU 资源和服务调度。

M13-04 会系统讲延迟、吞吐和 KV Cache。现在先建立“输入与输出 token 会以不同方式影响性能”的概念。

### 14. 多轮对话中 token 如何增长

如果每一轮都把全部历史原样附带，token 会不断增长：

```text
第 1 轮：system + user_1 + assistant_1
第 2 轮：system + user_1 + assistant_1 + user_2 + assistant_2
第 3 轮：system + ... + user_3 + assistant_3
```

这会导致后续每一轮都重新处理过去内容，成本和 TTFT 逐渐增加，并最终接近上下文窗口限制。

常用解决方案不是粗暴删除全部历史，而是分层：

```text
固定系统规则
+ 最近几轮原文
+ 会话/任务结构化摘要
+ 当前相关 RAG/记忆
+ 当前工具 observation
```

摘要本身也要基于已验证事实，避免把模型猜测压缩成“永久事实”。这与 M12 的 Agent memory、Checkpoint 和工作记忆完全相连。

### 15. 工具定义为什么也会消耗 token

在 Tool Calling 中，模型需要知道有哪些工具、每个工具何时适用、参数 schema 是什么。工具描述通常以文本/JSON schema 形式进入上下文，因此：

```text
工具越多、描述越长、schema 越复杂
-> 输入 token 越多
-> 选择难度、成本与首字延迟可能越高
```

这不是要求把工具描述写得模糊，而是要求按任务暴露最小必要工具集。M12 已讲过动作空间收缩：当前用户只是咨询退款时，不需要把所有浏览器、代码、管理员、工单写入工具都暴露给模型。

工具 schema 既是模型接口，也是一部分上下文成本和安全面。

### 16. RAG 片段为什么不能越多越好

RAG 的目标不是把所有“可能相关”的文档都放进 prompt，而是让模型获得回答当前问题最必要、最可靠、最可引用的证据。

片段过多会：

- 占用输入 token，挤压输出空间；
- 增加首字延迟和成本；
- 引入矛盾或过期内容；
- 稀释关键证据；
- 扩大 prompt injection 表面；
- 让模型更容易进行无依据拼接。

这就是为什么你已学习 chunking、metadata filter、hybrid search、rerank、citation 和 RAG evaluation。它们不仅提升检索质量，也是在优化模型上下文。

### 17. 模型输出与结构化输出的关系

无论自然语言、JSON、函数参数还是工具调用，底层仍是 token 序列。结构化输出只是通过 schema、解码约束或后处理，让输出 token 更符合预期格式。

这带来两个实践结论：

1. JSON 仍可能因输出上限、模型异常或服务中断而不完整，因此需要 schema 校验和错误处理。
2. 即使 JSON 格式正确，字段语义仍可能错误，例如订单号写错、权限结论错误、工具名不允许。因此结构化输出是降低格式不确定性，不是业务正确性证明。

### 18. 模型的“思考 token”与用户可见输出

不同模型/服务可能支持或内部使用更长的推理过程。有些 API 会以特定字段返回摘要或 reasoning 相关内容，有些不会对外暴露。

对应用工程而言，应注意：

- 模型内部推理/额外生成仍可能消耗时间与 token 资源；
- 用户可见答案不应被误认为全部计算过程；
- 业务审计应记录可验证的工具、状态、证据与决策摘要，而不是依赖完整自由推理文本；
- 高风险结论仍要用工具、规则和人工验证，不能因为模型“想得更久”就自动可信。

后续选型时，推理能力、延迟、成本和输出协议都应进入评估，而不是只看最终文字质量。

### 19. 一个完整走读：RAG + Tool Calling 请求的 token 构成

用户问：`“A1001 的物流异常能退款吗？”`

一次受控 Agent 请求可能包含：

```text
系统规则：只能基于真实订单和当前政策回答；写操作需确认
任务摘要：用户已提供订单号，当前没有待确认动作
工具定义：query_order_summary、query_logistics、search_refund_policy
RAG 结果：当前退款政策的两个高相关片段及引用
当前用户问题：A1001 的物流异常能退款吗？
```

这些全是输入 token。模型可能先输出：

```text
tool_call: query_order_summary(A1001)
```

工具结果再作为新的 observation 加入下一轮上下文：

```text
订单属于当前用户；已发货；物流 72 小时未更新
```

此时模型可能进一步调用物流工具，最后才生成面向用户的解释。

这个例子说明：用户的一句话问题可能引发多轮输入/输出 token，实际成本和延迟由整个 Agent Loop 决定。优化不能只盯最后一句回答长度。

### 20. 面向工程的 token 预算策略

在真正系统中，可以为不同层建立预算：

| 预算对象 | 目的 |
| --- | --- |
| 单请求输入上限 | 防止超窗口、超成本、恶意超长输入 |
| 单请求输出上限 | 防止生成失控与截断风险可控 |
| 单 Agent run token 上限 | 限制多轮工具/反思成本 |
| 单任务总 token 上限 | 限制长任务成本 |
| 用户/租户周期预算 | 公平性与费用治理 |
| RAG 上下文预算 | 保留最强证据，避免全文塞入 |
| 工具 schema 预算 | 控制动作空间和首字延迟 |

预算不是简单拒绝用户。接近上限时可选择：缩短历史、压缩摘要、减少 RAG chunk、选择更小模型、改为异步任务、让用户缩小范围、转人工或明确说明限制。

### 21. 本节知识与后续章节的连接

| 本节概念 | 后续会解决的问题 |
| --- | --- |
| 参数量与权重 | 模型文件大小、显存与量化 |
| token 与 tokenizer | 成本计算、上下文、文本长度控制 |
| prefill / decode | TTFT、输出速度、KV Cache |
| 上下文窗口 | RAG、记忆、工具 schema 和长任务上下文设计 |

| token 预算 | 模型网关、限流、成本和容量治理 |

理解这张连接表后，后续概念就不会只是零散术语。

## 常见误区

### 误区 1：一个字就是一个 token

不对。tokenizer 的切分取决于模型，token 与字符、单词、字节没有固定一一对应关系。精确统计应使用对应 tokenizer 或 API usage 数据。

### 误区 2：上下文窗口大，就可以无脑放入所有历史和文档

不对。长上下文仍有成本、延迟、注意力分散、过期信息、权限和注入风险。应优先提供最小、相关、可信、已授权的上下文。

### 误区 3：`max_tokens` 是要求模型固定输出长度

不对。它通常是最大允许输出上限。模型可能更早因 EOS、stop sequence、工具协议或服务中断而停止；也可能因为上限过小而生成不完整结果。

### 误区 4：temperature 设为 0 就一定正确且每次完全一样

不对。低温度只减少解码随机性，不提供事实验证、权限控制或提示注入防护。服务版本、上下文、工具结果和底层实现变化仍可能导致不同输出。

### 误区 5：模型输出一个很流畅的文本，就说明它拥有对应事实

不对。模型生成的是概率上合理的 token 序列。实时/高风险事实应来自业务工具或可引用知识来源，并由系统校验。

### 误区 6：短用户问题一定成本低、响应快

不对。系统提示、历史、RAG、工具定义和 observation 才可能是主要输入 token 来源。应分析完整请求构成。

### 误区 7：结构化输出解决了所有不确定性

结构化输出主要约束格式。即使 JSON 合法，字段值仍可能错误、越权或不符合当前业务状态，仍需后端校验。

## 本节练习

### 练习 1：计算上下文预算

某模型上下文窗口为 16,000 token。当前系统提示、历史、RAG、工具定义和用户问题共占 12,500 token。若希望给输出保留 2,500 token，是否安全？如果下一轮还可能加入 1,500 token 工具结果，应如何调整？

答案：当前 `12,500 + 2,500 = 15,000`，技术上未超过 16,000，但余量只有 1,000。若下一轮还会加入约 1,500 token 工具结果，则可能超窗口。应在本轮缩短历史/RAG/工具定义、降低输出上限、对工具结果做摘要，或为后续 Agent Loop 预留更多空间。不要只看第一轮恰好不超限。

### 练习 2：分析首字慢的原因

用户只问了一句话，但等待 8 秒才看到第一个字。系统带入了 15 轮聊天记录、12 个 RAG chunk 和 20 个工具 schema。你首先会怀疑什么？

答案：首先怀疑输入 token 太多导致 prefill 时间高，以及工具/schema 与 RAG 内容过长。应统计完整输入 token 构成，检查是否可使用会话摘要、rerank 后减少 chunk、按任务缩小工具集，并确认网关/模型服务是否存在排队。不能只因为用户问题短就排除上下文问题。

### 练习 3：选择随机性策略

以下任务更倾向低随机性还是较高随机性？说明理由：

1. 从文本中抽取订单号和日期，输出固定 JSON。
2. 为营销活动提供 10 个不同文案方向。
3. 根据真实订单和政策给出客服解释。

答案：1 应倾向低随机性，并用 schema 校验，避免格式/字段漂移。2 可使用较高随机性以获得多样方案，但仍要进行品牌/合规审查。3 通常使用较低到中等随机性，重心是事实和引用；随机性不能替代工具查询、权限与业务校验。

### 练习 4：解释截断

模型返回了一半 JSON，响应完成原因显示达到输出上限。应该如何理解和处理？

答案：这不是格式校验偶然失败，而是生成被 token 上限强制停止。系统应将其识别为不完整输出，不应直接使用；可根据任务调整输出上限、减少输入上下文为输出留空间、简化 schema/请求，或进行受控重试。仍要防止无限增大上限导致成本失控。

## 自测题

### 自测 1：token、tokenizer 与模型权重的关系是什么？

答案：tokenizer 将文本切分并映射为 token ID；模型权重学习的是这些 token ID 在上下文中的统计关系；推理时 token ID 输入模型，模型生成新的 token ID，再由 tokenizer 解码为文本。tokenizer 与权重/配置需要匹配。

### 自测 2：输入 token 和输出 token 对性能的主要影响有什么不同？

答案：输入 token 主要影响 prefill，即处理上下文和首 token 出现前的延迟；输出 token 主要影响逐 token decode 和完整生成时长。两者都影响成本和上下文窗口，但优化方法不同。

### 自测 3：为什么上下文窗口不等于长期记忆？

答案：上下文窗口只描述模型单次调用可读取的 token 上限，调用结束后不会自动保留；长期记忆需要应用系统保存、筛选、权限过滤并在未来按需注入。长窗口也不保证模型会正确利用全部内容。

### 自测 4：temperature 能解决哪些问题，不能解决哪些问题？

答案：temperature 调整解码随机性，可影响输出稳定性与多样性；它不能验证事实、保证格式/权限、阻止注入、控制业务副作用或消除模型幻觉。高风险任务仍需工具、规则和人工控制。

### 自测 5：为什么说 token 预算是应用架构问题，而不只是 API 参数？

答案：token 消耗来自系统提示、历史、RAG、工具 schema、observation 和输出，并在多轮 Agent Loop 中累积。它影响成本、延迟、上下文窗口、并发容量和用户体验，因此需要在上下文构造、检索、工具暴露、任务状态、网关和业务策略中统一管理。

## 本节小结

本节从一次请求的真实执行过程解释了 token、tokenizer、参数、上下文窗口与逐 token 生成。输入内容经过 tokenization 和 prefill，模型再通过 decode 逐步输出 token；上下文与输出共同受窗口限制，采样和停止规则影响生成行为。理解这些基础，才能正确设计 Prompt、RAG、Agent 上下文、流式体验、成本预算和后续推理服务性能。
