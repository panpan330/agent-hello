# M12 第 6 节：长任务、异步执行与队列

## 本节定位

前一节已经让 Agent 任务可以持久化、建立检查点并在故障后恢复。但还有一个根本问题：谁来执行这些任务？如果每次都由用户的 HTTP 请求一直等待模型、工具、文件解析、人工审批或第三方服务返回，会发生什么？

```text
浏览器连接可能断开；
网关和负载均衡器可能超时；
Web 进程被长任务占满；
突发流量会拖垮所有用户；
等待数小时的审批根本不适合占着一个请求。
```

因此，能持续较久、可延迟、可重试、需要削峰或需要跨服务执行的 Agent 工作，通常要从“请求内同步执行”转换为“创建任务 -> 调度 -> 异步 worker 执行 -> 查询/推送结果”的模式。

本节讲的是这套执行架构：长任务的识别、同步与异步边界、消息队列的职责、worker、确认（ack）、重试、退避、优先级、延迟任务、死信队列、背压和可观测性。它建立在上一节的任务状态与 Checkpoint 之上。

## 本节学习目标

学完后，你应当能：

1. 判断一个 Agent 工作何时应同步执行、何时必须异步化。
2. 区分 HTTP 请求、业务任务、队列消息、worker 和外部工具调用的生命周期。
3. 理解队列的削峰、解耦、异步调度和可靠投递价值。
4. 解释 ack、可见性超时、至少一次投递、重复消费与幂等的关系。
5. 设计任务重试、指数退避、最大次数、延迟执行和死信队列策略。
6. 说明优先级、并发控制、限流和背压为什么是 Agent 成本与稳定性的基础。
7. 能为一个长时间 Agent 任务设计从提交到结果通知的完整流程。

## 一句话先讲透

> 异步化不是“把函数放到后台跑”，而是把可持久化的业务任务交给受控调度系统：HTTP 负责受理和反馈，队列负责转交与削峰，worker 负责领取和执行，任务状态负责告诉所有参与者它现在是否运行、等待、重试、成功或失败。

## 基础知识铺垫

### 1. 同步请求模型的工作方式

传统同步接口大致是：

```text
客户端发 HTTP 请求
-> Web 服务处理
-> 调数据库/外部服务
-> 在本次连接中返回响应
```

它适合：参数校验、简单查询、短事务、少量低延迟工具调用等。用户等待几百毫秒或几秒可以接受，服务端资源也能及时释放。

但若请求需要：

- 多轮模型推理；
- 多个外部工具；
- 大文件解析、OCR、向量化；
- 批量处理数千条数据；
- 等待第三方回调；
- 等待人工审批；
- 调度多个子任务；

同步连接就不再是合适的任务载体。

### 2. 为什么“接口不超时”不是解决方案

有人会想：把 HTTP、网关、浏览器超时设置大一点不就行了？这只能临时掩盖问题。

长连接会带来：

1. **资源长期占用**：线程、协程、连接、内存、网关连接池都会被占住。
2. **链路脆弱**：浏览器、代理、负载均衡、移动网络中的任意一环断开，结果就难以传回。
3. **无法削峰**：瞬间来 1000 个长任务，Web 服务会同时开始执行，进而耗尽模型/工具配额。
4. **难以恢复**：请求处理进程崩溃，任务和用户连接一起消失。
5. **用户体验差**：用户只能盯着转圈，不知道任务是否仍在运行、可否关闭页面、何时完成。

将超时从 30 秒调成 10 分钟，可能对某个调试场景有用，但不是可靠的长任务架构。

### 3. 长任务不只等于“耗时长”

一个任务应否异步化，不能只看平均耗时。还要看以下维度：

| 维度 | 需要异步化的信号 |
| --- | --- |
| 时长 | 可能超过接口/用户可接受等待时间 |
| 不确定性 | 外部依赖、模型轮次、文件大小导致耗时波动大 |
| 等待 | 需要人工输入、审批、回调或定时重试 |
| 资源消耗 | CPU、内存、模型调用、并发连接成本高 |
| 可恢复性 | 中断后不能丢失或不应从头执行 |
| 流量形态 | 存在突发提交，需要削峰填谷 |
| 优先级 | 有紧急任务，不能被批量任务堵住 |
| 副作用 | 需要可审计、可取消、可重试的业务动作 |

例如一次 3 秒的模型调用，若流量很大、配额很紧，也可能应放入队列；一次 20 秒的管理报表，若低频且用户可等待，也可以先同步，但应有明确限制。

### 4. 异步不等于并行

这两个词常被混淆：

- **异步（asynchronous）**：发起方不必等待工作完成，可以稍后取得结果。
- **并行（parallel）**：多个工作单元在同一时间段同时执行。

一个异步队列可能只有一个 worker，任务异步但不并行；一个同步接口也可能在内部并行调用两个只读服务，但对客户端仍是同步响应。

Agent 系统同时会使用两者：异步让任务脱离 HTTP 生命周期；并行提高互不依赖子任务的吞吐，但也会增加成本、顺序、限流和一致性复杂度。

### 5. 队列不是数据库，也不是任务状态机

消息队列常被误解为“把任务放进去就可靠了”。队列主要负责消息的暂存和分发，任务状态机负责业务生命周期，数据库/持久化负责权威任务记录。

| 组件 | 主要职责 | 不应单独承担的职责 |
| --- | --- | --- |
| HTTP/API 服务 | 接收请求、校验、创建任务、返回任务 ID | 长时间执行所有工作 |
| 任务数据库 | 权威任务状态、checkpoint、审计、结果 | 高吞吐即时分发 |
| 队列/Broker | 缓冲、投递、削峰、解耦、延迟 | 解释业务状态和权限 |
| Worker | 领取、执行、续租、更新任务 | 只靠内存保存全部进度 |
| 通知通道 | SSE/WebSocket/邮件/回调等 | 决定任务是否成功 |

队列消息可能丢失、重复、延迟、乱序，具体行为取决于产品与配置。因此任务的真实状态不能只存在队列里。

### 6. 一个最小异步任务流程

```text
1. 客户端提交请求
2. API 校验输入与权限，创建 task_123（PENDING）
3. 在可靠边界投递 “执行 task_123” 消息
4. API 立即返回 202 Accepted + task_id
5. Worker 消费消息，原子领取 task_123
6. Worker 执行受控 Agent Loop，并持续写 checkpoint
7. 任务完成/等待/失败后更新状态
8. 客户端轮询、SSE/WebSocket 订阅，或系统主动通知结果
```

`202 Accepted` 的语义不是“已经完成”，而是“请求已被接受进行处理”。这能让用户理解：我拿到的是任务凭证，结果将在后续可查询。

### 7. 消息、任务和执行尝试的关系

同一个任务不一定只对应一条消息或一次 worker 执行。

```text
task_123（业务任务）
  ├─ message_001：首次执行
  │    └─ attempt_1：worker_A 执行到工具超时
  ├─ message_002：延迟重试
  │    └─ attempt_2：worker_B 成功执行
  └─ message_003：重复投递，但领取时发现任务已终态，安全忽略
```

业务任务是用户和系统关心的单位；消息是调度媒介；执行尝试是运行记录。分清三者才能正确处理重复消费与重试。

## 本节主题系统讲解

### 1. 异步架构中的职责边界

#### 1.1 API 服务：受理，不替 worker 长跑

API 服务应负责：

- 身份、租户、输入与基础权限校验；
- 创建任务和初始 checkpoint；
- 生成可查询的 `task_id`；
- 可靠地触发调度；
- 向客户端返回“已受理、当前状态、查询地址/订阅方式”。

它不应在请求线程里完成所有长时间 Agent Loop。即使 API 与 worker 使用同一种语言、同一个代码仓库，它们的运行角色也不同。

#### 1.2 队列：交接、缓冲与调度信号

队列消息通常很小，例如：

```text
{
  "event_type": "run_task",
  "task_id": "task_123",
  "expected_version": 5,
  "trigger": "created"
}
```

不建议把完整 prompt、大文件、敏感工具结果塞进队列消息。worker 收到任务 ID 后，应从受控持久化存储读取最新状态。这样重复/延迟消息不会把旧快照误当最新事实。

#### 1.3 Worker：以短“执行片段”推进任务

worker 不一定要从任务开始一直运行到结束。对包含等待或长循环的 Agent，一个更稳妥的思路是执行一个有预算的片段：

```text
领取 task_123
-> 执行最多 N 轮或最多 T 秒
-> 若完成，写终态
-> 若需要等待，写等待态并结束本次执行
-> 若仍可继续但本次预算用完，保存 checkpoint 后重新投递/延迟调度
```

这样可以避免某个复杂任务独占 worker 很久，也能提高公平性和恢复性。

### 2. 消息确认（ack）到底确认了什么

不同消息系统有不同术语，但核心问题是：broker 在何时认为一条消息已被成功处理？

两种极端都危险：

```text
先 ack，再执行任务：worker 崩溃则任务可能丢失。
执行完成很久才 ack：worker 崩溃则消息可能被重复投递。
```

常见务实流程是：

1. worker 收到消息，不立即 ack；
2. 从数据库原子领取任务；
3. 以受控预算推进任务，并保存 checkpoint；
4. 当本次消息对应的推进已可靠落库后 ack；
5. 若 worker 在 ack 前崩溃，broker 可能重新投递；新 worker 通过任务状态、版本和幂等判断如何处理。

因此 ack 不是“整个业务永远只执行一次”的承诺，而是“本次消息的可恢复推进已完成”的确认。

### 3. 可见性超时与消息重新投递

某些队列在 worker 取走消息后，会给它一个可见性超时（visibility timeout）：在此期间其他消费者看不见消息；若 worker 未确认，超时后消息重新可见。

它解决的是“消费者拿到消息后死掉，消息永远不见”的问题。但它也带来重复风险：

```text
worker_A 处理过慢，未在可见性期限内 ack
-> message 再次可见
-> worker_B 也开始处理
```

所以：

- 可见性超时要与单次执行片段预算匹配；
- worker 需要心跳/续租或分段执行；
- 任务领取必须有条件更新；
- 写操作必须幂等。

队列系统无法替应用自动解决业务副作用的重复。

### 4. 至少一次消费与“重复是正常现象”

许多可靠队列默认更接近至少一次（at-least-once）投递：只要 broker 无法确认消费者是否完成，就可能再次投递。

初学者容易把重复当成队列 bug；实际上它往往是为了避免丢消息的代价。应用必须把重复视为设计输入。

worker 收到同一 `task_id` 的重复消息后，可出现以下情况：

| 任务当前状态 | 正确处理倾向 |
| --- | --- |
| `PENDING` | 尝试原子领取并执行 |
| `RUNNING` 且租约有效 | 不重复执行，忽略/延迟 |
| `RUNNING` 且租约过期 | 进入恢复流程 |
| `WAITING_HUMAN` | 不执行，等待事件 |
| `WAITING_RETRY` 且未到时间 | 不执行，等待调度 |
| `SUCCEEDED/FAILED/CANCELLED` | 幂等地忽略或 ack |

这就是上一节任务状态、版本、租约和幂等在异步架构中的实际用途。

### 5. 重试策略：不是所有错误都值得重试

重试前先分类错误：

| 错误类型 | 例子 | 是否应重试 |
| --- | --- | --- |
| 暂时性基础设施错误 | 网络抖动、服务 503、短暂限流 | 通常可有限重试 |
| 永久请求错误 | 参数错误、schema 不匹配 | 不应原样重试 |
| 权限/策略拒绝 | 无权访问、未确认写操作 | 不应自动重试 |
| 业务冲突 | 状态已变化、资源已关闭 | 需要重新读取事实或结束 |
| 模型输出不合规 | 结构化输出不合法 | 可有限重试/修复，不能无限 |
| 结果未知写操作 | 超时但可能已执行 | 先对账，不是普通重试 |

“失败就重新放回队列”会让永久错误占据系统容量，甚至形成消息风暴。

### 6. 指数退避与抖动（Jitter）

如果很多任务在同一外部服务故障后立刻重试，会产生雪崩：服务还没恢复，流量又集中打过去。

指数退避（exponential backoff）让每次等待时间逐渐增加：

```text
第 1 次重试：约 1 秒后
第 2 次重试：约 2 秒后
第 3 次重试：约 4 秒后
第 4 次重试：约 8 秒后
```

抖动（jitter）是在等待时间中加入随机变化：

```text
不是所有任务都在 8 秒整同时重试，
而是在一个合理随机范围内分散重试。
```

实际策略还需要：最大等待时间、最大尝试次数、总任务截止时间、按错误类型定制策略。例如支付、写操作、模型限流和文档解析的重试策略不应完全相同。

### 7. 延迟任务与定时调度

有些任务不是现在执行，而是未来某时间才有资格执行：

- API 限流后 60 秒再试；
- 用户说“明天提醒我”；
- 等待审批截止；
- 每日定时汇总；
- 等待外部任务轮询窗口。

实现方式可能是队列原生延迟消息、延迟队列、数据库 `next_run_at` + 定时扫描、调度器等。无论用什么技术，都要把“何时可以执行”保存为状态事实：

```text
status = WAITING_RETRY
next_run_at = 2026-08-19T10:05:00+08:00
```

到时间后再产生一条调度消息。不要让 worker 长时间 `sleep` 等待，因为这会占用执行资源，也无法优雅地恢复和取消。

### 8. 死信队列（DLQ）解决什么问题

死信队列（Dead Letter Queue）用于接收多次消费失败、无法被正常处理的消息。它不是“自动修好错误”的地方，而是隔离问题，避免同一坏消息无限阻塞主队列。

常见进入 DLQ 的原因：

- 消息反复反序列化失败；
- 消费者代码存在兼容性问题；
- 达到最大投递/重试次数；
- 任务引用的对象始终不存在；
- 发生必须人工处理的异常。

DLQ 中应保留诊断信息：原消息、失败次数、最后错误、时间、消费者版本等。运维或开发人员可以修复后选择：

- 丢弃（确认无价值）；
- 修正并重新投递；
- 创建新的补偿任务；
- 转人工处理。

重要提醒：业务任务进入失败终态，不一定等于队列消息要进 DLQ。若 worker 已成功把任务标记为 `FAILED` 并 ack 了消息，消息处理本身是成功的。DLQ 更偏向“消息无法被可靠消费”的技术问题。

### 9. 优先级：不要让低价值批处理堵住紧急任务

Agent 任务的价值和紧急程度可能差异很大：

- 用户在线等待的客服问题；
- 高优先级风控告警；
- 夜间批量知识库重建；
- 管理员离线生成报告。

如果都放在同一先进先出队列，高优先任务可能被大量低优先任务阻塞。常见策略：

1. 多队列：`high`、`normal`、`batch`，worker 按权重消费。
2. 队列优先级：broker 支持时按优先级调度。
3. 独立 worker 池：高优任务使用隔离的并发资源。
4. 公平调度：避免单个租户或大批量任务长期霸占全部容量。

优先级也要防滥用。不能让所有调用方都把自己的任务标为最高；应由业务规则、角色、套餐或系统策略确定。

### 10. 并发控制与背压（Backpressure）

队列可以缓存任务，但如果 worker 无限制并发调用模型、数据库或第三方工具，最终仍会把下游压垮。

背压是系统在下游处理能力不足时，限制上游继续施压的机制。对 Agent 系统，常见控制维度有：

| 控制对象 | 例子 |
| --- | --- |
| 全局并发 | 同时最多 20 个模型 Agent run |
| 每租户并发 | 单租户最多 3 个重任务 |
| 每模型并发 | 某模型供应商最多 5 个请求 |
| 每工具并发 | 文档 OCR 最多 2 个并行任务 |
| 队列长度 | 超过阈值后拒绝低优先请求或延迟受理 |
| 成本预算 | 某用户每日最多 N 次高成本任务 |

背压不只是技术稳定性，也直接关系到模型配额、成本和公平性。没有背压，队列越可靠，越可能把积压任务最终集中释放成下游雪崩。

### 11. 限流与队列的区别

两者经常一起出现，但职责不同：

- **限流（rate limiting）**：限制一段时间内允许进入系统或调用下游的速率，例如每分钟最多 60 个请求。
- **队列**：把已经接受的工作排队等待执行。

例子：模型供应商限制每分钟 100 次调用。worker 即使从队列取到了 1000 个任务，也不能同时全发出去；需要令牌桶、漏桶、并发信号量或调度节流控制调用速率。

对客户端而言，系统可以：

- 直接拒绝超额请求（例如 `429 Too Many Requests`）；
- 接受任务但显示排队中；
- 降级为较慢/较便宜模型；
- 延迟执行低优先任务。

选择取决于业务承诺、成本和用户体验，而不是“有队列就不需要限流”。

### 12. Worker 的执行模型：不要让一个任务永久占用一个 worker

一个危险实现是：worker 收到任务后进入无限 Agent Loop，直到任务完成。若任务等待人工 3 小时，worker 就被占死；若模型反复失败，其他任务也被拖累。

更好的设计是**分段执行（bounded execution slice）**：

```text
每次 worker 领取任务后，只允许：
- 最多执行 5 个 Agent step；或
- 最多运行 30 秒；或
- 到达等待态/终态立即归还 worker。
```

若任务仍未完成但可以继续：写 checkpoint，重新投递一个后续执行消息。若任务等待外部事件：写等待态，不占 worker。这样 worker 是短期执行资源，任务状态才是长期存在的对象。

### 13. 批处理、Fan-out 与 Fan-in

有些 Agent 任务可以拆成多个独立子任务：

```text
父任务：分析 100 份合同
-> fan-out：拆成 100 个文档分析子任务
-> 子任务异步执行
-> fan-in：汇总所有完成结果，生成总报告
```

这能提高吞吐，但需要额外考虑：

- 父子任务关系与状态聚合；
- 子任务失败时父任务是失败、部分成功还是可重试；
- 并发上限，避免一次 fan-out 创建十万任务；
- 汇总何时触发，如何避免重复；
- 成本预算如何在父子任务间分配；
- 取消父任务时如何取消未开始和正在运行的子任务。

Fan-out/Fan-in 是后续 Multi-Agent 和长任务编排常见基础，但不能因为能并行就无节制拆分。

### 14. 排队时间也是用户体验的一部分

异步任务不能只关注执行耗时。用户还关心：

```text
我提交成功了吗？
现在在排队还是在执行？
大约还要多久？
我能否关闭页面？
失败后应该怎么办？
```

任务状态可面向用户适度映射：

| 内部状态 | 可展示表达 |
| --- | --- |
| `PENDING` | 已受理，等待处理 |
| `RUNNING` | 正在分析/处理中 |
| `WAITING_HUMAN` | 等待审核/等待你的确认 |
| `WAITING_RETRY` | 服务暂时繁忙，将自动重试 |
| `SUCCEEDED` | 已完成 |
| `FAILED` | 未完成，可查看原因或重新提交 |

注意不要提供虚假的精确进度。例如模型推理和外部工具耗时不确定，显示“67%”如果没有可靠依据，会损害信任。可以展示已完成的阶段、队列位置区间或“正在等待外部服务”等真实状态。

### 15. 结果交付方式：轮询、SSE、WebSocket、回调

异步任务完成后，如何让客户端知道？常见方式：

| 方式 | 优点 | 适用情况 |
| --- | --- | --- |
| 轮询（polling） | 简单、可靠、易实现 | 低频管理端、任务量不大 |
| SSE | 服务端单向推送、适合进度/日志流 | Web 前端实时展示 |
| WebSocket | 双向通信 | 需要实时交互控制的复杂界面 |
| Webhook/回调 | 系统对系统通知 | 外部集成平台 |
| 邮件/站内信/消息通知 | 用户不在线也能收到 | 长时间离线任务 |

这些通道只是**状态展示和通知方式**。真实任务状态仍应从持久化存储读取，客户端断线后可以重连和补拉，不能让 SSE 事件本身成为唯一事实来源。

### 16. 可靠投递：任务创建与发消息之间的空档

存在经典问题：

```text
1. 数据库写入 task_123 = PENDING 成功
2. 向队列发送 run_task 消息前，API 服务崩溃
```

结果是数据库里有任务，但队列里没有消息，任务永远不执行。

反过来：

```text
1. 先发送消息
2. 数据库事务失败或回滚
```

worker 收到消息后找不到任务或看见不完整状态。

上一节提到 Outbox 模式，正是为此设计：在同一数据库事务中写入任务和待投递事件；独立发布器可靠地把 outbox 事件投递到队列。即使发布器崩溃，事件仍在数据库中，稍后可继续投递。

消费者仍需幂等，因为 outbox 发布也可能重复投递。

### 17. 延迟、重试、定时和回调的统一视角

它们看似不同，本质上都是：任务当前不能立即继续，但将来某个事件可能使其可运行。

| 当前等待原因 | 触发恢复的事件 |
| --- | --- |
| 等待重试 | 到达 `next_retry_at` |
| 等待异步工具 | 外部回调或轮询发现完成 |
| 等待人工 | 审批批准/拒绝 |
| 等待用户输入 | 收到关联输入 |
| 等待定时计划 | 调度时间到达 |

统一设计时，可以让恢复事件都走同样的入口：校验任务状态和版本 -> 原子领取 -> 进入有限执行片段。这样避免为每种等待写一套互不兼容的恢复逻辑。

### 18. 队列积压如何理解和处理

队列长度增长不一定是故障，可能只是短期流量峰值；但持续积压通常意味着到达速率大于处理能力：

```text
任务进入速率 > worker 有效完成速率
```

处理思路不是只增加 worker 数：

1. 判断瓶颈：模型限流、OCR、数据库、网络、CPU、单租户大任务？
2. 设置并发上限，避免扩容把下游打垮。
3. 区分优先级，先保障关键任务。
4. 对低价值批量任务延迟或拒绝受理。
5. 优化任务步骤、缓存、批处理与模型选择。
6. 提供排队状态和合理预期。
7. 必要时扩容 worker 或申请下游配额。

排队系统的目标不是让队列永远为零，而是在波动下保持可控、可预测和公平。

### 19. 长任务的安全与权限复核

任务可能从提交到执行隔了很久。在这段时间里，用户权限、资源状态、政策、余额或订单归属都可能变化。

因此不能仅在任务创建时校验一次权限，然后后续永远信任旧结果。更合理的原则：

- 创建任务时验证“能否提交”；
- 执行每个敏感工具前验证“现在能否执行”；
- 从 checkpoint 恢复后重新检查取消、截止、权限和策略版本；
- 对高风险写操作使用短有效期确认，必要时再次人工审核；
- 将执行时实际使用的身份/租户上下文写入审计。

异步化拉长了时间边界，也就扩大了“事实会变化”的可能性。

### 20. 一个完整走读：异步文档分析 Agent

用户上传一份大型 PDF，希望提取风险条款并生成报告。

#### 提交阶段

1. API 校验文件类型、大小、用户权限和配额。
2. 创建 `task_doc_001`，状态 `PENDING`，保存文件引用、任务目标和截止时间。
3. 同事务写入 `run_task` outbox 事件。
4. 返回 `202 Accepted` 和任务 ID。用户可关闭页面。

#### 执行阶段

5. outbox 发布器将消息投递队列。
6. worker 领取任务，设置租约，进入 `RUNNING`。
7. 先提交 OCR/解析子任务，保存 `external_job_id`，转为 `WAITING_TOOL`，worker 结束本次执行。
8. 外部处理完成后回调，系统校验回调并重新投递任务。
9. worker 恢复任务，读取解析结果，执行有限轮次的条款分析和结构化提取。
10. 若超过本次时间/步骤预算，保存 checkpoint 后再次排队；若完成，保存报告引用，进入 `SUCCEEDED`。

#### 通知阶段

11. 任务完成事件通过 SSE/站内信/邮件通知用户；用户也可以查询任务详情。

这个过程没有任何一步依赖“某一个 HTTP 连接从头保持到尾”。每一步都可观察、可恢复、可限流。

### 21. 一套务实的建设顺序

从同步 Agent 演进到异步执行，建议分阶段：

1. 先有任务表和状态查询接口。
2. 将明显长/等待型任务改为返回 `202 + task_id`。
3. 引入一个 worker 进程，从任务存储领取执行。
4. 增加可靠投递（如 Outbox）与基本队列。
5. 为重试加入错误分类、延迟和最大次数。
6. 加入幂等、租约、重复消息处理和死信隔离。
7. 按模型/工具/租户增加并发和速率限制。
8. 建立优先级、积压监控、告警与用户状态反馈。
9. 再考虑复杂的父子任务、并行 fan-out、调度平台或工作流引擎。

不要一开始就为了“使用队列”而把所有简单接口异步化。异步带来可靠性和弹性，也带来最终一致、调试、状态展示和运维复杂度。

## 常见误区

### 误区 1：异步任务就是在 Web 接口里开一个后台线程

本地线程在进程重启、容器迁移、水平扩容后都不可靠，也难以跨实例调度、恢复和限流。生产长任务需要持久化任务状态和独立执行/调度机制。

### 误区 2：有消息队列就不会丢任务或重复任务

队列提升可靠性，但仍会有重复投递、消费者崩溃、消息与数据库状态不一致等问题。任务状态、Outbox、幂等、ack 和恢复逻辑仍不可少。

### 误区 3：消息 ack 等于业务成功

ack 只表示消费者已可靠处理了该消息所代表的推进。业务任务可能转为等待、失败或成功；这些状态要由任务记录定义。

### 误区 4：所有失败都应该立即重试

参数错误、权限拒绝、策略拦截、结果未知写操作都不适合普通重试。需要先分类、对账、修正输入或转人工。

### 误区 5：队列越长说明系统越可靠

短期缓冲是正常的，持续积压说明处理能力、下游配额或任务设计存在问题。队列不能替代背压、限流和容量规划。

### 误区 6：任务一旦入队，创建时的权限永远有效

异步延迟期间权限和资源可能变化。敏感动作在执行时和恢复时仍要重新校验。

### 误区 7：死信队列会自动解决坏消息

DLQ 只是隔离和保留诊断信息，仍需要人或程序分析原因、修复后重放、补偿或明确丢弃。

## 本节练习

### 练习 1：判断同步还是异步

下面任务中，哪些更适合异步化？说明理由。

1. 根据订单号查询当前状态。
2. 上传 500 页扫描 PDF，进行 OCR、提取、向量化和报告生成。
3. 用户提交退款申请，系统立即校验参数并创建申请记录。
4. 每天凌晨汇总所有客服工单并生成趋势分析。

答案：1 通常同步，属于短只读查询。2 明显异步，耗时不确定、资源重、可能涉及多个外部步骤。3 可以同步完成申请受理并返回申请/任务 ID，后续审核流程异步。4 异步定时批任务，不依赖用户连接且可能处理大量数据。

### 练习 2：重复消息处理

worker 收到 `run_task(task_123)`，但数据库显示 `task_123` 已是 `SUCCEEDED`。worker 应该怎么做？

答案：不再执行业务动作，幂等地确认/ack 该消息并记录必要的重复投递指标即可。重复消息在至少一次投递模型中是正常现象，不应因此重新生成结果或调用写工具。

### 练习 3：为重试分类

请判断下列情况的首选处理：普通延迟重试、修正后重试、对账确认、直接结束/转人工。

1. 外部搜索接口返回 503。
2. 模型请求参数不符合工具 schema。
3. 创建工单请求超时，无法确定是否已创建。
4. 当前用户无权访问订单。

答案：1 适合有限的延迟重试与退避。2 应进行输出修复/重新规划或结束，不能原样无限重试。3 应先对账确认，利用幂等键或外部请求 ID 查询。4 直接以权限拒绝结束或提示用户，自动重试无意义。

### 练习 4：解释 Outbox 的价值

为什么“先写任务表，再直接发队列消息”可能造成任务永远不执行？Outbox 如何缓解？

答案：如果任务表写成功后、消息发送前进程崩溃，任务留在 `PENDING` 但没有对应消息。Outbox 将任务记录和待发布事件在同一数据库事务中写入；独立发布器之后从 outbox 可靠投递，即使中断也能再次尝试，减少任务状态与消息脱节。

## 自测题

### 自测 1：异步化和并行化有什么区别？

答案：异步化使发起方不必等待任务完成，任务可稍后继续或获得结果；并行化是多个任务/子任务同时执行。异步任务可以不并行，同步请求也可能内部并行。

### 自测 2：队列、任务数据库和 worker 分别负责什么？

答案：队列负责消息缓冲、交接和调度信号；任务数据库负责权威状态、checkpoint、结果和审计；worker 负责领取任务、有限执行、更新 checkpoint 并处理恢复。它们协作，不能互相替代。

### 自测 3：为什么 worker 不应在等待人工时一直占用执行线程？

答案：人工等待可能持续很久，占用 worker 会降低吞吐、浪费资源并影响其他任务。应保存 `WAITING_HUMAN` checkpoint，结束本次执行，收到批准/拒绝事件后再重新调度。

### 自测 4：至少一次投递意味着什么？应用怎样应对？

答案：同一消息或任务可能被重复交给消费者，以避免因不确定确认而丢失。应用要通过条件领取、状态机、租约、幂等键和终态忽略等方式安全处理重复，而不是假定每条消息只来一次。

### 自测 5：背压为什么对 Agent 特别重要？

答案：Agent 可能消耗昂贵模型调用、外部工具配额、CPU 和数据库资源，且任务时长波动大。没有并发、速率、租户和成本边界，积压任务可能同时冲击下游，造成限流、费用失控和整体故障。背压让系统按实际能力受控处理工作。

## 本节小结

长任务的可靠执行需要从 HTTP 请求中解耦：API 负责受理，任务状态保存真实生命周期，队列负责交接与削峰，worker 以有限执行片段推进，重试/延迟/DLQ/背压负责在失败和流量波动下保持系统可控。队列不会自动消灭重复和一致性问题，幂等、checkpoint、租约与状态机仍是基础。
