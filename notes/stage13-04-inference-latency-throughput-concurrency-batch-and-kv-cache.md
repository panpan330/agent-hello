# M13 第 4 节：推理性能核心：延迟、吞吐、并发、Batch 与 KV Cache

## 本节定位

前面三节已经建立了模型推理的基本事实：文本会转为 token，模型逐 token 生成；权重、KV Cache 和临时空间占用计算资源；精度与量化会改变资源需求。现在要回答模型服务最常见、也最容易被误解的问题：

```text
为什么有时首字很慢，但后续输出很快？
为什么模型在单用户测试中很快，上线后却越来越慢？
为什么 GPU 利用率很高，用户仍觉得卡？
为什么提高并发有时提升吞吐，有时反而让所有人更慢？
为什么长上下文、长输出和多轮 Agent 任务会影响容量？
为什么 KV Cache 是大模型服务设计中的核心资源？
```

“模型性能”不是一个单一数字。交互式聊天关心首字速度，批量任务关心总吞吐，企业服务还关心高峰期排队、P95/P99 延迟、OOM、成本和公平性。本节通过统一的性能语言，让你能读懂推理服务监控、做出合理的部署取舍，并为后续推理引擎、网关、容量与 Kubernetes 学习打底。

## 本节学习目标

学完后，你应当能：

1. 区分延迟（latency）、吞吐（throughput）、并发（concurrency）、QPS/RPS 和排队时间。
2. 解释 TTFT、TPOT、端到端响应时间分别代表什么。
3. 理解 prefill 与 decode 的资源行为为何不同。
4. 系统理解 KV Cache 的作用、增长因素和容量影响。
5. 说明 batch、动态/连续批处理如何提升 GPU 利用率，以及它们的延迟权衡。
6. 判断长上下文、长输出、并发请求和 Agent Loop 怎样影响模型服务性能。
7. 知道性能优化应如何以指标、目标和真实工作负载为依据，而不是只追求某个单一数值。

## 一句话先讲透

> 推理性能不是“模型每秒生成多少字”这么简单：输入上下文决定 prefill 和首字延迟，输出长度决定逐 token decode 时长，活跃请求数决定 KV Cache 和排队压力，批处理决定硬件利用率与公平性；好的服务要在交互延迟、总体吞吐、显存容量、成本和稳定性之间做有目标的调度。

## 基础知识铺垫

### 1. 延迟、吞吐、并发：三个不能混用的词

这三个词经常同时出现，但回答的是不同问题。

| 概念 | 回答的问题 | 常见单位/表达 |
| --- | --- | --- |
| 延迟（latency） | 一个请求从开始到得到结果需要多久？ | ms、s、P95 延迟 |
| 吞吐（throughput） | 系统单位时间完成多少工作？ | requests/s、tokens/s、jobs/min |
| 并发（concurrency） | 同一时刻有多少请求/任务处于进行中？ | 活跃请求数、并发连接数 |

简单例子：

```text
单个请求 2 秒完成：延迟约 2 秒
同一时间处理 10 个请求：并发为 10
每秒完成 5 个请求：吞吐为 5 requests/s
```

提高并发可能提高吞吐，但也可能增加单请求延迟；降低延迟不一定提高总吞吐。它们必须结合用户场景讨论。

### 2. 为什么平均延迟不够

假设 100 个请求中，90 个在 1 秒内完成，10 个需要 15 秒。平均值约 2.4 秒，看上去还可以，但那 10 个用户体验很差。

因此生产系统常关注分位数：

| 指标 | 含义 |
| --- | --- |
| P50 | 50% 请求不超过的延迟，中位体验 |
| P90 | 90% 请求不超过的延迟 |
| P95 | 95% 请求不超过的延迟，常用于服务目标 |
| P99 | 99% 请求不超过的延迟，反映尾部异常 |

大模型服务的尾部延迟容易受长 prompt、长输出、排队、GC/内存、GPU OOM、模型冷启动、工具调用和网络抖动影响。只看平均值很容易掩盖真实问题。

### 3. 请求生命周期中的时间组成

一个用户从发请求到拿到最终答案，时间可能包括：

```text
网络传输
+ 网关认证/限流/排队
+ 应用构造上下文、RAG、工具准备
+ 模型服务排队
+ prefill
+ decode
+ 工具调用/多轮 Agent
+ 输出校验与返回
```

模型推理只是端到端延迟的一部分。若用户说“模型很慢”，可能真实瓶颈在：

- RAG 检索慢；
- 请求在队列等待；
- 工具 API 超时；
- 输入上下文过大；
- 模型输出过长；
- 网络或前端渲染慢；
- worker 并发/限流策略不合理。

性能优化必须先拆分时间，而不是只看模型名称。

### 4. 回顾 Prefill 与 Decode

上一节已经提到两个核心阶段：

```text
Prefill：模型处理全部已有输入上下文
Decode：模型一次生成一个输出 token，并不断追加到上下文
```

它们的性能特征不同：

| 阶段 | 主要输入规模 | 用户感知 | 常见瓶颈 |
| --- | --- | --- | --- |
| Prefill | 全部 prompt/context | 等首字 | 输入 token、计算、内存带宽、排队 |
| Decode | 已有状态 + 新 token | 等后续输出/完成 | 每 token 生成速度、显存带宽、KV Cache、并发调度 |

这就是为什么“模型能每秒输出很多 token”不代表首字一定快；“短输出回答快”也不代表长 RAG 请求快。

### 5. 什么是请求排队（Queueing）

当请求到达速度超过模型服务当前可立即处理的能力时，新请求必须等待。等待时间就是排队延迟。

```text
请求到达速率 > 当前可服务速率
-> 排队长度增长
-> 用户端延迟上升
-> 达到超时/队列上限时可能拒绝或失败
```

模型服务的“可服务能力”受 GPU、模型、上下文、并发、batch、KV Cache、限流和调度器影响。即使模型本身很快，若突然出现大量长任务，也可能让短请求排队很久。

第 6 阶段学过队列和背压；本节把同一思想落实到模型 token 级别。

## 本节主题系统讲解

### 1. 推理性能的核心指标

模型服务常见指标可以分为用户体验、系统容量和资源三类。

#### 1.1 用户体验指标

| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| E2E latency | 从用户请求到最终完成的总时间 | 用户最终等待感受 |
| TTFT | Time To First Token，首 token 时间 | 聊天/流式场景的“系统是否立刻响应” |
| TPOT | Time Per Output Token，后续每 token 平均时间 | 输出流畅度 |
| Inter-token latency | 相邻 token/流片段的间隔 | 流式输出是否卡顿 |
| Timeout rate | 超时率 | 服务是否在可用范围内 |

#### 1.2 容量与效率指标

| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| Request throughput | 每秒/每分钟完成多少请求 | 面向业务负载的能力 |
| Token throughput | 每秒处理/生成多少 token | 更贴近模型计算工作量 |
| Active concurrency | 活跃请求数 | KV Cache 与资源压力 |
| Queue length / wait | 排队数量与等待时间 | 容量不足或突发流量信号 |
| Batch size | 同一批次同时处理的请求/token 数 | GPU 利用率与延迟权衡 |

#### 1.3 资源指标

| 指标 | 含义 |
| --- | --- |
| VRAM 使用量 | 权重、KV Cache、临时空间是否接近上限 |
| GPU compute utilization | 计算单元忙碌程度 |
| Memory bandwidth utilization | 显存带宽压力（是否可观测取决于环境） |
| CPU/RAM 使用率 | tokenizer、调度、网络、预处理是否成为瓶颈 |
| 网络/磁盘 | 模型加载、外部存储、请求传输是否受限 |

没有任何单一指标能说明“服务好不好”。需要把用户延迟、吞吐、资源和错误率一起看。

### 2. TTFT：用户为什么在意第一个字

TTFT 是从服务收到请求或用户发出请求，到客户端收到第一个可见 token/流片段的时间。它常被理解为“系统开始响应的速度”。

对聊天系统，用户往往更能容忍后续逐步输出，而难以接受长时间完全无反馈。流式输出的价值就在于：即使完整答案要 10 秒，若 1 秒内开始输出，主观体验通常更好。

TTFT 可能受以下因素影响：

```text
网络和网关
+ 模型服务排队
+ 输入 token 数和 prefill
+ 模型冷启动/权重未就绪
+ 工具/RAG 是否在模型前同步执行
+ 请求调度和 batch 等待
```

优化 TTFT 时，不应只盯输出速度。通常先检查：输入是否过长、RAG 是否过多、工具 schema 是否过大、是否存在排队、是否把可异步工作阻塞在首字之前。

### 3. TPOT 与输出速度

TPOT 表示生成阶段每个输出 token 的平均耗时。它的倒数常被表达为输出 tokens/s：

```text
tokens/s ≈ 1 / TPOT（概念上）
```

输出速度影响：

- 长回答完成时间；
- 流式文本是否顺畅；
- 同一 GPU 能同时服务多少正在生成的请求；
- 长任务/Agent 报告的总体成本与容量。

TPOT 会受到模型大小、量化、GPU 显存带宽、KV Cache、并发调度、引擎优化和输出采样等影响。它与 TTFT 相关但不相同。

### 4. 端到端延迟的一个概念公式

可以用下式做诊断，不追求精确数学：

```text
E2E 总延迟
≈ 前置处理时间
+ 排队等待时间
+ Prefill 时间
+ 输出 token 数 × TPOT
+ 工具/多轮 Agent 时间
+ 后处理与网络时间
```

它帮助你问出正确问题：

- 前置处理是否包含慢 RAG/OCR/数据库？
- 队列是否因并发或限流积压？
- 输入是否使 prefill 太重？
- 输出是否过长？
- Agent 是否进行了不必要的多轮工具/反思？
- 工具 API 是否比模型慢？

不同任务的主导项不同。短问答可能主要受 TTFT 影响；长报告可能主要受输出和工具耗时影响；高峰期服务可能主要受排队影响。

### 5. 吞吐：到底应该统计请求还是 token

只统计 `requests/s` 容易误导，因为一个请求可能是 20 token 的分类，也可能是 100,000 token 上下文 + 5,000 token 报告。模型实际负载差异巨大。

因此模型服务常同时关注：

```text
输入 tokens/s（prefill 吞吐）
输出 tokens/s（decode 吞吐）
完成 requests/s（业务请求吞吐）
```

例子：

```text
服务 A：每秒完成 10 个短分类请求
服务 B：每秒完成 2 个长报告请求
```

不能只比较 10 与 2。需要看每个请求的输入/输出 token、服务等级目标和实际业务价值。

### 6. Little 定律的直觉：为什么排队会突然恶化

排队系统中有一个常见关系，称为 Little's Law：

```text
系统中的平均任务数 ≈ 到达速率 × 平均停留时间
```

不需要做严格推导，但它提供一个重要直觉：当请求到达速率接近服务能力上限时，平均等待时间会迅速上升。模型服务不是“差一点满载也没关系”的线性系统；接近饱和时，长请求和突发流量会让尾部延迟明显恶化。

因此生产系统通常不会把 GPU/队列长期推到 100% 理论利用率，而要预留容量、设置并发上限、采用优先级和背压，并为高峰做好扩容/降级策略。

### 7. KV Cache：为什么它能加速生成

Transformer 的注意力机制需要让当前 token 参考历史 token。若每生成一个新 token 都重新计算整个历史序列的中间表示，成本会越来越高。

KV Cache 保存历史 token 在每层注意力计算中产生的 key（K）和 value（V）表示。简化理解：

```text
没有 KV Cache：
每生成一个新 token，都要重新处理大量历史 token 的相关计算

有 KV Cache：
历史 token 的关键中间结果被缓存；
生成新 token 时主要计算新 token 并查询历史缓存
```

它显著减少逐 token decode 时的重复计算，使生成式服务成为可能。

### 8. KV Cache 的代价：用显存换计算

KV Cache 并不是免费加速。它需要保存每层、每个历史 token 的状态，因此占用 VRAM。

概念增长关系：

```text
KV Cache 大小
与模型层数、隐藏维度/注意力头配置、KV 精度、
上下文长度、已生成 token 数、活跃并发请求数近似正相关。
```

这可以简化记忆为：

```text
长上下文 × 高并发 = KV Cache 压力很大
```

权重是“模型固定成本”，KV Cache 是“每个活跃请求的可变成本”。模型服务容量规划必须同时考虑两者。

### 9. KV Cache 与 Agent/RAG 的关系

Agent 和 RAG 常常比普通聊天更容易让 KV Cache 增长：

- RAG 将多个 chunk 放入输入上下文；
- 工具定义/schema 占用 token；
- 工具调用结果作为 observation 继续累积；
- 多轮 Agent Loop 会重复带入计划、历史和事实；
- Planner/Critic 可能增加额外模型轮次；
- 长任务可能需要生成较长报告。

因此 AI 应用工程中“上下文工程”不仅影响回答质量，也影响模型服务的并发容量与显存稳定性。M12 的最小上下文、工作记忆、artifact 引用和工具动作空间收缩，在 M13 中都有直接性能价值。

### 10. Batch：为什么把请求放在一起计算可能更高效

GPU 擅长大规模并行计算。若把多个请求的相似计算合并处理，通常能提高硬件利用率和总体 token 吞吐。这种合并叫 batch（批处理）。

概念例子：

```text
逐个处理：请求 A 完成部分计算，再处理 B，再处理 C
批处理：A、B、C 的相似矩阵计算在一次更大计算中完成
```

批处理的潜在收益：

- 更充分利用 GPU 计算单元；
- 提高整体 tokens/s；
- 在高负载下减少单位 token 开销；
- 提升离线批任务效率。

但 batch 并不总是越大越好。它会增加显存使用，也可能让新到请求等待凑批，影响 TTFT。

### 11. 静态 Batch 与动态 Batch

#### 11.1 静态 Batch

预先收集固定数量或固定长度的请求，一起处理。常见于离线训练或批量 embedding。

优点是逻辑简单、硬件利用率可预测；缺点是不同请求长度差异大时会出现 padding 浪费，交互式请求也可能等待较久。

#### 11.2 动态 Batch

服务根据当前到达请求动态组合批次，尽量在延迟目标内提高利用率。它更适合在线推理，但调度更复杂。

动态 batch 需要在：

```text
等待更久以获得更大 batch
vs
尽快开始以获得更低 TTFT
```

之间平衡。

### 12. 连续批处理（Continuous Batching）的直觉

传统 batch 往往要求一批请求一起开始、一起结束。但生成请求长度不同：有的只生成 20 token，有的要生成 1000 token。若必须等最长请求结束，短请求会浪费资源。

连续批处理的核心思想是：

```text
生成中的请求每一步共享调度；
某个请求完成后，它释放的位置可让新请求加入；
不需要等整批请求全部结束再处理下一批。
```

它能提高在线 LLM 服务的吞吐和资源利用率，因此是现代推理引擎常见的关键设计方向。

但其实现复杂，需要管理不同请求的 KV Cache、长度、停止条件、优先级和取消。应用层仍要设置并发与预算，不能因引擎支持连续批处理就允许无限请求进入。

### 13. Prefill 与 Decode 混合调度的难点

新请求的 prefill 通常是较大计算；正在输出的请求需要持续 decode 才能保持流畅。两类工作可能争夺 GPU。

若调度偏向大量 prefill：

- 新请求 TTFT 可能改善；
- 已经在生成的用户可能出现 token 间隔变大、流卡顿。

若调度偏向持续 decode：

- 已在生成的流更平滑；
- 新请求可能在队列里等很久才开始。

推理引擎会采用不同调度策略平衡这两类负载。对应用工程师而言，关键是理解：TTFT 与 TPOT 可能存在权衡，不能只优化其中一个。

### 14. 并发不是线程数那么简单

在 Web 服务中，人们常用线程/协程数量理解并发；模型服务中并发还意味着：

- 同时有多少请求占用 KV Cache；
- 有多少请求正在 prefill/decode；
- 有多少流式连接持续等待；
- 有多少工具/Agent 任务等待模型；
- 引擎能否将它们放入有效 batch；
- 这些请求的上下文/输出长度有多大。

因此“允许 100 并发”没有脱离工作负载的意义。100 个短分类请求和 100 个 128K 上下文、长输出的 Agent 请求对显存和吞吐的影响完全不同。

### 15. 请求长度差异与公平性问题

如果一个长报告请求占用大量 KV Cache 并持续生成，而许多短问答请求不断到来，系统如何调度？这是性能之外的公平性问题。

可能策略包括：

- 为不同任务类型设置独立队列/优先级；
- 限制单请求最大上下文、输出和执行时间；
- 为交互短请求预留容量；
- 将长报告改为异步任务；
- 对租户设并发/成本配额；
- 使用可中断或分段的任务执行策略；
- 对超长请求降级、压缩上下文或要求确认。

没有公平性控制时，一个大客户或异常 Agent 任务可能挤占全部模型资源，让其他用户的 TTFT 急剧上升。

### 16. 长上下文的性能影响不只在显存

长上下文会：

1. 增加输入 token，prefill 更慢；
2. 增加 KV Cache，降低可并发请求数；
3. 增加网络传输/序列化与网关处理；
4. 增加 token 成本；
5. 增加模型注意力处理和质量风险；
6. 使重试、重复调用和多轮 Agent 更昂贵。

因此“支持超长上下文”的模型不意味着所有请求都应使用最大窗口。应按任务选择合理预算，并通过 RAG/摘要/引用减少无关 token。

### 17. 输出长度的性能与体验权衡

长输出会：

- 增加 decode 时间与总延迟；
- 扩大 KV Cache；
- 占用连接、GPU 调度和成本预算；
- 可能包含更多无关重复内容；
- 让用户更难阅读。

有时更好的产品策略不是让模型“写得更快”，而是：

- 先给简短结论和可展开详情；
- 将长报告改为异步生成；
- 使用结构化结果，让前端按需展示；
- 限制 Agent 每轮输出，只在最终阶段生成面向用户的总结；
- 对复杂任务提供阶段进度而非一直输出冗长推理。

性能优化和交互设计经常是同一件事。

### 18. 流式输出改善什么，不改善什么

流式输出通常通过 SSE/WebSocket 等通道，让服务在生成过程中逐步发送 token/文本片段。

它改善：

- 用户更早获得可见反馈；
- 聊天体验更连贯；
- 客户端可在最终完成前展示部分结果；
- 用户可能更早选择取消。

它不自动改善：

- 模型总计算量；
- 单 token decode 速度；
- 长上下文 prefill；
- GPU OOM；
- 工具调用前的等待；
- 最终完整响应时间（有时网络分片还会增加少量开销）。

流式是一种体验和传输策略，不是性能万能药。

### 19. 性能基准测试：为什么不能只测一次

单次本地测试容易受到缓存、冷启动、网络、随机输入和机器其他负载影响。更有意义的基准需要明确：

```text
模型/量化/引擎/硬件版本
输入 token 长度分布
输出 token 长度分布
并发水平和到达模式
是否流式
是否包含 RAG/工具
测量指标（TTFT、TPOT、P95、吞吐、显存、错误率）
预热策略和持续时间
```

例如只用 20 token 的固定问题测得很快，无法代表真实用户的长文档 Agent；只测满载吞吐，也无法代表交互用户的首字体验。

### 20. 负载测试的三种常见模式

| 模式 | 描述 | 用于发现什么 |
| --- | --- | --- |
| 稳态负载 | 持续固定速率/并发 | 正常容量、平均与分位延迟 |
| 突发负载 | 短时间大量请求到达 | 队列、背压、限流、冷启动 |
| 压力测试 | 逐步提高负载直到退化 | 最大容量、拐点、OOM、超时、恢复能力 |

对 Agent 系统还应增加混合负载：短问答、长 RAG、工具调用、长报告、embedding 等同时到达。只有混合测试才能暴露资源争用和优先级问题。

### 21. 性能退化的常见原因地图

| 现象 | 可能原因 |
| --- | --- |
| TTFT 很高 | 输入长、prefill 慢、排队、RAG/工具前置慢、冷启动 |
| 流输出断断续续 | TPOT 高、decode 被 prefill 抢占、并发过多、网络缓冲 |
| 总时间很长 | 输出过长、多轮 Agent、工具慢、排队、模型慢 |
| 高峰期 P99 暴涨 | 容量接近饱和、长请求阻塞、没有背压/优先级 |
| GPU OOM | KV Cache/并发/上下文/batch 超出显存，或权重太大 |
| GPU 利用率低但响应慢 | CPU/tokenizer、网络、RAG、调度、请求太小或排队配置问题 |
| 吞吐低 | batch/调度不佳、模型/硬件不匹配、带宽受限、外部工具阻塞 |

这是排查的起点，而不是结论。真正诊断需要 trace、指标和真实负载样本。

### 22. 性能优化的层级顺序

性能问题不应一上来就换更贵 GPU。通常可按以下顺序：

1. 明确用户/业务目标：优先 TTFT、吞吐、成本还是离线完成时间？
2. 拆分端到端时间，确认瓶颈是否真在模型。
3. 优化上下文：历史摘要、RAG 重排、工具集收缩、输出预算。
4. 优化应用流程：减少无效 Agent Loop、并行独立 I/O、长任务异步化。
5. 设置限流、队列、优先级、并发与成本预算。
6. 调整模型、量化、推理引擎和 batch/调度参数。
7. 增加或更换硬件、增加副本、采用多 GPU/弹性扩容。
8. 通过压测和灰度验证，不只看单次 benchmark。

这种顺序能避免用昂贵硬件掩盖低效上下文或无限循环等应用设计问题。

### 23. 一个完整走读：在线客服与离线报告共享模型服务

假设同一模型服务同时处理：

```text
在线客服：短问题、希望 TTFT < 1 秒、输出几十到几百 token
离线报告：长 RAG、长输出、可以等待数分钟
```

如果两类任务完全混在同一队列：

- 离线报告会使用长 prefill、长 decode 和大量 KV Cache；
- 在线客服可能排在报告后，TTFT 明显增加；
- GPU 满载时短请求体验恶化；
- 只看总吞吐可能看不出客服 SLA 已失败。

合理设计可能是：

```text
交互请求使用高优先级队列/独立副本/严格输出上限
长报告使用异步任务、较低优先级队列与更大任务预算
网关按任务类型路由模型和并发资源
控制层监控各队列 TTFT、P95、成本与积压
```

这说明性能治理本质上是服务等级、资源隔离和产品策略问题，而不只是 GPU 参数调优。

### 24. 一个完整走读：Agent Loop 为什么容易放大延迟

一个 Agent 任务可能经历：

```text
第 1 轮：模型决定查订单
-> 工具调用
第 2 轮：模型决定查政策
-> RAG/工具调用
第 3 轮：模型决定请求确认
-> 等待用户
第 4 轮：确认后创建工单
-> 工具调用
第 5 轮：模型生成总结
```

总延迟不是一次模型调用，而是多轮：

```text
多次 prefill + 多次 decode + 工具网络时间 + 等待时间 + 队列时间
```

优化不应简单要求“模型再快一点”，还可：

- 合并可确定的业务查询；
- 减少不必要工具和反思轮；
- 将等待人工转为持久化状态，不占模型/GPU；
- 将独立只读查询并行（在预算允许时）；
- 将长任务切分、异步化；
- 对每一轮使用最小必要上下文。

这与 M12 高级 Agent 工程直接相连。

### 25. 建立 SLO：性能目标必须可表达

服务等级目标（SLO）是对用户体验和系统可靠性的可量化承诺。示例：

```text
交互问答：P95 TTFT <= 1.5s；P95 完成时间 <= 8s
异步报告：95% 任务在 5 分钟内完成
模型服务：GPU OOM 导致的请求失败率 < 某阈值
高优客服队列：P95 排队等待 <= 某阈值
```

具体数值必须由业务、模型、硬件和成本共同确定，本节不提供万能目标。重要的是：没有 SLO，就无法判断优化是否成功，也无法在吞吐、延迟和成本之间做明确取舍。

### 26. 性能与成本的关系

提高性能往往需要成本：更多 GPU 副本、更多显存、更低量化、较低队列等待、保留冗余容量。降低成本也可能影响性能：使用较小模型、共享更高并发、排队更久、限制上下文/输出。

合理决策不是“性能越高越好”或“成本越低越好”，而是：

```text
在满足关键用户体验、安全与可靠性目标的前提下，
选择总拥有成本可接受的架构和运行策略。
```

模型网关、任务优先级、异步化、路由、量化和容量规划，都是实现这一平衡的手段。

## 常见误区

### 误区 1：tokens/s 高就代表用户体验一定好

不一定。tokens/s 主要反映输出生成速度；用户可能仍因长输入 prefill、RAG、排队或工具调用而等很久才看到首字。需要同时看 TTFT、E2E、P95/P99 和错误率。

### 误区 2：增加并发一定提高吞吐

在资源未饱和时可能提高吞吐；超过显存/计算/带宽/队列能力后，会造成排队、KV Cache 压力、OOM、上下文交换和尾部延迟恶化，吞吐也可能下降。

### 误区 3：KV Cache 是无关紧要的内部实现细节

不对。KV Cache 是逐 token 高效生成的关键，也是长上下文和并发显存规划的核心。不了解它就难以理解模型为何单用户可跑、多用户 OOM。

### 误区 4：流式输出能让模型真正更快完成

流式主要改善用户更早看到输出，通常不减少模型总计算量、长 prompt prefill 或工具等待。完整完成时间未必大幅缩短。

### 误区 5：把 batch 调大总是最佳优化

更大 batch 可提升吞吐，但也会增显存、等待时间和尾部延迟。交互式和离线任务的最优 batch/调度策略不同。

### 误区 6：GPU 利用率低说明应该提高并发

不一定。低利用率可能由 CPU/tokenizer、RAG、网络、队列或请求模式导致。盲目提高并发可能先把 KV Cache 撑爆。应先定位端到端瓶颈。

### 误区 7：长上下文问题只能靠更大上下文窗口解决

大窗口能容纳更多 token，但会增加 prefill、KV Cache、成本和质量风险。更好的方法通常包括检索、重排、摘要、artifact 引用、任务分段和最小上下文构造。

## 本节练习

### 练习 1：区分指标

某服务用户请求后 6 秒才看到第一个 token，但之后以每秒 30 token 的速度输出，最终 8 秒完成。请分别描述 TTFT、输出速度和端到端时间，并判断优先排查方向。

答案：TTFT 约 6 秒，输出速度约 30 tokens/s，端到端约 8 秒。输出阶段相对较快，主要问题在首字前的 6 秒。应优先检查模型服务排队、输入上下文/pre-fill、RAG/工具前置处理、冷启动和网关网络，而不是首先优化 decode 速度。

### 练习 2：分析容量变化

一个模型服务在 4 个并发短对话时稳定，但当请求都带长文档上下文并增加到 20 并发时 OOM。请解释最主要的资源变化。

答案：模型权重通常仍只加载一份，主要增长是每个并发请求的 KV Cache、输入/输出状态和 batch 临时空间。长上下文使单请求缓存更大，20 并发又将其叠加，因此显存可能超限。应控制上下文、输出、并发/队列或使用更大资源/合适量化与缓存策略。

### 练习 3：选择调度策略

一个系统同时有在线客服短问答和可等待的长报告任务。为什么不应简单放在同一个先进先出队列？

答案：长报告的长 prefill、长 decode 和 KV Cache 可能让短问答排队，显著破坏客服 TTFT/SLA；两个任务的延迟目标不同。应考虑优先级队列、独立资源池/副本、异步报告、并发/输出预算和按任务类型路由，以兼顾交互体验与总体吞吐。

### 练习 4：解释连续批处理

为什么传统静态 batch 在生成长度不同的用户请求上会浪费资源？连续批处理如何改进？

答案：静态 batch 中短请求完成后，可能要等待同批长请求结束，释放的资源无法立即使用。连续批处理允许请求在生成过程中动态加入/退出，短请求完成后的位置可给新请求使用，从而提高在线服务的吞吐与资源利用率；代价是调度和 KV Cache 管理更复杂。

## 自测题

### 自测 1：TTFT、TPOT 与 E2E 延迟分别是什么？

答案：TTFT 是从请求开始到收到第一个输出 token 的时间，反映首字响应；TPOT 是后续每个输出 token 的平均生成时间，反映流式输出速度；E2E 延迟是从请求开始到最终结果完成的总时间，包含前置处理、排队、prefill、decode、工具和网络等全部阶段。

### 自测 2：KV Cache 为什么既重要又昂贵？

答案：它缓存历史 token 的注意力 key/value，使生成新 token 时不必重算全部历史，从而显著加速 decode；但它会随模型结构、上下文、输出和活跃并发增长，占用大量 VRAM，因此成为长上下文高并发服务的关键容量约束。

### 自测 3：吞吐和延迟为什么可能互相冲突？

答案：通过更大 batch、更高并发可以提高硬件利用率和总体 tokens/s，但请求可能等待凑批或争夺显存/计算资源，TTFT、P95/P99 延迟和公平性可能变差。需按交互/离线场景设定目标和调度策略。

### 自测 4：为什么模型服务接近满载时尾部延迟容易暴涨？

答案：当到达速率接近或超过服务能力，少量长请求、波动或资源争用都会积累排队；请求在系统停留时间增加，又会增加活跃并发和 KV Cache 压力，形成正反馈。需要预留容量、背压、限流、优先级和扩容策略。

### 自测 5：优化模型服务性能的第一步是什么？

答案：先明确业务目标和工作负载，并拆分端到端时间与资源指标，确定瓶颈在前置处理、排队、prefill、decode、工具还是网络。不能在没有测量的情况下只靠换模型、加 GPU 或调大并发。

## 本节小结

本节建立了推理性能的完整语言：TTFT 反映首字体验，TPOT 反映逐 token 输出速度，E2E 反映用户最终等待；吞吐、并发和排队决定系统容量；KV Cache 用显存换取生成效率，并随着上下文、输出和并发增长；Batch 与连续批处理提高 GPU 利用率，但需要在吞吐、延迟、显存和公平性之间调度。性能优化应从真实目标、指标和负载开始。
