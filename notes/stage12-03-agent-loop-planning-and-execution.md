# M12 第 3 节：Agent Loop、规划与执行

## 本节定位

上一节把 Agent 看成一个有状态、有生命周期的业务任务。本节进入其中最容易被误解的一部分：任务处于 `RUNNING` 时，Agent 到底怎样一步步推进？

很多演示会把 Agent 描述成“模型自己思考，自己调用工具，最后完成任务”。这句话只保留了现象，遗漏了真正的工程边界。可靠的 Agent 不是让模型直接控制系统，而是让模型在受限动作空间中提出下一步建议，由程序验证、执行、记录观察结果，再决定是否继续。

本节讨论的是这一条受控闭环：

```text
读取任务状态
-> 理解目标与当前事实
-> 规划或选择下一步
-> 服务端校验
-> 执行允许的动作
-> 获得并规范化观察结果
-> 更新状态
-> 判断继续、等待或结束
```

它通常被称为 **Agent Loop**。后续的记忆、持久化、长任务、沙箱、Multi-Agent，都是在这条基础闭环之上扩展，而不是替代它。

## 本节学习目标

学完后，你应当能：

1. 用工程语言说明 Agent Loop 的组成和每一步职责。
2. 区分“计划（plan）”“动作（action）”“工具调用（tool call）”“观察（observation）”“最终答复（final answer）”。
3. 解释为什么模型只能提出动作，不能直接拥有工具执行权。
4. 理解 ReAct、Plan-and-Execute、单步决策等常见执行模式的差异。
5. 设计步骤上限、时间预算、工具预算、重复检测和停止条件。
6. 判断一次任务是应该继续循环、等待外部事件、转人工，还是结束。
7. 理解“模型输出看起来合理”与“任务实际完成”之间的区别。

## 一句话先讲透

> Agent Loop 的本质不是让模型无限思考，而是让模型在每一轮基于已验证事实选择一个受限动作，并由系统以预算、权限、状态机和可观测性约束这条循环何时继续、何时暂停、何时停止。

## 基础知识铺垫

### 1. 一次 LLM 调用、工作流和 Agent Loop 的区别

先建立三个层次，避免把它们混为一谈。

| 层次 | 结构 | 适合场景 | 主要特点 |
| --- | --- | --- | --- |
| 一次 LLM 调用 | 输入 -> 模型 -> 输出 | 摘要、分类、改写 | 无外部动作，最简单 |
| 固定 AI 工作流 | 固定步骤 A -> B -> C | 已知步骤的抽取、审核、生成 | 稳定、易测试，分支由程序决定 |
| Agent Loop | 状态 -> 模型选动作 -> 系统执行 -> 新状态 | 路径不完全确定的多步骤任务 | 下一步由模型在约束内选择 |

例如“把用户文本分类为退款、物流或账户问题”，一次模型调用就足够。若“先抽取字段，再校验格式，再写入数据库”，可以采用固定工作流。若“根据用户问题决定要不要查知识库、查订单、追问信息、请求确认，最后组织答案”，才可能需要 Agent Loop。

注意：Agent Loop 并不比固定工作流更高级。它只是把“下一步路径选择”从预先写死的程序逻辑，部分交给模型。路径越不确定，Agent 的价值越大；路径越确定，Agent 带来的不稳定性越不值得。

### 2. Agent 的最小闭环

一个最小 Agent Loop 可以抽象成五个元素：

```text
Goal         任务目标：最终要实现什么
State        当前状态：已经确认的事实、预算、历史
Action Space 可选动作：允许模型提出什么
Observation  观察结果：动作执行后系统得到什么事实
Stop Rule    停止规则：何时成功、失败、等待或终止
```

可以写成概念过程：

```text
while task is allowed to run:
    decision = model(goal, verified_state, allowed_actions)
    validate(decision)
    outcome = execute_or_wait(decision)
    state = record_verified_outcome(state, outcome)
    if stop_rule(state): finish
```

这不是可以直接上线的代码，而是一张职责图。任何可靠实现都应回答：谁维护 `state`？谁定义 `allowed_actions`？谁执行 `validate`？什么条件触发 `stop_rule`？

### 3. 模型的“决策”不是系统的“事实”

这是 Agent 工程里极其重要的分界线。

模型可以输出：

```text
我需要调用 query_order(order_id="A1001")。
```

这在系统中只是一个**动作提议**，而不是订单已被查询的事实。只有服务端完成以下步骤后，才产生可信事实：

1. 确认工具名在允许列表中。
2. 校验参数模式、当前用户、租户与资源权限。
3. 执行真实工具或受控模拟工具。
4. 接收结果，验证结果结构和来源。
5. 将结果作为 observation 写入任务状态。

因此应始终区分：

| 内容 | 来源 | 能否直接作为业务事实 |
| --- | --- | --- |
| 模型计划 | LLM | 不能，只是建议 |
| 模型工具调用参数 | LLM | 不能，必须校验 |
| 工具原始响应 | 外部系统 | 不一定，仍需验证和脱敏 |
| 已验证 observation | 受控后端 | 可以作为任务依据 |
| 最终答复 | LLM 或模板 | 需建立在已验证事实之上 |

### 4. 计划和动作不是同一个概念

人会自然地先规划再行动，Agent 也可能需要这样做，但两者必须分开：

- **计划（plan）**：为了完成目标，认为可能要采取哪些步骤的高层安排。
- **动作（action）**：当前这一轮实际请求系统执行的一个具体行为。

例如用户问“物流一直没更新，帮我处理”：

```text
计划：
1. 查询订单归属和当前状态。
2. 查询物流轨迹。
3. 判断是否需要创建工单。
4. 如需要，获取用户确认后创建工单。

当前动作：
query_order(order_id="A1001")
```

计划可以随着新证据调整：订单不存在、物流已签收、用户没有权限，都会改变后续路线。动作则必须精确、可校验、可执行。若把模糊计划直接当作动作，就会出现“查一下物流”“帮我处理一下”这类无法由工具安全执行的命令。

### 5. 什么是 observation，为什么不能叫“模型记忆”

observation（观察结果）是 Agent 执行动作后，从外部世界获得并经系统处理的结果。例如：

```text
工具：query_order
原始结果：{...大量订单字段...}
允许写入 observation 的结果：
{
  "order_id": "A1001",
  "belongs_to_current_user": true,
  "status": "SHIPPED",
  "logistics_status": "NO_UPDATE_72H"
}
```

它与普通“聊天记忆”不同：

- observation 强调来源、时间、工具、权限和结构；
- observation 是模型下一轮推理可用的事实输入；
- observation 也可能过期，因此需要时间戳与有效期；
- observation 不应原样塞入所有敏感工具响应。

把 observation 说成“模型记住了订单状态”很容易淡化其工程属性。正确说法是：系统保存了一个经过验证的订单观察结果，并在受控上下文中提供给模型。

### 6. 工具与动作空间（Action Space）

模型不是在“全世界所有动作”中自由选择，而是在服务端提供的动作空间中选择。动作空间可以包含：

```text
只读工具：query_order、search_knowledge_base、get_ticket
受控写工具：create_ticket、send_notification
交互动作：ask_user、request_confirmation
流程动作：finish、handoff_to_human
```

一个工具是否出现在某次任务的可用工具列表中，通常取决于：

- 当前任务类型；
- 当前状态；
- 用户与租户权限；
- 环境（开发、测试、生产）；
- 风险等级；
- 当前预算；
- 是否已有足够前置事实。

例如任务还没有查询到订单归属时，`create_ticket` 即使系统中存在，也未必应出现在模型可选动作中。**缩小动作空间**本身就是降低错误率和攻击面的重要方法。

### 7. 为什么需要“停下来”的能力

人们容易关注 Agent 会做什么，却忽略它何时必须停止。没有停止条件的循环可能带来：

- 反复调用同一个工具，浪费成本；
- 因错误 observation 进入死循环；
- 不断生成更长上下文，质量变差；
- 在不允许的情况下继续尝试写操作；
- 长时间占用 worker，挤压其他任务。

因此一个 Agent 需要至少四类停止出口：

| 出口 | 含义 | 例子 |
| --- | --- | --- |
| 成功结束 | 已满足客观完成条件 | 已获得订单事实并形成有依据的答复 |
| 失败结束 | 不可恢复或超过预算 | 工具连续失败且重试耗尽 |
| 等待暂停 | 等待用户、人工或异步结果 | 需要用户确认写操作 |
| 安全终止 | 发现权限、策略或风险问题 | 模型尝试未授权工具 |

“模型输出最终答案”只是一个可能信号，不是唯一也不是必然的成功出口。

## 本节主题系统讲解

### 1. Agent Loop 的标准轮次

一次受控循环可以拆成八个步骤。现实实现可合并其中部分，但职责不应丢失。

#### 第 1 步：装载可运行的任务状态

执行器读取任务，确认它确实处于可运行状态，例如 `RUNNING`，并加载：

- 原始目标和经校验的输入；
- 当前已验证 observation；
- 已发生的关键动作摘要；
- 用户、租户、权限上下文；
- 剩余步骤、时间、token、工具预算；
- 当前允许动作；
- 待确认动作或失败信息（如有）。

此时不能只读“对话文本”，否则执行器可能失去权限、预算或状态机事实。

#### 第 2 步：构造模型可见上下文

模型需要理解任务，但不应获得整个数据库、全部日志或所有内部实现细节。上下文应尽量由结构化事实组成：

```text
目标：解释订单物流异常；若需创建工单，必须先请求用户确认。
已知事实：订单 A1001 属于当前用户；72 小时无物流更新。
约束：只能使用列出的工具；不可承诺未验证结果；不可绕过确认。
可选动作：request_confirmation、create_ticket（需确认后）、finish。
预算：剩余 3 步；只读工具预算 2 次；写工具预算 1 次。
```

这里通常还会附带系统提示、工具模式、输出 schema 等，但核心原则是：**给模型完成当前决策所需的最少可信信息**。

#### 第 3 步：模型产生结构化决策

理想情况下，模型不返回随意的自然语言，而返回符合 schema 的决策。概念上可以是：

```json
{
  "decision_type": "tool_call",
  "tool_name": "query_logistics",
  "arguments": {"order_id": "A1001"},
  "reason_summary": "需要先获得真实物流轨迹再判断。"
}
```

或：

```json
{
  "decision_type": "wait_for_human",
  "pending_action": "create_ticket",
  "confirmation_summary": "物流 72 小时未更新，是否创建客服工单？"
}
```

或：

```json
{
  "decision_type": "finish",
  "answer_draft": "...",
  "evidence_refs": ["obs_order_01", "obs_logistics_02"]
}
```

结构化输出不是魔法。模型仍可能出错、字段缺失、提议不存在工具，因此下一步仍必须由系统验证。

#### 第 4 步：决策校验与策略检查

这是模型建议进入真实系统前的关口。至少要检查：

1. `decision_type` 是否是已知类型；
2. 工具名是否在当前可用工具集；
3. 参数是否符合 schema、类型、范围与格式；
4. 参数是否引用了当前任务允许访问的资源；
5. 当前状态是否允许这一动作；
6. 是否超出工具次数、费用、时间或风险预算；
7. 写操作是否已有有效确认；
8. 动作是否符合业务策略、数据权限与安全策略。

校验失败时，系统不应“照做后再看看”。可采取几种受控策略：

- 向模型返回受限的错误 observation，让它重新规划；
- 直接结束为策略拒绝或执行失败；
- 转人工；
- 对用户提出澄清问题。

选哪一种取决于错误类型和风险等级。

#### 第 5 步：执行动作或进入等待

通过校验后，系统才实际执行。动作大体分为四类：

| 动作类别 | 例子 | 执行后的常见走向 |
| --- | --- | --- |
| 同步只读 | 查订单、检索知识库 | 写入 observation，下一轮继续 |
| 同步写入 | 创建草稿、写备注 | 记录结果，下一轮继续或成功 |
| 异步动作 | 长报告生成、第三方处理 | 转 `WAITING_TOOL` |
| 交互动作 | 询问用户、请求审批 | 转 `WAITING_INPUT` / `WAITING_HUMAN` |

请注意：`ask_user`、`request_confirmation` 并不是“模型说一句话”这么简单，而是会改变任务状态，让执行循环停止，等待外部事件恢复。

#### 第 6 步：把结果规范化为 observation

工具返回不是自动可信、自动适合给模型看的。系统通常要进行：

- 响应 schema 校验；
- 字段白名单选择；
- 敏感信息脱敏；
- 错误分类；
- 结果长度截断或摘要；
- 结果与 `task_id`、`tool_call_id` 的关联；
- 时间戳、数据版本、来源记录。

随后才形成 `observation`。这一步既避免模型被无关噪声淹没，也避免把敏感字段无意放入模型上下文。

#### 第 7 步：更新任务状态和审计记录

每轮至少要记录对任务后续有意义的信息：

```text
第几轮
模型决策类型
请求的动作/工具
策略是否通过
执行结果概要
新增 observation 引用
当前预算消耗
状态转移
trace_id / model 信息 / 耗时
```

这不是为了保存模型“完整思维过程”。系统需要记录的是可复现、可审计、能定位故障的决策和事实，而不是不必要的内部推理文本。

#### 第 8 步：评估停止条件

每轮结束前系统检查：

- 任务是否已经满足成功条件？
- 是否进入等待状态？
- 是否触发取消、安全拒绝或不可恢复失败？
- 是否达到最大步数、总时限、工具次数或成本上限？
- 是否出现重复动作或没有信息增益？

只有都未触发时，才开始下一轮。这样“循环”才是有边界的循环。

### 2. 单步决策模式：每轮只允许一个下一步

最常用、最易控的 Agent 模式是单步决策：每次只让模型选择一个动作，然后重新观察。

```text
状态 S0 -> 模型选择 A1 -> 系统执行 -> 观察 O1
状态 S1 -> 模型选择 A2 -> 系统执行 -> 观察 O2
状态 S2 -> 模型选择结束或等待
```

优点：

- 每一步都有最新真实信息；
- 易插入权限、预算和人工审核；
- 容易定位哪一步失败；
- 可在每步后取消或恢复；
- 不要求模型一开始就规划完全正确。

缺点：

- 模型调用次数可能更多；
- 如果每步信息太少，可能显得犹豫或产生无意义动作；
- 需要设计好 observation 压缩，否则上下文会膨胀。

对于包含外部工具和写操作的企业 Agent，单步决策通常是稳妥起点。

### 3. ReAct：推理与行动交替，但不要误解“推理”

ReAct 是 Reason + Act 的简称，核心思想是模型在“根据观察作出判断”和“提出下一步动作”之间交替：

```text
Thought / reasoning: 当前还缺少物流事实。
Action: query_logistics(A1001)
Observation: 72 小时无更新。
Thought / reasoning: 信息足够，需要用户确认是否创建工单。
Action: request_confirmation(...)
```

它的真正价值不是展示一段很长的“思考过程”，而是让 Agent 能根据外部观察逐步修正路线。工程上应关注：

- 动作是否结构化；
- observation 是否真实、最小、受控；
- 下一步是否可解释；
- 是否存在预算与停机规则。

不应该依赖或要求记录模型的完整隐藏推理文本。对用户或日志而言，短的决策理由摘要通常已足够，例如“为了确认物流状态，需要查询物流信息”。

### 4. Plan-and-Execute：先形成计划，再逐项执行

Plan-and-Execute 模式通常先让模型形成较高层计划，然后由执行器逐步完成：

```text
Plan:
1. 检索相关退款政策。
2. 检查用户订单是否在适用范围。
3. 汇总可执行选项。

Execute:
step 1 -> observation
step 2 -> observation
step 3 -> final answer
```

它适合以下场景：

- 目标较复杂，但子步骤具有明显结构；
- 需要展示任务进度；
- 可将计划提交给人工审核；
- 可以并行或分配部分独立子任务。

但计划绝不能被当作不可变剧本。真实执行中可能发现政策不存在、用户没有订单权限、某个工具不可用。此时需要允许：

```text
continue plan
revise plan
skip step with reason
stop task
ask for human help
```

否则“先计划”会把模型早期的错误放大为整个任务的错误。

### 5. 规划粒度：太粗与太细都不合适

规划粒度决定了计划是否可执行、可验证。

**太粗：**

```text
1. 分析问题。
2. 解决问题。
3. 回复用户。
```

没有动作、条件和结果标准，几乎无法执行。

**太细：**

```text
1. 阅读第一句话。
2. 思考退款的定义。
3. 再阅读第二句话。
...
```

把模型内部细节伪装成业务步骤，既无法可靠验证，又徒增复杂度。

更合理的粒度是业务可观察、可执行、可判断成功的子目标：

```text
1. 获取当前用户对目标订单的访问事实。
2. 获取与问题相关的物流事实。
3. 根据政策与事实判断可提供的处理选项。
4. 如涉及写操作，取得明确确认。
```

### 6. 规划与执行的职责分离

在简单 Agent 中，一个模型调用既规划又决定动作并无问题；在复杂任务中，可以明确分层：

| 角色 | 关注点 | 不应负责的事 |
| --- | --- | --- |
| Planner | 目标分解、依赖关系、优先级 | 直接执行高风险动作 |
| Executor | 根据当前步骤选择受限工具并执行 | 擅自扩大任务目标 |
| Verifier/Critic | 检查结果是否满足标准、是否有证据 | 代替权限系统批准动作 |
| Orchestrator | 管理状态、预算、调度、人工介入 | 用自然语言猜测业务事实 |

这不意味着每个项目都要引入四个模型或四个 Agent。它首先是一种**职责思维**：规划、执行、校验、调度可以在同一服务中实现，但不能把安全和状态控制完全混入模型提示词。

### 7. “模型选择动作”与“程序选择动作”的边界

可把下一步决策分为三类：

| 决策类型 | 主要决策者 | 例子 |
| --- | --- | --- |
| 确定性业务规则 | 程序 | 用户无订单权限，直接拒绝 |
| 语义路径选择 | 模型 + 程序约束 | 用户问题该检索知识库还是查询订单 |
| 高风险授权 | 程序 + 人工 | 是否允许创建工单、退款、发消息 |

模型适合处理语言理解、不完整表达、多个合理探索路径；程序适合处理权限、金额、状态流转、确定条件；人工适合处理高影响、价值判断或规则不完备的决定。

一个成熟 Agent 的设计不是“让模型做得越多越好”，而是把不同类型的决策交给合适的控制者。

### 8. 动作校验的四层防线

当模型请求一个工具时，建议至少从四层检查：

#### 8.1 结构层：格式是否正确

- 是否是合法 JSON 或结构化输出；
- 工具名、参数名、类型是否符合 schema；
- 必填字段是否完整；
- 枚举值、长度、数值范围是否正确。

#### 8.2 能力层：这个动作是否在当前动作空间中

- 工具是否注册；
- 当前任务类型是否允许；
- 当前环境是否允许；
- 当前任务状态是否允许调用。

#### 8.3 权限与业务层：当前主体能否对当前资源做此事

- 用户是否有权访问这个订单；
- 该租户是否可以查询这个知识库；
- 是否满足创建工单的前置条件；
- 是否已经完成必要确认。

#### 8.4 风险与预算层：现在做是否仍然合算、安全

- 是否超过总步骤/调用次数/金额/时间预算；
- 是否是重复或低信息增益动作；
- 是否会产生不可逆副作用；
- 是否需要升级到人工处理。

四层的结论都应由系统计算，而不是让模型在输出中自我声明“我有权限”“我没有超预算”。

### 9. 观察结果的质量决定下一轮决策质量

Agent 不只受模型能力影响，也受 observation 质量影响。一个坏 observation 往往使后续每一轮都偏离。

常见问题：

| 问题 | 后果 | 改进 |
| --- | --- | --- |
| 工具返回太多原始字段 | 上下文噪声、泄露风险 | 字段白名单和摘要 |
| 结果无来源/时间 | 模型把过期数据当事实 | 附带来源、获取时间、版本 |
| 错误被当作空结果 | 模型误以为“没有数据” | 显式区分成功、未找到、拒绝、超时 |
| 结构不稳定 | 模型难以可靠引用字段 | 统一 schema |
| 没有权限过滤 | 越权信息进入模型上下文 | 工具层先做授权 |

建议将 observation 设计为“模型要据此做下一步决策的最小事实包”，而不是外部 API 响应的镜像。

### 10. 停止条件的完整设计

停止条件不应只有 `max_steps`。至少需要组合不同类型的边界。

#### 10.1 目标完成边界

任务不是因为模型说“完成”，而是因为系统能验证完成标准。例如：

- 已获得必须的业务事实；
- 最终输出通过格式、证据、权限检查；
- 写操作返回可验证的资源 ID；
- 已发送的外部副作用已确认或可追踪。

#### 10.2 步数边界

例如最多 8 轮。它防止无限循环，但不能保证每轮都有价值，因此还需其他规则。

#### 10.3 时间边界

例如一次同步 run 最多 60 秒、整个任务最多 30 分钟。达到时间边界后应根据任务类型失败、等待重试或转后台。

#### 10.4 成本边界

可以限制：模型调用次数、token 上限、付费工具调用次数、单任务允许的最大费用。成本预算应与任务优先级和业务价值匹配。

#### 10.5 风险边界

例如写操作最多一次；发送通知前必须确认；模型连续提议被策略拒绝两次后转人工。风险边界通常比通用步数更贴近业务安全。

#### 10.6 无进展边界

如果多轮后没有新增事实、重复调用同一工具、反复提出同一澄清问题，就应停止、调整策略或交给人工。

### 11. 防止循环：不仅是限制最大步数

以下是一段典型无效循环：

```text
Agent：查询物流
工具：物流暂时不可用
Agent：再次查询物流
工具：物流暂时不可用
Agent：再次查询物流
...
```

最大步数能最终切断它，但太晚。还可以增加：

1. **动作签名去重**：对 `(tool_name, normalized_arguments)` 形成签名，短时间内相同失败动作超过阈值时禁止重复。
2. **错误感知策略**：工具超时、限流、权限拒绝分别有不同后续路线；不能都让模型自由重试。
3. **信息增益判断**：新动作能否获得与已有 observation 不同的信息？
4. **计划进度检查**：计划中的关键子目标是否已推进；长期无推进则重规划或结束。
5. **反思/校验轮限制**：允许有限次数检查，不允许无止境“再检查一次”。

注意，重复并非必然错误。某些业务确实需要轮询，但轮询必须由明确的间隔、最大次数和截止时间控制，通常不应由模型每一轮临时决定。

### 12. 何时需要重新规划

计划不是一次生成后永远正确。以下事件通常值得重新规划：

- 关键工具返回“资源不存在”或“无权限”；
- 用户补充了会改变目标的新信息；
- 人工审核拒绝某个待执行动作；
- 依赖工具长期不可用；
- 已完成步骤发现前提错误；
- 预算收紧，需要从完整方案降级为最小可行答复。

重新规划时，模型应看到：原计划、已完成步骤、失败/拒绝的原因、不可再尝试的动作、剩余预算。否则模型很可能重新提出已经被拒绝的同一行动。

### 13. 最终答复生成应在“事实闭环”之后

一个常见错误是模型一收到用户问题，就迫不及待生成最终答复；随后即使工具查询失败，用户仍可能看到肯定性结论。

更稳妥的顺序：

```text
先获取和验证事实
-> 确认无需更多动作或已进入等待
-> 基于 observation 生成回答草稿
-> 进行引用、敏感信息、格式检查
-> 标记任务成功或等待
-> 输出给用户
```

这不意味着每句话都必须调用工具。对于纯知识问题，可由检索结果或模型已有能力回答；关键在于系统知道哪些结论是“外部事实”、哪些是“建议或解释”，不能混淆。

### 14. 最终答复也可能不是结束

在聊天界面里，用户看到一条答复后常以为任务结束。但在工程上可能有几种情形：

| 情形 | 用户看到什么 | 任务状态 |
| --- | --- | --- |
| 已完成 | 最终答复 | `SUCCEEDED` |
| 等待用户 | 澄清问题或确认请求 | `WAITING_INPUT` / `WAITING_HUMAN` |
| 后台继续 | 已受理，稍后通知 | `WAITING_TOOL` / `PENDING` |
| 安全拒绝 | 无法执行的说明和替代建议 | `FAILED` / `CANCELLED` / 受控完成 |

因此 UI 文案、任务状态和后台调度必须一致。不要显示“已完成”，实际却仍在执行写操作；也不要显示“失败”，实际是在等待用户选择。

### 15. Agent Loop 的伪代码应体现控制权归属

下面伪代码用于理解责任边界，不绑定任何 SDK：

```text
repeat while task.status == RUNNING:
    enforce_task_budget(task)
    context = build_minimal_verified_context(task)
    decision = ask_model_for_structured_decision(context)

    validated = policy_engine.validate(decision, task)
    if validated is rejected:
        record_rejection(task, validated.reason)
        decide_replan_or_stop(task)
        continue

    outcome = controlled_executor.execute(validated.action)
    apply_outcome_to_task_state(task, outcome)

    if task is terminal or waiting:
        stop
```

其中最重要的词不是 `ask_model`，而是：

- `build_minimal_verified_context`
- `policy_engine.validate`
- `controlled_executor.execute`
- `apply_outcome_to_task_state`
- `enforce_task_budget`

它们说明执行权和状态控制权属于系统，而不是模型。

### 16. 一个完整走读：退款咨询 Agent

用户问题：`“我的订单能退款吗？”`

假设系统允许的动作包括检索政策、查询订单、追问订单号、请求确认、结束；退款操作本身不由 Agent 直接执行。

#### 第一轮：信息不充分

任务状态中没有订单号。模型应选择：

```text
action = ask_user
question = 请提供订单号，以便核对订单状态和退款政策。
```

系统将任务转为 `WAITING_INPUT`，而不是让模型猜测订单、也不是标记失败。

#### 第二轮：用户补充订单号

系统校验用户输入，恢复为 `RUNNING`。模型可能选择 `query_order(A1001)`。系统先校验当前用户是否有权访问 A1001，查询成功后写入 observation：订单支付时间、履约状态、是否存在退款记录等。

#### 第三轮：需要政策证据

模型选择检索退款政策。检索结果经权限、版本和引用位置处理后成为 observation。

#### 第四轮：完成解释

模型基于订单事实与政策证据，生成带条件的答复：当前订单符合/暂不符合哪些条件，下一步可以怎么做。系统检查结果没有把未验证信息说成事实、没有泄露敏感字段、引用了正确证据后，标记 `SUCCEEDED`。

这里没有“模型自行退款”。如果用户进一步要求退款，系统应启动不同的高风险任务，走明确的资格校验、确认和业务流程。

### 17. Agent Loop 的可观测指标

只看“任务成功率”不足以理解 Loop 是否健康。可观测性可包含：

| 指标 | 它帮助发现什么 |
| --- | --- |
| 平均轮次 / P95 轮次 | 任务是否过度绕路 |
| 单任务工具调用数 | 工具使用是否膨胀 |
| 重复动作率 | 是否存在循环或错误规划 |
| 策略拒绝率 | 工具 schema、prompt 或权限设计是否有问题 |
| 等待人工比例与时长 | 是否把太多判断转给人工 |
| 重规划率 | 初始计划质量与外部环境变化 |
| 最大步数终止率 | 是否预算不足或逻辑不收敛 |
| 最终答案证据覆盖率 | 结论是否建立在观察事实之上 |

指标不是为了追求“轮次越低越好”。复杂任务本就需要多步；关键是每一步是否必要、是否安全、是否带来信息或业务进展。

### 18. 单 Agent Loop 的能力边界

理解 Agent Loop 也要知道它不能解决什么：

- 它不能替代真正的权限系统；
- 它不能保证模型对业务规则理解无误；
- 它不能让不可靠工具变可靠；
- 它不能自动解决长时间等待和跨进程恢复，需要持久化与队列；
- 它不能解决所有复杂任务的拆分协作，可能需要 Multi-Agent；
- 它不能将高风险决策从人工与业务规则中“自动化掉”。

Agent Loop 是控制框架，不是万能能力来源。能力质量取决于模型、工具、数据、策略、状态管理和人工机制共同组成的系统。

## 常见误区

### 误区 1：Agent Loop 就是一段无限 `while` 循环

错误。循环必须受任务状态、步数、时间、成本、权限、重复检测和停止条件限制。无边界循环不是 Agent，而是事故来源。

### 误区 2：模型产生 tool call，就可以直接调用

tool call 是不可信输入。必须校验工具白名单、参数、资源权限、当前状态、确认记录和预算。

### 误区 3：计划越详细，任务越可靠

计划应保持可执行的业务粒度，并允许依据 observation 调整。过度细化会制造伪精确，计划不可调整则会固化早期错误。

### 误区 4：工具原始 JSON 可以完整回传给模型

原始响应可能冗长、敏感、结构不稳定或包含无关信息。应先校验、脱敏、筛选和规范化为 observation。

### 误区 5：模型说“已创建”即可将任务标记成功

任务成功应以已验证的工具结果、持久化记录和业务完成条件为准。模型自然语言不能充当外部世界的回执。

### 误区 6：为避免出错，所有下一步都让程序写死

这样会退化为固定工作流，失去 Agent 处理语义不确定性和动态路径的价值。正确做法是让模型负责合适的路径选择，让系统负责不应交给模型的确定性控制。

### 误区 7：把完整模型推理文本当作审计日志

审计需要可验证的事件、动作、参数摘要、策略结论、工具结果引用与状态转移。保存不必要的内部推理文本既不能替代审计，也可能增加隐私、合规和噪声问题。

## 本节练习

### 练习 1：区分计划、动作与 observation

用户说：“查一下 A1001 的订单，如果物流异常就帮我创建工单。”请分别写出一个合理的计划、第一轮动作和第一轮可能得到的 observation。

答案：计划可以是“查询订单归属与状态，查询物流，判断是否满足创建工单条件，若需要写操作则请求确认”。第一轮动作可以是 `query_order(order_id="A1001")`。可能的 observation 是“订单 A1001 存在、属于当前用户、订单状态为已发货”，而不是模型自己猜测的物流结论。

### 练习 2：判断控制权

下面各项应主要由模型、程序还是人工决定？

1. 用户的自然语言问题更像物流还是退款。
2. 当前用户是否能查看订单 A1001。
3. 是否愿意接受一次超过平常成本的复杂报告任务。
4. 当前已知事实下应先查物流还是先查政策。

答案：1 主要由模型或分类规则处理；2 必须由程序和权限系统决定；3 通常由人工或预设业务策略决定；4 可由模型在受控工具范围内选择。实际系统可以组合使用，但不能把权限或高风险授权交给模型单独决定。

### 练习 3：为循环设计停止规则

某 Agent 连续三次调用同一个物流接口，均返回“服务暂不可用”。请给出比“继续试到成功”为更好的处理策略。

答案：将错误分类为暂时性工具故障，记录调用签名和失败次数；达到当前同步重试阈值后停止重复调用，转入 `WAITING_RETRY`，设置退避时间和总重试上限，或向用户说明暂时无法获取实时物流。若任务时限或重试预算耗尽，则以可解释失败结束或转人工。

### 练习 4：发现不可靠完成条件

以下哪一个更可靠，为什么？

1. 模型回答：“我已经创建了工单。”
2. 工具返回已验证的 `ticket_id`，系统成功持久化该结果，随后模型基于这个事实生成答复。

答案：第 2 个更可靠。它有来自真实业务系统的可验证结果，并且系统先将任务事实持久化，再生成自然语言说明。第 1 个只是模型文本，不能证明外部副作用真实发生。

## 自测题

### 自测 1：Agent Loop 中模型和系统各自最核心的职责是什么？

答案：模型基于目标和已验证 observation，提出计划、下一步动作或答复草稿；系统定义动作空间、构造受控上下文、校验动作、执行工具、记录可信结果、维护状态机、权限与预算。模型负责建议，系统负责控制和事实落地。

### 自测 2：为什么 observation 需要规范化？

答案：外部工具原始结果可能包含敏感字段、无关噪声、错误结构和过期信息。规范化能保留下一步决策需要的最小可信事实，附带来源和时间，并降低泄露、上下文膨胀和错误推理风险。

### 自测 3：Plan-and-Execute 是否意味着计划不能变？

答案：不是。计划是当前条件下的路线假设。工具失败、用户补充信息、权限拒绝、预算变化等新 observation 都可能要求重规划、跳过、降级或结束。

### 自测 4：最大步数为什么不够作为唯一停止条件？

答案：它只能最终防止无限循环，无法区分任务是否已完成、是否在等待人工、是否应因权限拒绝立即结束、是否已超成本或重复同一失败动作。停止条件应组合目标、状态、时间、成本、风险和无进展检测。

### 自测 5：在什么情况下应把任务转入等待态而不是继续调用模型？

答案：缺少用户必要输入、需要人工确认、等待异步工具回调、等待规定的重试时间等情况。此时继续调用模型无法产生新的可信事实，反而会造成猜测、重复和成本浪费。

## 本节小结

Agent Loop 是高级 Agent 的执行内核：模型依据受控上下文提出一个结构化下一步，系统完成校验、执行和 observation 规范化，再判断是否继续。它既保留了模型处理语义不确定性的能力，也把权限、状态、预算、工具执行和完成事实留在系统控制之中。
