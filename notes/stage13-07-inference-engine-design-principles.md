# M13 第 8 节：主流推理引擎的设计思想

## 本节定位

上一节解释了模型如何以 HTTP API 的形式对外提供服务。本节继续向下看一层：当大量请求真正到达运行模型的服务时，**推理引擎怎样组织计算、显存和请求，才能既不浪费 GPU，又尽量让用户尽快得到结果。**

这不是某个工具的安装教程，也不是产品排行榜。你需要先理解所有推理引擎共同面对的资源与调度问题，再理解 vLLM、SGLang、Text Generation Inference（TGI）、TensorRT-LLM、llama.cpp 等代表性方向为什么会做出不同设计。这样以后看到新的引擎时，你不会只能记住名字，而能判断它在优化什么、适合什么、又牺牲了什么。

本节仍是纯知识学习，不要求安装任何引擎，也不要求更改项目代码。

## 本节学习目标

学完后，你应当能够：

1. 说明为什么“用 Python 调一下 `generate()`”与生产推理服务之间有巨大差别。
2. 解释推理引擎要解决的四类核心问题：计算、显存、调度和协议/运维。
3. 理解静态批处理、连续批处理、chunked prefill、请求调度的基本思想。
4. 解释 PagedAttention / 分块 KV Cache 试图解决的显存碎片与利用率问题。
5. 理解前缀缓存、Radix/前缀树复用、推测解码、结构化解码等常见优化的适用边界。
6. 区分单机本地推理、单节点 GPU 服务、多 GPU 服务和大规模在线服务的需求。
7. 能从工作负载、硬件、模型格式、并发、延迟目标、运维能力和兼容需求选择引擎类别。
8. 不把某个引擎的宣传吞吐数字直接当成自己系统的性能结论。

## 一句话先讲透

**推理引擎的本质是资源调度器加高性能执行器：它必须在每个生成步中安排谁占用多少显存、谁与谁一起算、何时复用已算过的上下文，并在吞吐、首字延迟、公平性、成本和复杂度之间取舍。**

## 基础知识铺垫

### 1. 为什么普通模型代码不足以承担线上服务

离线脚本常见的使用方式是：

```text
加载模型
-> 读一批输入
-> 对这一批输入生成完整输出
-> 程序结束
```

这在实验、Notebook、离线数据处理里很合理。但线上服务面对的情形不同：

- 请求会在任意时刻到达，而不是一次性给齐；
- 每个请求的输入长度、输出长度、参数、截止时间都不同；
- 有些用户只问一句话，有些用户带很长的 RAG 上下文；
- 有些请求很快结束，有些请求会持续生成很长内容；
- 用户可能中途取消；
- GPU 显存既要放模型权重，也要放每个请求独立增长的 KV Cache；
- 服务必须面对限流、排队、异常、监控、滚动升级和多租户问题。

如果用最朴素的“一批请求一起开始、一起结束”的方式运行，短请求会被长请求拖住，已结束的请求占用的位置无法立即复用，新请求还要等整批结束。这会造成 GPU 空闲、用户等待长、显存利用差。推理引擎存在的意义，正是把这类动态、不均匀的工作负载处理好。

### 2. 先回忆一次自回归生成

对于大多数 decoder-only 大语言模型，生成过程可粗略理解为：

```text
输入 Token -> prefill -> 得到首个候选 Token
                 |
                 v
      已有上下文 + 新 Token -> decode -> 下一个 Token
                                      |
                                      v
                                  重复直到结束
```

这里有两个重要阶段：

- **Prefill（预填充）**：模型一次处理已有提示词/历史消息，建立 KV Cache。输入越长，这部分越重。
- **Decode（逐 Token 解码）**：模型每次只生成少量新 Token，并复用前面缓存。输出越长，循环次数越多。

它们的资源特性不同：prefill 更容易形成大块计算，常偏计算密集；decode 每一步计算较小但频繁访问 KV Cache，常更受显存带宽、调度和批处理组织影响。优秀引擎不会假装两者是同一种负载。

### 3. GPU 不是“模型跑起来就会自动用满”

GPU 有大量并行计算单元。单个短请求在 decode 阶段每次只生成一个 Token，可能无法充分利用这些单元。把多个请求合并到一个批次中，往往能提高硬件利用率。

但是批次越大也不一定越好：

- 模型权重和 KV Cache 受显存上限约束；
- 更大批次可能增加排队和首字延迟；
- 长输入请求可能霸占很多预填充预算；
- 不同长度请求一起算会有无效填充或调度复杂度；
- 太多并发会让延迟尾部恶化，甚至 OOM。

所以“GPU 利用率 100%”不是唯一目标。用户更关心响应是否及时，平台更关心成本、稳定性和可预测性。引擎必须做多目标权衡。

### 4. 批处理不等于把请求简单拼在一起

设有三个请求：

```text
A：输入 100 Token，输出 20 Token
B：输入 2,000 Token，输出 400 Token
C：输入 300 Token，输出 30 Token
```

若静态地把 A、B、C 组成一个 batch，并等待全部完成，那么 A、C 即使早已生成结束，也可能要等 B 的 400 Token 结束才释放位置。新到达的 D 也要排队等待。这就是**队首阻塞（head-of-line blocking）**的一种表现。

因此，推理引擎的批处理通常还需要回答：

- 什么时候让请求加入 batch？
- 请求完成后能否马上离开？
- 新请求能否在旧请求仍生成时加入？
- 长输入是否要一次处理完？
- 是否优先首字延迟、总吞吐、短请求或公平性？
- 取消请求后如何回收 KV Cache？

### 5. KV Cache 是高性能推理的中心资源

第 2 节中已经介绍 KV Cache。本节更强调它在多请求服务中的系统含义。

每个活跃请求都有自己的上下文状态，随着输入和输出增长而占用更多 Cache。若有 N 个并发请求，每个请求长度不同，显存中就会出现大量大小不同、生命周期不同的 KV Cache 区域。

朴素分配器可能产生：

- **内部碎片**：已分配大块中有未使用空间；
- **外部碎片**：总空闲空间不少，却没有连续大块满足新请求；
- **预留浪费**：为了可能生成的最大长度，过早给每个请求预留大量空间；
- **回收不及时**：完成或取消的请求不能及时归还空间。

这解释了一个常见现象：显存看起来还有余量，新请求却被拒绝或性能显著下降。总量不是唯一问题，空间组织方式和调度策略同样重要。

### 6. 性能指标必须分开看

评价推理引擎时，至少区分：

- **TTFT（Time To First Token）**：从提交到流式第一个有效 Token 的时间；
- **TPOT / ITL（Time Per Output Token / Inter-Token Latency）**：后续 Token 间隔；
- **E2E latency**：从请求发出到完整结束的时间；
- **吞吐（tokens/s 或 requests/s）**：单位时间完成的输出量或请求量；
- **并发容量**：在给定 SLO 和资源下可同时处理多少请求；
- **P50/P95/P99**：中位数和尾部延迟；
- **显存利用率/碎片率**：资源是否被有效使用；
- **成功率/拒绝率/取消率**：系统是否稳定。

某引擎在大 batch 下吞吐极高，不代表它适合要求极低 TTFT 的交互客服；某引擎单用户本地体验很好，也不代表它能在几十个并发用户下稳定服务。必须让评测负载匹配你的真实请求分布。

## 本节主题系统讲解

### 1. 推理引擎共同解决的四类问题

不论具体产品如何变化，绝大多数推理引擎都在处理以下四类问题。

#### 1.1 计算执行：怎样让硬件真正高效地算

这包括：

- 调用高性能矩阵乘法和 Attention 内核；
- 针对 GPU、CPU、Apple Silicon、NPU 或特定驱动选择后端；
- 利用半精度、量化和融合算子减少计算或内存访问；
- 支持多 GPU 的张量并行、流水线并行或其他分布方式；
- 在不同模型架构、位置编码、MoE、视觉模块上实现正确执行。

这一层追求的不只是“结果算出来”，还包括在目标硬件上以可接受的速度、显存和稳定性算出来。模型支持与硬件支持常常是组合关系：同一引擎可能支持某模型，但特定量化格式、特定 GPU、特定 Attention 后端或多 GPU 拓扑并不一定都支持。

#### 1.2 内存管理：怎样容纳尽可能多的有效上下文

模型权重通常长期驻留；KV Cache 则随请求进入、增长、完成和取消而变化。引擎需要决定：

- Cache 是否按固定大块、可变大小或分页块分配；
- 空闲块怎样复用；
- 是否能共享相同前缀的 Cache；
- 是否把一部分 Cache 放在 CPU 内存或更慢的介质；
- 是否量化 KV Cache；
- 显存接近上限时，拒绝、排队、换出还是缩短上下文。

内存管理看似底层，但会直接决定最大并发、长上下文稳定性和尾延迟。

#### 1.3 请求调度：谁先算、谁一起算、何时让位

调度器通常维护等待队列和活动请求集合。它要处理：

- 新请求到达；
- 活跃请求每步继续 decode；
- 某个请求结束；
- 某个请求取消；
- 长 prompt 的 prefill；
- 优先级、租户配额、截止时间和公平性；
- 可用 Token/显存预算。

调度器的策略决定了系统行为。例如严格优先短请求可能降低平均延迟，却让长任务长期饥饿；完全按到达顺序公平，但可能牺牲总体吞吐；优先给新用户首字可能改善体验，却降低已有生成的输出速度。

#### 1.4 服务化与治理：怎样可靠地对外提供能力

即使底层计算很快，线上系统还需要：

- HTTP/gRPC/API 适配；
- 流式协议；
- 健康检查、就绪检查、优雅停止；
- 鉴权、限流、请求大小限制；
- 指标、日志、Trace、错误分类；
- 模型加载、热更新、版本隔离；
- 容器化、弹性扩缩、故障恢复。

有些工具偏“本地运行器”，有些偏“生产推理服务器”，有些偏“底层执行库”。比较时必须先看它的产品定位，不能拿一个桌面本地工具去要求完整平台治理，也不能只因某服务器有 OpenAI 兼容端点就忽略其运维成本。

### 2. 静态批处理、动态批处理与连续批处理

#### 2.1 静态批处理

静态批处理先收集一组请求，统一 prefill 和生成，等所有请求完成后再处理下一批：

```text
等待 A/B/C/D
-> 组成 batch 1
-> batch 1 全部完成
-> 才开始 batch 2
```

优点是实现简单、计算形状稳定，适合离线任务或长度相对均匀的输入。缺点是容易被最长请求拖慢，新请求不能及时加入，完成的槽位难以即时复用。

#### 2.2 动态批处理

动态批处理会在一个短时间窗口内聚合新请求，并根据长度、参数或资源约束决定如何组 batch。它比静态批处理灵活，但很多实现仍然以“批次整体”为单位，完成后才释放。

#### 2.3 连续批处理（continuous batching）

连续批处理的关键思想是：**请求完成后立即释放其位置，新请求可在其他请求仍在生成时进入活动 batch。**

```text
时间 t1：A B C 同时生成
时间 t2：A 完成，D 进入，B C D 同时生成
时间 t3：C 完成，E 进入，B D E 同时生成
```

这能减少空槽、提高资源利用率，并常改善排队体验。许多现代推理服务器都将它作为重要机制。vLLM 的官方文档列出连续批处理、chunked prefill 和前缀缓存等能力；Hugging Face TGI 也将连续批处理作为提升总吞吐的重要能力。 [vLLM 官方文档](https://docs.vllm.ai/en/stable/), [TGI 官方文档](https://huggingface.co/docs/text-generation-inference/index)

但连续批处理不是免费午餐。它要求更复杂的 KV Cache 分配、请求状态管理、Token 预算和调度逻辑；如果策略不当，短请求、长请求、低优先级请求之间仍会相互影响。

### 3. Chunked Prefill：把长输入也纳入公平调度

一个很长的 prompt 可能包含几万 Token。若调度器坚持“一个请求的 prefill 必须一次完成”，这个请求会在一段时间里占用大量计算资源，正在 decode 的交互请求就可能出现 Token 间隔变长。

**Chunked prefill（分块预填充）**的思想是把长 prompt 的 prefill 切成多个 Token 块，穿插到其他请求的 decode 步中：

```text
不是：长请求 prefill 全部完成 -> 再继续其他请求
而是：长请求 prefill 一部分 -> 其他请求 decode -> 再 prefill 一部分 -> ...
```

它试图平衡两种需求：

- 长上下文请求不能永远等不到服务；
- 已经开始输出的用户不应因一个长 prompt 突然“卡住”。

块多小、优先给 prefill 还是 decode、如何设置 Token 预算，都取决于工作负载。客服聊天与离线文档总结的最佳配置可能不同。

### 4. PagedAttention：为什么要把 KV Cache 分块管理

可以把传统 KV Cache 想成每个请求都需要一段连续书架。请求长度不可预测，很多书架会预留得很长；有的请求早结束，留下零散空位；新请求即使只需一点空间，也可能找不到合适的连续位置。

**PagedAttention** 借鉴操作系统虚拟内存的分页思想，把 KV Cache 切成固定大小的块（block/page），每个请求维护自己的逻辑块到物理块的映射：

```text
请求 A 逻辑块：A0 -> 物理块 7，A1 -> 物理块 19，A2 -> 物理块 3
请求 B 逻辑块：B0 -> 物理块 8，B1 -> 物理块 21
```

它不要求某一请求的所有 Cache 物理连续，从而能更灵活复用空闲块、减少因可变长度造成的浪费。vLLM 因 PagedAttention 而广为人知；其文档也将连续批处理、前缀缓存等作为服务优化能力。 [vLLM 官方文档](https://docs.vllm.ai/en/stable/)

需要准确理解：

- 它不是把 GPU 显存真的变成操作系统的虚拟内存；
- 它不是让显存无限大；
- 它不消除 KV Cache 的总容量约束；
- 它解决的是 Cache 的分配、复用和碎片问题，从而提高有限显存的有效使用率。

### 5. 前缀缓存：重复上下文不应重复算

在很多应用中，不同请求共享开头：

```text
系统提示词 + 安全规则 + 工具定义 + 用户问题 A
系统提示词 + 安全规则 + 工具定义 + 用户问题 B
系统提示词 + 安全规则 + 工具定义 + 用户问题 C
```

共同前缀若每次都重新 prefill，会消耗重复计算和重复 KV Cache。**前缀缓存（prefix caching）**尝试识别可复用前缀，复用已经计算的状态。

潜在收益来自：

- 固定 System Prompt；
- 很长且稳定的工具 Schema；
- 多轮会话共享的历史前缀；
- RAG 模板中的固定说明；
- 同一文档被多次问答。

但复用需要严格的“前缀相同”判定。模型名、Tokenizer、聊天模板、system 消息、工具定义、采样前的输入序列有任何变化，都可能使 Cache 不可安全复用。不能只因自然语言“看起来差不多”就复用。

缓存还带来治理问题：不同用户/租户之间是否允许复用同一 Cache？缓存键是否泄露输入特征？缓存是否会挤占正常请求的显存？这些都属于生产策略的一部分。

### 6. Radix Attention / 前缀树复用的思路

普通前缀缓存可以理解为“找完整相同的开头”。而基于前缀树（Radix tree）的设计，尝试把很多请求的 token 前缀组织成可共享的数据结构，让最长公共前缀对应的 KV Cache 得到复用。

例如：

```text
系统规则 + 工具定义 + 查询订单 A1001
系统规则 + 工具定义 + 查询订单 A1002
系统规则 + 工具定义 + 查询订单 A1003
```

前三段可以被表示为共享路径，只有订单号后的部分分叉。SGLang 文档将 RadixAttention、前缀缓存和多 GPU 并行列为其面向低延迟、高吞吐推理的设计能力。 [SGLang 官方文档](https://docs.sglang.io/)

你无需把名称当作必须背诵的术语。关键是明白其本质：**当请求前缀的重复率高时，缓存组织方式会显著影响计算与显存成本；当输入几乎完全不同，前缀复用的收益则可能很小。**

### 7. 推测解码：用便宜模型帮助昂贵模型少走几步

自回归生成的瓶颈之一是目标大模型每次只确认少量 Token。**推测解码（speculative decoding）**大致遵循：

```text
小/快的 draft 模型先猜一段 Token
-> 大/慢的 target 模型一次验证这些候选
-> 接受符合条件的前缀，必要时修正
-> 继续下一轮
```

如果 draft 模型猜得足够准，大模型一次前向计算能确认多个 Token，从而提高生成速度。它的难点和边界包括：

- draft 模型必须与目标模型输出分布有足够匹配；
- 采样策略和正确性保证需要谨慎设计；
- 小模型、额外权重和调度也会占资源；
- 短输出、低并发或 GPU 已饱和时，收益未必明显；
- 不同引擎、模型架构和量化组合的支持程度不同。

因此它是性能优化工具，不是“部署两个模型就必然翻倍加速”的开关。

### 8. 结构化解码：让生成过程受语法约束

你学过 Structured Output。实现它的一条路线是让模型自由生成，然后在结束后尝试解析 JSON；另一条更强的路线是**约束解码（constrained / structured decoding）**：在每一步生成时，只允许符合目标 JSON Schema、正则或语法状态机的下一个 Token。

例如目标需要：

```json
{"category":"refund","priority":"normal"}
```

当生成到对象键名位置时，约束器可排除大量不合法 Token；当生成枚举值时，只允许 `refund`、`logistics` 等允许值。这能减少格式错误，但也会带来：

- 额外的状态机/掩码计算；
- Schema 复杂时的实现和性能挑战；
- “JSON 合法”不代表业务语义正确；
- 模型仍可能在允许的字段里填错值。

SGLang 的公开资料中将结构化生成和用于更快结构化解码的状态机优化作为其关注方向之一。 [SGLang 论文](https://arxiv.org/abs/2312.07104)

### 9. 多 GPU 并行：模型太大或吞吐要求更高时怎么办

单卡放不下模型，或单卡吞吐不足时，推理引擎需要多 GPU 并行。常见概念包括：

#### 9.1 张量并行（Tensor Parallelism, TP）

把同一层的大矩阵计算切分到多个 GPU 上并行完成，再通过高速通信汇总。它常用于让单个大模型跨多张 GPU 运行。TGI 的文档将 Tensor Parallelism 描述为把大模型放入多 GPU 的技术。 [TGI Tensor Parallelism 文档](https://github.com/huggingface/text-generation-inference/blob/main/docs/source/conceptual/tensor_parallelism.md)

优点是各 GPU 同时参与每层计算；代价是每层都可能有通信，GPU 间互联速度会强烈影响表现。

#### 9.2 流水线并行（Pipeline Parallelism, PP）

把模型的不同层放到不同 GPU，数据像流水线一样依次经过。它能分摊模型层，但会有流水线气泡、阶段平衡和请求调度复杂度。

#### 9.3 数据并行 / 副本扩展

把完整模型复制到多个实例，每个实例处理不同请求。这适合横向扩展吞吐和可用性。它不能帮助单个模型跨卡装下，但对多用户在线服务很常见。

实际系统往往组合使用：单个副本内部用 TP/PP 装下模型，多个副本用负载均衡分流请求。具体可行性取决于模型、引擎、GPU 拓扑、网络和运维设计。

### 10. 代表性引擎方向：理解定位，不做盲目排名

下面用“设计侧重点”理解常见生态。它们会持续演进，某版本支持什么不能只看本节，需要以官方文档和实测为准。

#### 10.1 vLLM：面向高吞吐在线服务的调度与 Cache 管理

vLLM 常被用于 GPU 上的大模型在线服务。其设计讨论中最常见的关键词包括 PagedAttention、连续批处理、chunked prefill 和前缀缓存。它的核心启发是：在线 LLM 服务的瓶颈不只是矩阵计算，还包括 KV Cache 的管理和动态请求调度。官方文档列出连续批处理、chunked prefill、前缀缓存及多种并行与服务能力。 [vLLM 官方文档](https://docs.vllm.ai/en/stable/)

典型考虑：

- GPU 服务器上有较多并发生成请求；
- 希望以 OpenAI 风格 API 暴露服务；
- 需要高吞吐与较好的显存利用；
- 团队愿意承担模型、CUDA/驱动、容器、监控和服务调参责任。

不能由此推导：它一定是所有场景“最快”或“唯一正确”的方案。单机 CPU、本地低资源、特殊硬件、极小并发、模型格式或快速原型场景，可能有其他更合适的工具。

#### 10.2 SGLang：把结构化 LLM 程序与高效运行时结合

SGLang 的方向之一是服务结构化生成、Agent、多轮与共享前缀场景，常讨论 RadixAttention、前缀缓存、结构化输出、多 GPU 并行等。官方文档定位为低延迟、高吞吐的推理，并明确列出 RadixAttention 与前缀缓存。 [SGLang 官方文档](https://docs.sglang.io/)

它提供的学习启发是：很多 Agent/RAG/多轮工作流的请求并非独立随机文本，它们常共享很长的系统提示、工具定义、模板和历史前缀。若运行时能识别这些结构，缓存策略就可能成为重要收益点。

评估时仍需回到具体负载：你的请求是否真的有可共享前缀？是否需要它支持的模型与硬件？结构化输出的约束方式是否符合业务？操作复杂度是否能接受？

#### 10.3 TGI：面向 Hugging Face 模型生态的生产推理服务

Text Generation Inference（TGI）是 Hugging Face 提供的推理服务工具。其文档列出连续批处理和多 GPU Tensor Parallelism 等能力，强调为文本生成模型提供服务化部署。 [TGI 官方文档](https://huggingface.co/docs/text-generation-inference/index)

从工程角度，它代表“模型生态、容器化服务、部署流程和运行时优化结合”的路线。若团队的模型来源、权重管理、评测和部署深度使用 Hugging Face 生态，这类工具的整合体验可能是重要因素。

注意不要把“能服务 Transformers 模型”理解为所有架构、量化格式、适配器、硬件、流式/工具协议都无差别支持。生产选择依然需要版本级兼容性验证。

#### 10.4 TensorRT-LLM 等硬件深度优化路线

某些推理框架更深度利用特定硬件平台的图优化、量化内核、编译和运行时能力。它们的目标通常是把目标模型在特定硬件上压榨出更低延迟或更高吞吐。

这类路线的典型权衡是：

- 优势：在受支持硬件、模型和精度组合上可能具有很强性能；
- 成本：构建、编译、版本适配、调试和升级链路通常更复杂；
- 风险：硬件绑定更强，跨平台迁移弹性较弱；
- 适合：规模足够大、性能目标明确、硬件固定、团队有平台工程能力的场景。

它提醒我们：性能不是抽象属性，而是“模型 + 精度 + 引擎 + 驱动 + GPU + 负载”的组合结果。

#### 10.5 llama.cpp：轻量、本地、多硬件与量化优先的方向

llama.cpp 的目标是以较少依赖在广泛硬件上运行 LLM/VLM，适合本地实验、边缘设备、个人电脑和低资源环境。其官方项目说明中包含多种整数位宽量化，并提供可启动 OpenAI 兼容 API server 的能力。 [llama.cpp 官方 README](https://github.com/ggml-org/llama.cpp)

它给出的工程启发是：并非所有场景都需要多 GPU 高吞吐服务器。若你要在笔记本、CPU、Apple Silicon 或资源受限环境离线学习、开发、验证数据不出本机的流程，轻量运行时与量化模型可能更实际。

但“本地能跑”与“生产能扛并发”是不同问题。你仍需评估响应速度、模型质量、上下文容量、并发、可用性、安全和运维。

#### 10.6 上层易用工具与底层引擎的关系

有些工具重点是模型下载、运行、命令行体验和本地开发；有些重点是高性能服务器；有些是底层库或硬件优化组件。它们可以处于同一技术栈的不同层次，甚至相互组合。

因此不要只问“哪个取代哪个”。先问：

```text
我现在缺的是模型管理易用性？
还是单机本地可运行性？
还是高并发在线服务？
还是特定硬件的极致性能？
还是多模型治理和网关能力？
```

问题不同，选择自然不同。

### 11. 引擎选择的系统决策框架

可以按照以下顺序收集事实，而不是先追热门工具。

#### 11.1 明确工作负载

至少统计或估计：

- 输入 Token 分布：P50/P95/P99；
- 输出 Token 分布；
- 是否流式；
- 峰值和稳定并发；
- 请求到达是否突发；
- 是否有很长 System Prompt / 工具定义 / 多轮历史；
- 是否需要工具调用、JSON Schema、多模态；
- 是否允许异步任务；
- TTFT 和总时延目标。

没有这些数据，就无法合理设置 batch token 预算、并发数、Cache 容量，也无法公平比较引擎。

#### 11.2 明确模型和格式

确认：

- 模型架构和版本；
- 权重格式；
- 是否需要 LoRA/适配器；
- 目标精度和量化格式；
- 上下文窗口；
- Tokenizer/聊天模板；
- 许可证是否允许目标用途；
- 引擎当前版本是否明确支持该组合。

“模型名字相同”但权重版本、量化、Tokenizer 或模板不同，也可能导致输出、显存和兼容问题明显不同。

#### 11.3 明确硬件与基础设施

需要知道：

- GPU 型号、数量、显存和 GPU 间互联；
- CPU、RAM、磁盘与网络；
- 驱动、CUDA/运行时兼容范围；
- 是否容器化；
- 是否允许使用特定云/硬件；
- 是否已有监控、密钥、日志和发布能力。

不要从别人的 A100/H100 基准直接推导到自己单张消费级 GPU、虚拟机或 CPU 环境。

#### 11.4 明确运营责任

要回答：

- 谁负责模型更新、权重下载、磁盘和显存容量？
- 谁处理 OOM、驱动升级、漏洞、节点故障？
- 谁监控 TTFT、队列、错误率和成本？
- 是否需要租户隔离、审计、请求脱敏、密钥轮换？
- 能否接受模型重启时短暂不可用？

引擎性能只是总成本的一部分。较高性能却需要团队无法承受的运维复杂度，整体上可能不是最佳方案。

### 12. 为什么基准测试经常误导人

一个基准数字通常隐藏了很多条件：

- 哪个模型、哪个精度、哪个版本；
- 输入/输出长度是多少；
- 并发多少，是否预热；
- 是否统计 prefill、网络和排队；
- 流式还是非流式；
- 采用 TTFT、平均吞吐还是 P99；
- 使用何种 GPU、驱动、互联和功耗策略；
- 是否启用了特定缓存、量化、投机解码或编译优化；
- 是否测的是持续饱和吞吐而非突发负载。

正确态度是把公开 benchmark 当作“值得进一步验证的线索”，而不是采购或架构决策的证据。你应使用自己的模型、提示词长度、并发、流式要求和质量验收集做压测。

### 13. 一个简化但完整的在线调度示例

假设 GPU 上模型权重已加载，调度器总共允许 8,000 个活动 Token 预算。当前有：

```text
R1：已占 1,500 Token，正在 decode
R2：已占 2,000 Token，正在 decode
R3：输入 3,000 Token，等待 prefill
R4：输入 300 Token，等待 prefill
```

若引擎采用粗暴策略，可能先将 R3 整体 prefill，导致 R1/R2 的下一 Token 等很久。若采用更细粒度策略，可能：

1. 保留部分预算给 R1/R2 的 decode，避免其流式输出停顿；
2. 先快速处理 R4，使短请求尽快拿到首字；
3. 把 R3 的 3,000 Token 拆成多个 prefill chunk；
4. 在每轮调度中，回收已完成请求的 Cache 块；
5. 若用户取消 R2，立即释放其资源；
6. 若总预算不足，拒绝或延后新请求，而不是盲目 OOM。

没有任何一条策略绝对正确。若 R3 是高优先级批任务，或 R4 属于低优先级租户，决策可能完全不同。引擎提供机制，平台和业务策略决定怎样使用机制。

### 14. 从引擎到你的 AI 应用：边界仍然存在

即使推理引擎支持 OpenAI 兼容接口、流式、工具字段或结构化输出，它也不应替代你的应用层职责：

- Prompt Injection 防护；
- 文档权限过滤；
- 工具参数业务校验；
- 写操作确认和幂等；
- RAG 检索、引用校验与答案评估；
- 用户认证、业务授权与审计；
- 领域错误提示和人工接管。

引擎优化“如何高效地产生 Token”；应用负责“为什么可以产生、产生后能否被信任和采取行动”。不要因为底层服务强大，就把业务安全边界下放给模型或引擎。

## 常见误区

### 误区 1：推理引擎就是换一个调用 SDK

纠正：SDK 只在调用侧封装 HTTP；推理引擎在服务端处理模型加载、GPU 执行、KV Cache、批处理、并发调度和服务生命周期，属于完全不同的层。

### 误区 2：batch 越大，系统一定越快

纠正：大 batch 可能提高饱和吞吐，却增加排队、TTFT 和显存压力。对交互请求，应该同时看 P95 TTFT、Token 间隔和用户体验。

### 误区 3：PagedAttention 让显存不再是限制

纠正：它提高 KV Cache 管理效率、减少碎片和浪费，但总显存仍有限。模型权重、KV Cache、临时工作区和运行时开销仍会导致资源瓶颈。

### 误区 4：前缀缓存总是有巨大收益

纠正：收益取决于请求是否有长且完全一致的前缀、缓存命中率、缓存容量和调度策略。输入高度个性化时收益可能有限。

### 误区 5：推测解码一定更快

纠正：它依赖 draft 模型质量、目标模型、采样设置、硬件和负载。额外模型和验证也有成本，必须实测。

### 误区 6：本地能跑某模型，就说明适合生产部署

纠正：能跑只证明一个最小可行路径。生产还需要并发、SLO、故障恢复、版本管理、可观测性、数据安全、成本和权限治理。

### 误区 7：某引擎的公开吞吐最高，就应直接选它

纠正：公开基准的模型、硬件、长度、并发和指标可能与你完全不同。选择必须以自己的工作负载和运维约束为准。

## 本节练习

### 练习 1：解释连续批处理的收益

请求 A、B 同时开始生成；A 在第 20 个输出 Token 结束，B 还要生成 300 个 Token。此时新请求 C 到达。静态批处理和连续批处理会有什么差别？

答案：静态批处理可能让 C 等到 B 也结束后才进入下一批，A 的位置在这段时间无法充分利用；连续批处理可在 A 结束时释放其资源，让 C 加入仍包含 B 的活动 batch。这样通常降低 C 的等待并提高硬件利用率，但需要引擎有更复杂的请求状态和 KV Cache 管理能力。

### 练习 2：判断前缀缓存价值

一个客服系统每个请求都带 5,000 Token 的固定系统规则和工具定义，之后再附上不同用户问题。另一个系统每个请求的上下文完全来自不同的长文档。哪个更可能从前缀缓存获益？为什么？

答案：第一个系统更可能获益，因为大量请求共享完全相同的长前缀，已计算的 KV Cache 有复用机会。第二个系统的前缀差异很大，即使文本主题相近，也不能安全地按 Token Cache 复用。实际收益还取决于缓存命中率、模型/模板是否一致和缓存容量。

### 练习 3：选择指标

一个面向用户的聊天客服与一个凌晨运行的百万文档摘要任务，分别应优先看哪些指标？

答案：聊天客服应优先看 TTFT、P95/P99 延迟、Token 间隔、错误率和在峰值并发下的体验；离线摘要任务更关注总吞吐、单位 Token 成本、任务完成时间、稳定性和可恢复性。两者都要关注质量，但对低 TTFT 的敏感度不同。

### 练习 4：分析“剩余显存却拒绝请求”

为什么一个服务显示仍有可用显存，却可能拒绝一个长上下文新请求？请至少给出三个可能原因。

答案：可能原因包括：空闲显存不满足当前分配策略所需的块/连续空间；调度器为现有请求和峰值保留了安全预算；新请求预估所需 KV Cache 超过允许 token 预算；显存还有碎片；还需为临时工作区或 CUDA 图等保留余量；服务还受并发、租户配额或队列上限限制。不能仅以操作系统显示的显存总量判断。

### 练习 5：判断引擎选择信息是否充分

有人说：“我们有一张 GPU，应该用某引擎，因为网上说它最快。”请列出至少六项在决定前还必须知道的信息。

答案：至少需要模型及其量化格式、GPU 型号/显存、输入和输出 Token 分布、峰值并发、是否要求流式和目标 TTFT、是否需要工具/JSON Schema/多模态、目标操作系统和驱动、是否本地实验或生产服务、可承担的运维能力、许可证和数据边界。没有这些信息，无法做有意义的比较。

## 自测题

### 自测 1：推理引擎最核心的四类职责是什么？

答案：高效计算执行、显存/KV Cache 管理、动态请求调度、服务化与运行治理。不同产品对这些职责的覆盖深度不同，但线上推理系统都必须有人承担它们。

### 自测 2：为什么 prefill 和 decode 需要不同的调度考虑？

答案：prefill 要处理整段输入，长上下文时计算量大；decode 每步只产生少量 Token，但频繁、依赖 KV Cache，且直接影响流式 Token 间隔。若长 prefill 独占资源，会伤害正在 decode 的交互请求，因此许多引擎使用 chunked prefill 等策略协调二者。

### 自测 3：PagedAttention 的基本思想是什么？

答案：将 KV Cache 按固定块分配，并让请求通过逻辑到物理块的映射使用不必连续的显存块，以减少可变长度请求导致的浪费和碎片、提高可复用性。它不增加物理显存总量。

### 自测 4：为什么引擎不能替代业务层 Agent 安全控制？

答案：引擎只负责高效执行模型推理和提供通用协议，不理解用户是否有业务权限、工具调用是否有副作用、订单数据能否查看、人工确认是否完成等领域语义。权限、校验、幂等、确认和审计仍由业务/Agent 层负责。

### 自测 5：如何正确看待产品基准测试？

答案：把它当成了解设计方向和筛选候选方案的线索，而不是自己的性能结论。必须用自己的模型、精度、硬件、输入输出长度、并发、流式模式和质量标准进行受控测试，并同时观察 TTFT、吞吐、尾延迟、失败率和成本。

## 本节小结

本节的主线是：推理引擎不只是“把模型启动起来”，而是围绕动态在线请求组织计算、显存和调度。连续批处理解决完成请求的槽位复用，chunked prefill 协调长输入和持续输出，分页 KV Cache 减少内存浪费，前缀缓存和推测解码则在特定工作负载下减少重复计算或加快生成。

vLLM、SGLang、TGI、硬件深度优化框架、llama.cpp 等代表的是不同侧重点，而不是简单的胜负关系。正确选择从工作负载、模型与格式、硬件、SLO、功能兼容和团队运维能力出发，并以真实压测验证。

下一节：M13 第 9 节，模型服务部署架构。会把单个推理引擎放回生产环境，讨论负载均衡、模型副本、网关、队列、存储、观测、故障域和发布策略怎样共同构成可运行的模型服务。
