# M13 第 13 节：什么时候该微调

## 本节定位

“模型回答不好，要不要微调？”是 AI 应用开发中最常见、也最容易被误判的问题之一。很多团队把微调当作模型不稳定、格式不听话、知识不够、成本太高时的通用解法，结果投入数据、GPU、评测和上线成本后，发现根因其实在 Prompt、RAG、权限、工具链、评估方式或基础模型选择。

本节不进入训练命令和参数细节，而是建立微调之前必须具备的决策能力：知道微调能改变什么、不能改变什么；知道哪些信号说明值得做，哪些信号说明应该先修其他层；知道何时该选 Prompt、RAG、工具、换模型、蒸馏、工作流约束或人工流程。

本节是纯知识学习，不要求准备数据集、GPU 或调用任何训练服务。

## 本节学习目标

学完后，你应当能够：

1. 用准确语言解释微调（fine-tuning）改变的对象和目标。
2. 区分预训练、指令微调、领域继续训练、偏好优化、蒸馏与 RAG 的基本边界。
3. 判断“模型知识不新”“答案不可靠”“格式不稳定”“风格不一致”“成本太高”等问题是否适合微调。
4. 建立一个从问题证据到候选解法的决策流程。
5. 解释为什么微调不能替代权限控制、工具校验、事实检索和业务规则。
6. 理解微调项目的总成本不仅是训练费用，还包括数据、评测、部署、版本和持续维护。
7. 识别微调前需要准备的质量基线、数据来源、风险边界和成功标准。
8. 能为一个 AI 业务场景提出“先不微调”或“可以进入微调验证”的可解释结论。

## 一句话先讲透

**微调适合把大量稳定、高质量、可复用的示例行为沉淀到模型权重中；它不适合充当实时知识库、权限系统、业务校验器或没有评测证据时的万能补丁。**

## 基础知识铺垫

### 1. 模型权重中到底存着什么

大语言模型经过训练后，得到大量参数（weights）。这些参数不是一张可直接查询的事实表，也不是一段可以精确增删的源代码；它们以分布式、统计性的方式编码了语言模式、概念关联、任务行为和训练数据中学到的规律。

这带来两个重要事实：

1. 训练可以让模型**更倾向于某些行为模式**，例如按固定风格回答、完成某类抽取、遵循某种输出结构、识别某领域常见表达。
2. 训练不能像修改数据库一行记录那样，保证“只加入一个事实且不影响其他能力”。它可能产生泛化收益，也可能带来遗忘、偏差、过拟合或意外行为变化。

因此，微调本质上是“调整模型行为分布”的工程实验，而不是给模型安装一个精确的知识插件。

### 2. 什么是微调

微调（fine-tuning）通常指在已有基础模型或指令模型的基础上，用相对小得多、任务更聚焦的数据继续训练，使模型更适应目标任务、领域、风格或输出契约。

可以抽象为：

```text
通用基础/指令模型
       +
目标任务的高质量训练样本
       |
       v
目标领域或任务更适配的模型版本
```

微调不等于从零训练。预训练从海量数据中学习通用语言能力，需要巨量计算和数据；微调是在已有能力上做定向调整，资源需求通常小得多，但仍要严肃对待数据质量和评测。

### 3. 常被混淆的几种方法

#### 3.1 Prompt Engineering

通过 system prompt、示例、格式要求、任务拆分和上下文构造改变单次调用的行为。它不改权重，迭代快，适合规则和要求会频繁变化的情况。

#### 3.2 RAG

在推理时检索外部文档，把相关证据放进上下文。它不修改模型权重，适合可更新、可引用、需要权限过滤的知识。

#### 3.3 Tool Calling / 工作流

让模型提出意图，再由系统调用数据库、搜索、订单、计算或业务 API，并在服务端校验与执行。它把事实读取和副作用操作放在确定性系统中。

#### 3.4 换基础模型

若当前模型语言能力、上下文、工具支持、推理质量或安全能力本身不够，换更适合的基础模型可能比微调小模型更有效。

#### 3.5 微调

通过训练样本调整模型对某类输入输出的偏好和能力。适合稳定重复的行为模式，但需要数据、评测、版本和上线治理。

#### 3.6 蒸馏（distillation）

用更强模型、人工专家或可靠流程生成/标注高质量输出，训练较小模型模仿目标行为。常用于降低高频任务成本或延迟。它仍依赖高质量目标和严格评测，不是把大模型“复制”到小模型的无损操作。

理解这些边界，是选择正确解法的前提。

### 4. 微调的常见目标

微调可能服务于以下目标：

- 稳定的领域表达、术语、语气和格式；
- 高频、定义明确的分类、抽取、路由或改写任务；
- 对固定 JSON/结构化输出习惯的强化；
- 特定输入形式到特定输出形式的映射；
- 小模型承接原先由大模型完成的重复任务；
- 特定业务对话策略或决策辅助风格；
- 多语言、方言、行业文本等分布适配。

注意这些目标都强调“稳定、重复、可由样本定义”。如果需求每天变、知识每周更新、权限每次不同，权重训练往往不是首选。

### 5. 为什么必须先定义“好”

模型输出看起来不满意，不是一个可训练的需求。必须把它变成可观察、可评估的问题：

```text
当前模型在什么输入上失败？
失败是事实错误、格式错误、风格不一致、漏字段、分类错误还是成本过高？
失败频率是多少？
对哪些用户/任务影响最大？
什么输出可被认为成功？
哪种指标、人工规则或业务结果能证明改善？
```

若无法回答这些问题，微调数据集也无法被正确构造，训练后更无法判断有没有变好。先做 Bad Case 分类和评测基线，通常比先开始训练更有价值。

## 本节主题系统讲解

### 1. 微调能解决什么，不擅长解决什么

可以先建立一张方向表：

| 问题类型 | 微调可能性 | 通常优先考虑 |
| --- | --- | --- |
| 固定风格、术语、表达格式不一致 | 较适合 | Prompt/示例先验证，稳定高频时可微调 |
| 高频分类、抽取、标准化改写 | 较适合 | 规则/小模型/微调，配合评测 |
| 模型对近期政策/订单事实不了解 | 不适合单靠微调 | RAG、数据库查询、工具 |
| 用户是否有权限看订单 | 不适合 | 业务授权与服务端校验 |
| 工具参数越权或写操作风险 | 不适合单靠微调 | Schema、白名单、确认、幂等、审计 |
| 当前模型上下文太小/视觉能力不足 | 通常不适合 | 换模型、改架构、分段处理 |
| 输出偶尔不合法 JSON | 有时适合但不是首选 | 结构化输出、Schema 校验、重试/修复 |
| 长文档事实性不好 | 视根因而定 | RAG、切分、检索、Rerank、引用校验 |
| 高频任务成本过高 | 可能适合 | Prompt/Token 优化、缓存、路由、蒸馏、微调小模型 |
| 模型持续违反安全规则 | 不应只靠微调 | 多层安全策略、权限、过滤、人工流程 |

表格的关键不是给出绝对“能/不能”，而是防止跳过更直接、更可控的解决层。

### 2. 微调前的根因分析框架

当某个 AI 能力表现不好，可按以下顺序排查。

#### 2.1 问题是否可复现且可定义

如果失败只是偶发主观不满意，先收集足够案例。若它在明确输入条件下稳定发生，例如“发票字段抽取常漏税率”“客服语气经常不符合品牌规范”，才具备形成训练任务的基础。

#### 2.2 输入是否正确、完整、可访问

模型答错可能是没有拿到关键事实：RAG 没检索到、权限过滤后无文档、工具未调用、用户信息缺失、上下文被截断。训练模型去“猜答案”通常不如修输入链路。

#### 2.3 输出契约是否明确且可校验

若你只说“回复专业一点”，数据标注会高度主观。若定义为“必须包含问题概述、依据、下一步；不得承诺退款；语气简洁；输出 JSON 字段固定”，才更接近可评估目标。

#### 2.4 当前模型是否具备基础能力

如果基础模型本身无法理解目标语言、复杂逻辑、图片或长上下文，少量微调样本通常无法弥补能力鸿沟。先评估更合适模型、模型尺寸、上下文或多模态能力。

#### 2.5 是否有更便宜、更可控的工程解

检查 Prompt、few-shot、结构化输出、RAG、Rerank、工具、规则、缓存、模型路由、输出校验和人工流程。它们通常迭代更快、事实更可更新、风险更小。

#### 2.6 是否存在足够高质量、合法可用的数据

没有可靠样本时，微调会把噪声、错误承诺、隐私信息和历史偏差一起学进去。数据质量是微调效果的上限，而不是训练参数能补救的问题。

### 3. 一个决策树：先不要急着训练

可用如下思路判断：

```text
发现模型问题
  |
  +-- 是事实/实时信息/私有数据缺失吗？
  |      是 -> 先检查 RAG、数据库、工具、权限、引用
  |
  +-- 是输出格式或字段约束问题吗？
  |      是 -> 先检查 Structured Output、Schema、解析和验证
  |
  +-- 是业务操作安全问题吗？
  |      是 -> 先检查服务端授权、工具白名单、确认、幂等、审计
  |
  +-- 是基础能力不够吗？
  |      是 -> 先评估换模型、上下文、视觉/工具能力或任务拆分
  |
  +-- 是稳定重复的风格/分类/抽取/映射问题吗？
         是 -> 收集高质量数据和基线，进入微调可行性验证
```

这个决策树不排斥组合方案。实际系统常见组合是：微调模型负责稳定抽取或分类，RAG 提供可更新知识，工具查询实时业务数据，服务端保证权限和副作用安全。

### 4. 适合微调的典型场景

#### 4.1 稳定的领域风格与写作规范

例如客服回复需要统一遵守品牌语气、固定结构、禁止性表述和行业术语。若这些规则长期稳定、样本充足、Prompt 已无法以合理 Token 成本稳定达到效果，微调可能让模型更自然地内化常见写法。

但仍需要输出校验。例如“不得承诺退款”这种高风险规则不能只依赖模型习惯，必须有业务流程和人工/规则兜底。

#### 4.2 高频分类与信息抽取

例如将工单归类到有限类别、从固定格式文本中抽取字段、识别意图或标准化商品描述。这些任务标签明确、样本容易积累、评测指标可定义，常是微调或蒸馏小模型的较好候选。

前提是先与规则、Prompt 和结构化输出基线比较。若 95% 情况用规则即可稳定处理，未必需要训练模型；若长尾语义复杂，微调才可能带来增量价值。

#### 4.3 固定输入到固定输出的转换

例如将客服原始记录改写为内部摘要模板、将自然语言需求转换为受控字段、把行业术语转换为标准编码说明。训练样本可明确表示输入和理想输出，且任务分布相对稳定。

#### 4.4 高频任务的模型蒸馏/成本优化

若大模型在大量重复任务上表现可靠，但成本或延迟过高，可用其输出加人工/规则审核形成训练样本，再训练/微调小模型承担低风险高频请求。复杂或低置信请求仍升级到大模型或人工。

这是一种工程分层，而不是“训练后小模型一定替代大模型”。关键要验证小模型在真实长尾和安全边界上的表现。

#### 4.5 特定语言或领域文本分布适配

通用模型可能不熟悉某行业缩写、文风、术语组合或文本格式。若这些模式稳定且有合法样本，微调可改善理解与生成的一致性。对不断更新的具体事实，仍应使用 RAG/工具。

### 5. 不适合直接微调的典型场景

#### 5.1 动态、频繁变化的事实知识

退款政策、库存、价格、订单状态、法规版本、当天新闻等会不断变化。把它们训练进权重会导致数据过期、更新成本高、无法精确删除和难以引用。

更合适：权威知识库 + RAG、数据库查询或服务端工具。微调可以学习“如何根据引用回答”，但不应承担“记住当前政策正文”。

#### 5.2 权限、合规和副作用

“是否能查看这个订单”“是否能退款”“是否可以创建工单”必须由确定性系统和审计流程决定。即使训练数据中模型从不越权，也不能把安全保证建立在概率行为上。

更合适：认证、授权、数据过滤、工具 Schema、确认、幂等、审计和人工审批。

#### 5.3 数据或检索链路错误

若模型因为拿到过期文档、错误 chunk、缺少元数据过滤或检索候选不足而答错，微调可能让它更自信地胡说，而不会修复证据缺失。

更合适：检查文档质量、切分、Embedding、检索、Rerank、权限过滤、引用和答案校验。

#### 5.4 输出必须 100% 严格合法

微调可提高格式倾向，但不能保证所有边界输入都合法。对接口参数、金额、状态机动作等必须由 JSON Schema、Pydantic/DTO 校验、服务端业务规则和失败处理保证。

#### 5.5 需求本身没有稳定定义

若团队每周都改变标签、风格、流程和政策，训练集会迅速过期。此时可配置 Prompt、规则、RAG 和工作流通常迭代更快。

### 6. Prompt、RAG、工具、微调的组合关系

不要把它们看作互斥选项。一个成熟系统可能：

```text
微调模型：稳定完成领域意图分类和摘要风格
RAG：提供当前可引用的政策知识
工具：查询实时订单、库存、账户状态
Structured Output：约束意图和工具参数形状
业务服务：权限、确认、幂等、审计
Prompt：组织角色、规则、上下文和任务边界
```

每一层负责它最擅长的部分。微调可降低 Prompt 的重复说明成本、提高特定行为一致性，但不能取消其他层的必要性。

### 7. 微调项目的总成本模型

很多人只比较“训练一次多少钱”。真实成本还包括：

- 样本收集、脱敏、授权和清洗；
- 专家标注、审阅、争议处理；
- 数据版本、训练集/验证集/测试集划分；
- 训练算力、存储、实验记录和失败尝试；
- 模型评测、红队、安全和质量回归；
- 部署、GPU 容量、推理成本和监控；
- 模型/适配器版本管理、灰度和回滚；
- 需求变化后的再训练；
- 线上 Bad Case 收集与持续维护；
- 法律、隐私、许可证和合规风险。

只有当长期、高频、稳定任务带来的质量、成本、延迟或控制收益超过这些成本时，微调才具有业务合理性。

### 8. 微调前必须有的证据

进入微调可行性验证前，至少应具备：

1. **明确任务定义**：输入、输出、禁止项、成功条件和边界。
2. **基线**：当前 Prompt/RAG/模型在代表性测试集上的质量、延迟、成本。
3. **Bad Case 分类**：知道最主要失败类型及其频率，而不是凭少数印象。
4. **高质量样本来源**：人工专家、已验证业务记录、规则审核输出或可靠教师模型加审阅。
5. **数据合法性**：隐私、版权、合同、用户授权、保留和删除要求清楚。
6. **独立评测集**：不能与训练样本混用，覆盖典型、长尾、对抗和安全场景。
7. **上线与回滚计划**：模型如何版本化、灰度、监控和撤回。

缺少其中几项不一定完全不能试验，但应把工作定位为研究/PoC，而不是直接承诺生产收益。

### 9. “数据越多越好”是错误问题

训练数据的数量重要，但质量、覆盖、分布、去重和标签一致性更重要。几个典型问题：

- 100 万条重复模板可能不如 1 万条覆盖真实长尾的高质量样本；
- 历史客服记录可能包含错误承诺、过时政策和不合规表达；
- 自动生成数据可能有系统性幻觉或风格单一；
- 训练集和测试集泄漏会让离线分数虚高；
- 只覆盖容易案例会让模型在真实难例上退化；
- 大量敏感数据会增加隐私、删除和审计负担。

在开始训练前，先抽样阅读数据，建立标签规范，统计类别/长度/时间/来源分布，通常是收益最高的工作之一。

### 10. 成功标准：必须与基线对比

微调不应以“模型看起来更像业务专家”作为唯一结论。可定义多维成功标准：

| 维度 | 示例 |
| --- | --- |
| 任务质量 | 分类准确/F1、字段抽取准确、人工偏好胜率、关键案例通过率 |
| 契约 | JSON 合法率、Schema 通过率、工具参数验证通过率 |
| 事实性 | 有引用场景的依据一致率、无证据拒答率 |
| 安全 | 越权/注入/危险请求拦截、敏感信息泄露率 |
| 性能 | TTFT、E2E、吞吐、显存占用 |
| 成本 | 每成功任务 Token/GPU/API 成本、人工复核成本 |
| 稳定性 | 长尾任务、不同语言、不同版本下的退化率 |

要有明确门槛和比较对象，例如“在独立测试集上，关键字段 F1 提升至少 X，安全集不低于基线，P95 延迟不超过基线 Y%，单位成功任务成本下降”。具体数值由业务决定，不存在通用万能阈值。

### 11. 试验顺序：从低成本、可逆方案开始

一个务实的优化顺序通常是：

```text
1. 明确任务与错误分类
2. 修输入/权限/工具/RAG 等确定性链路
3. 改善 Prompt、样例、输出 Schema、验证与重试
4. 比较更适合的基础模型或路由
5. 优化 Token、缓存、工作流和成本
6. 若稳定任务仍有明确差距，再做小规模微调试验
7. 用独立评测、灰度和监控验证，再决定扩大
```

这个顺序不是说微调永远最后，而是因为前几步往往更快、更便宜、更可解释、更容易回滚。若你已经有成熟训练数据和非常明确任务，微调当然可以更早进入验证。

### 12. 微调带来的新风险

微调不是单向提升，常见风险包括：

- **过拟合**：模型记住训练样例形式，面对新表达变差；
- **灾难性遗忘/能力退化**：过度偏向某任务，通用能力或其他任务下降；
- **数据偏差放大**：训练数据中的歧视、错误、过时政策被放大；
- **隐私泄露**：模型可能记忆敏感训练片段，或训练数据本身不合规；
- **评估幻觉**：训练/测试泄漏导致分数好看，线上无提升；
- **格式假象**：JSON 合法率提升，但字段语义仍错；
- **运营复杂度**：每个模型版本都需要部署、路由、容量、监控和回滚；
- **许可证问题**：基础模型、数据和输出的许可不一定允许目标训练/商用方式。

这些风险不是为了让你害怕微调，而是要求把微调当作软件/模型发布工程，而不是一次单纯的实验。

### 13. 一个客服场景的决策示例

场景 A：模型经常不知道“当前订单 A1001 是否已签收”。

结论：不应先微调。订单状态是实时业务事实，应通过受权限控制的订单工具查询。微调最多可以改善模型如何解释查询结果，不能代替实时数据源。

场景 B：模型总是把工单分类为错误类别，但类别固定、历史上有数万条人工确认的工单，标签定义稳定。

结论：值得进入微调/蒸馏可行性评估。先建立规则/Prompt/基础模型基线，再清洗样本、构建独立测试集，比较小模型或微调模型是否在准确率、成本和延迟上有收益。

场景 C：模型偶尔生成非法 JSON 工具参数。

结论：先采用结构化输出、JSON Schema、服务端校验和修复/拒绝机制。若在这些基础上仍存在稳定的领域格式问题，且任务高频，可将微调作为辅助增强；但不能把安全依赖于微调。

场景 D：客服回复总是太长，不符合品牌语气，Prompt 已很长且效果不稳定。

结论：可能适合微调。需要收集经审核的短回复样本，定义禁止项和评估规则，并验证微调能否减少 Prompt Token、提升一致性且不损害事实性/安全。

### 14. 微调决策记录应包含什么

一次严肃的微调决策建议记录：

- 业务问题、受影响范围、风险等级；
- 当前基线和失败样本分类；
- 已尝试且不够的 Prompt/RAG/工具/换模型方案；
- 为什么认为目标行为稳定、可学习；
- 数据来源、许可、隐私处理、时间范围和负责人；
- 候选训练方法与资源估算；
- 独立评测集、成功标准、安全门槛；
- 上线、灰度、监控、回滚和再训练计划；
- 结论：不做、PoC、有限上线或扩大使用。

这份记录不是形式主义。它迫使团队把“我觉得微调会更好”转化为可检验假设，并为以后结果复盘留下依据。

## 常见误区

### 误区 1：模型不知道某个事实，就把事实微调进去

纠正：动态事实、订单、政策、价格和库存更适合 RAG、数据库或工具。权重更新慢、难精确删除、难引用，也无法保证实时性。

### 误区 2：微调后就不需要 Prompt 和 RAG

纠正：微调可提升稳定行为，但 Prompt 仍负责当前任务边界，RAG 仍负责可更新证据。它们是互补关系。

### 误区 3：有很多历史数据就可以直接拿去训练

纠正：历史数据可能包含错误、过时政策、隐私、偏见、重复模板和不一致标签。必须进行合法性、质量、去重、时间和分布审查。

### 误区 4：微调能保证工具调用安全

纠正：训练可以让模型更倾向正确格式，但权限、参数边界、确认、幂等和审计必须由服务端确定性控制。

### 误区 5：离线分数提升就说明可以上线

纠正：还要检查独立数据、长尾/对抗场景、安全、延迟、成本、部署兼容和线上灰度指标。训练集泄漏或评测偏差会造成虚假提升。

### 误区 6：微调成本只是一次训练账单

纠正：数据、标注、清洗、评测、部署、GPU、版本、监控、再训练和合规都构成长期总成本。

### 误区 7：微调模型比基础模型一定更专业、更可靠

纠正：质量取决于基础模型、数据、方法、评测和任务分布。低质量或狭窄数据可能让模型更差或只在训练样式上表现好。

## 本节练习

### 练习 1：为问题选择优先方案

分别为以下问题选择最应优先检查的方案，并说明理由：

1. 用户问今天订单是否送达。
2. 模型经常漏掉合同抽取中的“生效日期”字段。
3. 新版本退款政策上线后，模型仍回答旧规则。
4. 高风险写操作偶尔被模型错误触发。
5. 大模型完成大量简单意图分类，成本很高。

答案：1. 订单查询工具和权限校验，因为是实时事实；2. 先检查 Schema、Prompt、样例与解析，再评估固定抽取任务的微调；3. RAG/权威知识库和版本管理，因为政策会更新；4. 服务端工具白名单、确认、权限、幂等和审计，因为安全不能靠概率模型；5. 先评估规则、轻量模型、缓存和路由，若任务稳定且有可靠标签，可考虑蒸馏/微调小模型。

### 练习 2：判断是否值得微调

某系统有 50 条人工反馈，用户说“回答不够专业”。没有失败样本分类、没有独立评测集，也没有固定输出标准。现在是否应开始微调？下一步更合理的工作是什么？

答案：不应直接开始。50 条主观反馈不能定义训练目标，也无法判断训练是否有效。应先收集代表性输入输出和失败类型，明确“专业”的可观察标准，建立 Prompt/模型基线，检查是否缺少事实依据或业务上下文，再决定是否有稳定、可学习的行为和足够合法高质量数据。

### 练习 3：设计成功标准

一个团队计划微调模型用于“从售后描述中抽取问题类别、订单号和优先级”。请给出至少五项发布前成功标准。

答案：可包括独立测试集上的类别 F1、订单号字段准确率、优先级准确率、完整 JSON Schema 通过率、无订单号时正确返回空/不猜测的比例、注入/异常文本下的安全表现、P95 延迟、每千条任务成本、与基线模型相比的统计改进、人工复核率。具体阈值应按业务风险定义。

### 练习 4：解释“知识微调”的风险

为什么将完整退款政策微调进模型后，仍可能出现错误回答？

答案：政策可能过期或有多个版本；模型权重不是可精确查询的数据库，可能记错、混合规则或在边界条件下泛化错误；训练数据可能不完整；模型无法提供可靠来源或按用户权限过滤；更新与删除成本高。因此应以权威文档检索/工具为事实来源，微调若使用也更适合训练回答方式而非作为唯一知识库。

### 练习 5：比较微调与蒸馏

一个昂贵大模型在固定分类任务中表现很好，团队想降低成本。蒸馏/微调小模型的合理流程是什么？

答案：先定义任务、风险和基线；收集真实代表性输入，使用人工确认或可靠大模型加审阅得到高质量标签；划分独立测试集；训练/微调候选小模型；比较质量、安全、延迟和端到端成本；为低置信/长尾任务保留升级到大模型或人工的路径；灰度后继续收集 Bad Case。不能仅把大模型输出全部不加审核地当真值。

## 自测题

### 自测 1：微调和 RAG 最根本的差别是什么？

答案：微调通过训练调整模型权重中的行为倾向；RAG 在推理时从外部可更新数据源检索证据并放入上下文。微调适合稳定可复用行为，RAG 适合动态、可引用、可权限控制的知识；二者可组合。

### 自测 2：什么时候微调更有可能有价值？

答案：任务定义稳定、输入输出模式重复、高质量合法样本充足、基础模型已有基本能力、Prompt/RAG/工具等更简单方案已验证不足、存在独立评测和明确的质量/成本/延迟收益目标，并且团队能承担部署和持续维护时。

### 自测 3：为什么微调不能代替业务授权？

答案：模型输出是概率性的，训练无法保证每次都遵守权限；授权依赖实时用户、租户、资源和业务状态，必须由服务端确定性机制检查、记录和审计。

### 自测 4：什么是微调前的基线，为什么重要？

答案：基线是当前模型、Prompt、RAG、工作流在独立代表性评测集上的质量、性能、成本和安全表现。没有基线就无法知道微调是否真的提升，也无法评估它是否值得成本或是否造成其他维度退化。

### 自测 5：为什么高质量数据比盲目增加数据量更重要？

答案：训练会学习数据中的模式。错误、过时、重复、偏见、泄漏或标签不一致会直接限制甚至损害模型行为；大量低质量样本不能替代覆盖真实任务和长尾的高质量、合法、经过审阅的数据。

## 本节小结

本节的核心结论是：微调是调整稳定行为模式的工具，不是实时知识库、权限系统或万能修复器。面对模型问题，应先用事实和 Bad Case 分类确定根因，再依次检查输入/RAG/工具、结构化输出、基础模型能力、Prompt 和工作流等更直接的方案。

当任务稳定、高频、可定义、有高质量合法数据，并且存在可量化的质量、成本或延迟收益时，微调才值得进入可行性试验。微调项目必须有基线、独立评测、安全边界、版本和发布治理，才能从“训练一次”变成可靠的工程能力。
