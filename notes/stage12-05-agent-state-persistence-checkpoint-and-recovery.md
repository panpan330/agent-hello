# M12 第 5 节：Agent 状态持久化、Checkpoint 与断点恢复

## 本节定位

前两节已经建立了两个基础：Agent 任务有状态机，任务运行时有工作记忆。现在需要面对生产环境一定会发生的事实：进程会重启，机器会故障，网络会超时，模型调用会中断，worker 会被调度器替换，用户确认可能在几小时后才到达。

如果任务的关键状态只保存在 Python/Java 进程内存中，那么服务一重启，Agent 只会遇到两种糟糕结果：

```text
要么忘记进度，任务永远卡住或直接丢失；
要么从头再跑，重复调用工具、重复扣费，甚至重复执行写操作。
```

**状态持久化（state persistence）**与 **Checkpoint（检查点）** 的目标，是把一个运行中的 Agent 任务变成可暂停、可恢复、可迁移、可审计的工作单元。它不是把“模型的所有思考”存下来，而是在关键边界保存足以安全继续的结构化执行状态。

本节会说明检查点保存什么、何时保存、如何恢复、如何避免重复执行，以及它与幂等、版本、并发控制、外部副作用之间的关系。

## 本节学习目标

学完后，你应当能：

1. 解释内存状态、持久化状态、Checkpoint 和事件日志之间的区别。
2. 说明 Agent 任务为什么必须在等待、工具调用、状态转移等边界建立检查点。
3. 设计一个可恢复任务至少需要保存哪些内容。
4. 区分“恢复推理上下文”和“恢复外部副作用状态”。
5. 理解至少一次、至多一次、恰好一次语义在 Agent 工程中的现实含义。
6. 解释幂等键、工具调用 ID、任务版本、租约如何协同避免重复执行。
7. 判断任务重启后应继续、重试、查询确认、转人工还是终止。

## 一句话先讲透

> Checkpoint 的价值不是让 Agent 机械地从某一行代码继续，而是在每个可能中断的边界保存“已确认发生了什么、下一步允许做什么、哪些副作用结果仍未知”，使系统能在故障后以可证明的方式恢复，而不是猜测或盲目重做。

## 基础知识铺垫

### 1. 为什么进程内存不可靠

程序运行时，变量、对象、调用栈、线程状态通常存在内存中。它们读取快、使用方便，但生命周期依赖于当前进程。

下列情况都会让内存状态消失：

- 应用发布或热重启；
- 服务器重启；
- 容器被重建或 OOM 杀死；
- worker 进程异常退出；
- 自动扩缩容将任务迁移到其他实例；
- 人为终止调试进程；
- 进程出现未处理异常。

对一个同步、无副作用、几十毫秒完成的操作，内存丢失的影响可能有限；客户端重新请求即可。对一个多步骤 Agent 任务，内存丢失可能意味着：已查询的事实消失、待确认的动作不见、已发出的外部请求无法追踪、用户无法知道任务处于什么位置。

### 2. 什么是持久化状态

持久化（persistence）是把数据写入进程生命周期之外的可靠介质，使后续实例仍能读取。常见介质包括关系数据库、键值存储、对象存储、消息队列或专用工作流存储。

但“写到了数据库”不自动等于“可恢复”。可恢复需要保存的状态具备：

1. **完整性**：恢复时有足够信息判断下一步。
2. **一致性**：状态与已执行副作用之间不能明显矛盾。
3. **版本性**：能识别旧格式、并发更新和新旧 checkpoint。
4. **可定位性**：能找到任务、执行轮次、工具调用与对应结果。
5. **可审计性**：能理解任务为何停在这里。

### 3. Checkpoint 不是普通保存

Checkpoint（检查点）源自长时间计算和系统恢复领域。它指在某个明确边界，保存一个足以继续工作的一致快照。

对于 Agent，典型检查点不应该随意发生在“模型正在生成第 117 个 token”时，而应发生在**业务和执行边界**：

```text
任务创建后
计划/决策已被验证后
外部工具调用发起前
外部工具调用结果确认后
转入等待人工前
人工确认结果写入后
转为成功、失败、取消后
```

“边界”意味着恢复时系统能判断：在这个时刻之前哪些事已经确认，之后哪些事尚未开始或仍不确定。

### 4. 快照（Snapshot）与事件日志（Event Log）

两种常见思路：

| 方式 | 保存什么 | 优点 | 代价 |
| --- | --- | --- | --- |
| 快照 | 当前完整状态 | 恢复快、读取直观 | 需要处理更新覆盖与历史细节 |
| 事件日志 | 一系列发生过的事件 | 审计完整、可重放 | 重建状态较复杂，事件设计要求高 |
| 混合模式 | 当前快照 + 关键事件 | 兼顾恢复与审计 | 实现和一致性设计更复杂 |

一个任务快照可能是：

```text
task_id = task_123
status = WAITING_HUMAN
current_step = request_confirmation
verified_facts = [订单归属已验证, 物流 72 小时未更新]
pending_action = create_ticket
confirmation_id = confirm_abc
budget = {remaining_steps: 2}
version = 17
```

事件日志可能是：

```text
task_created
worker_claimed
order_queried
logistics_queried
confirmation_requested
```

很多实际系统采用混合方式：任务表保存当前快照，事件表保存状态转移和关键副作用记录。这样读当前任务很快，事后也能追溯“它为什么到这里”。

### 5. 任务恢复不是“从头再跑一次”

从头重跑看起来简单，但对 Agent 来说会引起多个问题：

- 会重新调用模型和工具，增加成本；
- 外部事实已经变化，结果不一致；
- 用户确认可能已失效或被重复使用；
- 写操作可能被重复执行；
- 原本失败的步骤被再次触发，形成循环；
- 审计记录无法说明到底哪次执行产生了真实副作用。

恢复的基本原则是：

> 只恢复尚未确认完成的部分；已确认完成的步骤不重复；状态未知的外部副作用先确认再决定是否重试。

这句话贯穿整节内容。

### 6. 失败、超时和结果未知不是同一种事

外部调用时，以下情形非常不同：

| 情形 | 系统知道什么 | 合理下一步 |
| --- | --- | --- |
| 明确成功 | 外部系统返回成功和资源 ID | 记录成功，不重试 |
| 明确失败 | 返回参数非法、权限拒绝等 | 分类处理，通常不盲目重试 |
| 调用超时 | 不知道对方是否已执行 | 查询确认、用幂等键重试或转人工 |
| 连接中断 | 请求可能根本未到，也可能已到 | 同样属于结果未知 |
| worker 崩溃 | 不知道崩溃前执行到哪一步 | 读取 checkpoint 与调用记录判断 |

最危险的是把“没有收到响应”直接当成“没有执行”。对于写操作，这会导致重复创建、重复付款、重复通知。

## 本节主题系统讲解

### 1. 一个可恢复 Agent 任务应保存什么

不同任务复杂度不同，但至少可以从六类信息思考。

#### 1.1 身份与作用域

```text
task_id
task_type
tenant_id
user_id / requester_id
conversation_id（如有）
trace_id
created_at / updated_at
```

恢复时必须知道任务属于谁、在哪个租户、使用什么权限上下文。不能因为 worker 换了实例，就丢失原任务的安全边界。

#### 1.2 生命周期与调度状态

```text
status
current_node / current_step
attempt_count
next_retry_at
deadline_at
lease_owner / lease_expires_at
cancel_requested_at
```

这些字段回答：任务是否能运行、现在停在什么边界、谁正在处理、何时允许重试、是否已取消或过期。

#### 1.3 输入与目标

```text
validated_input
task_goal
task_policy_version
requested_capabilities
```

要保存的是经校验后的输入和明确任务目标，而非只依赖原始 HTTP body 或聊天文本。恢复时还要知道当时适用的策略/版本，避免发布新版本后旧任务被无意用不同规则推进。

#### 1.4 工作记忆与可验证 observation

```text
plan_summary
completed_steps
verified_observations
pending_question
pending_confirmation
rejected_actions
remaining_budget
```

这里保存的是继续决策所需的结构化事实和摘要，不需要保存所有临时变量或全部模型输出。

#### 1.5 外部副作用与工具调用账本

```text
tool_call_id
tool_name
normalized_arguments
idempotency_key
request_started_at
request_status
external_request_id
result_reference
result_known / result_unknown
```

它决定故障恢复时能否判断某个工具是否已经调用、是否已成功、是否可以安全重试。

#### 1.6 审计和版本控制

```text
state_version
checkpoint_version
transition_events
actor / trigger
model_and_prompt_version（按需）
```

`state_version` 通常用于并发更新控制；`checkpoint_version` 用于数据结构升级；事件记录则帮助解释变化原因。

### 2. Checkpoint 应在哪些时机写入

Checkpoint 过少会丢失关键进度，过多会增加数据库写压力、复杂度和一致性窗口。可以优先选择以下高价值边界。

#### 2.1 任务创建时

在接收到经过验证的请求后，先创建 `PENDING` 任务再投入执行。不要先在内存跑一半，最后才决定保存。否则服务在最初阶段崩溃时，用户甚至得不到可查询的任务 ID。

#### 2.2 领取执行权时

任务从 `PENDING` 转为 `RUNNING` 时，记录 worker 租约或领取信息。这是避免多个执行器同时处理同一任务的基础。

#### 2.3 外部写操作之前

在调用可能有副作用的工具前，先持久化“准备执行什么”和幂等标识：

```text
tool_call_id = call_789
action = create_ticket
idempotency_key = task_123:create_ticket:1
status = EXECUTING_EXTERNAL_ACTION
```

为什么是“之前”？因为如果先发请求、进程在写记录前崩溃，恢复后系统不知道请求是否已发送。先记录意图不能消灭所有不确定性，却大幅缩小未知范围。

#### 2.4 外部调用结果确认后

外部系统明确返回成功、失败或可识别结果后，写入结果引用与新的任务状态。成功时还要保存外部资源 ID，便于后续查询和幂等处理。

#### 2.5 进入等待态时

例如 `WAITING_HUMAN`、`WAITING_INPUT`、`WAITING_TOOL`、`WAITING_RETRY`。这类状态可能持续很久，必须完整保存等待原因、恢复条件、截止时间和关联 ID。

#### 2.6 任务终止时

成功、失败、取消、过期都应作为终态 checkpoint。结果、失败码、最终摘要、最后状态转移都要可查询。

### 3. Checkpoint 的一致性问题：不能只看单张任务表

设想下面顺序：

```text
1. 任务状态更新为“工单已创建”
2. 调用创建工单 API
3. API 调用失败
```

此时任务状态与外部现实不一致。反过来：

```text
1. 调用创建工单 API 成功
2. 保存任务状态前进程崩溃
```

此时外部工单已存在，但任务记录不知道。

当一次业务动作跨越本地数据库和外部服务时，无法轻易获得一个包含双方的原子事务。这个问题常被称为分布式一致性问题。Agent 不是特殊例外，反而更常遇到，因为它会跨工具、跨服务运行。

工程上通常不追求抽象意义的“神奇绝对原子”，而是组合以下策略：

- 先记录调用意图；
- 对写操作使用幂等键；
- 保存外部请求 ID；
- 超时或崩溃后主动查询外部状态；
- 使用可补偿操作处理部分失败；
- 通过事件/Outbox 保证消息最终投递；
- 对无法自动判断的情况转人工。

### 4. 幂等性是恢复安全的核心搭档

回顾上一节：幂等意味着同一个逻辑操作重复请求，最终效果仍等价于只执行一次。

对 Agent 的写动作，推荐让幂等键体现“哪个任务的哪一次业务动作”：

```text
task_123:create_ticket:step_4
```

如果 worker 在发起创建工单后崩溃，新 worker 恢复时可用同一个幂等键：

- 若外部系统第一次已成功，重复请求返回原结果或说明已处理；
- 若第一次未到达，新的请求完成创建；
- 若外部系统仍无法判断，可用外部请求 ID 或查询接口确认。

关键点：幂等键要由系统生成和持久化，不能让模型每轮随机生成；也不能在重试时换一个新键，否则会失去幂等保护。

### 5. 递送语义：至少一次、至多一次与“恰好一次”的现实

在队列、任务执行和外部调用中，常见三种语义：

| 语义 | 含义 | 风险/代价 |
| --- | --- | --- |
| 至少一次（at-least-once） | 任务可能重复，但尽力不丢 | 需要幂等处理 |
| 至多一次（at-most-once） | 任务不重复，但可能丢失 | 可能漏执行重要任务 |
| 恰好一次（exactly-once） | 看似只执行一次 | 跨系统很难真正保证，常依赖幂等和事务组合 |

实际分布式系统中，端到端“绝对恰好一次”通常比口号复杂得多。网络超时会让调用方不确定对方是否执行；消息系统的确认与业务数据库写入也可能在不同时间发生。

因此更务实的目标往往是：

> 调度层允许至少一次投递；业务副作用通过幂等键、唯一约束和结果查询实现“可观察效果上的至多一次”。

比如任务 worker 可能重复领取，但“创建同一工单”的业务操作用同一幂等键保证不产生两张工单。

### 6. 任务恢复流程：从发现中断到安全继续

一个概念性的恢复流程可以是：

```text
1. 扫描可恢复任务：租约过期、等待时间到达、收到回调、人工批准。
2. 读取最新 checkpoint，并以版本/条件更新领取执行权。
3. 检查任务是否取消、过期、已终态或权限上下文失效。
4. 检查当前步骤是否存在结果未知的外部调用。
5. 若结果已知：写入结果，继续下一步。
6. 若结果未知：优先用外部请求 ID / 幂等键查询确认。
7. 只有确认可安全重试时，才重新发起调用。
8. 恢复工作记忆和预算，重新进入受控 Agent Loop。
```

这不是“读取任务然后继续 while 循环”那么简单。恢复过程本身就是一个需要策略、权限和审计的状态转移。

### 7. 结果未知（Unknown Outcome）应成为显式状态或显式字段

最容易被忽略的是调用超时后：

```text
本地没有收到成功响应
≠ 外部系统没有成功
```

对于只读工具，可以选择重试，因为重复查询通常安全；对于写工具，应该保留明确的未知状态：

```text
tool_call.status = UNKNOWN
task.status = WAITING_TOOL_RECONCILIATION
```

然后执行“对账/确认（reconciliation）”：

- 用 `external_request_id` 查询；
- 用 `idempotency_key` 查询；
- 按业务唯一条件查询可能创建的资源；
- 经过时间窗口后再有限重试；
- 无法确认则转人工。

比起错误地报告“失败”或盲目重复，这种设计能诚实地表示系统的知识边界。

### 8. Checkpoint 与任务状态机如何配合

状态机定义“允许怎样转移”；Checkpoint 负责让每次重要转移可恢复。可以将二者联系为：

```text
状态转移：RUNNING -> WAITING_HUMAN
Checkpoint：保存待确认动作、confirmation_id、事实依据、过期时间、版本

状态转移：WAITING_HUMAN -> RUNNING
Checkpoint：保存批准/拒绝事件、审批人、时间、确认对象，再重新领取执行权

状态转移：RUNNING -> SUCCEEDED
Checkpoint：保存最终结果、证据引用、外部资源 ID、完成时间
```

如果状态转移没有匹配的持久化信息，恢复后可能只知道“在等待人工”，却不知道等谁、等什么、何时过期；如果只保存杂乱信息没有明确状态，也无法由调度器决定下一步。

### 9. Checkpoint 的粒度：不要每一个 token 都保存

过度 checkpoint 会产生明显问题：

- 高写入频率和存储成本；
- 状态表竞争严重；
- 难以区分真正可恢复的边界；
- 审计噪声淹没关键信息；
- 任务恢复反而更复杂。

应优先在以下情况保存：

1. 状态机即将跨越生命周期边界；
2. 即将或刚刚发生外部副作用；
3. 即将进入可能持续较久的等待；
4. 完成了一步昂贵或不可重复的计算；
5. 需要切换 worker、服务或执行环境；
6. 需要让用户或运营查询进度。

模型生成过程中某个中间词通常不是恢复边界；模型调用完成后的结构化决策可能是。

### 10. 乐观锁：防止两个恢复者同时推进任务

恢复任务时，可能有两个 worker 几乎同时发现“租约过期的任务”。如果都恢复，就会产生重复动作。

乐观锁（optimistic locking）的思路是：任务记录有版本号 `version`。worker 读取时记住旧版本，更新时要求版本仍匹配：

```text
UPDATE task
SET status = RUNNING, version = version + 1
WHERE task_id = ? AND version = ? AND status = PENDING
```

若受影响行数为 0，说明别人已经更新过，当前 worker 不再继续。这种做法不需要长时间持数据库锁，适合竞争通常不高、外部执行时间较长的任务。

乐观锁不能替代幂等：它主要防止同一时刻本地状态被多方推进；如果 worker 在外部调用后崩溃，仍需用幂等键处理重复副作用。

### 11. 租约与心跳：`RUNNING` 的任务怎么判断“还活着”

假设 worker 领取任务后设置：

```text
lease_owner = worker_A
lease_expires_at = 10:05:00
```

运行期间 worker 定期续租，例如每 30 秒更新到更晚时间。若 worker 崩溃，它无法续租；到期后其他 worker 才有资格尝试恢复。

这比简单的 `status=RUNNING` 更可靠，因为状态本身不带“执行者是否仍活着”的信息。

但租约设计还要考虑：

- 单次工具可能超过租约时长，应提前续租；
- 时钟差异可采用数据库时间或容忍窗口；
- worker 网络隔离但仍在执行时，可能造成双执行风险，幂等仍必不可少；
- 高风险动作可要求更严格的领取和确认机制。

### 12. 任务版本与代码/策略版本

任务可能在版本 A 创建，在版本 B 部署后恢复。若新代码改变了状态字段、工具参数、策略或 prompt，直接恢复可能出错。

因此可在 checkpoint 中保存：

```text
schema_version
workflow_version
policy_version
tool_contract_version
prompt_template_version（按需）
```

恢复策略可以是：

- 兼容读取旧 checkpoint；
- 在恢复前迁移数据结构；
- 旧任务继续走旧工作流版本；
- 不兼容时停止自动恢复，转人工或重新创建任务；
- 对高风险任务要求显式版本迁移审查。

这解释了为什么任务持久化不是“把 Python dict 序列化”那么简单。长期运行系统必然要面对数据演进。

### 13. 任务输入、模型上下文和 checkpoint 的关系

将完整 prompt、全部原始消息和所有工具响应都作为 checkpoint 保存，可能带来成本、隐私和升级困难；但只保存一个最终答案，又无法恢复。

一种较稳妥的分层是：

| 内容 | 是否进入 checkpoint | 原因 |
| --- | --- | --- |
| 经过校验的任务输入 | 是 | 恢复目标的基础 |
| 当前状态与预算 | 是 | 决定能否继续 |
| 关键 observation 的结构化摘要/引用 | 是 | 恢复决策依据 |
| 工具调用账本与幂等键 | 是 | 防止重复副作用 |
| 原始大文档/大响应 | 通常保存引用 | 避免 checkpoint 过大 |
| 模型完整内部推理文本 | 通常不保存 | 不必要且可能有风险 |
| 当前最终给模型的全部拼接 prompt | 视审计需要 | 可保存版本与关键组成，而非盲目保存全部 |

恢复时应重新构造受控上下文，而不是机械重放旧 prompt。这样也能按当前权限、数据脱敏和上下文预算重新校验。

### 14. 异步工具与回调恢复

长时间工具通常以任务 ID 或回调形式返回。例如：

```text
Agent 任务 task_123
-> 提交文档分析外部任务 external_job_456
-> 保存关联关系并进入 WAITING_TOOL
-> 过 10 分钟，外部系统回调 external_job_456 已完成
-> 系统核对关联、验签/权限、保存结果
-> task_123 回到 RUNNING
```

恢复和回调需要注意：

- 回调必须验证来源，不能任何请求都改变任务状态；
- 回调可能重复、乱序或晚到；
- 任务可能已取消或过期，不能因晚到回调重新执行；
- 任务与外部 job 的绑定必须持久化；
- 回调结果要做 schema、大小、敏感信息校验。

在没有回调时，调度器可根据 `next_poll_at` 进行轮询，但轮询也要有间隔、预算和截止时间。

### 15. 人工确认恢复与一次性确认令牌

当任务处于 `WAITING_HUMAN`，恢复不是直接继续，而是等待明确事件。一个可审计确认通常关联：

```text
confirmation_id
task_id
pending_action_summary
requested_at / expires_at
required_role
approved_by / approved_at
decision = APPROVED or REJECTED
used_at
```

确认本身应具有：

- **绑定性**：只能批准指定任务和指定动作；
- **时效性**：过期后不可继续使用；
- **一次性**：防止批准被重放导致重复写操作；
- **权限性**：只有有权主体能批准；
- **可审计性**：记录完整决策证据。

恢复时先检查这些条件，再将任务从 `WAITING_HUMAN` 转为可运行。不能只根据用户消息里出现“同意”两个字就继续执行。

### 16. 取消与恢复的竞态

可能发生以下并发情形：

```text
10:00:00 worker 正在恢复 task_123
10:00:01 用户请求取消 task_123
10:00:02 worker 准备调用 create_ticket
```

若 worker 只在开始时检查一次取消状态，仍可能在取消后执行写操作。较稳妥的做法是：

1. 取消请求通过条件更新尽快写入状态/取消标记；
2. worker 在每个高风险动作前再次读取或校验版本/取消标记；
3. 工具调用携带任务/幂等标识；
4. 对已经在途的调用进行结果确认和必要补偿；
5. 审计记录谁在何时取消、工具处于何种阶段。

无法保证物理世界中的所有动作瞬间停止，但可以保证系统不把“取消”当作只是前端提示。

### 17. 从失败恢复还是从头重建：如何选择

并非所有任务都值得恢复。可按任务性质分类：

| 任务类型 | 更常见策略 | 原因 |
| --- | --- | --- |
| 只读、成本低查询 | 可从头再跑 | 幂等且结果容易重新获得 |
| 长耗时文档处理 | 从 checkpoint 恢复或复用中间产物 | 避免浪费大量时间与费用 |
| 有写副作用的业务动作 | 先确认结果，再决定恢复 | 必须防止重复 |
| 等待人工审批 | 持久化等待，收到事件后恢复 | 用户等待可能很长 |
| 依赖已不兼容旧版本的任务 | 转人工或显式迁移 | 盲目恢复风险高 |
| 已过业务时限任务 | 过期终止或创建新任务 | 旧结果可能不再有意义 |

恢复不是道德要求，而是风险、成本、时效和用户体验之间的选择。

### 18. Checkpoint 与 Outbox 模式的关系

有些任务状态变化后需要发布消息，例如“任务已完成，通知用户”“等待人工审批，发送待办”。若先更新数据库再发送消息，进程可能在发送前崩溃；若先发消息再更新数据库，又可能出现消息指向不存在状态。

Outbox 模式的核心是：在同一个本地数据库事务中，同时写入：

```text
任务状态更新
+ 待发布事件（outbox record）
```

之后由可靠发布器异步读取 outbox 并投递消息，成功后标记已发送。它不等于所有分布式问题都消失，但能降低“本地状态已变而事件丢失”或“事件已发而本地状态未写”的风险。

对 Agent 来说，Outbox 常用于：任务创建后投递执行消息、状态变更后通知 UI、等待人工时创建待办、完成后发送通知。它是持久化任务向异步调度演进的重要桥梁。

### 19. 恢复能力如何测试

不能只测试“正常执行成功”。至少应设计故障注入或模拟场景：

1. 在工具调用前重启，恢复后任务是否仍能执行？
2. 在写工具请求已发出但结果未保存时崩溃，恢复后是否先查询/幂等处理？
3. worker 租约过期后，是否只有一个新 worker 成功领取？
4. `WAITING_HUMAN` 任务重启后，待确认信息是否仍完整？
5. 已取消任务收到晚到回调，是否会保持取消而不重新执行？
6. 旧 checkpoint 在新版本系统中能否明确处理，而不是静默损坏？
7. 同一回调重复两次，结果是否只应用一次？

这些测试关心的是系统行为，不是模型回答是否优雅。恢复与幂等问题往往只有在故障路径中才暴露。

### 20. 一个完整走读：创建工单时 worker 崩溃

任务目标：物流异常时，在用户确认后创建工单。

#### 正常路径

```text
WAITING_HUMAN
-> 用户批准
-> checkpoint：批准信息已保存，任务转 RUNNING
-> checkpoint：准备 create_ticket，生成 call_001 与 idempotency_key
-> 调用工单系统
-> 返回 ticket_id=T1001
-> checkpoint：call_001 成功，保存 T1001
-> SUCCEEDED
```

#### 异常路径：外部调用后崩溃

```text
... -> 调用工单系统
外部系统已创建 T1001
本地进程在保存成功结果前崩溃
```

重启后：

1. 恢复器读取 checkpoint，发现 `call_001` 已发起但结果为 `UNKNOWN`。
2. 使用相同的幂等键或外部请求 ID 查询工单系统。
3. 得知 T1001 已存在，将调用记录更新为成功。
4. 保存任务结果并进入 `SUCCEEDED`。

错误做法是直接再次发一个不带幂等键的创建请求。那可能制造 T1002，用户也会收到重复工单。

### 21. 一套务实的最小落地顺序

若从零开始，不要一开始追求复杂工作流引擎。可以分层建设：

1. 持久化 `task_id`、状态、输入、结果、失败码和时间字段。
2. 引入状态转移表和乐观锁，保证一个任务不被多方同时推进。
3. 为写操作保存 `tool_call_id` 和稳定幂等键。
4. 为等待人工、异步工具、重试增加明确 checkpoint。
5. 加入租约、超时扫描和恢复 worker。
6. 处理结果未知与对账。
7. 添加事件审计和 Outbox。
8. 最后再考虑可视化工作流、复杂分支、跨系统补偿和高级编排框架。

每一步都可以带来真实可靠性提升。不要跳过前面基础，直接用一个框架名称掩盖任务一致性问题。

## 常见误区

### 误区 1：把完整聊天记录保存起来，就已经支持断点恢复

聊天记录只能帮助模型理解语义，不能说明工具是否已执行、确认是否有效、幂等键是什么、任务是否取消、谁拥有执行权。恢复需要结构化任务状态和调用账本。

### 误区 2：工具请求超时就代表调用失败，可以直接重试

对写操作尤其危险。超时可能意味着外部系统已执行但响应丢失。应将其视为结果未知，优先按请求 ID 或幂等键确认。

### 误区 3：用数据库事务就能覆盖所有外部工具调用

本地数据库事务无法自动把第三方 API、邮件、支付或另一个服务的状态纳入同一个原子提交。需要幂等、对账、补偿、Outbox 等组合策略。

### 误区 4：只要加最大重试次数，就具备恢复能力

重试只处理部分暂时性错误。恢复还要知道从哪里继续、结果是否未知、是否已取消、权限是否变化、旧版本是否兼容，以及是否会重复副作用。

### 误区 5：任务处于 `RUNNING` 就说明 worker 还在执行

worker 可能已经崩溃。需要租约/心跳与过期恢复机制，但恢复时仍需幂等防护。

### 误区 6：所有任务都应该自动恢复

有些任务已过期、策略版本不兼容、风险过高或外部状态无法确认。此时终止、转人工或创建新任务可能比自动恢复更安全。

### 误区 7：Checkpoint 越频繁越可靠

无意义的高频保存会增加竞争、成本和复杂度。应围绕状态变化、外部副作用、等待和昂贵计算等可恢复边界建立检查点。

## 本节练习

### 练习 1：判断检查点时机

对于“查询订单 -> 请求用户确认 -> 创建工单 -> 通知用户”的任务，请写出至少四个必须或强烈建议建立 checkpoint 的时机。

答案：可以包括：1）任务创建为 `PENDING` 后；2）用户确认请求已生成、任务转为 `WAITING_HUMAN` 前/时；3）用户批准信息已验证并写入后；4）创建工单调用前，保存 `tool_call_id` 和幂等键；5）工单系统确认返回 `ticket_id` 后；6）任务成功并准备发送通知时。核心是覆盖等待与外部副作用边界。

### 练习 2：处理未知结果

创建工单 API 调用超时。系统没有收到响应，但此前已保存调用意图和幂等键。下一步最合理是什么？

答案：将调用标记为结果未知，不要立即使用新幂等键重复创建。优先使用外部请求 ID 或原幂等键查询工单系统；若系统支持，使用同一幂等键安全重试；仍无法确认时根据业务风险等待、转人工或走对账流程。

### 练习 3：区分乐观锁和幂等键

为什么即使已有乐观锁，创建工单仍需要幂等键？

答案：乐观锁主要防止两个 worker 同时更新同一条本地任务状态；它无法覆盖 worker 在发出外部请求后崩溃、网络超时或外部系统重复收到请求的情形。幂等键由外部业务动作识别重复逻辑请求，防止产生多个真实副作用。两者解决不同层面的重复问题。

### 练习 4：选择恢复策略

以下情况应自动恢复、从头重跑、查询确认还是转人工？

1. 只读知识库检索在 worker 崩溃时未完成。
2. 付款指令发送后网络中断，结果未知。
3. 等待法务审批的合同任务服务重启。
4. 一个月前创建、已超过业务截止日期的临时报告任务。

答案：1 通常可以从头重新检索或恢复，因只读且成本低。2 应先查询确认/对账，不能盲目重试。3 应持久化等待状态，重启后继续等待审批事件。4 通常应过期终止或由用户重新发起，而不是自动恢复旧任务。

## 自测题

### 自测 1：Checkpoint 和事件日志分别解决什么问题？

答案：Checkpoint 保存当前可恢复状态，使系统快速知道任务此刻在哪、下一步怎么做；事件日志保存关键历史变化，帮助审计、排障和必要时重建状态。实际常用当前快照加关键事件的混合模式。

### 自测 2：为什么写操作应在调用前保存调用意图与幂等键？

答案：因为调用后可能在记录结果前崩溃。预先保存调用意图、稳定调用 ID 和幂等键，可让恢复器知道这一步可能已发生，并能向外部系统查询或安全重试，减少重复副作用。

### 自测 3：什么是“结果未知”，为什么它不应直接等同于失败？

答案：结果未知表示本地没有得到明确回执，但外部系统可能已经执行，例如超时或网络中断。把它当失败并盲目重试会重复写入；应先对账、查询幂等结果或转人工。失败是已知未完成，未知是系统暂时不知道外部真实状态。

### 自测 4：租约和心跳解决什么问题？它们不能解决什么问题？

答案：租约和心跳帮助判断 `RUNNING` 任务的执行者是否仍活着，并允许租约过期后被其他 worker 恢复。它们不能保证旧 worker 绝不会在网络隔离时继续执行，也不能防止外部写操作重复，因此仍需幂等和状态确认。

### 自测 5：恢复任务时最重要的原则是什么？

答案：只继续尚未确认完成的部分；已确认的步骤不重复；对外部副作用结果不明的步骤先确认再决定是否重试。恢复必须服从当前状态、权限、预算、版本与取消规则。

## 本节小结

持久化与 Checkpoint 让 Agent 从临时进程中的循环，变成能跨重启、跨 worker、跨等待和跨故障的任务系统。核心不是保存更多文本，而是围绕状态转移和副作用边界保存可验证事实、调用账本、幂等标识、版本与恢复条件。
