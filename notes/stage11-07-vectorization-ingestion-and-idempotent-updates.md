# M11 第 7 节：向量化、入库与幂等更新

## 本节定位

前面已经把文件加工为有结构、有页码、有版本和权限的知识材料。本节讨论这些材料怎样稳定变成在线可检索索引，以及任务重复、失败、重试和升级时如何不制造重复或半成品知识。

## 本节学习目标

1. 区分 embedding、向量、索引、入库和发布。
2. 理解模型、维度、距离度量和文本模板的一致性要求。
3. 解释幂等、批处理、重试、状态机与候选发布。
4. 区分文件重复、内容变化、规则变化和模型变化。
5. 建立入库验收与离线任务可观测性意识。

## 一句话先讲透

**入库不是调用 embedding 后写一批数字，而是把一个明确版本的知识快照，以可重复、可验证、可回滚的方式发布成在线证据索引。**

## 基础知识铺垫

### 1. embedding 和向量是什么

Embedding 是把文本映射为一串数字的过程；得到的数字数组叫向量。语义相近的文本，在同一模型产生的向量空间中通常更接近。

但向量不是原文的压缩备份：不能可靠还原文本、页码、版本、权限和例外。相似度高也不代表资料一定正确、有效或适用于当前用户。

### 2. 索引、入库与发布

```text
向量化：将确定的知识块变成向量。
索引：让向量与字段可被快速搜索。
入库：写入正文、向量、元数据和处理记录。
发布：让通过验证的索引开始参与在线查询。
```

把“写入成功”当作“可以回答”是典型错误。在线可用还要求字段完整、权限正确、版本有效、块数完整、质量通过。

## 本节主题系统讲解

### 1. 向量空间为什么必须一致

一个集合中的文档向量和查询向量必须来自兼容配置：

```text
embedding 模型与版本。
向量维度。
文本预处理和拼接模板。
归一化规则。
距离度量，例如 cosine、dot product、euclidean。
```

若文档用模型 A、查询用模型 B，即使维度相同，距离也不再有稳定语义。若标题被写入文档向量但查询处理方式已变，也会导致检索行为不可预测。

### 2. 输入快照：本次到底处理什么

每次入库前应有明确快照：

```text
document_version_id。
规范化后的块内容与元数据。
content_hash。
pipeline_version。
embedding 配置。
目标知识库和索引版本。
```

没有快照，重跑后无法判断差异来自文件变化、清洗规则、分块规则、模型变化还是任务错误。

### 3. 幂等性

幂等的含义是：同一业务操作重复执行，最终可见结果与执行一次一致。

文档入库中会自然出现重复：用户重复上传、网络响应丢失后重试、任务中断恢复、定时扫描重复执行、多个入口同时处理同一版本。

若不幂等，同一段内容会被写入多次，检索结果满是重复块，成本、引用和评估都会失真。

### 4. 怎样判断“是否需要处理”

| 情况 | 合理处理 |
| --- | --- |
| 文件字节未变 | 通常跳过解析和向量化 |
| 文件变了但规范化内容未变 | 视业务更新文件记录，索引可复用 |
| 内容变了 | 重建受影响块并让旧块退出 |
| 内容未变但分块规则变了 | 构建新索引版本 |
| 内容未变但 embedding 模型变了 | 重新向量化 |
| 权限或有效期变了 | 更新过滤元数据，必要时重新发布 |

file hash 与 content hash 不同：前者看原文件字节，后者看规范化内容。两者都需要明确计算范围。

### 5. 批处理与资源治理

大文档可能有成千块。逐块 embedding 很慢且易限流；一次全塞进请求又可能超限制并放大失败影响。

批处理要平衡：批大小、并发、token 上限、API 限流、失败粒度、任务进度和成本。离线任务也需要速率限制、优先级、暂停恢复、重试上限和失败队列，不能因为用户看不见就无限消耗 provider 配额。

### 6. 处理状态与发布状态

```text
received -> parsing -> chunking -> embedding -> indexing -> validating -> ready
```

还可能有 `failed`、`needs_review`、`disabled`、`archived`。关键原则：正在构建的新版本不能直接替代当前线上版本。否则用户会检索到半成品，或新任务失败时旧资料也被清空。

### 7. 候选版本、验证与发布

稳定发布可理解为：

```text
构建候选索引
-> 检查块数、维度、hash、权限、页码和抽样查询
-> 标记候选版本通过
-> 切换在线查询范围
-> 保留旧版本以便回滚
-> 异步清理旧派生数据
```

这与部署新服务的灰度/回滚思想相似：新数据先证明自己完整可用，再影响用户。

### 8. 哪些失败可重试

| 失败 | 处理 |
| --- | --- |
| 网络抖动、短暂 5xx | 有上限的退避重试 |
| API 限流 | 等待、降并发、分批重试 |
| 无效凭据 | 停止并修复配置，不盲重试 |
| 文件损坏、格式不支持 | 标记失败或人工处理 |
| 维度不匹配 | 配置错误，禁止发布 |
| 权限字段缺失 | 默认不可发布，等待补全 |

重试前必须确认稳定 ID 和幂等键；否则“服务已写入但响应丢失”会被重复写入。

### 9. 入库验收

不能只看接口 `200`。应检查：

```text
预期块数与可检索块数一致。
正文、document_id、版本、页码、权限和状态完整。
向量维度与集合配置一致。
重复执行没有新增可见重复块。
抽样查询能召回目标证据。
失败块被记录，未静默遗漏。
```

这让“技术写入成功”变成“业务知识已正确发布”。

### 10. 离线任务可观测性

记录：处理哪份文件、哪个版本、使用什么 pipeline/embedding；页数、块数、成功失败跳过数；每阶段耗时；失败原因和是否可重试；最终是否发布。

当用户说“文档上传了但问不到”，这些信息能定位是解析、索引、过滤还是发布问题，而不是靠猜。

## 常见误区

### 误区 1：embedding 成功就代表文档入库成功

不对。还要验证写库、字段、质量、状态、发布和实际查询。

### 误区 2：重复上传只需前端禁止

不对。网络、任务和多个入口都会重复，幂等必须由服务端和数据模型保证。

### 误区 3：内容没变就永远不用重建

不对。分块、清洗、embedding、权限模型升级都会影响派生索引。

### 误区 4：失败后全量重跑最省事

不一定。它会浪费成本并可能覆盖可用版本；应记录进度、失败块和发布状态。

## 本节练习

### 练习 1：为什么查询向量和文档向量必须兼容？

答案：相似度比较假设它们在同一语义空间。模型、维度、预处理或距离度量不兼容时，分数不再有可靠含义。

### 练习 2：入库幂等性是什么意思？

答案：同一份明确输入重复入库后，最终在线可见知识与执行一次一致，不应出现额外重复块或不一致状态。

### 练习 3：为什么候选索引要先验证再发布？

答案：防止半成品、错误权限、缺块或配置错误直接影响用户；旧版本可在新版本验证前继续提供服务。

## 自测题

### 自测 1：什么变化通常必须重新向量化？

答案：正文内容、分块边界、embedding 文本模板或 embedding 模型变化时，通常需重新向量化。

### 自测 2：离线任务为何也要限流和成本治理？

答案：它会消耗模型/API 配额和费用，失控的大规模重建还可能影响在线用户请求。

### 自测 3：本节最重要的结论是什么？

答案：入库是可验证、可发布、可重建的知识发布流程，不是一次无状态的向量写入。
