# M13 第 7 节：推理服务与 OpenAI 兼容接口

## 本节定位

前面几节分别讨论了模型权重、Token、硬件资源、量化和模型接入方式。它们解释的是“模型为什么能被加载和推理”。但业务系统中的 Java、Python、前端或工作流服务通常不会直接操作 GPU 显存，更不会直接调用 `forward()` 函数；它们需要的是一个稳定的网络服务。

本节讨论这一层转换：**模型权重和推理引擎，怎样被包装成一个可访问、可鉴权、可观测、可演进的推理服务；OpenAI 兼容接口又到底兼容了什么。**

它和你已经学过的 LLM API 调用、SSE 流式输出、Structured Output、Tool Calling 直接相连。此前你站在“调用方”视角学习 `client.chat.completions.create(...)`；现在转到“服务提供方和平台设计者”视角，理解这条调用跨越了哪些边界，以及为什么不能只看路径像不像 OpenAI。

## 本节学习目标

学完后，你应当能够：

1. 区分模型、推理引擎、推理服务、API 网关和业务应用各自负责什么。
2. 解释一次聊天请求从 HTTP 到 Token 输出、再到 HTTP/SSE 响应的大致链路。
3. 说明 REST、JSON、HTTP 状态码、SSE 在推理 API 中分别解决什么问题。
4. 说清 OpenAI 兼容接口的含义、价值和边界，不把“接口长得像”误认为“能力完全一样”。
5. 判断 `/v1/chat/completions`、`/v1/embeddings`、`/v1/models` 等常见端点的职责。
6. 理解流式和非流式响应在协议、用户体验、资源占用上的差别。
7. 设计调用方应具备的超时、重试、错误分类、鉴权和能力探测原则。
8. 识别生产环境中“直连模型服务”与“经由网关访问”各自的适用范围。

## 一句话先讲透

**推理服务不是模型本身，而是把模型运行能力封装为网络契约；OpenAI 兼容接口不是对某家模型能力的保证，而是对一部分请求与响应形状的约定。**

## 基础知识铺垫

### 1. 从库调用到网络调用

假设你在 Python 中直接导入一个模型库：

```python
tokens = tokenizer.encode("你好")
result = model.generate(tokens)
```

这叫**进程内调用**：调用代码、Tokenizer、模型权重、推理引擎和 GPU 可能都在同一个进程或同一台机器上。它很适合实验，但业务系统很少直接采用这种方式，原因包括：

- 每个业务服务都要安装庞大的模型依赖和权重；
- 每个服务都要管理显卡、显存、并发和模型生命周期；
- 多个业务服务会重复加载同一个模型，浪费资源；
- 权限、审计、限流、调用统计和统一升级很难做；
- Java、Python、Node.js 等不同语言难以共享同一套进程内库。

另一种做法是把模型运行放到独立进程或独立机器里，对外暴露网络接口：

```text
业务应用 --HTTP--> 推理服务 --调用--> 推理引擎 --使用--> 模型权重 / GPU
```

这样，业务应用只需要遵守 HTTP 协议和 JSON 数据格式。模型服务可以独立扩容、升级、监控和保护。这就是**推理服务化**。

注意：服务化没有让推理变得“没有成本”。GPU、队列、显存、故障和模型限制仍然存在，只是被集中到更合适的边界中管理。

### 2. 客户端、服务器与 API 契约

在网络调用中：

- **客户端（client）**：发起请求的一方，例如你的 Python AI 服务、Java 后端或前端不能直接访问的 BFF；
- **服务器（server）**：监听端口、接收并处理请求的一方，例如模型推理服务；
- **API（Application Programming Interface）**：双方对“请求如何写、响应如何读、失败如何表达”的共同约定；
- **契约（contract）**：比“接口地址”更完整的约定，包含字段、类型、必填性、默认值、枚举、语义、错误、版本和兼容策略。

例如，下面两个请求的路径一样、字段也相似：

```http
POST /v1/chat/completions
Content-Type: application/json

{"model":"example-model","messages":[{"role":"user","content":"你好"}]}
```

但它们未必是同一个契约：一个服务可能支持 `tools`，另一个忽略它；一个服务的 `temperature=0` 基本稳定，另一个仍有随机性；一个响应能返回 `usage`，另一个没有；一个能输出 JSON Schema 约束结果，另一个只能在提示词里要求 JSON。**字段名称相同不等于语义相同。**

### 3. HTTP：请求和响应的传输外壳

HTTP 是应用层协议。推理 API 常用它，因为跨语言、跨网络、工具生态和代理支持都成熟。

一次 HTTP 请求至少包含：

```text
请求方法 + URL 路径 + 请求头 + 可选请求体
```

常见元素：

- `POST`：提交一段输入，让服务执行生成、向量化、重排序等操作；
- `GET`：读取状态或模型列表，例如 `GET /v1/models`；
- URL：例如 `https://api.example.com/v1/chat/completions`；
- 请求头（header）：鉴权令牌、追踪 ID、内容类型、客户端信息；
- 请求体（body）：通常是 JSON，包含模型名、消息、参数等。

响应也包含状态码、响应头和响应体：

```text
HTTP/1.1 200 OK
Content-Type: application/json

{"id":"...","choices":[...]}
```

HTTP 只负责“消息如何在网络上传递”，不负责知道什么是 Token、工具调用或向量。LLM 的业务语义由 API 契约定义。

### 4. JSON：结构化数据，不是自然语言文本

JSON 用键值对和数组表示结构，例如：

```json
{
  "model": "example-model",
  "temperature": 0.2,
  "messages": [
    {"role": "system", "content": "你是客服助手。"},
    {"role": "user", "content": "订单什么时候到？"}
  ]
}
```

JSON 的重要性质：

- 对象键名必须是双引号字符串；
- 字符串必须用双引号；
- 数字、布尔值、`null` 不加引号；
- 数组有顺序，对象字段通常不应依赖书写顺序；
- JSON 是数据格式，不自动提供字段合法性校验。

最后一点很关键。JSON 能解析成功，只说明语法正确；不表示 `model` 存在、消息角色合法、工具参数满足 Schema，或调用方有权限使用该模型。后续仍需要服务端校验。

### 5. 同步响应、流式响应与“连接保持”

传统同步 HTTP 的模式是：

```text
客户端请求 -> 服务器处理完全部结果 -> 服务器一次性响应 -> 客户端拿到完整结果
```

非流式聊天就是这个模式。优点是简单，适合短输出、机器间调用和后续 JSON 解析；缺点是用户必须等到所有 Token 都生成完成，才能看到第一个字。

流式响应则让服务器在生成过程中分多次发送片段：

```text
客户端请求 -> 服务端开始推理 -> 片段 1 -> 片段 2 -> ... -> 结束信号
```

常见实现是 **SSE（Server-Sent Events）**。它基于一个持续打开的 HTTP 响应，服务器单向推送事件。常见格式如下：

```text
data: {"choices":[{"delta":{"content":"您好"}}]}

data: {"choices":[{"delta":{"content":"，我来帮您"}}]}

data: [DONE]
```

这里的空行是 SSE 事件边界的一部分。客户端不能把每一行都当成完整 JSON，更不能假设一个网络数据包恰好对应一条事件；它需要按 SSE 协议持续解析并拼接增量内容。

### 6. HTTP 状态码和业务错误码

HTTP 状态码首先表达传输层和通用请求结果：

- `200 OK`：请求成功；
- `400 Bad Request`：请求格式或字段非法；
- `401 Unauthorized`：没有有效身份凭证；
- `403 Forbidden`：身份可能有效，但无权访问该资源；
- `404 Not Found`：端点、模型或资源不存在；
- `409 Conflict`：请求与当前资源状态冲突；
- `422 Unprocessable Content`：格式可解析但语义校验不通过，部分框架常用；
- `429 Too Many Requests`：被限流或额度耗尽；
- `500 Internal Server Error`：服务端内部错误；
- `502 Bad Gateway`、`503 Service Unavailable`、`504 Gateway Timeout`：网关、上游或临时不可用。

而业务错误码通常放在 JSON 响应里，提供更精确的信息，例如：

```json
{
  "error": {
    "code": "context_length_exceeded",
    "message": "输入超过该模型允许的上下文窗口。",
    "type": "invalid_request_error"
  }
}
```

调用方应同时看 HTTP 状态与结构化错误体。只根据响应正文里的文字猜错因，会让重试、告警和用户提示都变得不可靠。

### 7. “兼容”在软件工程中的几种层次

兼容不是非黑即白。至少可以区分：

1. **连接兼容**：能连到相同协议的地址，例如都支持 HTTPS。
2. **路径兼容**：都有 `/v1/chat/completions` 这样的 URL。
3. **请求形状兼容**：接受类似的 JSON 字段，例如 `model`、`messages`、`stream`。
4. **响应形状兼容**：返回类似的 `choices`、`usage`、错误对象或流式 `delta`。
5. **行为语义兼容**：相同字段有相近含义和边界，例如 `max_tokens` 真正限制同一类输出预算。
6. **能力兼容**：工具调用、视觉输入、结构化输出、Embedding、批处理等功能都可用。
7. **性能与治理兼容**：限流、并发、超时、审计、版本、区域和数据处理方式也满足同样要求。

日常所说的“OpenAI 兼容”，通常最多承诺第 2 至第 4 层，有些还包含部分第 5 层。它**通常不自动承诺**第 6 和第 7 层。

## 本节主题系统讲解

### 1. 推理服务的完整分层

一个可调用的模型能力常可拆成以下层次：

```text
业务应用层
  Java / Python 服务、工作流、前端背后的 BFF
        |
接入与治理层
  API 网关、鉴权、限流、租户、审计、路由、配额
        |
推理 API 层
  /chat/completions、/embeddings、/models、流式协议、错误协议
        |
推理服务层
  请求校验、排队、调度、批处理、Tokenizer、结果序列化
        |
推理引擎层
  执行模型计算、KV Cache、显存分配、GPU 内核调度
        |
模型资产层
  权重、Tokenizer、配置、模板、适配器、版本元数据
        |
基础设施层
  GPU/CPU、网络、磁盘、容器、日志、监控、密钥系统
```

现实中一个产品可能把多层合在一起，或者拆成多个独立组件。但作为学习和排障模型，分层十分有用。

举例：调用返回 `429` 时，问题可能来自网关的租户限流，也可能来自推理服务的队列保护，不一定说明模型出错；调用返回“模型不存在”，可能是模型资产未加载，也可能是网关的模型路由表没有该别名。分层让你知道该在哪一层找证据。

### 2. 一次非流式聊天请求发生了什么

以一个典型聊天接口为例：

```http
POST /v1/chat/completions
Authorization: Bearer <token>
Content-Type: application/json
X-Request-Id: req-123

{
  "model": "support-chat",
  "messages": [
    {"role": "user", "content": "我想查询订单 A1001"}
  ],
  "temperature": 0.2,
  "stream": false
}
```

服务端可能依次做下面的事：

1. **网络接收与基础防护**：检查 TLS、请求大小、连接数、反向代理规则。
2. **身份认证**：解析 API Key、JWT 或内部服务凭证，确认请求来自谁。
3. **授权与配额**：判断该调用方能否用 `support-chat`，是否还有调用额度，是否超过 QPS/并发上限。
4. **协议校验**：检查 JSON 是否有效，`messages` 是否为数组，参数类型是否合法。
5. **模型解析**：将公开模型名映射为具体模型版本、部署实例或路由策略。
6. **输入准备**：套用聊天模板，调用 Tokenizer，检查上下文窗口，处理工具定义或多模态附件。
7. **调度排队**：若 GPU 正忙，请求进入队列；服务决定何时与哪些请求一起执行。
8. **推理执行**：先完成 prefill，再持续 decode 新 Token；可能使用 KV Cache 和连续批处理。
9. **输出后处理**：识别停止条件，整理文本、工具调用、用量信息，按响应 Schema 序列化。
10. **记录与返回**：写入必要的指标、审计和追踪信息，然后返回 JSON。

调用方看到的只是一段 JSON，但它是上述多层工作结束后的产品。因而“HTTP 200”只代表服务给出了一个成功响应，不必然代表答案正确、工具参数安全或业务任务已经完成。

### 3. 常见端点及其职责

不同供应商名字可能不同，但以下形态非常常见。

#### 3.1 `POST /v1/chat/completions`

这是以 `messages` 表示对话历史的接口。它通常支持：

- system、user、assistant 等角色；
- 生成参数，例如 `temperature`、`top_p`、输出长度；
- `stream`；
- 某些实现支持 `tools` / `tool_choice`；
- 某些实现支持响应格式或 JSON Schema。

它的核心抽象是“给定一串消息，请模型生成下一条 assistant 消息”。即使你做的是 RAG、工具调用或 Agent，最后仍常会落到这种生成接口。

#### 3.2 `POST /v1/responses`

一些较新的 API 用更统一的“输入和输出项”抽象来承载文本、图片、工具、推理摘要或多轮状态。不同平台对它的支持差异较大。

不要因为路径名先进就默认它更适合当前项目。是否选择它，应看你的 SDK、目标模型、工具调用语义、流式事件、迁移成本和团队已有协议。

#### 3.3 `POST /v1/embeddings`

Embedding 接口不是“让模型回答问题”，而是把文本转成固定维度向量：

```json
{
  "model": "text-embedding-model",
  "input": ["退款政策", "物流进度"]
}
```

响应一般包含若干浮点数数组和用量信息。它与聊天接口可能属于同一服务，但其模型、批处理方式、维度、限额和质量指标都不同。RAG 系统不能把聊天模型 API 的稳定性推论到 Embedding API 上。

#### 3.4 `GET /v1/models`

模型列表端点通常用来展示“当前凭证或当前服务可见的模型”。它可能返回模型 ID、归属、能力标签或创建时间。

它有价值，但不能被误用为完整能力说明：

- 列在列表里不代表所有参数、工具或结构化输出都可用；
- 没列出不一定代表绝对不可用，可能是权限或别名策略；
- 列表是瞬时视图，服务端可以滚动升级或下线模型。

生产系统更可靠的做法是维护自己的允许模型清单和能力矩阵，并在发布或启动时执行受控的探测验证。

#### 3.5 非标准扩展端点

重排序、文件上传、批任务、内容安全、缓存管理、模型加载/卸载、运行指标等能力经常没有统一的 OpenAI 兼容标准。供应商可能使用自己的路径和字段。

这不是“接口不好”，而是说明兼容标准覆盖范围有限。工程上应把这些扩展能力隔离在适配器中，而不是把供应商私有字段散落到业务代码各处。

### 4. OpenAI 兼容接口真正解决什么问题

它的核心价值是**降低调用侧迁移和集成成本**。

如果多个服务都接受近似的请求：

```python
from openai import OpenAI

client = OpenAI(
    api_key="...",
    base_url="https://provider.example.com/compatible-mode/v1",
)

response = client.chat.completions.create(
    model="provider-model-name",
    messages=[{"role": "user", "content": "你好"}],
)
```

调用方往往不需要为每个供应商重写底层 HTTP 客户端、流读取器和基础数据结构。你可以替换 `base_url`、凭证和模型名，在较小改动下接入云模型、企业模型网关或本地推理服务。

但它没有解决所有问题。兼容接口通常**不保证**：

- 模型理解能力、中文质量、事实性或安全性相同；
- Tokenizer 相同，因此 Token 计数、上下文上限和成本计算相同；
- 采样参数的默认值和实际行为相同；
- `tools`、`response_format`、视觉输入、推理模式等高级字段一致；
- 返回的 `usage` 字段齐全、口径一致；
- 流式事件切分、结束事件、心跳行为完全一致；
- 错误码、限流规则、重试建议和服务等级相同；
- 数据存储地域、日志保留和安全合规政策相同。

因此，正确的理解是：**OpenAI 兼容是一个良好的“最小公共语言”，不是消除模型和平台差异的魔法转换器。**

### 5. 兼容性最容易出问题的地方

#### 5.1 模型名不是通用标准

`gpt-...`、`qwen-...`、`llama-...` 这类名称由平台定义。一个平台上的模型 ID 在另一个平台几乎一定不能直接用。

更稳健的业务代码应使用内部逻辑名，例如：

```text
customer_support_default
embedding_zh_v1
rerank_policy_v1
```

再由配置或路由层映射到当前提供方的实际模型 ID。这样切换供应商或升级版本时，不需要在各处业务逻辑中全局替换字符串。

#### 5.2 字段被接受，不代表字段被执行

有的兼容服务为了客户端兼容，会接受某些字段，但可能忽略它、部分支持它，或对其做平台特定解释。例如：

- 请求传入 `seed`，但服务端没有确定性保证；
- 请求传入 `logprobs`，但响应不返回或只在某模型可用；
- 请求传入 `response_format`，但仅支持 JSON object，不支持 JSON Schema；
- 请求传入 `tools`，模型可能返回普通文本而非工具调用；
- 请求传入较大的 `max_tokens`，服务端可能按自身上限截断或报错。

所以集成高级能力时，不能只看“SDK 没报参数错误”。要用代表性的输入做行为验证，并把结论写入能力矩阵。

#### 5.3 消息内容形态不完全一致

最简单的消息内容是字符串：

```json
{"role": "user", "content": "请总结这段文本"}
```

多模态协议可能允许 `content` 为数组，其中包含文本、图片 URL、文件或其他内容块。不同兼容服务可能只支持字符串，或对图片格式、文件大小、URL 可访问性有额外限制。

因此，适配层应在请求发送前检查“当前模型是否支持当前内容形态”，而不是让底层服务以难以理解的 400/500 失败来暴露问题。

#### 5.4 工具调用的返回结构和循环语义

工具调用不是单次 HTTP 请求结束就完成的能力。它至少涉及：

```text
模型输出工具请求
-> 业务系统校验并执行工具
-> 将 tool result 追加回消息
-> 再次调用模型
```

不同服务可能在 `tool_calls`、参数 JSON 字符串、调用 ID、并行调用和工具结果消息格式上有细微差异。更重要的是，**无论兼容服务怎样返回，工具执行权都在你的应用手里**。不要把兼容 API 当成工具权限控制系统。

### 6. 流式 API 的真实链路

当请求中包含：

```json
{"stream": true}
```

通常会发生：

```text
客户端建立 HTTP 连接
-> 服务端鉴权、排队、prefill
-> 生成第一个可发出的增量
-> 响应头 Content-Type: text/event-stream
-> 持续发送 SSE data 事件
-> 发送结束事件
-> 关闭连接
```

流式的价值主要是降低用户的**首字等待感受**，也就是你在上一节见过的 TTFT（Time To First Token）。它不一定让总生成时间更短，甚至因网络逐片传输和渲染产生一点额外开销。

#### 6.1 调用方如何正确处理流

调用方通常需要：

1. 给连接和首事件分别设置合理超时；
2. 持续读取事件，而不是等待整个响应体；
3. 校验每个事件是否可解析；
4. 识别文本增量、工具调用增量、用量事件和结束事件；
5. 将需要展示的文本按顺序拼接；
6. 只有收到明确的结束信号后，才把这轮结果视为完整；
7. 客户端取消时，中止下游连接，避免无效生成继续占用 GPU；
8. 记录请求 ID、模型、TTFT、总时长、终止原因等观测数据。

“收到了一些字”不等于“请求成功完成”。网络中断、上游重启、客户端取消、内容过滤或生成异常，都可能让流在中间终止。

#### 6.2 流式重试为什么更谨慎

非流式请求在连接失败且无法确认服务端是否处理时，已经要谨慎重试；流式更复杂，因为用户可能已经看到了部分内容。

如果你直接重新发起整个请求，可能导致：

- 页面上出现两段重复开头；
- 工具调用被重复触发；
- 已经创建的业务资源重复创建；
- 账单、用量或审计记录难以解释。

对纯文本生成，通常可以向用户明确提示“生成中断，请重新生成”，或采用保存上下文后重新开始的策略。对带副作用的工具链，必须依靠幂等键、确认状态和工具执行记录，而不是靠“再试一次”解决。

### 7. 鉴权不是把 API Key 写进请求就结束了

最常见的外部模型鉴权形态是：

```http
Authorization: Bearer <API_KEY>
```

它表达“调用方用这个凭证请求服务”。但一个成熟系统还需要回答：

- 这个 Key 属于哪个人、应用、环境或租户？
- 它能访问哪些模型和端点？
- 有效期和轮换策略是什么？
- 是否能区分开发、测试、生产？
- 是否按 Key 记录配额、审计、成本和异常？
- 泄露后怎样撤销和替换？

在你的业务系统中，浏览器前端不应直接持有云模型供应商的长期 API Key。通常应是：

```text
浏览器 -> 你的业务后端 / AI 服务 -> 模型网关或模型提供方
```

这样可以把供应商密钥保留在服务端，并在服务端完成用户身份、权限、限流、脱敏、审计、RAG 和工具安全控制。

### 8. 超时：不能只设置一个很大的数字

推理调用可按阶段理解时间：

```text
DNS/建连 -> TLS -> 排队 -> prefill -> 首 Token -> 持续生成 -> 完整响应
```

单一“总超时”固然必要，但常不够精确。常见的工程划分包括：

- **连接超时**：网络是否能建立连接；
- **读取/空闲超时**：连接建立后长期没有任何数据是否判定异常；
- **首 Token 超时**：流式请求多久没有第一段输出就报警或中止；
- **总请求超时**：整个任务最多允许多久；
- **调用链预算**：上游业务请求的总时间必须为下游调用、重试和兜底预留空间。

例如一个网页请求最多允许 30 秒，不应让对模型的单次调用配置为 30 秒后再准备重试两次；因为上游早已超时，后台却还在消耗资源。超时应从端到端预算倒推，而不是随手填一个很大的值。

### 9. 重试：按失败类型决定，而不是“失败就再发一次”

可以先做一个简化分类：

| 情况 | 常见处理思路 |
| --- | --- |
| 请求参数非法（400/422） | 不重试，修正调用或给出明确错误 |
| 凭证无效（401） | 不重试，检查密钥/环境 |
| 权限不足（403） | 不重试，检查授权或模型许可 |
| 限流（429） | 按服务端建议或退避重试，并控制并发 |
| 临时不可用（503） | 有上限地退避重试或切换降级模型 |
| 网关超时（504） | 判断是否可能已执行；对有副作用流程尤其谨慎 |
| 内容/上下文超限 | 不盲目重试，压缩上下文、减少输出或换模型 |

重试还需要：最大次数、指数退避、抖动（jitter）、总体时间预算和可观测记录。若所有客户端在故障时同时立即重试，会形成**重试风暴**，让本来紧张的推理服务彻底失去恢复机会。

### 10. 模型网关与直连模型服务

小型实验中，应用可直接访问模型提供方或本地推理服务：

```text
AI 服务 -> 模型 API
```

当模型来源、应用数量、租户、成本和治理要求增加时，常引入模型网关：

```text
业务应用 -> 模型网关 -> 云模型 A / 云模型 B / 自部署服务
```

网关可能承担：

- 统一身份认证与密钥托管；
- 内部逻辑模型名到实际模型部署的映射；
- 模型路由、灰度、回退和熔断；
- 请求大小限制、限流、并发控制和配额；
- 日志、Trace、成本计量和审计；
- 脱敏、内容策略、区域路由；
- 统一或适配多个供应商的 API 形态。

网关的代价是多一跳网络、多一层运维和新的潜在故障点。它不是每个项目一开始都必须有的组件。更合理的路径通常是：先在应用内建立清晰的模型客户端适配边界，模型数量和治理需求增长后，再将共性能力下沉到网关。

### 11. 适配层：把供应商差异关在业务代码外

业务代码不应到处写：

```python
if provider == "A":
    ...
elif provider == "B":
    ...
```

这会让切换、测试和治理越来越困难。更好的思想是定义你自己的最小领域接口，例如：

```text
generate(messages, options) -> GenerationResult
embed(texts) -> EmbeddingResult
rerank(query, documents) -> RerankResult
```

然后由不同适配器处理：模型名映射、请求字段差异、流式协议差异、错误转换和用量口径。这里的重点不是为了“抽象而抽象”，而是为了让核心业务只依赖自己真正需要的语义。

接口也不应假装所有平台能力完全一致。若某项能力只在部分供应商可用，应显式建模能力，例如：

```text
supports_tools
supports_json_schema
supports_vision
max_context_tokens
streaming_mode
```

这样，在运行前就能做可解释的能力检查，而不是运行中默默降级或神秘失败。

### 12. 推理服务的观测：要看到“模型调用”而非只看到 HTTP 成败

对每次模型调用，至少应能关联以下信息：

- 请求 ID / Trace ID；
- 调用方服务、用户或租户标识（遵守隐私最小化原则）；
- 逻辑模型名、实际模型版本、提供方和区域；
- 是否流式、输入/输出 Token 量、上下文长度；
- 排队时间、TTFT、总耗时、完成原因；
- HTTP 状态、结构化错误类型、是否重试或降级；
- 工具调用、RAG 检索等关键链路摘要；
- 成本或用量指标。

同时要避免把完整用户提示、敏感文档、密钥、身份证号或内部订单信息无差别写入日志。可观测性与隐私安全不是二选一，而是要求你设计字段分级、脱敏、访问控制和保留期限。

### 13. 如何评估一个“兼容 API”是否适合接入

不要只用“你好”做连通性测试。更可靠的验证清单应覆盖：

1. **基础成功路径**：非流式文本能否返回，编码是否正常。
2. **流式协议**：首段、增量、结束、取消和中断时的行为。
3. **参数边界**：温度、最大输出、超长输入、空消息、非法类型。
4. **目标能力**：工具调用、结构化输出、视觉、Embedding 或 Rerank 中你真正会用的部分。
5. **错误语义**：错误状态、响应结构、限流和超时是否可被程序稳定处理。
6. **用量与成本**：`usage` 是否存在，统计口径能否满足成本治理。
7. **并发与稳定性**：在预期负载下的 P95 延迟、失败率和限流行为。
8. **安全与合规**：密钥、地域、日志、数据使用政策、模型许可证。

这组验证的目的不是做一次“验收仪式”，而是为你自己的适配层、降级逻辑、超时设置和告警阈值提供事实依据。

## 常见误区

### 误区 1：OpenAI 兼容等于可以完全无修改迁移

纠正：基础聊天调用往往改动很小，但模型 ID、参数支持、工具调用、结构化输出、流式事件、用量字段和错误策略都应验证。兼容降低改造量，不消除验证责任。

### 误区 2：HTTP 200 就代表模型调用“成功”

纠正：200 只代表 API 返回成功。模型可能给出不符合业务要求的内容，可能没有遵循结构，可能拒答，也可能生成了不可执行的工具参数。还需要应用层校验、评估和安全控制。

### 误区 3：流式输出天然更快

纠正：它主要缩短用户看到首字的时间，不必然降低总耗时；对于要严格解析 JSON、做批处理或机器间任务，非流式往往更简单可靠。

### 误区 4：API Key 放在前端也没关系，反正接口有鉴权

纠正：前端代码、浏览器开发者工具、网络请求和构建产物都可能暴露密钥。供应商 Key 应留在受控后端或网关，浏览器只使用你自己的用户会话凭证。

### 误区 5：遇到 5xx 或网络错误，一律自动重试

纠正：要考虑请求是否已被处理、是否会重复收费、是否触发工具副作用，以及端到端时间预算。重试必须有限、退避并可观测。

### 误区 6：`/v1/models` 返回了模型，就能放心使用所有高级能力

纠正：模型列表通常只说明可见性或基本可用性。实际能力需要看文档、能力矩阵和受控验证。

### 误区 7：网关能替代业务层安全

纠正：网关可以做认证、限流和路由，但它不了解“用户是否有权看这个订单”“此操作是否已确认”等业务语义。业务授权、工具白名单和副作用确认仍应留在业务/Agent 边界。

## 本节练习

### 练习 1：区分不同层的职责

某团队的 Python 服务调用 `POST /v1/chat/completions` 后收到 429。请分别写出下列层可能负责的内容：业务应用、模型网关、推理服务、推理引擎。

答案：业务应用应决定当前请求能否延迟、降级或提示用户，并记录业务上下文；模型网关可能按 API Key、租户或逻辑模型做限流和配额；推理服务可能因内部队列、并发或显存保护而拒绝请求；推理引擎主要执行计算和资源调度，通常不是直接向业务暴露 HTTP 429 的层。实际原因需用请求 ID、网关日志和服务指标定位，不能只凭 429 断言某一层故障。

### 练习 2：判断兼容范围

一个平台宣称“兼容 OpenAI Chat Completions”，并且基础文本请求可正常返回。能否据此断定它支持 JSON Schema 结构化输出、并行工具调用、视觉输入和与 OpenAI 相同的 Token 计费？说明理由。

答案：不能。该声明通常最多证明路径和基础请求/响应形状兼容。JSON Schema、并行工具调用、视觉输入属于扩展能力；Tokenizer 和计费是模型/平台实现问题。必须查对应模型文档并做受控验证。

### 练习 3：为错误设计处理策略

分别给出收到 400、401、429、503、上下文超限错误时，调用方的首要处理动作。

答案：400：停止重试，修正请求字段或调用逻辑；401：停止重试，检查密钥、环境和凭证轮换；429：遵循限流策略，退避、降低并发或使用受控降级；503：有限次数退避重试或切换健康的备用模型/区域；上下文超限：压缩历史、减少 RAG 上下文、降低输出预算或换更大窗口模型，不应原样重试。

### 练习 4：解释流式中断

用户已经看到“我已经为您查询到订单”，流连接突然断开。为什么不能直接在前端无提示地重新发同一个请求？

答案：重新请求可能产生重复文本；如果这轮请求包含工具调用或写操作，服务端可能重复执行副作用；新一轮生成也未必与前一段自然衔接。应区分纯文本和副作用任务，使用取消/幂等/执行记录等机制，并向用户呈现明确的中断状态或重新生成操作。

### 练习 5：设计最小能力矩阵

为一个客服 AI 系统列出至少 6 个你会写入“模型能力矩阵”的字段。

答案：可以包含逻辑模型名、实际模型 ID/版本、最大上下文 Token、最大输出 Token、是否支持流式、是否支持工具调用、是否支持 JSON Schema、是否支持视觉输入、是否支持 Embedding、输入/输出价格或内部成本口径、区域、数据保留策略、状态（灰度/启用/下线）。字段应服务于真实路由和治理，而不是为了表格完整而堆砌。

## 自测题

### 自测 1：推理引擎与推理服务有什么差别？

答案：推理引擎负责将模型权重和输入 Token 实际转化为输出 Token，并管理底层计算、KV Cache 和硬件执行；推理服务在其上增加网络 API、请求校验、鉴权、排队、调度、响应序列化、错误表达和观测等能力。引擎偏计算执行，服务偏对外提供可治理的能力边界。

### 自测 2：为什么 JSON 解析成功仍可能被 API 拒绝？

答案：JSON 解析成功只表明语法正确。API 还会校验字段类型、必填字段、模型是否存在、参数范围、消息角色、上下文长度、权限、配额和能力支持等语义条件。

### 自测 3：什么是 OpenAI 兼容接口最准确的工程解释？

答案：它表示服务在一定范围内接受和返回与 OpenAI API 相似的协议形态，使现有客户端和基础集成更容易复用。它不自动保证模型能力、参数语义、流式细节、Token 统计、限流、成本和数据治理完全一致。

### 自测 4：为什么生产系统不宜让浏览器直接调用外部模型 API？

答案：长期供应商密钥会暴露在用户可控制的环境中，难以执行业务权限、脱敏、配额、审计、RAG、工具安全和统一错误处理。通常应由受控后端或模型网关持有供应商凭证。

### 自测 5：流式接口的“完成”应由什么判断？

答案：应由协议定义的明确结束事件或正常完成状态判断，而不是“已经收到若干文本片段”。中途断流可能是网络、服务、取消或过滤问题，已收到部分内容不能证明本轮生成完整成功。

## 本节小结

本节将模型推理放回真实服务架构中理解：模型资产和推理引擎负责计算，推理服务将计算封装为可调用 API，网关和业务应用再分别承担治理与业务语义。HTTP、JSON、SSE、状态码、鉴权、超时和重试共同构成调用契约的一部分。

OpenAI 兼容接口的价值是复用调用生态、降低迁移成本；它的边界是只承诺有限协议兼容，不保证模型能力和运行治理完全相同。面对多个模型或供应商，应通过内部逻辑模型名、适配层、能力矩阵、受控验证和可观测性管理差异。
