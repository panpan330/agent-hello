# M12 第 2 节：Agent 任务模型与状态机

## 本节定位

上一节解决的是架构选择问题：一个需求是否真的需要 Agent。本节继续回答另一个决定 Agent 是否可靠的问题：

```text
一个 Agent 任务从收到请求，到完成、等待人工、失败、取消，究竟处于什么状态？
每一种状态允许做什么？又在什么条件下进入下一种状态？
```

很多早期 Agent 只有一段循环：模型想一步、调一个工具、拿结果、再想一步。它演示起来很直观，但工程上很脆弱：进程重启后任务去哪了？工具超时算失败还是仍在执行？人工审核时怎样阻止模型继续操作？用户取消后，后台任务为什么还在继续？

**任务模型与状态机**就是为这些问题建立共同语言和明确规则。它不是给 Agent 增加一层形式化包装，而是让一个有生命周期的任务能够被观察、恢复、限制和追责。

## 本节学习目标

学完后，你应当能：

1. 区分“用户的一次请求”“一次 Agent 运行”“一次业务任务”“一次工具调用”。
2. 解释状态、事件、状态转移和状态机不变量分别是什么。
3. 设计一个包含等待、人工审核、失败、取消和完成状态的 Agent 任务生命周期。
4. 判断哪些状态转移应由程序强制校验，而不是交给模型决定。
5. 理解幂等、超时、重试、恢复与状态机之间的关系。
6. 能够说明为什么长任务必须先有任务状态，再谈队列、持久化和 Multi-Agent。

## 一句话先讲透

> Agent 不应被理解为“一次模型调用”，而应被理解为一个会经历生命周期的任务实例；状态机负责规定这个实例此刻是什么、下一步能做什么，以及它在异常时如何被安全地收束。

## 基础知识铺垫

### 1. 先分清四个容易混在一起的对象

在开发时，人们常说“这个 Agent 请求失败了”。这句话太笼统。至少要分清下面四个对象。

| 对象 | 含义 | 例子 | 生命周期 |
| --- | --- | --- | --- |
| 用户请求（request） | 用户向系统发起的一次 HTTP、SSE 或消息请求 | “帮我查询 A1001 订单并说明物流情况” | 通常很短，连接断开就结束 |
| Agent 运行（run） | 模型在一次上下文中完成一次推理和动作选择 | 模型决定先查订单、再查物流 | 从启动到本次推理停止 |
| 业务任务（task） | 系统为实现业务目标维护的可追踪工作单元 | `task_123`：处理“物流异常咨询” | 可持续数秒、数分钟甚至数天 |
| 工具调用（tool call） | 任务中的一个外部动作 | 调订单接口、创建工单、发送邮件 | 很短，也可能异步 |

它们通常有包含关系：

```text
用户请求
  └─ 创建或查询一个业务任务 task
        ├─ 第 1 次 Agent run
        │     ├─ tool call：查询订单
        │     └─ tool call：查询物流
        ├─ 等待人工审核
        └─ 第 2 次 Agent run
              └─ tool call：创建工单
```

一个 HTTP 请求结束，并不等于业务任务结束。例如用户点击“生成月度客服问题汇总”，系统可以立即返回任务编号；后续任务在后台检索、汇总、等待审核、生成报告。若把整个任务错误地绑在一个 HTTP 请求里，就会遇到连接超时、重启丢失和无法追踪等问题。

### 2. 什么是“状态”

状态是系统对某个对象在当前时刻所处阶段的**明确、可判断、可持久化描述**。

例如工单可以是 `OPEN`、`PROCESSING`、`RESOLVED`；支付订单可以是 `PENDING`、`PAID`、`CANCELLED`。Agent 任务也同样需要状态，例如：

```text
PENDING       已创建，尚未真正执行
RUNNING       正在由执行器或 Agent 处理
WAITING_TOOL  已发起异步工具，等待结果
WAITING_HUMAN 等待人工确认或补充信息
SUCCEEDED     已完成且结果可用
FAILED        已终止，未完成目标
CANCELLED     被用户或系统取消
```

状态不是日志文本，也不是模型自然语言总结。`“模型似乎正在查询订单”`无法被可靠地判断；`WAITING_TOOL`则是程序可以据此控制行为的结构化事实。

一个合格状态至少要满足：

1. **互斥性**：在一个状态机中，任务此刻通常只能处于一个主状态。
2. **可解释性**：运营、开发和后续程序能理解该状态代表什么。
3. **可行动性**：状态决定允许的下一步操作。
4. **可持久化**：进程重启后能够恢复这个事实。
5. **稳定性**：不要为瞬时的内部细节随意增加状态，否则生命周期会失控。

### 3. 状态、事件、动作与状态转移

这四个概念必须分开理解。

| 概念 | 回答的问题 | 示例 |
| --- | --- | --- |
| 状态（state） | 任务现在处于哪里？ | `WAITING_HUMAN` |
| 事件（event） | 发生了什么？ | 审核人点击“批准” |
| 动作（action） | 系统接下来做什么？ | 调用“创建工单”工具 |
| 状态转移（transition） | 状态因此如何变化？ | `WAITING_HUMAN -> RUNNING` |

例如“人工批准创建工单”这个业务过程可以拆开：

```text
当前状态：WAITING_HUMAN
事件：human_approved
动作：恢复任务，允许进入下一步执行
状态转移：WAITING_HUMAN -> RUNNING
```

之后 Agent 可能提出创建工单，系统再执行工具：

```text
当前状态：RUNNING
事件：tool_call_requested(create_ticket)
动作：提交创建工单请求
状态转移：RUNNING -> WAITING_TOOL
```

工具返回成功后：

```text
当前状态：WAITING_TOOL
事件：tool_succeeded
动作：把结果写入任务上下文，继续执行
状态转移：WAITING_TOOL -> RUNNING
```

模型可以参与“建议下一步动作”，但不能代替系统定义状态转移规则。

### 4. 什么是状态机

状态机（Finite State Machine，有限状态机，FSM）是一种描述系统生命周期的模型。它由以下部分组成：

```text
状态集合 S
事件集合 E
允许的状态转移 T
初始状态
终止状态
转移条件（guard）与转移副作用（effect）
```

不必先记数学符号。工程上可以把它理解为一张受限的路线图：

```text
PENDING -> RUNNING -> SUCCEEDED
                  ├-> WAITING_TOOL -> RUNNING
                  ├-> WAITING_HUMAN -> RUNNING
                  ├-> FAILED
                  └-> CANCELLED
```

“受限”是关键。并不是任意状态都能跳到任意状态。例如已经 `SUCCEEDED` 的任务不能再直接回到 `RUNNING`；已经 `CANCELLED` 的任务通常也不能被后台工作线程继续执行。

### 5. 终态、暂态与等待态

设计状态机时，先把状态分成三类会更清晰。

#### 5.1 终态（terminal state）

终态代表此次任务生命周期已经结束，正常情况下不会再向外执行新动作。

常见终态：

- `SUCCEEDED`：目标完成，结果已产生。
- `FAILED`：任务无法完成，已记录失败原因。
- `CANCELLED`：任务被主动终止。
- `EXPIRED`：超过业务时限，不再继续。

终态不一定意味着“再也不能做任何事”。系统可以允许创建一个新任务来“重新执行”，但那应当是新的任务实例，或至少有明确的重开规则，不能悄悄把旧任务改回运行中。

#### 5.2 暂态（transient state）

暂态代表系统正主动执行工作，通常停留时间较短。

- `PENDING`：等待调度器领取。
- `RUNNING`：正在规划、调用工具或处理结果。
- `COMPENSATING`：正在执行补偿操作，例如撤销前一步可撤销的预留。

如果一个任务长期停在 `RUNNING`，它可能没有真正运行，而是工作进程宕机、线程卡死或回调丢失。因此需要超时检测和租约（lease）机制，后续会进一步学习。

#### 5.3 等待态（waiting state）

等待态不是失败，也不是空闲，而是任务主动暂停，等待外部世界给出确定结果。

- `WAITING_TOOL`：等待异步工具或外部系统回调。
- `WAITING_HUMAN`：等待人工批准、拒绝或补充信息。
- `WAITING_INPUT`：等待用户上传文件、选择选项、提供订单号。
- `WAITING_RETRY`：等待重试时间到达。

等待态的价值在于：即使服务重启，系统也知道它没有丢任务，只是在等待特定事件；同时系统不会让 Agent 在缺少条件时胡乱继续。

### 6. 为什么 Agent 比普通接口更需要状态机

普通 CRUD 接口大多是同步、确定、短时间完成的：校验参数，读写数据库，返回结果。即使失败，用户重试一次也常能理解。

Agent 任务则经常同时具备以下特征：

1. **步骤由模型动态选择**：执行路径不是完全预先写死的。
2. **可能跨多个系统**：知识库、业务 API、搜索、消息、审批、数据库。
3. **存在等待**：等待模型、异步工具、人类或用户输入。
4. **运行时间更长**：从数秒到数天都有可能。
5. **有副作用风险**：可能创建工单、发通知、修改数据。
6. **需要审计**：要知道何时、因何、由谁触发了每一步。

没有状态机时，系统只能依赖内存变量或一串日志推测发生了什么。遇到重启、重复请求、网络超时、人工审核，就很难明确下一步是否安全。

## 本节主题系统讲解

### 1. 一个可用的 Agent 任务模型

先不绑定任何框架。一个面向工程的任务记录，通常至少包含以下信息：

```text
task_id                 任务唯一标识
task_type               任务类别，例如 customer_support
status                  当前主状态
input                   经校验后的用户输入
context                 执行过程中的结构化上下文
result                  成功时的最终结果或结果引用
failure                 失败码、失败原因、可否重试
created_at/updated_at   创建和最后更新时间
requested_by            发起用户、租户、来源渠道
trace_id                全链路追踪标识
attempt_count           已执行或重试次数
version                 乐观锁版本号
```

这里的重点不是字段数量，而是职责边界：

- `input` 保存用户最初要解决什么，通常应尽量不可变。
- `context` 保存执行过程中逐步获得的事实，例如已查到的订单摘要、已选择的工具、人工审核决定。
- `result` 保存任务最终对外可见的结果，不应混入过程噪声。
- `failure` 保存机器可读的失败信息，而不只是一段自然语言。
- `status` 是调度、展示、恢复与权限控制共同依赖的核心字段。

### 2. 从“聊天记录”到“任务状态”的重要转换

很多人会把 Agent 的全部状态塞进 messages：用户说了什么、模型说了什么、工具返回了什么。消息历史当然重要，但它不等于任务状态。

例如以下两段对话历史都可能存在：

```text
模型：我将创建工单，需要确认。
用户：同意。
```

仅凭文本，程序很难保证：

- 是哪个用户同意的？是否有权限？
- 同意的是哪一个具体动作？
- 确认是否过期？
- 工单是否已经创建过？
- 任务现在是可以继续、已完成还是已取消？

因此需要把关键控制事实提升为结构化状态和事件，例如：

```text
status = WAITING_HUMAN
pending_action = create_ticket
confirmation_id = confirm_abc
confirmation_status = APPROVED
approved_by = user_001
```

自然语言用于沟通；结构化状态用于控制。二者相互补充，不能互相替代。

### 3. 设计状态机的第一步：先写业务目标和终止条件

不要一开始就列十几个状态。先回答：

1. 一个任务成功的客观标准是什么？
2. 哪些情况必须停止？
3. 哪些情况应该等待，而不是失败？
4. 哪些动作有副作用，必须确认或可补偿？

以“用户咨询订单物流，必要时创建客服工单”为例：

**成功标准**可能是：

- 已向用户返回基于真实订单与物流信息的解释；或
- 经人工/用户确认后，成功创建一张工单并返回工单编号。

**必须停止**的情况可能是：

- 当前用户无权访问订单；
- 连续达到最大尝试次数；
- 任务被取消；
- 发现高风险或不允许的操作。

**应等待**的情况可能是：

- 用户尚未提供订单号；
- 工具异步处理尚未返回；
- 创建工单需要用户确认。

有了这些事实，状态才是为业务服务，而不是为了“看上去完整”。

### 4. 一个典型状态图

下面是一个适合学习的、简化但完整的 Agent 任务状态图：

```text
                         +------------------+
                         |     PENDING      |
                         +---------+--------+
                                   |
                              worker claimed
                                   v
                         +------------------+
              +--------> |     RUNNING      | <--------------------+
              |          +--+---+-----+---+-+                      |
              |             |   |     |   |                        |
              |             |   |     |   +--> completed --> SUCCEEDED
              |             |   |     |
              |             |   |     +--> unrecoverable error -> FAILED
              |             |   |
              |             |   +--> need human --> WAITING_HUMAN
              |             |                            |
              |             |                       approved/input
              |             |                            |
              |             |                            +----------+
              |             |
              |             +--> async tool --> WAITING_TOOL
              |                                      |
              |                                  tool result
              |                                      |
              +--------------------------------------+ 

任何非终态 -- cancel --> CANCELLED
WAITING_* -- deadline exceeded --> EXPIRED 或 FAILED
```

图中最值得注意的不是箭头数量，而是三个规则：

1. `RUNNING` 才能主动安排下一步动作。
2. `WAITING_*` 不能继续执行，需要明确外部事件恢复。
3. 终态不能被普通执行器重新推进。

### 5. 状态转移表比状态图更接近可实现规则

状态图适合沟通，状态转移表适合实现和测试。

| 当前状态 | 事件 | 条件 | 下一状态 | 系统动作 |
| --- | --- | --- | --- | --- |
| `PENDING` | worker_claimed | 任务未取消且未过期 | `RUNNING` | 写入执行租约、开始处理 |
| `RUNNING` | tool_requested | 工具在白名单且参数已校验 | `WAITING_TOOL` 或仍为 `RUNNING` | 执行同步工具或登记异步任务 |
| `WAITING_TOOL` | tool_succeeded | 回调与任务/调用 ID 匹配 | `RUNNING` | 保存观察结果 |
| `WAITING_TOOL` | tool_failed | 失败可重试且未超预算 | `WAITING_RETRY` | 记录失败和下次执行时间 |
| `WAITING_HUMAN` | approved | 审核人有权限且确认未过期 | `RUNNING` | 固化审批证据 |
| `WAITING_HUMAN` | rejected | 审核人有权限 | `CANCELLED` 或 `SUCCEEDED` | 结束或生成替代答复 |
| 非终态 | cancel_requested | 发起人或管理员有权限 | `CANCELLED` | 阻止后续新动作 |
| `RUNNING` | final_answer_ready | 输出通过必要校验 | `SUCCEEDED` | 保存结果 |

注意表中的“条件”。事件本身并不能自动让状态变化。比如有人发来 `approved` 事件，并不意味着一定可执行：还要校验审批对象、审批权限、确认 ID、有效期和任务当前状态。

### 6. 状态机不变量：不能被破坏的规则

不变量（invariant）是无论经历何种路径，都必须成立的规则。它们比“正常流程”更重要，因为系统事故通常发生在边界和异常路径。

常见的 Agent 任务不变量包括：

1. **终态不可被普通流程重新执行**：`SUCCEEDED`、`FAILED`、`CANCELLED` 不能再次执行副作用工具。
2. **等待人工时不能执行待确认动作**：任务处于 `WAITING_HUMAN`，只能等待确认、拒绝、取消或过期。
3. **任务取消后禁止新副作用**：取消与工具提交存在并发时，应以取消标记和执行前再检查降低风险。
4. **工具结果必须可归属**：异步回调必须匹配正确的 `task_id`、`tool_call_id`，不能把 A 任务的结果写进 B 任务。
5. **状态变化必须可审计**：至少记录谁、何时、因何事件从什么状态变成什么状态。
6. **重试受预算约束**：不能因为模型或外部系统反复失败而无限循环。
7. **租户与用户上下文不得丢失**：任务恢复、异步回调、子任务执行时仍需沿用正确的权限边界。

这些规则应该由服务端代码、数据库约束、队列消费者或工作流引擎保障，而不应该只写在 prompt 里。

### 7. 为什么“模型说完成了”不等于任务成功

语言模型可以产生“已经完成”的文本，但任务是否成功必须由系统判断。

下面是错误思路：

```text
模型输出：工单已创建。
系统：将任务标记为 SUCCEEDED。
```

如果实际创建工单的请求还未发出、超时但结果未知、或被权限系统拒绝，这会制造严重的不一致。

更可靠的原则是：

```text
模型负责提出完成意图或总结。
系统依据可验证事实判断任务是否真的完成。
```

例如创建工单成功必须至少有：

- 后端工具返回成功状态；
- 返回了可验证的工单 ID；
- 该结果与当前任务和确认记录匹配；
- 必要时已持久化。

满足后，系统才把状态设为 `SUCCEEDED`，再让模型组织面向用户的自然语言答复。

### 8. 同步工具与异步工具如何影响状态设计

工具调用不一定都需要 `WAITING_TOOL`。关键在于工具是否能在当前执行窗口内可靠地返回。

#### 8.1 同步工具

例如读取订单详情、读取知识库、计算一个简单数值。调用通常在毫秒到数秒内返回：

```text
RUNNING
  -> 调用同步工具
  -> 得到结果
  -> 仍处于 RUNNING，继续规划
```

内部可以有短暂的“工具调用中”日志，但未必需要把它设计为持久化主状态。否则每个极短动作都要写一次状态，复杂度和存储压力会上升。

#### 8.2 异步工具

例如生成大报告、调用耗时数据处理、等待第三方回调、执行需要人工审批的支付流程。其结果不适合由一个 HTTP 请求一直等待：

```text
RUNNING
  -> 登记异步调用
  -> WAITING_TOOL
  -> 外部完成事件 / 轮询发现结果
  -> RUNNING
```

使用等待态后，即使执行进程退出，系统也能在重启后从持久化记录得知：这个任务在等哪个工具、何时发起、是否已经超时。

### 9. 失败不是一种状态那么简单

`FAILED` 是任务的最终状态，但失败本身应被分类。否则系统无法决定是提醒用户、自动重试、转人工，还是立刻告警。

可以从两个维度理解失败：

| 维度 | 分类 | 例子 |
| --- | --- | --- |
| 可恢复性 | 可重试 / 不可重试 | 网络超时 / 参数非法 |
| 责任来源 | 用户输入 / 模型规划 / 工具 / 系统 / 权限 | 订单号缺失 / 模型选错工具 / 第三方 503 / 数据库故障 / 拒绝访问 |

例如：

- 用户没有提供订单号，通常不是 `FAILED`，更适合 `WAITING_INPUT`。
- 订单接口返回 503，可能进入 `WAITING_RETRY`，到达次数上限后才 `FAILED`。
- 模型提出未注册工具，属于受控拒绝；可以记录规划错误后让 Agent 重新规划，或结束为可解释失败。
- 当前用户无权查看订单，是业务上明确的拒绝，不应通过重试解决。

失败码应面向程序稳定分类，例如 `TOOL_TIMEOUT`、`PERMISSION_DENIED`、`MAX_STEPS_EXCEEDED`、`HUMAN_REJECTED`；用户消息则可以更友好，但不应替代失败码。

### 10. 取消不是“把前端页面关掉”

用户关闭浏览器、SSE 断开、HTTP 超时，不代表任务一定应取消。有些任务应该继续，例如用户提交了“生成报告”；有些任务应停止，例如用户取消了一个仍未发送的写操作。

因此要把“连接状态”和“任务取消”分开：

```text
客户端断开：通信通道结束，任务策略由产品决定
用户取消：产生一个可审计的 cancel_requested 事件
任务取消完成：状态进入 CANCELLED，并阻止后续动作
```

取消还涉及“已经发出的副作用怎么办”。例如创建工单请求已发送但未收到响应，系统可能无法立刻知道工单是否创建成功。此时不能简单假设失败并盲目重发，需要配合幂等键、查询确认或补偿流程。

### 11. 幂等性：为什么任务状态机必须关心“重复”

幂等（idempotency）意味着一个操作被重复执行，最终效果与执行一次相同。它在 Agent 场景非常重要，因为以下情况很常见：

- 网络超时，调用方不知道请求是否到达；
- worker 崩溃后重新领取任务；
- 消息队列可能至少投递一次；
- 用户连续点击提交；
- 异步回调被重复发送。

对“查询订单”这类只读动作，重复通常问题不大；对“创建工单”“发送通知”“扣减余额”这类写动作，重复可能造成业务事故。

任务模型通常需要能关联：

```text
task_id
action_id 或 tool_call_id
idempotency_key
external_request_id
```

然后由业务系统保证：相同幂等键的写操作只生效一次，或重复请求返回第一次的结果。状态机不能单独解决幂等性，但它能明确何时创建和复用这些标识。

### 12. 并发与竞争：两个执行器不能同时“拥有”同一任务

设想两个 worker 因为网络抖动或调度错误，同时看到任务 `PENDING`：

```text
Worker A: 读取 task_001，状态 PENDING
Worker B: 读取 task_001，状态 PENDING
Worker A: 执行创建工单
Worker B: 也执行创建工单
```

仅靠“先读取再更新”的普通逻辑不能防止这一点。工程上通常使用以下机制之一或组合：

- **乐观锁**：更新时带上 `version`，只有版本仍匹配才更新成功。
- **条件更新**：例如只允许 `status=PENDING` 的记录更新为 `RUNNING`。
- **悲观锁/行锁**：在短事务内排他领取任务，但不应长时间持锁执行外部工具。
- **租约（lease）**：worker 领取任务后获得有期限的执行权；超时未续约才能被其他 worker 接手。

这些属于实现层知识，但概念上都服务于同一个状态机要求：**某一时刻，一个任务的下一步必须由唯一的、受控的执行者推进。**

### 13. 超时和重试应该成为显式状态，而不是隐藏循环

错误做法是把重试写成不透明循环：

```text
while true:
    call tool
    if success: break
```

问题是：看不到已尝试多少次；进程崩溃后不知道下次是否应重试；不同错误不能采用不同策略；可能无限耗费成本。

更清晰的任务级设计是：

```text
RUNNING
  -> 工具超时
  -> 判断是否可重试、是否仍有预算
  -> WAITING_RETRY（记录 retry_at、attempt_count、失败原因）
  -> 到达 retry_at 后重新进入 PENDING 或 RUNNING
  -> 成功 / 最终 FAILED
```

需要区分三类时间限制：

| 名称 | 限制对象 | 示例 |
| --- | --- | --- |
| 单次调用超时 | 一个模型或工具请求 | 查物流最多 5 秒 |
| 单次运行预算 | 一次 Agent run | 本次推理最多 8 个步骤、60 秒 |
| 任务总时限 | 整个业务任务 | 报告任务必须在 24 小时内完成 |

三者不能互相代替。单次工具不超时，不代表整个任务不会无限等待；总时限很长，也不代表每次请求可以一直挂着。

### 14. 状态机与 Agent Loop 的关系

Agent Loop 关注一次执行过程中的决策循环：

```text
读取状态 -> 推理 -> 选择动作 -> 执行 -> 获得观察 -> 下一轮
```

任务状态机关注这个循环在整个业务生命周期中的位置：

```text
PENDING -> RUNNING -> WAITING_HUMAN -> RUNNING -> SUCCEEDED
```

可以这样理解：

- **Agent Loop 是 `RUNNING` 状态内部的行为机制。**
- **状态机是 Agent Loop 外部的生命周期边界。**

当任务进入 `WAITING_HUMAN` 或 `CANCELLED`，Agent Loop 必须停止或不再被调度；当人工批准后重新进入 `RUNNING`，才允许从已保存状态继续规划。下一节会专门讲 Agent Loop、规划与执行如何在这个边界内运作。

### 15. 任务状态与业务状态不能混为一谈

这是企业系统中很常见的设计错误。

| 状态类型 | 描述对象 | 示例 |
| --- | --- | --- |
| Agent 任务状态 | Agent 是否在运行、等待、成功、失败 | `WAITING_HUMAN` |
| 工单业务状态 | 工单在业务流程中的阶段 | `OPEN`、`IN_PROGRESS`、`RESOLVED` |
| 工具调用状态 | 某一次外部调用的生命周期 | `REQUESTED`、`ACKNOWLEDGED`、`TIMEOUT` |
| 审批状态 | 某项审批决策的状态 | `PENDING`、`APPROVED`、`REJECTED` |

例如“创建工单的 Agent 任务已经成功”，不等于“工单已解决”；它只代表 Agent 成功完成了创建动作。把所有状态混成一个字段，会导致语义混乱、权限规则错误和无法维护的条件分支。

### 16. 从状态机得到可观测性与审计

每次转移都可以形成一条事件记录：

```text
event_id: evt_001
task_id: task_123
from_status: WAITING_HUMAN
to_status: RUNNING
event_type: human_approved
actor_type: user
actor_id: user_001
occurred_at: ...
trace_id: ...
metadata: { confirmation_id: "confirm_abc" }
```

这样可以回答实际生产问题：

- 为什么任务卡住？最后一次状态转移是什么？
- 是谁批准了写操作？批准的对象是什么？
- 为什么重试了三次？每次失败属于哪一类？
- 某个模型版本是否增加了 `WAITING_HUMAN` 的比例？
- 一天内有多少任务因权限拒绝而结束？

这也是为什么状态机不仅是开发细节，还连接了监控、审计、评估、成本控制和运营。

### 17. 一个完整的走读示例：物流问题与人工确认

用户输入：`“A1001 的物流一直没更新，帮我处理。”`

下面按任务状态，而不是按模型文本，走一遍合理流程：

1. 系统创建 `task_001`，状态为 `PENDING`，保存用户、租户、订单号和追踪 ID。
2. worker 原子领取任务，`PENDING -> RUNNING`。
3. Agent 在允许工具中选择查询订单与物流；系统完成权限校验。
4. 同步查询返回后，任务保持 `RUNNING`，上下文记录真实物流事实。
5. Agent 判断需要创建客服工单。由于这是写操作，系统生成待确认动作：`RUNNING -> WAITING_HUMAN`。
6. 用户在界面确认，系统验证确认 ID、用户身份、任务仍未过期；`WAITING_HUMAN -> RUNNING`。
7. 系统使用幂等键调用创建工单工具；如果它是异步流程，则先转为 `WAITING_TOOL`。
8. 工具确认工单创建成功，保存工单 ID；任务重新进入 `RUNNING`。
9. 模型根据已验证事实生成答复，输出经安全/格式校验后，`RUNNING -> SUCCEEDED`。

任何一步出现问题，都不会只靠“模型重新说一次”。例如用户拒绝确认，可进入 `CANCELLED` 或产出“未创建工单”的完成结果；工具临时故障，可进入 `WAITING_RETRY`；订单无权限，则以明确业务结果结束，不应重试。

### 18. 设计时应避免的两种极端

#### 极端一：没有状态机，全部依赖 prompt 和内存

优点是原型快；缺点是任务不可恢复、人工确认无边界、并发不受控、失败不可分类。它只适合一次性、无副作用、无长期价值的演示。

#### 极端二：状态过度细化

例如为模型的每个 token、每次内部推理、每次短暂函数调用都建一个持久化主状态。这样会使转移表爆炸、实现和运维成本升高，而且不一定增加业务价值。

适度原则是：

> 只有当某个阶段会影响恢复、权限、调度、用户可见进度、审计或异常处置时，才值得成为持久化状态。

模型内部思考过程通常不是业务主状态；等待人工、等待异步结果、成功、失败和取消通常是。

## 常见误区

### 误区 1：状态机只适合传统工作流，Agent 不需要

恰好相反。Agent 的执行路径更不确定、工具更多、运行更长，因此更需要外层状态机来约束。

### 误区 2：只要保存聊天 messages，就等于保存了 Agent 状态

messages 可帮助恢复语义上下文，却不能可靠表达权限、审批、幂等键、当前执行权和终态约束。控制状态必须结构化保存。

### 误区 3：任务失败就立刻重试

要先判断失败类型。权限拒绝、参数错误、用户取消、策略拦截等重试无意义；网络抖动或暂时性 503 才可能适合受预算约束的重试。

### 误区 4：用户关闭页面就应该取消任务

页面/连接生命周期与业务任务生命周期不同。是否继续必须按任务类型和产品策略决定，并且取消要成为明确事件。

### 误区 5：`RUNNING` 代表任务一定还活着

任务可能因进程崩溃、网络分区或 worker 卡死而永久停在 `RUNNING`。需要心跳、租约、超时扫描和恢复策略。

### 误区 6：状态转移只要写一个 if/else 就够了

简单任务可以，但必须显式维护“允许从何处到何处、需要什么条件、要记录什么副作用”。随着状态增多，应采用状态转移表、集中校验或工作流引擎，而不是把规则散落在业务代码里。

## 本节练习

### 练习 1：区分对象

用户发起“生成退款政策摘要”，系统调用模型三次，并调用一次文档检索工具。请分别指出：用户请求、业务任务、Agent run、工具调用可能各有几个。

答案：通常有 1 次用户请求，它可以创建 1 个业务任务；任务内可有 3 次 Agent run（取决于实际设计，例如初步规划、补充检索后总结、质量检查），以及 1 次文档检索工具调用。数量不是固定规则，重点是四者生命周期和职责不同。

### 练习 2：设计状态

为“用户提交一份合同，Agent 提取关键条款，风险条款必须由法务审核后才能发送报告”的任务，给出至少五个状态，并指出其中终态和等待态。

答案：可以设计 `PENDING`、`RUNNING`、`WAITING_HUMAN`、`SUCCEEDED`、`FAILED`、`CANCELLED`。其中 `SUCCEEDED`、`FAILED`、`CANCELLED` 是终态；`WAITING_HUMAN` 是等待态。若合同解析是异步服务，还可加入 `WAITING_TOOL`。

### 练习 3：判断非法转移

以下转移哪些应被禁止，并说明原因：

1. `SUCCEEDED -> RUNNING`
2. `WAITING_HUMAN -> RUNNING`，但确认 ID 不匹配
3. `RUNNING -> CANCELLED`
4. `CANCELLED -> WAITING_TOOL`

答案：1 应禁止，因为终态不能被普通执行流程重新启动；如需重做应创建新任务或走明确重开流程。2 应禁止，因为无法证明批准的对象正确，可能造成越权执行。3 通常允许，但取消后要阻止后续新副作用并处理在途调用。4 应禁止，已取消任务不应再登记新的工具等待。

### 练习 4：同步与异步

“查询数据库中的订单详情”和“生成一个耗时 15 分钟的文件分析报告”，它们是否都需要 `WAITING_TOOL`？

答案：通常查询订单是同步短操作，不需要持久化为 `WAITING_TOOL`，在 `RUNNING` 内完成即可。15 分钟报告应异步化，登记外部任务或队列任务后进入 `WAITING_TOOL`，等待回调或轮询结果，避免占住请求和 worker。

## 自测题

### 自测 1：为什么 Agent 的“聊天历史”不能替代任务状态？

答案：聊天历史描述语义交流，难以可靠表达当前执行权、审批有效性、幂等键、是否终态、重试次数、权限上下文等控制事实。任务状态必须是程序可校验、可持久化、可审计的结构化数据。

### 自测 2：`WAITING_HUMAN` 和 `FAILED` 的本质差异是什么？

答案：`WAITING_HUMAN` 表示任务按设计暂停，仍有明确的恢复条件，例如批准、拒绝或补充输入；`FAILED` 表示本次任务已无法继续完成，通常是终态。把“缺少确认”直接当作失败，会丢失恢复和审计能力。

### 自测 3：为什么任务取消后仍可能需要查询外部系统？

答案：取消阻止后续新动作，但对于已发送且结果未知的写操作，系统可能需要查询外部系统确认实际结果，或执行必要补偿。取消不是抹去历史，而是改变后续执行策略。

### 自测 4：状态机不变量举例并说明价值。

答案：例如“终态任务不可被普通流程再次执行”“等待人工时不能执行待确认写操作”“异步结果必须匹配 task_id 与 tool_call_id”。不变量防止异常路径、并发和重复事件绕过业务安全边界。

### 自测 5：Agent Loop 和任务状态机分别解决什么问题？

答案：Agent Loop 解决任务运行期间的“观察、推理、选择动作、执行、再观察”；任务状态机解决整个任务生命周期的“创建、运行、等待、恢复、失败、取消、完成”。前者通常发生在 `RUNNING` 内，后者约束前者什么时候可以执行。

## 本节小结

本节建立了高级 Agent 工程的第一根骨架：把 Agent 当成**可追踪的业务任务**，而不是一段临时模型调用。任务状态机通过状态、事件、转移条件和不变量，让任务在等待、异常、重试、取消、人工确认与恢复时仍保持可控。
