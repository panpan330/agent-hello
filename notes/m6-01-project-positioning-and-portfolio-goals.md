# M6 第 1 节：项目定位和作品化目标

## 本节定位

这一节是 M6 快速作品化阶段的第一节。

M6 的目标不是继续大规模加新功能。

M6 的目标是：

```text
把已经完成的 AI 客服工单系统学习项目，整理成别人能看懂、自己能演示、面试能讲清楚、简历能准确表达的作品项目。
```

所以这一节先解决一个最基础的问题：

```text
这个项目到底是什么？
```

如果这个问题说不清楚，后面的 README、架构图、演示脚本、简历描述都会写散。

你现在最容易卡住的点是：

```text
它不是一个完整生产系统，那它怎么作品化？
```

这一节要给出准确答案：

```text
它不是完整生产系统。
但它是一个完整的 AI 应用工程学习项目和原型系统。
它能展示你对 LLM、RAG、Tool Calling、LangGraph Agent、评测和生产化边界的理解。
所以它可以作品化，但必须诚实定位。
```

这句话非常重要。

M6 不是虚假包装项目。

M6 是把项目真实、清楚、专业地表达出来。

## 二、本节先不做什么

这一节不做这些事：

1. 不改业务代码。
2. 不新增接口。
3. 不启动 Docker。
4. 不真实调用大模型。
5. 不把 Java mock service 改成 Spring Boot。
6. 不写完整 README。
7. 不画架构图。
8. 不写简历最终版。

原因是：

```text
M6 第 1 节先定方向。
方向不清楚，后面写得越多越容易乱。
```

这一节只做三件事：

```text
定义项目是什么。
定义项目不是什么。
定义 M6 要把它整理成什么样。
```

## 三、基础知识铺垫

### 1. 什么是项目定位

项目定位就是回答：

```text
这个项目是什么？
它面向什么场景？
它解决什么问题？
它用什么技术路线？
它当前完成到什么程度？
它还没有完成什么？
```

项目定位不是项目名字。

比如：

```text
AI 客服助手
```

这是名字。

但它没有说清楚项目范围。

更完整的定位应该是：

```text
一个面向客服场景的企业知识库 RAG + 智能工单 Agent 原型系统。
```

这句话比“AI 客服助手”更准确。

它说明了：

```text
业务场景：客服
核心能力：企业知识库 RAG + 智能工单 Agent
当前成熟度：原型系统
```

项目定位越准确，后面的表达越稳。

### 2. 什么是作品化

作品化不是把项目吹得更厉害。

作品化是：

```text
把已经做过的内容整理成别人能理解、能运行、能评估你能力的形式。
```

作品化通常包括：

```text
README
架构图
流程图
运行说明
演示脚本
测试说明
技术亮点
项目边界
后续路线
面试讲稿
简历描述
```

如果没有作品化，一个项目可能只有你自己知道价值。

别人打开仓库只会看到：

```text
很多文件
很多笔记
很多目录
不知道从哪看
不知道怎么运行
不知道核心能力是什么
不知道你到底学会了什么
```

作品化的意义就是把这些内容整理出来。

### 3. 作品化不等于生产上线

这是你现在最应该分清楚的点。

作品化：

```text
让项目可以展示、可以讲解、可以证明学习成果。
```

生产上线：

```text
让项目真正服务真实用户、真实数据、真实流量和真实故障。
```

两者不是一回事。

一个项目可以作品化，但还没生产上线。

比如：

```text
毕业设计
开源学习项目
技术原型
面试作品
架构验证项目
```

这些都可以作品化。

但它们不一定是完整生产系统。

当前项目就属于：

```text
AI 应用工程学习项目 + 原型系统 + 作品项目
```

而不是：

```text
已经正式上线的商业客服系统
```

### 4. 为什么不完整也可以作为作品

一个技术作品的价值，不只看它是不是完整商业产品。

还要看它能不能展示技术能力。

当前项目虽然没有真实前端、真实数据库、真实登录权限和真实上线环境，但它已经展示了很多 AI Agent 工程能力：

```text

结构化输出
Tool Calling
工具权限边界
RAG
Embedding
Qdrant
Milvus
LangGraph Agent
Human-in-the-loop
checkpoint/thread_id

bad case analysis

Docker Compose
health/readiness

```

这些能力已经足够说明：

```text
你不是只会调一个聊天 API。
```

你学的是：

```text
怎样把 AI 能力放进一个后端工程系统里。
```

这就是作品价值。

### 5. 为什么必须诚实说明项目边界

作品化时最忌讳的是夸大。

不要把当前项目说成：

```text
完整生产级 AI 客服系统
```

因为别人一问：

```text
用户登录在哪？
权限表在哪？
订单表在哪？
工单表在哪？
真实 Spring Boot 服务在哪？
生产监控在哪？
压测结果在哪？
线上地址在哪？
```

如果答不上来，就会显得不真实。

更专业的说法是：

```text
这是一个面向客服场景的 AI 应用工程原型系统。
当前重点展示 RAG、Tool Calling、LangGraph Agent、评测和生产化设计能力。
它还没有接入完整生产认证、真实数据库、前端工作台和线上部署。
```

这叫边界意识。

边界意识不是缺点。

边界意识是工程能力的一部分。

### 6. 学习项目、作品项目、生产项目的区别

可以这样区分：

| 类型 | 核心目的 | 典型特点 |
| --- | --- | --- |
| 学习项目 | 帮自己学会知识 | 笔记多、代码随学习推进、重点是理解 |
| 作品项目 | 帮别人看懂你的能力 | README 清楚、架构图清楚、演示路径清楚、边界清楚 |
| 生产项目 | 服务真实用户和业务 | 有真实数据、权限、监控、部署、告警、运维和 SLA |

当前项目现在处于：

```text
学习项目 -> 作品项目
```

还没到：

```text
作品项目 -> 生产项目
```

M6 做的是第一步转换。

M6 后面真实化阶段才是第二步转换。

### 7. 为什么先作品化，再真实化

你可能会问：

```text
既然项目还不完整，为什么不先继续做真实化？
```

原因是：

```text
当前项目已经积累了大量学习成果，如果不先整理，会越来越难讲清楚。
```

继续加技术当然可以。

但如果现在不整理，会出现：

```text
README 越来越旧
笔记越来越多但入口不清楚
项目定位越来越模糊
面试时不知道该讲哪条主线
后续学习方向容易散
```

所以先用 M6 做一次快速作品化。

它不会花太久。

它的价值是：

```text
把已有成果收束成一个清楚的作品底座。
```

然后再进入：

```text
阶段 7：真实 Java Spring Boot + MySQL/Redis 业务服务
```

这样后面真实化改造也更有方向。

### 2. 当前项目完整定位

完整定位可以这样写：

```text
本项目是一个面向客服业务场景的 AI 应用工程原型系统。

它使用 Python FastAPI 构建 AI 服务，结合 LLM API、RAG、Tool Calling 和 LangGraph，实现企业知识库问答、订单查询和智能工单创建流程。

Java mock service 用来模拟业务后端，向 Python AI 服务提供订单查询和工单创建接口。

项目重点不只是完成聊天功能，而是学习并落地 AI 应用工程中的结构化输出、工具权限边界、用户确认、Agent 状态管理、自动化评测、可观测性、稳定性保护、Docker Compose 编排和 CI 回归。

```

这段可以作为后面 README 的基础文案。

### 3. 当前项目解决什么问题

项目模拟的是客服场景里的三个问题：

```text
问题 1：用户问企业政策，模型本身不知道公司内部规则。
问题 2：用户问订单状态，AI 不能直接查数据库，需要调用业务服务。
问题 3：用户要投诉或处理问题，AI 不能直接创建工单，必须收集字段并等待用户确认。
```

对应解决方案：

```text
RAG 解决企业知识库问答。
Tool Calling 解决受控业务系统调用。
LangGraph Agent 解决多步骤工单流程编排。
Human-in-the-loop 解决写操作确认。
Eval 和 regression 解决 AI 效果验证。
生产化策略解决可追踪、可兜底、可回归。
```

这就是项目主线。
