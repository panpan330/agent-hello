# M13 第 2 节：CPU、GPU、显存与模型运行资源

## 本节定位

上一节说明了模型如何将文本转成 token，并逐 token 生成输出。现在自然会出现一个工程问题：这么多模型参数、上下文和生成状态究竟存在哪里、由什么硬件计算？为什么云端模型服务通常使用 GPU？为什么下载一个模型后常看到“显存不足（OOM）”？为什么同样的模型在不同机器上速度差异巨大？

本节的目标不是让你背显卡型号或立刻搭建 GPU 服务器，而是建立模型运行的硬件地图：

```text
磁盘：长期保存模型文件和数据
CPU 内存（RAM）：操作系统、程序、部分模型/缓存的工作空间
GPU 显存（VRAM）：高吞吐模型计算所需的权重和中间状态
CPU/GPU：真正执行计算的处理器
网络：云模型调用、分布式服务和模型文件传输
```

理解这张地图之后，你就能读懂后续量化、推理引擎、批处理、KV Cache、容器 GPU、扩缩容和 Kubernetes GPU 调度的前提条件，也能判断“某个模型是否能跑在某台机器上”时到底该问哪些问题。

## 本节学习目标

学完后，你应当能：

1. 区分 CPU、GPU、RAM、VRAM、磁盘和网络在模型推理中的职责。
2. 解释 GPU 为什么通常更适合大模型推理，但 CPU 并非没有价值。
3. 理解模型运行时显存/内存的主要构成：权重、KV Cache、临时计算空间、运行时开销。
4. 用近似公式估计模型权重的最低存储/显存需求。
5. 说明参数精度、量化、上下文长度、并发和输出长度为什么影响显存。
6. 区分“模型加载失败”“GPU OOM”“CPU OOM”“磁盘不够”“性能慢”等不同问题。
7. 知道硬件选型不能只看显存，也要看计算能力、带宽、并发、部署目标和成本。

## 一句话先讲透

> 模型推理需要同时保存权重和每个请求的上下文计算状态；GPU 之所以常用，是因为它能并行完成大量矩阵计算并以高带宽读取显存，但显存容量、精度、上下文长度、并发请求和运行时开销共同决定一个模型能否稳定运行，而不是只看“显卡有多少 GB”。

## 基础知识铺垫

### 1. 先认识五类资源

模型服务运行时最常遇到的资源，不是只有 GPU。可以先用一张表建立直觉：

| 资源 | 它像什么 | 主要用途 | 典型限制 |
| --- | --- | --- | --- |
| 磁盘/SSD | 仓库 | 保存模型文件、容器镜像、日志、数据、缓存 | 容量、读写速度 |
| CPU | 通用指挥与计算中心 | 处理请求、tokenizer、网络、调度、部分推理 | 核数、频率、内存带宽 |
| RAM | CPU 的工作台 | 操作系统、应用、文件缓存、CPU 推理、模型加载中转 | 容量、带宽 |
| GPU | 大规模并行计算器 | 高吞吐矩阵运算、模型推理/训练 | 计算能力、显存、显存带宽 |
| VRAM（显存） | GPU 的工作台 | 模型权重、KV Cache、临时张量、批处理状态 | 容量、带宽、碎片 |

网络也很重要：使用云模型 API 时，模型运行在远端 GPU，用户侧更关心网络、请求排队和供应商服务；自部署时，网络还影响模型文件下载、网关调用、分布式推理和存储访问。

### 2. CPU 是什么，为什么它仍然不可替代

CPU（Central Processing Unit，中央处理器）擅长执行复杂、分支多、控制逻辑强的通用任务。它通常拥有较少但更强的计算核心，适合：

- 运行操作系统、Web 服务、数据库客户端、队列 worker；
- 处理 HTTP 请求、认证、权限、日志和任务状态机；
- 执行 tokenizer、文本预处理、JSON/schema 校验；
- 调度 GPU 工作、管理内存和网络；
- 在模型较小、并发较低时直接进行推理；
- 运行不需要 GPU 的传统业务逻辑。

即使模型主要在 GPU 上推理，CPU 也不是闲置的。一个模型服务可能因为 CPU 太弱、tokenizer 太慢、网络线程不足、数据预处理阻塞而无法充分利用 GPU。

### 3. GPU 是什么，为什么它适合模型计算

GPU（Graphics Processing Unit，图形处理器）最初为图形渲染设计，后来因其大规模并行计算能力被广泛用于机器学习。

一个直觉对比：

```text
CPU：少量强核心，擅长复杂流程和不同任务的快速切换
GPU：大量较小计算单元，擅长对大量相似数据同时做相同类型运算
```

神经网络推理中最核心的计算往往是矩阵乘法、向量运算和张量操作。它们具有高度并行性：大量数字可以同时按同一种规则计算。GPU 正好适合这类工作。

例如可以把一次大型矩阵乘法想成：

```text
很多行、很多列的数字配对相乘再求和
```

GPU 能同时处理大量这类相似运算，因此在大模型推理和训练中通常比通用 CPU 快得多。

### 4. GPU 不是“更快的 CPU”

GPU 与 CPU 擅长的事情不同。GPU 在以下场景不一定占优：

- 任务规模很小，数据传输/启动开销超过并行收益；
- 逻辑分支极多、每个任务都不一样；
- 程序主要在等待网络、磁盘或数据库；
- 模型极小、低并发、对延迟要求不高；
- 运行环境或软件不支持 GPU 加速。

对个人学习、小模型、离线实验，CPU 推理可能完全可用，只是速度较慢。对高并发、较大模型、实时用户服务，GPU 通常才体现出决定性价值。

### 5. RAM 与 VRAM：两个不同的工作空间

RAM 是系统内存，CPU 可以直接高效访问；VRAM 是 GPU 专用的显存，GPU 可以高效访问。

它们不是同一种资源，不能简单相加理解为“总内存”。

```text
CPU 访问 RAM 很快
GPU 访问 VRAM 很快
CPU <-> GPU 之间传数据需要经过总线/互联，通常比各自本地访问慢
```

模型若要在 GPU 上高效推理，关键权重和推理状态通常需要放到 VRAM 中。若 VRAM 不够，某些方案可将部分权重/缓存放到 RAM，称为 CPU offload 或分层卸载，但这通常会显著降低速度，并增加系统设计复杂度。

### 6. 显存不是显卡的全部能力

模型能否运行，显存容量确实是第一道硬门槛，但不是全部：

| GPU 特征 | 为什么重要 |
| --- | --- |
| 显存容量 | 是否放得下权重、KV Cache 和运行时空间 |
| 显存带宽 | 读取权重/状态速度，影响 token 生成速度 |
| 计算能力 | 矩阵运算吞吐，影响 prefill/训练等计算密集阶段 |
| 精度支持 | 对 FP16、BF16、INT8 等计算和存储的支持情况 |
| GPU 间互联 | 多 GPU 时通信效率 |
| 软件生态 | 驱动、运行时、推理引擎是否支持 |
| 稳定性与运维 | 长时间运行、监控、散热、虚拟化/容器支持 |

“显存够了”只说明有可能加载，并不保证推理速度、并发能力或生产稳定性符合需求。

### 7. 为什么大模型需要这么多存储空间

模型有数十亿乃至更多参数，每个参数要以某种数值精度保存。假设一个参数用 2 字节保存，粗略计算：

```text
模型权重大小（字节）
≈ 参数数量 × 每个参数字节数
```

例如一个约 7B 参数模型若使用 16 位精度（约 2 字节/参数）：

```text
7,000,000,000 × 2 字节
≈ 14 GB
```

这只是权重本身的理想近似，尚未包含：

- 模型配置与 tokenizer；
- 推理引擎自身开销；
- 临时计算张量；
- KV Cache；
- 显存碎片与预留空间；
- 多并发请求状态；
- 可能的图优化/编译缓存。

因此“14GB 权重”不意味着 14GB 显存一定能稳定运行。实际部署必须留安全余量。

### 8. 数值精度（Precision）的直觉

模型参数是浮点或量化数值。常见精度概念包括：

| 表示 | 近似每参数存储 | 特点 |
| --- | --- | --- |
| FP32 | 4 字节 | 精度高，内存/显存占用大 |
| FP16 | 2 字节 | 常见半精度，较省资源 |
| BF16 | 2 字节 | 常用于深度学习，数值范围特点不同 |
| INT8 | 约 1 字节 | 量化后更省存储/显存，可能有精度代价 |
| 4-bit 等更低位表示 | 约 0.5 字节或更多元数据 | 更节省，但实现和质量权衡更复杂 |

这里先有两个正确结论：

1. 精度越低，权重通常越省空间；
2. 精度越低不代表必然更快、更便宜或质量完全不变，需看硬件、推理引擎、模型、量化方法和任务。

量化会在 M13-03 系统学习，本节只需要理解“参数占用多少字节”是硬件资源估算的第一步。

## 本节主题系统讲解

### 1. 模型推理时，显存里到底放了什么

将“模型占显存”拆开，通常至少包含四类主要内容：

```text
1. 模型权重（weights）
2. KV Cache（每个活跃请求的上下文状态）
3. 临时计算空间（activations/workspace）
4. 推理引擎、运行时和碎片预留
```

这四类内容共同决定显存使用量。

#### 1.1 模型权重

权重通常是最稳定、最容易估算的部分。模型启动后，推理引擎会将它们从磁盘读入 RAM/VRAM 或分层存放。权重越大、精度越高，占用越多。

#### 1.2 KV Cache

KV Cache 是生成式 Transformer 模型为避免重复计算历史 token 而保存的键/值缓存。它会随：

- 上下文长度；
- 活跃并发请求数；
- 模型层数/隐藏维度；
- 使用的 KV 精度；
- 已生成输出 token 数；

而增长。

KV Cache 是理解“模型明明能加载，为什么多几个用户就 OOM”的关键。后续 M13-04 会详细讲它的工作原理和性能意义。

#### 1.3 临时计算空间

推理过程中，某些矩阵计算、批处理、注意力运算和框架内部操作需要临时张量/workspace。它不一定像权重那样固定，也可能随 batch、序列长度和引擎优化策略变化。

#### 1.4 运行时开销与碎片

GPU 驱动、CUDA/运行时、深度学习框架、推理引擎和显存分配器都会有开销。显存可能还因频繁分配释放产生碎片，导致“理论总量够，但找不到足够连续空间”。因此生产部署不应把显存按 100% 用满。

### 2. 一个近似显存账本

可用概念公式理解单 GPU 推理显存：

```text
总 VRAM 需求
≈ 权重显存
+ KV Cache 显存
+ 临时计算显存
+ 框架/运行时开销
+ 安全余量
```

其中：

```text
权重显存
≈ 参数量 × 每参数字节数
```

这个公式不能给出百分百精确数字，但足以指导初步判断：

- 模型为什么加载不上；
- 量化为什么能帮助；
- 上下文和并发为什么会挤占显存；
- 为什么部署必须预留余量；
- 为什么仅看模型文件大小不够。

### 3. 模型文件大小、RAM 占用与 VRAM 占用的区别

以下三个指标很容易混淆：

| 指标 | 发生位置 | 含义 |
| --- | --- | --- |
| 磁盘文件大小 | SSD/HDD | 下载/存储模型产物需要多少空间 |
| RAM 占用 | CPU 内存 | 加载、缓存、CPU 推理、应用和数据处理需要多少系统内存 |
| VRAM 占用 | GPU 显存 | GPU 推理实际运行权重/缓存/临时计算需要多少显存 |

例如一个模型文件可能在磁盘上是 8GB，加载过程中暂时需要更多 RAM；如果在 GPU 上用不同精度运行，VRAM 占用可能又是另一数值。模型格式、压缩、加载方式、量化和引擎策略都会影响三者。

不要因为磁盘还剩很多空间就认为模型一定能运行，也不要因为系统 RAM 很大就认为能替代 GPU 显存。

### 4. CPU 推理、GPU 推理与 Offload

#### 4.1 CPU 推理

模型权重和计算主要在 RAM/CPU 上进行。优点是硬件门槛低，不一定需要独立 GPU；缺点是大模型/长上下文/高并发下速度通常明显较慢。

适合：

- 学习 tokenizer、模型文件和本地推理概念；
- 小模型、低频离线任务；
- 没有可用 GPU 的原型；
- 对速度要求不高的实验。

#### 4.2 GPU 推理

权重和主要计算放在 GPU/VRAM，利用 GPU 并行矩阵计算和高带宽。优点是更适合大模型、高吞吐、较低延迟；代价是显存、驱动、运行环境和硬件成本。

#### 4.3 CPU/GPU Offload

当显存不足时，某些运行方式允许部分权重或缓存放在 RAM，由 GPU 处理另一部分。它能让较大模型“勉强运行”，但数据在 CPU 与 GPU 之间搬运通常会带来性能损失。

Offload 是资源折中，不是免费扩容。对于个人学习可有意义；对高并发生产服务，应更慎重评估延迟和稳定性。

### 5. 数据传输为什么会成为瓶颈

CPU 与 GPU 分属不同的计算/内存域。数据在 RAM 与 VRAM 之间传输要经过硬件互联，速度通常远低于 GPU 在本地 VRAM 中读取数据的速度。

因此：

- 将模型每一层来回在 CPU/GPU 间搬运会很慢；
- 频繁把大批输入/输出复制会影响延迟；
- GPU 空闲不一定说明模型计算不够，可能在等待 CPU、数据准备或传输；
- 多 GPU 推理也会因 GPU 间通信而产生额外成本。

从系统视角看，性能由最慢环节决定。强 GPU 配弱 CPU、慢磁盘、拥塞网络或低效数据管线，都可能得不到预期速度。

### 6. GPU 为什么特别重视显存带宽

对大语言模型的逐 token 生成，模型往往需要反复读取大量权重并进行计算。若读取权重的速度受到显存带宽限制，GPU 的理论计算能力可能无法完全发挥。

简单直觉：

```text
计算能力：一次能做多少运算
显存带宽：每秒能把多少数据送到计算单元
```

若“数据送不够快”，计算单元就会等待。不同推理阶段、模型大小、batch 和硬件架构下，瓶颈可能偏计算或偏带宽。你不需要现在精确判断，但要知道“显存容量”和“显存带宽”是不同维度。

### 7. 为什么上下文长度会增加显存

上一节学习了模型会逐 token 生成，并需要看到历史上下文。若每生成一个 token 都重新计算全部历史，成本会非常高。Transformer 推理通常通过 KV Cache 保存每层注意力机制所需的历史键和值表示。

直觉上：

```text
上下文越长
-> 需要缓存的历史 token 越多
-> KV Cache 越大
-> 每个活跃请求占用更多显存
```

这意味着上下文窗口不是“越大越没有代价”。即使模型权重已加载完成，超长会话、超多 RAG chunk 或长文档处理仍会占用更多 KV Cache，并降低可并发服务的请求数。

### 8. 为什么并发会增加显存

模型权重通常可由多个请求共享：同一实例不需要为每个用户再复制一套完整权重。但每个活跃请求需要自己的上下文/KV Cache、输入输出状态和部分临时空间。

```text
1 个用户请求：权重 + 1 份 KV Cache
10 个并发请求：权重 + 10 份 KV Cache
100 个并发请求：权重 + 100 份 KV Cache
```

所以模型服务扩容的难点不只是“能否加载一个模型”，还包括：

- 预计最大并发多少？
- 每个请求最大上下文多长？
- 每个请求最大输出多少？
- 是否使用长思考/多轮 Agent？
- 是否需要支持流式长连接？
- 何时排队、限流或扩容？

这些问题将在性能、网关与容量章节继续展开。

### 9. 为什么输出长度也会影响显存和资源

输出 token 会不断追加到当前序列，因此通常也会增长 KV Cache。用户请求开始时上下文可能很短，但如果模型持续生成很长的报告，KV Cache、时间、成本和连接占用都会逐渐增加。

这就是为什么：

- 输出上限不仅是内容控制，也是资源控制；
- 长报告适合异步任务和明确预算；
- Agent Loop 多轮工具结果会不断扩展上下文；
- 流式输出改善体验，但并不减少生成本身的计算成本。

### 10. Batch（批处理）与硬件利用率的直觉

GPU 擅长同时做大量相似计算。若每次只处理一个很小请求，可能无法充分利用 GPU；将多个请求合并为 batch，有机会提高整体吞吐。

但 batch 也有权衡：

| 好处 | 代价 |
| --- | --- |
| 更充分利用 GPU | 某些请求需等待凑 batch，增加延迟 |
| 提高整体吞吐 | 显存占用增加 |
| 降低每 token 平均开销 | 不同长度请求调度更复杂 |
| 更适合批量任务 | 交互式首字体验可能变差 |

现代推理引擎通常会做动态/连续批处理，让不同请求在生成过程中更灵活地共享计算资源。M13-04 会专门讲批处理、吞吐和调度；本节只要知道 batch 会同时影响计算利用率和显存需求。

### 11. GPU OOM（显存不足）是什么

OOM 是 Out Of Memory 的缩写。GPU OOM 表示推理引擎或框架在 GPU 显存中无法为所需数据分配足够空间。

可能原因：

- 模型权重本身就超过显存；
- 模型精度太高，未量化；
- 上下文窗口设置太大；
- 并发请求过多；
- 单请求输出过长；
- batch 太大；
- KV Cache 预留太多；
- 显存被其他进程占用；
- 显存碎片使连续空间不足；
- 推理引擎运行时开销未被估算。

OOM 不是“模型不适合做这个任务”的直接结论，而是当前硬件、精度、上下文、并发和引擎配置组合无法满足资源需求。

### 12. GPU OOM 的处理思路

遇到 OOM 时，不应先盲目反复重启。应按“账本”排查：

1. 当前 GPU 还有多少可用显存，是否被其他进程占用？
2. 权重以什么精度/量化方式加载？
3. 模型参数量与显存是否基本匹配？
4. 上下文窗口、最大输出和并发/batch 设置是多少？
5. KV Cache 是否预留过大？
6. 是否可缩短上下文、限制输出、降低并发？
7. 是否可用更低精度量化、较小模型、更多/更大 GPU，或 CPU offload？
8. 是否存在显存泄漏或未释放的旧任务？

处理策略应与目标匹配：个人测试可降低上下文和并发；生产服务可能要做队列、限流、模型路由、扩容或采用更合适的硬件/引擎。

### 13. CPU OOM 与 GPU OOM 的区别

| 问题 | 资源不足位置 | 常见表现 | 典型处理方向 |
| --- | --- | --- | --- |
| CPU OOM | 系统 RAM | 进程被系统杀死、内存分配失败、整机卡顿 | 增加 RAM、减少并发/数据、优化加载/缓存 |
| GPU OOM | GPU VRAM | GPU 框架报显存分配失败、模型无法加载 | 降精度、缩上下文/并发、换 GPU/模型 |
| 磁盘不足 | SSD/HDD | 下载/写缓存/日志失败 | 清理、扩容、分层存储 |
| CPU 过载 | CPU 计算/线程 | tokenizer、网络、调度慢，GPU 等待 | 增加 CPU、优化并发/预处理 |
| GPU 利用低 | 可能是供给不足或小 batch | 模型速度未达预期 | 查 CPU/网络/数据搬运/调度 |

排障时要先确定瓶颈位置。将 GPU OOM 当作“内存不够”而去扩系统 RAM，通常无法直接解决；将 CPU tokenization 瓶颈误认为“GPU 不够强”，也会造成错误采购。

### 14. 显存碎片：为什么“剩余显存看着够”仍可能 OOM

程序不断申请和释放不同大小的显存块后，空闲显存可能被分成许多不连续碎片。某次操作需要一块较大的连续空间时，即使总空闲量看似足够，也可能分配失败。

实际表现依赖框架和分配器，但工程启示是：

- 长时间运行、高频不同长度请求的服务需要关注显存分配策略；
- 不要将显存长期压到极限；
- 遇到异常 OOM 要检查并发、缓存、旧进程和分配行为；
- 通过合理的 batch、上下文上限、引擎配置和实例重启/滚动更新控制风险。

这不是要求初学者自己手写显存分配器，而是避免把“剩余显存总数”当作唯一真相。

### 15. 模型加载慢与推理慢是不同问题

模型服务的时间可以拆分：

| 阶段 | 做什么 | 主要受什么影响 |
| --- | --- | --- |
| 下载模型 | 从网络/对象存储获取权重 | 网络、镜像/缓存、文件大小 |
| 加载模型 | 从磁盘读入 RAM/VRAM，初始化运行时 | SSD、CPU、PCIe/互联、权重大小 |
| 首次预热 | 编译、缓存、内核初始化等 | 引擎、驱动、硬件、配置 |
| 单请求 prefill | 处理输入上下文 | GPU/CPU、输入 token、带宽 |
| 单请求 decode | 逐 token 生成 | GPU、显存带宽、模型、输出长度 |
| 高并发运行 | 调度多个请求 | KV Cache、batch、队列、限流 |

因此“模型启动要五分钟”和“用户回答要十秒”不是同一问题，优化手段也不同。部署/运维阶段需要分别观测。

### 16. GPU 利用率不能单独说明系统健康

监控中常会看到 GPU utilization（利用率）、显存使用量、温度等指标。它们有价值，但要结合上下文解释：

- GPU 利用率低，可能是没有请求，也可能是 CPU/tokenizer/网络/队列瓶颈；
- GPU 利用率高，可能是健康高吞吐，也可能是请求积压、错误循环或资源饱和；
- 显存占用高，可能是模型和 KV Cache 正常驻留，也可能是泄漏或配置过度预留；
- 显存占用低，可能是小模型/低并发，也可能是模型未真正使用 GPU。

完整观测需结合请求数、TTFT、TPOT、队列长度、错误率、token 使用、CPU/RAM、网络和成本指标。M13-11 会系统讨论观测与容量。

### 17. 单 GPU、多 GPU 与分布式推理的直觉

若一个模型或目标并发超出单 GPU 能力，可以使用多个 GPU，但有不同模式：

| 方式 | 核心思想 | 适用直觉 |
| --- | --- | --- |
| 多副本（replica） | 每张 GPU 跑一份模型，分流请求 | 模型单卡放得下，需要更高并发 |
| 模型并行 | 将一个模型拆到多张 GPU | 模型单卡放不下或需要更大实例 |
| 数据/请求并行 | 不同请求交给不同资源处理 | 提高吞吐 |
| 分布式服务 | 多机器、多实例协作 | 更大规模、弹性与高可用 |

多 GPU 不等于显存可以毫无代价简单相加。模型并行需要 GPU 间通信，通信带宽和拓扑会影响性能；多副本则要求每张 GPU 都能放得下完整模型。后续部署和 Kubernetes 阶段会在更高层讨论调度与扩缩容。

### 18. 硬件选型的正确问题顺序

不要先问“哪张显卡最好”，而应先问：

1. 使用云 API、个人本地学习，还是自部署生产服务？
2. 模型是什么规模、什么精度、是否允许量化？
3. 最大上下文长度、最大输出长度和目标并发是多少？
4. 更看重首字延迟、总吞吐还是离线批处理能力？
5. 是否需要 embedding、rerank、OCR、视觉模型等额外工作负载？
6. 数据治理是否要求本地/内网部署？
7. 预算包括硬件、云 GPU、存储、网络、电力、运维和冗余吗？
8. 是否需要高可用、灰度、故障转移、多租户隔离？

只有这些问题明确后，显存、GPU 数量、CPU、RAM、SSD、网络和部署方式才有实际意义。

### 19. 一个近似估算例子

假设有一个约 7B 参数的模型。仅做概念估算：

| 权重表示 | 理想权重大小近似 | 实际部署时还要考虑 |
| --- | --- | --- |
| FP32（4 字节/参数） | 约 28GB | KV Cache、运行时、临时空间、余量 |
| FP16/BF16（2 字节/参数） | 约 14GB | 同上 |
| INT8（约 1 字节/参数） | 约 7GB | 量化元数据、引擎实现、KV Cache |
| 4-bit（约 0.5 字节/参数） | 约 3.5GB | 分组/缩放元数据、性能/质量权衡 |

这些只是“参数数 × 每参数字节”的粗估，不能作为采购或上线保证。例如 INT8/4-bit 实际文件和运行占用通常大于理想值；上下文和并发仍需额外显存；不同量化格式/引擎的支持程度不同。

这个例子真正要教会你的不是具体数字，而是估算方法和“权重之外还有大量运行时资源”的意识。

### 20. 一个实际任务走读：为什么 Agent 比普通短问答更吃资源

用户问：`“帮我分析这份长合同，找出风险，并生成报告。”`

与短聊天相比，资源压力可能来自：

```text
长文档抽取/分块 -> CPU、磁盘、可能的 OCR
RAG 检索与 rerank -> CPU/GPU/向量库资源
长上下文与多个引用 -> 输入 token 和 KV Cache
多轮 Planner/Executor/Critic -> 多次模型调用
长报告输出 -> 输出 token、decode 时间和 KV Cache
并行子任务 -> 并发显存、队列和预算
```

这解释了为什么企业 Agent 系统需要任务队列、上下文预算、模型网关、成本控制和异步执行。模型资源不是孤立的 GPU 问题，而是整个任务链路的容量问题。

### 21. 面向应用工程师的资源控制策略

即使你不管理底层 GPU，也可在应用层控制资源：

- 为请求设置最大输入、输出和 Agent 步数；
- 对 RAG chunk 数、长度、工具结果设置预算；
- 对长任务采用异步队列和并发上限；
- 对不同用户/租户做速率和成本配额；
- 路由简单任务到更小/更便宜模型；
- 对高成本任务要求确认或离线执行；
- 记录 token、延迟、工具次数和失败原因；
- 发生资源紧张时进行排队、降级、拒绝低优任务或回退。

这说明硬件资源管理与 M12 的任务状态、队列、预算、背压并不分离。模型服务只是把资源限制变得更具体。

## 常见误区

### 误区 1：系统内存大，就能替代 GPU 显存

不对。RAM 与 VRAM 位于不同硬件域，GPU 高效推理通常需要在 VRAM 中访问权重和状态。CPU offload 可作为折中，但常显著影响性能，不能将 RAM 与 VRAM简单相加。

### 误区 2：模型文件大小等于所需显存

不对。模型文件只是磁盘上的产物；GPU 推理还需要 KV Cache、临时张量、运行时开销、显存余量和并发请求状态。实际所需显存通常更高且与配置有关。

### 误区 3：显存够放下权重，就一定能支持任意上下文和并发

不对。上下文长度、输出长度和并发都会增长 KV Cache；batch 和临时空间也占用显存。单用户能跑不代表高并发服务能跑。

### 误区 4：GPU OOM 只要重启就能解决

重启有时能释放残留显存或缓解碎片，但如果根因是模型太大、精度过高、上下文/并发配置超出资源，重启后仍会发生。应按显存账本排查。

### 误区 5：GPU 利用率越高，模型服务越健康

不一定。高利用率可能是高效服务，也可能是积压或异常循环；低利用率可能是低流量，也可能是 CPU/网络/调度瓶颈。需要结合延迟、队列、错误、显存和 token 指标判断。

### 误区 6：量化一定既更快又完全不损失质量

量化通常节省存储/显存，但实际性能和质量取决于模型、量化算法、硬件、推理引擎和任务。它是工程权衡，不是免费优化。

### 误区 7：只要买更强 GPU，就不需要做上下文和并发控制

硬件会提高容量，但输入无限增长、输出无限长、并发无限制、Agent 无限循环仍会耗尽资源和成本。应用层预算、队列、限流和任务边界永远需要存在。

## 本节练习

### 练习 1：区分资源职责

请分别指出下列任务主要依赖 CPU、RAM、GPU、VRAM 或磁盘中的哪些资源：

1. 从 SSD 加载模型权重文件。
2. 将用户文本切分为 token，并进行 JSON 参数校验。
3. 对大模型执行矩阵计算、生成下一个 token。
4. 为 50 个长上下文并发请求保存历史注意力状态。
5. 保存模型镜像、下载缓存和任务产物。

答案：1 主要依赖磁盘读取、RAM 中转和 CPU 调度，之后可能传到 VRAM。2 主要依赖 CPU 与 RAM。3 主要依赖 GPU 与 VRAM。4 主要依赖 VRAM 中的 KV Cache（也可能有部分卸载到 RAM）。5 主要依赖磁盘。实际系统中资源会协作，但应先抓住主导资源。

### 练习 2：估算权重大小

一个约 13B 参数模型以 FP16 存储，按 2 字节/参数做理想估算，权重约需要多少 GB？为什么这不能直接作为最小显存结论？

答案：约 `13B × 2 bytes = 26GB`，即约 26GB（忽略单位换算细节的粗估）。这只是权重本身；实际推理还需要 KV Cache、临时计算空间、运行时开销、显存碎片余量和并发请求空间，因此 26GB 显存不一定能稳定加载和服务该模型。

### 练习 3：分析 OOM

某模型单用户短问题能运行，但在开启 20 个并发、较长上下文后开始 GPU OOM。最可能新增占用的是什么？你会优先检查哪些配置？

答案：最可能是每个活跃请求增加的 KV Cache、输入/输出状态和 batch 临时空间。应检查上下文窗口、最大输出 token、并发/批处理上限、KV Cache 预留、实际显存占用和其他 GPU 进程；可通过缩短上下文、限制输出/并发、排队、量化或扩容等方式处理。

### 练习 4：判断部署方式

某团队只想在个人开发机上体验一个小模型的基本问答，不追求并发和实时性能。一定需要高端 GPU 吗？

答案：不一定。可根据模型规模和可接受速度使用 CPU 推理、较小或量化模型，或继续使用云 API。GPU 能显著提升性能，但是否需要取决于任务、模型、预算和学习目标。个人试验与生产高并发服务的硬件要求不同。

## 自测题

### 自测 1：模型推理时显存主要由哪些部分组成？

答案：主要包括模型权重、每个活跃请求的 KV Cache、临时计算/workspace、推理引擎/运行时开销和安全余量。权重通常稳定，KV Cache 会随上下文、输出和并发增长。

### 自测 2：GPU 为什么常比 CPU 更适合大模型推理？

答案：大模型核心计算包含大量可并行的矩阵/张量运算，GPU 拥有大量并行计算单元和高显存带宽，适合高吞吐处理。CPU 仍负责控制逻辑、tokenizer、网络和调度，也可运行小模型/低频推理，但大模型性能通常较弱。

### 自测 3：为什么“模型能加载”不代表“模型能上线服务”？

答案：加载只证明权重在当前资源下可被放入运行环境。上线还需考虑 KV Cache、并发、上下文、输出、延迟、队列、权限、监控、故障恢复、成本和版本治理。单请求成功无法代表多用户稳定服务。

### 自测 4：上下文长度为什么影响显存？

答案：生成式 Transformer 推理通常用 KV Cache 保存历史 token 的注意力键和值，避免每一步重算全部历史。上下文越长、输出越多、并发越高，需要保存的缓存越多，从而增加显存占用。

### 自测 5：遇到 GPU OOM 的第一原则是什么？

答案：先按资源账本定位根因：权重精度/大小、可用显存、上下文、输出、并发/batch、KV Cache、临时空间和其他进程，而不是盲目重启或只增加系统 RAM。再按任务目标选择缩减、量化、排队、offload、换模型或扩容。

## 本节小结

本节建立了模型运行资源的基础地图：磁盘保存产物，CPU/RAM处理通用逻辑与数据，GPU/VRAM承担高吞吐模型计算。推理显存不只包括权重，还包括会随上下文、输出和并发增长的 KV Cache，以及临时空间和运行时余量。理解这一账本后，你才能正确分析 OOM、硬件选择、并发能力与部署成本。
