# M13 第 15 节：LoRA、QLoRA 与微调完整流程

## 本节定位

上一节建立了高质量 SFT 数据与独立评估的基础。本节讨论“怎样训练”：全参数微调为什么资源昂贵，LoRA 如何只训练少量低秩增量参数，QLoRA 如何在量化基础模型上进一步降低显存需求，以及一次可靠的微调实验怎样从基线、数据、训练、评估、部署候选到回滚计划形成闭环。

本节的重点不是让你立即背训练命令或某个框架参数，而是理解方法的机制、假设、资源取舍与工程流程。只有理解这些，未来面对不同模型、显卡、平台和训练工具时，才不会把 LoRA/QLoRA 当成神秘的“一键微调”按钮。

本节仍是纯知识学习，不要求本机 GPU、模型下载或训练代码。

## 本节学习目标

学完后，你应当能够：

1. 解释全参数微调（full fine-tuning）为什么消耗大量显存和存储。
2. 理解 LoRA 的低秩增量思想，知道基础权重冻结、可训练适配器和 rank 的含义。
3. 区分 LoRA 的“基础模型量化推理”与 QLoRA 的“量化基础模型上训练适配器”。
4. 说明量化、LoRA、QLoRA 各自降低的资源成本和引入的限制。
5. 理解学习率、batch size、梯度累积、epoch、最大序列长度、checkpoint 等训练配置的基本作用。
6. 描述一个从任务定义到上线候选的完整微调实验流程。
7. 识别过拟合、训练不稳定、数据/模板错误、评测泄漏、适配器兼容等常见风险。
8. 知道适配器合并、部署、版本、灰度和回滚为什么是微调工程的一部分。

## 一句话先讲透

**LoRA 不重写整个模型，而是在冻结基础权重旁学习一个小的“增量修正”；QLoRA 再把冻结基础模型以低比特形式保存以节省显存，但无论方法多省资源，数据质量、独立评估和发布治理仍决定微调是否值得。**

## 基础知识铺垫

### 1. 为什么训练比推理更吃资源

推理时，模型主要需要：

- 模型权重；
- 输入/输出相关的 KV Cache；
- 临时计算工作区。

训练时，除权重和前向计算外，还要为反向传播保存更多信息：

- 激活值（activations），用于计算梯度；
- 每个可训练参数的梯度；
- 优化器状态，例如 Adam 类优化器常为参数保留额外状态；
- 混合精度中的主权重或缩放状态；
- 更长序列、更大 batch 时的额外中间结果；
- checkpoint、数据加载和日志的 CPU/磁盘资源。

所以一个“推理能装下”的模型，不代表“可以全参数微调”。训练显存往往远大于只加载模型进行推理的显存。

### 2. 全参数微调（Full Fine-Tuning）

全参数微调指模型的大部分或全部参数都参与梯度计算和更新：

```text
预训练权重 W
  -> 对所有/大部分参数求梯度
  -> 优化器更新 W
  -> 得到新权重 W'
```

优点：

- 调整空间大，理论上可更充分适应任务；
- 不需要额外适配器组合逻辑；
- 在规模、数据和资源充足时，可能获得较强效果。

成本与风险：

- 训练显存、计算和时间高；
- 每个任务都保存一整份模型权重，存储与分发昂贵；
- 更容易造成通用能力退化或灾难性遗忘；
- 多任务/多客户版本管理复杂；
- 需要更严格的训练基础设施与实验治理。

全参数微调不是过时方法。它适合资源充足、任务重要、数据规模大、需要深度模型适配且评测证据充分的场景；但对多数应用团队的首次领域适配，通常不是最经济的起点。

### 3. 参数高效微调（PEFT）是什么

PEFT（Parameter-Efficient Fine-Tuning）是一类方法：冻结绝大多数基础模型参数，只训练少量新增或选择出的参数，以更低资源完成任务适配。

常见思想包括 Adapter、Prefix/Prompt Tuning、IA3、LoRA 等。它们的共同目标是：

```text
尽量保留基础模型 W
只训练较小参数集合 θ_small
让 W + θ_small 在目标任务上表现更好
```

优点：

- 训练参数少，显存和计算通常更低；
- 每个任务只保存较小的适配器；
- 可在同一基础模型上维护多个任务/客户适配器；
- 更容易回退到未微调的基础模型；
- 试验成本更适合中小团队。

限制：

- 并非所有任务都能以小适配器达到全参数微调效果；
- 仍需要前向计算和激活，资源并非极低；
- 基础模型、任务、数据和注入位置会影响效果；
- 推理时仍需加载基础模型，适配器不是独立小模型。

### 4. 线性层与“增量更新”的直觉

Transformer 中大量计算可抽象为线性变换：

```text
y = W x
```

其中：

- `x` 是输入向量；
- `W` 是大型权重矩阵；
- `y` 是输出向量。

全参数微调会直接学习 `W` 的变化：

```text
W' = W + ΔW
```

而 LoRA 的核心假设是：目标任务所需的 `ΔW` 可以用一个低秩分解近似：

```text
ΔW ≈ B A
```

其中 `A` 和 `B` 的中间维度很小，称为 rank（秩）`r`。原本很大的矩阵更新，不再直接训练完整 `ΔW`，而是训练两个更小的矩阵 `A` 与 `B`。

这不是说所有真实变化天然是低秩，而是一种经验上经常有效的参数效率假设：许多下游适配不需要在每个方向上都独立自由调整。

## 本节主题系统讲解

### 1. LoRA 的机制：冻结 W，学习 BA

设基础线性层权重：

```text
W ∈ R^(d_out × d_in)
```

若全量更新，需要训练同样大小的 `ΔW`，参数量约为：

```text
d_out × d_in
```

LoRA 选择一个较小秩 `r`，学习：

```text
A ∈ R^(r × d_in)
B ∈ R^(d_out × r)
```

于是：

```text
W' = W + scale × B A
```

可训练参数量约为：

```text
r × d_in + d_out × r
```

当 `r` 远小于 `d_in` 和 `d_out` 时，参数量会明显小于完整矩阵。例如一个 `4096 × 4096` 的矩阵，全量更新约 1,677 万个参数；若 `r=16`，LoRA 的 A、B 共约 13 万个参数，数量级大幅下降。

实际实现还常包含缩放因子（常与 `alpha` 相关）和 dropout。你不必死记具体公式，但要理解：

- 基础 `W` 通常冻结不更新；
- `A`、`B` 是训练得到的适配器参数；
- 前向计算把基础输出与小增量相加；
- 适配器文件小得多，但依赖对应基础模型。

### 2. rank（r）不是“越大越好”的质量旋钮

rank 决定 LoRA 更新的表达能力和可训练参数规模：

- rank 较小：参数少、显存/存储更省、训练更快，但可能不够表达复杂任务；
- rank 较大：适配能力更强，但参数、显存、训练成本和过拟合风险增加；
- 过大时逐渐失去参数高效优势，也可能把数据噪声学得更深。

正确选择不靠直觉，而应在资源允许范围内结合独立验证集试验。rank 与模型大小、目标模块、数据量、任务复杂度、学习率和序列长度相互影响。不要把网上某个常用数字当作所有任务的最佳值。

### 3. target modules：LoRA 插到模型哪里

Transformer 不只有一个线性层。常见候选位置包括 Attention 中的投影层（例如 Q/K/V/O）和前馈网络（MLP）的线性层。

“target modules”指你选择在哪些模块旁注入 LoRA 增量。不同选择的权衡：

- 只作用于少数 Attention 投影：参数更少、训练更轻，可能已足够；
- 同时作用于 Attention 和 MLP：适配空间更大，但成本增加；
- 过广注入：训练参数和复杂度上升，未必带来同比例收益；
- 目标层命名依赖模型架构和训练框架，不能机械复制别的模型配置。

选择目标模块属于实验变量。应记录它，并在验证集/测试集上与基线比较，而不是把“某教程用了 q/v”当作普适真理。

### 4. LoRA 的初始化与训练直觉

常见 LoRA 初始化会让初始增量接近零，因此训练刚开始时模型行为近似基础模型：

```text
W' ≈ W
```

随后随着 `A`、`B` 学到任务模式，增量逐渐改变输出。这个设计使训练起点相对稳定，也便于将“基础模型能力”和“任务适配变化”区分开。

但不要因此认为 LoRA 天然安全：错误数据、过高学习率、过多训练轮数或模板不匹配仍会造成明显退化。冻结基础权重只缩小了更新范围，不保证训练目标正确。

### 5. adapter 文件与基础模型的关系

训练后的 LoRA 通常保存的是适配器权重和配置，而不是完整基础模型：

```text
base-model-v1
  + adapter-support-classification-v1
  -> 运行时组合
```

这使得多个任务可以共享一个基础模型：

```text
base-model-v1 + adapter-ticket-classifier-v1
base-model-v1 + adapter-support-style-v2
base-model-v1 + adapter-summary-v1
```

但也带来强兼容关系：适配器通常绑定基础模型架构、权重版本、Tokenizer/聊天模板和目标模块配置。将某个适配器直接套到“名字相似但版本不同”的基础模型上，结果可能错误、加载失败或质量明显退化。

适配器版本记录至少应包含基础模型精确 ID/哈希、Tokenizer、训练数据版本、LoRA 配置、训练代码/框架版本、评测结果和许可证。

### 6. 合并（merge）与不合并（unmerged）部署

LoRA 增量可在推理时动态叠加，也可在部署前合并到基础权重：

```text
动态：y = (W + BA)x，在运行时加载 adapter
合并：预先生成 W_merged = W + BA，按普通模型权重部署
```

动态加载的优点：

- 同一基础模型可切换多个 adapter；
- 模型资产更小，回滚只需移除 adapter；
- 便于多任务/多租户适配器管理。

合并的优点：

- 某些推理引擎或部署路径更容易支持；
- 减少运行时适配器组合的管理复杂度；
- 对固定单一 adapter 的服务可能更直接。

合并的代价：生成新的完整权重资产，存储/发布变大，回滚和多 adapter 切换不如动态方式灵活。选择要考虑引擎支持、部署方式、延迟、模型数量和运营复杂度。

### 7. QLoRA：量化基础模型，训练 LoRA 适配器

QLoRA 的基本思路是：

```text
基础模型权重：以较低比特量化形式加载（通常冻结）
可训练部分：LoRA 适配器保持可训练精度
训练时：通过量化基础模型进行前向/反向相关计算，更新 adapter
```

它的主要目标是降低基础模型驻留显存，让较有限的 GPU 资源也能进行较大模型的适配训练。

必须准确区分：

- **量化推理**：为减少推理显存/加速而用低比特权重运行模型。
- **LoRA**：冻结基础模型，训练低秩适配器。
- **QLoRA**：在量化冻结基础模型的前提下训练 LoRA 适配器，以降低训练资源需求。

QLoRA 并不是“训练出的模型自动量化得更好”，也不是“不需要显存”。激活、梯度、适配器、序列长度、batch、优化器和临时工作区仍会占用资源。

### 8. QLoRA 的工程收益与边界

可能收益：

- 降低基础模型权重常驻显存；
- 让单卡或较小资源环境可以完成原先难以完成的适配实验；
- 适配器仍较小，便于版本管理和分发；
- 在许多任务上可获得实用效果。

边界与风险：

- 量化格式、训练框架、GPU/驱动和模型架构兼容性更复杂；
- 量化会带来数值近似，效果与稳定性必须实测；
- 数据、序列长度和 batch 仍可能导致 OOM；
- 训练速度不一定线性更快，有时受量化解码、内存访问或硬件支持影响；
- 不是每个推理引擎都能直接部署训练产物的组合；
- “能在小显卡跑”不代表质量、训练时长和上线收益合理。

QLoRA 的价值是扩大可实验范围，不是替代严肃的资源与质量评估。

### 9. 微调完整流程：从假设到上线候选

把一次微调看作受控实验，而非单次命令。一个完整流程可分为十一步：

#### 第一步：明确业务假设

例如：“在不降低安全/Schema 合法率的前提下，针对售后分类任务训练 LoRA adapter，可使关键类别 F1 提升，并降低高频分类成本。”

假设应有对象、预期收益、约束和验证方式。

#### 第二步：建立并冻结基线

记录当前基础模型、Prompt、参数、RAG/工具配置，在独立评测集上的质量、延迟、成本和 Bad Case。没有基线，训练后无从比较。

#### 第三步：准备并冻结数据版本

使用上一节的数据规格、标注、清洗、脱敏、去重和 train/validation/test/challenge 切分。记录数据哈希、来源和已知局限。

#### 第四步：选择候选基础模型和方法

确认基础模型许可、能力、上下文、Tokenizer、聊天模板、硬件兼容和推理部署路径。选择 full fine-tuning、LoRA 或 QLoRA 应来自资源和目标，而不是工具流行度。

#### 第五步：定义实验配置

明确：目标模块、rank/alpha/dropout、最大序列长度、学习率、batch、梯度累积、epoch、warmup、评估频率、保存策略、随机种子和资源上限。

#### 第六步：运行小规模冒烟实验

先用很小、受控数据验证数据能解析、聊天模板正确、loss 能变化、checkpoint 能保存、评测脚本能运行、adapter 能加载。此阶段不是为了得出最终效果。

#### 第七步：正式训练与过程监控

观察训练/验证 loss、显存、吞吐、异常、样本跳过、NaN、checkpoint、训练时长。发现异常先定位数据和配置，不要盲目延长训练。

#### 第八步：选择候选 checkpoint

根据验证集与业务代理指标选择有限候选。不要只选最后一个 epoch，也不要只看 train loss 最低。

#### 第九步：独立测试与安全评估

在未参与调参的测试集、挑战集和安全集上与基线比较。确认质量提升没有伴随格式、安全、长尾、成本或延迟的不可接受退化。

#### 第十步：部署兼容与灰度验证

验证 adapter/merged model 能被目标推理引擎加载，API、流式、结构化输出、工具链、资源和观测正常。再以小流量、受控任务或影子流量验证线上分布。

#### 第十一步：上线、监控与持续回流

记录版本和路由；观察质量、延迟、成本、错误和用户反馈；收集 Bad Case；必要时回滚或进入下一轮数据改进。训练结束不是项目结束。

### 10. 关键训练配置的基本含义

下面的参数名称会随框架不同而变化，但概念相通。

#### 10.1 学习率（learning rate）

决定每次参数更新的步幅：

- 太大：可能震荡、发散、破坏基础能力或产生 NaN；
- 太小：学习极慢，看不到任务适配；
- 最佳范围依赖模型、数据、方法、batch、rank 和训练步数。

不要只问“LoRA 的标准学习率是多少”。应在受控实验中比较少量候选，并看验证和业务评测。

#### 10.2 Batch size 与梯度累积（gradient accumulation）

batch size 是一次前向/反向实际装入设备的样本数或 token 数，受显存限制。梯度累积是在多个小 batch 后再更新一次参数，用更少显存近似更大的有效 batch：

```text
实际 batch = 1
累积 8 次梯度
-> 有效 batch 近似 8（概念上）
```

它能缓解显存限制，但不等于完全免费：训练会更慢，调度、随机性和学习率关系也要重新观察。

#### 10.3 最大序列长度（max sequence length）

限制每条训练样本可包含的 Token 数。它影响：

- 可保留多少上下文；
- 激活显存与训练速度；
- 是否截断重要内容；
- 训练与线上真实输入的分布差异。

不能盲目设置为模型最大上下文。若真实任务多为短文本，过长设置浪费资源；若任务依赖长文档，过短会让模型从未见过完整上下文。需要先统计数据长度分布并制定截断策略。

#### 10.4 Epoch、step 与训练轮数

一个 epoch 表示训练器大致遍历一遍训练集；step 是一次或若干次参数更新。训练过少可能未适配，训练过多可能过拟合。适当保存 checkpoint 并观察 validation 指标，比预先认定固定 epoch 更可靠。

#### 10.5 Warmup 与学习率调度

训练开始时直接使用较大学习率可能不稳定。warmup 让学习率从较低值逐步上升；后续调度可能再衰减。具体策略是优化稳定性的工具，不是保证质量的秘诀。应结合曲线、资源和验证指标判断。

#### 10.6 Dropout

Dropout 在训练时随机屏蔽部分连接/更新路径，用于减轻过拟合的一种手段。LoRA 中也可能使用。它不是“越大越安全”：过高会让学习不足，是否使用与数据规模、噪声和任务有关。

#### 10.7 随机种子（seed）

数据打乱、初始化和某些计算可能带随机性。记录 seed 有助于复现，但在并行硬件和不同库版本下不一定能做到每一位完全一致。可复现的目标是尽量能解释和重跑结果，而不是承诺所有环境位级相同。

### 11. 显存与序列长度：为什么小 batch 仍可能 OOM

常见误解是“我用 LoRA，所以显存应该很低”。实际训练显存受多项共同影响：

```text
基础模型权重
+ 量化/精度表示
+ 激活（与 batch × sequence length 强相关）
+ 适配器参数、梯度和优化器状态
+ 注意力/临时工作区
+ 框架和 CUDA 开销
```

长序列尤其会明显增加激活和 Attention 相关成本。即使基础模型量化、实际 batch 为 1，超长样本仍可能 OOM。

排查顺序通常是：确认真实 Token 长度和截断；降低最大序列长度或采用更合理的 packing；减小 batch/增加梯度累积；选择更小模型/更低资源方法；检查目标模块与优化器；最后再考虑硬件扩容。不要只反复降低 rank，因为 OOM 的主因可能根本不在适配器。

### 12. Packing：提高短样本训练效率，也有语义边界

若数据中有大量短样本，训练器可能把多个样本拼入同一长序列，以减少 padding，称为 packing。它可以提高 token 利用率和吞吐。

但必须确保：

- 样本边界和 EOS 正确；
- attention mask 不让样本之间错误互相看到；
- loss mask 仍只计算目标 assistant 部分；
- 评测时不把训练 packing 的效率当作线上交互行为；
- 对多轮对话、工具调用或特殊格式，确认框架处理语义正确。

Packing 是训练吞吐优化，不会替代高质量数据和正确聊天模板。

### 13. Checkpoint、实验记录与可恢复训练

训练时间可能很长，硬件/网络/进程可能中断。checkpoint 通常保存某个阶段的 adapter/模型状态、优化器状态、训练步数及可能的随机状态。

需要明确：

- 保存频率与磁盘成本；
- 哪些 checkpoint 用于恢复，哪些用于候选评估；
- 最佳 checkpoint 依据什么选择；
- 是否能从中断处恢复且数据顺序/配置一致；
- checkpoint 是否包含敏感训练数据或不应外泄的路径；
- 训练完成后保留/清理策略。

实验记录至少关联：代码版本、基础模型、数据版本、训练配置、硬件环境、随机种子、日志、checkpoint、评测结果和结论。否则几周后很难解释“adapter_v3 为什么更好”。

### 14. 训练失败的典型信号与排查

#### 14.1 loss 为 NaN 或突然爆炸

可能涉及学习率过大、数值精度、数据异常、损坏样本、梯度不稳定或框架/硬件问题。先检查数据与配置日志，而不是只重跑。

#### 14.2 训练 loss 很低，验证/测试差

可能过拟合、训练测试泄漏、训练分布与真实分布不同、标注/模板有问题，或模型只学会格式。需要回到数据覆盖、切分和挑战集。

#### 14.3 模型开始重复、答非所问或不结束

可能是聊天模板、EOS/停止 Token、目标 mask、数据格式、学习率或过度训练问题。确认训练时的消息格式与部署时完全兼容。

#### 14.4 JSON 更像样但字段语义变差

可能模型过度学习表面模板，或训练数据中字段标签存在偏差。应拆分评估：语法、Schema、语义和业务安全，而非只看格式率。

#### 14.5 部署时加载失败或效果与训练评测不同

检查基础模型精确版本、Tokenizer、聊天模板、LoRA target modules、量化/合并方式、推理引擎版本、生成参数和 API 适配。训练环境与线上环境不一致是常见根因。

### 15. 如何选择 LoRA、QLoRA 或全参数微调

可以用下面的判断框架：

| 条件 | 更可能的起点 |
| --- | --- |
| 数据和资源有限，需要快速验证任务适配 | LoRA |
| GPU 显存紧张，但希望适配较大模型 | QLoRA |
| 多任务/多客户，需要保存多个小版本 | LoRA/QLoRA adapters |
| 有大量高质量数据、充足资源、任务需深度模型改变 | 评估全参数微调 |
| 只是动态知识、权限或工具问题 | 不应优先微调 |
| 高风险业务且无独立评测/回滚能力 | 先补数据与治理，不急于训练 |

这是候选起点，不是保证。最终要用基线、验证、测试、安全和部署成本决定。

### 16. 一个小型但严谨的实验设计示例

目标：改善售后工单分类，减少高频大模型调用。

```text
假设：LoRA 适配的小模型可在独立测试集上达到不低于当前大模型基线的关键类别 Recall，
     且 JSON Schema 合法率和安全挑战集不退化，P95 延迟/成本明显更低。

基线：当前大模型 + 固定 Prompt + Structured Output
数据：人工确认、脱敏、按订单分组切分的分类样本
候选：同一基础模型上的两组 LoRA rank/target-module 配置
验证：使用 validation 选择候选，而不碰 final test
验收：final test + challenge + 人工抽样 + 推理部署兼容测试
上线：先只处理低风险、可人工复核的流量；低置信度升级到大模型
回滚：路由切回原基线，不删除旧路径
```

这里最重要的不是 rank 数字，而是实验假设、独立评测和上线范围都明确。它能让“微调值得吗”得到可审计答案。

## 常见误区

### 误区 1：LoRA 就是不训练基础模型，所以完全不需要 GPU 资源

纠正：基础权重通常仍需加载并参与前向计算，训练还要保存激活、适配器梯度、优化器状态和临时工作区。LoRA 降低可训练参数成本，不让训练变成零资源。

### 误区 2：QLoRA 等于把训练结果量化

纠正：QLoRA 的关键是以量化形式加载冻结的基础模型，并训练 LoRA adapter，以降低训练显存。训练产物部署时如何量化/合并是另一个问题。

### 误区 3：rank 越大，微调一定越好

纠正：更高 rank 增加表达能力，也增加资源和过拟合风险。应在数据、任务和独立验证下选择，而不是追求最大值。

### 误区 4：adapter 很小，所以可以脱离基础模型单独部署

纠正：adapter 只包含相对于基础模型的增量，需要兼容的基础权重、架构、Tokenizer 和配置才能运行。

### 误区 5：训练结束时最后一个 checkpoint 就是最佳模型

纠正：后期可能过拟合或退化。应根据验证集和业务代理指标选择候选，再用独立测试集做最终判断。

### 误区 6：显存 OOM 只要把 rank 调小就能解决

纠正：长序列、激活、batch、模型权重、临时工作区可能才是主要原因。应从真实 Token 长度和整体显存构成排查。

### 误区 7：LoRA 训练成功就等于可以直接上线

纠正：还需验证基础模型/adapter/Tokenizer/模板/推理引擎组合、API 契约、结构化输出、工具安全、性能、成本、灰度和回滚。

## 本节练习

### 练习 1：计算参数量直觉

某线性层 `W` 的形状为 `4096 × 4096`，LoRA rank 为 8。全量更新和 LoRA 更新分别大约训练多少参数？不必考虑 bias。

答案：全量更新约为 `4096 × 4096 = 16,777,216` 个参数。LoRA 训练 `A(8 × 4096)` 与 `B(4096 × 8)`，约为 `32,768 + 32,768 = 65,536` 个参数。LoRA 参数量远小于完整矩阵更新，但实际总训练显存还受基础模型、激活等影响。

### 练习 2：区分 LoRA 与 QLoRA

请用自己的话说明 LoRA 与 QLoRA 的关键差别。

答案：LoRA 冻结基础模型权重，在部分层旁训练低秩适配器增量；基础模型可以以常规精度加载。QLoRA 在 LoRA 思路上进一步以低比特量化形式加载冻结基础模型，以降低常驻显存，再训练适配器。二者都不是全参数更新；QLoRA 主要面向资源受限下的训练可行性。

### 练习 3：定位 OOM 的优先顺序

某团队使用 QLoRA，实际 batch size 已经是 1，但仍然 OOM。请列出至少四项优先检查项。

答案：检查真实最大序列长度和是否存在异常超长样本；检查激活/Attention 是否因长上下文占用过高；检查基础模型大小、量化格式和模型是否真的按预期量化加载；检查目标模块范围、优化器和临时工作区；检查 GPU 是否被其他进程占用；考虑降低序列长度、采用梯度累积而非扩大实际 batch、选择更小模型或调整资源。只调小 rank 可能无效。

### 练习 4：设计 adapter 元数据

一个 LoRA adapter 发布时，至少要记录哪些信息，才能让他人正确加载和评估？

答案：至少包括 adapter 名称和版本、精确基础模型 ID/哈希、Tokenizer/聊天模板版本、训练数据版本、任务定义、LoRA rank/alpha/dropout/目标模块、训练框架与关键配置、最大序列长度、评测集与结果、许可证、已知限制、推理加载/合并方式、上线日期和负责人。adapter 文件本身不足以解释其行为。

### 练习 5：判断训练完成条件

训练 loss 下降到很低，validation loss 也略有下降。是否可以直接上线？还需要哪些验证？

答案：不能直接上线。还需在未参与调参的测试集、挑战/安全集上与基线比较任务质量、结构化语义、工具/权限边界、长尾表现；验证部署环境可正确加载模型和 adapter；测试延迟、显存、成本、流式/API 契约；制定灰度、监控和回滚。loss 仅是候选选择信号。

## 自测题

### 自测 1：LoRA 的核心公式表达了什么？

答案：它将基础权重更新表示为低秩增量，近似为 `W' = W + scale × BA`。训练时冻结大的基础权重 `W`，只学习较小的 `A` 和 `B`，从而减少可训练参数和相关资源开销。

### 自测 2：为什么 LoRA adapter 不能随意套用到其他基础模型？

答案：adapter 的参数形状、目标模块、模型结构、基础权重版本、Tokenizer 和聊天模板都与训练时环境相关。基础模型不同或版本不兼容时，可能无法加载、输出异常或质量退化。

### 自测 3：什么决定了训练显存，而不只是 LoRA rank？

答案：基础模型权重及其精度/量化、序列长度、batch、激活、Attention 临时工作区、adapter 参数/梯度/优化器状态、框架和 CUDA 开销、GPU 上其他进程等共同决定。长序列常是关键因素。

### 自测 4：合并 adapter 与动态加载 adapter 的主要取舍是什么？

答案：动态加载保留基础模型与多个小 adapter 的灵活组合，便于切换和回滚；合并后部署路径可能更简单或兼容，但生成完整权重资产，存储/发布变大、切换多个 adapter 不灵活。选择取决于引擎、运行时和运营需求。

### 自测 5：可靠微调实验的最小闭环是什么？

答案：明确业务假设和成功标准；建立基线；冻结合法高质量数据版本和独立评测；选择基础模型/方法并做小规模冒烟；训练和记录实验；按验证集选择候选；在测试/挑战/安全集评估；验证部署兼容与性能；灰度上线、监控、回滚并持续回流 Bad Case。

## 本节小结

LoRA 通过冻结基础权重、训练低秩增量适配器，大幅减少可训练参数；QLoRA 在此基础上量化冻结基础模型，以进一步降低显存需求。它们让微调更易试验和管理，但不会消除训练的激活、序列长度、数据质量、评测和部署成本。

方法选择只是微调工程的一环。真正可靠的流程始于明确假设和基线，经过数据版本、受控实验、独立评测和部署兼容验证，最后以灰度、监控和回滚进入线上。下一节将完成 M13：模型上线、版本管理与阶段设计复盘，把模型权重、adapter、配置、评测和路由统一纳入可持续运营的生命周期。
