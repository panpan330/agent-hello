# M13 第 0 节：模型推理与模型生命周期总览

## 本节定位

在前面的阶段里，你已经能够通过云端 API 调用大模型，也理解了 Prompt、Structured Output、Tool Calling、RAG、Agent、评估与企业级控制。但“调用一个模型 API”与“理解模型怎样被运行、部署、版本化和下线”之间，仍有一层非常重要的知识。

例如：

```text
模型文件是什么？
为什么模型有参数量、上下文窗口和不同精度？
模型为什么可以被下载到本地或部署到服务器？
训练、微调、推理三者分别在做什么？
为什么同一个模型在不同服务上速度和成本差异很大？
模型 API、推理引擎、模型服务、网关和业务系统分别负责什么？
模型更新后，如何保证线上系统可回滚、可评估、可审计？
```

M13 的目标不是让你立刻训练一个大模型，也不是让你把个人电脑变成生产推理集群，而是先建立完整且正确的模型服务认知。理解这条生命周期后，你才能真正判断：什么时候继续使用云模型 API，什么时候使用本地模型，什么时候值得自部署，什么时候该微调，以及 Kubernetes 在 AI 系统中究竟解决什么。

## 本节学习目标

学完后，你应当能：

1. 区分基础模型、模型权重、训练、微调、推理、部署和模型服务。
2. 描述一个模型从训练数据到用户请求响应的完整生命周期。
3. 解释“模型本身”“推理引擎”“模型 API”“模型网关”“业务应用”分别是什么。
4. 理解模型版本、数据版本、提示词版本和服务版本为什么必须分开管理。
5. 说明云 API、本地运行和自部署推理服务在生命周期中的位置。
6. 理解为什么模型上线不是“把模型文件放到服务器上”这么简单。
7. 为 M13 后续的 GPU、量化、推理性能、部署和微调课程建立概念地图。

## 一句话先讲透

> 大模型不是一个抽象的“聊天能力”，而是一组经过训练得到的参数文件；推理服务把这组参数加载到计算资源上，接收输入并生成输出；企业应用再通过网关、权限、任务、工具和评估机制，将这项概率能力变成可控的产品能力。

## 基础知识铺垫

### 1. 先把“模型”从神秘概念变成工程对象

在日常交流中，人们会说“某模型很强”“调用一下模型”“把模型部署起来”。这些说法都没有错，但它们可能指不同层次的对象。

可以先建立下面这张关系图：

```text
训练数据
  -> 训练过程
  -> 模型参数（weights / checkpoint）
  -> 推理引擎加载模型
  -> 模型服务暴露 API
  -> 网关/业务应用调用 API
  -> 用户得到结果
```

每个箭头后的东西都不是同一个“模型”。例如：

| 术语 | 它是什么 | 它不是什么 |
| --- | --- | --- |
| 模型架构 | 网络如何组织的设计 | 某个具体训练好的文件 |
| 模型权重/参数 | 训练后得到的大量数值 | 一段可读的业务规则 |
| 推理引擎 | 加载并计算模型的程序 | 模型训练数据本身 |
| 模型服务 | 将推理能力暴露为网络 API 的系统 | 业务系统的全部逻辑 |
| 模型网关 | 路由、鉴权、限流、观测的控制层 | 用来训练模型的框架 |
| AI 应用 | 为用户解决业务问题的产品 | 仅仅一个模型接口 |

在 M13 中，我们会不断把这几层拆开。因为许多误解都来自把它们统称为“模型”。

### 2. 什么是参数（Parameters）

神经网络模型中，参数通常是大量可学习数值。训练过程通过数据不断调整这些数值，使模型在给定输入后更可能输出符合训练目标的结果。

你不需要在这一阶段推导反向传播公式，但应有正确直觉：

```text
模型不是把每一条知识按原文存进一个数据库；
模型参数是从大量训练样本中学习得到的统计结构；
推理时，模型依据这些参数和当前输入，计算下一个 token 的概率分布。
```

参数量常以百万（M）、十亿（B）计，例如“7B 模型”通常表示约 70 亿个参数。参数更多常常意味着更大的表达能力和更高计算/显存成本，但不代表在所有任务上必然更好。数据质量、训练方法、架构、上下文、工具/RAG、提示与推理服务实现都会影响最终效果。

### 3. 什么是权重（Weights）与 Checkpoint

在工程实践中，“模型权重”“模型文件”“checkpoint”常被一起提及。

- **权重（weights）**：训练得到的参数数值，通常是模型最核心、体积最大的部分。
- **checkpoint（检查点）**：训练过程中保存的状态快照；它可能包含权重，也可能包含优化器状态、训练步数、配置等，以便恢复训练。
- **模型发布产物**：用于推理的一组文件，通常包括权重、模型配置、tokenizer 配置、词表、特殊 token 规则等。

一个可推理模型往往不是单个文件，而是一组彼此匹配的产物：

```text
权重分片文件
+ 网络结构配置
+ tokenizer / vocabulary
+ generation 配置
+ 许可证与模型卡（按发布方式）
```

如果权重、配置和 tokenizer 版本不匹配，即使“文件都下载了”，模型也可能无法正确加载或输出异常。

### 4. Tokenizer：模型为什么不直接处理汉字或单词

模型通常不直接以“一个完整自然语言单词”作为计算单位，而是通过 tokenizer（分词器/编码器）把文本转换为 token ID 序列：

```text
用户文本
-> tokenizer 编码
-> token IDs
-> 模型计算
-> token IDs
-> tokenizer 解码
-> 输出文本
```

token 不等于字、不等于词，也不等于固定长度字符。中文、英文、数字、标点、代码和特殊符号的 token 切分方式会不同。

Tokenizer 与模型权重必须匹配，原因是：模型参数学习的是“这些 token ID 在什么上下文中如何关联”。如果把一个模型与不匹配的 tokenizer 混用，输入/输出符号的含义可能发生错位。

后续你学习上下文窗口、token 成本、吞吐与 KV Cache 时，会频繁用到 tokenizer 的概念。

### 5. 训练（Training）与推理（Inference）的区别

训练与推理使用同一类模型架构，但目标和资源行为差异很大。

| 维度 | 训练 | 推理 |
| --- | --- | --- |
| 目标 | 更新参数，让模型学习 | 固定参数，生成/预测结果 |
| 输入 | 大量训练样本 | 用户请求、文档、工具结果 |
| 输出 | 新 checkpoint、训练指标 | 文本、结构化结果、向量等 |
| 计算 | 前向计算 + 反向传播 + 参数更新 | 主要是前向计算/逐 token 生成 |
| 资源 | 通常更高，需梯度和优化器状态 | 重点是权重、KV Cache、并发与延迟 |
| 频率 | 较低、批处理式 | 高频、在线或批量服务式 |

可以用一个简单类比：

```text
训练像“学习和调整大脑连接”；
推理像“使用已经学到的连接解决一个具体问题”。
```

类比并不完全准确，但能帮助你记住：普通用户调用模型 API 做的是推理，不是在训练模型。

### 6. 基础模型、指令模型与领域模型

同一模型家族可能有不同阶段的产物。

#### 6.1 基础模型（Base Model）

基础模型通常经过大规模预训练，擅长继续文本、理解语言模式，但未必天然适合直接遵循人类对话指令。

#### 6.2 指令模型（Instruction-tuned / Chat Model）

指令模型在基础模型之上进一步训练，使其更擅长理解“请总结”“请以 JSON 输出”“请解释”等指令，并遵循对话格式和安全策略。你日常通过云 API 使用的大多数聊天模型通常属于这一类或类似对齐后的模型。

#### 6.3 领域模型/微调模型

某些模型会针对特定领域或任务做额外训练，例如代码、法律、医疗、客服分类、结构化抽取等。它们可能更擅长指定分布内的任务，但不一定在所有通用能力上更强。

理解这三层很重要：后续讨论“要不要微调”时，你需要先判断当前问题是提示、RAG、工具、工作流就能解决，还是确实需要让模型参数学习新的稳定模式。

### 7. 从“模型文件”到“可用 API”中间缺了很多层

许多人第一次接触本地模型时会想：下载了权重，就等于有了一个可用模型。但模型文件本身不能接受 HTTP 请求，也不能自动处理并发、认证、日志、超时、流式输出和成本控制。

完整路径更接近：

```text
模型产物
-> 推理引擎加载到 CPU/GPU 内存
-> 请求调度和 token 生成
-> 推理服务暴露 API
-> 网关做鉴权、限流、路由、观测
-> 业务应用构造上下文、调用服务
-> 用户得到结果
```

后续章节会逐层讲清。现在先记住：**权重是能力资产，推理引擎是运行程序，模型服务是网络产品，业务应用是实际用户价值的承载者。**

### 8. 为什么模型需要版本

传统软件会有版本，因为代码会变；模型也同样需要版本，因为以下内容都会变：

- 权重来源、训练阶段或微调版本；
- tokenizer 与模型配置；
- 推理引擎版本与运行参数；
- 系统 prompt、工具 schema、RAG 文档；
- 安全策略、审批阈值和网关路由；
- 业务服务契约。

假设某次答复质量变差，你需要能追溯：

```text
当时用了哪个模型版本？
用了什么 prompt 模板？
检索了哪一版知识库？
走了哪个工具和策略版本？
服务是否发生了量化、引擎或参数变更？
```

只记录一个模型名称往往不够。企业系统中的“模型版本”应理解为一个可复现的组合，而不是简单字符串。

## 本节主题系统讲解

### 1. 模型生命周期的全景

将模型相关工作按时间顺序展开，可以看到一条完整生命周期：

```text
需求定义
-> 数据准备
-> 预训练或选择基础模型
-> 对齐/指令训练/微调（按需）
-> 离线评估
-> 打包与登记模型产物
-> 部署推理服务
-> 灰度发布与在线观察
-> 运行中的质量/成本/安全治理
-> 新版本替换、回滚、归档或下线
```

并非每个团队都自己完成每一步。例如使用云模型 API 时，基础模型训练、权重打包和底层推理部署主要由模型供应商负责；你的团队仍需要完成模型选择、上下文构造、工具控制、评估、网关治理和应用发布。

这条生命周期能帮助你理解自己在不同部署模式中的责任范围。

### 2. 阶段一：需求定义，先决定“模型要解决什么”

模型项目最早的问题不该是“选哪个模型”，而应是：

```text
用户目标是什么？
模型在流程中负责什么？
成功如何衡量？
错误影响是什么？
是否需要实时性、私有部署、离线处理或多语言？
是否存在敏感数据、合规和成本约束？
```

例如“让用户能查订单”并不是模型需求，传统业务 API 已能完成。模型可能真正负责的是：理解用户不完整的自然语言、追问缺失订单号、解释查询结果、从政策文档中提炼条件、在受限工具中编排调查路径。

先划清模型职责，才能避免把本应由业务规则、数据库或权限服务完成的事情错误交给模型。

### 3. 阶段二：数据与知识准备

模型能力与数据关系可分成至少三种：

| 数据类型 | 用途 | 是否改变模型参数 |
| --- | --- | --- |
| 训练数据 | 训练/微调模型 | 会改变或产生新参数 |
| 检索知识 | RAG、上下文补充 | 不改变参数 |
| 在线业务数据 | 订单、库存、用户权限等实时事实 | 不改变参数 |

初学者常把“让模型知道一份新政策”理解为“训练模型”。实际上，如果政策会更新、需要引用、存在权限边界，通常更适合放入 RAG 或权威业务服务，而不是微调进权重。

这正是你已经学习 RAG 的意义：模型参数提供通用语言和推理能力，检索与工具提供新鲜、可引用、可控的外部事实。

### 4. 阶段三：模型选择，而不是盲目追求最大模型

选择模型时应看任务匹配，而不只是排行榜或参数规模。常见维度：

| 维度 | 要问的问题 |
| --- | --- |
| 能力 | 是否擅长中文、代码、工具调用、结构化输出、长文本？ |
| 质量 | 在你的真实评估集上是否满足正确性和安全要求？ |
| 延迟 | 用户能接受多久首字和完整回答？ |
| 吞吐 | 同时有多少请求、每分钟需要多少 token？ |
| 成本 | 每请求、每用户、每租户成本是否可接受？ |
| 上下文 | 是否能容纳必要的历史、RAG 结果和工具 schema？ |
| 部署 | 能否通过 API 使用，是否允许自部署，运行资源要求如何？ |
| 数据治理 | 数据能否发送给供应商，是否需要特定地域/隔离？ |
| 许可证 | 使用、商用、再分发和微调是否符合要求？ |

一个较小模型配合好的 RAG、工具约束和工作流，可能比一个更大模型直接裸聊更可靠、更便宜。模型选择应通过任务评估来决定，而不是通过印象。

### 5. 阶段四：训练、对齐与微调的关系

#### 5.1 预训练（Pre-training）

预训练通常使用大规模通用数据，让模型学习语言、代码、世界知识模式和预测能力。它成本极高，普通应用团队通常不会从零开始做。

#### 5.2 对齐/指令训练（Alignment / Instruction Tuning）

这一步使模型更适合与人交互：遵循指令、按格式回答、拒绝不当请求、保持特定对话风格等。聊天模型往往在这一阶段或相关流程后形成。

#### 5.3 微调（Fine-tuning）

微调是在已有模型基础上，用较小但更针对性的高质量数据继续训练，以改变或增强模型对某类任务、格式、语气或领域模式的稳定表现。

微调不是“把公司的所有文档塞进去”，也不是“遇到回答不准就训练”。后续 M13 会专门讲什么时候该用微调、数据怎样准备、LoRA/QLoRA 为什么流行以及如何评估。

### 6. 阶段五：模型登记与可复现产物

当一个模型准备进入测试或生产，团队需要能够准确识别它。概念上可为模型版本建立“登记卡”：

```text
模型标识：model-name + version
基础模型来源与版本
权重/配置/tokenizer 的校验信息
训练或微调数据版本
训练配置与代码版本
许可证/使用范围
离线评估结果
已知限制与风险
支持的输入输出能力
推荐/禁止使用场景
```

这常被称为模型注册（model registry）或模型管理的一部分。即使你使用外部 API，也应在自己的系统中记录“业务路由使用的是哪个供应商模型版本、什么参数、什么评估结论”，否则出现质量回归时难以定位。

### 7. 阶段六：推理（Inference）到底发生了什么

推理是模型接收输入并产出结果的过程。对生成式语言模型，简化过程可写为：

```text
文本输入
-> tokenizer 转成 token IDs
-> 模型根据已加载参数计算下一个 token 概率
-> 根据采样/解码规则选择一个 token
-> 将该 token 加入上下文
-> 重复，直到停止条件满足
-> tokenizer 解码为文本
```

模型通常不是一次性“想到整段答案”，而是逐 token 生成。由此带来几个重要工程事实：

- 输出越长，生成时间和成本通常越高；
- 上下文越长，首次处理输入的成本和延迟可能越高；
- 多用户并发时，需要调度多个 token 生成请求；
- 模型服务可以流式返回 token，让用户先看到输出；
- 随机采样参数会影响多次回答是否一致。

后面的推理性能章节会把这些事实展开。

### 8. 推理引擎（Inference Engine）负责什么

推理引擎是将模型权重高效运行在硬件上的软件。它通常负责：

- 加载模型权重、配置和 tokenizer；
- 将计算映射到 CPU、GPU 或其他加速硬件；
- 管理显存/内存中的权重和请求状态；
- 对多个请求进行排队、批处理和调度；
- 按 token 生成并支持流式输出；
- 提供推理参数控制；
- 有时暴露 HTTP/gRPC/OpenAI 兼容接口。

可以把它理解为“模型的运行时”。模型权重像程序所需的大型数据资产，推理引擎像使其在硬件上真正运行的运行环境。

不同引擎的差别主要体现在：性能优化、支持的硬件/模型格式、并发调度、量化、接口兼容、扩展能力和运维复杂度。M13 后续会讲这些设计思想，而不是把某个工具名称当成唯一答案。

### 9. 模型服务（Model Serving）负责什么

模型服务是面向网络调用者提供推理能力的服务层。它通常提供：

```text
认证后的请求入口
-> 输入校验与请求排队
-> 调用推理引擎
-> 流式或非流式输出
-> 错误处理、超时、指标和日志
```

常见能力可能包括聊天生成、补全、embedding、rerank、模型列表、健康检查等。不同供应商的 API 可能不同，因此 OpenAI 兼容格式在生态中很常见：业务应用只需遵循一套常见请求/响应习惯，就可以更容易替换后端模型服务。

但要注意：接口兼容不表示模型能力、参数、错误语义、限流规则或结构化输出行为完全相同。兼容协议降低接入成本，不消除模型差异。

### 10. 模型网关（Model Gateway）为什么存在

当应用只调用一个云模型时，可以直接在业务服务中使用 SDK；但当系统要处理多模型、多个团队、配额、审计、回退和成本时，通常需要模型网关或类似控制层。

模型网关可能负责：

- API Key/用户/租户认证；
- 模型别名到实际供应商/部署版本的路由；
- 限流、配额、预算和并发控制；
- 请求脱敏、日志关联、trace；
- 失败回退、重试与熔断；
- 统一 OpenAI 兼容接口；
- 成本统计和模型使用策略。

网关不是模型能力本身。它的价值是让“调用模型”从散落在各个业务模块的 SDK 代码，变成可统一治理的基础能力。

### 11. 业务应用为什么不能只等于模型服务

模型服务能回答“给定这些 token，生成什么 token”。业务应用还必须处理：

```text
用户是谁？
是否有权限访问数据？
当前任务是什么？
该用哪些真实工具和知识？
模型输出是否符合 schema？
写操作是否确认和幂等？
结果如何展示、保存、审计和评估？
```

这正是你前面学习 FastAPI、Java 服务、RAG、Agent、工具调用、评估、监控和企业控制面的价值。模型服务只是底座之一，不能取代完整应用架构。

### 12. 三种模型使用方式在生命周期中的位置

#### 12.1 云模型 API

```text
供应商负责：模型训练、权重、推理基础设施、底层服务
你的团队负责：选择模型、调用、业务上下文、工具、权限、评估、成本治理
```

优点是启动快、无需管理 GPU/权重和底层部署；代价是供应商依赖、数据治理边界、可控性、定价和配额约束。

#### 12.2 本地运行模型

```text
你负责：下载/管理模型文件、运行时、硬件资源、调用方式
```

适合学习、离线试验、个人开发或对数据不出本机有强要求的小规模场景。它不自动等于生产可用，仍要考虑硬件、并发、鉴权、升级、监控和故障恢复。

#### 12.3 自部署模型服务

```text
你/团队负责：模型产物、推理引擎、GPU/CPU、容器/网络、服务扩缩容、网关、监控、成本和安全
```

它提供更强的可控性和部署自由度，但运维与工程责任也更大。M13、M14 将逐步建立这部分知识。

### 13. 模型部署不是一次性动作，而是服务生命周期

把一个模型“部署”到服务器上，至少包含：

```text
选择模型和版本
-> 准备权重、配置、运行时和硬件
-> 启动推理服务
-> 健康检查和基础验证
-> 接入鉴权、网关、监控与限流
-> 灰度接流量
-> 观察质量、延迟、错误和成本
-> 扩容、替换、回滚或下线
```

其中“启动成功”只是开始。一个能监听端口的推理进程，距离可靠的模型服务还差：请求隔离、并发、资源控制、日志、告警、容量、版本和回滚等多个方面。

### 14. 模型生命周期中的四类版本

模型系统最常见的排障困难，是把所有变化归因于“模型变了”。实际上至少要区分：

| 版本类型 | 示例 | 为什么独立管理 |
| --- | --- | --- |
| 模型产物版本 | 权重、tokenizer、量化版本 | 直接改变基础生成能力和资源需求 |
| 推理服务版本 | 引擎、容器、运行参数 | 影响性能、兼容和输出行为 |
| 应用编排版本 | prompt、工具 schema、Agent 工作流 | 影响上下文、工具选择和输出格式 |
| 数据版本 | RAG 文档、embedding、索引、评估集 | 影响事实、引用和质量判断 |

例如同一个权重，换了 tokenizer、量化、系统提示词或知识库，都可能导致不同结果。能够分层记录，才能准确做回归分析与回滚。

### 15. 一个端到端例子：云模型 API 的实际生命周期

假设你开发“企业知识问答 Agent”，使用云端聊天模型。

```text
用户提问
-> 应用认证用户和租户
-> RAG 服务检索当前授权文档
-> Agent 控制层构造最小上下文和允许工具
-> 模型网关选择云模型、施加预算与限流
-> 云模型 API 进行推理，返回结构化答复/工具提议
-> 应用校验输出、执行受控工具、记录任务事件
-> 生成最终带引用答复
-> 保存 trace、模型版本、成本、评估信号
```

即使模型权重完全由云供应商托管，模型生命周期仍有你自己的部分：业务模型选择、提示版本、检索数据版本、工具策略、网关路由、评估和发布。

### 16. 一个端到端例子：自部署模型服务的生命周期

假设组织有数据不出内网或成本规模化需求，决定部署自己的推理服务。

```text
选择允许自部署的模型产物
-> 验证许可证、模型能力和硬件需求
-> 下载并校验权重、配置和 tokenizer
-> 选择推理引擎和量化精度
-> 在受控环境加载模型并启动 API 服务
-> 用小流量进行功能、性能和安全验证
-> 在网关后接入业务应用
-> 监控显存、延迟、吞吐、队列、错误和成本
-> 新模型版本灰度发布
-> 若质量/性能异常，路由回旧版本或云模型
```

这个例子解释了 M13 后面为什么会包含 GPU、显存、量化、KV Cache、Docker、网关、可观测性、微调和发布治理。它们都是自部署生命周期的一部分。

## 常见误区

### 误区 1：调用模型 API 就等于掌握模型部署

调用 API 主要使用了模型服务；部署需要理解并负责模型产物、硬件、推理引擎、服务、网络、鉴权、并发、监控、版本和回滚。两者相关，但责任范围不同。

### 误区 2：模型参数就是模型存储的原始知识库

参数从训练数据中学习统计模式，不是可直接查询、可精确删除、可逐条引用的文档库。需要新鲜、可引用、可授权知识时，RAG 与工具通常更合适。

### 误区 3：下载一个模型文件就等于完成本地部署

还需要匹配的配置/tokenizer、推理引擎、计算资源、服务接口、资源控制、错误处理和运维治理。下载权重只是准备资产。

### 误区 4：微调和 RAG 都是在“给模型加知识”，所以可以互换

RAG 在推理时提供可更新、可引用的外部知识；微调改变模型参数，更适合稳定任务模式、行为或格式。它们解决的问题、更新方式和治理成本不同。

### 误区 5：模型越大，应用一定越好

大模型可能能力更强，但也会带来更高延迟、成本、资源需求和部署难度。应用质量还由数据、RAG、工具、提示、工作流、权限和评估共同决定。

### 误区 6：模型服务成功返回 HTTP 200，就代表 AI 应用成功

HTTP 200 只说明请求在协议层可能成功。应用仍可能存在无依据回答、越权检索、错误工具选择、成本超标、业务状态不一致或用户体验问题。

### 误区 7：模型升级只要改一个 model 名称

模型升级可能同时影响 tokenizer、上下文、输出格式、工具调用、成本、延迟、量化、推理引擎和安全表现。应通过版本、评估、灰度和回滚管理。

## 本节练习

### 练习 1：区分对象

请分别说明下列对象主要是什么：模型权重、tokenizer、推理引擎、模型服务、模型网关。

答案：模型权重是训练得到的大量参数数值；tokenizer 负责把文本与 token ID 相互转换；推理引擎负责将权重加载到硬件并进行生成计算；模型服务将推理能力作为网络 API 提供；模型网关负责模型调用的鉴权、路由、限流、成本、观测等统一治理。它们相互依赖，但职责不同。

### 练习 2：判断数据该放在哪里

以下信息更适合进入微调数据、RAG/知识库、实时业务工具，还是用户记忆？

1. 每月会更新的退款政策。
2. 用户当前订单的物流状态。
3. 希望模型始终以固定 JSON 格式返回某类抽取结果。
4. 用户明确设置的答复语言偏好。

答案：1 更适合 RAG/知识库，因为需要更新、版本和引用。2 应从实时业务工具查询，因为它是权威且会变化的事实。3 可先用 Structured Output/Prompt；若任务稳定、高频且提示难以满足，再评估是否适合微调数据。4 适合经过授权和治理的用户偏好记忆。不能因为都是“信息”就把它们都塞入模型权重。

### 练习 3：解释云 API 的责任边界

使用云模型 API 时，供应商和应用团队各自通常负责什么？

答案：供应商通常负责基础模型训练、权重托管、底层 GPU/推理基础设施和对外模型服务；应用团队仍需负责模型选型、用户/租户权限、Prompt 与上下文、RAG、工具控制、业务流程、输出校验、成本预算、评估、日志和应用发布。使用 API 减少基础设施负担，但不免除应用工程责任。

### 练习 4：解释版本差异

同一业务应用的回答质量发生变化，但模型名称未变。请至少列出四类可能变化来源。

答案：可能是系统 prompt/Agent 工作流变了；RAG 文档、embedding、rerank 或索引版本变了；工具 schema 或业务工具返回字段变了；网关路由/推理参数/供应商底层版本变了；用户上下文或记忆检索策略变了；服务端量化、引擎或限流导致行为/超时变化。排障不能只盯模型名称。

## 自测题

### 自测 1：训练和推理的根本区别是什么？

答案：训练通过数据、损失计算和参数更新改变或产生模型权重；推理使用固定权重处理当前输入并生成输出。训练重点是学习，推理重点是服务请求、延迟、并发和资源效率。

### 自测 2：为什么模型权重、配置和 tokenizer 必须匹配？

答案：权重学习的是特定 token ID 与网络结构下的统计关系；配置定义网络如何构建，tokenizer 定义文本如何编码/解码。任一部分不匹配，都可能导致无法加载、输入输出错位或生成异常。

### 自测 3：为什么模型服务不等于 AI 应用？

答案：模型服务只负责接收输入并执行推理；AI 应用还要处理身份、权限、任务、知识、工具、输出校验、业务副作用、用户体验、评估和治理。模型是能力组件，应用才是解决用户问题的系统。

### 自测 4：模型网关的核心价值是什么？

答案：将模型调用的认证、模型路由、限流、预算、重试/回退、日志、trace 和成本统计集中治理，避免业务模块各自散乱调用不同模型服务，并支持多模型和生产运营策略。

### 自测 5：本节最重要的生命周期观点是什么？

答案：模型从训练或选择开始，经由模型产物、推理引擎、模型服务、网关和业务应用进入用户流程；上线后还需要评估、观测、版本、灰度、回滚与下线。模型部署不是一次启动，而是一套持续运行和治理的生命周期。

## 本节小结

本节建立了 M13 的总地图：模型权重是训练产物，tokenizer 负责文本与 token 的转换，推理引擎让模型在硬件上运行，模型服务将能力暴露为 API，网关和业务应用将其纳入权限、任务、工具、成本与治理体系。训练、微调、推理、部署和运营是同一条模型生命周期上的不同阶段。
