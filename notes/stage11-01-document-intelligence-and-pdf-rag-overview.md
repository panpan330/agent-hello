# M11 第 1 节：企业为什么需要文档智能与 PDF RAG

## 本节定位

阶段前置基础已经说明：企业文档 RAG 是证据加工与治理系统。本节进一步回答业务层的问题：为什么企业不能只靠文件夹、关键词搜索、数据库或模型记忆来解决文档问答？为什么 PDF RAG 会成为一个独立工程主题？

本节不讨论具体 PDF 库、OCR 产品或向量数据库参数。目标是建立正确的系统全景与技术边界，避免后续把所有问题都误归为“大模型效果不好”。

## 本节学习目标

学完后，你应当能：

1. 解释企业文档问答的真实困难来自哪里。
2. 区分文件存储、关键词搜索、RAG、微调、数据库查询和人工知识条目。
3. 画出 PDF RAG 从资料进入到用户回答的全链路。
4. 理解文档系统中管理员、用户和维护者的不同职责。
5. 说清楚一套知识库“可用”和“可信”的区别。

## 一句话先讲透

**企业需要 PDF RAG，不是因为 PDF 无法保存，而是因为人无法稳定地从大量、不断变化、带权限边界的资料中快速找出正确证据并解释给正确的人。**

## 基础知识铺垫

### 1. 企业文档问题首先是“知识发现”问题

企业通常不缺文件，缺的是把文件转成可用知识的能力。资料可能散落在网盘、邮件、共享目录、内部 wiki 和业务附件中；同一制度可能有草稿、旧版、正式版；用户也不一定知道应该搜哪个文件名。

例如用户问：

```text
活动商品签收后多久还能申请退款？
```

他真正需要的是：当前有效规则、适用商品范围、例外条件、原文依据，而不是 20 个文件名中恰好含有“退款”的 PDF。

### 2. 企业资料为什么比互联网搜索难

企业文档有几个额外约束：

```text
私有：模型的公共训练数据通常没有这些资料。
变化：政策、价格、流程和版本会更新。
权限：不同租户、部门和角色能看的内容不同。
风险：错误规则、错版本、错金额可能造成真实损失。
格式复杂：PDF、扫描件、表格、附件和图文混排并存。
可追责：用户和审核者需要知道答案依据。
```

因此，企业文档问答不是“让模型更聪明”这么简单，而是“让模型在正确、可访问、可核验的资料中工作”。

### 3. 搜索、RAG、微调、数据库各解决什么

| 方式 | 核心能力 | 适合场景 | 局限 |
| --- | --- | --- | --- |
| 文件夹/网盘 | 存放与人工浏览 | 文件量少、人工熟悉资料 | 难理解自然语言，难控制版本问答 |
| 关键词搜索 | 找精确词、编号、文件名 | 产品型号、条款号、已知关键词 | 用户换说法、同义表达时效果有限 |
| RAG | 找证据后生成自然语言回答 | 私有、更新快、需解释的资料 | 依赖资料加工与检索质量 |
| 模型微调 | 改变模型稳定行为或输出格式 | 分类、风格、固定任务模式 | 不适合频繁更新的事实资料 |
| 业务数据库 | 查询精确、实时、可事务处理的事实 | 订单、余额、库存、状态 | 不擅长长篇制度和自然语言说明 |
| 人工知识条目 | 高质量、严格受控答案 | 高风险、规则少且稳定的内容 | 维护成本高，覆盖范围有限 |

它们不是互斥技术。成熟系统往往同时使用：关键词补足精确召回，RAG 解释政策，数据库查询实时事实，人工条目承载高风险标准答案。

## 本节主题系统讲解

### 1. RAG 到底解决了什么

RAG 的全称是 Retrieval-Augmented Generation，检索增强生成。它不是把文档“教会”模型，而是在每次问题出现时，把相关外部证据检索出来，和问题一起交给模型。

```text
用户问题
-> 查找相关证据
-> 选择当前有效且有权限的资料
-> 将问题与证据提供给模型
-> 模型基于证据组织回答与引用
```

它的关键价值：资料可更新、私有资料可使用、回答可引用、错误可定位到证据链。它的关键限制：如果原始资料没解析好、没过滤权限、没找到例外，模型无法神奇补救。

### 2. 一套 PDF RAG 的完整架构

可以从三条链理解：

```text
离线加工：上传 -> 解析/OCR -> 清洗结构 -> 分块元数据 -> 向量/全文索引 -> 验证发布

在线问答：身份问题 -> 权限/版本过滤 -> 召回 -> 重排/上下文补全 -> 模型回答 -> 引用

知识治理：版本、生效、删除、重建、评测、bad case、审计和运营
```

离线链保证“资料做对”；在线链保证“证据找对、用对”；治理链保证“长期不变坏”。只做在线向量检索，系统会在资料更新、权限变化和错误反馈积累后失控。

### 3. 一个贯穿案例：售后政策助手

用户问：“活动商品可以提现吗？”系统需要的不是单一模型知识，而是：

```text
资料管理员发布的当前政策版本。
PDF 中“活动商品”章节、脚注和表格信息。
当前用户的租户与角色范围。
用户是否在问一般政策，还是某笔订单的实际资格。
回答依据对应的页码和版本。
```

若是一般政策问题，RAG 可基于文档回答；若问“我的订单”，还要用业务数据库查询订单类型、签收时间和状态。模型只负责把两类已确认信息解释清楚，不应自己判定未知事实。

### 4. 三类用户的不同需求

| 角色 | 主要关注 |
| --- | --- |
| 资料管理员 | 文件上传、分类、版本、生效、权限、失败处理 |
| 最终用户 | 快速得到易懂答案、依据、下一步动作 |
| 系统维护者 | 解析质量、检索、成本、权限、版本、错误定位 |

只站在最终用户角度，容易忽略更新和安全；只站在工程角度，又容易只展示分数和 ID，不给用户可核验的引用。企业系统必须同时服务三类角色。

### 5. “能用”与“可信”的区别

一个 Demo 能用，通常表示：上传文档后，问几个问题能得到看似合理的回答。

一个可信系统至少还应做到：

```text
能判断文件是否被可靠解析。
能知道回答来自哪份资料、哪版、哪页。
能过滤无权、草稿和过期内容。
能在证据不足时拒绝确定回答。
能在文档更新后让旧知识退出默认检索。
能把错误案例复现、修复并回归验证。
```

这就是 M11 存在的原因：把“RAG 能跑”提升到“文档知识能被信任”。

### 6. 方案选择从问题而非工具开始

面对“做 PDF RAG”需求，先问：

```text
资料有多少、更新多快、哪些是扫描件？
谁使用、资料是否多租户或分密级？
最严重的错误是什么：答错、越权、旧版本还是延迟？
用户需不需要查看原页、表格和版本？
是否需要查询历史时点规则？
无法确认时应转人工还是拒答？
```

这些答案才决定是否需要 OCR、复杂表格处理、多版本索引、细粒度权限、混合检索或人工审核。工具选择是结果，不是起点。

### 7. 文档 RAG 不应该做什么

```text
不应代替数据库保存实时订单事实。
不应以模型回答判定合同、签名或审批法律效力。
不应让模型决定用户权限。
不应把所有图片和附件不加判断地向量化。
不应把检索分数当作结论正确率。
不应在没有证据时用自然语言补齐企业规则。
```

明确“不做什么”，能避免把一个知识问答系统做成没有责任边界的万能助手。

## 常见误区

### 误区 1：RAG 比关键词搜索更强，所以可以完全替代搜索

不对。产品名、编号、条款号等精确条件仍常需要关键词或结构化过滤；实际系统常使用混合检索。

### 误区 2：资料经常更新，就应该微调模型

不对。频繁变化的事实更适合通过 RAG 在查询时读取当前资料；微调不适合作为版本治理手段。

### 误区 3：模型看见文档就会理解所有表格和例外

不对。模型输入依赖前面的解析、结构、分块和上下文选择。前面丢失的信息无法稳定恢复。

### 误区 4：只要答案里加文件名就算可引用

不对。可信引用应能定位文档版本、页码或章节，并真正支持相应结论。

## 本节练习

### 练习 1：为什么频繁更新的企业政策通常适合 RAG 而不是微调？

答案：RAG 在查询时检索当前资料，版本更新后可通过资料治理和索引发布生效；微调把知识固化在模型参数中，更新慢、难追溯、也难精确删除旧事实。

### 练习 2：用户问“我的订单能不能退款”时，RAG 与数据库分别提供什么？

答案：RAG 提供退款政策、条件和例外；数据库提供该订单的商品类型、签收时间、状态等实时事实。系统应结合受控业务规则处理，模型负责解释。

### 练习 3：为什么企业 PDF RAG 要有知识治理链？

答案：资料、版本、权限和处理规则会变化。治理链负责更新、失效、删除、重建、评测和审计，防止旧知识、重复知识和错误知识长期影响回答。

## 自测题

### 自测 1：RAG 的核心流程是什么？

答案：先检索与问题相关且当前可访问的外部证据，再将问题和证据交给模型生成回答，并尽量返回来源定位。

### 自测 2：企业文档系统的三类关键用户是谁？

答案：资料管理员、最终提问者和系统维护者；他们分别关注资料治理、回答体验与系统质量安全。

### 自测 3：本节最重要的结论是什么？

答案：PDF RAG 的价值是让企业资料以可更新、可授权、可追溯的证据形式服务问答。它是文档加工、检索、模型解释和长期治理的组合系统。
