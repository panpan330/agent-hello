# M12 第 1 节：高级 Agent 工程总览与适用边界

## 本节定位

M12 的第一节不急着讲队列、记忆或 Multi-Agent。先解决一个更重要的架构判断：

```text
一个需求到底需要普通接口、固定工作流、单 Agent、Multi-Agent，还是根本不应交给 Agent？
```

高级 Agent 的价值不来自“模型会自己想”，而来自在信息不完整、路径不固定、多工具协作的任务中，仍能保持受控推进。若任务本来完全确定，使用 Agent 反而会降低稳定性、增加成本和排错难度。

## 本节学习目标

学完后，你应当能：

1. 区分确定性业务流程、AI 辅助工作流和 Agent 任务。
2. 判断一个问题是否真的需要 Agent。
3. 理解单 Agent 与 Multi-Agent 的收益和成本。
4. 说明“自主性”为什么必须有范围、预算和权限边界。
5. 用工程语言解释为什么某些场景不应使用 Agent。

## 一句话先讲透

**Agent 不是比工作流更高级的默认方案；它只适合步骤无法完全预先写死、但目标、允许动作、风险边界和完成条件仍能被系统明确控制的任务。**

## 基础知识铺垫

### 1. 确定性与不确定性

传统业务系统擅长处理确定性：输入满足规则 A，就执行步骤 B；库存不足，就返回错误 C。

```text
创建订单
-> 校验参数
-> 扣减库存
-> 创建支付单
-> 返回订单号
```

流程的每一步、状态和异常大多已知，应由代码和规则引擎控制。

自然语言任务则常存在不确定性：用户表达模糊、资料分散、需要选择工具、需要补问信息、不同案例路径不同。Agent 的作用是处理这部分“有限范围内的路径选择”，而不是推翻确定性业务规则。

### 2. 自动化不等于 Agent

下面都属于自动化，但不一定需要 Agent：

```text
定时导入 CSV。
按固定模板生成日报。
订单超时后自动取消。
用户上传文件后执行固定 OCR 流程。
表单校验和状态流转。
```

只要步骤和分支能被开发者明确枚举，普通工作流通常更可靠、成本更低、更容易测试。

### 3. Agent 的核心特征

一个工程意义上的 Agent 至少有：

```text
目标：要完成什么。
状态：目前已知什么、已做什么。
可选动作：允许调用哪些工具或转人工。
观察：工具结果、用户补充、审批结果和异常。
决策：根据状态选择下一步。
边界：时间、步骤、成本、权限与终止条件。
```

如果只有“模型回答一句话”，它是 LLM 功能；如果步骤完全由代码预定义，它是工作流；只有当系统需要在受控动作中动态决定下一步时，才更接近 Agent。

## 本节主题系统讲解

### 1. 四种实现方式的选择

| 方式 | 路径是否预定义 | 模型是否决定下一步 | 典型场景 |
| --- | --- | --- | --- |
| 普通接口/规则 | 是 | 否 | 下单、扣款、权限、状态流转 |
| 固定工作流 + AI 节点 | 基本是 | 仅局部内容生成 | 文档摘要、固定分类、客服模板 |
| 单 Agent | 不完全是 | 是，在允许动作内 | 复杂问答、诊断、资料收集、受控任务执行 |
| Multi-Agent | 不完全是，且有分工 | 多个角色协作决策 | 跨专业任务、独立子问题、审查分离 |

选型顺序应从左向右。能用普通规则解决，就不要引入模型；能用固定工作流解决，就不要引入 Agent；单 Agent 已足够时，不要为了“高级”拆 Multi-Agent。

### 2. 判断是否需要 Agent 的五个问题

```text
1. 任务目标是否清楚，且有可验证的完成条件？
2. 完成路径是否真的无法完全预定义？
3. Agent 是否拥有有限、可审计的动作集合？
4. 工具结果是否会影响后续路径选择？
5. 错误或越权时，系统能否限制影响并转人工？
```

若第 1 或第 3、5 项回答是否定的，不应贸然使用 Agent。目标不清和动作无限，会让“自主”变成不可控。

### 3. 适合 Agent 的典型场景

#### 3.1 受控复杂客服

用户问题表达多样，可能需要检索政策、查询订单、补问信息、解释结果或请求创建工单。路径不固定，但工具集合、权限、写操作审批和成功条件可控。

#### 3.2 多资料诊断

例如排查某次失败：需要阅读日志、检索知识库、查询配置、归纳可能原因，并在无法确认时请求人工。Agent 可根据证据决定下一步，但不应直接修改生产环境。

#### 3.3 文档处理编排

面对不同类型文件，系统需要决定走文本提取、OCR、表格恢复或人工审核。前提是每种动作和质量门槛明确，不能让模型随意处理不可信文件。

### 4. 不适合 Agent 的场景

```text
金额计算、税率计算、库存扣减。
权限判定、风控拦截、合规规则。
固定审批流和确定状态机。
高频、低延迟、低容错的简单接口。
没有明确授权或无法审计的写操作。
无法验证完成条件的开放式任务。
```

这些问题应优先使用数据库、规则引擎、传统服务或人工流程。Agent 可以辅助解释，但不能成为权威执行者。

### 5. Agent 的自主性是一个刻度，不是开关

可以按自主程度分层：

| 等级 | 行为 | 示例 |
| --- | --- | --- |
| L0 | 只提供建议，不执行 | 给出排查步骤 |
| L1 | 自动读取资料和工具结果 | 查询订单、检索政策 |
| L2 | 在规则内执行低风险动作 | 创建草稿、生成摘要 |
| L3 | 执行高影响动作前请求审批 | 创建工单、外发消息 |
| L4 | 高自主执行 | 仅限边界极清楚、风险极低的受控环境 |

企业系统多数应停留在 L1-L3。L4 不代表更先进，而代表更高的安全、审计、恢复和责任要求。

### 6. 单 Agent 的收益和限制

单 Agent 具有一个统一任务状态和决策中心。优点：状态简单、成本低、容易追踪、上下文一致；缺点：职责太多时 prompt 和工具会膨胀，容易在计划、执行、审查之间自我确认。

单 Agent 是默认起点。只有当职责、上下文、权限或评估目标明显冲突时，才考虑拆分角色。

### 7. Multi-Agent 的真实成本

Multi-Agent 可能带来专业分工与并行，但同时增加：

```text
谁拥有最终状态？
Agent 间传递什么信息，是否泄露敏感内容？
两个 Agent 结论冲突怎么办？
如何防止互相循环调用？
如何计算总 token、工具成本和超时？
如何定位错误来自哪个角色？
```

因此 Multi-Agent 不是“多个专家更聪明”的简单加法，而是分布式任务协调问题。M12 后面会单独学习。

### 8. Agent 的最小安全合同

任何 Agent 设计前，都应明确：

```text
目标和成功条件。
允许工具与禁止工具。
可访问数据范围。
读操作与写操作的权限差异。
哪些操作需要用户/人工审批。
每任务的步骤、时间、token、费用预算。
失败、超时、冲突和取消时的状态。
审计记录的最小字段。
```

这份合同相当于 Agent 的“运行许可证”。没有它，模型的工具调用只是不可控脚本。

### 9. 一个决策案例

需求：“用户反馈物流长期没更新，系统帮忙处理。”

错误设计：让模型自由决定能做什么、直接调用所有工具。

更合理的拆分：

```text
固定规则：身份认证、订单归属、权限、状态合法性。
Agent 可做：查询订单、检索物流政策、解释异常、生成工单草稿。
需要确认：真正创建工单、发送外部通知。
不可做：直接修改订单状态、退款、调用未授权系统。
完成条件：给出有证据的解释，或在确认后创建可审计工单。
```

这就是“固定工作流和 Agent 协作”：确定部分由系统控制，不确定的资料收集和对话路径交给 Agent。

### 10. 如何评价一个 Agent 是否值得存在

不要只看它演示时能否完成一次任务。应问：

```text
相对固定工作流，它减少了多少人工分支或维护成本？
成功率、人工转交率、延迟、成本是否可接受？
失败时能否停止、解释和恢复？
是否出现越权、重复执行、无意义循环？
用户是否能理解和信任其结果？
```

若 Agent 没有带来足够收益，却增加大量不确定性，就应退回固定工作流或缩小 Agent 权限。

## 常见误区

### 误区 1：所有带模型的应用都应该做成 Agent

不对。大量任务只需模型作为固定工作流中的一个节点，甚至根本不需要模型。

### 误区 2：Agent 越能自由调用工具越有价值

不对。价值来自在授权范围内可靠完成目标。自由度越大，越需要更强安全与恢复机制。

### 误区 3：Multi-Agent 天然更准确

不对。角色拆分可能带来冲突、上下文丢失、成本和循环；必须证明其收益大于协调成本。

### 误区 4：只要最后让用户确认，前面可以随便调用读工具

不对。读数据也可能泄露隐私或机密；工具权限与数据权限在每一步都要控制。

## 本节练习

### 练习 1：判断“订单创建后自动发送短信”是否需要 Agent。

答案：通常不需要。触发条件、内容模板和发送步骤都可预定义，应由固定工作流实现；模型可选地生成文案，但不应决定业务状态或发送权限。

### 练习 2：为什么“查资料、补问信息、生成工单草稿”适合受控 Agent？

答案：用户表达与信息缺失使路径不固定，Agent 可在有限工具内选择下一步；但订单归属、权限、真正创建工单等确定且高风险部分仍由系统规则和审批控制。

### 练习 3：请说出两个不应由 Agent 决定的问题。

答案：例如权限是否通过、金额计算、库存扣减、订单状态流转、税率计算或合同法律效力。它们应由确定性系统或人工权威流程负责。

## 自测题

### 自测 1：Agent 与固定工作流最根本的区别是什么？

答案：固定工作流由开发者预先确定步骤与分支；Agent 在系统允许的动作范围内，根据状态和观察动态选择下一步。两者都应有边界与审计。

### 自测 2：Agent 自主性为什么不是越高越好？

答案：自主性会扩大行为空间、成本与风险。企业应按任务影响和可验证性选择恰当等级，并用权限、审批、预算与审计约束。

### 自测 3：本节最重要的结论是什么？

答案：Agent 是处理受控不确定性的工具，不是默认架构。先用确定性方案解决确定部分，只把路径选择交给有状态、有边界的 Agent。
