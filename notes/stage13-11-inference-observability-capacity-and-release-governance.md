# M13 第 12 节：推理服务观测、容量与发布治理

## 本节定位

模型服务上线后，最容易陷入一种错觉：接口返回 200、页面也能显示文字，于是服务“没问题”。但生成式 AI 的真实风险远不止 HTTP 成败：首字可能变慢、队列可能堆积、Token 成本可能失控、模型可能悄悄切换、结构化输出可能退化、工具调用可能失败、某个版本可能只在长上下文下出错。

本节讨论如何把这些不可见的问题变成可观察、可度量、可定位、可发布和可回滚的工程事实。它连接你此前学过的 Trace、评估、成本控制、模型路由、推理性能和部署架构。

本节仍是纯知识笔记，不要求连接监控平台或修改项目代码。

## 本节学习目标

学完后，你应当能够：

1. 区分日志、指标、Trace、事件和评估记录各自解决的问题。
2. 解释为什么模型调用需要 Token、TTFT、队列、模型版本、路由和质量等专用观测维度。
3. 理解 RED、USE、SLO、SLI、错误预算等传统可观测概念如何适配模型服务。
4. 设计一次模型调用最小而安全的观测字段集合。
5. 从请求分布、队列、吞吐、显存和 SLO 推导容量规划的基本方法。
6. 区分压力测试、负载测试、峰值测试、稳定性测试和发布前回归。
7. 说明模型、Prompt、RAG、引擎或配置变更为什么都需要受控发布与回滚。
8. 能解释“服务健康”应同时包含可靠性、性能、成本、安全和质量，而不只是一条 `/health`。

## 一句话先讲透

**模型服务治理的目标不是收集更多日志，而是让每一次异常都能回答五个问题：谁受影响、慢/错/贵在哪里、使用了什么版本和路径、是否突破服务目标、现在该如何止损和改进。**

## 基础知识铺垫

### 1. 可观测性不是“有日志”

可观测性（observability）强调：当系统内部状态无法直接看到时，能否根据它输出的证据推断发生了什么，并定位问题。

常见证据类型：

- **日志（logs）**：离散事件的详细记录，例如某请求被限流、模型加载失败、某条路由规则命中。
- **指标（metrics）**：可聚合的数值时间序列，例如每分钟请求数、P95 TTFT、GPU 显存、429 比例、Token 成本。
- **Trace（追踪）**：一次请求跨越多个服务和步骤的因果路径，例如浏览器 -> AI 服务 -> RAG -> 模型网关 -> 模型 API -> 工具服务。
- **事件（events）**：部署、配置变更、模型切换、告警确认、熔断打开等生命周期事实。
- **评估记录（evaluation records）**：模型输出是否正确、是否有引用、是否安全、是否满足结构化契约等质量证据。

它们不是互相替代：日志能看一条请求的细节，指标能看整体趋势，Trace 能看端到端瓶颈，事件能解释趋势为什么突然变化，评估记录能判断“返回成功”是否意味着业务正确。

### 2. 三种常见问题，需要不同证据

设用户投诉“AI 客服最近不好用”。这句话可能指：

| 现象 | 需要的主要证据 |
| --- | --- |
| 很久才出现第一个字 | TTFT、队列、长 Prompt、模型/网络 Trace |
| 回复到一半断了 | 流式结束原因、连接错误、容器重启、取消事件 |
| 回答质量下降 | 模型/Prompt/RAG 版本、评测集、人工标注、引用指标 |
| 费用突然增加 | 输入输出 Token、路由、重试、缓存命中、租户用量 |
| 某些用户总失败 | 身份/租户标签、权限规则、地域、限流、错误码 |

如果只记录 `request failed`，几乎无法区分这些问题。模型系统的观测字段必须与模型行为和业务风险对齐。

### 3. SLI、SLO、SLA 与错误预算

这些概念来自可靠性工程：

- **SLI（Service Level Indicator）**：实际测量的指标，例如“过去 5 分钟聊天请求的成功率”“P95 TTFT”。
- **SLO（Service Level Objective）**：内部希望达到的目标，例如“99% 的普通聊天请求 TTFT 小于 2 秒”。
- **SLA（Service Level Agreement）**：对外承诺，可能涉及合同、赔偿或服务条款。它通常比 SLO 更慎重。
- **错误预算（error budget）**：SLO 允许的失败空间。例如月成功率 SLO 为 99.9%，理论上约允许 0.1% 不满足目标。

模型服务可有多维 SLO，而不是只看可用性：

```text
可靠性：成功率、超时率、流中断率
交互性能：P95 TTFT、P95 总时延、P95 Token 间隔
质量：结构化输出合法率、关键任务评测分数、引用覆盖率
成本：每任务 Token 成本、预算超限率
安全：越权调用率、敏感数据策略拦截正确性
```

并非每个指标都适合一开始写进硬 SLO。重要的是先把业务目标和可测量指标连接起来。

### 4. 平均值为什么会骗人

假设 100 个请求中，95 个在 1 秒内返回，5 个等待 60 秒。平均响应时间约 4 秒多，看似还能接受；但那 5 个用户的体验非常差。

所以在线服务常看：

- **P50**：中位数，代表典型用户；
- **P95**：95% 请求不超过的值，反映多数用户的较差体验；
- **P99**：极端尾部，反映高峰、排队、资源争抢和异常情况；
- **最大值**：可辅助排查，但容易受异常点影响。

模型服务尤其容易出现长尾：一个超长 Prompt、一个慢工具、一次外部 API 波动、GPU OOM 恢复、模型冷启动都可能影响少量请求。只看平均值会让问题长期被掩盖。

### 5. 指标需要标签，但标签不能无限爆炸

指标常带标签（label/dimension），例如：

```text
model=support_chat_default
provider=cloud_a
environment=production
route=primary
status=success
```

标签让你能回答“是哪个模型、哪个环境、哪条路由变慢”。但把 `user_id`、`request_id`、完整订单号、完整 URL、原始 Prompt 作为指标标签会产生**高基数（high cardinality）**问题：每个值都不同，指标系统难以存储、聚合和查询。

规则很简单：

- 低基数、有限枚举值适合作指标标签，例如模型名、环境、错误类别、路由类型；
- 每请求唯一的信息放日志或 Trace，例如 request_id、用户标识（必要时脱敏）、完整错误详情；
- 敏感内容不应因为“方便筛选”就进入任何遥测系统。

## 本节主题系统讲解

### 1. 传统 RED 与 USE 如何用于模型服务

两组经典观测视角很有帮助。

#### 1.1 RED：面向请求服务

RED 指：

- **Rate**：请求速率，例如每秒聊天请求、每分钟输入/输出 Token；
- **Errors**：错误，例如 4xx、5xx、超时、流中断、结构化验证失败；
- **Duration**：时延，例如 E2E、TTFT、队列等待、工具耗时。

对模型 API，RED 可扩展为：

```text
请求速率：requests/s、active streams、input/output tokens/s
错误：HTTP 错误、provider 错误、限流、取消、schema failure、tool failure
时延：queue、prefill、TTFT、TPOT、E2E、RAG/tool 子阶段
```

#### 1.2 USE：面向资源

USE 指：

- **Utilization**：资源被使用的程度，例如 GPU 利用率、显存占用、CPU、网络；
- **Saturation**：资源是否处于排队/过载状态，例如队列长度、等待 Token、连接池等待；
- **Errors**：资源错误，例如 GPU OOM、磁盘满、节点故障、驱动错误。

模型服务里常见误区是只看 GPU 利用率。GPU 利用率低但请求很慢，可能是网络、Tokenization、长排队、单请求 decode、外部工具或路由错误；GPU 利用率高也可能是健康的高效运行，或是即将过载的征兆。需要结合队列、TTFT、显存和错误一起看。

### 2. 一次模型调用的端到端 Trace

一个典型 AI 请求可以拆为多个 span：

```text
HTTP 请求接入
  -> 用户认证/权限检查
  -> 会话历史读取
  -> RAG 检索
  -> Rerank
  -> Prompt 构建/Token 估算
  -> 模型路由
  -> 模型网关调用
  -> 推理队列
  -> prefill / 首 Token
  -> 流式输出
  -> 工具执行（如果有）
  -> 结果校验/引用整理
  -> 返回用户
```

Trace 的价值在于回答“慢在哪里”。若 E2E 为 8 秒：

- RAG 可能占 5 秒，模型 TTFT 仅 500ms；
- 模型排队可能占 4 秒，推理本身不慢；
- 外部工具调用可能在模型生成后卡住；
- 网关重试可能让同一调用被发了两次；
- 客户端网络可能使用户晚看到内容。

没有统一 Trace ID，这些事实散落在多个服务日志中，很难关联。Trace ID 应在入口生成或接收，并沿网关、RAG、模型、工具调用传播。

### 3. 模型调用最小观测字段

一次模型调用不需要记录全部 Prompt 才能有用。可以按类别设计：

#### 3.1 身份与关联

```text
trace_id / request_id
environment
calling_service
业务场景或 task_type
tenant / user 的受控、脱敏标识（若确有必要）
```

#### 3.2 路由与版本

```text
logical_model
actual_model_id
model_version / deployment_version
provider / region
route_reason
is_fallback / degradation_mode
prompt_template_version
retrieval_index_version（如相关）
```

#### 3.3 性能与用量

```text
input_tokens
output_tokens
cached_tokens（若提供）
queue_ms
ttft_ms
e2e_ms
completion_reason
streamed
retry_count
```

#### 3.4 结果与错误

```text
http_status
normalized_error_type
provider_error_code（受控记录）
schema_valid
tool_call_count / tool_result_status
content_policy_result
```

#### 3.5 成本与治理

```text
estimated_cost
budget_bucket
data_classification
redaction_applied
audit_policy_id
```

字段要按最小必要原则确定。真正需要查看内容时，应走受控调试、抽样、脱敏和权限流程，而不是默认把所有输入输出永久保存在普通日志里。

### 4. 模型特有的性能拆分

普通 HTTP API 常只看“总耗时”。模型调用应进一步拆解：

```text
client/network time
gateway processing
queue wait
prompt/tokenization
prefill
time to first token
decode duration / inter-token latency
post-processing
tool/RAG duration
response delivery
```

几个关键关系：

- `E2E` 高而 `TTFT` 低：用户能较快看到首字，可能只是输出长或后续 Token 慢；
- `TTFT` 高而 GPU 利用率低：可能是网关、排队配置、Tokenizer 或冷启动问题；
- `TTFT` 高且队列高：容量不足或调度不合理；
- `TTFT` 高且输入 Token 突增：长 Prompt/RAG 上下文可能是原因；
- `E2E` 高但模型 span 短：慢点在检索、工具、数据库或网络；
- 输出 Token 突增：可能是 Prompt 改动、停止条件失效或模型版本行为变化。

这些不是机械诊断规则，而是帮助你快速提出可验证假设。

### 5. Token 是性能和成本的共同单位

模型服务中，Token 是连接性能、容量和成本的关键数据：

- 输入 Token 大，prefill 时间和上下文费用常增加；
- 输出 Token 大，decode 时间和输出费用常增加；
- 并发活跃 Token 大，KV Cache 显存压力上升；
- 重试/回退会将同一业务任务的 Token 消耗放大；
- RAG 文档、工具 Schema、系统提示和历史消息都可能造成隐性 Token 膨胀。

因此仅统计“请求数”常常不够。一个 100 Token 的聊天与一个 100,000 Token 文档任务对资源影响完全不同。

建议至少按任务、模型、租户或路由统计：输入 Token、输出 Token、总 Token、失败 Token、重试 Token、缓存命中 Token（若有）和每成功任务 Token。这样能发现“成功率没变但成本翻倍”的隐性回归。

### 6. 成本可观测性：从调用量到单位业务价值

成本治理可分三层：

#### 6.1 基础用量

每模型、每提供方、每环境的输入/输出 Token、请求数、重试数、并发和时间。

#### 6.2 归因成本

将成本关联到租户、业务功能、任务类型、Prompt 版本、RAG 策略、模型路由和工具链。这样可以发现“哪个功能贵”，而不是只知道总账单高。

#### 6.3 单位价值成本

进一步问：每次成功解决问题、每个完成工单、每篇成功入库文档、每次人工节省所花成本是多少？

这一步最难，因为“成功”需要业务定义和质量证据。但它能避免两个极端：只压低单次 Token 成本导致大量低质量重试；或只追求最佳模型质量却忽略业务收益是否匹配成本。

### 7. 从指标到告警：告警必须可行动

一个告警应能回答：谁需要做什么。如果告警只说“GPU 指标异常”，接收者不知道该扩容、回滚、熔断还是忽略，就会造成告警疲劳。

模型服务可设计的可行动告警例子：

- 某逻辑模型的 P95 TTFT 连续 10 分钟超 SLO：检查队列、长输入、模型副本和外部提供方状态；必要时限流或回退。
- 流式中断率突然上升：检查网关超时、容器重启、客户端取消和网络。
- 某模型的输入 Token P95 异常翻倍：检查 Prompt、RAG top-k、历史拼接或工具 Schema 变更。
- JSON Schema 验证失败率超过阈值：暂停该模型/Prompt 灰度或切回旧版本。
- 429/配额拒绝快速增加：检查突发流量、租户滥用、供应商额度和路由配置。
- GPU OOM 或模型副本反复重启：摘除实例、保护流量、检查容量和模型/参数版本。
- 单租户成本超预算：限额、降级、通知或人工审批，而非等账单结束才发现。

告警通常需要“持续时间 + 阈值 + 影响范围”，不能因一个偶发慢请求就立即惊动所有人。

### 8. 容量规划：先构建需求画像

容量规划的第一步不是买硬件，而是建立需求画像：

- 每类任务的到达率：平均、峰值、突发；
- 输入/输出 Token 的 P50/P95/P99；
- 流式比例、取消率、工具调用比例；
- 模型、量化、上下文长度和路由分布；
- SLO：TTFT、总耗时、成功率、最大排队时间；
- 可接受的降级策略；
- 计划中的增长、营销活动、批任务和发布窗口。

缺少 Token 长度分布是常见盲区。只用“每天 1 万请求”做容量估计，无法区分一万个短 FAQ 与一万个长文档总结。

### 9. 一个简化的容量推导过程

假设某类在线聊天有以下目标：

```text
峰值到达率：每分钟 600 请求
P95 输入：2,000 Token
P95 输出：400 Token
P95 TTFT：小于 2 秒
P95 完成时间：小于 15 秒
```

正确做法不是用这几行数字直接得出“需要 X 张卡”，因为模型、量化、引擎、GPU 和并发策略都会改变结果。更可靠的过程：

1. 在候选模型和目标硬件上，用接近真实长度分布的压测数据预热。
2. 逐渐提高并发或到达率，记录 TTFT、TPOT、E2E、队列、Token 吞吐、显存和错误率。
3. 找到仍能满足 SLO 的稳定区间，而不是最高 tokens/s 的极限点。
4. 估算该区间内单个副本可承担的负载。
5. 根据峰值、冗余、发布和单副本故障要求计算副本数。
6. 再考虑 GPU 资源池、网络、网关、数据库/RAG、外部 API 的容量，避免只扩模型导致其他层成为瓶颈。

容量规划是持续过程。实际流量和模型版本变化后，需要用线上数据修正假设。

### 10. 压测类型：不要只跑一次并发脚本

#### 10.1 基准测试（benchmark）

测单模型/单引擎在固定硬件、固定输入输出下的性能。适合比较配置，但不代表生产。

#### 10.2 负载测试（load test）

模拟预期正常和峰值流量，验证是否满足 SLO、队列和错误目标。

#### 10.3 压力测试（stress test）

逐步超过设计容量，观察系统何时退化、如何拒绝、是否能恢复。目标不是追求压垮，而是验证保护机制。

#### 10.4 峰值/突发测试（spike test）

突然提高流量，验证限流、队列、弹性、缓存和回退是否能应对突发。

#### 10.5 稳定性测试（soak test）

在较长时间保持负载，发现内存泄露、Cache 碎片、日志膨胀、连接泄露、成本累积和性能衰减。

#### 10.6 质量回归测试

对固定评测集比较模型/Prompt/RAG/引擎配置变更前后的回答质量、结构化输出、工具安全和引用。它不替代性能压测，二者都需要。

### 11. 发布治理：什么变化算一次“模型发布”

以下变更都可能影响线上行为，应纳入发布治理：

- 模型权重、量化版本、Tokenizer 或聊天模板；
- 推理引擎、容器基础镜像、CUDA/驱动组合；
- 采样参数、最大上下文、最大输出、停止词；
- Prompt 模板、安全策略、工具 Schema；
- RAG 索引、切分、Embedding、Rerank 配置；
- 模型路由、回退和成本规则；
- 网关超时、重试、限流、并发和缓存设置。

“没有改业务代码”不意味着没有发布风险。模型系统的行为由大量配置和数据共同决定，版本管理必须覆盖这些资产。

### 12. 发布前的最小验证门

一个务实的发布门可包含：

1. **配置与资产确认**：模型、Tokenizer、Prompt、RAG 索引、规则、镜像版本可追溯。
2. **契约测试**：API、流式、JSON Schema、工具调用和错误形态仍满足调用方需要。
3. **关键质量回归**：覆盖高风险场景、典型任务、拒答、安全和引用。
4. **性能基线**：在代表性负载下，TTFT、E2E、Token 吞吐和资源不出现不可接受回归。
5. **安全与数据检查**：密钥、数据外发、权限和日志策略没有被破坏。
6. **回滚准备**：旧版本、路由配置、索引或镜像是否可恢复，负责人和触发条件是否明确。

这不是要求每次都做巨大流程。低风险的内部 Prompt 文案与高风险模型/工具/数据策略变更可采用不同级别的发布门；关键是风险越大，证据越充分。

### 13. 灰度、A/B 与影子流量的不同用途

#### 13.1 灰度（canary）

让少量真实用户流量进入新版本，观察错误、延迟、成本和业务质量，发现问题可快速停止。适合验证真实环境兼容性。

#### 13.2 A/B 测试

将用户或请求随机分组，比较不同版本对明确业务指标的影响，例如解决率、满意度、人工转接率。它需要实验设计、样本量和风险控制。

#### 13.3 影子流量（shadow traffic）

复制部分真实请求给新版本，但不将结果返回用户，用于比较性能和输出。它可降低用户风险，但会增加成本与负载，还必须处理敏感数据、日志和绝不能重复执行写工具的问题。

三者都不是“把新模型开一开”。要预先定义观察指标、停止条件、样本范围、数据脱敏、成本预算和回滚方式。

### 14. 回滚：回到什么，如何证明已恢复

模型系统的回滚对象可能包括：

- 模型/量化版本；
- 推理引擎镜像；
- Prompt 或工具 Schema；
- RAG 索引或检索策略；
- 路由与回退规则；
- 配额、超时和缓存配置。

因此“回滚”不能只理解为重新部署旧容器。需要明确版本对应关系。例如模型已回到旧版，但 Prompt 保持新格式，可能仍然失败；RAG 索引已替换，旧模型的回答质量也可能不同。

回滚成功也不是控制台显示“部署完成”。应检查关键 SLI：错误率是否恢复、TTFT 是否回落、Schema 合法率是否恢复、成本是否正常、用户投诉是否下降，并留下事件记录。

### 15. 质量观测：把模型行为接入运营闭环

技术监控会告诉你服务是否可用，却不能完全告诉你回答是否对。质量观测可以包括：

- 离线基准集分数和关键案例通过率；
- 结构化输出/工具参数校验失败率；
- RAG 引用覆盖率、引用可验证率和无证据回答率；
- 人工转接率、用户追问率、重复提问率、负反馈率；
- 安全策略拦截、越权尝试、Prompt Injection 命中；
- Bad Case 新增、修复、回归状态；
- 人工抽样标注和标注一致性。

要谨慎解释这些指标：人工转接率上升可能是模型变差，也可能是业务规则调整；用户追问率下降可能是答案更好，也可能是用户放弃了。质量指标需要与场景、版本和人工调查结合。

### 16. 发布事件必须进入观测时间线

当 P95 TTFT 在 14:00 突然上升，最有价值的信息常常是：14:00 是否发生了模型升级、Prompt 改动、RAG 重建、节点扩缩、供应商切换或流量活动。

因此应将下面事件写入观测时间线：

- 部署开始、完成、失败、回滚；
- 模型上/下线、路由权重改变；
- Prompt/RAG/工具/安全规则版本切换；
- 限流、熔断、降级策略触发；
- 容量扩缩、节点故障与恢复；
- 预算阈值、供应商配额、重大外部故障。

这使指标图不再只是曲线，而能与变化建立因果假设。注意事件记录不能替代严谨验证，但能大幅减少盲查范围。

### 17. 一个可操作的故障响应流程

可用以下顺序处理模型服务异常：

1. **确认影响**：哪些逻辑模型、区域、租户和任务受影响？是全部失败、变慢、变贵还是质量异常？
2. **保护用户**：必要时限流、熔断异常路径、切换已验证备用、降级非关键能力或转人工。
3. **用 Trace 定位层次**：入口、业务、RAG、网关、队列、模型副本、GPU、外部供应商、工具中的哪一层异常？
4. **检查最近变化**：模型、Prompt、索引、配置、部署、流量、供应商状态。
5. **选择可逆动作**：回滚、摘除副本、恢复旧路由、暂停批任务、扩容或修复配置。
6. **验证恢复**：观察相关 SLI、质量抽样和用户路径，而不是只看进程重启。
7. **复盘与预防**：补监控、测试、容量余量、运行手册、发布门或路由保护。

这个过程的核心是先止损再深挖，先证据后猜测。模型输出不可预测不等于系统运行不可管理。

## 常见误区

### 误区 1：返回 200 就说明模型服务健康

纠正：200 只能证明某次 API 调用成功。还要看 TTFT、队列、流中断、结构化契约、质量、成本、安全和版本行为。

### 误区 2：只看平均延迟即可

纠正：模型服务常有长尾。P95/P99、最大排队、TTFT 和不同任务类型的分布更能反映用户体验与容量风险。

### 误区 3：记录完整 Prompt 才能排查问题

纠正：大量问题可通过版本、Token、路由、耗时、错误、校验和抽样得到定位。默认记录全量内容会造成隐私、合规、成本和访问控制风险；应采用最小化、脱敏和受控调试。

### 误区 4：GPU 利用率高就是好，低就是坏

纠正：高利用率可能代表高效运行，也可能表示资源饱和、队列恶化；低利用率可能代表空闲，也可能是网络/单请求/调度瓶颈。必须和 SLO、队列、显存、Token 吞吐和错误一起判断。

### 误区 5：压测跑出最高吞吐就是容量结论

纠正：最高吞吐点可能早已违反 TTFT/P95、产生大量队列或接近 OOM。容量应以满足业务 SLO 的稳定区间为准，并考虑故障冗余和发布余量。

### 误区 6：只在升级模型权重时做发布治理

纠正：Prompt、工具 Schema、RAG 索引、量化、引擎、路由、超时和缓存配置都可能显著改变行为、质量和成本，同样需要版本、验证和回滚。

### 误区 7：告警越多越安全

纠正：不可行动的告警会造成疲劳，真正重要的信号被忽略。告警应关联影响、持续时间、阈值、责任人和推荐动作。

## 本节练习

### 练习 1：为“慢”设计排查字段

用户报告聊天变慢。请列出至少八个你希望从一条 Trace 或关联指标中看到的字段/阶段。

答案：可包括 trace_id、逻辑/实际模型和版本、路由/是否回退、输入输出 Token、RAG 检索耗时、Rerank 耗时、模型网关耗时、队列等待、TTFT、Token 间隔、E2E、重试次数、工具耗时、HTTP/流结束原因、实例/GPU 标识、时间窗口内同模型的 P95。字段应帮助判断慢在输入、队列、推理、工具还是网络。

### 练习 2：解释高平均成功率下的坏体验

某服务成功率 99.8%，平均总耗时 2 秒，但用户仍大量投诉。请给出至少四种可能原因。

答案：可能是少量请求的 P95/P99 非常慢；TTFT 高导致用户长时间看不到首字；流式中断后仍被统计为成功；模型回答质量下降但 HTTP 成功；特定租户/地区/任务持续失败被平均数掩盖；输出过短或结构化字段不合法；成本/限流造成部分用户体验差。需要按任务、模型、租户和版本拆分指标并看 Trace 与评估。

### 练习 3：设计一个可行动告警

请为“主聊天模型可能容量不足”设计一个告警条件和第一步处置动作。

答案：例如：`support_chat_default` 在生产环境连续 10 分钟 P95 queue_ms 超过 1 秒且 P95 TTFT 超过 2 秒，同时活跃请求/Token 接近已验证容量上限。第一步可暂停低优先级批任务、检查异常长 Prompt 与流量突发、将满足条件的低风险请求切到已验证备用模型或增加健康副本；同时保留 Trace 和发布事件用于定位。阈值应由该服务的实际 SLO 和压测基线决定。

### 练习 4：判断发布风险

以下哪些变化应纳入模型发布治理：修改 system prompt 一句话；切换 Embedding 模型；把 `max_output_tokens` 从 512 改为 4096；升级 GPU 驱动；修改 Rerank top_n；新增一个备用模型。说明理由。

答案：全部都应纳入，只是验证强度可不同。Prompt 会改变质量与安全；Embedding 切换会影响向量空间和索引兼容；输出上限会影响延迟、成本和显存；驱动会影响运行稳定性与性能；Rerank 参数会改变 RAG 召回质量与 Token 成本；备用模型会影响回退路径与数据治理。每类都至少需要版本记录、受控验证和可回滚方式。

### 练习 5：区分负载测试和稳定性测试

为什么在 10 分钟内跑满并发仍不足以证明模型服务可以长期运行？

答案：短时间测试可能看不到 KV Cache/内存碎片累积、内存泄露、日志膨胀、连接泄露、缓存失效、供应商配额周期、磁盘增长、长期成本和模型副本性能衰退。稳定性测试需要在代表性负载下持续较长时间，并观察资源趋势、错误和尾延迟。

## 自测题

### 自测 1：日志、指标和 Trace 的主要区别是什么？

答案：日志记录单个离散事件的详细上下文；指标以可聚合时间序列显示趋势和告警；Trace 把一次请求跨服务的因果路径连接起来。模型系统还需要版本事件和质量评估记录，才能解释“为什么变化”和“是否答对”。

### 自测 2：模型服务为什么要同时统计输入和输出 Token？

答案：输入 Token 影响 prefill、上下文成本和可能的队列压力；输出 Token 影响 decode 时间、输出成本和 KV Cache 生命周期。两者分别变化时，根因和优化方向不同。

### 自测 3：什么是错误预算的实际意义？

答案：它把可靠性目标转化为可管理的容忍空间。当服务消耗错误预算过快时，应减少高风险发布、优先修复稳定性或启用保护措施；它不是允许忽略错误，而是帮助团队在速度和可靠性间做明确决策。

### 自测 4：为什么模型系统回滚可能比普通 API 回滚复杂？

答案：影响输出的资产不只代码和容器，还包括模型权重/量化、Tokenizer、Prompt、工具 Schema、RAG 索引、路由、配置和运行时。只回滚其中一个可能无法恢复原行为，因此需要记录版本组合和验证恢复效果。

### 自测 5：容量规划的可靠依据是什么？

答案：基于真实或代表性请求分布、明确 SLO、目标模型/硬件/引擎配置下的压测和线上数据，找到满足延迟、成功率和资源安全余量的稳定区间，并考虑峰值、冗余、发布和故障情况。不是只看请求数或理论 GPU 算力。

## 本节小结

模型服务治理要同时观察可靠性、性能、成本、安全和质量。日志、指标、Trace、版本事件和评估记录各自提供不同证据；TTFT、队列、输入输出 Token、路由、模型版本、结构化校验和成本归因是模型系统特别重要的观测内容。

容量规划应从请求和 Token 分布、SLO、压测与冗余出发，而发布治理应覆盖模型、Prompt、RAG、引擎、路由和配置等全部行为资产。只有能观测、灰度、回滚、复盘的模型服务，才真正具备持续演进的基础。
