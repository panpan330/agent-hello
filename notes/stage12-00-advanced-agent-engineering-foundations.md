# M12 阶段前置基础：高级 Agent 工程的统一模型

## 为什么 M12 需要前置基础

你前面已经学过 Tool Calling、Agent Loop、LangGraph、Human-in-the-loop、状态持久化与权限控制。M12 不是重复这些名词，而是继续回答一个更难的问题：

```text
当 Agent 不再只完成一次短对话，而要执行多步骤、耗时长、可暂停、可恢复、需要人批准、甚至需要多个角色协作的任务时，系统应如何设计？
```

如果没有统一模型，后面“任务队列、记忆、Checkpoint、Sandbox、Multi-Agent、浏览器 Agent”会像互不相干的流行词。实际上，它们都围绕同一件事：**怎样让一个由模型参与决策的任务，在真实系统中可控地推进、停止、恢复、审计和纠错。**

## 学习目标

读完后，你应当能：

1. 区分 LLM、工作流、Agent 与 Multi-Agent。
2. 解释 Agent 的目标、状态、动作、观察、记忆和终止条件。
3. 理解短任务与长任务在工程上的根本区别。
4. 说明为什么 Agent 必须有权限、审批、审计、超时和恢复机制。
5. 建立 M12 后续所有主题的共同心智模型。

## 一句话先讲透

**高级 Agent 工程不是让模型“更自由”，而是把模型参与的任务决策放进一个有状态、有边界、有恢复能力、有人工控制点的工程系统。**

## 第一部分：先区分四个容易混淆的概念

### 1. LLM 调用

一次 LLM 调用是：输入 prompt，得到输出。它可能很有用，但本身没有任务生命周期、不会保存状态，也不能可靠执行外部动作。

```text
问题 -> 模型 -> 回答
```

适合摘要、分类、抽取、改写、问答等单步任务。

### 2. 工作流

工作流（workflow）是由开发者预先确定步骤和分支的流程：

```text
表单校验 -> 查询订单 -> 调用支付 -> 创建工单 -> 通知用户
```

每一步、顺序和条件大体可预期。工作流的优点是稳定、可测试、可审计；缺点是面对开放式自然语言任务时不够灵活。

### 3. Agent

Agent 指系统在一个目标下，能根据当前状态和观察结果选择下一步动作的执行者。它不等于“大模型聊天”：

```text
目标：解决用户的退款问题。
状态：已知订单号、用户身份、已查到的资料、当前步骤。
动作：检索政策、查询订单、请求确认、创建工单、停止。
观察：工具返回、用户补充、错误、审批结果。
```

模型可参与“下一步选择”，但 Agent 仍需系统提供状态、工具、权限、终止条件和安全控制。

### 4. Multi-Agent

Multi-Agent 不是“一个任务多调用几个模型”就成立。它意味着多个有明确职责、输入输出和交接规则的 Agent 协作，例如：

```text
Supervisor：分配任务与控制全局。
Retriever：负责资料检索。
Order Specialist：负责订单事实分析。
Policy Specialist：负责制度解释。
Reviewer：检查证据、风险与输出。
```

如果一个 Agent 已能稳定完成任务，拆成多个 Agent 只会增加状态、通信、成本和调试复杂度。Multi-Agent 是架构选择，不是默认升级。

## 第二部分：一个 Agent 的最小模型

可把 Agent 看成一个受控循环：

```text
读取当前状态
-> 理解目标与约束
-> 选择下一步动作
-> 执行动作或等待外部结果
-> 把观察结果写回状态
-> 判断继续、暂停、成功、失败或转人工
```

这和传统状态机很接近。模型只是帮助选择部分动作；系统必须定义哪些状态存在、哪些动作允许、什么情况下不能继续。

### 1. 目标

目标不是一句模糊的“帮用户解决问题”。一个可执行目标要包含范围和完成标准：

```text
在用户已授权范围内查询订单 A1001 的物流状态；
若存在异常，给出政策依据；
如需创建工单，先获得用户确认；
成功条件是得到可引用回答或创建一张可审计工单。
```

目标越模糊，Agent 越容易无限探索或越权执行。

### 2. 状态

状态是任务到目前为止已知和已发生的事实，例如：

```text
task_id、用户身份、目标、当前步骤。
已识别意图、已调用工具、工具结果。
检索证据、待确认动作、审批结果。
重试次数、错误信息、完成结果。
```

状态不能只放在模型上下文里。长任务、服务重启、人工审批和并发访问都要求状态能被持久化、版本化和审计。

### 3. 动作与工具

动作可以是纯推理动作，也可以是外部工具调用。真实高风险动作通常包括读数据、写数据、发消息、执行命令、访问浏览器。

工具不应由模型任意创造。系统应为工具定义：输入 schema、权限、超时、重试、幂等性、审计字段、错误类型和输出边界。

### 4. 观察

观察是 Agent 决策的反馈来源：工具结果、用户补充、审批结果、任务进度、异常或超时。没有可靠观察，Agent 只是在猜测自己是否成功。

### 5. 终止条件

Agent 必须知道何时停止：

```text
目标已达成。
证据不足，需要用户补充。
需要人工审批。
工具连续失败或超过重试上限。
超过时间、成本或步骤预算。
发现权限不足或安全风险。
```

没有终止条件的 Agent Loop 容易无限调用模型和工具，成本与风险都会失控。

## 第三部分：短任务与长任务

短任务常在一次 HTTP 请求中完成：用户提问，系统检索、调用模型、返回答案。它通常秒级完成，可用简单同步模型处理。

长任务则可能：

```text
等待文件解析、外部系统、人工审批或浏览器操作。
包含数十步，运行分钟、小时甚至更久。
服务重启后仍要恢复。
用户可能取消、修改目标或离开页面。
需要展示进度并允许查询任务状态。
```

长任务不能依赖一次 HTTP 连接一直挂着。它需要任务 ID、持久状态、异步执行、队列、Checkpoint、超时、取消和恢复机制。M12 第 5、6 节会深入这些内容。

## 第四部分：记忆不是“把聊天记录都塞回去”

Agent 常被说有“记忆”，但记忆至少分四类：

| 类型 | 保存什么 | 典型用途 |
| --- | --- | --- |
| 上下文/短期记忆 | 当前会话最近信息 | 当前对话连贯性 |
| 工作记忆 | 当前任务计划、工具结果、待办 | 多步骤任务推进 |
| 长期记忆 | 用户偏好、稳定事实、经验 | 跨会话个性化与复用 |
| 检索记忆 | 通过 RAG 找到的资料 | 外部知识证据 |

所有历史消息都塞进 prompt，会导致成本高、噪声多、隐私与过期信息风险。记忆需要选择、摘要、过期、权限和删除策略，而不是无限累积。

## 第五部分：为什么人工必须保留控制权

Human-in-the-loop 不只是“让用户点确定”。它承担不同层级：

```text
输入确认：用户确认目标、订单、范围。
执行审批：写操作、付款、外发消息前批准。
异常介入：模型不确定、资料冲突、工具失败时转人工。
质量审核：高风险文档、合同、金额、政策结论复核。
结果接管：人可以修改、拒绝、终止或恢复任务。
```

审批点要放在真实风险边界，而不是每一步都让人点击。过少会越权，过多会让 Agent 没有实际价值。

## 第六部分：安全边界为什么会在 M12 变得更重要

Agent 的风险高于纯问答，因为它可能调用工具、写数据、访问外部网络或控制浏览器。需要多层防线：

```text
身份与权限：谁能发起什么任务。
工具白名单：模型只可选择允许工具。
参数校验：工具输入必须符合 schema 和业务规则。
最小权限：工具令牌只拥有必要资源范围。
审批与幂等：高风险写操作需要确认，重试不会重复执行。
Sandbox：不可信代码、文件、网络和命令在隔离环境中运行。
预算：限制步骤、时间、token、工具调用和成本。
审计：记录谁、何时、为什么、使用什么证据和工具执行了什么。
```

安全不是给模型一条“请谨慎”的 prompt，而是系统用规则限制模型能够看到和做到的事情。

## 常见误区

### 误区 1：Agent 就是“能调用工具的聊天机器人”

不够准确。工具调用只是能力之一；真正 Agent 还要有目标、状态、观察、动作边界与终止条件。

### 误区 2：Agent 越自主越高级

不对。企业系统追求的是恰当自主：低风险动作可自动化，高风险动作受权限、审批、预算与审计约束。

### 误区 3：Multi-Agent 一定比单 Agent 强

不对。协作带来通信、冲突、状态一致性、成本和调试复杂度。单 Agent 能稳定完成时不应拆分。

### 误区 4：任务状态就是聊天记录

不对。聊天记录只是短期上下文的一部分；任务状态还需要工具结果、进度、权限、审批、错误、版本与恢复点。

### 误区 5：有人工审批就不需要安全控制

不对。审批不能替代最小权限、参数校验、隔离和审计。人也可能误点或无法检查复杂请求。

## 本篇练习

### 练习 1：分别说明 LLM 调用、工作流、Agent 和 Multi-Agent 的核心区别。

答案：LLM 调用是一次输入输出；工作流的步骤由开发者预定义；Agent 根据目标、状态和观察选择下一步动作；Multi-Agent 是多个职责明确的 Agent 按交接规则协作。它们可组合，但不是同义词。

### 练习 2：一个可执行的 Agent 目标为什么不能只写“帮用户解决问题”？

答案：它缺少范围、授权、成功条件和终止边界，容易导致无限探索或越权。可执行目标要明确对象、允许动作、完成标准和需要人工介入的条件。

### 练习 3：为什么长任务不能仅依赖一次 HTTP 请求？

答案：它可能等待很久、经历重启、需要审批或取消。需要任务 ID、异步执行、持久状态、Checkpoint、超时和恢复机制。

## 自测题

### 自测 1：Agent 的最小循环由哪些部分构成？

答案：读取状态，理解目标和约束，选择动作，执行并获取观察，更新状态，然后继续、暂停、完成、失败或转人工。

### 自测 2：为什么 Agent 记忆不能等同于完整聊天历史？

答案：不同记忆有不同用途、权限和生命周期。无限历史会增加成本、噪声、过期和隐私风险；应有工作记忆、长期记忆和检索记忆等明确策略。

### 自测 3：本篇最重要的结论是什么？

答案：高级 Agent 工程的核心是受控任务执行。模型只是决策参与者，状态、工具、权限、审批、预算、恢复和审计必须由系统保证。

## 小结

从这一篇开始，M12 每节都围绕同一个问题展开：如何让 Agent 在真实任务中既有行动能力，又不失去可控性。
