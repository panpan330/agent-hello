# M12 第 9 节：Planner、Executor 与 Critic

## 本节定位

一个简单 Agent 可以由同一次模型调用完成：理解问题、决定工具、执行、总结。随着任务变复杂，单一循环容易出现几类问题：模型一边规划一边行动，目标会漂移；执行时忽略前置条件；生成答案后自己宣布“已完成”；为了修正错误而无限反复。

Planner、Executor、Critic（规划者、执行者、评审者）是一种常见的职责拆分方式：

```text
Planner：目标如何拆成可验证的步骤？
Executor：当前允许执行的下一步是什么？
Critic：结果是否满足目标、证据、约束与停止条件？
Orchestrator：谁在何时运行，状态如何变化，边界是否被遵守？
```

它们不一定是四个独立模型，不一定是四个服务，也不一定要用 Multi-Agent 框架。它首先是一种设计方法：把规划、执行、验证和调度的责任拆清楚，并让关键控制仍留在程序和状态机中。

本节会讲分工的价值、输入输出契约、计划质量、验证类型、反思/重规划边界、常见失败模式，以及什么时候应该保持单 Agent 简单设计。

## 本节学习目标

学完后，你应当能：

1. 说明 Planner、Executor、Critic、Orchestrator 的职责与边界。
2. 区分计划、步骤、动作、验证条件、执行结果和最终结论。
3. 设计可执行、可调整、可审计的任务计划。
4. 理解 Critic 不等于“再让一个模型说好不好”。
5. 判断哪些验证应由确定性程序完成，哪些可由模型辅助审查，哪些需要人工。
6. 解释重规划、反思、重试与无限循环之间的关系。
7. 判断任务是否值得引入这种角色拆分，避免不必要复杂度。

## 一句话先讲透

> Planner、Executor、Critic 的价值不在于增加模型数量，而在于把“要做什么”“实际做了什么”“结果是否真的达标”拆成可验证契约；模型可以承担语义判断，系统必须保留状态、权限、预算、事实和终止条件的最终控制权。

## 基础知识铺垫

### 1. 单 Agent 并不天然不好

在学习角色拆分前，先避免一个误区：单 Agent 是一种完全合理的设计。

适合单 Agent 的场景包括：

- 任务只有一两步；
- 工具很少，路径清晰；
- 无高风险副作用；
- 输出可用确定规则快速检查；
- 失败后用户可轻松重新发起；
- 成本和延迟非常敏感。

例如“根据当前问题检索知识库后给出带引用答复”，可以由一个受控 Agent Loop 完成。强行增加 Planner、Executor、Critic 三次模型调用，可能只是增加 token、延迟、调试难度和新的不一致来源。

角色拆分的价值出现于：目标复杂、步骤有依赖、证据要求高、工具多、失败代价较大、任务长或需要明确进度时。

### 2. 角色不是身份，职责不是模型数量

以下三种实现都可能符合 Planner/Executor/Critic 的思想：

| 实现 | 描述 | 适合情况 |
| --- | --- | --- |
| 单模型多阶段 | 同一模型在不同调用中分别生成计划、执行决策、检查结果 | 中等复杂度，成本可控 |
| 单模型单调用多字段 | 一个结构化输出同时包含计划/下一步/检查项 | 简单任务、低延迟 |
| 多模型/多 Agent | 不同模型或上下文承担不同角色 | 专业化、并行或强隔离需求 |

因此，“使用 Planner”并不等于“必须引入另一个 LLM”；“Critic”也不一定是模型，很多关键检查应由普通程序完成。

### 3. 目标、计划、步骤、动作的层级

这些词经常被混用。可以按从抽象到具体的层级区分：

```text
目标（goal）
  -> 计划（plan）
      -> 步骤（step）
          -> 动作（action/tool call）
              -> 观察结果（observation）
```

例子：

```text
目标：回答用户的退款资格问题，并在需要时说明下一步。

计划：
1. 获得订单和用户归属事实。
2. 检索当前退款政策。
3. 将订单事实与政策条件进行匹配。
4. 生成有依据、无越权承诺的答复。

步骤 1 的动作：query_order(order_id=A1001)

观察结果：订单归属已验证；订单已签收 3 天；无退款记录。
```

计划提供方向和依赖关系；动作是系统实际执行的最小单元；observation 是动作后获得的可信事实。

### 4. 验证（Verification）与评审（Critique）不同

验证往往意味着能用明确规则判断对错，例如：

- JSON 是否符合 schema；
- 用户是否有权限；
- 工具是否返回成功状态；
- 引用是否来自允许知识库；
- 输出是否包含必填字段；
- 是否超过金额、步骤或时间预算。

评审则通常涉及语义或质量判断，例如：

- 答复是否真正回答了用户问题；
- 计划是否遗漏关键调查步骤；
- 多份证据是否存在矛盾；
- 语言是否清晰、克制、有适当说明。

程序擅长验证明确规则；模型可辅助语义评审；高影响的价值判断仍可能需要人工。把所有验证交给 Critic 模型，既不稳定，也可能让模型替代应由程序保障的安全规则。

### 5. 为什么“自我反思”不是可靠保证

让模型在输出后再问自己“有没有错”可能改善部分质量，但有局限：

- 同一个模型可能重复同一种错误；
- 它无法凭空获得缺失的外部事实；
- 它不能绕过错误工具结果；
- 它可能为了显得自信而批准自己的答案；
- 反思轮次会增加成本，甚至陷入无限改写。

因此反思应是有限、结构化、与外部验证结合的机制，而不是“让模型一直检查直到满意”。

## 本节主题系统讲解

### 1. 四类职责的清晰边界

#### 1.1 Planner：将目标变成可执行假设

Planner 的主要职责：

- 澄清目标和成功标准；
- 识别必须先获得的事实；
- 拆分可观察的子目标；
- 描述依赖关系、顺序和可并行部分；
- 估计风险、需要确认/人工的节点；
- 为每步定义预期产出或验证条件。

Planner 不应：

- 直接绕过工具权限执行操作；
- 把模糊意图伪装成已完成事实；
- 决定用户是否真的有权限；
- 无限生成漂亮但无法执行的计划。

#### 1.2 Executor：在当前边界内把计划推进为事实

Executor 的主要职责：

- 读取当前任务状态、计划和 observation；
- 选择当前可以执行的最小下一步；
- 调用已授权、已校验的工具或触发等待/确认；
- 将工具结果规范化为 observation；
- 更新步骤执行状态和 checkpoint；
- 遇到阻塞时报告事实，而不是编造完成。

Executor 不应：

- 擅自扩大任务目标；
- 执行未授权写操作；
- 忽略计划依赖与当前状态；
- 将模型的动作提议当作真实结果。

#### 1.3 Critic：检查“结果是否足以结束或需要修正”

Critic 的主要职责：

- 检查计划是否覆盖目标和必要约束；
- 检查执行结果是否有足够证据；
- 发现矛盾、遗漏、不完整、越界或无依据结论；
- 给出有限、可行动的修正建议；
- 判断可以结束、需要重规划、需要补充事实，还是必须转人工。

Critic 不应：

- 自己修改真实业务数据；
- 代替权限系统批准动作；
- 无边界要求“再想一次”；
- 将风格偏好误当成业务失败。

#### 1.4 Orchestrator：维护系统级控制权

Orchestrator 可以是代码、状态机、工作流引擎或一组服务。它负责：

- 决定何时调用 Planner/Executor/Critic；
- 维护任务状态、版本、预算、租约和 checkpoint；
- 校验工具、权限、审批和幂等；
- 处理等待、重试、失败、取消和恢复；
- 限制角色间能看到和能做的范围；
- 记录审计与可观测事件。

它不是“第四个更聪明的模型”，而是 Agent 工程的控制平面。

### 2. 一个好的计划需要包含什么

计划不应只有自然语言编号列表。对于可执行 Agent，至少要让系统和人理解：

```text
plan_id / plan_version
task_goal
success_criteria
steps[]
  - step_id
  - purpose
  - prerequisites
  - allowed_tools/actions
  - expected_observation / completion_criteria
  - risk_level / approval_requirement
  - fallback / failure_policy
dependencies
budget_estimate
```

示例（概念化）：

```text
步骤 S1：验证订单归属
前置：用户提供订单号
允许工具：query_order_summary
完成条件：得到“订单存在且当前用户可访问”或明确拒绝
失败策略：无权限则结束，不重试

步骤 S2：获取物流事实
前置：S1 成功
允许工具：query_logistics
完成条件：得到近期轨迹或明确“服务暂不可用”
失败策略：可延迟重试 2 次

步骤 S3：决定处理路径
前置：S1、S2 的 observation
完成条件：选择直接答复、请求确认创建工单或转人工
风险：创建工单需用户确认
```

计划越接近可验证契约，执行与调试就越可靠。

### 3. 计划质量的四个标准

#### 3.1 可执行性（Executable）

每一步必须能映射到已存在、当前允许的能力，或明确是等待/人工节点。`“深入分析并彻底解决问题”`不是可执行步骤。

#### 3.2 可验证性（Verifiable）

每一步有可判断完成条件。`“理解订单情况”`太模糊；`“获得当前订单归属、状态和物流最后更新时间”`更可验证。

#### 3.3 依赖正确性（Dependency-aware）

不能在验证订单归属前查询敏感详情，也不能在未确认前创建工单。计划需要显式表示前置条件。

#### 3.4 可调整性（Adaptable）

计划不是死板脚本。应允许在新 observation 下跳过、补充、替换或终止步骤，并记录变更原因。

### 4. Planner 的输入和输出不能越权

Planner 应收到完成规划所需的受控信息：用户目标、任务类型、允许能力摘要、已知事实、约束、预算和风险策略。

Planner 不应直接收到：

- 无权限的业务数据；
- 可直接使用的高权限凭据；
- 所有底层命令/网络能力；
- 与本任务无关的其他用户记忆；
- 不受控的工具原始输出。

输出也应受结构化约束。一个 Planner 即使提出“调用管理员接口删除旧数据”，Orchestrator 也应发现该动作不在允许能力中并拒绝计划中的该步骤。

### 5. Executor 的核心：最小可行动作

Executor 不应该拿到一个计划后就一次性执行所有步骤。更合理的模式是：

```text
读取计划与当前完成状态
-> 找到已满足前置条件的最小下一步
-> 请求/执行一个受控动作
-> 获得 observation
-> 更新状态
-> 再决定下一步
```

原因包括：

- 外部事实可能改变后续路径；
- 每一步都需要权限/预算/取消检查；
- 高风险步骤可能要等待人工；
- 工具可能失败或返回意外结果；
- 中断后可从稳定 checkpoint 恢复。

Executor 的“最小”不是把业务步骤切得越碎越好，而是每次动作应足够明确、可验证、可回滚或可安全重试。

### 6. Critic 的三种层次

Critic 不应该只有一种“好/不好”的评价。可以分成：

#### 6.1 确定性 Critic（程序规则）

适用于可精确判断的要求：

- 输出 schema、字段、长度、格式；
- 引用是否存在、是否来自允许来源；
- 任务是否超预算；
- 工具调用是否经过审批；
- 是否有必需 observation；
- 是否尝试越权或重复副作用。

这是最可靠、最便宜的层，应优先使用。

#### 6.2 语义 Critic（模型辅助）

适用于规则不易穷举的质量检查：

- 答复是否回答了用户真正问题；
- 是否把“政策一般规则”和“当前订单事实”区分清楚；
- 是否存在逻辑矛盾或遗漏的重要条件；
- 语言是否清晰、适度、不夸大。

语义 Critic 应被要求输出明确问题和证据，而不是一句笼统的“我觉得可以”。

#### 6.3 人工 Critic（专家审查）

适用于高影响、专业判断或冲突无法自动消解的场景：法律、医疗、金融、高金额动作、敏感投诉、复杂异常。人工审查的结果应进入状态与审计，而不是只停留在聊天记录。

### 7. 验证目标必须与任务成功标准一致

一个典型失败是 Critic 只检查“语言很流畅”，却没有检查是否完成了用户目标。

例如任务目标是“回答退款资格并给出处置建议”，成功标准可能包括：

```text
已验证订单归属；
引用当前版本退款政策；
明确区分已确认事实与条件性说明；
不承诺未执行的退款；
必要时给出下一步或人工路径。
```

Critic 应围绕这些标准检查，而不是泛泛检查“语气专业”“字数适中”。风格可以是附加质量项，但不能盖过事实、权限和业务完成度。

### 8. 反思（Reflection）如何受控进行

合理反思通常有清晰触发和次数：

```text
触发：确定性校验失败、语义 Critic 发现具体遗漏、工具结果矛盾
输入：失败项、证据、当前计划、剩余预算
动作：修正答复 / 补充一个事实查询 / 重规划某步骤
上限：最多 1-2 次
终止：仍不满足则转人工或明确失败
```

不合理反思：

```text
“再仔细想想。”
“再检查一次。”
“直到完全确定为止。”
```

后者没有可测目标和停止条件，容易产生昂贵循环，且不一定带来新证据。

### 9. 重规划（Replanning）与重试（Retry）的区别

| 概念 | 为什么发生 | 改变什么 | 示例 |
| --- | --- | --- | --- |
| 重试 | 同一动作暂时失败 | 通常不改计划 | 物流 API 503 后延迟重试 |
| 修复 | 输出/参数格式有问题 | 修正同一动作表示 | 工具参数 schema 不合规 |
| 重规划 | 前提、目标、事实或可用能力变化 | 改变步骤或路径 | 订单不存在，改为追问订单号 |
| 转人工 | 自动路径不应继续 | 责任主体变化 | 高风险争议退款 |

把它们混为“让模型再试一次”，会让系统难以控制成本和解释失败原因。

### 10. 计划版本与变更记录

在长任务中计划可能多次变化。建议将计划视为版本化对象：

```text
plan_v1：初始调查和答复路线
plan_v2：因物流服务不可用，改为等待重试
plan_v3：用户要求转人工，终止自动创建工单步骤
```

每次变更应记录：

- 谁/什么触发（模型、规则、人工、用户、外部事件）；
- 变更前后差异；
- 新计划是否仍满足原目标；
- 被废弃步骤如何处理；
- 已产生的副作用是否受影响；
- 使用的策略和工具版本。

计划版本不是为了保留模型所有草稿，而是让长任务在恢复、审计和排错时有稳定的路线记录。

### 11. Planner 和 Critic 是否需要不同模型

有时会使用不同模型、不同提示词或不同采样参数，让 Critic 更独立；但这不是必要条件，也不能自动保证正确。

考虑因素：

| 选择 | 可能收益 | 代价 |
| --- | --- | --- |
| 同一模型、不同角色提示 | 简单、成本低、上下文一致 | 容易保留同一偏见/错误 |
| 不同模型 | 可能增加差异化视角 | 成本、延迟、契约调试复杂 |
| 规则 + 模型 Critic | 关键约束可靠，语义质量补充 | 需要设计规则和评估集 |
| 人工 Critic | 高风险判断更可靠 | 人力延迟和容量限制 |

优先顺序通常应是：先用确定性规则处理确定问题，再考虑模型 Critic 补充语义质量，最后按风险引入人工。不要为了“多模型互审”而忽略基础验证。

### 12. Critic 的输出应是可行动反馈

不好的 Critic 输出：

```text
答案不够好，请改进。
```

好的 Critic 输出（概念）：

```text
verdict: NEEDS_REVISION
blocking_issues:
  - 缺少订单归属验证，不能对订单状态作确定结论
  - 结论引用的是过期政策版本
allowed_next_actions:
  - query_order_summary
  - retrieve_current_refund_policy
budget_impact: requires at most 2 additional steps
```

这样 Orchestrator 才能判断是否有必要、是否允许、是否有预算执行修正。Critic 不能只输出情绪化评价。

### 13. 防止“Critic 与 Executor 互相打架”

没有清晰协议时，Critic 可能无限要求补充，Executor 可能忽略；Planner 重写计划又抹掉已完成进度。

可建立规则：

1. Critic 只能提出有限类别的发现：阻塞问题、建议问题、风险升级。
2. 阻塞问题必须有证据或可验证依据。
3. Orchestrator 决定是否采纳 Critic 建议，受预算和权限限制。
4. Executor 只执行当前批准计划中可用的步骤。
5. 新计划不能重复已确认完成的副作用。
6. 同一问题达到最大修正次数后，结束或转人工。

角色协作不是角色之间自由聊天，而是通过状态和结构化契约交接。

### 14. 一个完整走读：合同风险摘要任务

任务：分析合同，找出可能风险条款，生成供法务复核的摘要。注意：Agent 不做最终法律结论。

#### Planner

生成计划：

```text
S1：确认文档可解析且属于当前任务。
S2：提取条款、页码和章节结构。
S3：按受控风险清单匹配可能条款。
S4：为每项候选风险保留原文定位和不确定性说明。
S5：生成“供人工复核”的摘要，转法务审核。
```

成功标准包括“每个风险项都有来源定位”“不将建议表述为法律结论”。

#### Executor

逐步调用受控文档解析和检索工具，形成条款 observation。对无法提取的扫描页，记录不足，而不是臆测内容。到 S5 时不直接向外签发结论，而是生成审核材料并进入 `WAITING_HUMAN`。

#### Critic

确定性检查：每个风险项是否有页码/段落引用，是否越过允许术语，是否漏掉必填分类。

语义检查：摘要是否将“可能存在风险”错误写成“合同违法”，是否忽略了例外条款，是否清楚说明需要法务复核。

#### Orchestrator

维护文件权限、任务状态、工具预算、人工审核队列与 checkpoint。Critic 发现引用不足时，只允许 Executor 补充解析/定位，而不允许它自行改写合同或直接给出法律决定。

### 15. 一个完整走读：客服工单分流任务

任务：识别用户问题，查询必要事实，建议处理路径。

Planner 可能只需要很轻量：判断是否需要订单号、是否需要查知识库、是否可能涉及高风险动作。

Executor 负责查询订单、检索政策、生成工单草稿或请求确认。

Critic 可用大部分确定规则：工单分类是否是允许枚举、是否包含订单引用、是否引用真实 observation、是否在未确认时创建工单。模型 Critic 仅检查回复是否遗漏用户主要诉求或把政策条件说得过于绝对。

这个例子说明：角色拆分可很轻，不必为每个客服问题创建三个独立 Agent。

### 16. 何时应避免 Planner/Executor/Critic 模式

以下场景通常应保持简单：

- 只有单步、可确定执行的业务流程；
- 输出只需 schema/规则验证；
- 低延迟要求极高；
- 增加模型轮次的成本大于质量收益；
- 团队尚未建立状态、工具和评估基础；
- 没有明确成功标准，拆角色只会让模糊变得更复杂。

可以先做一个受控单 Agent Loop，收集失败案例后，再针对真正反复出现的规划、执行或质量问题增加角色分工。

### 17. 评估角色分工是否有效

引入角色后，不应只看“架构图更复杂”。应评估：

| 指标 | 要问的问题 |
| --- | --- |
| 成功率/任务完成度 | 是否更常完成真正目标？ |
| 证据质量 | 是否减少无来源、漏条件结论？ |
| 工具错误率 | 是否减少错误工具、重复动作、越权提议？ |
| 修正收益 | Critic 发现的问题是否真的提升最终结果？ |
| 成本与延迟 | 新增模型调用是否值得？ |
| 人工介入质量 | 是否把人工用在更有价值的例外上？ |
| 可调试性 | 出错时是否更容易定位规划、执行还是验证问题？ |

如果 Critic 经常只改文风、Planner 经常生成后从未被使用、或总成本翻倍但质量无明显改善，就应简化设计。

### 18. 一套务实的落地顺序

1. 先写清任务目标、成功标准、禁止行为和状态机。
2. 将复杂任务的高层计划以结构化字段表达，但先不必单独调用 Planner 模型。
3. 让 Executor 以单步受控工具调用推进，并记录 observation。
4. 优先加入确定性验证：权限、schema、引用、预算、完成条件。
5. 对确实存在的语义质量问题，增加有限次数的模型 Critic。
6. 对高风险或专业判断建立人工复核，而不是依赖 Critic 模型自证。
7. 只有当职责、上下文、并行或专业化需要明确时，再扩展到独立多 Agent 角色。

这种顺序让复杂度跟随真实问题增长，而不是跟随流行名词增长。

## 常见误区

### 误区 1：Planner、Executor、Critic 必须是三个独立 Agent

它们首先是职责。可以由同一模型分阶段完成，也可以大量使用确定性程序。是否拆成独立 Agent 取决于复杂度、隔离、并行和成本，而不是名称。

### 误区 2：有详细计划就不需要每步校验

计划只是对未来的假设。工具结果、权限、用户输入和外部状态会变化，每个敏感动作仍要在执行时校验。

### 误区 3：Critic 说“通过”就代表业务一定正确

模型 Critic 只能提供语义辅助。权限、金额、引用存在性、工具成功、幂等和高风险授权应由程序和人工保障。

### 误区 4：发现问题就让模型无限反思

反思需要明确问题、允许动作和次数上限。无边界反思会产生循环、成本浪费和虚假的确定感。

### 误区 5：重试、修复和重规划是一回事

它们触发原因和改变范围不同：重试重复同一动作，修复改正动作表示，重规划改变路线。区分后才容易控制预算和审计。

### 误区 6：计划越长越专业

过长计划可能包含无法执行的伪步骤和模型内部思维。好计划要可执行、可验证、有依赖、有边界且能调整。

### 误区 7：角色拆分一定提升质量

增加角色也会增加接口、上下文传递、延迟和不一致风险。应通过评估验证收益，不要将复杂架构当成质量证明。

## 本节练习

### 练习 1：划分职责

任务：“根据用户上传的合同，生成风险条款摘要并提交法务审核。”请将下列工作分配给 Planner、Executor、Critic、Orchestrator：

1. 检查每项风险是否有页码引用。
2. 制定先解析文档、再提取条款、再汇总的路线。
3. 验证当前用户是否有权访问文件。
4. 调用受控文档解析工具。
5. 判断摘要是否把不确定风险误说成法律结论。

答案：1 主要是确定性 Critic/程序检查。2 主要是 Planner。3 属于 Orchestrator/权限系统。4 由 Executor 提议/推进，受 Orchestrator 控制执行。5 可由语义 Critic 辅助检查，且对高风险场景应交法务人工复核。

### 练习 2：改进一个坏计划

以下计划有什么问题？如何改进？

```text
1. 深入研究订单。
2. 妥善处理物流。
3. 让用户满意。
```

答案：步骤抽象且不可执行、没有前置条件、工具、完成标准、风险边界或失败策略。可改为：1）验证订单归属并读取允许摘要；2）查询物流最后状态；3）依据事实判断直接说明、请求创建工单确认或转人工；4）每步定义允许工具、完成条件和确认要求。

### 练习 3：判断应重试还是重规划

1. 物流 API 返回 503。
2. 工具返回订单不存在，但用户给的是明显不完整订单号。
3. 退款政策检索到两个冲突版本。

答案：1 通常是受退避策略控制的重试。2 需要重规划为追问完整订单号或校验输入，不应原样重试。3 需要补充版本/生效时间事实或转人工，属于重规划/证据消解问题，而不是普通重试。

### 练习 4：设计 Critic 输出

为“客服答复是否可以发送”设计三个确定性检查项和两个语义检查项。

答案：确定性检查可包括：是否引用了允许且存在的来源；是否包含未验证的订单事实；是否在无确认情况下声称已执行写操作。语义检查可包括：是否直接回答用户问题；是否清楚区分一般政策与当前个案条件，并给出合适的下一步。

## 自测题

### 自测 1：Planner、Executor、Critic、Orchestrator 的关键区别是什么？

答案：Planner 拆解目标和依赖；Executor 在当前边界内将步骤推进为真实 observation；Critic 检查计划/结果是否满足成功标准与约束；Orchestrator 维护状态、权限、预算、调度、工具执行和终止条件。它们是职责分工，不必一一对应独立模型。

### 自测 2：为什么 Critic 不能替代确定性程序校验？

答案：模型评审具有概率性，可能遗漏、误判或自我确认；权限、schema、引用存在性、金额限制、幂等和状态转移等应有明确程序规则。Critic 适合补充语义质量，不应取代系统安全边界。

### 自测 3：什么情况下应重规划？

答案：当目标澄清、关键前提改变、工具/资源不可用、观察结果与计划假设冲突、用户补充新信息、人工拒绝/修改路径或预算变化导致原路线不再合适时，应有条件地重规划。短暂性同一动作失败通常只需重试。

### 自测 4：什么是可行动的 Critic 反馈？

答案：它应说明具体阻塞问题、相关证据或规则、建议的有限下一步和预算影响，例如“缺少订单归属 observation，只允许补充 query_order_summary 后再生成结论”。而不是只说“答案不够好”。

### 自测 5：何时不应引入完整角色拆分？

答案：任务单步或路径明确、低风险、可用规则验证、低延迟/低成本要求高、没有真实规划或质量问题时，应保持受控单 Agent 或固定工作流。复杂度应由实际需求驱动。

## 本节小结

Planner、Executor、Critic 将复杂 Agent 任务中的路线设计、事实推进与结果验证分开，使每一层都能有清晰输入输出和责任边界。真正的可靠性来自结构化计划、单步受控执行、确定性验证优先、有限反思与由 Orchestrator 维护的状态、权限和预算，而不是简单增加模型角色。
