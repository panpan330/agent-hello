# M13 第 16 节：模型上线、版本管理与阶段设计复盘

## 本节定位

阶段 13 从模型是什么、Token 与上下文、GPU/显存、量化、推理性能、服务接口、推理引擎、部署架构、Docker、网关、观测一路讲到微调数据和 LoRA/QLoRA。现在需要把这些分散知识收束成一个完整的工程对象：**一个可以被上线、追踪、灰度、回滚、复现和持续改进的模型能力版本。**

如果只把“模型版本”理解为某个权重文件名，就无法解释为什么一次回答变了、为什么成本升高、为什么 RAG 质量退化、为什么微调 adapter 加载后工具调用失效。真实 AI 应用的行为来自一组共同工作的资产和运行策略，本节把它们组织为可治理的生命周期。

本节仍是纯知识学习，不要求部署模型或修改项目。

## 本节学习目标

学完后，你应当能够：

1. 解释“模型版本”为什么不应只包含基础权重文件。
2. 区分模型资产、运行配置、提示资产、检索资产、路由资产与业务安全资产。
3. 理解模型注册表、版本清单、谱系（lineage）和可复现性的作用。
4. 设计从开发、评测、候选、灰度、正式、废弃到下线的模型生命周期。
5. 说明模型发布、Prompt 发布、RAG 索引发布、adapter 发布和路由发布之间的依赖关系。
6. 理解灰度、影子、A/B、回滚、停止条件和发布证据如何共同降低风险。
7. 能用阶段 13 的知识诊断“模型慢、贵、错、不可用”分别应看哪些层。
8. 对推理、部署和微调建立一张可用于面试、设计和后续学习的整体心智地图。

## 一句话先讲透

**线上 AI 行为由“模型权重 + Tokenizer/模板 + 适配器 + Prompt + RAG 数据/索引 + 工具与安全规则 + 路由与运行配置”共同决定；只有把这组资产作为一个可追溯、可验证、可回滚的发布单元，模型能力才真正可运营。**

## 基础知识铺垫

### 1. 软件版本与模型版本的共同点和不同点

传统软件版本通常能关联到：源码提交、构建产物、依赖版本、配置、测试结果和部署记录。模型系统也需要这些，但还额外包含模型特有资产：

- 基础模型权重和量化格式；
- Tokenizer、聊天模板、特殊 Token；
- LoRA/QLoRA adapter 或合并后的权重；
- 训练数据、训练代码、训练参数和 checkpoint；
- Prompt、工具 Schema、结构化输出 Schema；
- Embedding 模型、文档版本、切分和向量索引；
- Rerank 模型和检索配置；
- 路由、限流、回退、缓存、采样、上下文预算；
- 评测集、质量门槛、红队结果和线上指标。

同一基础模型权重在不同 Prompt、不同 RAG 索引或不同采样参数下，可能表现得像不同产品。因此需要比传统二进制版本更完整的“行为版本”视角。

### 2. 不可变资产与可变配置

一个有用的区分是：

- **不可变资产（immutable artifacts）**：一旦发布就不应被原地修改，例如某个权重文件、adapter 文件、评测数据快照、构建镜像、向量索引快照。若改变内容，应产生新版本/新哈希。
- **可变配置（mutable configuration）**：可以在受控流程下调整，例如逻辑模型路由、流量权重、限流阈值、开关、环境地址。

不可变资产保证“今天看到的 `model-v1` 与昨天是否同一东西”有答案；可变配置让系统能在不重新构建全部资产的情况下进行治理。

但可变不等于随意改。路由、Prompt、检索参数和超时都可能显著改变行为，仍应有版本、审批、审计和回滚。

### 3. 哈希、版本号与人类可读名称

一个成熟资产通常同时需要三种标识：

- **人类可读名称**：例如 `support-chat`、`ticket-classifier`，便于业务沟通；
- **版本号/发布标签**：例如 `v1.3.0`、`2026-08-20`，便于生命周期管理；
- **不可变内容标识**：例如文件哈希、镜像 digest、数据集快照 ID，便于精确复现。

仅用“latest”或“production”很危险，因为它们会随时间指向不同内容。它们可用作环境别名或路由标签，但不应作为唯一的可追溯身份。

### 4. 谱系（lineage）：回答“它从哪里来”

模型谱系是从上线版本反向追溯其来源和过程的能力。例如：

```text
线上逻辑模型：support_chat_default
  -> 实际部署：support-chat-adapter-v3
  -> 基础模型：base-model-7b revision abc123
  -> adapter：lora-support-v3
  -> 训练数据：support-sft-v4 snapshot 2026-08-01
  -> 训练配置：rank 16 / target modules ...
  -> 评测：eval-suite-v5，关键集通过
  -> 镜像：inference-server digest ...
  -> Prompt：support-system-prompt v12
  -> RAG：embedding v4 + index snapshot 2026-08-15
  -> 路由：router policy v8
```

谱系让你能回答：某次输出为什么变化？某批训练数据发现隐私问题影响哪些模型？一个基础模型漏洞需要替换哪些部署？某次质量回归该回滚哪一层？

### 5. 生命周期不是线性“训练完就结束”

模型/适配器可能经历：

```text
idea
-> experiment
-> candidate
-> evaluated
-> canary
-> active
-> deprecated
-> retired / archived
```

不同资产的生命周期也不同：一个基础模型可能长期 active；Prompt 每周迭代；RAG 索引每天更新；adapter 每月重训；旧版本因审计和回滚需要保留一段时间。

生命周期管理的目的不是制造审批流程，而是让系统知道什么版本可以试验、什么版本允许处理生产数据、什么版本正在灰度、什么版本已禁止使用，以及何时能安全删除。

## 本节主题系统讲解

### 1. 定义“AI 发布单元”

一个在线 AI 能力的发布单元不必把所有资产物理打包在一起，但必须逻辑关联。可以用一份**发布清单（release manifest）**描述：

| 类别 | 需要锁定/记录的内容 |
| --- | --- |
| 模型 | 基础模型 ID/哈希、量化、Tokenizer、聊天模板、adapter/merged 权重 |
| 推理 | 引擎/镜像版本、GPU/并行、最大上下文、采样、并发/缓存参数 |
| Prompt | system prompt、few-shot、模板、输出约束、版本 |
| RAG | 文档集合版本、切分规则、Embedding、向量索引快照、Rerank、top-k/过滤 |
| 工具 | 工具定义、Schema、工具版本、白名单、确认与幂等策略 |
| 安全 | 数据分级、脱敏、权限策略、内容策略、审计规则 |
| 路由 | 逻辑模型名、主/备用路径、灰度权重、超时、重试、熔断/降级规则 |
| 证据 | 评测集版本、质量/性能/安全结果、审批或责任人、已知限制 |
| 运行 | 环境、区域、部署副本、镜像 digest、配置版本、监控仪表盘 |

不是每次小改动都要复制一整份巨大清单，但关键行为资产必须能关联起来。发布清单可由配置系统、模型注册表、CI/CD 元数据或受控文档共同实现。

### 2. 为什么 Prompt、RAG 和模型必须共同版本化

考虑以下变化：

- 只升级模型权重，但新模型对旧聊天模板理解不同；
- 只改 Prompt，让模型要求引用字段，但旧 RAG 索引没有提供来源元数据；
- 只换 Embedding 模型，却继续使用旧向量索引；
- 只换 Rerank 模型，候选顺序和 Token 输入长度显著变化；
- 只改工具 Schema，却让旧 adapter 仍按旧字段生成；
- 只切换路由，却把敏感请求回退到不允许的数据区域。

每项单看都像“配置小改”，组合后却可能导致质量、成本、安全或兼容性事故。

因此应把它们看作**兼容矩阵**，而不是互不相关的文件：

```text
模型版本 <-> Tokenizer/模板
模型版本 <-> adapter
Prompt <-> 模型能力/上下文
Prompt <-> 工具 Schema
Embedding 模型 <-> 向量索引
RAG 文档 <-> 权限/引用
路由 <-> 数据边界/能力/回退
```

发布前验证的重点，就是检查这个矩阵中被改变的一条边是否仍成立。

### 3. 模型注册表（model registry）的作用

模型注册表不必限定为某个具体产品。概念上，它是管理模型/adapter/部署候选元数据和生命周期状态的可信目录。

它通常支持：

- 登记模型名称、版本、来源、哈希、许可证、负责人；
- 关联训练数据、代码、配置、评测和实验记录；
- 记录状态：实验、候选、灰度、生产、已废弃；
- 记录允许环境、数据等级、能力、风险和部署位置；
- 保存发布/回滚事件；
- 为路由器或部署系统提供“哪些版本可被选择”的依据。

注册表不是模型文件夹的花哨名字。若它只列出文件路径，却不能关联评测、安全、数据与状态，就无法承担治理职责。

### 4. 版本命名策略：名称表达意图，哈希表达身份

一个实用命名例子：

```text
逻辑能力：support_ticket_classifier
候选版本：support_ticket_classifier:2026.08.20-rc1
正式标签：support_ticket_classifier:v1.4.0
物理资产：adapter sha256:...
基础模型：base-model-7b@revision-...
数据版本：ticket-sft:v4
评测版本：ticket-eval:v5
```

避免的命名：

```text
new
final
final2
latest
really_final
```

这些名字无法表达来源、兼容性和生命周期。即使团队很小，也应在名称中保留任务、日期/语义版本、候选状态等关键信息，并用不可变哈希完成精确定位。

### 5. 从实验到生产的门禁（gates）

模型/adapter 不应因“训练完成”直接进入生产。可以设计分层门禁：

#### 5.1 资产门禁

确认基础模型、数据、adapter、Tokenizer、镜像和配置来源可信、版本明确、许可证和安全要求满足。

#### 5.2 离线质量门禁

在独立 test/challenge/safety 集上，与基线比较任务质量、结构化语义、拒答、引用、工具安全等。不满足关键门槛不进入灰度。

#### 5.3 运行性能门禁

验证目标硬件与引擎能加载该版本，TTFT、E2E、吞吐、显存、错误率和启动时间满足目标。不要只在训练环境验证。

#### 5.4 契约兼容门禁

验证 API、流式、JSON Schema、工具调用、错误语义、Tokenizer/模板、RAG 元数据与下游应用兼容。

#### 5.5 上线风险门禁

明确灰度范围、停止条件、监控、回滚责任人和备用路径。高风险写操作、敏感数据和重要用户路径应采用更严格门槛。

门禁不是要求所有变化同样重。修改低风险展示 Prompt 与替换基础模型、改变数据外发路径的风险不同，验证强度应与风险匹配。

### 6. 灰度发布：让现实流量成为受控证据

离线测试无法覆盖所有真实网络、负载、用户表达和数据分布。灰度让新版本处理受控比例的真实流量：

```text
0% -> 1% -> 5% -> 20% -> 50% -> 100%
```

每一步都应观察预设指标：

- 错误、超时、流中断、429；
- TTFT、P95/P99、队列、显存、吞吐；
- 输入/输出 Token、成本、重试、回退；
- JSON/工具/引用等契约指标；
- 关键任务质量、人工转接、用户反馈；
- 安全策略命中、数据治理异常。

灰度不是“慢慢放量”这么简单，而是**每一步都有继续、暂停或回滚的判据**。若没有停止条件，灰度会变成无责任的线上实验。

### 7. 影子流量与 A/B：不同问题，用不同方法

#### 7.1 影子流量

复制一部分真实请求给候选版本，但不将候选结果用于用户决策。它适合观察：部署兼容、延迟、成本、输出结构和与基线的离线对比。

限制：会额外消耗模型资源和费用；需要脱敏与数据许可；绝不能让影子请求触发真实写工具或重复副作用。

#### 7.2 A/B 测试

将用户/会话随机分到不同版本，比较明确的业务结果，例如人工转接率、解决率、编辑时间或满意度。它适合检验“新版本是否更有业务价值”。

限制：需要合适样本量、分流一致性、风险控制和指标解释；不能把高风险用户随意放入未经验证的版本。

#### 7.3 灰度

更强调安全地逐步扩大真实使用范围，通常先于或结合 A/B。三者可以组合，但目的不同，不能混为一谈。

### 8. 回滚设计：在变更前就准备好

回滚不是事故发生时才想的命令。发布前应明确：

- 回滚到哪个模型/adapter/Prompt/RAG/路由版本；
- 旧版本是否仍保留、可加载、容量足够；
- 是否有数据/索引不可逆迁移；
- 哪些配置会影响旧版本兼容；
- 谁可以触发回滚，依据什么告警或质量证据；
- 回滚后如何验证恢复；
- 已经产生的异步任务、缓存、会话、工具结果如何处理。

一个很重要的原则：**不要在新版本完全验证前删除旧版本或复用其唯一资源。**

模型回滚可能涉及多个层：

```text
模型/adapter 回滚
Prompt 回滚
Tokenizer/模板回滚
RAG 索引回滚
路由权重回滚
推理引擎/镜像回滚
安全或工具 Schema 回滚
```

实际故障时应基于证据选择最小、可逆、能快速止损的动作，而不是一口气回退所有层导致新的不确定性。

### 9. 模型下线与删除：别让资产无限堆积

模型、adapter、数据集、checkpoint 和镜像会持续积累。无限保留带来存储、成本、漏洞、许可证和隐私风险；过早删除又会破坏审计、复现和回滚。

需要定义保留策略：

- 生产版本与最近可回滚版本保留多久；
- 实验 checkpoint 在评估结束后如何清理；
- 训练数据和日志的保留期限与删除流程；
- 发现数据授权/隐私问题时如何追溯并撤销受影响资产；
- 已废弃模型是否从路由和密钥权限中彻底移除；
- 是否保留最小元数据和评测摘要用于长期审计。

下线应包括“停止被新路由选择、停止接受新流量、处理存量任务、归档必要证据、撤销权限、按策略删除资产”，而不是只改一个 `enabled=false`。

### 10. 模型变更的兼容性清单

每次变更都可问以下问题：

#### 10.1 输入兼容

- Tokenizer、聊天模板、system/user/tool 消息格式是否一致？
- 上下文窗口和最大输入是否满足当前 Prompt/RAG？
- 是否支持图片、文件、工具、结构化输出？

#### 10.2 输出兼容

- JSON/Schema、工具调用、finish reason、stream chunk 是否能被应用解析？
- 新模型是否更容易输出额外文字、不同枚举或不同停止方式？
- usage/Token 统计是否有变化？

#### 10.3 行为兼容

- 关键任务质量、安全拒答、事实性、引用和风格是否达标？
- 是否改变了模型对 system prompt 或工具描述的遵循方式？

#### 10.4 性能兼容

- TTFT、输出速度、并发、显存、冷启动和吞吐是否可接受？
- 高峰或长上下文是否出现新瓶颈？

#### 10.5 治理兼容

- 数据地域、许可、日志、审计、密钥、成本和回退策略是否仍合规？

把这张清单作为发布评审的思考框架，可避免“接口没变，所以可以直接换”的错误。

### 11. 从症状回到阶段 13 的知识地图

当系统出现问题，可以按症状定位到本阶段的不同主题。

#### 11.1 “模型变慢了”

检查：

```text
输入/输出 Token 是否增长？                    -> M13-01
GPU/显存/CPU 是否成为瓶颈？                    -> M13-02
量化或格式是否改变性能/兼容？                  -> M13-03
TTFT、队列、batch、KV Cache 是否异常？         -> M13-04 / M13-07
API、网络、流式或超时是否有问题？              -> M13-06
部署副本、负载均衡、异步隔离是否合理？         -> M13-08
容器/GPU 运行时和冷启动是否异常？              -> M13-09
路由是否切到备用或发生重试？                   -> M13-10
Trace、P95、发布事件如何证明？                 -> M13-11
```

#### 11.2 “模型变贵了”

检查：输入/输出 Token、重试/回退、长 Prompt、RAG 候选、工具 Schema、缓存命中、模型路由、并发利用率和单位业务价值。对应 M13-01、M13-04、M13-05、M13-10、M13-11。

#### 11.3 “模型答错了”

先区分是事实、检索、权限、工具、结构、基础能力、Prompt 还是模型版本问题。事实/实时数据优先检查 RAG/工具；结构优先 Schema/验证；安全优先业务控制；稳定重复行为再评估微调。对应 M13-06、M13-10、M13-12、M13-13、M13-14。

#### 11.4 “模型服务不可用”

检查 API 鉴权/错误、实例健康/就绪、队列/容量、GPU/容器、路由/熔断/回退、发布事件和故障域。对应 M13-06、M13-08、M13-09、M13-10、M13-11。

这种“症状 -> 分层 -> 证据”路径，正是阶段 13 不是零散知识的原因。

### 12. 阶段 13 的完整心智模型

可以将本阶段压缩成一条完整链路：

```text
模型资产
  权重、Tokenizer、模板、量化、adapter
        |
        v
推理运行
  CPU/GPU/显存、prefill/decode、KV Cache、batch、调度、引擎
        |
        v
推理服务
  HTTP/SSE、OpenAI 兼容、鉴权、错误、超时、重试、流式
        |
        v
部署平台
  容器、GPU 运行时、模型副本、负载均衡、队列、存储、网络、健康检查
        |
        v
治理与路由
  逻辑模型、能力矩阵、限流、熔断、回退、降级、数据边界、成本
        |
        v
观测与发布
  Trace、指标、SLO、容量、灰度、A/B、回滚、版本与谱系
        |
        v
模型适配
  是否微调、SFT 数据、评估、LoRA/QLoRA、adapter 生命周期
```

业务 AI 应用位于这条链路之上和之中：它负责 Prompt、RAG、工具、用户权限、业务规则和最终用户体验。推理系统再强，也不会自动替代业务可信边界。

### 14. 你现在应能做出的工程判断

完成阶段 13 后，你不必声称自己已经能独立运维超大规模 GPU 集群，但应能做出比“选个模型 API 调一下”更成熟的判断：

- 为什么同样的模型在不同上下文、量化、引擎和硬件上性能不同；
- 云 API、自部署、本地运行的责任边界如何比较；
- 为什么 OpenAI 兼容不等于所有能力和行为相同；
- 高并发服务为什么离不开 KV Cache、调度、队列和容量规划；
- 为什么 Docker 不能替代 GPU、存储、密钥、发布和可观测性设计；
- 多模型路由为什么必须先满足能力、数据与安全硬约束；
- 模型慢、贵、错、不可用时如何分层收集证据；
- 微调为什么是数据/评测/发布工程，而不是训练命令；
- 为什么模型输出的概率性永远不能替代业务权限、工具校验和副作用控制。

这些判断能力，是从“会调用模型”迈向“能设计并运营 AI 应用基础设施”的关键一步。

## 常见误区

### 误区 1：模型版本就是权重文件版本

纠正：真实行为还受 Tokenizer、模板、adapter、Prompt、RAG、工具、路由、采样、引擎和配置影响。权重不变也可能因其他资产变化而输出不同。

### 误区 2：只要模型/API 没改，Prompt 或 RAG 改动无需发布流程

纠正：Prompt、索引、Embedding、Rerank、工具 Schema 和路由都能改变质量、安全、成本和兼容性。变更风险不同，但都应可追溯、验证和回滚。

### 误区 3：灰度就是把新模型开给一部分用户

纠正：灰度还需要预设观察指标、停止条件、可用旧版本、回滚责任和数据/安全边界。没有这些，灰度只是不可控的线上试验。

### 误区 4：上线后有监控就够了

纠正：监控只能发现部分问题。需要离线评测、挑战集、发布门禁、版本谱系、灰度、用户反馈和 Bad Case 回流共同组成质量闭环。

### 误区 5：回滚就是重启旧容器

纠正：故障可能来自模型、adapter、Prompt、RAG、路由、引擎或配置。必须识别根因，回滚合适层，同时验证恢复；只重启容器未必有用。

### 误区 6：旧模型/数据随时删掉，反正新版本已经上线

纠正：过早删除会破坏回滚、审计和问题复现；无限保留又有成本和隐私风险。应有明确保留与下线策略。

### 误区 7：阶段 13 学的是运维，所以与 AI 应用开发关系不大

纠正：模型能力、Token、延迟、成本、RAG、工具、路由和微调直接决定 AI 应用可行性。不了解运行边界，应用设计就很容易停留在演示级别。

## 本节练习

### 练习 1：列出发布单元

某团队将客服模型从基础模型升级为 LoRA adapter 版本，同时修改系统 Prompt，并替换 Embedding 模型。请列出至少十项应该进入发布清单的内容。

答案：可包括逻辑模型名、基础模型精确版本/哈希、adapter 版本与 LoRA 配置、Tokenizer/聊天模板、推理引擎镜像和参数、系统 Prompt 版本、Embedding 模型版本、文档/切分规则、向量索引快照、Rerank 配置、RAG top-k、工具 Schema、数据权限规则、路由/回退配置、评测集与质量结果、性能与成本结果、灰度范围、监控面板、回滚版本和负责人。具体字段取决于改动，但不能只记录 adapter 文件。

### 练习 2：分析兼容性事故

团队换了新的 Embedding 模型，却没有重建已有向量索引，RAG 质量快速下降。为什么？如何避免？

答案：不同 Embedding 模型通常产生不同维度、语义空间和向量分布；即使维度碰巧相同，旧文档向量与新查询向量也不一定可比较，导致检索失真。应将 Embedding 模型与索引版本绑定，重建或双写/灰度索引，使用检索评测验证，再切换查询路径；保留旧索引以便回滚。

### 练习 3：设计灰度停止条件

为一个新的客服聊天 adapter 设计至少四项灰度观察指标和两项停止/回滚条件。

答案：观察指标可包括 P95 TTFT、流中断/错误率、JSON/工具契约通过率、关键评测/人工抽样质量、用户转人工率、输入输出 Token 与单位成本、敏感策略命中率。停止/回滚条件例如关键安全测试或线上越权信号出现；结构化输出失败率高于基线阈值；P95 TTFT 持续超 SLO；关键任务人工抽样质量显著低于基线。阈值应在发布前定义而不是事后解释。

### 练习 4：追溯一次异常回答

用户投诉昨天和今天问同一问题得到不同答案。请列出你会查询的至少八项谱系/观测信息。

答案：请求时间、trace_id、逻辑模型和实际模型/adapter 版本、Tokenizer/聊天模板、Prompt 版本、RAG 文档/索引/Embedding/Rerank 版本、检索到的引用、路由和是否回退、生成参数、工具调用及结果、用户权限/数据过滤结果、输入输出 Token、发布/配置事件、错误/重试记录。先比较这些证据，才能判断差异来自模型、知识、路由、数据还是用户上下文。

### 练习 5：选择回滚层

发布后发现模型响应速度正常，但所有工具调用都因字段名不匹配失败；模型本身、RAG 和 GPU 指标均正常。最优先怀疑并回滚/修复哪一层？为什么？

答案：优先检查工具 Schema、Prompt 中的工具定义、模型 API 的工具调用适配和下游参数映射，而不是先回滚模型或扩容 GPU。症状指向输出契约兼容性问题；应用 Trace 和契约测试确认字段变化，选择最小可逆修复或回滚该配置/适配层。

## 自测题

### 自测 1：什么是模型谱系？

答案：模型谱系是从一个线上模型能力版本反向关联其基础权重、adapter、Tokenizer、训练数据、训练配置、评测、镜像、Prompt、RAG、路由和部署事件的可追溯关系。它用于复现、审计、排障、回滚和治理。

### 自测 2：为什么不可变资产和可变配置要区分？

答案：不可变资产通过版本/哈希保证内容可精确复现；可变配置支持受控路由、流量、开关和环境调整。区分后既能稳定追溯，又能灵活运营，但两者都需要审计和变更控制。

### 自测 3：模型上线最少需要哪些类别的证据？

答案：至少需要资产/许可和来源证据、独立质量与安全评测、目标运行环境的性能/资源验证、API/工具/RAG 契约兼容、灰度与回滚计划、上线后的观测和责任归属。具体深度随风险提升。

### 自测 4：为什么“model:latest”不足以支持生产排障？

答案：`latest` 是可变别名，时间不同可能指向不同权重/镜像，无法精确复现。生产应同时记录实际模型/镜像/数据等不可变 ID 或哈希，以及人类可读版本和路由事件。

### 自测 5：完成 M13 后，模型服务异常应如何开始排查？

答案：先确定影响范围与症状（慢、贵、错、不可用），保护用户并查看 Trace/指标/发布事件；再按层检查 Token/上下文、资源与引擎、API/网络、部署/队列、路由/回退、RAG/工具/权限、模型/Prompt/数据版本；最后用可逆动作恢复并复盘。不要未收集证据就盲目换模型或重启全部服务。
