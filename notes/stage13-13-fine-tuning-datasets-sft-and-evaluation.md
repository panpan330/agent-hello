# M13 第 14 节：微调数据集、SFT 与评估

## 本节定位

上一节回答了“什么时候值得微调”。一旦决定进入验证，最关键的工作通常不是先选 GPU、调学习率或运行训练命令，而是定义并治理数据：样本到底代表什么任务，什么是正确答案，哪些数据可合法使用，怎样避免训练集泄漏到评测集，怎样证明训练后的模型真的变好。

本节讲监督微调（SFT）的数据与评估基础。你会看到微调项目更像一个数据和实验工程：训练只是其中一环，数据规格、标注规范、切分、质量检查、离线评估和上线验证共同决定结果是否可信。

本节仍是纯知识笔记，不会要求你准备或上传任何真实业务数据。

## 本节学习目标

学完后，你应当能够：

1. 解释监督微调（SFT）的输入、目标和基本训练思想。
2. 区分原始数据、样本、标注、训练集、验证集、测试集和线上评估数据。
3. 为一个任务写出清晰的数据规格和标注规范。
4. 说明数据质量、代表性、覆盖、去重、合法性、时间范围和标签一致性的重要性。
5. 理解数据泄漏、近重复泄漏、时间泄漏和评测集污染的常见形式。
6. 掌握训练/验证/测试划分的目的与基本原则。
7. 为分类、抽取、生成、结构化输出等任务选择合适评估维度。
8. 解释为什么损失（loss）下降不等于业务质量提升。

## 一句话先讲透

**SFT 是让模型从“输入上下文 -> 理想输出”的示例中学习目标行为；训练数据定义了它会学什么，独立评测数据决定你是否有资格说它真的学会了。**

## 基础知识铺垫

### 1. 什么是监督学习

监督学习的基本形式是：给模型许多带有“参考答案”的样本，让它学习从输入到目标输出的映射。

```text
输入 x  ->  目标 y
```

例如：

```text
输入：用户描述“收到的商品有破损，想退货”
目标：{"category":"quality_issue","priority":"normal"}
```

训练过程中，模型产生预测输出，与目标输出比较，计算差异（loss），再通过优化算法调整参数，使未来在类似输入上更倾向于产生目标形式。

这不是“模型背诵正确答案”的简单过程。你希望它从多个样本中学到可泛化规律；但如果数据少、重复、错误或与真实请求分布不一致，模型可能只记住表面模板，面对新表达就失败。

### 2. 什么是监督微调（SFT）

监督微调（Supervised Fine-Tuning，SFT）是在已有模型上，使用高质量的输入输出示例继续训练。

对于对话模型，一个样本可能表示为消息序列：

```json
{
  "messages": [
    {"role": "system", "content": "你是售后分类助手。"},
    {"role": "user", "content": "鞋子开胶了，想处理一下。"},
    {"role": "assistant", "content": "{\"category\":\"quality_issue\",\"priority\":\"normal\"}"}
  ]
}
```

训练时，模型通常以 system/user 等前文为条件，学习预测 assistant 的目标 Token。很多实现会对用户输入部分做 **mask**，即不把“复现用户说了什么”作为主要训练目标，而把 assistant 输出作为计算损失的重点。

不同训练框架的数据字段与模板可以不同，但本质一致：**让模型在给定上下文后生成期望的助手行为。**

### 3. 样本不是原始记录的同义词

原始业务数据可能是一整段聊天、一个工单表、一份 PDF、一次 API Trace 或一条人工反馈。训练样本是经过任务定义、筛选、清洗、脱敏、标注和格式化后，能用于学习的单位。

```text
原始客服对话
-> 选择与目标任务有关的片段
-> 去除隐私和无关上下文
-> 按标注规范给出正确输出
-> 形成一个可审计训练样本
```

直接把原始数据全量喂给训练通常不可靠，因为其中可能含有：错误回复、过期政策、隐私信息、无效闲聊、系统异常、重复文本、未完成任务、与目标无关的字段。

### 4. 数据集的基本角色

一个规范数据项目至少区分：

- **训练集（train set）**：模型真正看到并据此更新参数的数据。
- **验证集（validation/dev set）**：训练过程中用于选择超参数、检查过拟合、比较实验的独立数据。
- **测试集（test/holdout set）**：在方案确定后才用于最终评估的数据，不能用于反复调参。
- **线上监控/回流集**：上线后从真实请求和 Bad Case 中得到的新证据，用于长期观察，而非直接混入当前测试结论。

它们的分离不是形式要求。若你用同一份数据训练、调参、汇报结果，模型可能只是记住样本，你却会误以为它学会了任务。

### 5. 训练损失与业务指标的差别

训练损失衡量模型输出 Token 与训练目标 Token 的统计差异。损失下降通常意味着模型更能拟合训练分布，但它不自动说明：

- 新的真实用户表达也能正确处理；
- JSON 字段的语义正确；
- 模型不越权、不泄露、不幻觉；
- RAG/工具链能正常工作；
- 业务满意度、人工节省或成本得到改善；
- 在长文本、对抗输入和长尾场景下没有退化。

所以 loss 是训练过程的重要信号，却不是上线决策的充分证据。最终要用独立测试集和业务相关指标验证。

### 6. 数据集版本：数据也需要像代码一样管理

若你不能回答“这个模型用了哪批数据训练”，就无法复现、审计或解释结果。数据集版本至少应记录：

- 数据集名称、版本、创建日期和负责人；
- 原始数据来源和时间范围；
- 任务定义、标注规范和标签版本；
- 样本数量、类别分布、长度分布；
- 清洗、去重、脱敏、过滤规则；
- train/validation/test 的切分规则和随机种子；
- 数据许可、隐私和使用范围；
- 已知局限、排除项和变更记录。

数据版本不必一开始就引入复杂平台。哪怕是受控目录、清晰元数据和不可随意覆盖的快照，也比“final_v2_new.jsonl”可靠得多。

## 本节主题系统讲解

### 1. 从业务目标写出数据规格

在收集样本前，先写**数据规格（data specification）**。它回答“要让模型学什么”，而不是“目前手里有什么数据”。一个完整规格可包含：

1. **任务名称与业务目的**：例如“售后文本意图分类，辅助工单分流”。
2. **输入范围**：允许哪些字段、最大长度、语言、是否含历史上下文。
3. **输出契约**：标签、JSON Schema、允许值、空值、错误/不确定时如何表达。
4. **不做什么**：不判断退款资格、不查询订单、不执行工具、不输出个人信息。
5. **正确性标准**：如何判断标签/字段/文本是对的。
6. **安全与合规规则**：敏感信息、版权、用户授权、保留期限。
7. **覆盖目标**：核心类别、长尾类别、边界案例、注入/异常输入、不同语言/渠道。
8. **评估指标和门槛**：何时认为模型可以进入灰度。

没有规格时，数据收集会被“有什么就用什么”主导，训练目标和评估目标也会逐渐漂移。

### 2. 标注规范：把“人的理解”变成一致规则

标注规范（annotation guideline）是给标注者、审核者和未来维护者的共同语言。它通常应包括：

- 每个标签/字段的定义；
- 正例、反例和容易混淆的例子；
- 决策顺序与优先级；
- 多标签/冲突/信息不足时如何处理；
- 日期、金额、订单号等字段的格式；
- 是否允许根据常识补全未出现的信息；
- 遇到隐私、攻击性、违法或无关内容如何标记；
- 不确定样本如何进入复审队列；
- 标注版本和变更历史。

例如“物流问题”和“未收到货”看似相近，但标注规范要回答：超过预计送达时间但仍在运输中算哪个？用户既说包装破损又说物流慢，主类如何决定？没有订单号是否返回 `null` 还是猜测？

规则不清时，不同标注者会产生互相矛盾的“正确答案”，模型只能学到噪声。

### 3. SFT 样本的输入上下文设计

对话模型的训练样本通常包含 system、user、assistant，有时还有工具调用或工具结果。关键原则是：训练时的上下文形态要尽量接近推理时真实形态。

#### 3.1 System 消息

system 消息可表达稳定角色、输出契约和安全边界。若线上 system prompt 会长期变化，是否在 SFT 样本中包含它需要谨慎：

- 包含：模型可学习在该固定前提下的行为，但可能过度绑定某模板；
- 不包含或简化：更灵活，但训练与线上分布差异可能增大。

没有通用答案，应记录选择原因，并保持训练/推理模板兼容。

#### 3.2 User 输入

应保留对任务必要的自然语言和上下文，删除无关/敏感字段。不要人为把所有输入改得特别规范，否则模型上线后遇到真实错别字、口语、重复描述和不完整信息会失效。

#### 3.3 Assistant 目标输出

目标应真实体现你希望模型学会的行为。若要结构化输出，示例必须稳定、合法且符合同一 Schema；若允许不确定性，应显式示范“信息不足”的正确输出，而不是把所有样本都强行标为某个类别。

### 4. 对话数据中的训练目标与 Mask

一个多轮样本可能是：

```text
system: 你是分类助手。
user: 订单物流三天没更新。
assistant: {"category":"logistics","priority":"normal"}
user: 已经超过预计送达日期了。
assistant: {"category":"logistics","priority":"high"}
```

SFT 训练通常希望模型学习 assistant 部分，而不是学习复述 system/user 内容。框架会通过标签 mask 或格式模板，将不需要预测的位置设为忽略。

理解这一点有两个好处：

- 你知道为什么聊天模板与角色边界会影响训练；
- 你不会误以为“把任意纯文本拼成一行”就等价于对话 SFT。

不同框架对 assistant 起止标记、EOS Token、工具消息和多轮 loss 的处理不同。训练前必须确认数据预处理与实际模型模板一致，否则模型可能学会错误的角色、重复输入或无法正确结束。

### 5. 结构化输出样本的设计

结构化任务常见目标：

```json
{
  "category": "logistics",
  "priority": "high",
  "order_id": null,
  "needs_human_review": true
}
```

高质量样本应统一：

- 键名、大小写、字段顺序（若评测依赖）、枚举值和空值表达；
- 日期/金额/ID 格式；
- 是否允许额外字段；
- 不确定或缺失信息的表达；
- 输出是否只包含 JSON，还是包含解释字段；
- 何时应拒绝或要求补充信息。

但必须记住：训练样本统一格式不等于线上可以相信模型输出。线上仍需 JSON Schema、解析、类型校验、业务校验和失败处理。SFT 提高倾向，确定性验证负责保证边界。

### 6. 数据质量的六个维度

可以从六个维度审查训练数据。

#### 6.1 正确性（correctness）

目标输出是否符合事实、规则和任务定义？错误标签会被模型学习。

#### 6.2 一致性（consistency）

相似输入是否按同一规则标注？不同类别、不同标注者、不同时间段的定义是否一致？

#### 6.3 代表性（representativeness）

数据是否像真实线上输入？渠道、语言、长度、拼写错误、长尾、时间段和用户群体是否被覆盖？

#### 6.4 覆盖性（coverage）

关键类别、边界、负例、信息不足、对抗输入、罕见但高风险案例是否存在？

#### 6.5 合法性与安全性（legality and safety）

数据是否有训练许可？是否包含个人信息、密钥、受版权保护内容、敏感业务数据？脱敏是否真的不可逆且保留任务价值？

#### 6.6 可追溯性（traceability）

样本能否追溯来源、标注规则、审核状态和版本？发现错误后能否定位并处理受影响模型？

数据量是第七个维度，但不是第一位。大量不一致、过时或不合规数据会让项目风险变大。

### 7. 清洗、过滤与去重

训练数据通常要经过多步处理：

```text
原始候选
-> 格式校验
-> 去除空/乱码/损坏/重复
-> 敏感信息检测与脱敏
-> 规则过滤（长度、语言、质量）
-> 标注与审核
-> 近重复检测
-> 切分与版本冻结
```

#### 7.1 精确重复

完全相同的样本重复出现，会让模型过度关注某些模板，并使评测数据可能虚高。可通过规范化文本、哈希等方法识别。

#### 7.2 近重复

更危险的是只改了订单号、姓名、少量措辞的样本：

```text
“订单 A1001 三天没更新”
“订单 A1002 三天没更新”
```

若一个进入训练、另一个进入测试，模型可能只是见过几乎一样的模式，测试分数不代表对真正新样本的泛化。近重复检测可基于模板、相似度、来源会话、文档 ID 或时间分组进行。

#### 7.3 过滤不是越严格越好

过度清洗会把真实世界中的拼写错误、口语、混合语言、不完整描述全部删掉，让模型只见过“教科书输入”。应删除无价值噪声和不合规数据，但保留经过安全处理的真实难例。

### 8. 脱敏与数据最小化

业务训练数据可能含姓名、电话、地址、订单号、账号、合同、内部策略甚至 API Key。必须在进入训练管道前定义处理方式：

- 删除不影响任务的字段；
- 用占位符替换，例如 `<PHONE>`、`<ORDER_ID>`；
- 使用一致但不可逆的伪标识，保留同一用户/订单的关联特征；
- 对无法安全脱敏的数据不纳入训练；
- 限制原始数据和清洗数据的访问权限、保留期限和导出路径。

脱敏并非简单正则替换。上下文组合可能重新识别个人，例如罕见事件、地址片段、时间、姓名组合。对高敏感领域应与安全、法务或数据治理要求协同，而不是由开发者单独猜测。

### 9. 训练、验证、测试如何切分

#### 9.1 基本目标

- 训练集用于更新权重；
- 验证集用于训练过程中选择策略；
- 测试集在最终方案冻结前尽量不看，作为近似“未来未见数据”的评估。

常见比例如 80/10/10 只是起点，不是规则。小数据集可能需要交叉验证或更谨慎的人工复核；高风险任务要确保测试集数量和覆盖足够。

#### 9.2 随机切分的局限

随机切分在独立同分布（IID）假设下简单，但真实业务常不满足：同一用户、同一文档、同一工单模板、同一时间事件高度相关。随机切分容易把近重复样本分到不同集合，造成泄漏。

#### 9.3 分组切分

按用户、会话、订单、文档、来源系统或模板分组，使同一组只进入一个集合。它更接近真实泛化：模型要处理未见过的新会话/新文档，而不是同一事件的改写。

#### 9.4 时间切分

若数据会随政策、产品、语言风格或业务流程变化，可用较早时间的数据训练、较晚时间的数据测试。它能暴露“模型是否能适应未来分布”，也能避免把未来政策或结果泄漏给过去任务。

#### 9.5 挑战集（challenge set）

除常规测试集外，专门收集高风险边界：长文本、拼写错误、多意图、缺失字段、冲突描述、Prompt Injection、越权请求、罕见类别、不同方言/语言。它不一定反映平均流量，但能防止模型在关键边界上失控。

### 10. 数据泄漏：为什么分数会虚高

数据泄漏是指训练或调参阶段以不应有的方式获得了评测答案或与答案高度相关的信息。常见形式：

#### 10.1 精确样本泄漏

相同输入输出同时出现在训练和测试中。

#### 10.2 近重复泄漏

只替换少数实体、日期、订单号或标点的样本跨集合出现。

#### 10.3 会话/文档泄漏

同一用户会话、同一 PDF 的相邻 chunk、同一工单不同轮次被随机分到不同集合。

#### 10.4 时间泄漏

训练数据包含测试时间之后才会知道的信息，例如后续状态、最终处理结果、新版政策。

#### 10.5 标签泄漏

输入中意外包含答案字段，例如文件名、内部处理标签、人工备注、系统提示或可直接识别的编码。

#### 10.6 评测集污染

团队根据测试集反复改 Prompt、数据、规则和超参数，最终测试集变成验证集。即使没有直接用于训练，最终分数也会过度乐观。

防泄漏的根本不是某个工具，而是把数据来源、分组、时间、模板、标注字段和评测访问流程设计清楚。

### 11. 验证集与测试集如何分别使用

一个健康流程：

```text
训练集：训练模型
验证集：选择训练轮数、学习率、数据配方、适配器配置
测试集：在方案冻结后做一次或有限次数最终评估
挑战集：检查高风险边界和安全
线上灰度：验证真实分布与业务结果
```

如果每次实验后都根据测试集得分调整方案，测试集就被“看穿”了。可以保留一个更严格的最终 holdout，只在发布候选确定时使用；或将不同评测集分为开发、验证、验收三层。

### 12. 任务评估：不同任务，指标不同

#### 12.1 分类任务

可用准确率、Precision、Recall、F1、混淆矩阵、每类指标、宏/微平均等。

- 类别不平衡时，单看 accuracy 会误导。例如 95% 都是物流类，模型全猜物流也可能有高准确率。
- 高风险小类要单独看 Recall，不能被总体平均淹没。
- 混淆矩阵能看出哪些类别总被误判为彼此。

#### 12.2 信息抽取任务

可按字段计算精确匹配、部分匹配、字段级 Precision/Recall/F1、格式合法率、空值处理正确率。

例如订单号字段的评估不能只看 JSON 是否可解析，还要看是否提取正确、是否在不存在时乱猜、是否把别的 ID 当订单号。

#### 12.3 生成与摘要任务

自动指标（如词面重合）可提供部分参考，但常无法充分反映事实性、风格、完整性和安全。需要结合：

- 规则检查：是否含必须字段、是否超长度、是否引用；
- LLM-as-judge：应有固定 rubric、抽样人工校准、避免让同一模型自证；
- 人工评审：尤其是高风险、少量关键样本；
- 业务指标：人工转接率、编辑时间、用户满意度等。

#### 12.4 结构化输出和工具调用

至少分层评估：

```text
语法合法：JSON 是否能解析
Schema 合法：字段、类型、枚举是否正确
语义正确：分类/参数是否符合用户意图和业务事实
安全合法：是否越权、越界、跳过确认
执行成功：下游工具是否接受并完成
```

只报告“JSON 合法率 99%”可能掩盖最重要的语义和安全错误。

### 13. 人工评测如何提高可信度

生成任务常无法完全自动判定，需要人工。人工评测应尽量减少随意性：

- 使用明确评分 rubric，例如事实性、完整性、风格、安全、引用；
- 对评测者做校准，先共同评一些样本；
- 让多个评测者独立评一部分数据，检查一致性；
- 进行盲评，尽量不让评测者知道来自哪个模型；
- 随机打乱样本顺序，避免版本顺序偏差；
- 记录不确定和争议样本，不强迫伪精确标签；
- 对高风险案例设专家复审；
- 记录标注规范版本和评测时间。

人工评测不是绝对客观，但通过规范可让它足够可靠地用于工程决策。

### 14. 训练曲线应该怎么看

训练过程中常看到 train loss 和 validation loss 曲线：

```text
训练损失持续下降，验证损失也下降：通常是正向信号
训练损失下降，验证损失上升：可能开始过拟合
两者都几乎不下降：数据、任务、学习率、格式或模型能力可能有问题
两者剧烈抖动：训练不稳定、数据异常、批次过小或配置不合适
```

但要避免过度解读：

- validation loss 最低的 checkpoint 不一定业务指标最好；
- 生成任务的微小 loss 差异可能不显著改善人工偏好；
- 训练/验证模板不一致时，曲线本身就失去解释性；
- 测试集和挑战集仍是最终外部证据。

训练曲线帮助选择候选 checkpoint，业务评测决定是否可用。

### 15. 数据平衡与真实分布的取舍

真实数据常类别极不平衡：常见物流咨询很多，罕见欺诈或安全事件很少。若完全按真实比例训练，模型可能忽略稀有但重要类别；若强行完全均衡，又可能偏离线上分布、使常见任务退化。

可考虑：

- 对稀有高风险类适度过采样或增加人工样本；
- 保持评测集同时包含真实分布与挑战集；
- 分别报告总体指标和关键少数类指标；
- 对无法安全自动处理的稀有类使用“转人工/不确定”策略；
- 不用合成数据替代所有真实长尾证据。

目标不是让数据表格看起来均匀，而是让模型在真实业务风险下表现可接受。

### 16. 合成数据：有用，但不能当真相来源

合成数据可由模板、规则、教师模型或人工组合生成。它的价值包括补足罕见表达、扩展格式覆盖、快速构建 PoC、生成边界案例。

风险包括：

- 生成器本身的错误和偏见被复制；
- 文本风格单一，模型只学会“合成腔”；
- 合成标签看似完整，实则与真实业务规则不一致；
- 用同一模型生成训练和评测数据，造成自我循环和虚高分；
- 包含不应被模型学习的假设或敏感模式。

正确用法是将合成数据作为受控补充：标记来源、抽样审核、与真实数据分开统计、在真实独立测试集上验证，不把它当作无成本的高质量数据。

### 17. 一个完整的数据集流水线示例

以“售后工单结构化分类”为例：

```text
1. 定义任务
   输入：脱敏后的用户描述 + 必要上下文
   输出：category / priority / needs_human_review

2. 写标注规范
   类别定义、冲突规则、缺失信息、拒绝/转人工条件

3. 收集候选数据
   已人工确认的历史工单，明确时间范围和许可

4. 安全处理
   去除姓名、电话、地址、完整订单号及无关内部备注

5. 清洗与审核
   格式、重复、过时政策、标签冲突、异常文本

6. 分组/时间切分
   同一会话/订单只在一个数据集；保留较新时间段做测试

7. 冻结版本
   生成数据统计、哈希、规则、样本清单、已知缺陷

8. 建立基线
   当前 Prompt/基础模型在 test/challenge 上的多维指标

9. 训练候选模型
   使用 train，按 validation 选择方案

10. 最终评估和灰度
    使用未被调参污染的 test/challenge，再在线上受控验证
```

这个过程看起来比“导出 JSONL -> 开始训练”长，但它直接决定训练结论有没有价值。

### 18. 数据卡（Data Card）的最小内容

对一个重要训练数据集，可以建立简化的数据卡：

```text
名称与版本：support-ticket-sft-v1
任务：售后工单分类与字段抽取
数据来源：已授权、人工确认的历史工单，时间范围...
规模与分布：总数、类别、语言、长度、来源渠道
处理：脱敏、过滤、去重、标注审核规则
切分：按会话/订单分组，按时间保留测试集
许可与隐私：允许用途、访问控制、保留/删除策略
已知限制：罕见类别样本不足、某渠道覆盖较少
禁止用途：不用于退款资格裁决、不用于身份判断
负责人和变更记录：...
```

它帮助训练、评测、部署和合规人员共享同一事实，也帮助未来发现数据问题时追溯影响。

## 常见误区

### 误区 1：有输入和输出就已经是高质量 SFT 数据

纠正：样本还需要任务定义、正确标签、一致格式、合法来源、代表性、去重、脱敏和可追溯性。原始历史记录常不是可直接训练的数据。

### 误区 2：训练 loss 下降就说明模型更好

纠正：loss 主要说明对训练分布的拟合。必须在独立测试集、挑战集和业务指标上比较质量、安全、格式、延迟和成本。

### 误区 3：随机切分总是公平的

纠正：同一会话、订单、文档或模板的近重复样本会泄漏到不同集合。真实业务常需要分组或时间切分。

### 误区 4：JSON 能解析就代表抽取正确

纠正：还要检查 Schema、每个字段语义、空值、不猜测、权限和下游执行结果。语法合法只是最低层。

### 误区 5：训练数据越多效果一定越好

纠正：大量重复、错误、过期、不合规或不代表真实分布的数据会损害模型和评估。质量、覆盖与一致性更关键。

### 误区 6：测试集可以反复用来调方案

纠正：反复依据测试分数调 Prompt、数据或超参数会污染测试集，使它变成验证集。应保留严格 holdout 或分层评测集。

### 误区 7：脱敏就是把姓名替换为星号

纠正：组合上下文仍可能识别个人；不同任务需要保留不同结构；还要考虑访问、保留、导出、删除和授权。脱敏是数据治理过程，不是单一正则操作。

## 本节练习

### 练习 1：写数据规格

请为“将用户售后描述分类为 `logistics`、`refund`、`quality_issue`、`other`，并输出是否需人工复核”的任务写出至少六项数据规格内容。

答案：可包括任务目的（辅助分流而非最终裁决）；输入（脱敏用户描述、可选订单状态摘要，长度/语言范围）；输出 JSON Schema 和标签定义；不做什么（不决定退款、不查询实时订单）；缺失/多意图/攻击输入时 `needs_human_review` 的规则；类别覆盖目标；数据许可与脱敏要求；评估指标如每类 F1、JSON Schema 通过率、关键高风险类 Recall、人工复核正确率；上线门槛和回滚条件。

### 练习 2：识别泄漏

以下切分方式有什么问题：同一张订单的第一轮客服聊天在训练集，第二轮聊天在测试集；同一 PDF 的相邻 chunk 随机分入不同集合；2026 年的最终退款结果被作为 2025 年预测任务的输入字段。

答案：第一种是会话/订单泄漏，模型可能看到相同事件和实体；第二种是文档/近重复泄漏，测试不代表对新文档泛化；第三种是时间/未来信息泄漏，真实预测时不可能获得该字段。应按订单/会话/文档分组，并按时间边界切分和审查字段。

### 练习 3：为抽取任务设计评估层次

对“抽取订单号、问题类别、优先级”的模型，为什么不能只统计 JSON 解析成功率？请列出至少四层评估。

答案：至少包括 JSON 语法是否合法；是否符合 Schema（字段、类型、枚举）；字段语义是否正确，例如订单号是否真的来自输入、类别是否匹配；缺失信息时是否正确返回 null/人工复核而非猜测；高风险或注入输入下是否安全；若触发下游流程，工具参数是否通过业务校验。解析成功仅是第一层。

### 练习 4：判断数据是否可直接训练

团队拿到 10 万条历史客服记录，其中包含真实姓名、电话、订单号、已经废弃的政策和大量客服错误回复。请说明不能直接训练的原因，并给出处理步骤。

答案：存在隐私/授权风险、过时知识、错误行为学习、与目标任务无关内容、重复/模板数据和标签不一致风险。应先定义任务和使用许可；进行访问控制、脱敏/最小化；按时间和政策版本过滤；筛选人工确认或审核过的目标输出；清洗去重；按标注规范复核；按会话/订单/时间切分；冻结版本并建立独立评测集。不能把“历史存在”当作“训练可用”。

### 练习 5：解释验证集和测试集

训练过程中用验证集多次选择最佳学习率和训练轮数后，是否还应使用它报告最终效果？为什么？

答案：不应只用它报告最终效果，因为方案已根据验证集反复调整，它会产生选择偏差。应在未参与调参的测试集或最终 holdout 上进行最终评估，并报告验证和测试用途的区别。

## 自测题

### 自测 1：SFT 的基本训练目标是什么？

答案：在给定上下文（通常包括 system、user 和可能的历史/工具消息）后，学习生成高质量的目标 assistant 输出。训练通过最小化预测与参考输出的差异来调整已有模型权重。

### 自测 2：为什么训练/验证/测试要分开？

答案：训练集用于学参数，验证集用于选择训练配置，测试集用于近似评估对未见数据的泛化。混用会导致模型或开发过程“记住”评测样本，离线分数虚高。

### 自测 3：数据代表性指什么？

答案：训练和评测数据在语言、渠道、长度、类别、时间、噪声、用户群体和真实任务难度上，能合理反映模型上线后会遇到的分布。只用整洁的典型样本会导致线上分布偏移。

### 自测 4：什么是近重复泄漏？

答案：训练和测试中没有完全相同的样本，但共享几乎相同的模板、会话、文档、实体或只改少量词。模型可能凭记忆取得高分，不能证明对真正新问题的泛化。

### 自测 5：数据卡有什么作用？

答案：数据卡记录数据集的来源、任务、规模、分布、处理、切分、许可、隐私、局限、禁止用途和版本，帮助复现、审计、协作和发现数据问题后的追溯。

## 本节小结

本节建立了 SFT 数据工程的主线：先用数据规格定义任务，再用标注规范保证一致性；从原始记录中经过合法性审查、脱敏、清洗、去重和审核得到可用样本；用合理的训练/验证/测试/挑战集切分防止泄漏；再用与任务匹配的多维评估验证真实收益。

损失下降只是训练信号，不是业务成功。模型是否值得上线，需要在独立数据上同时证明质量、结构化契约、安全、性能和成本不劣于基线。下一节会在此基础上讲 LoRA、QLoRA 与微调完整流程，说明怎样用参数高效微调把这些数据和评测真正变成一次受控实验。
