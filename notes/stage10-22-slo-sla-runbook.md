# 阶段 10 第 22 节：SLO / SLA / Runbook

## 本节定位

前面第 20 节我们学习了生产监控指标与告警，第 21 节学习了灰度发布、回滚和配置开关。

这一节继续往线上运营方向走：当系统真的上线后，团队不能只说“有监控、有告警、有回滚”。还要能说清楚：

- 我们承诺这个服务应该达到什么水平？
- 哪些指标代表服务对用户来说是好的？
- 指标坏到什么程度算故障？
- 故障发生后谁来处理、先看什么、先做什么、什么时候升级、什么时候回滚？
- 故障恢复后怎么复盘，避免下一次再发生？

这就是 SLO、SLA 和 Runbook 解决的问题。

## 本节学习目标

学完本节，你应该能讲清楚：

- SLI、SLO、SLA 分别是什么。
- 为什么“有监控指标”不等于“服务质量有目标”。
- 错误预算是什么，它为什么能帮助团队决定是否继续发版。
- P0、P1、P2、P3 故障分级一般怎么理解。
- Runbook 为什么不是普通文档，而是故障时按步骤执行的操作手册。
- AI 应用里的 SLO 为什么不只包括 HTTP 可用性，还要包括 LLM、RAG、工具调用、成本和安全。
- 当前项目如何用代码把 SLO、故障信号、故障分级和 Runbook 结构化记录下来。

## 一句话先讲透

监控告诉你“系统现在发生了什么”，SLO 告诉你“系统应该达到什么水平”，SLA 告诉外部“达不到会承担什么承诺”，Runbook 告诉工程师“坏了之后按什么步骤恢复”。

## 基础知识铺垫

### 1. 为什么光有监控还不够

监控指标可以告诉你很多事实：

- 过去 15 分钟 HTTP 5xx 是否升高。
- p95 延迟是否超过 5 秒。
- LLM 调用失败率是否超过 10%。
- RAG 是否出现大量无上下文结果。
- token 成本是否突然上涨。

但是指标本身不会自动告诉你“这到底严重不严重”。

举个例子：

- p95 延迟 3 秒，对后台导出任务可能可以接受。
- p95 延迟 3 秒，对实时客服聊天可能已经明显影响体验。
- RAG 偶尔没有检索结果可能正常。
- RAG 大量没有检索结果，可能说明知识库挂了、权限过滤错了、score threshold 设置太高了。

所以线上系统需要把指标进一步翻译成服务目标。

服务目标回答的问题是：

```text
从用户角度看，这个服务到底要稳定到什么程度才算合格？
```

这就是 SLO 的价值。

### 2. SLI 是什么

SLI 的英文是 Service Level Indicator，意思是“服务等级指标”。

它是一个可以被测量的指标，用来代表用户感受到的服务质量。

常见 SLI：

- 可用性：成功请求数 / 总请求数。
- 延迟：p95 请求耗时。
- 错误率：失败请求数 / 总请求数。
- 数据正确性：回答通过引用校验的比例。
- 工具成功率：工具成功执行次数 / 工具执行总次数。
- 流式体验：首 token 延迟、流式中断率。

SLI 的重点是“能代表用户体验”。

不是所有 metric 都适合做 SLI。比如：

- `trace_id` 数量不是 SLI。
- 某台机器 CPU 使用率一般不是直接 SLI。
- 某个内部函数执行次数一般也不是 SLI。

它们可以辅助排查，但不一定直接代表用户体验。

### 3. SLO 是什么

SLO 的英文是 Service Level Objective，意思是“服务等级目标”。

它是在 SLI 上设置一个目标值。

例如：

```text
30 天内，AI 服务可用性 >= 99.5%
30 天内，聊天接口 p95 延迟 <= 5 秒
30 天内，LLM 调用成功率 >= 98%
30 天内，RAG 引用校验通过率 >= 97%
30 天内，工具调用成功率 >= 98%
```

SLI 是指标，SLO 是目标。

对比一下：

```text
SLI：AI 服务成功请求比例。
SLO：30 天内 AI 服务成功请求比例至少达到 99.5%。
```

如果你只说“我们看 HTTP 成功率”，这还只是监控。

如果你说“我们要求 30 天窗口内成功率不低于 99.5%，低于目标就停止扩大灰度并进入故障处理”，这才更像生产化运营。

### 4. SLA 是什么

SLA 的英文是 Service Level Agreement，意思是“服务等级协议”。

它更偏对外承诺，通常会出现在商业合同、客户协议、云服务承诺里。

比如：

```text
如果月度可用性低于 99.9%，客户可以获得一定服务补偿。
```

SLO 和 SLA 的关系可以这样理解：

- SLO 是团队内部要达到的目标。
- SLA 是对客户或业务方做出的承诺。
- SLA 通常比 SLO 更慎重，因为它可能涉及赔付、合同、信誉。

真实公司里常见做法是：

```text
内部 SLO 比外部 SLA 更严格。
```

例如：

- 对外 SLA 承诺 99.5%。
- 内部 SLO 设置 99.9%。

这样团队有缓冲空间，不会一接近目标就直接违反外部承诺。

### 5. 错误预算是什么

错误预算英文是 Error Budget。

它来自一个很朴素的想法：

如果我们不要求系统 100% 永不出错，而是允许它在目标范围内有少量失败，那这部分“允许失败的空间”就是错误预算。

例如 SLO 是：

```text
30 天可用性 >= 99.5%
```

那么允许失败比例就是：

```text
100% - 99.5% = 0.5%
```

这 0.5% 就是错误预算。

如果 30 天内实际可用性是 99.8%：

```text
实际失败比例 = 0.2%
允许失败比例 = 0.5%
错误预算消耗 = 0.2 / 0.5 = 40%
```

说明系统还有余量。

如果实际可用性是 99.2%：

```text
实际失败比例 = 0.8%
允许失败比例 = 0.5%
错误预算消耗 = 0.8 / 0.5 = 160%
```

说明错误预算已经耗尽，服务质量低于目标。

错误预算的作用不是为了“允许摆烂”，而是为了平衡稳定性和迭代速度。

错误预算充足时：

- 可以继续灰度新模型。
- 可以继续上线新的 RAG 参数。
- 可以继续试验新的 prompt 或工具链。

错误预算接近耗尽时：

- 应该暂停高风险发布。
- 优先修复稳定性问题。
- 控制 fallback、重试、成本和故障来源。

这和第 21 节灰度发布联系很紧：灰度不是只看“有没有报错”，还应该看候选版本是否消耗了过多错误预算。

### 6. 故障分级是什么

故障分级是为了让团队在故障发生时快速判断优先级。

常见分级：

```text
P0：最高级别，核心服务大面积不可用，严重影响业务。
P1：核心能力明显受损，需要立即处理，可能需要回滚或升级。
P2：局部功能异常或体验下降，需要尽快处理，可以先降级。
P3：轻微问题、低风险问题、观察类问题，可以排查和排期修复。
```

在 AI 应用中，故障不一定只表现为“接口挂了”。

还可能是：

- LLM provider 大量失败。
- 模型正常返回，但回答明显变慢。
- RAG 检索为空，导致无法回答政策问题。
- 工具调用失败，导致查订单、建工单不可用。
- 安全策略异常，正常用户大量被拦截。
- Prompt Injection 攻击流量突然增加。
- token 成本异常上涨。

所以 AI 应用的故障分级要比传统 CRUD 后端多考虑几类 AI 特有风险。

### 7. Runbook 是什么

Runbook 可以翻译成运行手册、故障处理手册。

它不是普通学习笔记，也不是代码注释。

Runbook 是故障发生时工程师可以照着执行的操作步骤。

一个合格的 Runbook 通常应该回答：

- 什么告警触发这个 Runbook？
- 这个故障大概是什么等级？
- 目标是什么，是恢复可用性、降低延迟、控制成本，还是防止不安全回答？
- 第一步看什么指标？
- 第二步做什么降级？
- 什么时候回滚？
- 什么时候升级给其他负责人？
- 怎么判断已经恢复？

故障时人的状态通常不好，压力很大，信息很多，时间很紧。

所以 Runbook 的价值是：提前把处理路径写清楚，让故障时少靠临场发挥。

### 8. 为什么 AI 应用特别需要 Runbook

传统后端常见故障是：

- 数据库挂了。
- 接口 500。
- Redis 不通。
- 某个服务超时。

AI 应用在这些之外，还多了很多不确定性：

- 模型 provider 可以返回非预期错误。
- fallback 可能导致成本升高。
- RAG 参数调整可能导致召回变差。
- prompt 改动可能导致回答风格或结构变坏。
- 工具调用成功，但模型总结错误。
- 用户输入可能包含 prompt injection。
- 流式输出可能开始后中断，无法再返回普通 JSON 错误。

所以 AI 应用的 Runbook 不能只写“看日志、重启服务”。

更好的方式是围绕链路拆分：

```text
入口 HTTP
-> 鉴权/限流
-> Prompt 安全检查
-> LLM 调用
-> RAG 检索
-> Rerank
-> Tool Calling
-> Java 业务服务
-> 模型总结
-> SSE 输出
```

故障时要知道问题到底出在哪一段。

## 本节主题系统讲解

### 1. 从指标到 SLO 的完整关系

第 20 节已经有指标和告警，例如：

- `http.server.requests`
- `http.server.duration`
- `llm.failures`
- `rag.retrieval.empty_results`
- `rag.citation.failures`
- `tool.failures`
- `llm.estimated_cost`

这些指标解决的是“观测事实”。

本节在它上面再加一层：

```text
metric
-> SLI
-> SLO
-> error budget
-> incident classification
-> runbook
```

含义分别是：

- metric：原始监控数据。
- SLI：从用户体验角度挑出的关键指标。
- SLO：对 SLI 设置目标。
- error budget：目标允许的失败空间。
- incident classification：根据故障信号判断严重程度。
- runbook：按严重程度和故障类型执行恢复步骤。

如果把系统上线比作开车：

- metric 像仪表盘上的速度、油量、温度。
- SLI 是你真正关心的关键读数。
- SLO 是你希望保持的安全范围。
- error budget 是允许偏离的空间。
- incident classification 是判断是小问题还是大事故。
- runbook 是出现问题后的标准处理流程。

### 2. 本项目为什么定义这些 SLO

本节默认定义了 5 个 SLO：

```text
ai_service_availability
chat_p95_latency
llm_success_ratio
rag_citation_quality
tool_success_ratio
```

它们覆盖了一个 AI 客服与智能工单系统最核心的质量面：

- 服务能不能用。
- 用户等得久不久。
- 大模型依赖稳不稳。
- RAG 回答有没有依据。
- 工具调用能不能完成真实业务动作。

这里没有把所有指标都做成 SLO。

比如成本也非常重要，但成本更适合做预算、告警和运营指标，不一定都要变成面向用户的 SLO。安全也是类似，很多安全指标应该作为强约束和告警，而不是简单用一个“比例目标”表达。

这点要注意：SLO 不是越多越好。

SLO 太多会导致团队不知道真正该守住什么。

更合理的方式是：

```text
少量关键 SLO + 丰富监控指标 + 清晰 Runbook
```

### 3. 为什么错误预算只对 ratio SLO 做计算

本节代码里的 `build_ratio_error_budget_snapshot()` 只支持 `unit="ratio"` 且 `comparator=">="` 的 SLO。

原因是错误预算最容易解释的是比例型目标。

例如：

```text
成功率 >= 99.5%
```

它天然可以换算：

```text
允许失败率 = 1 - 目标成功率
```

但延迟型目标不一样：

```text
p95 延迟 <= 5000ms
```

这不是“成功率 99.5%”这种形式。它也可以做预算或 burn rate，但计算方式不如比例型 SLO 直接。

为了让你先真正理解错误预算，本节只实现最容易讲透的比例型错误预算。

### 4. 故障分级为什么映射到不同动作

本节把故障信号分成 P0、P1、P2、P3，并映射到默认动作：

```text
P0 -> escalate
P1 -> rollback
P2 -> degrade
P3 -> investigate
无故障 -> monitor
```

这不是唯一标准，但很适合作为学习起点。

解释一下：

- P0：影响面太大，不能只靠单人慢慢查，要立即升级。
- P1：核心能力受损，通常要快速止损，回滚是常见动作。
- P2：体验变差或局部异常，可以先降级，比如关闭昂贵路径、降低模型档位、放宽非核心流程。
- P3：影响轻，可以先排查，不一定马上动生产配置。

AI 应用里“降级”很重要。

比如：

- RAG 慢，可以临时减少 top_k。
- Rerank 慢，可以临时关闭 rerank。
- 强模型慢或贵，可以切到 balanced 模型。
- LLM 失败率高，可以使用 fallback。
- RAG 没上下文，宁可回答“当前资料不足”，也不要让模型编。

### 5. Runbook 和灰度回滚的关系

第 21 节已经有：

- stable version
- candidate version
- feature flag
- kill switch
- guardrail metric
- rollback decision

本节的 Runbook 会引用这些灰度策略名称。

例如：

```text
llm_provider_failure_runbook
-> related_rollout_policies = ["llm-balanced-model-canary"]
```

意思是：如果 LLM 失败率异常，排查时要考虑是不是候选模型引入的问题。

如果异常和候选模型相关，就应该：

```text
关闭 canary flag
-> 流量回到 stable model
-> 观察 llm.failures 是否下降
```

这就是监控、SLO、Runbook、灰度回滚形成闭环。

### 6. 一个真实故障处理链路应该怎么想

假设告警：

```text
High LLM failure rate
```

不要第一反应就“重启服务”。

更合理的排查顺序是：

```text
1. 看失败是否集中在某个 provider。
2. 看失败是否集中在某个 model。
3. 看 error_code 是 auth、quota、timeout、rate_limit 还是 provider_error。
4. 看最近是否做过模型灰度。
5. 看 fallback 是否生效。
6. 看用户侧错误是否被安全包装，没有泄露内部错误。
7. 如果候选模型导致失败，关闭 canary。
8. 如果 provider 故障，切换备用模型或降级。
9. 观察一个告警窗口，确认恢复。
```

这就是 Runbook 要提前写出来的原因。

### 7. Runbook 不是越复杂越好

Runbook 最怕两种情况：

第一种是太空：

```text
收到告警后排查问题并恢复服务。
```

这句话几乎没有帮助。

第二种是太碎：

```text
复制几十个命令，检查几十个页面，每一步都没有判断依据。
```

故障时也很难执行。

好的 Runbook 应该是：

- 步骤有顺序。
- 每一步有目的。
- 每一步知道看什么信号。
- 有明确止损动作。
- 有升级条件。
- 有恢复判断。

本节代码通过 `RunbookStep.order`、`action`、`instruction`、`expected_signal`、`stop_condition` 来表达这些信息。

## 本节代码讲解

### 1. `ServiceLevelIndicatorSpec`

这个模型表示 SLI。

它包含：

- `name`：SLI 名称。
- `metric_name`：来自监控系统的指标名。
- `description`：这个 SLI 的含义。
- `good_event_description`：什么算好事件。
- `total_event_description`：总事件范围是什么。
- `unit`：单位，比如 ratio、ms。

重点是 `good_event_description` 和 `total_event_description`。

因为很多比例指标都必须先定义清楚：

```text
成功率 = 好事件 / 总事件
```

如果好事件和总事件定义不清，成功率就没有意义。

### 2. `ServiceLevelObjectiveSpec`

这个模型表示 SLO。

它把 SLI 变成目标：

```text
sli + comparator + target_value + window
```

例如：

```text
successful_http_request_ratio >= 0.995 in 30d
```

这里的 `window` 很重要。

SLO 很少只看某一分钟，因为短时间波动很多。常见窗口是 7 天、30 天、90 天。

### 3. `ErrorBudgetSnapshot`

这个模型表示某个时刻的错误预算状态。

核心字段：

- `target_ratio`：目标成功率。
- `actual_ratio`：实际成功率。
- `allowed_bad_ratio`：允许失败比例。
- `consumed_bad_ratio`：实际失败比例。
- `consumed_percentage`：错误预算消耗百分比。
- `remaining_percentage`：剩余错误预算百分比。
- `exhausted`：是否耗尽。

如果 SLO 是 99.5%，实际是 99.2%，说明实际失败比例超过允许失败比例，错误预算耗尽。

### 4. `IncidentSignal`

这个模型表示故障信号。

例如：

```text
llm.failures >= 0.1
severity = p1
```

它的 `breached` 属性会调用第 20 节已有的 `evaluate_alert_condition()`。

这说明第 22 节不是另起炉灶，而是在复用已有监控告警判断能力。

### 5. `classify_incident()`

这个函数根据故障信号判断当前故障等级。

它会：

- 过滤出已经触发的信号。
- 从触发信号里找最高严重级别。
- 根据级别给出建议动作。

比如同时出现：

```text
P2 高延迟
P1 LLM 失败率高
```

最终应该按 P1 处理。

故障处理中不能平均主义。只要出现更严重的信号，就要按更高等级处理。

### 6. `RunbookSpec`

这个模型表示一份 Runbook。

它包含：

- `trigger_alerts`：由哪些告警触发。
- `severity`：默认故障等级。
- `goal`：处理目标。
- `owner`：负责人。
- `steps`：处理步骤。
- `related_rollout_policies`：相关灰度策略。
- `escalation_hint`：什么时候升级。

代码里要求步骤 order 唯一且递增。

这是为了避免 Runbook 变成“无顺序的建议列表”。故障处理需要顺序，因为通常要先确认影响面，再降级或回滚，最后观察恢复。

## 常见误区

### 误区 1：把监控指标等同于 SLO

监控指标只是事实，SLO 是目标。

你可以有很多指标，但只选少数真正代表用户体验的指标作为 SLO。

### 误区 2：SLO 设置得越高越专业

不是。

99.99% 听起来好，但它意味着允许失败时间非常少，对架构、运维、成本要求都更高。

学习项目和中小型业务系统不应该随便喊“四个 9”。

### 误区 3：SLA 和 SLO 混用

SLO 是内部目标，SLA 是外部承诺。

内部可以定得更严格，对外承诺要谨慎。

### 误区 4：错误预算耗尽后还继续发高风险版本

这会让系统越改越不稳。

错误预算耗尽时，优先级应该从“继续做新功能”切换到“恢复稳定性”。

### 误区 5：Runbook 只写排查，不写恢复动作

只写“查看日志、查看监控”不够。

Runbook 还要写：

- 怎么降级。
- 怎么回滚。
- 怎么判断恢复。
- 什么时候升级。

### 误区 6：AI 应用只关注接口可用性

AI 应用即使接口 200，也可能回答质量很差。

所以还要关注：

- RAG 引用质量。
- 工具调用成功率。
- 模型 fallback。
- prompt injection。
- 成本异常。

## 本节练习

### 练习 1：区分 SLI、SLO、SLA

下面三句话分别属于 SLI、SLO、SLA 哪一类？

1. “聊天接口成功请求比例。”
2. “30 天内聊天接口成功请求比例 >= 99.5%。”
3. “如果月度可用性低于合同承诺，客户可以获得服务补偿。”

参考答案：

1. SLI。它只是一个可测量指标。
2. SLO。它给 SLI 加了目标值和时间窗口。
3. SLA。它是对外承诺，并且可能涉及补偿。

### 练习 2：计算错误预算

某服务 SLO 是 30 天可用性 >= 99.5%，实际可用性是 99.8%。错误预算消耗了多少？

参考答案：

允许失败比例：

```text
1 - 99.5% = 0.5%
```

实际失败比例：

```text
1 - 99.8% = 0.2%
```

错误预算消耗：

```text
0.2% / 0.5% = 40%
```

所以错误预算消耗 40%，还剩 60%。

### 练习 3：判断故障动作

如果同时出现：

```text
P2：p95 延迟超过 5 秒
P1：LLM 失败率超过 10%
```

应该按哪个等级处理？默认动作是什么？

参考答案：

应该按 P1 处理，因为 P1 比 P2 严重。

本节代码里 P1 默认动作是 `rollback`，意思是先考虑快速止损，比如回滚候选模型、关闭灰度开关或恢复稳定配置。

### 练习 4：为什么 RAG 质量也适合进入服务目标

问题：RAG 接口返回 HTTP 200，但引用来源大量对不上，算不算服务质量问题？

参考答案：

算。

因为 AI 应用的质量不只看接口是否成功，还要看回答是否可靠。RAG 引用大量对不上，说明用户可能拿到没有依据或误导性的答案。对客服、政策、订单解释这类场景来说，这属于很重要的质量问题。

### 练习 5：设计一个简单 Runbook 步骤

为“RAG no-context spike”写一个第一步排查动作。

参考答案：

可以这样写：

```text
动作：检查检索健康状态。
具体做法：查看 empty result rate、知识库 collection 状态、metadata filter、score threshold 和最近一次 ingestion 记录。
预期信号：确认问题来自数据缺失、过滤条件错误、阈值过高，还是向量数据库不可用。
```

## 自测题

### 自测 1：SLI 和 SLO 的核心区别是什么？

答案：

SLI 是服务质量指标，表示“测什么”；SLO 是服务质量目标，表示“这个指标要达到什么水平，并且通常带有时间窗口”。

### 自测 2：为什么内部 SLO 通常应该比外部 SLA 更严格？

答案：

因为 SLA 是对外承诺，可能涉及合同、赔付和信誉。内部 SLO 更严格可以给团队留出缓冲，提前发现风险，避免直接触碰外部承诺底线。

### 自测 3：错误预算耗尽后，团队应该优先做什么？

答案：

应该优先恢复稳定性，比如暂停高风险发布、修复故障、降低错误率、回滚异常版本，而不是继续扩大灰度或上线高风险功能。

### 自测 4：Runbook 为什么要写 `expected_signal`？

答案：

因为故障处理不是盲目执行命令。每一步都应该知道自己希望看到什么信号，这样才能判断方向是否正确，以及是否需要进入下一步、回滚或升级。

### 自测 5：AI 应用的 Runbook 为什么要包含 LLM、RAG、Tool、成本和安全？

答案：

因为 AI 应用的故障来源不只在传统 HTTP 和数据库。模型失败、检索质量下降、工具调用失败、token 成本异常、prompt injection 和隐私风险都会影响真实用户体验和生产稳定性。
