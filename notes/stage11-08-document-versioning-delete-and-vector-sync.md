# M11 第 8 节：文档版本、删除与向量库同步

## 本节定位

一份文档上线后会更新、失效、归档、撤销访问或被删除。最常见且危险的 RAG 问题不是“新文件没上传”，而是新旧文件、解析文本、向量、缓存和在线检索范围没有一起变化，导致系统继续回答不该使用的知识。

本节学习知识生命周期与跨存储一致性：怎样让“业务上不该回答的资料”真正退出模型上下文。

## 本节学习目标

1. 建立版本、修订、生效、归档、软删除和物理删除的基础概念。
2. 理解原文件、数据库、向量库和缓存为什么会发生不一致。
3. 区分全量重建、增量更新与双版本切换策略。
4. 说明在线过滤为何比“等待旧向量删除”更关键。
5. 能设计防止幽灵知识、半更新和误删除的基本原则。

## 一句话先讲透

**文档更新不是覆盖一个文件，而是让原始资料、版本记录、文本块、向量索引、缓存与在线过滤在同一生命周期规则下协同变化。**

## 基础知识铺垫

### 1. 什么是版本

版本不是文件名末尾加一个日期，而是“同一逻辑资料在某一时间点的内容快照”。

```text
逻辑文档：售后服务政策。
版本 2026.06：曾经有效。
版本 2026.08：当前有效。
版本 2026.10：已审批但未来生效。
```

覆盖同一路径会丢失历史事实：某笔订单在 6 月适用哪个规则？为什么系统昨天和今天回答不同？谁发布了新版本？版本化就是为这些问题保留证据。

### 2. 三种时间语义

文档系统至少有：

```text
业务有效时间：规则现实中从何时生效到何时失效。
系统记录时间：系统何时收到、修订或解析该文件。
查询目标时间：用户问的是现在，还是历史时点。
```

它们可能不同。旧政策今天补录，记录时间是今天，业务有效时间却是去年；未来政策今天上传，也不能立刻用于当前回答。没有时间语义，版本治理会退化成“谁最后上传就听谁的”。

### 3. 派生数据与副本

同一份知识可能存在多个位置：原始 PDF、文档数据库记录、解析文本、知识块、向量索引、全文索引、缓存、引用摘要、评测样本、备份。

这些不是完全独立的数据，而是从原件派生的副本。任何更新或删除都必须考虑它们，否则会产生“文件已改，模型还记得旧句子”的现象。

### 4. 一致性与最终一致性

理想上，一个版本要么完整可用，要么完全不可见，称为原子性。现实中，文件存储、数据库、向量库和缓存通常不能放在同一个事务里，不可能保证同时物理更新。

工程上常采用最终一致性：允许后台副本稍后清理，但在线查询必须立即遵循权威状态和版本过滤。也就是说，旧向量即使暂未物理删除，也不能再被召回和送入模型。

## 本节主题系统讲解

### 1. 生命周期动作的真正含义

| 动作 | 业务含义 | 在线检索通常如何处理 |
| --- | --- | --- |
| 新版本 | 同一逻辑资料的新快照 | 验证后进入目标时间范围 |
| 失效 | 不再适用于新的业务判断 | 默认过滤，可能保留历史审计 |
| 归档 | 低频保留资料 | 默认不检索，受控访问 |
| 软删除 | 标为不可见/不可检索 | 立即从在线范围排除 |
| 物理删除 | 真正清除文件和副本 | 按保留政策执行 |
| 撤销权限 | 用户/角色不再可访问 | 立即更新查询过滤和缓存 |

“看不到”与“物理不存在”不是同一件事。隐私删除、审计保留和业务失效的处理范围各不相同。

### 2. 幽灵知识如何产生

幽灵知识是业务上已不该使用，却仍被系统回答出的内容。常见原因：

```text
删除了文件记录，没删向量块。
旧版本仍是 ready，查询没有按有效期过滤。
新版本只写入一半块就开始对外服务。
缓存仍保存旧检索结果或旧 prompt 上下文。
多个知识库副本只同步了一部分。
更新任务新增了新块，却没有禁用旧块。
```

它不是模型幻觉，而是数据生命周期错误。正确修复重点是版本、状态、过滤和发布，而不是让模型“优先相信新版”。

### 3. 三种更新策略

#### 全量重建

重新解析、分块和向量化全部资料，构建新索引。适合早期系统、重大 pipeline 升级、embedding 更换或历史数据不可信场景。优点是逻辑清楚、可消除残留；代价是成本和时间高。

#### 增量更新

只处理内容或元数据变化的文档/块。适合稳定的大知识库，成本低、速度快；但需要稳定 ID、内容指纹、差异识别和旧块退出机制。若变更判断错，最容易留下幽灵知识。

#### 双版本/蓝绿切换

旧索引继续服务，新索引在后台完整构建和验证，通过后再切换查询范围。适合高风险更新和大规模策略变化，优点是不会让用户看到半新半旧数据，且便于回滚；代价是短期需要双份资源。

### 4. 发布与清理的顺序

更可靠的顺序是：

```text
创建候选版本。
处理并验证所有派生块。
在权威文档记录中标记可发布。
让查询过滤切到新版本。
失效旧版本的在线可见性。
清理旧向量、缓存与派生副本。
保留审计与回滚所需信息。
```

最先要保证的是“旧资料不再对用户可见”，而不是“每个旧副本已经立刻物理消失”。

### 5. 删除范围必须被明确声明

用户说“删除文档”时，系统必须明确：

```text
只是从当前在线检索移除？
是否删除原文件、解析结果、知识块、向量、缓存和引用？
评测集和日志中是否有受控摘录？
备份保留多久、谁有权恢复？
是否受法律、审计或合同保留要求限制？
```

没有范围声明的“删除成功”只是模糊承诺，很容易产生安全和合规问题。

### 6. 历史查询与当前查询

“当前默认检索只使用当前有效版本”不等于历史版本永远不能使用。若用户要核对 2025 年订单当时适用的政策，系统需要按目标业务时间查询历史版本。

因此必须区分：

```text
当前问答：默认只查当前有效、可访问资料。
历史审计：在明确授权和目标时间下查历史快照。
删除/隐私撤销：即使历史查询也可能绝对不可用。
```

时间、权限和保留政策必须共同决定是否可访问。

### 7. 缓存为何是隐蔽风险

即使索引已切换，缓存可能还保存：查询结果、rerank 结果、模型回答、引用链接或完整上下文。缓存 key 必须包含知识版本、租户、权限范围和必要的业务时间；版本切换、权限撤销、删除后需按策略失效。

否则系统表面上已经更新，用户仍从缓存看到旧答案，这是最难排查的“同步看似成功”问题之一。

### 8. 用不变量验证正确性

可定义系统不变量：

```text
当前查询只命中 ready 且目标时间有效的版本。
同一逻辑文档在一个业务时间点只有一个默认有效版本。
已撤销或删除内容不进入模型上下文。
同一更新任务重跑不制造重复可见块。
新版本未验证通过前不替代旧版本。
```

不变量把模糊的“同步应该没问题”变成可测试、可审计的规则。

## 常见误区

### 误区 1：上传新文件后重新 embedding 就够了

不对。旧块、状态、有效期、缓存、引用和查询过滤也必须同步。

### 误区 2：物理删除向量后才算安全

不完全对。物理清理重要，但在线过滤必须更早阻断其进入模型；不同副本的清理可最终一致。

### 误区 3：让模型自己选择新版本

不对。版本适用性是系统和业务规则，不是语言模型应承担的决策。

### 误区 4：增量更新一定优于全量重建

不对。重大 pipeline 或 embedding 变更时，构建新版本再切换通常更可靠。

## 本节练习

### 练习 1：业务有效时间和系统记录时间有什么区别？

答案：业务有效时间决定规则现实中何时适用；系统记录时间表示系统何时收到、处理或修订文件。旧资料今天补录不会变成当前规则。

### 练习 2：什么是幽灵知识？举两个成因。

答案：它是业务上不应使用却仍被回答的知识。例如旧向量未退出查询范围；缓存仍返回旧结果；新旧版本同时处于可检索状态。

### 练习 3：双版本切换解决什么问题？

答案：旧索引继续服务，新版本在后台完整构建、验证后才切换，避免用户看到半更新数据并保留回滚能力。

## 自测题

### 自测 1：软删除与物理删除的区别？

答案：软删除使内容不可见或不可检索，数据可能仍保留；物理删除真正清除存储副本。两者都需明确在线检索是否已阻断。

### 自测 2：为什么缓存需要版本与权限维度？

答案：相同问题在不同版本、租户或角色下可见证据不同。缓存缺少这些维度会返回旧答案或越权结果。

### 自测 3：本节最重要的结论？

答案：知识生命周期是跨多个派生副本的一致性问题；在线状态和过滤是防止旧知识影响模型的第一道保证。
