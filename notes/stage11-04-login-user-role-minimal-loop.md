# 阶段 11 第 4 节：登录与用户角色最小闭环

## 本节定位

第 3 节已经创建了 Vue3 前端工作台骨架。

第 4 节开始补第一个真实项目必备边界：

```text
用户身份和角色边界。
```

任何后台系统都不能只有页面，没有身份。因为不同用户看到的菜单、能访问的数据、能执行的操作都不一样。

本节先做前端最小闭环：

- 登录页。
- 本地演示账号。
- Pinia 会话状态。
- localStorage 会话持久化。
- 路由守卫。
- 角色菜单过滤。
- 退出登录。
- 无权限页面。

Java 真实用户表和真实登录接口放到后续“Java 业务数据模型补全”一起做。

## 为什么本节先做前端最小闭环

当前 Java 服务已经有订单、工单、internal API 和 MyBatis 结构，但还没有完整的用户、角色、登录接口。

如果本节同时做：

```text
前端登录
Java 用户表
Java 角色表
Java 登录接口
token 签发
前端接真实接口
权限拦截器
```

改动会过大，容易把第 4 节拖成前后端大重构。

所以本节采用更稳的拆法：

```text
先让前端具备身份和角色边界。
后续再把模拟登录替换成 Java 真实登录。
```

这不是降低真实化要求，而是按阶段推进。

## 本节关键概念

### 1. 认证和授权的区别

认证回答：

```text
你是谁？
```

比如登录账号密码，确认当前用户是 `admin`。

授权回答：

```text
你能做什么？
```

比如 `customer` 不能访问系统配置页，`admin` 可以访问。

本节同时做了最小认证和最小授权：

- 登录页负责认证。
- 路由 meta roles 和菜单过滤负责前端授权。

### 2. 前端权限不是最终安全边界

前端隐藏菜单只是用户体验层面的权限控制。

它不能替代后端权限。

原因：

- 用户可以手动输入 URL。
- 用户可以修改浏览器 localStorage。
- 用户可以直接调用接口。

所以真实项目必须由 Java 后端继续做接口权限校验。

阶段 11 后续会补：

```text
Java 用户表
Java 角色表
登录接口
当前用户接口
接口权限控制
```

### 3. 为什么用 Pinia 保存当前用户

当前用户是很多页面都会用到的全局状态：

- 顶部用户栏。
- 菜单过滤。
- 路由守卫。
- API 请求头。
- 后续角色权限判断。

用 Pinia 管理比每个组件自己保存更清晰。

### 4. 为什么现在用 localStorage

localStorage 让刷新页面后还能恢复登录状态。

当前只是本地演示。

后续真实登录时，需要更谨慎处理：

- token 过期。
- 退出登录。
- 401 自动跳登录。
- 不在前端保存敏感密钥。
- 根据后端 `/api/me` 刷新当前用户。

## 本节练习

### 练习 1：认证和授权有什么区别？

参考答案：

认证是确认“你是谁”，比如登录账号密码。授权是确认“你能做什么”，比如某个角色能不能访问系统配置页。

### 练习 2：为什么前端隐藏菜单不等于安全？

参考答案：

因为用户可以直接输入 URL，也可以伪造请求或修改浏览器里的本地状态。真正的权限必须由后端接口校验。前端权限主要提升用户体验，不能作为最终安全边界。

### 练习 3：为什么现在不直接做 Java 真实登录？

参考答案：

当前 Java 服务还没有完整用户、角色、登录接口。本节目标是先让前端身份边界跑通，避免一次改动过大。后续补 Java 用户表和登录接口后，再替换前端模拟登录。
