# M13 第 5 节：云模型 API、本地模型与自部署模型的选型

## 本节定位

前面已经学习了模型生命周期、token、上下文、GPU/显存、量化和推理性能。现在可以回答一个真正影响项目路线的问题：模型究竟应该怎么使用？

常见选择看似有三种：

```text
1. 调用云模型 API
2. 在个人/本地环境运行模型
3. 在团队服务器或云 GPU 上自部署模型服务
```

但这不是一个简单的“云端贵、本地免费”选择。每种方式都意味着不同的质量上限、数据边界、延迟特征、硬件成本、运维责任、弹性能力、模型选择自由度和合规风险。

本节的目标是让你从工程和业务角度做判断。你不需要因为学了模型部署就立刻自建推理集群，也不应因为云 API 使用方便就忽略数据、成本和供应商依赖。正确选择应服务于真实任务，而不是追随技术潮流。

## 本节学习目标

学完后，你应当能：

1. 说明云模型 API、本地运行和自部署模型服务的基本边界。
2. 区分“本地运行用于学习/试验”与“自部署用于生产服务”的责任差异。
3. 从能力、数据治理、延迟、成本、并发、可用性、运维和许可证等维度比较方案。
4. 理解 API 成本与自部署总拥有成本（TCO）不能只按单次价格比较。
5. 判断何时应使用单一提供方、多模型路由、混合云本地或回退策略。
6. 识别“为了自部署而自部署”“把本地运行误认为生产化”等常见误区。
7. 能为一个真实 Agent/RAG 项目提出合理的模型接入方案与演进路径。

## 一句话先讲透

> 云 API、本地运行和自部署不是能力高低的阶梯，而是责任分配方式：云 API 把模型和底层推理运维交给供应商，本地运行适合学习与小规模实验，自部署换取更强控制和数据边界，却要承担硬件、性能、可靠性、安全、版本和容量的完整责任；应以任务风险、规模和总成本做选择。

## 基础知识铺垫

### 1. 三种方式首先是“责任边界”不同

很多人只从“模型在哪里运行”区分三种方式，但更重要的是谁负责什么。

| 方式 | 模型运行在哪里 | 基础推理设施主要由谁负责 | 应用团队主要负责什么 |
| --- | --- | --- | --- |
| 云模型 API | 云供应商环境 | 供应商 | 业务应用、上下文、工具、评估、调用治理 |
| 本地运行 | 个人电脑/开发机 | 个人/开发者 | 模型文件、运行环境、硬件限制、试验 |
| 自部署服务 | 自有服务器/云 GPU/内网 | 团队/组织 | 从模型产物到服务治理的完整链路 |

不论哪种方式，应用团队都不能放弃：用户/租户权限、RAG、工具控制、Agent 状态、输出校验、业务逻辑、评估和安全责任。区别在于你是否还要负责模型底层运行。

### 2. 云 API 不等于“没有工程工作”

云模型 API 省掉的是：购买/租用 GPU、下载权重、部署推理引擎、处理底层模型扩缩容等工作。它并不自动解决：

- 用户鉴权与租户隔离；
- Prompt、上下文、RAG 和工具选择；
- API Key 安全、网关、限流、重试、超时；
- 业务工具权限与写操作确认；
- 成本预算、多模型路由与回退；
- 输出结构校验、引用、评估和 Bad Case；
- 数据发送边界、隐私和合规；
- 应用可用性和用户体验。

云 API 是“购买推理能力”，不是“购买完整 AI 应用”。

### 3. 本地运行不等于自部署生产服务

在个人电脑上下载一个量化模型并能对话，通常属于本地运行/开发实验。它很有学习价值，但离生产服务仍有距离：

| 本地试验常见特点 | 生产自部署通常还需要 |
| --- | --- |
| 单用户、手工启动 | 多用户、自动启动/恢复 |
| 允许速度较慢 | 明确延迟、吞吐和 SLO |
| 本机文件/账号环境 | 最小权限、网络/文件隔离 |
| 无需高可用 | 健康检查、故障转移、灰度/回滚 |
| 手工看控制台 | 日志、指标、trace、告警 |
| 单个模型版本 | 模型注册、评估、版本治理 |
| 不考虑峰值 | 队列、限流、容量与成本控制 |

“本地能跑”是理解模型运行的第一步，不能直接推导为“可以承载企业用户”。

### 4. 自部署不等于必须买物理服务器

自部署可以运行在：

- 自己的工作站/本地 GPU；
- 公司内网 GPU 服务器；
- 云厂商提供的 GPU 虚拟机/裸金属实例；
- 容器平台或 Kubernetes 集群；
- 由第三方托管但可控制模型/网络边界的专用环境。

关键不在硬件属于谁，而在组织是否负责模型权重、推理引擎、运行环境、扩缩容、监控、安全和服务可靠性。云 GPU 上运行自己的模型服务，仍属于自部署；供应商提供的托管 API，则通常不是。

### 5. 选型是多目标优化，不是单指标比较

任何方案都在多个目标之间权衡：

```text
质量
安全与数据治理
延迟
吞吐/并发
成本
上线速度
可维护性
可用性
模型可替换性
合规与许可证
```

不同业务的权重不同：内部原型最看重上线速度；高敏感数据业务最看重边界；大规模稳定流量可能更看重长期成本与容量；面向用户的客服可能更看重 TTFT、可用性和回退。

没有脱离场景的“最佳部署方式”。

## 本节主题系统讲解

### 1. 云模型 API：购买成熟能力

云模型 API 指通过网络调用供应商提供的模型服务，通常使用 HTTPS/SDK 和 API Key/访问令牌。你已经通过 OpenAI 兼容 API 调用过 Qwen 类模型，这就是典型形态。

#### 1.1 主要优势

| 优势 | 具体含义 |
| --- | --- |
| 上手快 | 不必先理解 GPU、权重、驱动和推理引擎 |
| 能力强 | 通常可直接使用供应商维护的高能力模型 |
| 弹性由供应商承担 | 大部分底层扩缩容、硬件故障、模型加载由供应商处理 |
| 生态成熟 | 通常支持聊天、embedding、工具调用、流式、结构化等能力 |
| 前期成本低 | 无需为学习/小流量提前购买大量 GPU 资源 |
| 版本演进快 | 供应商可能持续发布新模型或优化服务 |

#### 1.2 主要限制和责任

| 限制/风险 | 应用团队需要考虑什么 |
| --- | --- |
| 数据出域 | 输入、RAG、工具结果能否发送给供应商？ |
| 供应商依赖 | 服务故障、价格变化、区域限制、接口变化怎么办？ |
| 模型控制有限 | 无法自由修改底层权重和引擎策略 |
| 配额/限流 | 高峰期能否满足并发？如何重试/回退？ |
| 成本随量增长 | token、工具、推理模式可能导致波动成本 |
| 行为变化 | 供应商升级模型/安全策略后质量是否变化？ |
| 合规 | 数据地域、保留、审计、合同和使用条款是否满足？ |

使用云 API 时，最常见错误是把 API Key 直接放在前端或代码仓库。正确做法仍是服务端托管密钥、通过网关/配置管理调用、记录成本和权限，并将用户请求与供应商调用隔开。

### 2. 本地模型运行：学习、试验与离线场景

本地运行通常指在个人电脑或开发机上加载模型，可能使用 CPU、消费级 GPU 或专用本地运行工具。

#### 2.1 它特别适合什么

- 理解模型文件、tokenizer、量化、显存和推理参数；
- 验证某个开源模型在自己任务上的基础效果；
- 离线学习、个人实验和原型；
- 测试数据不希望离开本机的低风险场景；
- 尝试小模型、embedding 模型、分类/抽取任务；
- 学习 OpenAI 兼容服务和本地 API 接入。

#### 2.2 它通常不适合直接承担什么

- 多用户、高并发、持续在线的生产服务；
- 高可用、容灾、严格 SLA；
- 需要稳定 GPU 资源、监控、告警和弹性扩容的场景；
- 使用个人浏览器、个人账号、个人文件环境的高风险 Agent；
- 未经评估就处理敏感企业数据的系统。

本地运行的价值是缩短学习反馈周期。你能亲眼观察模型下载、权重加载、内存、速度和量化差异；这会让 M13 的概念变得具体。但它不是生产架构的替代品。

### 3. 自部署模型服务：获得控制，也获得责任

自部署是将模型、推理引擎和服务运行在组织可控制的环境中，向内部或外部应用提供 API。

#### 3.1 可能带来的价值

| 价值 | 说明 |
| --- | --- |
| 数据边界 | 可以让模型请求留在指定内网/地域/云账户范围 |
| 模型选择 | 可选择允许部署的开源/自有/微调模型 |
| 深度定制 | 可控制量化、引擎、上下文、批处理、缓存和版本 |
| 长期规模成本 | 在稳定大流量下，可能比按 token API 更可控 |
| 低延迟路径 | 通过靠近业务服务部署，可能减少公网网络往返 |
| 离线能力 | 网络隔离或特殊环境中仍可运行 |
| 统一平台 | 多个内部应用共享模型网关和推理服务 |

#### 3.2 新增的工程责任

```text
模型来源、许可证、权重校验和漏洞治理
GPU/CPU、存储、网络和成本
推理引擎、驱动、容器、版本兼容
模型服务 API、认证、限流、网关和路由
监控、日志、trace、告警和 SLO
并发、KV Cache、队列、背压、OOM 和容量规划
模型灰度、回滚、评估和变更管理
数据、密钥、网络、Sandbox 与权限隔离
故障恢复、备份、容灾和运维值守
```

自部署不是把供应商成本“消失”，而是将一部分按量付费转化为硬件/云资源、工程人力、运维风险和容量冗余成本。

### 4. 云 API、本地运行、自部署对比表

| 维度 | 云模型 API | 本地运行 | 自部署模型服务 |
| --- | --- | --- | --- |
| 启动速度 | 快 | 快到中等 | 中等到慢 |
| 初期硬件投入 | 很低 | 使用现有设备 | 需要 GPU/云资源规划 |
| 模型能力上限 | 可直接用供应商高能力模型 | 受本机资源限制 | 受可部署模型和资源限制 |
| 数据控制 | 依赖供应商与合同/区域 | 较强，但仅本机范围 | 可按组织环境设计 |
| 并发与弹性 | 多由供应商承担 | 通常很弱 | 团队需自行设计 |
| 运维复杂度 | 低到中等 | 低到中等 | 高 |
| 长期成本可预测性 | 受 token/价格影响 | 个人设备成本 | 需计算资源 + 人力 + 冗余 |
| 模型/引擎可控性 | 较低 | 较高 | 高 |
| 高可用能力 | 依赖供应商 SLA | 通常没有 | 需自行实现 |
| 适合场景 | 快速产品、波动流量、强模型需求 | 学习、试验、离线小规模 | 数据边界、稳定大规模、深度定制 |

该表帮助比较，但最终仍需看具体业务。比如云 API 也可能满足严格数据治理要求，前提是供应商区域、合同、数据使用策略和组织合规均符合；自部署也可能因为运维不足而比云 API 更不可靠。

### 5. 选型维度一：模型能力与任务匹配

先问：任务真正需要什么能力？

- 中文对话、长文档理解、代码、视觉、语音、embedding、rerank？
- Structured Output 和 Tool Calling 是否稳定？
- 是否需要高复杂推理、极长上下文或多模态？
- 是否需要特定行业语言风格、固定抽取格式或私有能力？

云 API 往往更容易获得最新/高能力模型；自部署可选择的模型受许可证、硬件、引擎和团队能力限制。本地小模型可能适合分类、提取、embedding 或简单问答，却未必适合复杂 Agent 编排。

正确方法是：先用真实评估集比较候选，而不是根据“开源/闭源”或“参数量”做抽象判断。

### 6. 选型维度二：数据治理与信任边界

数据问题通常不是简单的“能不能上云”。应具体拆分：

```text
哪些输入会发送到模型？
是否含个人信息、商业机密、源代码、合同、订单、医疗/金融数据？
供应商是否会保留、训练或用于改进？
数据处理在哪个地域？
是否有加密、访问控制、审计和删除机制？
是否可在发送前脱敏、最小化、摘要化？
是否有组织政策、监管或合同限制？
```

自部署可减少数据离开组织控制域的范围，但不自动等于安全：内部权限、日志、对象存储、运维账号、Browser/Sandbox、模型记忆和 RAG 向量库仍需治理。

云 API 也不一定不可用：在满足供应商协议、地区、专有网络、数据不留存配置、脱敏和组织审批等条件下，可能是合理选择。关键是明确边界，而不是口号化地说“云端不安全”或“本地绝对安全”。

### 7. 选型维度三：延迟、网络与用户体验

云 API 的延迟通常包含公网/专网网络往返、供应商排队和模型推理；自部署可将服务部署在靠近业务系统或用户的区域，可能降低网络路径，但仍要处理自身的排队和硬件容量。

要问：

- 用户对 TTFT 和完整响应时间的要求是什么？
- 请求是交互聊天、实时语音、后台报告还是批处理？
- 用户和模型服务是否处于同一地域/网络？
- 是否需要离线或断网可用？
- 外部工具/RAG 的时间是否比模型推理更主要？

不要假设自部署必然低延迟。若自部署模型较小/较慢、GPU 资源不足或调度不佳，可能比成熟云服务更慢；若云 API 在远端且网络不稳定，也可能无法满足实时需求。

### 8. 选型维度四：成本与总拥有成本（TCO）

云 API 常见成本是 token、请求、模型档位、缓存、推理模式或其他计费项。自部署成本则更分散：

```text
GPU/云实例租用或采购
+ CPU/RAM/SSD/网络
+ 容器与平台资源
+ 存储/带宽/备份
+ 高可用冗余
+ 监控、日志、告警
+ 工程开发和运维人力
+ 模型下载、评估、升级、回滚
+ 安全、合规与事故风险
```

这就是 TCO（Total Cost of Ownership，总拥有成本）。

自部署在稳定高用量下可能降低单位 token 成本，但若 GPU 长时间闲置、峰谷差很大、团队维护能力不足或需要多副本冗余，总成本可能远高于按量 API。云 API 在早期和不确定流量下通常更具成本弹性，但大规模持续调用需要严密预算与路由策略。

### 9. 一个概念性的成本比较方法

不需要在学习阶段算精确财务模型，但可按以下步骤比较：

1. 收集真实或假设工作负载：每日请求数、平均输入/输出 token、峰值并发、长任务比例。
2. 计算云 API 的预估按量费用，并考虑不同模型/缓存/区域。
3. 估算自部署要满足 P95 延迟和峰值时需要的 GPU 副本、存储、网络和冗余。
4. 将资源按小时/月计价，加上平台与人力维护成本。
5. 考虑利用率：GPU 是否全天高效使用，还是只有少量高峰？
6. 考虑质量差异：自部署较小模型若需要更多重试、人工介入或用户流失，不能只比较硬件账单。
7. 考虑供应商故障/价格变化与自建故障/运维风险的成本。

成本比较必须和服务目标一起做。仅比较“单次 API 价格”和“一张 GPU 价格”没有意义。

### 10. 选型维度五：并发、弹性与容量

云 API 的显著优势之一是供应商通常已处理大规模模型容量（但仍有速率/配额限制）。自部署需要自己面对：

- 一张 GPU 可承载多少模型、上下文和并发？
- 高峰期如何排队、限流、扩容？
- GPU 故障时如何转移？
- 多副本之间如何做模型版本和流量路由？
- 长报告是否会挤压在线聊天？
- 用户/租户如何公平共享资源？

如果业务流量波动很大，云 API 的按需弹性可能更合适；如果流量稳定且规模足够，自部署的固定容量可能更经济。混合方案也常用于平衡峰谷：自部署承载基础流量，云 API 承载溢出、复杂任务或紧急回退。

### 11. 选型维度六：可用性与故障责任

使用云 API 时，模型服务的底层可用性主要依赖供应商，但你的应用仍要处理：超时、限流、错误重试、熔断、降级和多提供方回退。

自部署时，团队还要处理：

```text
GPU/主机故障
驱动/引擎启动失败
模型文件损坏或下载失败
显存 OOM、内存泄漏、队列积压
容器重启、网络/存储故障
版本升级导致兼容/质量回归
监控告警和故障响应
```

自部署不应只有一台“唯一 GPU 机器”。若业务需要高可用，至少要考虑副本、健康检查、流量切换、模型/数据备份、回退策略和演练。M14 会进一步学习这些平台能力。

### 12. 选型维度七：模型版本与供应商锁定

云 API 可能使用专有模型或供应商特有能力，迁移到其他服务时会面临：

- API 字段/错误语义不同；
- 模型对 Prompt、工具 schema、结构化输出行为不同；
- token 计数、上下文、限流和价格不同；
- 安全/内容策略不同；
- embedding 空间不同，可能需要重建向量库；
- 评估结果和用户体验变化。

这并不意味着必须避免云 API，而是要设计合理抽象：

- 在应用内使用模型客户端适配层；
- 以业务能力而不是供应商特定字段定义接口；
- 保留 Prompt、工具、评估和模型路由版本；
- 使用真实评估集验证替换；
- 对关键场景准备回退方案。

OpenAI 兼容协议可降低接入成本，但不能消除行为差异。你之前使用兼容 API 的经验正好是这一点的基础。

### 13. 单模型、多模型与模型路由

选型不一定是“永远只用一个模型”。常见模式：

| 模式 | 描述 | 适合情况 |
| --- | --- | --- |
| 单一云模型 | 所有任务调用同一服务 | 初期简单、任务类型少 |
| 云端多模型 | 按成本/能力/任务路由 | 分类、聊天、复杂推理差异明显 |
| 自部署单模型 | 内部统一部署一个可控模型 | 数据边界或稳定任务 |
| 混合模型 | 自部署 + 云 API | 控制基础流量，保留高能力/回退 |
| 多提供方回退 | 主供应商失败时切换 | 高可用、风险分散 |

模型路由必须受评估、预算和策略控制。不能只凭模型自我选择或根据用户文字随意切换；不同模型的安全、上下文、工具能力和成本不同，路由决定也应可观测、可回滚。

### 14. 混合架构为什么常见

混合架构不代表设计不坚定，反而常是务实选择。例子：

```text
本地/自部署 embedding：数据不出内网，成本稳定
自部署小模型：分类、改写、低风险摘要
云端强模型：复杂推理、关键生成、能力兜底
另一云模型：主服务故障时的回退
```

也可以按数据分级：允许出域的公开/低敏任务走云 API；必须留在内网的高敏文档使用自部署模型；任何高风险写操作仍由业务规则和人工审批控制。

混合架构的代价是路由、评估、监控、数据边界和版本管理更复杂。因此应从真实需求开始，而不是为了“多模型”而多模型。

### 15. 许可证与模型来源

自部署开源/开放权重模型时，除了技术问题，还要检查：

- 是否允许商用；
- 是否允许修改、微调、再分发；
- 是否有用户规模、行业或地区限制；
- 是否要求保留声明或署名；
- 权重来源是否可信、是否有校验和/签名；
- 模型卡是否说明训练数据、已知风险和适用范围；
- 依赖组件/容器镜像是否有许可证与安全问题。

“可以下载”不等于“可以随意用于公司生产业务”。许可证、合规和供应链治理是自部署生命周期的一部分。

### 16. 开源、开放权重、开源代码不是同一个概念

在模型生态中常被混用：

- **开源代码**：训练/推理代码公开，不代表权重公开；
- **开放权重（open weights）**：可获得模型权重，不代表训练数据/完整训练过程公开；
- **开源模型**：不同社区/许可证下含义可能不同，需看具体条款；
- **托管 API**：只提供调用，不提供权重。

工程决策不应只看宣传标签。真正要看能否合法部署、能否审核、能否满足数据/安全要求、能否与目标引擎硬件匹配。

### 17. 一个场景判断：初创/个人项目

特点：需求快速变化、用户量不确定、团队缺少 GPU 运维、希望快速验证产品。

通常合理起点：

```text
云 API + 应用侧模型适配层 + 成本预算 + 评估集
```

原因：前期最稀缺的通常是产品验证速度和模型能力，而不是单位 token 的极致成本。应同时预留未来迁移空间：不把供应商 SDK 调用散落全项目，记录模型/Prompt/评估版本，避免敏感数据直接发送。

这不是说永远不自部署，而是先让复杂度与业务规模匹配。

### 18. 一个场景判断：个人学习和离线实验

特点：希望理解权重、量化、GPU/CPU、推理引擎；并发和 SLA 不重要；预算有限。

通常合理起点：

```text
本地小模型或量化模型 + 云 API 对照
```

这样可以亲自看到模型文件、资源占用、速度、不同量化版本和 OpenAI 兼容接口的差异；云 API 可作为能力对照和无 GPU 时的继续学习路径。

不要把个人电脑当作需要 24 小时在线、处理真实敏感企业数据的生产集群。

### 19. 一个场景判断：数据敏感的企业知识库

特点：文档、合同、源代码或内部数据不宜出组织控制域；任务可能稳定、高频；有一定平台/运维能力。

可能路线：

```text
自部署 embedding / rerank / 部分生成模型
+ 内网 RAG 与严格权限
+ 对极复杂、允许出域的任务按策略使用云模型（可选）
```

但要注意：自部署只是数据边界的一部分。文档解析、向量库、日志、对象存储、监控、备份、管理账号和人工工作台也必须在同样的治理范围内。

### 20. 一个场景判断：稳定大规模在线服务

特点：请求量稳定、模型任务相对标准化、对单位成本和延迟敏感、能投入平台建设。

可能路线：

```text
自部署/托管专用推理服务
+ 模型网关
+ 多副本/队列/限流/容量规划
+ 灰度、评估、监控和回滚
+ 云 API 作为峰值或复杂任务回退（可选）
```

是否真的比云 API 更划算，需要以 TCO 和质量为准。若流量不稳定、模型更新频繁、团队无法维护 GPU 平台，直接自部署可能反而降低整体质量和可用性。

### 21. 决策树：从问题到方案

可以用下面顺序做初步判断：

```text
是否需要快速验证，且数据可按规则发送给供应商？
  是 -> 云 API 通常是合理起点

是否主要为了学习、离线实验或小模型验证？
  是 -> 本地运行很合适

是否存在明确数据不出域/内网/地域要求，且组织有维护能力？
  是 -> 评估自部署或专用托管环境

是否有稳定大规模流量，长期 API 成本明显，且可承担平台责任？
  是 -> 用真实 TCO 与质量评估自部署

是否需要最高能力/新模型、弹性流量或快速迭代？
  是 -> 云 API 或混合架构常更合理

是否需要同时满足数据边界和复杂能力？
  是 -> 按数据/任务分级的混合路由
```

这只是起点。最终仍要做 PoC、评估、压测、安全审查和成本测算。

### 22. PoC（概念验证）应验证什么

当团队犹豫是否自部署时，可先做小范围 PoC，而不是一次投入完整平台。PoC 应回答：

- 目标模型在真实任务上质量是否达到门槛？
- 目标硬件/量化/引擎下，TTFT、输出速度、并发和 OOM 表现如何？
- 能否提供所需 API、流式、结构化输出、embedding/工具协议？
- 数据、网络、权限、日志和密钥边界能否满足？
- 升级、回滚和监控需要多少工程工作？
- 预计 TCO 与云 API 相比如何？
- 出现故障时是否有回退方案？

PoC 不应该只演示“模型在终端回答了一句话”。那只能证明模型文件可以加载，不能证明服务可用。

### 23. 模型接入抽象层的价值

无论现在选择云 API 还是本地服务，应用中都应尽量把模型调用封装为能力接口，例如概念上的：

```text
generate_chat_response(...)
create_embedding(...)
rerank_documents(...)
stream_response(...)
```

而不是让所有业务模块直接依赖某个供应商 SDK、模型名称和响应字段。

这样未来可以：

- 由云 API 切换到 OpenAI 兼容自部署服务；
- 为不同任务路由不同模型；
- 添加成本、trace、重试和回退；
- 用 fake client 做测试；
- 对模型版本灰度和回滚。

抽象层不是为了隐藏一切差异。不同模型的能力、上下文、工具协议和限制仍需暴露为可配置能力，不能假装所有模型完全相同。

### 24. 供应商回退与多提供方策略

对关键系统，可能需要定义：

```text
主模型服务不可用/限流/超时
-> 是否重试？
-> 是否降级到较小模型？
-> 是否切换到第二提供方？
-> 是否只提供 RAG 检索/人工路径？
-> 是否拒绝高风险写操作？
```

回退不应盲目。不同模型可能：

- 输出结构不同；
- 工具调用/Structured Output 行为不一致；
- 数据地域和安全策略不同；
- 质量不足以处理高风险任务；
- 有不同成本与上下文限制。

因此回退策略要按任务分级，并通过提前评估验证。关键业务不应在故障时第一次临时尝试另一个模型。

### 25. 选型后的持续复审

模型接入方式不是一次决定永久不变。应定期复审：

- 流量、token、成本和峰值是否变化？
- 模型质量、RAG、工具成功率和人工介入是否变化？
- 数据/合规要求是否变化？
- 供应商模型、价格、区域或限额是否变化？
- 自部署硬件利用率和运维负担是否符合预期？
- 是否出现更合适的模型、量化、引擎或托管模式？

这也是为什么模型、Prompt、数据、网关路由和评估都要版本化和可观测。没有数据就无法知道原先的选型是否仍然合理。

## 常见误区

### 误区 1：云 API 一定更贵，自部署一定更便宜

不对。云 API 省去了 GPU 闲置、冗余、运维、升级和故障成本，早期/低波动流量可能更经济；自部署在稳定大规模下可能更划算，但需计算完整 TCO、质量差异和人力成本。

### 误区 2：本地模型不联网，所以天然适合生产敏感数据

本地运行确实可能减少出域，但个人电脑、日志、文件、账号、权限、备份和物理安全未必满足企业要求。数据安全是完整系统问题，不是模型位置问题。

### 误区 3：自部署后就不再受供应商或生态影响

仍会依赖硬件、云 GPU、驱动、推理引擎、模型许可证、容器镜像、存储和网络等生态。自部署减少某类依赖，不等于没有依赖。

### 误区 4：云 API 使用方便，所以应用不需要模型网关和评估

云 API 仍会限流、故障、价格变化和模型行为升级。网关、预算、版本、评估、回退和审计依然是生产应用需要的能力。

### 误区 5：只要模型能自部署，就应立即迁移

是否迁移取决于任务质量、数据、流量、成本、团队能力和风险。若自部署模型质量不达标、GPU 长期闲置或团队无法维护，迁移可能降低整体业务价值。

### 误区 6：OpenAI 兼容接口保证任意模型可以无缝替换

兼容接口主要降低请求格式迁移成本。模型能力、上下文、工具调用、结构化输出、限流、错误语义、价格和安全行为仍可能不同，必须评估和灰度。

### 误区 7：混合架构一定比单一方案先进

混合路由可平衡能力、成本和数据边界，但会增加评估、监控、数据治理和故障路径复杂度。没有明确需求时，简单受控的单一方案更易维护。

## 本节练习

### 练习 1：选择起点

一个两人团队想快速验证 AI 客服产品，用户量未知，暂时没有 GPU 运维经验，且输入可以在合规条件下发送给云供应商。合理的第一选择是什么？还应提前做哪些设计？

答案：通常可先选择云模型 API，以较低基础设施成本快速验证产品和模型质量。同时应将模型调用封装在服务端适配层，管理密钥、用户/租户权限、token/成本预算、超时/重试、Prompt/模型版本、评估集和 Bad Case；不要把 SDK 调用和 API Key 散落在前端或业务模块中。这样后续可根据真实流量和数据要求再评估自部署。

### 练习 2：区分本地与生产

个人电脑上一个 4-bit 模型可在命令行回答问题。为什么这不足以证明它可替代云模型成为企业生产服务？

答案：它只证明该模型在该机器、该配置、单用户场景下可运行。生产还需要评估真实任务质量、并发、TTFT/吞吐、KV Cache/OOM、认证授权、数据隔离、日志监控、故障恢复、模型版本、容器/网络、扩缩容、回滚和运维责任。命令行可用不等于服务可用。

### 练习 3：分析混合方案

某企业要求合同文档不得离开内网，但允许低敏公开问题调用云端高能力模型。请给出一种合理的混合路由思路，并指出一个必须防范的风险。

答案：可将合同解析、embedding、RAG 检索和涉及合同原文的生成限制在内网自部署模型/服务；公开低敏问题按数据分类路由到云 API；网关记录路由、版本和成本。必须防范分类/脱敏错误导致合同原文、RAG chunk、工具结果或记忆被误发到云端，因此数据标签、最小上下文、出域策略和审计必须在服务端强制。

### 练习 4：解释 TCO

为什么不能仅因“某云 API 单价高于一小时 GPU 租金”就判定自部署更便宜？

答案：GPU 租金只是自部署成本的一部分，还要考虑峰值所需冗余、GPU 利用率、CPU/RAM/存储/网络、平台、监控、安全、工程和运维人力、故障风险、模型升级、许可证与质量差异。云 API 则按量弹性且承担部分基础设施责任。应基于真实工作负载和服务目标比较总拥有成本。

## 自测题

### 自测 1：云 API、本地运行和自部署的核心差别是什么？

答案：核心差别是模型底层运行责任由谁承担。云 API 由供应商负责权重、GPU 和推理基础设施，应用负责使用与治理；本地运行主要用于个人学习/试验；自部署由组织负责从模型产物、硬件、引擎、服务到监控、安全、容量和回滚的完整链路。

### 自测 2：自部署最适合哪些信号明确的场景？

答案：例如明确的数据不出域/内网/地域要求、稳定且足够大的流量、对模型/引擎/部署有深度定制需求、可承担 GPU 平台和运维责任、并且目标模型在真实任务质量与成本上经过验证。单一信号通常不足以自动决定自部署。

### 自测 3：为什么模型选型必须包含数据治理？

答案：模型调用可能发送用户输入、RAG 文档、工具结果、历史和记忆。不同部署方式决定数据经过哪些网络、服务和地域，影响保留、访问、审计、合规和泄露风险。数据边界必须与模型能力、成本同等参与决策。

### 自测 4：混合模型架构的价值与代价是什么？

答案：价值是可按任务/数据/成本/能力分级使用自部署和云模型，并提供峰值或故障回退；代价是路由、评估、版本、数据边界、监控、错误处理和运营更复杂。只有明确需求时才值得引入。

### 自测 5：选型后为什么还要持续复审？

答案：流量、成本、模型质量、供应商能力/价格、数据政策、团队运维能力和硬件利用率都会变化。原先合理的方案可能不再适合，因此需要通过版本、指标、评估和成本数据持续检查并逐步调整。

## 本节小结

本节建立了模型接入方式的工程判断：云 API 适合快速使用成熟能力并将底层推理责任交给供应商；本地运行适合学习和小规模实验；自部署提供数据边界与深度控制，但需要承担完整平台责任。选型应综合模型能力、数据治理、延迟、并发、TCO、可用性、许可证和团队能力，并允许通过适配层、评估、混合路由和持续复审逐步演进。
