# M13 第 10 节：Docker 化模型服务与运行环境

## 本节定位

你此前已经接触过 Docker、Docker 容器和数据库/向量数据库的容器化运行。本节不重复把 Docker 当成一串命令，而是把它放进模型推理场景重新理解。

模型服务与普通 Web 服务相比，通常多出大体积权重、Tokenizer、GPU/驱动兼容、长时间冷启动、显存资源、下载缓存和高成本运行等问题。因此“写一个 Dockerfile 然后 `docker run`”只是开始。你需要理解：**什么应该打进镜像，什么应该挂载为数据卷，什么应通过环境变量注入，什么应该交给宿主机或编排平台，以及为什么这些边界会影响安全、发布和故障恢复。**

本节是纯知识笔记，不会要求你构建镜像或改动现有项目。

## 本节学习目标

学完后，你应当能够：

1. 区分 Docker 镜像、容器、镜像层、数据卷、网络、环境变量和运行时参数。
2. 解释容器化对模型服务真正解决什么，以及不能解决什么。
3. 说明模型代码、模型权重、Tokenizer、配置、密钥、日志和缓存分别适合放在哪里。
4. 理解宿主机 GPU 驱动、容器 CUDA 运行时、推理引擎和模型格式之间的兼容边界。
5. 解释为什么把模型权重直接塞进镜像通常不是默认最佳做法。
6. 了解端口、内部网络、卷挂载、只读文件系统和非 root 用户的安全意义。
7. 说明启动顺序、健康检查、预热、优雅停止和重启策略对模型容器的重要性。
8. 能够审查一个模型容器方案中常见的可重复性、安全性和运维风险。

## 一句话先讲透

**Docker 把应用运行依赖封装成可重复交付物，但模型服务的权重、GPU、数据、密钥和容量仍属于外部运行环境；容器化解决一致性，不替代资源规划、安全治理和生产运维。**

## 基础知识铺垫

### 1. 什么是镜像，什么是容器

可以先用一个近似但有用的类比：

- **镜像（image）**像只读的软件交付模板：包含基础系统层、依赖、应用文件、默认命令等。
- **容器（container）**像由镜像启动出的一个运行实例：有自己的进程、网络命名空间、可写层和运行参数。

```text
同一个镜像
   |----> 容器 A：端口 8000，开发配置
   |----> 容器 B：端口 8001，测试配置
   |----> 容器 C：生产环境配置，绑定 GPU 0
```

镜像本身不等于正在运行的服务；容器也不等于虚拟机。容器通常共享宿主机内核，但通过命名空间、文件系统层、网络和资源限制形成隔离。隔离强度、GPU 暴露、文件挂载和权限仍需正确配置。

### 2. 为什么要容器化

没有容器时，一个模型服务的运行往往依赖：

- 操作系统版本；
- Python/Java/Node.js 等运行时；
- 依赖库和系统动态库；
- 推理引擎版本；
- CUDA/加速库；
- 启动命令和环境变量；
- 证书、模型目录、端口和网络配置。

手工在每台机器上安装，容易出现“我电脑能运行，服务器不行”。容器化通过声明镜像构建过程，让大部分用户态依赖可重复地交付：

```text
源码 + 依赖声明 + Dockerfile
              |
              v
          构建镜像
              |
              v
  在不同环境中用相同镜像启动容器
```

这带来的核心价值是环境一致性、交付可追溯、部署自动化基础和更容易的回滚。它不是“性能加速器”，也不是“自动解决生产问题的按钮”。

### 3. 镜像层与构建缓存

Dockerfile 的每一步通常会形成镜像层或参与层缓存。一个概念性的例子：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install ...
COPY app/ ./app/
CMD ["python", "-m", "app"]
```

如果依赖文件未变而只改了业务代码，构建器可能复用“安装依赖”对应的缓存层，从而减少构建时间。反过来，如果你先复制所有源码再安装依赖，任意代码改动都可能让依赖安装层失效。

模型场景还要额外考虑：权重文件通常非常大，任何层变化都可能导致大规模重新传输和存储膨胀。层缓存不是把大模型塞进镜像的理由，反而应促使你谨慎区分应用镜像和模型资产。

### 4. 容器可写层不是可靠数据盘

容器启动后可以写文件，但这些数据通常位于容器的可写层。删除并重建容器后，它们可能消失；迁移到另一台机器也不会自动带走。

因此需要区分：

- **临时运行文件**：可放容器临时目录，例如短暂中间文件；
- **需要持久化的数据**：应放 Docker volume、宿主机目录、对象存储或数据库；
- **可重新下载的缓存**：可放专用缓存卷，方便重建但不作为唯一真相来源；
- **不可丢失业务数据**：必须用可靠存储、备份和恢复策略，不应仅依赖容器层。

模型下载缓存、Hugging Face 缓存、量化后的权重、Tokenizer 和用户文档有不同的生命周期，不能都随手放在 `/app` 下。

### 5. 宿主机、容器和 GPU 的边界

一个常见误解是：“容器里装了 CUDA，所以容器就有 GPU。”实际至少涉及三层：

```text
宿主机：物理 GPU + NVIDIA 驱动（或其他硬件驱动）
      |
容器运行时：将允许的 GPU 设备和相关运行库暴露给容器
      |
容器用户态：CUDA/加速库 + 推理引擎 + 模型代码
```

容器通常不能独立携带或替代宿主机的内核级 GPU 驱动。宿主机驱动、容器中使用的 CUDA 运行时、推理引擎编译需求和框架版本需要在兼容范围内。

因此“本地镜像构建成功”并不保证生产 GPU 节点上能运行；“容器能看到 GPU”也不保证目标模型、量化格式和 Attention 后端可用。需要以实际硬件和完整推理请求验证。

### 6. 配置、密钥与镜像的边界

镜像应尽量是可在不同环境复用的不可变交付物。环境差异应通过运行时配置提供：

- 模型逻辑名或路径；
- 服务端口、日志级别；
- 上游 API 地址；
- 并发、Token、显存预算等运行参数；
- 开关和环境标识。

而 API Key、数据库密码、内部令牌、私有证书等敏感信息不应写入 Dockerfile、镜像层、源码仓库或普通日志。因为镜像可能被推送、缓存、导出、扫描或被更多人拉取。

运行时可通过受控环境变量、密钥文件挂载、专门密钥管理系统或平台 Secret 注入。选择哪种方式取决于成熟度，但“密钥不进入镜像”是基本原则。

## 本节主题系统讲解

### 1. 模型服务容器化到底要封装什么

一个模型服务通常由以下类别组成：

| 类别 | 典型内容 | 通常的放置建议 |
| --- | --- | --- |
| 应用与推理服务代码 | API、调度配置、适配层 | 镜像 |
| 语言和依赖 | Python、Java、推理库、系统库 | 镜像 |
| 默认非敏感配置 | 默认端口、健康检查路径 | 镜像或受版本管理的配置 |
| 模型权重与 Tokenizer | 大型只读资产 | 外部模型仓库、对象存储、共享卷或节点缓存 |
| 可重建缓存 | 下载缓存、编译缓存 | 专用缓存卷 |
| 业务数据 | 用户、任务、文档、向量 | 数据库、对象存储、向量库 |
| 密钥和证书 | API Key、数据库密码、TLS 私钥 | Secret 系统或受控运行时挂载 |
| 日志与指标 | 标准输出、Trace、指标端点 | 输出到收集系统或受控日志卷 |

表格不是绝对规则。例如离线演示镜像可以内置一个小模型，便于完全离线分发；高安全离线环境也可能把审核过的权重与镜像一同交付。关键是明确代价：镜像会变大、构建/分发变慢、升级粒度变粗、权重版本与应用版本被强绑定。

### 2. 为什么模型权重通常不直接打进应用镜像

把权重复制进镜像确实看起来简单：启动容器后不必下载，版本也“固定”。但默认情况下，它会造成以下问题：

#### 2.1 镜像体积与分发成本

模型权重可能从几 GB 到几十甚至上百 GB。每次推送、拉取、保存、扫描和复制镜像都变慢，占用镜像仓库和节点磁盘。

#### 2.2 应用版本与模型版本耦合

只想修复一个 API Bug，却要重新构建和分发整个模型镜像；只想替换量化权重，却要重新发布应用镜像。二者的发布节奏往往不同。

#### 2.3 安全与许可证治理更困难

权重可能有访问限制、许可证条款或内部来源。将其复制到通用镜像仓库，会扩大分发范围和审计难度。

#### 2.4 缓存和多副本重复

多个服务版本或多个节点可能存有大量重复权重层，清理和容量规划更复杂。

更常见的选择是让镜像包含“加载权重的能力”，让权重从受控位置获得：对象存储、内部模型仓库、节点缓存、只读共享卷或预加载的本地目录。这样模型和服务可独立版本化，但也引入冷启动、网络、权限、完整性校验和缓存管理问题。

### 3. 模型文件的三种常见供应方式

#### 3.1 启动时下载

```text
容器启动 -> 校验本地缓存 -> 缺失时从模型仓库/对象存储下载 -> 加载到内存/GPU -> 就绪
```

优点：镜像小、模型版本可按配置切换、节点无需人工预置。缺点：首次启动慢，网络和上游存储会成为依赖，多个副本同时启动可能造成下载风暴。

适合：开发、较小模型、可接受冷启动、已有可靠内部模型仓库或缓存机制的环境。

#### 3.2 节点预置或持久卷挂载

```text
节点/Volume 已有审核好的权重
-> 容器以只读方式挂载
-> 服务加载并预热
```

优点：启动更快、减少重复下载、权重可独立管理。缺点：节点调度受数据位置约束，卷权限和一致性需要管理，跨节点分发仍是问题。

适合：稳定 GPU 节点、较大模型、需要较快恢复的服务。

#### 3.3 镜像内置

优点：单一产物、离线环境方便、运行时外部依赖少。缺点是前面提到的体积、耦合和分发问题。

适合：小模型演示、强离线分发、权重很小且发布频率低的特殊场景。它应是经过权衡的选择，而非默认做法。

无论哪种方式，都应记录模型 ID、来源、哈希/校验、Tokenizer、量化格式、许可证、加载参数和发布日期。模型文件是软件供应链的一部分，不应只靠目录名辨认。

### 4. Dockerfile 的模型服务设计原则

以下是原则，不是要求你照抄的通用模板。

#### 4.1 使用明确、可信且尽量小的基础镜像

基础镜像决定系统库、漏洞面和兼容性。模型服务有时必须使用带 CUDA 运行时的基础镜像，体积会大于通用 `slim` 镜像；这不是错误，但要明确为什么需要它。

应避免使用来源不明、长期不更新或不固定版本的基础镜像。`latest` 便于试验，却不利于可重复构建和故障复现。

#### 4.2 固定关键依赖版本

推理引擎、深度学习框架、CUDA 相关库、Tokenizer 和模型加载库之间有兼容关系。锁定版本可以让“昨天能跑、今天重建失败”的概率降低。

锁定不意味着永远不升级。正确流程是：记录当前可用组合，在测试环境验证升级，再有计划发布和回滚。

#### 4.3 用多阶段构建减少最终镜像负担

如果构建阶段需要编译器、头文件、测试工具或下载工具，而运行阶段不需要，可以把它们留在 builder stage，最终镜像只带运行产物。这能减少体积和攻击面。

对于需要编译特定 GPU 扩展的场景，多阶段构建更有价值，但也会让构建链路更复杂。不要为了追求极小镜像牺牲可调试性和可靠性。

#### 4.4 利用构建缓存，但不要把缓存当成正确性保证

应先复制依赖描述文件、安装依赖，再复制经常变动的应用代码，以提高开发构建效率。模型下载缓存、包管理缓存可以在受控场景下利用。

但构建缓存可能让旧依赖或旧模型意外留存。发布构建应有明确的版本、校验和必要的无缓存验证策略。

#### 4.5 明确默认命令与可配置参数

镜像应有合理的默认启动命令，但端口、模型路径、并发、日志级别、显存利用上限等通常应可在运行时覆盖。这样同一镜像可以服务开发、测试和生产，而不会把环境差异写死在镜像里。

### 5. GPU 容器运行时：谁负责什么

可以用下面的责任划分理解 GPU 容器：

```text
硬件厂商/宿主机管理员
  负责：物理 GPU、内核驱动、主机稳定性

容器运行时/平台
  负责：将允许的 GPU 设备、驱动相关库、资源约束暴露给容器

镜像维护者
  负责：用户态运行库、框架、推理引擎、应用代码的兼容组合

模型服务配置
  负责：使用哪些 GPU、并行方式、显存预算、模型和量化格式
```

常见排障顺序也应按层进行：

1. 宿主机是否识别 GPU 和驱动？
2. 容器是否被允许看到正确的 GPU 设备？
3. 容器内框架能否识别设备和运行时？
4. 推理引擎是否支持该 GPU、模型与精度组合？
5. 是否因显存、并行参数、权限或模型文件导致加载失败？

不要在第一步失败时就盲目更换模型或改 Prompt。层次化排障能显著减少无效操作。

### 6. 资源限制：CPU、内存、GPU 和磁盘都要明确

模型容器最显眼的是 GPU，但其他资源同样会成为瓶颈：

- **CPU**：Tokenization、请求解析、网络、部分后处理、文件下载和数据预处理；
- **系统内存**：加载前权重、下载缓冲、CPU offload、队列、日志和缓存；
- **GPU 显存**：模型权重、KV Cache、工作区、CUDA 图等；
- **磁盘**：权重、容器层、下载缓存、日志、临时文件；
- **网络**：权重下载、模型 API、流式连接、跨节点通信。

容器资源限制的意义不只是“防止用太多”，还在于避免单个服务把宿主机拖垮、让调度器能做容量判断、让故障更容易复现。限制设置过低会导致 OOM 或性能抖动；完全不设又可能造成邻居服务互相影响。

GPU 的资源隔离比普通 CPU 更复杂。要明确某容器能看到哪些 GPU、是否允许多进程共享、显存争抢时谁负责限额。不要在同一张卡上随意启动多个高负载服务，再通过“看起来能启动”判断系统稳定。

### 7. 网络：端口暴露与内部通信

容器网络常见的三个层次：

```text
容器内部端口：进程监听的端口，例如 8000
容器网络：同一受控网络中的服务互相访问
宿主机发布端口：将容器端口映射到宿主机/外部
```

例如模型服务内部监听 8000，不意味着应将宿主机 `0.0.0.0:8000` 暴露给所有网络。更安全的思路通常是：

```text
模型服务：只加入内部网络，不直接发布公网端口
AI 应用服务：通过内部服务名调用模型服务
反向代理/网关：唯一对外暴露的入口，负责 TLS 与访问控制
```

这样可以减少攻击面和误调用。开发环境为了方便把端口映射到本机没有问题，但要明确那是开发便利，而非生产默认安全方案。

### 8. 数据卷与挂载：便利和风险同时存在

卷（volume）或 bind mount 可让容器访问外部文件。常见用途：

- 挂载只读模型权重；
- 挂载下载缓存；
- 挂载开发时的源码；
- 挂载证书或密钥文件；
- 挂载持久化日志或数据目录。

但挂载会削弱容器文件系统隔离。例如：

- 把宿主机根目录挂进容器，几乎等于扩大了容器权限；
- 以可写方式挂载模型目录，服务 Bug 或被入侵后可能篡改权重；
- 挂载包含密钥的目录，日志或调试接口可能意外读取；
- 开发时挂载源码便于热更新，生产时会破坏镜像不可变性。

因此要遵守最小挂载原则：只挂真正需要的目录，默认只读，明确所有者和权限，区分开发/测试/生产用途。

### 9. 环境变量：适合配置，不适合一切

环境变量适合注入小型、非文件型、运行时变化的配置，例如：

```text
MODEL_ID=customer-support-v2
PORT=8000
LOG_LEVEL=INFO
MAX_CONCURRENT_REQUESTS=32
```

它们也常被用于传入密钥，但这有可见性和泄露风险：某些进程检查、诊断输出、崩溃报告或管理接口可能暴露环境。更高安全要求下可使用 Secret 文件挂载或专门密钥系统。

环境变量不适合：

- 大型 JSON 配置或长 Prompt；
- 模型权重本体；
- 大型证书内容；
- 需要层级、注释、版本校验的复杂配置。

无论用哪种方式，服务启动时应校验必填配置并避免把敏感值原样打印出来。

### 10. Compose：多容器本地编排的价值与边界

Docker Compose 可以用一份声明管理多个本地容器及其网络、卷、端口和环境变量：

```text
ai-app
  -> model-service
  -> redis
  -> vector-db
  -> database
```

它在本地开发、演示、集成测试和单机环境很有价值，因为可以把依赖关系、端口、卷和启动命令显式写下来，而不是靠手工记忆。

但 Compose 不是完整的生产编排平台。它通常不自动处理跨机器调度、弹性副本、复杂服务发现、滚动升级、多区域高可用、企业级密钥管理和集群资源治理。不要贬低它，也不要把它当成所有规模的终点。

### 11. 启动顺序：容器启动不等于依赖已可用

假设 AI 应用依赖数据库、向量库和模型服务。即使按顺序启动容器，也可能出现：

```text
数据库进程已启动，但迁移未完成
向量库端口已监听，但索引尚未恢复
模型服务端口已监听，但权重还在加载
```

因此依赖关系应基于**就绪状态**而非“容器是否已经被创建”。应用也应具备连接失败后的有限重试、超时和清晰错误，而不是假定所有依赖会在同一时刻准备好。

对于模型服务，冷启动尤其明显。权重加载和预热可能远长于普通 HTTP 服务启动。部署设计必须给它充分时间，并避免大量依赖服务同时盲目重试造成启动风暴。

### 12. 健康检查和优雅停止在容器中的实现意义

容器平台常需要从外部检查服务状态。模型服务应至少区分：

- **liveness**：进程是否还活着，是否需要重启；
- **readiness**：模型是否加载完成、是否可安全接新流量；
- **startup**：允许较长的初始加载时间，避免尚未加载完就被误判反复重启。

优雅停止时，应先使 readiness 失败，让流量入口停止分配新请求；再等待现有流、短任务或队列中的必要工作完成；最后在宽限期结束前退出。若容器一收到停止信号就立即杀进程，用户会看到大量流式输出被截断。

### 13. 日志、指标和标准输出

容器内应用通常把结构化日志输出到标准输出/标准错误，再由宿主机或平台收集。这样容器可以保持短生命周期，不依赖内部日志文件永久存在。

模型服务日志至少要避免两个极端：

- 什么都不记，出了慢、OOM、429 无法定位；
- 把完整用户 Prompt、检索文档、API Key、令牌和隐私数据全部打印，造成泄露。

可以记录请求 ID、模型版本、输入输出 Token 数、队列时间、TTFT、总时延、状态码、错误类型、缓存命中、GPU 资源摘要等；敏感内容按脱敏和访问策略处理。

指标一般通过独立端点或采集代理暴露，不应与用户聊天 API 混在同一个无保护路径上。监控系统的访问权限也属于安全边界。

### 14. 镜像供应链与安全

容器化引入了供应链问题：基础镜像、系统包、Python 包、推理引擎、模型文件、构建脚本和镜像仓库都可能带来风险。

基本实践包括：

- 使用可信来源并固定基础镜像/依赖版本；
- 定期更新并评估漏洞，不盲目升级；
- 构建后做镜像漏洞扫描和许可证审查；
- 用最小运行权限启动，避免默认 root；
- 尽可能使用只读根文件系统和最小 Linux capabilities；
- 不把密钥、私有模型、开发工具和调试端口带入通用生产镜像；
- 记录镜像版本、构建来源、模型版本和部署环境；
- 对私有权重、镜像仓库和模型下载凭证设置访问控制。

需要保持务实：安全加固也要兼顾推理引擎实际写缓存、生成临时文件、访问 GPU 设备的需要。目标是最小权限，而不是不理解运行需求地一律禁止。

### 15. 一个概念性模型服务容器方案

可以用下图理解各部分，而不是把它当作唯一实现：

```text
宿主机 / 节点
  ├─ GPU + 驱动
  ├─ 容器运行时
  ├─ 受控内部网络
  ├─ 持久卷：模型权重（只读）
  ├─ 持久卷：可重建下载缓存（可写）
  └─ 容器：model-server
       ├─ 推理引擎与 API 代码（镜像）
       ├─ 配置（环境变量/配置文件）
       ├─ 密钥（受控注入，不写入镜像）
       ├─ 读取 /models（只读）
       ├─ 写入 /cache（受控）
       ├─ 只暴露内部端口
       ├─ readiness：模型加载且预热完成
       └─ 标准输出：结构化日志与指标
```

同一模型服务在不同阶段可逐步演进：本地可直接下载权重并映射端口；内部环境可挂载缓存和内网；生产环境再引入专用节点、网关、负载均衡、镜像仓库和密钥系统。变化的不是“Docker 有没有用”，而是运行环境责任越来越明确。

### 16. 常见故障的分层排查思路

当模型容器出问题时，先确认属于哪一层：

| 现象 | 优先检查的层 |
| --- | --- |
| 容器无法启动 | 镜像命令、环境变量、挂载路径、权限、依赖库 |
| 容器反复重启 | 启动探针、模型加载时长、内存/GPU OOM、错误日志 |
| 容器看不到 GPU | 宿主机驱动、容器运行时 GPU 配置、设备权限 |
| 模型加载失败 | 权重完整性、格式、Tokenizer、引擎/框架版本、显存 |
| 首次请求极慢 | 冷启动、预热、权重下载、内核初始化、缓存 |
| 服务偶发中断 | 资源限制、健康检查阈值、网络、优雅停止、节点压力 |
| 重建后数据丢失 | 将需要持久化的数据写进了容器可写层 |
| 镜像太大/发布太慢 | 权重内置、构建层设计、缓存/调试文件未清理 |

这种层次化方法比“重建一次、重启一次、换个镜像”更有效。每一步应留下日志、版本和资源证据，避免偶然成功后无法复现。

### 17. 容器化与可重复性：仍需记录什么

即使镜像 Tag 已固定，模型服务的可重复性还依赖：

- 模型权重版本、哈希和来源；
- Tokenizer、聊天模板、LoRA/适配器版本；
- 推理引擎启动参数；
- GPU 类型、驱动、运行时版本；
- 卷中缓存是否影响行为；
- 环境变量和配置文件；
- 网关路由和默认模型映射；
- 数据库/RAG 索引版本；
- 外部 API 和密钥权限。

这说明容器是可重复性的一个重要部件，不是全部。遇到“同镜像在两处输出不同/性能不同”时，要回到完整运行清单比较，而不是只看镜像 digest。

## 常见误区

### 误区 1：镜像和容器是同一个东西

纠正：镜像是可复用的只读交付模板，容器是它的一个运行实例。删除容器通常不等于删除镜像；同一镜像可以运行多个有不同配置的容器。

### 误区 2：把模型权重内置到镜像永远最稳定

纠正：它可减少运行时下载依赖，但会显著放大镜像、耦合模型和代码发布、增加分发与许可证治理负担。应根据离线需求、模型大小、发布频率和安全边界选择。

### 误区 3：容器里装了 CUDA 就不需要宿主机驱动

纠正：容器通常仍依赖宿主机提供的 GPU 驱动和设备访问。容器用户态运行库、宿主机驱动和推理引擎必须在兼容范围内。

### 误区 4：容器启动成功就代表模型服务已准备好

纠正：端口监听时，模型可能仍在下载、加载权重、初始化 GPU 或预热。应使用就绪检查，只有关键路径可用才接流量。

### 误区 5：所有配置都放环境变量最方便

纠正：环境变量适合小型运行时配置，但不适合大配置、模型文件和复杂证书；密钥放环境变量也要考虑可见性。应按数据类型选择配置文件、Secret、卷或专用配置系统。

### 误区 6：挂载宿主机目录只是开发便利，没有安全影响

纠正：挂载会把宿主机文件暴露给容器。可写、过宽目录、包含密钥的目录都会扩大风险。应最小化、默认只读并明确权限。

### 误区 7：Docker Compose 就等于生产集群管理

纠正：Compose 很适合单机开发和小型部署，但不天然解决跨节点调度、弹性、高可用、复杂发布和企业级治理。它是工具边界不同，不是优劣问题。

## 本节练习

### 练习 1：为文件选择存放位置

请为下面每项选择更合适的默认存放位置，并说明理由：推理服务代码、50GB 模型权重、下载缓存、数据库密码、用户上传 PDF、运行日志、临时 Tokenizer 缓存。

答案：推理服务代码和依赖适合放镜像；50GB 模型权重通常适合对象存储、模型仓库或只读持久卷，以便独立版本管理；下载缓存适合可重建的专用可写卷；数据库密码应通过 Secret/受控运行时注入，不能放镜像；用户上传 PDF 应放对象存储或受控文件服务；运行日志应输出到日志收集系统或受控日志目录；临时 Tokenizer 缓存可放可重建缓存卷。具体选择还受离线、合规和平台能力影响。

### 练习 2：解释容器重建后的数据丢失

一个开发者将模型下载到容器内 `/root/.cache`，删除旧容器并用同一镜像重新启动，发现模型需要重新下载。原因是什么？如何改善？

答案：下载文件位于容器可写层，删除容器后该层被删除。可将模型下载缓存挂载到受控持久卷或宿主机目录；更成熟时用内部模型仓库/对象存储和节点缓存。缓存可重建，但需要考虑磁盘容量、权限、版本和清理策略。

### 练习 3：诊断“容器看不到 GPU”

请按从底到上的顺序给出一个排查列表。

答案：先检查宿主机是否识别 GPU 且驱动正常；检查容器运行时是否安装/配置为允许 GPU 透传；检查启动参数或平台资源声明是否分配了目标 GPU；进入容器检查框架能否识别 GPU 和相关运行库；最后检查推理引擎、模型格式和显存配置。不要一开始就修改模型或业务代码。

### 练习 4：设计就绪条件

一个模型服务的端口在进程启动后立即监听，但权重加载需要 90 秒。请写出至少四个 readiness 通过前应满足的条件。

答案：模型权重和 Tokenizer 已成功加载；目标 GPU 可用且显存分配满足安全阈值；推理引擎完成必要初始化；用无敏感的预热请求验证基本生成路径；关键配置和模型版本已校验；服务未处于下线状态。仅端口监听不能作为就绪条件。

### 练习 5：分析一个危险的挂载

有人运行模型容器时把宿主机根目录以可写方式挂载到容器 `/host`。风险是什么？更好的原则是什么？

答案：容器中的进程一旦出错或被攻破，就可能读取、修改或删除宿主机大量文件，容器隔离大幅失效。应采用最小挂载原则：只挂载必要目录，尽可能只读，使用受限用户和明确权限，并避免把密钥、系统目录和无关数据暴露给模型服务。

## 自测题

### 自测 1：Docker 化模型服务主要解决什么问题？

答案：它主要解决应用用户态依赖、启动方式和交付环境的一致性，使构建、部署、版本和回滚更可重复。它不自动解决 GPU 容量、模型质量、网络安全、密钥、监控、高可用、数据持久化和业务安全。

### 自测 2：为什么模型服务比普通小 Web 服务更要重视冷启动？

答案：模型权重可能非常大，需要下载/读取、载入系统内存和 GPU 显存；推理框架还可能初始化 CUDA、选择或编译内核、建立缓存。启动耗时长会影响扩容、发布和故障恢复，因此需要就绪检查、预热和容量预留。

### 自测 3：模型权重与下载缓存有什么区别？

答案：模型权重是需要可追溯、可校验、受许可证和版本管理的关键模型资产；下载缓存是为了加快再次获取或加载而存在的可重建副本。缓存丢失通常可重新获取，权重的唯一来源、版本和完整性不能只依赖缓存。

### 自测 4：为什么不应把供应商 API Key 写进 Dockerfile？

答案：Dockerfile 和构建层可能进入源码、构建日志、镜像历史、镜像仓库和缓存，密钥难以撤回且会扩大泄露范围。应在运行时通过受控 Secret、环境注入或密钥管理系统提供，并避免日志打印。

### 自测 5：优雅停止模型容器的基本顺序是什么？

答案：先让实例不再就绪并从流量入口摘除；停止接收新请求；在配置的宽限期内完成或可控取消活跃请求、保存必要状态；最后退出。对异步任务还需有任务状态与恢复策略。

## 本节小结

本节从模型服务视角重新组织 Docker 知识：镜像适合封装代码和可版本化依赖，容器是运行实例，卷/对象存储承载权重与数据，Secret 承载敏感配置，宿主机与运行时共同提供 GPU，网络与端口决定暴露边界。模型服务需要额外面对大权重、GPU 兼容、冷启动、显存和高成本资源。

正确的容器化方案不追求“把一切都放进一个镜像”，而是清楚划分不可变应用、外部模型资产、可重建缓存、持久化业务数据和敏感配置。它为可重复部署提供基础，但仍需要健康检查、预热、优雅停止、资源限制、供应链安全和可观测性配合，才能成为可靠运行环境。
