# 阶段 6 第 36 节：阶段 6 项目整理和面试表达

## 本节定位

这一节是阶段 6 的收尾课。

阶段 6 的主题是：

```text
生产化与评测
```

这句话听起来很大。

但它不是一个空泛概念。

它真正解决的是：

```text
一个已经能跑的 AI 项目，怎样从 demo 逐步变成可验证、可排查、可恢复、可部署、可持续迭代的工程系统。
```

前面几个阶段，我们已经学过：

```text
Python 基础
FastAPI 服务基础
LLM API 基础
Tool Calling
Java mock 业务服务
RAG 知识库
LangGraph 智能工单 Agent
```

这些内容让项目“能跑起来”。

阶段 6 继续往前走了一步：

```text
让项目更像一个真实工程。
```

一个真实工程不是只看“功能有没有写出来”。

还要看：

```text
效果怎么判断？
改动后有没有退化？
模型输出不稳定怎么办？
真实模型和 fake 模式怎么切换？
工具调用怎么控制权限？
状态怎么保存？
请求怎么追踪？
日志和指标怎么设计？
上游超时、限流、失败时怎么办？
多个服务怎么本地编排？
服务 ready 不 ready 怎么判断？
CI 怎么自动回归？
```

阶段 6 就是围绕这些问题展开的。

这一节不继续新增功能。

这一节要做的是：

```text
把阶段 6 学过的内容整理成你能理解、能复述、能面试、能继续扩展的知识体系。
```

你最终不能只说：

```text
我写过一些测试。
我写过一些日志。
我写过 Docker Compose。
```

你要能说：

```text
我知道为什么 AI 应用需要 eval。
我知道单元测试和效果评测的边界。
我知道如何把真实模型放进 Agent，同时保留 fake 模式保证测试稳定。
我知道模型输出不能盲信，必须有结构化校验和失败兜底。
我知道工具调用尤其是写操作必须有权限和确认边界。
我知道多轮 Agent 为什么需要 thread_id、checkpoint 和生命周期管理。
我知道 trace、span、log、metrics 分别解决什么问题。
我知道 timeout、retry、rate limit、circuit breaker、degradation 是一组稳定性保护手段。
我知道 health/readiness/CI 怎样帮助服务上线和持续迭代。
```

这才是阶段 6 的真正学习成果。

17. 生产日志字段为什么要控制粒度、敏感信息和基数。

24. 下一阶段为什么应该进入作品整理、演示材料、架构图、截图、面试讲稿和简历描述。

## 二、本节先不学什么

本节不做这些事：

1. 不新增新的 Agent 节点。
2. 不新增新的 RAG 检索算法。
3. 不接入新的数据库。

7. 不改 CI 的行为。


如果不停新增功能，但说不清楚为什么这么设计，那学习质量反而会下降。

```text

项目边界意识
后续规划能力
```

## 三、基础知识铺垫

### 1. 什么是 demo

demo 是演示版本。

它的核心目标是：

```text
证明一个想法能跑通。
```

比如：

```text
用户输入问题
系统返回回答
用户说要创建工单
系统能生成一个模拟工单
```

这就是 demo。

demo 的特点是：

```text
功能链路短
异常情况少
数据规模小
用户数量少
依赖服务少
测试覆盖少
部署要求低
可观测性要求低
```

demo 可以帮助你快速验证方向。

但 demo 不能直接等于真实工程。

因为真实工程会遇到很多 demo 阶段不明显的问题：

```text
模型偶尔胡说
模型输出格式不稳定
用户输入很乱
外部 API 超时
向量库不可用
Java 服务返回 500
同一个用户多轮对话状态丢失
多个用户并发访问
日志里不知道哪里出错
改了一行 prompt 后老功能退化
CI 没跑测试，合并后才发现坏了
Docker 容器 running 但服务没 ready
```

阶段 6 就是在补这些问题。

### 2. 什么是可上线雏形

可上线雏形不是“完美生产级”。

它更像是：

```text
核心链路能跑。
关键边界有保护。
失败情况有兜底。
质量有评测。
状态能管理。
日志能追踪。
服务能启动。
回归能自动跑。
```

它不一定已经支撑大量用户。

也不一定已经有完整权限系统、数据库、Kubernetes、监控大盘。

但它已经从“玩具 demo”向真实工程靠近。

判断一个 AI 项目是不是可上线雏形，可以问这些问题：

1. 模型答错了，能不能通过 eval 发现？
2. 改 prompt 后，能不能知道有没有退化？
3. 模型输出结构坏了，业务系统会不会直接被污染？
4. 用户没有确认，系统会不会执行写操作？
5. 外部服务超时，用户看到的是不是安全可理解的回答？
6. 多轮对话中断后，系统能不能知道该不该恢复？
7. 一个请求失败了，能不能按 trace_id 找到经过哪些节点？
8. 成本突然上升，能不能从 token 和调用次数上解释？
9. 服务启动后，负载均衡或 Compose 能不能判断它 ready？
10. 代码提交后，CI 能不能自动跑关键测试？

如果这些问题完全回答不上来，就还停留在 demo 阶段。

### 3. 什么是生产级系统

生产级系统比可上线雏形更严格。

生产级系统要面对真实用户、真实数据、真实并发、真实成本和真实故障。

它通常需要：

```text
真实认证授权
真实业务数据库
真实消息队列
真实密钥管理
真实日志采集
真实指标系统
真实 tracing 后端
真实告警
灰度发布
回滚机制
容量规划
压测
安全审计
数据备份
故障演练
合规要求
```

所以我们现在不能夸大项目。

更准确的表达是：

```text
这是一个面向客服业务场景的 RAG + LangGraph 智能工单 Agent 学习项目。
目前已经从功能 demo 推进到可上线雏形，具备评测、结构化校验、工具安全、状态生命周期、可观测性设计、稳定性策略、本地编排和 CI 回归能力。
它还没有接入完整生产认证、真实数据库、生产监控栈和正式部署平台。
```

这句话比“我做了一个生产级 Agent”更可信。

面试中可信很重要。

你讲得越准确，别人越容易相信你真的理解。

### 4. AI 应用为什么更需要评测

普通后端接口通常是确定性的。

比如：

```text
GET /orders/O1001
```

只要订单存在，返回结果通常稳定。

同样的输入，大概率得到同样的输出。

AI 应用不一样。

AI 应用里有很多不稳定因素：

```text
模型可能理解错意图
模型可能漏字段
模型可能多输出字段
模型可能格式不符合 JSON
模型可能把知识库之外的内容编出来
模型可能因为 prompt 小改动行为变化
模型可能因为模型版本升级行为变化
```

所以 AI 应用不能只靠普通测试。

它还需要 eval。

普通测试更像是在问：

```text
代码有没有按规则运行？
```

eval 更像是在问：

```text
AI 系统的效果有没有达到预期？
```

阶段 6 的前 12 节就是围绕这个展开。

### 5. 为什么要把测试和评测分开

测试和评测都重要。

但它们关心的问题不同。

测试更适合验证确定性边界：

```text
函数输入 A 是否返回 B
Pydantic 是否拒绝非法字段
404 是否被分类为不可重试
用户未确认时是否阻断写操作
readiness 缺 API Key 是否返回 503
```

评测更适合验证效果表现：

```text
用户这句话应该识别成什么意图
这段描述应该提取哪些工单字段
这个问题应该走 RAG 还是创建工单
这个回答是否引用了正确来源
改 prompt 后旧样本是否退化
```

如果把 eval 全部当普通测试，会遇到问题：

```text
模型输出不是 100% 固定
某些答案可以有多个合理表达
效果好坏有时候需要规则、人工或 LLM judge 综合判断
```

如果把普通测试全部当 eval，也会遇到问题：

```text
代码 bug 本该直接失败，却被模糊评测掩盖
确定性规则不清楚，问题难定位
CI 变慢、变贵、变不稳定
```

所以阶段 6 的正确思路是：

```text
确定性边界用 test。
AI 效果表现用 eval。
核心回归用稳定、便宜、可重复的规则评测。
真实模型能力用受控 smoke 或离线评测补充。
```

### 6. 什么是工程复盘

工程复盘不是把文件列表复制一遍。

工程复盘要回答：

```text
一开始的问题是什么？
我为什么这样设计？
我拆成了哪些模块？
每个模块解决什么风险？
它们怎么串起来？
怎么验证它们是对的？
还有什么没做？
下一步怎么做？
```

比如阶段 6 不能这样复盘：

```text
我写了 evaluator。
我写了 retry。
我写了 Docker Compose。
```

这样的表达太散。

更好的表达是：

```text
我把 Agent 的生产化分成四层：

第一层是质量评测，解决效果不可量化的问题。
第二层是真实模型接入，解决从规则/fake 走向真实 LLM 的问题。
第三层是运行时安全和状态管理，解决工具调用、写操作、多轮状态和恢复的问题。
第四层是生产运行保障，解决可观测性、成本、稳定性、部署和 CI 回归的问题。
```

这就从“文件视角”变成了“能力视角”。

面试更看重能力视角。

### 7. 什么是项目表达

项目表达就是：

```text
把自己做过的项目，用别人能理解、能追问、能信服的方式讲出来。
```

项目表达不是背稿。

项目表达要做到：

```text
讲目标
讲架构
讲流程
讲关键技术点
讲难点
讲取舍
讲验证方式
讲边界和不足
讲下一步
```

如果只讲“我用了 FastAPI、LangChain、LangGraph、Qdrant”，这只是技术名词堆叠。

更好的表达是：

```text
这个项目面向客服场景，目标是让 AI 既能基于企业知识库回答政策问题，也能在需要人工处理时收集信息并创建工单。

Python FastAPI 负责 AI 服务，Java mock service 模拟业务系统，RAG 负责知识库问答，LangGraph 负责把意图识别、知识库回答、订单查询、字段提取、用户确认和创建工单组织成可控流程。

阶段 6 我重点补了生产化能力，包括 eval 评测集、真实模型节点、Pydantic 输出校验、工具安全、checkpoint 生命周期、可观测性、稳定性保护、Docker Compose 编排和 CI 回归。
```

这个表达就更完整。

### 8. 面试表达为什么要讲取舍

真实工程没有绝对完美方案。

面试官很关心你是否知道取舍。

比如：

```text
为什么当前 eval 优先用规则 evaluator，而不是一上来全用 LLM-as-judge？
```

可以回答：

```text
因为当前项目先要保证 CI 可重复、低成本、稳定运行。规则 evaluator 对意图、字段、路由这类结构化任务足够直接，也方便定位问题。LLM-as-judge 更适合评估开放式回答质量，但成本、稳定性和 judge prompt 本身也需要管理，所以后续再补。
```

这比只说“因为我还没学”专业得多。

再比如：

```text
为什么 Docker Compose 里 Qdrant 和 Milvus 用 profile？
```

可以回答：

```text
因为默认开发只需要 Python AI 服务和 Java mock 服务。向量库不是每次都必须启动，Milvus 资源占用也更高，用 profile 可以按需启动，避免本地环境过重，也降低端口冲突和启动成本。
```

能讲取舍，说明你不是只会照抄。

### 9. 面试表达为什么要讲验证

项目不是“我觉得可以”。

项目要能说明：

```text
我怎么知道它可以？
```

阶段 6 里最重要的验证方式包括：

```text
pytest 单元测试和节点测试
Agent eval 脚本
eval report
bad case analysis
regression evaluation
fake LLM / fake Java client 测试
compileall 语法检查
health/readiness 接口测试
CI 自动回归
```

讲项目时如果能带上验证，就会更像工程师：

```text
我不是只手工点了几次接口，而是把意图识别、字段提取、路由和 RAG 组合能力做成了 eval suite，并把关键确定性边界放进 pytest。后面又用统一回归脚本接到 GitHub Actions，保证每次 push/PR 都能跑 Java mock 和 ai-service 的测试。
```

### 10. 面试表达为什么要讲不足

很多初学者怕讲不足。

其实合理讲不足反而加分。

因为真实项目一定有边界。

如果你把一个学习项目讲成已经完全生产级，别人一追问就会露出问题。

更好的方式是主动说明：

```text
当前项目还没有接入真实认证授权、真实业务数据库、正式监控平台、告警系统、线上部署和压测。现在更准确的定位是一个具备生产化设计意识的可上线雏形。下一阶段会整理展示材料和面试讲稿，如果继续工程化，可以补 Redis/Postgres checkpoint、真实前端工作台、Kubernetes 或云部署、真实观测后端和更大规模 eval dataset。
```

这叫边界意识。

边界意识是工程能力的一部分。

## 四、本节主题系统讲解

### 1. 阶段 6 的完整主线

阶段 6 不是随机学了 36 个主题。

它可以被整理成 8 条主线：

```text
第一条：Agent 效果评测
第二条：评测工程化
第三条：真实模型接入
第四条：模型输出边界
第五条：工具调用生产化
第六条：状态持久化与会话生命周期
第七条：可观测性、成本和稳定性
第八条：本地编排、就绪检查和 CI
```

如果把它们画成一条能力升级路线，就是：

```text
能跑
  -> 能评测
  -> 能接真实模型
  -> 能防模型乱输出
  -> 能安全调用工具
  -> 能保存和恢复状态
  -> 能追踪和排查问题
  -> 能控制失败、成本和延迟
  -> 能本地多服务启动
  -> 能自动回归
```

这就是阶段 6 的完整逻辑。

### 2. 第 1-12 节：Agent 效果评测体系

第 1-12 节解决一个根本问题：

```text
AI 应用到底怎么判断好不好？
```

我们不是只用肉眼看几次回答。

而是建立了：

```text
eval dataset
eval case
expected output
evaluator
eval suite
eval report
bad case analysis
regression evaluation
```

这一组东西的关系是：

```text
eval dataset：评测样本集合
eval case：单条评测样本
expected output：这条样本希望系统达到的结果
evaluator：判断 actual 是否符合 expected 的规则
eval suite：把多个 evaluator 组织起来运行
eval report：把运行结果写成可阅读报告
bad case analysis：失败样本的原因分析
regression evaluation：防止旧能力被新改动破坏
```

在当前项目里，评测不是只有一种。

它分成多层：

```text
意图识别评测：用户到底想问政策、查订单、创建工单、闲聊还是拒绝处理？
字段提取评测：模型或规则有没有从用户描述里提取出工单字段？
路由评测：Agent 有没有走正确节点路径？
RAG + Agent 组合评测：知识库回答、引用来源、无上下文拒答和工单决策是否正确？
```

为什么要拆这么细？

因为 Agent 出错时，如果只看最终回答，很难定位问题。

比如用户说：

```text
我的订单 O1001 迟迟没到，帮我看看。
```

最终回答错了，可能是：

```text
意图识别错了
订单号没提取出来
路由没走 query_order
Java 工具调用失败
工具结果校验失败
最终总结模型说错了
```

拆分评测后，就能知道失败发生在哪一层。

阶段 6 前 12 节训练的核心能力是：

```text
不要只评最终答案，要评中间决策。
```

这对 Agent 特别重要。

因为 Agent 不是单次问答。

Agent 是多步决策流程。

多步流程必须有中间可观测、可评测的节点。

### 3. 第 13-18 节：真实模型接入与输出边界

第 13-18 节解决第二个问题：

```text
怎么把真实 LLM 放进 Agent，又不让系统变得不可测、不可控？
```

我们接入了真实 LLM 意图识别节点和真实 LLM 字段提取节点。

但没有把整个系统直接绑死在真实模型上。

而是保留：

```text
rule_based 模式
fake_llm 模式
real_llm 模式
```

它们各自有意义：

```text
rule_based：最稳定，适合默认开发和 CI。
fake_llm：模拟真实模型 JSON 边界，适合测试解析、校验和失败处理。
real_llm：调用真实模型，适合 smoke、人工验证和后续真实效果评测。
```

这体现了一个很重要的工程原则：

```text
真实依赖可以接入，但不能让所有测试都依赖真实依赖。
```

如果 CI 每次都真实调用模型，会有很多问题：

```text
成本不可控
速度慢
网络不稳定
API Key 管理复杂
模型输出不完全稳定
失败原因可能不是代码问题
```

所以当前项目让真实模型成为可切换依赖。

这就是 dependency injection 的意义：

```text
同一条业务链路，可以注入真实模型，也可以注入 fake 模型。
```

第 15 节的 Pydantic 校验也非常关键。

它解决的是：

```text
模型输出不能直接进入业务系统。
```

大模型即使被要求输出 JSON，也可能：

```text
多字段
少字段
字段类型错
枚举值错
空字符串
订单号格式错
把说明文字混进 JSON
```

所以我们用 Pydantic 做第二道边界：

```text
LLM 原始输出
  -> JSON parse
  -> Pydantic schema validate
  -> 业务对象
```

只有通过结构化校验的数据，才允许进入后续 Agent 状态。

这也是 AI 工程和普通 prompt demo 的区别。

### 4. prompt 版本管理为什么重要

prompt 看起来像文字。

但在 AI 应用里，prompt 其实像代码。

它会影响：

```text
意图识别结果
字段提取结果
工具调用判断
回答风格
拒答边界
安全行为
成本和 token
```

如果 prompt 没有版本，后面会出现问题：

```text
不知道线上用的是哪版 prompt
评测报告无法关联到 prompt 版本
模型行为变化后难以回滚
不同环境 prompt 不一致
```

所以阶段 6 加了 prompt spec：

```text
prompt_name
prompt_version
prompt content
```

并在日志或调用上下文里记录 prompt 信息。

这让你可以回答：

```text
这个 eval report 是在哪个 prompt 版本下跑出来的？
这次线上问题是不是因为 prompt 改动导致？
如果新版 prompt 效果变差，能不能回退？
```

这就是 prompt engineering 往 prompt operations 发展的方向。

### 5. 模型输出失败为什么要分类

模型输出失败不能只写：

```text
except Exception:
    return fallback
```

因为不同失败原因，对应的处理策略不同。

常见失败有：

```text
不是 JSON
JSON 结构不对
字段类型不对
枚举值不对
必填字段缺失
模型 API 超时
模型 API 认证失败
模型 API 限流
模型返回空内容
模型输出和业务规则冲突
```

这些失败不能一刀切。

比如：

```text
认证失败：通常是配置问题，不应该悄悄 fallback 掩盖。
格式失败：可以走规则 fallback 或让用户重试。
字段缺失：可以继续追问用户。
限流失败：可能要降级、排队或提示稍后再试。
```

阶段 6 做模型输出失败分类，本质是在训练一个能力：

```text
失败不是一个状态，失败是一组可分类、可观察、可处理的情况。
```

### 6. 第 19-21 节：工具调用生产化

第 19-21 节解决第三个问题：

```text
Agent 怎么安全调用业务系统？
```

AI 调工具不是让模型直接操作数据库。

正确链路应该是：

```text
模型或规则提出工具意图
  -> 后端校验工具名
  -> 后端校验参数
  -> 后端判断权限
  -> 后端执行受控工具
  -> 后端校验工具返回
  -> 后端把结构化结果写回 Agent 状态
  -> 模型或模板生成最终回答
```

当前项目里的 query_order 是只读工具。

它虽然是只读，也不能完全放开。

因为还要考虑：

```text
订单号格式是否正确
订单是否存在
Java 服务是否超时
Java 服务是否返回 500
返回字段是否符合白名单
用户是否有权限查询这个订单
```

创建工单是写操作。

写操作边界更严格。

因为它会改变业务系统状态。

写操作至少需要：

```text
用户确认
权限判断
参数校验
幂等键
错误处理
审计日志
```

阶段 6 第 21 节补的就是写操作安全回归。

它体现一个非常重要的 AI 工程原则：

```text
模型可以建议动作，但最终执行权必须在后端规则里。
```

模型不能因为“看起来用户想创建工单”就直接创建。

用户确认是安全边界。

后端授权是执行边界。

幂等键是重复提交边界。

测试和回归是行为边界。

### 7. 第 22-25 节：checkpoint 与会话生命周期

第 22-25 节解决第四个问题：

```text
多轮 Agent 的状态怎么保存、恢复和清理？
```

普通 HTTP 请求是一次性的。

但智能工单 Agent 很多流程不是一次完成。

比如：

```text
用户：我要投诉订单 O1001。
系统：请补充问题类型和详细描述。
用户：配送太慢，客服没有回应。
系统：请确认是否创建工单。
用户：确认。
系统：创建成功。
```

这里至少有多轮交互。

如果没有状态管理，系统不知道：

```text
这个确认对应哪一次创建工单？
之前提取过哪些字段？
哪些字段还缺？
这个 thread 是否已经过期？
这个用户是否还允许恢复旧会话？
已完成会话还能不能继续写？
```

所以需要：

```text
thread_id：标识一条多轮对话线程。
checkpoint：保存某个时间点的 Agent 状态快照。
thread lifecycle：管理 active、waiting_confirmation、completed、closed、expired。
cleanup policy：清理过期状态，避免状态无限增长。
```

这里要区分几个概念：

```text
thread_id 是身份标识。
checkpoint 是状态快照。
lifecycle 是状态机规则。
cleanup 是资源治理策略。
```

面试中如果被问：

```text
checkpoint 和 thread_id 是不是一回事？
```

你应该回答：

```text
不是。thread_id 用来标识一条对话或任务链路，checkpoint 是这个 thread 在某个时间点保存下来的状态内容。thread_id 是索引，checkpoint 是数据。一个 thread_id 可以对应多个 checkpoint 或一个最新 checkpoint，具体取决于存储策略。
```

### 8. 第 26-30 节：可观测性、日志、指标、成本

第 26-30 节解决第五个问题：

```text
系统出问题时怎么知道发生了什么？
```

可观测性不是只打印日志。

可观测性至少包括：

```text
trace
span
log
metrics
```

它们分工不同。

trace 解决：

```text
一次请求从入口到结束经过了哪些步骤？
```

span 解决：

```text
这次请求中的某一个步骤耗时多久、是否出错？
```

log 解决：

```text
某个时间点具体发生了什么事件？
```

metrics 解决：

```text
一段时间内整体趋势如何？
```

比如用户反馈：

```text
今天创建工单特别慢。
```

你不应该只看最终报错。

你可以按这个顺序排查：

```text
先看 metrics：延迟是否整体升高？
再看 trace：慢请求卡在哪个阶段？
再看 span：是 LLM、RAG、Java API 还是 checkpoint 慢？
再看 log：具体错误码、重试次数、fallback 状态是什么？
```

这就是阶段 6 可观测性部分的核心。

第 30 节补了成本、token 和延迟指标。

AI 应用必须关注成本。

因为每次模型调用都可能消耗：

```text
prompt tokens
completion tokens
模型费用
网络时间
用户等待时间
```

如果没有 token 和成本指标，就很难回答：

```text
哪个接口最贵？
哪个 prompt 版本 token 增加了？
哪类用户问题最容易触发多次模型调用？
RAG 上下文是不是塞得太长？
真实模型是否需要降级为便宜模型？
```

这也是 AI 应用和普通 CRUD 应用的明显差别之一。

它们不是完全重复。

可以这样理解：

```text
OpenTelemetry 更偏通用分布式系统可观测性标准。
```

LangSmith 适合看：

### 10. 第 31-33 节：稳定性保护体系

第 31-33 节解决第六个问题：

```text
外部依赖慢、失败、限流时，系统怎么保护自己？
```

AI 应用依赖很多外部组件：

```text
LLM API
embedding API
Qdrant
Milvus
Java 业务服务
文件系统
checkpoint store
```

任何一个慢了，都可能拖慢整条链路。

所以需要稳定性策略。

timeout 解决：

```text
不能无限等。
```

retry 解决：

```text
临时失败可以有限重试。
```

rate limit 解决：

```text
限制请求速度，避免把自己或上游打爆。
```

circuit breaker 解决：

```text
上游持续失败时快速失败，避免继续浪费资源。
```

degradation 解决：

```text
主能力不可用时，用较低质量但安全的方式继续服务。
```

这些策略不能乱用。

比如 retry：

```text
读操作通常更容易重试。
写操作必须有幂等键才能谨慎重试。
401/403 不应该重试。
429 可以按 Retry-After 或退避策略处理。
5xx 可以短暂重试。
```

再比如 circuit breaker：

```text
它不是提高成功率的魔法。
它的重点是保护系统，避免故障扩散。
```

稳定性保护的核心思想是：

```text
系统不能假设所有依赖永远正常。
```

### 11. 第 34-35 节：本地编排、readiness 和 CI

第 34-35 节解决第七个问题：

```text
多个服务怎么启动，启动后怎么判断可用，代码变更后怎么自动验证？
```

当前项目不是只有一个 Python 文件。

它至少包含：

```text
Python ai-service
Java mock service
Qdrant
Milvus
CI 回归脚本
学习笔记和索引
```

Docker Compose 的作用是：

```text
用一个 compose.yml 描述多个服务怎么启动、怎么联网、怎么配置环境变量、怎么暴露端口、怎么做健康检查。
```

但容器 running 不代表服务 ready。

所以第 35 节把 `/health` 和 `/ready` 区分开。

可以这样记：

```text
/health：我这个进程还活着吗？
/ready：我现在准备好接收真实请求了吗？
```

比如 ai-service 在 `real_llm` 模式下没有 API Key：

```text
/health 可以是 ok。
/ready 应该是 not_ready，并返回 503。
```

原因是：

```text
进程活着，不代表它能完成真实模型调用。
```

CI 的作用是：

```text
每次 push 或 PR 时自动跑回归，防止代码悄悄破坏已有功能。
```

当前 CI 的一个重要设计是：

```text
本地回归和 GitHub Actions 复用 scripts/run_regression.py。
```

这样做的好处是：

```text
本地和 CI 验证口径一致。
开发者可以先在本地跑同一套检查。
CI 配置更薄，真正逻辑放在脚本里。
后续新增项目或检查项时只改一处。
```

### 14. 当前项目的一条完整请求链路

以“用户查询订单并可能创建工单”为例。

完整链路可以这样讲：

```text
用户请求进入 ai-service。
FastAPI 生成或接收 trace_id。
请求进入 LangGraph Agent。
Agent 先进行输入归一化和意图识别。
如果意图是查订单，进入 query_order 节点。
query_order 节点提取或读取订单号。
后端用 Pydantic 校验 QueryOrderArgs。
后端通过 JavaOrderClient 调用 Java mock service。
Java mock service 返回订单数据。
Python 侧做字段白名单映射和 Pydantic 响应校验。
Agent 把结构化订单结果写回状态。
如果用户还需要创建工单，Agent 进入字段提取、缺字段追问、用户确认。
只有用户确认后，后端才授权 create_ticket 工具。
创建工单时使用幂等键防重复提交。
整个过程记录 trace/span/log/metrics 相关字段。
测试中使用 fake LLM 和 fake Java client，CI 不真实调用模型。
```

这条链路非常重要。

因为它把阶段 3、4、5、6 全部串起来了。

### 15. 怎么讲“我不是只会调 API”

面试里，如果别人问：

```text
你这个项目是不是就是调了个大模型 API？
```

不要急着反驳。

可以这样回答：

```text
大模型 API 只是能力来源之一。这个项目的重点不是单次聊天，而是把 LLM 放进可控业务流程里。

我做了几层工程约束：

第一，模型输出要用 Pydantic 做结构化校验，不能直接进入业务系统。
第二，工具调用由后端注册表、参数 schema、权限和确认机制控制，模型不能直接执行写操作。
第三，多轮流程用 thread_id 和 checkpoint 管理状态，避免确认和补字段流程丢上下文。
第四，用 eval dataset、evaluator、bad case 和 regression 评估 Agent 决策效果。
```

这就能把“调 API”提升为“AI 工程系统设计”。

### 16. 怎么讲“为什么用 LangGraph”

你可以这样讲：

```text
这个项目不是单轮问答，而是多步骤、多分支、有状态、有人工确认的业务流程。

如果只用普通函数，开始可以跑，但随着节点变多，状态传递、分支跳转、中断恢复、错误兜底和测试会越来越难维护。

LangGraph 的价值是把 Agent 流程建模成图：节点负责单步逻辑，边负责流程跳转，State 保存中间状态，checkpoint 支持恢复，conditional edge 支持按意图和状态分支。
```

再补一句当前边界：

```text
当前项目还不是复杂多 Agent 系统，LangGraph 主要用于单 Agent 业务流程编排。
```

这句话很稳。

它既说明你理解 LangGraph 的价值，又没有过度夸大。

### 17. 怎么讲“为什么要 RAG”

你可以这样讲：

```text
客服场景里很多回答依赖企业内部政策，比如退款规则、账户安全规则、物流说明。模型自身参数里没有这些实时、私有、可变的业务知识，所以需要 RAG。

RAG 的思路是先把文档切成 chunk，生成 embedding 存入向量库；用户提问时先检索相关 chunk，再把检索结果作为上下文交给模型回答，并要求回答带引用来源。如果检索不到足够相关内容，就拒答或转工单，而不是让模型凭空编。
```

阶段 6 中 RAG 的生产化重点是：

```text
RAG + Agent 组合评测
引用来源评测
无上下文拒答
向量库超时和降级
Qdrant/Milvus 本地编排
```

### 18. 怎么讲“为什么要 Java mock service”

你可以这样讲：

```text
我学习路线是 Java 后端 + Python AI 服务，所以项目里用 Java mock service 模拟真实业务系统。

Python 负责 AI 编排和模型能力，Java 服务模拟订单查询、工单创建等后端业务接口。这样可以训练真实企业里常见的服务拆分方式：AI 服务不直接改业务数据，而是通过受控 API 调用业务后端。
```

这里有一个重要点：

```text
mock service 不是最终生产形态。
```

它的价值是：

```text
让学习阶段先跑通跨服务调用、工具边界、错误处理、测试和编排。
```

后续可以替换成真实 Spring Boot 服务和数据库。

### 19. 怎么讲“为什么测试中不用真实模型”

可以这样回答：


### 29. 面试常见问题：你怎么保证 AI 不乱调用工具？

可以回答：

```text
我把工具调用权限放在后端，而不是交给模型。

模型或规则可以提出工具意图，但真正执行前后端要检查工具名是否注册、参数是否符合 schema、用户是否具备权限、是否是写操作、写操作是否已获得用户确认。

比如 create_ticket 是写操作，必须经过字段提取、缺字段追问、用户确认和 authorize_tool_call 后才会调用 Java 服务，而且会带幂等键防止重复创建。
```

### 30. 面试常见问题：模型输出格式错了怎么办？

可以回答：

```text
模型输出先经过 JSON 解析，再经过 Pydantic 校验。Pydantic 会限制字段类型、枚举值、必填字段、多余字段和业务格式，比如订单号格式。

如果校验失败，不会把结果直接写入业务状态，而是分类成模型输出失败，再根据失败类型决定 fallback、追问、提示重试或暴露配置错误。
```

### 31. 面试常见问题：怎么评测 Agent？

可以回答：

```text
我把 Agent 评测拆成多层，而不是只看最终回答。

意图识别评测判断用户问题应该进入哪个业务分支。
字段提取评测判断工单字段是否提取正确。
路由评测判断 LangGraph 节点路径是否符合预期。
RAG + Agent 组合评测判断知识库回答、引用来源、无上下文拒答和工单决策。

评测结果会生成报告，失败样本会进入 bad case analysis，关键样本会进入 regression，后续改 prompt 或代码时防止退化。
```

### 32. 面试常见问题：为什么不用真实模型跑所有测试？

可以回答：

```text
真实模型输出有不确定性，而且有成本、网络和密钥风险。自动化测试更适合使用 fake LLM 和规则 evaluator 验证确定性边界。

真实模型适合在单独 smoke、离线 eval 或人工验收中验证。当前项目通过 rule_based / fake_llm / real_llm 三种模式把这两个需求分开。
```

### 33. 面试常见问题：如果 Java 服务挂了怎么办？

可以回答：

```text
工具节点会捕获和分类 Java 服务错误，比如 404、超时、5xx、结果校验失败。不同错误对应不同策略：订单不存在不可重试，超时和 5xx 可以按策略重试，结果校验失败要安全兜底。

在更生产化的设计里，还会配合 timeout、retry、rate limit、circuit breaker 和 degradation，避免 Java 服务故障拖垮 Agent。
```

### 34. 面试常见问题：你怎么排查一次请求为什么失败？

可以回答：

```text
先拿 trace_id 定位这次请求，再看 trace 中经过哪些 span，比如意图识别、RAG 检索、工具调用、字段提取、创建工单。

如果是单个节点异常，看结构化日志里的 event_name、error_code、node_name、thread_id、fallback_used、retry_count 等字段。

如果是整体趋势，比如延迟升高或成本上升，看 metrics 里的请求耗时、模型 token、调用次数、错误率和依赖失败率。
```

### 35. 面试常见问题：当前项目最大的工程收获是什么？

可以回答：

```text
最大的收获是理解了 AI 应用不是只调模型，而是要把模型放进一个有边界的工程系统。

模型负责理解和生成，但后端必须负责结构化校验、权限控制、工具执行、状态管理、评测、可观测性和稳定性保护。

阶段 6 让我把“能跑”升级到“能验证、能排查、能兜底、能持续迭代”。
```

要求：

不要超过 60 字。

参考答案：

```text
阶段 6 的目标是把能运行的 RAG + 智能工单 Agent，推进成可评测、可追踪、可兜底、可编排、可回归的工程化雏形。
```

### 练习 2：说出 demo 和可上线雏形的区别

参考答案：

```text
demo 主要证明功能能跑通，通常只覆盖少量正常路径；可上线雏形除了功能能跑，还要有评测、测试、错误处理、状态管理、日志追踪、稳定性策略、部署编排和自动回归等工程保障。
```

### 练习 3：为什么 AI 应用不能只靠普通单元测试？

参考答案：

```text
因为 AI 应用存在模型理解、生成和格式输出的不确定性。单元测试适合验证确定性代码边界，但 AI 效果还需要 eval dataset、evaluator、报告、坏例分析和回归评测来判断意图、字段、路由、引用和最终回答是否符合预期。
```

### 练习 4：解释 fake_llm 和 real_llm 为什么都需要

参考答案：

```text
fake_llm 用来做稳定、低成本、可重复的自动化测试，验证 JSON 解析、Pydantic 校验、节点分支和错误处理。real_llm 用来验证真实模型在实际语言理解和字段提取上的效果。两者分开，既能接近真实能力，又不会让 CI 依赖真实模型。
```

### 练习 5：解释模型输出为什么要经过 Pydantic

参考答案：

```text
模型输出可能不是合法 JSON，也可能字段类型、枚举值、必填字段或业务格式不符合要求。Pydantic 相当于模型输出进入业务系统前的结构化边界，只有通过校验的数据才能进入 Agent 状态或工具调用链路。
```

### 练习 6：解释写操作为什么必须确认

参考答案：

```text
写操作会改变业务系统状态，比如创建工单。模型只能判断用户可能想创建工单，但不能替用户授权。必须由后端确认字段完整、权限允许，并得到用户明确确认后才执行，同时最好带幂等键防止重复提交。
```

### 练习 7：用自己的话解释 checkpoint 和 thread_id

参考答案：

```text
thread_id 是一条多轮对话或任务流程的标识，用来找到同一个流程。checkpoint 是这个流程在某个时间点保存的状态快照。thread_id 更像索引，checkpoint 更像数据内容。
```

### 练习 8：说明 trace、span、log、metrics 的区别

参考答案：

```text
trace 表示一次请求的完整链路，span 表示链路中的一个步骤，log 记录某个时间点发生的事件，metrics 观察一段时间内的整体趋势，比如延迟、错误率、token 和成本。
```

### 练习 9：为什么 timeout、retry、熔断和降级要配合使用？

参考答案：

```text
timeout 防止无限等待，retry 处理临时失败，熔断在上游持续失败时快速失败保护系统，降级在主能力不可用时提供较低质量但安全的服务。它们解决的是不同层面的稳定性问题，不能互相替代。
```

### 练习 10：用 1 分钟讲当前项目

参考答案：

```text
这是一个 Java + Python 的 AI 客服工单项目。Python FastAPI 负责 LLM、RAG 和 LangGraph Agent，Java mock service 模拟订单查询和工单创建。系统能基于知识库回答客服政策问题，也能识别用户意图、查询订单、收集工单字段，并在用户确认后创建工单。后续补了 Agent 评测、真实模型节点、Pydantic 输出校验、工具安全、checkpoint/thread_id、可观测性、成本指标、稳定性策略、Docker Compose 和 CI 自动回归，所以它不是简单调模型 API，而是一个有工程边界的 AI 应用雏形。
```

## 十、自测问题

### 自测 1：阶段 6 为什么不是只学 Docker 或 tracing？

答案：

```text
因为生产化是一个系统能力，不是单点技术。Docker 只解决本地编排和启动问题，tracing 只解决链路观察问题。阶段 6 还包括 AI 效果评测、真实模型接入、结构化校验、工具安全、状态生命周期、日志指标、成本、timeout、retry、限流、熔断、降级、readiness 和 CI 回归。
```

### 自测 2：为什么 Agent 要评测中间节点？

答案：

```text
Agent 是多步流程，最终回答错误可能来自意图识别、字段提取、RAG 检索、工具调用、路由分支或最终总结。只评最终回答难定位问题，评测中间节点可以更快发现错误发生在哪一层。
```

### 自测 3：为什么规则 evaluator 仍然有价值？

答案：

```text
规则 evaluator 稳定、便宜、可重复，适合 CI 和结构化任务，比如意图、字段、路由、引用来源等。它不能覆盖所有开放式质量判断，但在当前阶段很适合做核心回归。
```

### 自测 4：为什么 prompt 版本要记录？

答案：

```text
prompt 会影响模型行为，和代码一样可能引入退化。记录 prompt_name 和 prompt_version，可以让评测报告、日志和线上问题关联到具体 prompt，便于回滚、对比和排查。
```

### 自测 5：工具调用链路中，模型和后端分别负责什么？

答案：

```text
模型负责理解用户意图、提出可能需要调用的工具和参数。后端负责工具注册、工具名校验、参数 schema 校验、权限判断、用户确认、真正执行工具、结果校验、错误分类和状态写回。
```

### 自测 6：为什么 readiness 失败应该返回 503？

答案：

```text
503 表示服务暂时不可用。readiness 检查的是服务是否准备好接收真实请求，如果关键配置或依赖不满足，返回 503 可以让编排系统或调用方知道暂时不要把流量打进来。
```

### 自测 7：为什么 CI 不应该依赖真实 API Key？

答案：

```text
真实 API Key 有安全风险，真实模型调用也有成本、网络和输出不稳定问题。CI 应该优先跑确定性测试和稳定回归，真实模型验证可以放在单独 smoke 或受控评测流程中。
```

### 自测 8：如果面试官问“你项目还有什么没做”，怎么答更好？

答案：

```text
应该具体回答当前边界，比如还没有真实认证授权、真实数据库、生产监控告警、线上部署、压测、更大规模真实 eval dataset 和完整前端工作台。这样比笼统说“还不完善”更可信，也说明自己知道后续工程方向。
```

### 自测 9：阶段 6 最重要的学习转变是什么？

答案：

```text
从“我能把 AI 功能写出来”，转向“我能让 AI 功能可评测、可控制、可追踪、可恢复、可兜底、可部署、可持续迭代”。
```

### 自测 10：下一阶段为什么适合做作品整理？

答案：

```text
因为项目已经有 Python、Java、RAG、Agent、评测和生产化基础，但这些能力需要被整理成别人能看懂的 README、架构图、演示流程、截图、简历描述和面试讲稿。作品整理能把学习成果转化成可展示成果。
```

## 十一、本节总结

阶段 6 到这里完成。

这一阶段最重要的不是某一个库。

也不是某一个接口。

而是你开始理解：

```text
AI 应用开发不是只把模型接进来。
```

真正的 AI 工程要考虑：

```text
质量评测
真实模型接入
输出结构化边界
工具调用安全
写操作确认
状态保存和恢复
会话生命周期
可观测性
成本和延迟
超时和重试
限流和熔断
降级
本地编排
就绪检查
CI 自动回归
```

你现在应该能把这个项目讲成一条完整主线：

```text
从 FastAPI 接口开始，
接入 LLM，
通过 RAG 解决企业知识库问答，
通过 Tool Calling 和 Java mock service 连接业务系统，
通过 LangGraph 把多步骤 Agent 流程组织起来，
再通过阶段 6 的评测和生产化设计让它变得可验证、可追踪、可恢复、可兜底、可编排、可回归。
```

这就是阶段 6 的收获。

下一阶段建议进入：

```text
M6：作品整理和面试准备
```

重点不是继续写很多新功能，而是把已有项目整理成：

```text
别人打开 GitHub 能看懂。
你自己能完整演示。
面试时能讲清楚。
简历上能写准确。
后续继续扩展有路线。
```
