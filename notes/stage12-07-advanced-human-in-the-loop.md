# M12 第 7 节：高级 Human-in-the-loop（人工参与闭环）

## 本节定位

前面已经学习了 Agent 的状态机、执行循环、记忆、Checkpoint 和异步任务。它们让系统可以在等待状态中暂停并恢复。现在要解决一个非常现实的问题：当任务涉及高风险、信息不完整、价值判断、合规要求或模型不确定性时，**谁有权决定下一步？**

答案不应是“让模型再想一次”，也不应简单理解为“让用户点一下确认”。企业 Agent 中的人工参与（Human-in-the-loop，HITL）是一套明确的控制机制：

```text
系统识别需要人工的条件
-> 将任务暂停到可审计等待态
-> 向合适的人展示足够、但不过度的信息
-> 人批准、拒绝、修改、补充或接管
-> 系统验证决策对象、权限、时效和版本
-> 恢复、终止或改道执行
```

HITL 的目的不是否定自动化，而是把人类判断放在真正需要的位置，让低风险、可验证的部分继续自动化，让高影响部分有可追责的控制点。

## 本节学习目标

学完后，你应当能：

1. 区分用户确认、业务审批、人工复核、人工接管和人工标注。
2. 判断哪些 Agent 动作应自动执行、需要确认、需要审批或必须人工处理。
3. 设计与具体任务、动作、参数、版本和时效绑定的确认/审批对象。
4. 解释批准、拒绝、修改、补充信息和超时分别应如何影响任务状态。
5. 理解人工参与与权限、幂等、Checkpoint、异步恢复之间的关系。
6. 避免“形式上有确认、实际上可被绕过”以及“什么都找人审核”的两种极端。
7. 为一个客服/业务 Agent 设计可用的风险分级与人工介入流程。

## 一句话先讲透

> Human-in-the-loop 的核心不是让人替模型按按钮，而是把高风险决策变成一个有明确对象、权限、依据、有效期和审计记录的状态机事件；人决定是否放行或如何修改，系统仍负责执行边界和副作用控制。

## 基础知识铺垫

### 1. 自动化不是二选一：自动或人工之间有很多层

人们常把系统分成“全自动”和“人工处理”，但实际 Agent 可按自主性分层：

| 层级 | 系统能力 | 人的角色 | 例子 |
| --- | --- | --- | --- |
| L0：只展示 | 系统只提供信息 | 人完全决策 | 展示相关政策与订单事实 |
| L1：给建议 | Agent 给出建议/草稿 | 人决定并执行 | 推荐工单分类，由客服提交 |
| L2：先确认后执行 | Agent 准备动作 | 人批准/拒绝 | 创建工单前由用户确认 |
| L3：自动执行可回看 | 低风险操作自动完成 | 人抽查、纠错 | 自动生成工单草稿、自动分类 |
| L4：受限自主 | 在明确预算和权限内连续执行 | 人处理例外 | 只读调查、低风险信息整合 |

成熟系统会按动作类型、数据敏感度、影响范围、错误可逆性和模型置信度选择层级，而不是追求“自主越高越先进”。

### 2. Human-in-the-loop 的五种不同形态

它们都叫“人参与”，但解决的问题不同。

| 形态 | 谁参与 | 人做什么 | 示例 |
| --- | --- | --- | --- |
| 用户确认（user confirmation） | 请求发起人 | 同意或拒绝与自己相关的动作 | “是否创建这张客服工单？” |
| 业务审批（approval） | 有特定职责的人 | 审核合规、金额、风险或资源使用 | 主管批准大额退款 |
| 人工复核（review） | 专家/客服/审核员 | 检查 Agent 结论是否准确 | 法务复核合同风险摘要 |
| 人工接管（handoff/takeover） | 人工处理者 | 停止或暂停 Agent，自行继续处理 | 高风险投诉转人工客服 |
| 人工标注/反馈（annotation/feedback） | 运营、专家或用户 | 为改进系统提供标签、纠错 | 标记某回答引用错误 |

把它们混用会带来权限和体验问题。例如用户有权确认“创建自己的工单”，但未必有权批准“修改组织政策”；审核员可以复核结果，但不一定应代替用户授权数据使用。

### 3. 为什么模型自我检查不能替代人工审批

模型可以被要求“在执行前检查风险”，这能作为辅助，但不能成为唯一安全机制：

- 模型对风险的判断不稳定，受上下文和措辞影响；
- 模型无权决定业务授权；
- 模型可能误解规则或遗漏外部事实；
- 用户、监管和审计需要明确的人类责任主体；
- 高影响决策需要可解释、可复核的依据。

模型适合提出“可能需要人工审核”的建议；系统规则决定何时必须进入审核；人类根据职责和证据完成授权；系统再按已批准范围执行。

### 4. 人工参与也需要最小权限原则

并非“人”就可以看到全部数据、批准所有任务。人工参与者也应被限制在：

- 合适的租户、团队、地区、业务线；
- 与其角色匹配的审批权限；
- 处理当前决策真正需要的最小信息；
- 有效的时间范围和任务范围；
- 可审计的操作路径。

例如法务审核合同风险，不必看到用户完整支付信息；客服主管可批准某类优惠，但不应能直接修改系统权限；普通用户只能确认自己发起的动作。

HITL 扩大了系统参与者，也必须扩大权限治理，而不是绕过它。

### 5. 人工参与的成本与价值

人工审核会增加延迟、人力成本和流程摩擦，但也可能显著降低严重错误、合规事故和不可逆损失。设计时要比较：

```text
自动执行错误的影响
vs
等待人工的成本、延迟和审核准确性
```

低风险、可撤销、规则清晰的动作可自动化；高金额、强合规、影响多人、难以撤销或模型不确定的动作应提高人工参与等级。

目标不是“审核越多越安全”。审核过载会导致审核员疲劳、机械点击通过，最终形成一种看似安全、实则失效的流程。

## 本节主题系统讲解

### 1. 风险分级：决定何时介入的第一张表

设计 HITL 前，应先将动作按风险分类。可参考以下维度：

| 维度 | 要问的问题 |
| --- | --- |
| 影响范围 | 影响一个用户、一个团队还是大量客户？ |
| 可逆性 | 错误后能否可靠撤销或补偿？ |
| 财务影响 | 是否涉及金额、账务、资源消耗？ |
| 敏感性 | 是否处理隐私、机密、受监管数据？ |
| 权限性质 | 是否改变权限、角色、访问范围？ |
| 规则明确度 | 能否用确定规则验证，还是需要专业判断？ |
| 模型/数据不确定性 | 证据是否充分、冲突或过期？ |
| 用户预期 | 用户是否清楚动作会发生什么？ |

将维度映射为动作策略：

| 风险级别 | 典型动作 | 推荐控制 |
| --- | --- | --- |
| 低 | 只读查询、摘要、分类草稿 | 自动执行，记录审计 |
| 中低 | 创建草稿、建议回复、低影响通知 | 自动执行或事后抽查 |
| 中 | 发送对外消息、创建工单、修改非关键字段 | 请求用户确认或规则校验 |
| 高 | 退款、权限调整、合同承诺、批量修改 | 具备角色的人工审批 |
| 极高 | 支付、法律结论、敏感数据导出、不可逆删除 | 多级审批、强验证或不交给 Agent |

这是产品与风控规则的共同产物，不应只由提示词中一句“重要操作请确认”来定义。

### 2. 确认/审批对象必须绑定什么

一个安全的确认不能只是前端传来 `confirmed=true`。它至少应绑定：

```text
confirmation_id / approval_id
task_id
action_type
action_parameters_digest 或受控参数快照
business_object_ids
requester / required_approver_role
created_at / expires_at
task_state_version 或 action_version
decision = pending / approved / rejected / expired / consumed
actor_id / actor_role
reason / comment（可选）
```

为什么要绑定参数摘要或版本？

```text
用户批准：为订单 A1001 创建普通优先级工单
之后模型/程序把订单改成 A1002，或优先级改成紧急
```

若确认只绑定任务 ID，不绑定具体动作内容，旧确认可能被错误用于新动作。正确做法是：动作变化后旧确认失效，必须重新确认。

### 3. 确认内容应该展示什么

人无法对模糊动作做有意义的批准。确认界面或通知至少要让参与者看懂：

1. **要做什么**：创建工单、发送邮件、修改哪项信息。
2. **对谁/什么做**：订单、账户、合同、文件、收件人。
3. **为什么建议这么做**：简短依据和相关事实。
4. **会产生什么影响**：是否对外可见、是否扣费、是否可撤销。
5. **可选择什么**：批准、拒绝、修改、要求补充、转人工。
6. **有效期**：什么时候过期，过期后如何处理。

示例：

```text
建议动作：创建客服工单
对象：订单 A1001
依据：订单归属已验证；物流 72 小时无更新
预计影响：将创建一张普通优先级物流问题工单，不会自动退款
请选择：确认创建 / 暂不创建 / 修改说明 / 转人工客服
有效期：30 分钟
```

这比“是否确认操作？”安全得多，也更符合知情同意。

### 4. 人工决策的状态机

一个审批对象自身也有状态机，不应只作为任务的一段文本：

```text
PENDING
  -> APPROVED
  -> REJECTED
  -> EXPIRED
  -> CANCELLED
  -> CONSUMED（已被用于实际动作）
```

任务状态与审批状态之间常见关系：

| 任务状态 | 审批状态 | 合理后续 |
| --- | --- | --- |
| `WAITING_HUMAN` | `PENDING` | 等待决定 |
| `WAITING_HUMAN` | `APPROVED` | 经过校验后恢复运行 |
| `WAITING_HUMAN` | `REJECTED` | 结束、生成替代方案或转人工 |
| `WAITING_HUMAN` | `EXPIRED` | 过期终止、要求重新确认或转人工 |
| `RUNNING` | `CONSUMED` | 已使用批准执行指定动作，不得重放 |

审批状态不等于任务状态。一个批准可以让任务恢复，但任务仍可能因工具失败而未完成；一个任务成功也不意味着审批记录可以被删除，它可能需要长期审计。

### 5. 批准、拒绝、修改、补充、接管的不同后果

#### 5.1 批准（approve）

批准的含义应当是：在当前有效期、当前版本、当前参数范围内，允许系统执行已描述动作。批准后不是直接让模型自由运行，而是：

```text
验证批准身份和对象
-> 标记批准已生效
-> 恢复任务
-> 系统仍做执行前权限、状态、预算与幂等校验
-> 仅执行被批准的范围
```

#### 5.2 拒绝（reject）

拒绝不一定等于任务失败。可能有几种产品策略：

- 不执行写操作，但给用户提供说明，任务成功结束；
- 转为替代低风险路径；
- 直接取消任务；
- 转人工客服继续沟通。

例如用户拒绝创建工单，Agent 可以回答“已不创建工单；你仍可稍后在订单页发起服务请求”。这可以是一次成功完成的交互，而非系统错误。

#### 5.3 修改（modify）

人工可能不接受原动作，但愿意修改参数，例如将工单优先级从紧急改为普通，或修改通知收件人。修改意味着新的动作版本：

```text
原待执行动作 v1：创建紧急工单
人工修改为 v2：创建普通工单
原确认失效 / 新决策直接绑定 v2
```

不要把修改后的参数悄悄写回旧动作并沿用旧确认，否则审计和授权对象不一致。

#### 5.4 补充信息（request more information）

审核人或用户可能要求更多证据：例如“请先确认是否已有同类工单”。任务可以回到 `RUNNING`，但动作空间应被限制为补充调查，不可趁机执行原写动作。

#### 5.5 人工接管（take over）

接管意味着人不只是对一个动作表态，而是成为后续处理责任主体。系统应：

- 停止或冻结 Agent 的自动后续动作；
- 保存当前 checkpoint、事实、建议和未完成项；
- 分配到人工工作台；
- 标注责任转移和可见权限；
- 明确何时可重新交回 Agent，以及是否需要新的任务/确认。

### 6. 确认的有效期、一次性与重放防护

确认是授权凭证，天然需要防重放（replay）。主要规则：

1. **短有效期**：状态、价格、权限可能变化，确认不应永久有效。
2. **一次性消费**：同一批准不能用于重复执行写操作。
3. **精确绑定**：绑定任务、动作类型、参数版本和资源对象。
4. **身份校验**：不能只凭一个可猜测的 URL 或前端字段；要验证登录身份/角色。
5. **状态校验**：任务取消、终态、过期或动作变更后，确认应失效。
6. **审计留痕**：记录批准人、时间、来源、设备/渠道（按需要）和理由。

例如创建工单的确认一旦已被消费，即使客户端重复提交“确认”请求，系统也应返回已有结果或安全拒绝，不能创建第二张工单。

### 7. 人工审核队列与分配策略

当不只是用户本人确认，而是内部审核人员处理大量任务时，需要一个人工工作队列。它与技术消息队列不同，关心的是人力分配和处理体验。

可按以下因素路由：

- 业务类型：财务、法务、客服、安全；
- 租户、地区、语言；
- 金额、风险等级、SLA；
- 审核人资质和权限；
- 当前负载与在线状态；
- 是否需要双人复核。

审核队列也要防止两个人同时处理同一事项。可采用“领取审核任务”的租约或锁，并允许超时释放。审核人看到的页面应基于当前版本；若他提交时对象已被别人处理，应明确提示冲突，而非悄悄覆盖。

### 8. 升级与降级：人工不是唯一出口

HITL 设计需要定义升级（escalation）和降级（de-escalation）。

**升级到人工的触发条件**可能是：

- 高风险动作；
- 证据冲突或模型低置信；
- 多次工具失败；
- 用户明确要求人工服务；
- 发现疑似诈骗、敏感内容或合规风险；
- 多次自动路径无进展；
- 超过金额/影响阈值。

**从人工降级/交回自动化**应更谨慎：

- 人已完成关键判断，剩余只是低风险自动步骤；
- 人明确选择“继续由系统执行”；
- 系统重新评估权限、任务版本和待执行动作；
- 高风险授权仍必须绑定具体动作。

不应因为人工长时间未响应，就让 Agent 自动执行原本必须审批的高风险操作。超时通常意味着过期、提醒、升级或取消，而不是默认批准。

### 9. 审批阈值和规则要可配置、可解释

实际业务中，规则会变化：金额阈值、可自动执行的动作、不同租户的政策、节假日策略、角色层级等。将全部阈值写死在 prompt 或散落 if/else 中，维护风险很高。

一个更好的思路是将规则作为受版本控制的策略：

```text
动作：退款
金额 <= 100 且风险评分低：自动执行/事后审计
100 < 金额 <= 1000：主管审批
金额 > 1000 或风险评分高：双人审批 + 人工处理
```

Agent 可以读取“当前动作需要哪类审批”的结果，但不应自行改写规则。任务 checkpoint 可记录当时使用的策略版本，便于未来审计“为什么这次需要审批”。

### 10. 置信度不能单独决定是否人工审核

模型可能输出一个“置信度 0.95”，但这个数字通常不具备可校准的业务含义。即使模型很自信，也可能在关键事实上出错；即使模型不自信，规则也可能足够确定。

是否介入应综合：

```text
动作风险
+ 数据来源与证据质量
+ 业务规则明确度
+ 用户影响
+ 模型不确定性
+ 异常/冲突信号
```

模型置信度可作为一个弱信号，例如“建议复核”，但不能作为高风险写操作的唯一放行条件。

### 11. 人工界面需要什么信息，而不只是一个按钮

一个糟糕的审核界面只显示“Approve / Reject”。审核人不知道背景，只能凭习惯点击。一个可用的工作台应提供：

- 任务目标与当前状态；
- 待批准动作的清晰摘要；
- 已验证的关键事实和来源；
- 模型建议与不确定项；
- 对用户/业务的预计影响；
- 当前策略规则和触发原因；
- 可选操作：批准、拒绝、修改、请求补充、转交、接管；
- 过期时间、优先级、SLA；
- 历史状态转移和审计摘要。

同时遵循最小披露：审核人只看到完成审核必需的信息，不把全部模型上下文、其他用户数据或内部密钥暴露出来。

### 12. 人工纠错如何回流为系统改进

人工参与不仅用于放行，还可产生高价值反馈：

```text
Agent 建议：工单分类为 logistics，优先级 urgent
人工修改：分类为 refund，优先级 normal
原因：用户实际询问退款时效，不是物流异常
```

这种反馈可用于：

- 发现 prompt、分类规则、RAG 或工具选择问题；
- 构建评估数据集和 Bad Case；
- 优化人工路由规则；
- 训练/微调（若后续确有合规数据与需求）；
- 改进审核界面和说明内容。

但不能把每次人工修改直接自动写成全局规则。需要统计、评估、审核和版本化，防止个案被过度泛化。

### 13. 人工介入的审计字段

高质量审计不只是保留“approved=true”。应能回答谁、对什么、根据什么、在什么版本下做了什么决定。

概念上可记录：

```text
approval_id
task_id
action_id / action_version
decision
actor_id / actor_role
occurred_at
reason/comment
evidence_refs
policy_version
before_snapshot_digest
after_snapshot_digest（如有修改）
channel
trace_id
```

审计记录不一定都要暴露给普通用户，但应在合适权限下可查询、不可被随意篡改，并有明确保留策略。

### 14. 多人审批与职责分离

极高风险操作可能要求两人或不同角色审批，例如：

```text
发起人：业务负责人
一级审批：财务主管
二级审批：风控/合规
执行人：系统或独立操作员
```

这种职责分离（segregation of duties）用于避免一个人同时提出、批准和执行高风险动作。设计时要明确：

- 是否必须按顺序审批；
- 谁能拒绝；
- 修改后是否需重新走全部审批；
- 一人审批超时如何处理；
- 代理审批/代班如何授权；
- 最终执行是否还需重新核验状态。

Multi-step approval 不是所有 Agent 项目都需要，但理解它能帮助你判断何时单一确认已不足够。

### 15. 人工参与与 Agent 记忆的边界

人工批准/拒绝是强审计事实，不应仅作为普通聊天记忆；它应进入审批记录、任务 checkpoint 和必要的业务审计。人工反馈中可以提炼经验，但必须区分：

| 信息 | 应存放位置 |
| --- | --- |
| “本次动作已批准” | 审批对象 + 任务状态 |
| “用户偏好先确认再创建工单” | 用户偏好记忆（若用户明确设置） |
| “此类动作通常需主管审批” | 版本化策略规则 |
| “审核人修改了分类，原因是…” | 反馈/评估数据集 |

将审批结论随意写入长期记忆，可能导致它被错误复用于另一个任务或另一个对象。

### 16. 一个完整走读：高风险退款申请

用户提出退款请求。系统设计规则：金额低且条件明确可自动处理；中等金额需主管审批；高风险或争议情况转人工客服。

#### 第一步：自动调查

Agent 在只读权限内查询订单、付款、履约、退款政策。所有工具结果经过权限和字段过滤，形成 observation。

#### 第二步：风险评估与路由

系统规则计算：退款金额 650，处于“主管审批”区间；同时订单存在争议标记。任务不能直接调用退款工具。

```text
RUNNING -> WAITING_HUMAN
pending_action = refund(order=A1001, amount=650, reason=...)
required_role = refund_supervisor
expires_at = ...
```

#### 第三步：主管审核

主管看到订单事实、政策依据、争议标记、金额和 Agent 建议。主管可：批准、拒绝、将金额改为部分退款、要求补充调查、转人工客服。

#### 第四步：批准后恢复

若批准的是“部分退款 300”，系统创建新的动作版本和审批记录。恢复任务时仍要检查订单状态是否变化、权限是否有效、批准是否未过期。然后使用幂等键执行退款。

#### 第五步：结果与审计

退款系统返回真实交易引用后，任务更新为成功；用户收到清晰说明。若退款调用超时，任务进入结果未知对账流程，而不是因为“主管已经批准”就反复扣款。

这个例子说明：人工审批授权的是具体风险动作，但不能替代系统对外部执行结果、幂等和状态一致性的控制。

### 17. 如何衡量 HITL 是否健康

人工流程既可能降低风险，也可能成为瓶颈。可观察：

| 指标 | 代表的问题 |
| --- | --- |
| 人工介入率 | 是否把太多低风险工作升级了 |
| 批准/拒绝/修改比例 | Agent 建议质量与规则合理性 |
| 审批等待时长 | SLA、人员容量、通知机制 |
| 过期率 | 审批是否太慢或有效期不合理 |
| 人工接管率 | 自动路径是否经常无法解决问题 |
| 复核后纠错率 | 模型结论、检索或工具是否存在系统性问题 |
| 重放/冲突拒绝次数 | 确认对象和并发控制是否有效 |
| 审核员负载分布 | 是否存在某角色被压垮 |

不能只追求“人工介入率下降”。若下降是因为系统错误地放宽了高风险动作，会比审核多更危险。指标必须结合风险事件、用户体验和业务质量解释。

### 18. 从最小可用到成熟 HITL 的建设顺序

1. 明确哪些动作属于写操作或高风险，禁止模型直接执行。
2. 为一个最典型的动作建立用户确认：任务、动作、参数、有效期、一次性消费。
3. 将确认接入状态机与 checkpoint：`RUNNING -> WAITING_HUMAN -> RUNNING`。
4. 加入角色权限、审批工作队列和可审计操作记录。
5. 支持拒绝、修改、补充信息和人工接管，而不只支持批准。
6. 按风险分级和策略版本扩展到更多动作。
7. 建立人工反馈到评估/改进的闭环。
8. 对极高风险场景再引入多级审批、职责分离、抽检与合规控制。

先把一个动作做成真正不可绕过的闭环，比在许多地方放很多没有绑定对象的“确认按钮”更有价值。

## 常见误区

### 误区 1：Human-in-the-loop 就是在前端弹出“确认吗”

若确认未绑定具体任务、参数、有效期、身份和一次性使用规则，用户只是点了一个模糊按钮，无法形成可靠授权。HITL 是状态和权限控制，不是 UI 装饰。

### 误区 2：模型置信度高就不需要人工审核

模型置信度不等于业务风险或法律授权。高影响动作仍应由风险、权限、可逆性和策略规则决定是否介入。

### 误区 3：人工批准后就可以跳过所有后端校验

批准只允许特定范围内的动作；执行前仍需检查当前权限、资源状态、预算、取消标记和幂等。批准不是万能通行证。

### 误区 4：拒绝意味着任务失败

拒绝可能只是选择了“不执行该动作”。系统可以提供替代方案、结束交互或转人工，而不是把它视为技术错误。

### 误区 5：所有不确定都交给人工

这会造成审核过载、延迟和机械批准。应先用确定性规则、只读调查、结构化信息收集和低风险自动化解决可处理部分，再把真正需要人类价值判断的点升级。

### 误区 6：用户消息里说“我同意”就能恢复高风险任务

自然语言可能歧义、被伪造、与多个待确认动作不匹配。应通过明确 confirmation ID、身份验证、参数版本和状态校验完成批准。

### 误区 7：人工反馈可以直接成为全局 Agent 规则

单次人工修改可能是个案。应先进入评估/反馈体系，经统计、审核和版本化后再影响通用策略或提示词。

## 本节练习

### 练习 1：给动作分级

请为下列动作选择“自动执行、用户确认、角色审批、必须人工处理”中最合适的一种，并说明理由：

1. 查询当前用户自己的订单状态。
2. 为用户创建一张普通客服工单。
3. 为用户发起 2000 元退款。
4. 删除组织内所有历史合同文件。

答案：1 通常可自动执行，但仍需权限校验。2 通常需要用户确认，因它会创建业务记录和后续处理成本。3 通常需要具备角色的审批，可能还需多级审核，金额和风险较高。4 应视为极高风险，不应由普通 Agent 自动处理，需严格人工流程、多重验证和可能的变更管理。

### 练习 2：指出确认设计缺陷

某接口只接收 `{ "task_id": "task_123", "confirmed": true }`，并据此执行任务中任何待处理写操作。请指出至少三个问题。

答案：它没有绑定具体动作和参数，任务内容变化后旧确认仍可被使用；没有确认人身份/角色和有效期；没有一次性消费机制，重复请求可能重复执行；也缺少任务当前状态/版本校验，取消或终态任务可能被错误恢复。

### 练习 3：审批后参数被修改

主管已批准“为 A1001 退款 300 元”，随后 Agent 因新信息建议退款 500 元。能否直接用原批准执行？

答案：不能。金额和动作参数已改变，原批准只覆盖 300 元的特定动作版本。系统应创建新动作版本并重新走适用审批流程，不能把旧批准扩大解释。

### 练习 4：审批超时策略

一个高风险操作等待审批 24 小时后仍无人处理。为什么不应默认批准？可以有哪些合理处理？

答案：默认批准会把“无人响应”错误当成授权，尤其高风险动作会造成严重后果。可将审批标记过期，提醒/升级到后备审核人，转人工队列，取消任务或要求用户重新发起；具体取决于业务 SLA 和风险规则。

## 自测题

### 自测 1：用户确认和角色审批的本质差异是什么？

答案：用户确认通常表示请求发起人同意与自己相关的某个动作；角色审批表示具备业务职责和权限的人员对合规、金额、风险或组织资源作出授权。两者的参与者、权限依据和审计要求不同。

### 自测 2：为什么确认必须绑定动作参数或版本？

答案：因为任务在等待期间可能发生重规划、对象变化或参数升级。若只绑定任务 ID，原本对低风险/小金额动作的批准可能被错误用于不同对象或更高风险动作。绑定参数摘要和版本保证授权对象明确。

### 自测 3：人工接管时系统应做什么？

答案：冻结或停止 Agent 的自动后续动作，保存当前 checkpoint、事实和未完成项，按权限将任务分配给人工处理者，记录责任转移，并明确何时、以什么条件可重新交回自动化。接管不是只给模型多一段人类留言。

### 自测 4：为什么审批通过后仍要执行前校验？

答案：任务等待期间权限、资源状态、金额、政策、取消状态都可能变化；批准也可能过期或已被消费。执行前校验确保实际发生的动作仍在当前允许范围内，并配合幂等防止重复副作用。

### 自测 5：什么叫“审核疲劳”，如何缓解？

答案：审核疲劳指人工面对大量低价值或信息不足的审批时，逐渐机械点击、降低注意力和判断质量。可通过风险分级、自动化低风险动作、提供清晰证据摘要、合理路由、优先级、抽检和反馈改进来减少无意义审核。

## 本节小结

高级 Human-in-the-loop 是 Agent 安全与责任分配的一部分。它通过风险分级、明确审批对象、身份权限、时效与一次性消费，把“需要人决定”的节点纳入任务状态机；人工可以批准、拒绝、修改、补充或接管，而系统始终保留执行校验、幂等、checkpoint 和审计控制。
