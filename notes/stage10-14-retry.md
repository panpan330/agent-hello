# 阶段 10 第 14 节：重试

## 本节定位

这一节学习生产 AI 应用里的重试。

第 13 节学的是限流：

```text
请求太频繁时，系统主动拒绝。
```

这一节学的是重试：

```text
请求失败后，系统是否应该再试一次。
```

重试看起来很简单，但真实生产里非常容易用错。用对了能提升稳定性，用错了会把一次小故障放大成系统事故。

## 本节学习目标

- 理解什么是重试，为什么重试能提升稳定性。
- 理解临时失败和永久失败的区别。
- 理解哪些错误可以重试，哪些错误不能重试。
- 理解读操作、写操作和幂等性的关系。
- 理解重试次数、重试间隔、指数退避、Retry-After。
- 理解 retry 和 fallback、限流、超时、成本控制的区别和配合方式。
- 看懂本节新增的 `llm_retry.py` 和 LLM service 接入方式。

## 本节新增和修改

- 新增 `app/core/llm_retry.py`。
- 修改 `app/services/llm_service.py`，在 LLM 创建请求阶段加入应用层重试。
- 修改 `app/services/llm_client.py`，关闭 OpenAI SDK 内部重试，让重试由本项目显式控制。
- 修改 `.env.example`，补充 `LLM_MAX_RETRIES` 的说明。
- 新增 `tests/test_llm_retry.py`，补充 LLM service 和 client 测试。

## 一句话先讲透

重试就是：当一次外部依赖调用因为临时原因失败时，系统不要立刻放弃，而是在有限次数、有限间隔、明确错误类型的约束下再试；但参数错误、权限错误、业务拒绝、非幂等写操作不能盲目重试。

## 基础知识铺垫

### 1. 什么是重试

重试的英文是：

```text
Retry
```

它的意思是：

```text
某次调用失败后，再执行一次相同或等价的调用。
```

例如：

```text
第一次调用模型超时。
等 0.2 秒。
第二次再调用同一个模型。
第二次成功，用户就不感知第一次失败。
```

重试的价值是提高系统对临时失败的容忍度。

### 2. 为什么生产系统需要重试

真实系统不是每一次调用都会稳定成功。

常见临时问题包括：

```text
网络抖动
连接短暂失败
模型供应商短暂 5xx
下游服务偶发超时
限流后提示稍后再试
服务实例正在重启
负载均衡把请求打到临时繁忙节点
```

这些问题可能下一秒就恢复。

如果系统没有重试，一次短暂抖动就会变成用户可见失败。

所以重试解决的是：

```text
临时失败不要马上暴露给用户。
```

### 3. 重试为什么也危险

重试不是无脑再来一次。

它会带来额外成本：

```text
多一次模型调用费用
多一次网络请求
多一次下游压力
多一次等待时间
多一次日志和 trace
```

更严重的是，如果下游已经不稳定，所有请求都一起重试，就可能出现：

```text
重试风暴
```

重试风暴的意思是：

```text
下游服务已经扛不住了，上游还不断自动重试，导致压力越来越大。
```

所以重试必须被约束：

```text
只重试可重试错误。
限制最大次数。
重试前等待一小段时间。
尊重 Retry-After。
结合限流和超时。
写操作必须考虑幂等。
```

### 4. 临时失败和永久失败

重试的第一个判断是：

```text
这个失败是不是临时的？
```

临时失败通常可以重试。

例如：

```text
超时
连接错误
网络错误
模型供应商 500/502/503/504
429 且服务端建议稍后再试
```

永久失败通常不能重试。

例如：

```text
API key 错误
没有模型权限
模型名称不存在
请求参数错误
结构化输出 schema 写错
用户没有业务权限
订单不存在
业务规则拒绝
Prompt Injection 被拦截
成本预算超限
```

永久失败的问题不是“刚才运气不好”，而是“再试也大概率还是错”。

### 5. 哪些 LLM 错误可以重试

本节把这些错误作为可重试错误：

```text
LLM_TIMEOUT
LLM_RATE_LIMITED
LLM_PROVIDER_ERROR
LLM_CONNECTION_ERROR
LLM_PROVIDER_STATUS_ERROR
LLM_CALL_FAILED
```

它们对应的是：

```text
超时
供应商限流
供应商服务异常
网络连接失败
供应商返回异常状态
未知临时调用失败
```

这些错误可能是临时性的，所以可以有限重试。

### 6. 哪些 LLM 错误不能重试

本节不重试这些错误：

```text
LLM_AUTHENTICATION_FAILED
LLM_PERMISSION_DENIED
LLM_RESOURCE_NOT_FOUND
LLM_BAD_REQUEST
LLM_COST_BUDGET_EXCEEDED
LLM_EMPTY_RESPONSE
LLM_BAD_RESPONSE
```

原因分别是：

```text
认证失败：API key 配错，再试也不会好。
权限失败：账号没有权限，再试也不会好。
资源不存在：模型名或地址错，再试也不会好。
参数错误：请求构造错，再试只会重复错误。
成本超限：这是系统主动拦截，不应该绕过。
空响应/坏响应：当前先不把它当成同模型重试对象，避免掩盖解析或提示词问题。
```

### 7. 重试和幂等

幂等是重试必须掌握的核心概念。

幂等的意思是：

```text
同一个操作执行一次和执行多次，最终效果一样。
```

例如查询订单：

```text
GET /orders/A1001
```

执行 1 次或 3 次，都是查询同一个订单，不会额外创建数据。

这类读操作通常更容易重试。

但创建工单不同：

```text
POST /tickets
```

如果没有幂等键，第一次其实已经创建成功，只是响应超时了；第二次重试可能又创建一个重复工单。

所以写操作自动重试必须有：

```text
Idempotency-Key
```

或者其他业务去重机制。

本节只给 LLM 创建请求做重试，不提前重试真实写工具。

### 8. 重试次数

重试次数不能无限大。

本项目使用：

```text
LLM_MAX_RETRIES
```

如果配置为：

```text
LLM_MAX_RETRIES=2
```

含义是：

```text
最多额外重试 2 次。
总尝试次数 = 1 次原始调用 + 2 次重试 = 3 次。
```

所以你要区分：

```text
max_retries：额外重试次数。
max_attempts：最多总尝试次数。
```

### 9. 重试间隔和指数退避

如果失败后立刻重试，可能继续撞在下游故障上。

所以重试前通常要等一下。

本节使用简单指数退避：

```text
第 1 次失败后等 0.2 秒。
第 2 次失败后等 0.4 秒。
后续逐步增加，但最多 2 秒。
```

指数退避的作用是：

```text
故障越持续，重试越不要频繁。
```

真实生产里还常加 jitter，也就是随机抖动，避免大量请求同时在同一时刻重试。本节先不加随机抖动，保持教学代码可预测。

### 10. Retry-After

第 13 节限流学过 `Retry-After`。

当模型供应商返回 429，并带上：

```text
Retry-After: 3
```

意思是：

```text
建议 3 秒后再试。
```

本节会读取这个响应头。

但为了避免一次请求等待太久，本项目会做上限保护：

```text
最多等待 2 秒。
```

这是教学项目的保守策略。真实生产中要结合接口 SLA、用户体验和供应商规则调整。

### 11. retry 和 fallback 的区别

retry 是：

```text
同一个模型或同一个依赖再试一次。
```

fallback 是：

```text
换一个模型、换一条路径或换一种降级方案。
```

举例：

```text
retry：qwen-fast 超时后，再请求一次 qwen-fast。
fallback：qwen-fast 仍失败后，改用 qwen-balanced。
```

本节采用的顺序是：

```text
先 retry，再 fallback。
```

原因是：

```text
如果只是网络抖动，同一个模型重试可能就恢复了。
如果同一个模型多次失败，再考虑 fallback。
```

### 12. 为什么 fallback 不再额外重试

如果 primary 模型最多 3 次，fallback 模型也最多 3 次，那么一次请求最多可能 6 次模型调用。

如果还有 Agent Loop、RAG、工具调用，成本和延迟会继续放大。

所以本节设计为：

```text
primary 模型支持应用层重试。
primary 重试耗尽后才进入 fallback。
fallback 仍保持一次尝试。
```

这是为了避免：

```text
retry * fallback
```

把调用次数放大。

后续如果要支持 fallback 也重试，必须结合成本预算、总超时和更完整的调用预算。

### 13. 重试和限流的关系

限流会拒绝高频请求。

重试会增加请求次数。

如果不小心，重试可能把限流打得更严重。

例如：

```text
100 个请求同时收到 429。
每个请求马上重试 2 次。
瞬间变成 300 次请求。
```

所以遇到 429 时要：

```text
尊重 Retry-After。
设置最大重试次数。
不要立刻无限重试。
```

### 14. 重试和超时的关系

超时和重试必须一起看。

如果一次模型调用超时时间是 30 秒，最多重试 2 次，总耗时可能接近：

```text
30 + 0.2 + 30 + 0.4 + 30 = 90.6 秒
```

这对普通接口来说可能太长。

所以后续学习超时治理时，会继续补：

```text
请求总超时
单次调用超时
重试预算
流式首 token 超时
下游工具超时
```

本节先完成重试决策和代码边界。

### 15. 重试和成本控制的关系

重试会增加模型调用次数。

一次请求如果重试 2 次，最坏情况下可能产生 3 次模型调用费用。

第 12 节成本控制是单次调用前的预算预检。

本节没有做完整的“重试累计成本预算”，但已经保留一个重要边界：

```text
成本控制先执行。
成本控制阻断的请求不进入 retry。
高成本请求仍可禁用 fallback。
```

后续做更完整生产化时，可以继续加入：

```text
单请求总调用预算
单用户日预算
租户预算
重试累计 token 预算
```

### 16. SDK 内部重试和应用层重试

OpenAI SDK 本身支持内部重试。

但内部重试的问题是：

```text
业务日志不一定清楚每次重试决策。
不容易和 fallback、成本控制、trace_id 统一。
不容易教学和排查。
```

所以本节修改为：

```text
SDK max_retries = 0
应用层根据 LLM_MAX_RETRIES 显式重试
```

这样你能在日志里看到：

```text
第几次失败
是否重试
为什么重试
下一次尝试是第几次
等待多久
```

这就是生产可观测性的思路。

## 本节主题系统讲解

### 1. 本节在当前 LLM 链路里的位置

现在普通聊天链路变成：

```text
用户请求
-> 选择模型 route_llm_model
-> 构造 messages
-> 成本控制 build_llm_cost_control_decision
-> 创建模型请求 create_completion_with_retry
-> 提取模型回答
-> 成功日志
```

如果创建模型请求失败：

```text
-> 映射成 AppException
-> 根据 error_code 判断是否重试
-> 如果允许重试，等待后再调用同一个模型
-> 如果不允许或次数耗尽，再进入 fallback 判断
```

### 2. 本节只重试模型创建阶段

普通聊天里，模型调用是一次普通请求，所以创建阶段失败可以重试。

流式聊天不同。

流式输出分成两个阶段：

```text
创建 stream 连接
迭代 stream chunk
```

本节只重试：

```text
创建 stream 连接失败
```

不重试：

```text
stream 已经输出一半后失败
```

原因是如果已经给用户输出了部分内容，再重新请求模型，可能造成内容重复、语义断裂，前端也很难合并。

### 3. 本节的错误决策结构

核心对象是：

```text
LLMRetryDecision
```

它记录：

```text
should_retry
reason
error_code
attempt_number
max_attempts
next_attempt_number
next_delay_seconds
```

这比返回 true/false 更适合生产系统。

因为排查时你需要知道：

```text
为什么重试？
为什么不重试？
第几次失败？
还剩没有下一次？
下一次要等多久？
```

### 4. 本节的重试顺序

以 `LLM_MAX_RETRIES=2` 为例：

```text
attempt 1：原始请求
失败，判断是否重试
等待 0.2 秒
attempt 2：第一次重试
失败，判断是否重试
等待 0.4 秒
attempt 3：第二次重试
失败，次数耗尽
进入 fallback 判断
```

注意：

```text
attempt_number 是当前失败的这一次。
next_attempt_number 是准备执行的下一次。
```

### 5. 本节的安全日志

重试日志只记录低敏信息：

```text
operation
model
error_code
attempt
max_attempts
should_retry
reason
next_attempt
next_delay
```

不记录：

```text
用户原文
prompt
messages
API key
模型完整返回
工具参数
```

这延续了前面 LLM 调用日志安全的要求。

### 6. 本节暂时不做什么

本节不做：

```text
写工具自动重试
数据库写操作重试
Redis 分布式重试预算
全链路总耗时预算
重试 jitter
按租户动态重试次数
fallback 模型再次重试
```

这些不是不重要，而是需要和幂等、超时、成本预算、监控告警一起设计。

当前先掌握：

```text
LLM 创建请求的可解释、可控、有限重试。
```

## 本节代码讲解

### 1. `app/core/llm_retry.py`

这个模块只负责重试决策，不负责真实调用模型。

它的核心职责是：

```text
根据错误码、当前第几次尝试、最大重试次数，判断是否应该再试。
```

这样设计的好处是：

```text
重试策略可以单独测试。
LLM service 不需要塞满判断细节。
以后其他 LLM 场景也可以复用。
```

### 2. `RETRYABLE_LLM_ERROR_CODES`

这个集合定义了可重试错误。

当前包括：

```text
LLM_TIMEOUT
LLM_RATE_LIMITED
LLM_PROVIDER_ERROR
LLM_CONNECTION_ERROR
LLM_PROVIDER_STATUS_ERROR
LLM_CALL_FAILED
```

如果错误不在集合里，默认不重试。

这是一种保守策略：

```text
不确定能不能重试时，先不要重试。
```

### 3. `build_llm_retry_decision`

这个函数按顺序判断：

```text
1. attempt_number 是否合法。
2. LLM_MAX_RETRIES 是否为 0。
3. error_code 是否可重试。
4. 当前尝试次数是否已经耗尽。
5. 如果是 429 且有 Retry-After，使用 Retry-After。
6. 否则使用指数退避。
```

它不会直接 sleep，也不会直接调用模型。

它只返回决策。

### 4. `calculate_llm_retry_delay`

这个函数计算重试等待时间。

当前规则：

```text
第 1 次失败后：0.2 秒
第 2 次失败后：0.4 秒
最多：2.0 秒
```

这个值在测试里是确定的，所以测试不会因为随机抖动变得不稳定。

### 5. `extract_retry_after_seconds`

这个函数从异常对象里读取：

```text
response.headers["retry-after"]
```

如果能解析成正数，就返回秒数。

如果没有、不是数字、不是正数，就返回 `None`。

本节只处理最常见的数字秒数格式。

### 6. `llm_client.py`

本节把 OpenAI SDK 的内部重试关闭：

```text
max_retries=0
```

原因是：

```text
本项目要在应用层显式控制重试。
```

这样日志和测试能看到每次重试，而不是由 SDK 在内部悄悄处理。

### 7. `llm_service.py`

新增了：

```text
_create_completion_with_retry
_create_chat_completion_with_retry
_create_stream_completion_with_retry
_log_retry_decision
```

普通聊天调用：

```text
_create_chat_completion_with_retry
```

流式聊天创建阶段调用：

```text
_create_stream_completion_with_retry
```

fallback 仍然调用原来的：

```text
_create_chat_completion
_create_stream_completion
```

也就是说：

```text
primary 支持重试。
fallback 不额外重试。
```

## 关键测试说明

本节关键测试覆盖：

```text
可重试错误在次数未耗尽时允许重试。
429 可以使用 Retry-After，但会被最大等待时间限制。
重试关闭时不会重试。
次数耗尽后不会继续重试。
认证错误等永久失败不会重试。
LLM service 会先重试同一模型。
stream 创建失败可以重试。
SDK 内部重试被关闭。
日志字段不包含 prompt 或用户原文。
```

测试中不会真实调用大模型。

## 常见误区

### 误区 1：失败就应该重试

不对。

只有临时失败适合重试。

认证失败、权限失败、参数错误、业务拒绝不应该重试。

### 误区 2：重试次数越多越稳定

不对。

重试次数越多，成本、延迟、下游压力越大。

超过一定次数后，继续重试只是在放大故障。

### 误区 3：写操作可以像查询一样重试

不对。

写操作必须考虑幂等。

没有幂等键的创建工单、扣款、发短信、改状态，不能盲目自动重试。

### 误区 4：SDK 有重试就不用管了

不对。

SDK 内部重试不一定符合你的业务边界，也不一定方便观测。

生产系统更常见的是在应用层定义清晰策略。

### 误区 5：流式输出中途失败可以直接重试

不能简单这么做。

因为用户可能已经看到部分输出。重新调用模型可能造成重复、冲突或断裂。

本节只重试 stream 创建阶段。

### 误区 6：429 应该马上重试

不应该。

429 表示请求过多。应该根据 Retry-After 或退避策略等待，而不是立刻继续打请求。

## 本节练习

### 练习 1：解释 retry 和 fallback 的区别

参考答案：

```text
retry 是同一个模型或同一个依赖在失败后再试一次。
fallback 是换一个模型、依赖或降级方案。
例如 qwen-fast 超时后再请求 qwen-fast 是 retry；qwen-fast 多次失败后改用 qwen-balanced 是 fallback。
```

### 练习 2：判断哪些错误可以重试

下面哪些适合重试？

```text
1. LLM_TIMEOUT
2. LLM_CONNECTION_ERROR
3. LLM_AUTHENTICATION_FAILED
4. LLM_PERMISSION_DENIED
5. LLM_RATE_LIMITED 且有 Retry-After
6. LLM_BAD_REQUEST
```

参考答案：

```text
1、2、5 适合有限重试。
3、4、6 不适合重试，因为它们通常是配置、权限或参数问题，再试也大概率失败。
```

### 练习 3：为什么写操作重试要考虑幂等键

参考答案：

```text
因为写操作可能已经在下游执行成功，只是响应丢失或超时。
如果没有幂等键，重试可能创建重复工单、重复扣款或重复发送消息。
幂等键能让服务端识别“这是同一次业务请求”，从而返回同一个结果或避免重复执行。
```

### 练习 4：为什么本节关闭 SDK 内部重试

参考答案：

```text
因为本项目希望在应用层显式控制重试，方便结合日志、trace、fallback、成本控制和测试。
如果 SDK 内部也重试，真实总尝试次数会变得不清楚，还可能和应用层重试叠加。
```

### 练习 5：为什么 stream 输出中途失败不重试

参考答案：

```text
因为中途失败时用户可能已经收到部分内容。
如果重新请求模型，可能导致前端看到重复内容、回答断裂或语义冲突。
所以本节只重试 stream 创建阶段，不重试 chunk 迭代阶段。
```

## 自测题

### 自测 1：`LLM_MAX_RETRIES=2` 表示总共尝试几次

参考答案：

```text
最多总共尝试 3 次。
1 次原始调用，加 2 次额外重试。
```

### 自测 2：为什么重试要加等待时间

参考答案：

```text
因为失败可能来自下游短暂繁忙或网络抖动。
如果立刻重试，可能继续失败，还会增加下游压力。
等待时间和指数退避可以降低重试风暴风险。
```

### 自测 3：为什么成本控制阻断的请求不应该重试

参考答案：

```text
因为成本控制阻断是系统主动判断本次请求预算超限，不是临时故障。
重试不会让请求变便宜，反而可能试图绕过预算边界。
```

### 自测 4：为什么认证失败不能重试

参考答案：

```text
认证失败通常表示 API key 缺失、错误或无效。
这不是临时问题，再试也不会恢复，应该修配置而不是自动重试。
```

### 自测 5：为什么重试可能造成事故

参考答案：

```text
重试会增加请求次数、成本和下游压力。
如果下游已经故障，大量上游请求同时重试，会形成重试风暴，把小故障放大成更严重的系统事故。
```

### 自测 6：本节为什么先 retry 再 fallback

参考答案：

```text
因为如果只是同一模型的一次临时网络抖动，同模型重试可能直接恢复。
如果同一模型多次失败，再 fallback 到备用模型更合理。
这样可以区分临时抖动和主模型持续不可用。
```

## 本节小结

这一节你要记住：

```text
重试不是失败后再试这么简单，而是要回答“什么错误、什么操作、最多几次、等多久、是否幂等、是否会放大成本和故障”。
```

当前项目已经具备：

```text
LLM 应用层重试决策
可重试/不可重试错误分类
指数退避
Retry-After 读取和等待上限
SDK 内部重试关闭
普通聊天创建阶段重试
流式聊天创建阶段重试
primary retry 后再 fallback
fallback 不额外重试
安全重试日志
自动化测试覆盖
```

```text
超时治理。
```
