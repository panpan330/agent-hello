# M12 第 10 节：Multi-Agent 架构

## 本节定位

上一节将复杂任务拆为 Planner、Executor、Critic 等职责。一个自然的问题是：既然职责可以拆分，是否应该让多个独立 Agent 协作？

答案是：**有时应该，但远没有想象中频繁。** Multi-Agent（多智能体）带来的不是自动的“更聪明”，而是一组新的工程问题：谁拥有任务最终状态？Agent 之间如何传递事实而不是互相编故事？哪一个 Agent 能调用哪些工具？并行结果冲突时听谁的？一个子 Agent 失败会不会拖垮全局？成本、延迟和循环如何控制？

本节讨论的不是某个框架 API，而是一套架构判断和协作原则：

```text
什么时候一个受控单 Agent 已经够用；
什么时候可以引入专门子 Agent；
如何让它们通过明确任务、状态、消息和权限协作；
如何避免“多个模型围绕同一个问题无限聊天”。
```

本节建立在前面状态机、Agent Loop、Checkpoint、队列、人工参与、Sandbox 和角色分工之上。若这些基础没有建立，直接上 Multi-Agent 往往只会让问题更难排查。

## 本节学习目标

学完后，你应当能：

1. 区分多角色职责拆分与真正的 Multi-Agent 架构。
2. 判断一个任务是否具备拆成多个 Agent 的合理条件。
3. 理解 Supervisor、Router、Orchestrator、Worker Agent、共享状态和消息契约的作用。
4. 区分集中式、层级式、流水线式、并行扇出式与协商式协作模式。
5. 说明 Multi-Agent 如何处理权限隔离、上下文隔离、结果冲突、失败和取消。
6. 理解并行带来的吞吐收益与成本、限流、一致性代价。
7. 能为一个实际业务任务设计“是否需要多 Agent”的理性方案。

## 一句话先讲透

> Multi-Agent 的本质是把一个复杂目标分配给多个有明确输入、输出、权限和终止条件的受控工作单元；真正的核心不是 Agent 之间会聊天，而是系统能证明每个子任务为何存在、由谁负责、使用了哪些事实、何时结束，以及如何把结果安全地汇总回一个权威任务状态。

## 基础知识铺垫

### 1. 多个模型调用不等于 Multi-Agent

以下情况不一定是 Multi-Agent：

- 一个模型先生成计划，再生成答案；
- 对同一问题调用三次模型后选一个；
- 一个服务内部串行调用多个 prompt；
- 一个模型执行多个工具调用。

它们可能只是多阶段单 Agent 或普通工作流。

通常认为“多 Agent”至少意味着存在多个相对独立的工作单元，它们具有某种角色、局部状态、输入输出契约或能力范围，并通过协调机制共同服务于一个更大目标。

例如：

```text
主任务：生成合同风险报告
  ├─ 文档解析 Agent：只负责结构和文本提取
  ├─ 条款识别 Agent：只负责按受控分类发现候选条款
  ├─ 证据校验 Agent：只检查引用和覆盖度
  └─ 汇总 Agent：将经过验证的结果组织为报告草稿
```

即使这四个角色使用同一个模型，也可能构成 Multi-Agent；反过来，即使使用四个不同模型，但没有独立任务边界和协调机制，也可能只是混乱的多调用。

### 2. 为什么会想用 Multi-Agent

合理动机通常来自以下一种或多种需求：

| 需求 | Multi-Agent 可能的价值 |
| --- | --- |
| 任务可分解 | 每个子问题有独立目标和完成条件 |
| 专业化 | 不同角色使用不同工具、提示、模型或知识范围 |
| 权限隔离 | 某些 Agent 只能读，某些只能生成草稿 |
| 并行 | 多个独立子任务可同时执行以缩短总时间 |
| 上下文隔离 | 避免所有细节堆入一个超长 prompt |
| 可验证性 | 让独立角色检查证据、格式或约束 |
| 组织映射 | 与真实业务团队/流程边界对齐 |

不合理动机包括：

- “多 Agent 听起来更高级”；
- “一个 Agent 回答不稳定，所以加几个一起猜”；
- “不清楚需求，先让多个 Agent 自由讨论”；
- “不想设计状态和工具契约，交给 Agent 自己协商”。

复杂度必须有明确收益作为理由。

### 3. 拆分前先看任务依赖图

一个任务能否并行或拆分，取决于依赖关系，而不是名称能否拆成多个角色。

```text
顺序依赖：
验证订单归属 -> 查询物流 -> 判断是否创建工单

可并行：
解析合同第 1 章  ┐
解析合同第 2 章  ├-> 汇总
解析合同第 3 章  ┘
```

若后一步必须使用前一步的真实 observation，则强行并行只会产生猜测或重复工作。若多个子任务真正独立，则 fan-out/fan-in 才可能带来收益。

### 4. 共享状态与共享上下文不是同一回事

Multi-Agent 中常见两个极端：

```text
极端 A：每个 Agent 都拿到全部消息、全部工具结果、全部记忆。
极端 B：每个 Agent 完全独立，互相不知道前人做了什么。
```

前者导致上下文膨胀、泄露、注入扩散和责任不清；后者导致重复调查、事实不一致和无法协作。

更合理的是区分：

| 信息类型 | 是否共享 | 例子 |
| --- | --- | --- |
| 任务身份/状态/预算 | 通常共享或由 Orchestrator 管理 | task_id、deadline、取消标记 |
| 已验证关键事实 | 按需共享 | 订单归属、文档页码、工具结果引用 |
| 原始敏感数据 | 最小化共享 | 仅授权 Agent 可读 |
| 局部推理/中间草稿 | 通常不全局共享 | 某子 Agent 的内部工作笔记 |
| 工具凭据 | 不共享给模型 | 由工具层/任务能力令牌控制 |
| 最终交付物 | 经校验后共享 | 结构化子结果、引用、失败说明 |

共享的是受控事实和契约化结果，而不是所有对话文本。

### 5. 多 Agent 也需要一个权威控制面

如果每个 Agent 都可以随意改变全局状态、调用写工具或创建更多 Agent，系统会很快失控。

无论协作方式多复杂，通常都需要一个权威控制面：

```text
任务状态机
权限与工具策略
预算与并发限制
子任务创建/取消规则
Checkpoint 与事件审计
结果汇总与终态决定
```

它可以由 Orchestrator、Supervisor、工作流引擎或业务服务承担，但不能完全交给自然语言协商。

## 本节主题系统讲解

### 1. Multi-Agent 的基本构成

一个可控的 Multi-Agent 系统通常包含：

```text
Parent Task（父任务）
  ├─ Orchestrator / Supervisor（编排/调度）
  ├─ Agent Registry（角色和能力注册）
  ├─ Child Tasks（子任务）
  ├─ Shared State / Artifact Store（受控共享状态与产物）
  ├─ Message / Queue（异步分发）
  ├─ Policy & Permission Layer（策略和权限）
  └─ Aggregator / Finalizer（结果汇总与终结）
```

每个子 Agent 最好能回答：

```text
我的目标是什么？
我能读取哪些输入？
我能调用哪些工具？
我会产出怎样的结构化结果？
我如何报告成功、失败或等待？
我的预算和截止时间是多少？
谁可以取消或重试我？
```

如果无法回答这些问题，所谓“子 Agent”很可能只是一个无边界聊天机器人。

### 2. 常见协作模式一：流水线（Pipeline）

流水线适合后一步依赖前一步产物的任务：

```text
文件解析 Agent
-> 文本清洗 Agent
-> 条款提取 Agent
-> 证据校验 Agent
-> 报告生成 Agent
```

优点：

- 数据流和状态转移清晰；
- 每步可单独测试、缓存和重试；
- 权限和工具可按阶段收缩；
- 失败定位相对容易。

风险：

- 任一步慢会阻塞整体；
- 上游错误会传播；
- 过度拆分会增加序列化、传输和模型调用成本；
- 需要明确每一步的输入输出 schema 和版本。

流水线很多时候其实更像“带 AI 节点的工作流”，不一定要让每个阶段都有自主 Agent Loop。若步骤固定，普通工作流往往更简单可靠。

### 3. 常见协作模式二：Supervisor / Router

Supervisor 或 Router 根据任务类型、状态和需求，将任务交给合适的专门 Agent：

```text
用户问题
-> Router：退款？物流？账户？文档？
-> 选择对应领域 Agent
-> 领域 Agent 在受限工具中处理
-> Supervisor 汇总/结束/转人工
```

这里 Router 的责任是**路由**，不是让它无限解决问题。路由结果可由规则、分类模型、LLM 或组合产生，但系统应限制：

- 可路由的 Agent 白名单；
- 每类任务允许的次数；
- 置信不足时的澄清/人工路径；
- 禁止在 Agent 之间无限来回转交；
- 路由决策的审计。

对许多企业应用，“一个 Router + 多个受控领域工作流”比“多个自由协商的 Agent”更符合实际需要。

### 4. 常见协作模式三：层级式（Hierarchical）

层级式结构中，父 Agent 或 Supervisor 将较大目标分派给子 Agent，子 Agent 可再细分受限子任务：

```text
任务总控
  ├─ 调研 Agent
  │    ├─ 知识检索子任务
  │    └─ 数据查询子任务
  ├─ 分析 Agent
  └─ 汇总 Agent
```

它适合复杂、可分解的大任务，但需要严格限制层级深度和子任务数量。否则容易出现：

- 子 Agent 无限创建子 Agent；
- 预算无法控制；
- 父任务不清楚子任务真实状态；
- 错误和敏感上下文在层级中扩散；
- 取消无法向下传播。

工程上可设置：最大层级、最大子任务数、父任务预算切分、显式能力继承规则、父子状态聚合规则。

### 5. 常见协作模式四：并行扇出/汇聚（Fan-out/Fan-in）

该模式适合多个独立子问题可同时执行：

```text
父任务：分析 20 个文档
-> fan-out：为每个文档创建解析/提取子任务
-> 并行执行
-> fan-in：等待、汇总、标记部分失败
-> 生成总报告
```

并行并非免费。需要处理：

- 全局与每任务并发上限；
- 子任务预算分配；
- 任何一个失败是否阻塞总任务；
- 部分完成是否可交付；
- 子任务结果 schema 是否一致；
- 汇总任务何时触发且不重复；
- 父任务取消如何传播。

合理的父任务状态可以不是简单成功/失败，而是：

```text
RUNNING
PARTIALLY_SUCCEEDED
WAITING_FOR_CHILDREN
FAILED
CANCELLED
```

但要避免状态泛滥。关键是对部分失败有明确业务含义，例如“20 份中 18 份完成，报告标明未处理的两份”。

### 6. 常见协作模式五：辩论/协商（Debate/Negotiation）

有些研究或演示会让多个 Agent 互相辩论、投票或协商。这在生成多角度方案、对创意进行审阅时可能有帮助；但在企业业务执行中风险较高：

- 争论不一定产生新事实；
- 多轮消息快速增加成本与延迟；
- 模型可能相互强化错误；
- 没有权威裁决者就无法停止；
- 难以审计每个结论的事实基础。

若使用，应限制为：

- 无副作用的方案比较；
- 固定轮次；
- 明确评价标准；
- 基于同一受控证据集；
- 最终由规则、人工或明确的汇总器决策。

不要让“讨论”替代查询真实数据、执行验证或业务授权。

### 7. 子 Agent 的输入输出契约

子 Agent 之间最好通过结构化 Artifact（产物）或消息交接，而不是复制长对话。

一个子任务输入可以包含：

```text
parent_task_id
child_task_id
goal
authorized_context_refs
allowed_tools
budget/deadline
expected_output_schema
policy_version
```

输出可以包含：

```text
status: succeeded / failed / waiting
result: 结构化结果
evidence_refs: 数据来源/页码/工具调用引用
confidence_or_uncertainty: 受控表达
blocked_reason: 若失败/等待
cost_and_usage_summary
```

这种契约带来几个好处：

- 汇总方可以验证结果是否完整；
- 子 Agent 无法把无关隐私直接传给所有人；
- 可独立重试或替换一个角色；
- 可进行版本演进和自动化测试；
- 审计能追溯结论来自哪个子任务。

### 8. 谁拥有全局真相：父任务与子任务状态

多 Agent 最重要的设计之一是明确权威状态：

- 父任务负责整体目标、用户可见状态、全局预算、最终结果和取消。
- 子任务负责局部目标、局部状态、局部 checkpoint 和结果。
- Orchestrator 负责依据状态转移规则聚合二者。

子任务不应直接将父任务标记为成功，也不应直接调用其他不相关子任务的写工具。它应该报告自己的结构化结果；父任务/Orchestrator 根据汇总规则决定下一步。

例如三个文档分析子任务中两个成功、一个失败：是父任务部分成功、重试失败子任务、生成含缺失说明的报告，还是整体失败？这属于父任务业务规则，不应由任一子 Agent 单方面决定。

### 9. 共享状态设计：引用优于复制

大型文本、原始文件、敏感数据和完整工具输出不应在 Agent 间反复复制。更好的方法是：

```text
共享 Artifact ID / evidence reference
-> 有权 Agent 按需读取受控内容
-> 返回最小结构化结论
```

例如：

```text
document_artifact_id = doc_001
extracted_clause_refs = [clause_12, clause_29]
```

而不是在每个 prompt 中塞入完整合同全文。引用机制既减少 token 和延迟，也有利于权限过滤、版本控制、删除和审计。

### 10. 上下文隔离：降低污染和角色漂移

不同 Agent 应只获得完成当前职责所需的上下文：

| Agent | 应看到 | 不应默认看到 |
| --- | --- | --- |
| 文档解析 Agent | 文件引用、解析规则 | 用户完整历史、写工具权限 |
| 订单调查 Agent | 当前订单授权范围 | 其他用户订单、退款执行凭据 |
| 汇总 Agent | 已验证子结果与证据引用 | 所有原始敏感字段 |
| 审核 Agent | 待审核动作和必要依据 | 无关内部系统密钥/全量日志 |

上下文隔离还能减少 Prompt Injection 扩散。若某个网页或文档包含恶意文本，它不应自动传播到所有 Agent 的上下文。

### 11. 权限隔离：每个 Agent 都不应是“全能代理”

多 Agent 的一个真正优势是能力分离：

```text
Research Agent：只读检索和公开信息获取
Business Agent：受控查询当前用户订单
Draft Agent：只能生成草稿，无外部写能力
Action Agent：仅在有效审批后可调用特定写 API
```

即使某个低权限 Agent 被注入或误导，它也无法直接执行高风险动作。Action Agent 也不应被所有角色直接调用，而应由 Orchestrator 在策略条件满足后显式调度。

切勿因为“都是内部 Agent”就让它们共享一个管理员令牌或完整工具集。内部边界同样重要。

### 12. Agent 间通信的两种方式

#### 12.1 直接消息通信

Agent A 向 Agent B 发一条结构化消息，适合短期、明确的协作：

```text
请求：请检查以下引用是否覆盖退款条件。
输入：evidence_refs [...]
期望：coverage report schema
```

优点是直接；风险是形成复杂消息网和循环依赖。应限制允许通信的角色关系和最大往返次数。

#### 12.2 共享任务/产物存储

Agent 将结果写为 artifact，其他 Agent 通过任务状态或 Orchestrator 得知何时读取。适合异步、长任务和审计：

```text
子任务完成 -> 保存 result_artifact -> 发布 task_completed event
-> 汇总任务读取 artifact
```

优点是可恢复、可审计、便于权限控制；缺点是实现更像标准分布式工作流。企业系统通常更偏向这种模式。

### 13. 结果冲突如何处理

多个 Agent 可能给出矛盾结论，例如：

```text
政策 Agent：订单可能符合退款条件
订单 Agent：订单已超过申请期限
```

不能简单按“谁的模型更强”或“多数投票”决定。应优先：

1. 检查来源权威性和时间：实时订单事实通常优先于一般政策摘要。
2. 检查是否其实讨论不同维度：政策一般条件与当前订单具体事实可共同成立。
3. 让 Critic/规则指出冲突点与缺失证据。
4. 补充必要的权威查询或版本信息。
5. 高风险或无法消解时转人工。

冲突处理规则应由业务与数据来源层决定，不应让 Agent 通过修辞“谈判”掩盖矛盾。

### 14. 失败、超时与部分成功

Multi-Agent 比单 Agent 多了一层失败传播问题。应提前定义：

| 子任务结果 | 父任务可能策略 |
| --- | --- |
| 必需子任务失败 | 有限重试、替代工具、转人工或整体失败 |
| 可选子任务失败 | 继续交付，明确说明缺失部分 |
| 子任务等待人工 | 父任务等待、并行做其他无依赖步骤 |
| 子任务超预算 | 降级方案、停止该分支、报告限制 |
| 子任务被取消 | 根据依赖决定取消父任务或部分完成 |

把所有子任务失败都升级为父任务失败会降低可用性；忽略必需子任务失败又会产生无依据结论。必须根据业务成功标准分类“必需”和“可选”。

### 15. 取消与预算如何向下传播

父任务取消后，系统应：

```text
标记父任务取消
-> 阻止创建新子任务
-> 向未开始子任务发取消
-> 让运行中子任务在安全边界停止
-> 对在途写操作做对账/补偿
-> 汇总各子任务最终状态
```

预算也应层层分配：

```text
父任务总预算：10 次模型调用、5 分钟、100 单位成本
-> 子任务 A：最多 3 次、30 单位
-> 子任务 B：最多 2 次、20 单位
-> 汇总保留 2 次、20 单位
```

若不分配，某个子 Agent 可能耗尽全部预算，导致更重要的汇总或验证无法执行。父任务应保留全局裁决权，不让子任务自行无限扩张。

### 16. 并行的成本、限流和公平性

并行多个 Agent 会缩短墙钟时间，但会增加：

- 同时模型请求数；
- 工具/数据库并发；
- token 与外部 API 成本；
- 结果汇总复杂度；
- 限流失败概率；
- 日志、存储和监控压力。

因此需要与第 6 节队列和背压结合：

```text
全局最大并发
每父任务最大子任务数
每租户最大并发
按角色/模型的并发池
优先级队列
成本预算和超时
```

最快的方案不一定是最优方案。若子任务很小，调度和上下文传递成本可能超过并行收益。

### 17. 可观测性：必须能看见协作图

一个 Multi-Agent 任务出错时，不能只看到“任务失败”。应能追踪：

```text
parent_task_id
  -> child_task_id / agent_role
      -> tool_calls / artifacts / state transitions
      -> result / error / budget usage
```

推荐观测字段：

- 父子任务关系和层级深度；
- Agent 角色、模型/版本、工具集；
- 计划与状态版本；
- 每个子任务耗时、成本、重试次数；
- 消息/队列延迟；
- artifact 引用和来源；
- 冲突、人工介入、取消传播事件；
- 最终汇总决策依据。

分布式追踪中的 trace/span 关系很适合表示这类树状调用，但追踪本身不等于业务状态，仍需和任务/审计记录关联。

### 18. 一个完整走读：企业知识问答与订单调查

用户问：“我的 A1001 订单迟迟没到，退款政策怎么规定？能帮我处理吗？”

先判断：是否真的需要 Multi-Agent？任务包含两个相对独立部分：订单/物流事实调查，以及退款政策检索；两者的结果再汇总决定是否需要工单或人工。因此可以采用轻量并行结构。

```text
Parent Task：处理订单物流与退款咨询
  ├─ Order Investigation Agent
  │    - 只读订单与物流工具
  │    - 仅可访问当前用户授权的订单
  ├─ Policy Retrieval Agent
  │    - 只读、当前版本政策知识库
  │    - 产出规则与引用，不做个案决定
  └─ Coordinator/Finalizer
       - 汇总两个已验证结果
       - 检查冲突和缺失
       - 决定直接答复、请求创建工单确认或转人工
```

两条调查可并行，但 Finalizer 不能在其中一条尚无结果时承诺最终结论。若物流 Agent 无权限或失败，Policy Agent 的一般信息仍可作为部分答复，但系统应明确“无法验证当前订单状态”，而非猜测。

工单创建仍由单独受控 Action Agent 或业务工具在确认后执行，不能因为多个调查 Agent 共同“认为应该创建”就自动写入。

### 19. 一个完整走读：批量合同分析

任务：分析 100 份合同，生成风险统计与需要法务复核的清单。

合理结构：

```text
父任务：批量合同分析
  -> fan-out：每份合同一个 Document Analysis 子任务
      - 解析、提取候选条款、输出结构化 evidence
  -> fan-in：统计完成/失败/待人工的子任务
  -> Aggregation Agent：只读取经验证的子结果，生成统计与清单草稿
  -> Human Review：法务复核高风险项
```

这里并行价值明显，因为文档之间大多独立。需要控制：最大并发、每份文档成本、部分失败交付、父任务超时、子任务重试、文件权限隔离和汇总去重。

不合理结构则是让 100 个 Agent 围绕同一份合同互相讨论，每个都拥有写权限和全量数据。那会成本高、事实混乱且难以审计。

### 20. 何时用多 Agent，何时用固定工作流

可以用一张简化判断表：

| 问题 | 倾向选择 |
| --- | --- |
| 路径几乎固定、步骤明确 | 固定工作流 |
| 只有一个语义决策点 | 单 Agent Loop |
| 有不同领域/权限/上下文，需要选择处理者 | Router + 专门 Agent/工作流 |
| 多个独立子任务可并行且结果需汇总 | Fan-out/Fan-in Multi-Agent |
| 高风险写操作 | 受控业务流程 + HITL，不因多 Agent 而放宽 |
| 需要自由讨论寻找创意方案 | 限轮次协作/辩论，可不接真实副作用 |
| 团队还无法可靠维护任务状态、工具和评估 | 暂缓 Multi-Agent，先补基础 |

Multi-Agent 是结构化分解的工具，不是通用质量增强器。

### 21. 一套务实的落地顺序

1. 先实现一个受控单 Agent 或固定工作流，明确成功标准、状态、工具和评估。
2. 找出真实瓶颈：上下文过长、工具权限不同、任务可并行、角色混杂还是质量缺陷。
3. 先按职责/工具/权限拆出一个子任务，不要一次拆五个。
4. 为父子任务建立结构化输入输出、状态、预算和取消协议。
5. 通过队列和 checkpoint 支持异步、重试和恢复。
6. 加入 artifact 引用、权限过滤、追踪和成本观测。
7. 明确部分成功、冲突和人工升级规则。
8. 用评估数据证明拆分确实提升成功率、速度、成本或可维护性；没有收益则回退简化。

## 常见误区

### 误区 1：多个 Agent 一定比一个 Agent 更聪明

多个模型可能重复错误、互相放大幻觉，并增加通信和汇总损失。Multi-Agent 的收益来自合理拆分、独立事实来源、专门能力或并行，而不是数量本身。

### 误区 2：让所有 Agent 共享完整聊天记录最方便

这会扩大敏感信息和注入内容的传播范围，增加 token 成本，也让角色边界模糊。应按需共享已验证事实和 artifact 引用。

### 误区 3：每个子 Agent 都能直接修改父任务或调用写工具

这会失去全局控制和审计。子 Agent 应报告结构化结果；父任务/Orchestrator 依据规则、权限和审批决定是否推进全局状态或执行副作用。

### 误区 4：并行越多越快

并行受模型配额、工具容量、数据库、成本和汇总开销限制。过度并行会导致限流、排队、资源争用和更高失败率。

### 误区 5：子 Agent 失败就让它无限自我修复

子任务也需要预算、重试分类、终止条件和上报机制。失败后应由父任务决定重试、替代、部分成功、转人工或整体终止。

### 误区 6：通过投票解决所有冲突

多数模型输出不等于事实。冲突应优先按权威数据、来源版本、时间、规则和人工复核消解；投票最多是无副作用主观任务的辅助信号。

### 误区 7：用了 Multi-Agent 就不需要工作流和状态机

恰好相反。多 Agent 增加更多任务、消息和状态，更需要任务状态机、Checkpoint、队列、权限与可观测性作为控制骨架。

## 本节练习

### 练习 1：判断是否需要 Multi-Agent

对于“用户上传一份 PDF，系统提取文字、生成摘要并展示结果”，是否必须使用 Multi-Agent？请说明一种更简单的合理方案。

答案：不必须。若步骤固定，可用受控流水线/工作流：文件校验 -> 文本提取 -> 清洗 -> 摘要 -> 输出校验。只有当文档很大、可按章节并行、不同领域分析需要不同权限/专业化，或确有复杂路由时，再考虑子 Agent。固定工作流通常更简单、易测、成本更低。

### 练习 2：设计子任务契约

为“政策检索 Agent”写出至少五项输入/输出契约字段。

答案：输入可包括 `parent_task_id`、当前问题、允许知识库范围、租户/权限上下文、截止时间、输出 schema。输出可包括 `status`、政策结论摘要、`evidence_refs`（文档和版本/页段定位）、不确定项、失败/阻塞原因、耗时/成本摘要。重点是结果可被汇总方验证而非只有自由文本。

### 练习 3：处理冲突

订单调查 Agent 返回“订单已签收”，物流 Agent 返回“48 小时无更新”。下一步应如何处理？

答案：不能简单投票或选一个结果。应检查两个 observation 的时间、来源与字段含义：物流轨迹可能在签收前 48 小时无更新，或其中一项数据过期。可查询最新事件时间、确认是否已签收，再由汇总规则解释；若涉及争议或数据冲突无法消解，则转人工或明确说明限制。

### 练习 4：取消传播

父任务正在并行分析 20 个文档，用户取消任务。请给出至少三项系统应做的事。

答案：标记父任务取消并阻止创建新子任务；向未开始子任务发取消；让运行中子任务在安全检查点停止并回收资源；对已发出外部写动作进行对账；汇总各子任务最终状态并向用户展示已停止/已完成的范围。具体实现需结合幂等与任务状态机。

## 自测题

### 自测 1：Multi-Agent 与多次模型调用的区别是什么？

答案：多次模型调用可能只是单 Agent 的多阶段流程。Multi-Agent 通常包含多个相对独立的工作单元，各自具有角色、目标、局部状态、输入输出契约或能力范围，并由协调机制共同完成父任务。关键是职责和控制边界，不是调用次数。

### 自测 2：为什么父任务应拥有全局终态决定权？

答案：子任务只知道局部目标，无法判断其他必需依赖、全局预算、用户目标、部分成功规则或高风险动作是否满足条件。父任务/Orchestrator 统一聚合状态和结果，避免任一子 Agent 擅自宣告整体成功或执行全局副作用。

### 自测 3：Agent 间为什么优先共享 artifact 引用而不是原始全文？

答案：引用减少 token、延迟和重复复制，便于按权限读取、版本管理、删除和审计，也降低敏感数据及 prompt injection 在角色间扩散的范围。需要内容时由有权 Agent 按需获取最小范围。

### 自测 4：并行 fan-out 的关键控制点有哪些？

答案：子任务独立性、最大子任务数、全局/租户并发、预算分配、父子状态聚合、部分失败策略、取消传播、幂等汇总、结果 schema 与追踪。并行不能绕过限流、成本和权限控制。

### 自测 5：什么时候应选择 Router + 领域工作流，而不是自由协商的多个 Agent？

答案：当任务可按领域或类型清晰路由，后续步骤相对固定，且需要较强权限、审计和可预测性时，Router 选择受控领域工作流更简单可靠。自由协商更适合无副作用的创意/研究场景，仍需固定轮次和裁决规则。

## 本节小结

Multi-Agent 只有在任务可分解、专业化/权限隔离有明确价值、或独立子任务并行能带来真实收益时才值得引入。可靠架构需要父任务权威状态、结构化子任务契约、最小共享上下文、能力隔离、预算与取消传播、冲突处理和完整可观测性。它不是“让多个模型自由对话”，而是受控分布式任务协作。
