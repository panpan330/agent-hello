# M13 第 9 节：模型服务部署架构

## 本节定位

上一节讨论推理引擎怎样在一台或一组机器上高效执行模型。本节再向外扩展：当模型服务真的要被多个业务系统、多个用户、多个环境长期访问时，怎样组织入口、网关、模型副本、队列、存储、观测、故障隔离和发布流程。

本节的目标不是让你立刻搭一套大型集群，而是建立**部署架构的判断模型**。以后不管你使用云模型 API、单机本地模型、Docker 容器、虚拟机还是 Kubernetes，都能看懂每个组件存在的原因，知道哪些问题可以暂时不解决，哪些问题不能被“模型已经启动”掩盖。

本节仍是纯知识学习，不要求安装或改动任何项目代码。

## 本节学习目标

学完后，你应当能够：

1. 区分模型服务“能启动”“能被调用”“可稳定服务”“可运营”的不同成熟度。
2. 画出从用户请求到模型生成结果的基本部署链路。
3. 说明负载均衡、API 网关、模型副本、队列、缓存、对象存储、数据库和观测系统在模型架构中的职责。
4. 理解无状态服务、状态服务、模型权重和 KV Cache 在部署上的差异。
5. 解释扩容模型副本为什么不一定能降低单请求延迟。
6. 理解健康检查、就绪检查、优雅停止、冷启动、预热和滚动发布的关系。
7. 区分同步交互请求、异步长任务和批处理任务的部署路径。
8. 用故障域、降级、隔离、容量和 SLO 的视角评估模型服务架构。

## 一句话先讲透

**模型部署架构的核心不是把权重放到一台机器上，而是在性能、可用性、数据边界、成本和运营复杂度之间，为不同类型的请求建立可预测的运行路径。**

## 基础知识铺垫

### 1. “部署成功”有不同层次

很多人说“模型部署好了”，实际可能只完成了其中一层：

1. **进程启动**：命令没有报错，模型进程仍在运行。
2. **本机可调用**：在机器本地用 `curl` 能得到回复。
3. **网络可访问**：其他受控服务能通过网络地址访问。
4. **可重复部署**：换一台机器或重启后能用相同方法恢复。
5. **可稳定服务**：在预期并发、长输入、异常请求下仍满足延迟和成功率目标。
6. **可运营**：能够监控、告警、升级、回滚、审计、扩容、处理密钥和应对故障。

前两层是实验成功；后四层才逐渐接近生产服务。把这些层次分开，不是为了制造复杂度，而是避免“本地跑通一次”被误认为“可以承载业务”。

### 2. 部署架构与代码架构不是一回事

代码架构关心模块、类、函数、领域边界；部署架构关心：

- 哪些进程在什么机器/容器中运行；
- 它们通过什么网络通信；
- 哪些组件可以复制，哪些必须持久化；
- 数据放在哪里；
- 请求经过哪些安全和治理边界；
- 一处故障会影响多大范围；
- 如何升级、扩容、观测和恢复。

同一份 Python 服务代码可以本地直接运行、打包成 Docker 容器、部署在虚拟机、放入 Kubernetes，也可以运行在托管平台。代码变化不一定很大，但运行责任和可用能力可能完全不同。

### 3. 控制面与数据面

理解部署系统时，常用一个有帮助的划分：

- **数据面（data plane）**：真正处理业务流量和模型请求的路径，例如网关转发、推理服务生成 Token、向量数据库检索。
- **控制面（control plane）**：配置、发布、扩缩容、服务发现、证书、策略、模型路由和资源调度等管理动作。

用户问“订单在哪里”时，走的是数据面；管理员把 `model-v1` 的 10% 流量切到 `model-v2`，属于控制面。

二者不必由不同产品实现，但概念上分开很重要：控制面故障不应随意中断已经在跑的数据面；数据面指标也不能只靠控制面显示“部署成功”来判断。

### 4. 状态：为什么模型服务看起来无状态，实际上又有状态

传统 Web API 常被设计成近似无状态：任何一个副本都能处理任意请求，用户会话、订单和文件等持久状态放到数据库、缓存或对象存储中。

模型服务有两面：

- **请求之间通常无持久会话状态**：下一次聊天请求通常由调用方重新携带历史消息，因此不同副本可以处理不同请求。
- **请求执行期间具有大量短生命周期状态**：Tokenizer 状态、KV Cache、流式连接、队列位置、GPU 显存分配都在当前实例内。

模型权重本身更像大型只读资产：加载慢、占显存、可由多个请求共享，但换模型版本或重启时需要重新准备。这个特点决定了模型副本不像普通小型 HTTP 服务那样“瞬间扩缩”。

### 5. 延迟、吞吐与可用性是不同目标

部署多个副本能提高总吞吐和故障容忍，但不一定直接降低单个请求的模型计算时间。单个请求仍需经过：

```text
网络 -> 鉴权/路由 -> 排队 -> prefill -> decode -> 网络回传
```

若瓶颈是模型本身每个 Token 的计算，增加副本主要是让更多请求并行处理；若瓶颈是某副本队列太长，合理分流才可能改善个体等待；若瓶颈是用户上传的超长上下文，副本数量也无法消除该请求的 prefill 成本。

因此架构设计必须明确：你是在优化可用性、总吞吐、TTFT、P95、成本，还是某个业务任务完成时间。不同目标会导向不同策略。

## 本节主题系统讲解

### 1. 一个最小可用的模型服务部署

最简单的部署可以是：

```text
业务应用
   |
   | HTTP
   v
单个模型服务进程
   |
   v
推理引擎 + 模型权重 + GPU
```

这在本地学习、内部工具、低风险 PoC 中非常有价值。它让你快速验证：模型是否可加载、接口是否能调用、质量是否达到最低要求、资源是否够用。

它的限制也很清晰：

- 单进程崩溃则服务不可用；
- 模型升级/重启会中断请求；
- 不能自然分担高并发；
- API Key、网络暴露、限流和审计容易被忽略；
- 日志和磁盘可能与模型进程混在一起；
- 一台机器的 GPU、内存、磁盘和网络就是硬上限。

最小架构不是“错误架构”。关键是明确它的适用边界，并且不把它误用为高可用生产系统。

### 2. 典型的生产模型调用链

一个较完整的在线交互链路可以抽象为：

```text
浏览器 / 外部客户端
        |
        v
边缘入口：DNS、TLS、WAF、反向代理
        |
        v
业务 API / BFF：用户认证、会话、领域权限
        |
        v
AI 应用服务：Prompt、RAG、工具编排、业务校验
        |
        v
模型网关：模型路由、密钥、配额、限流、审计、回退
        |
        v
负载均衡：选择健康模型副本
        |
        +------------------+------------------+
        v                  v                  v
模型副本 A            模型副本 B           模型副本 C
推理引擎 + GPU        推理引擎 + GPU       推理引擎 + GPU
```

旁路还可能有：

```text
数据库：用户、会话、订单、任务、配置
Redis：短期缓存、限流、队列、会话或分布式锁
对象存储：模型权重、文档、上传文件、离线结果
向量数据库：Embedding 和检索索引
消息队列：异步任务、削峰、重试、任务分发
可观测系统：日志、指标、Trace、告警
密钥系统：供应商 Key、内部令牌、证书
```

不是所有系统都要在第一天引入全部组件。图的意义是帮你识别职责，理解“某个能力应该由哪个边界承担”，而不是鼓励无条件堆技术。

### 3. 边缘入口与反向代理

外部请求通常不会直接暴露到模型进程端口。边缘入口/反向代理经常负责：

- HTTPS/TLS 终止，即浏览器与入口之间加密；
- 域名和路径路由；
- 基础请求大小限制；
- CORS、压缩、静态资源与连接管理；
- WAF、IP 规则、基础 DDoS 防护；
- 将请求转发给内部业务服务。

模型服务尤其不适合裸露在公网：它通常资源昂贵，容易被大请求、长连接或并发滥用拖垮；而且它不应直接理解浏览器用户身份和领域权限。

反向代理也不是业务安全的全部。它能限制“谁能连进来、请求多大、路径是否合法”，却不了解“该用户能不能看这张订单”“这个工具调用是否已确认”。后者仍属于业务应用层。

### 4. 业务服务与 AI 应用服务的边界

一个成熟 AI 应用常将以下责任明确放在业务/AI 应用层：

- 验证用户身份和租户；
- 根据权限过滤可检索文档和可访问业务数据；
- 选择适合任务的 Prompt、模型和工具；
- 执行 RAG、重排序、引用和答案校验；
- 执行 Tool Calling 的白名单、参数校验、确认、幂等和审计；
- 将模型输出转换为领域 API 响应；
- 将原始错误变为可理解、不过度泄露内部细节的业务错误。

模型服务只需接收已构造好的模型请求，并高效返回生成或向量。它不应该直接连接你的核心订单库后自行决定能否修改数据。这样拆分也让模型可以被多个应用复用，同时不共享不该共享的业务权限。

### 5. 模型网关：统一接入，而不是再造一个万能系统

模型网关位于 AI 应用与模型提供方/自部署模型之间。它常见的职责包括：

- 内部逻辑模型名映射到云模型或部署版本；
- 供应商密钥托管和轮换；
- 配额、限流、预算和成本标签；
- 多模型路由、熔断、故障回退；
- 请求 Trace、审计和用量采集；
- 对多个供应商协议做有限适配；
- 模型版本灰度与流量切分。

它适合解决跨应用的共性问题。以下事情不应强行塞进网关：复杂业务规则、订单权限判断、业务工作流、领域数据拼装、工具副作用确认。把这些混进去，网关会变成难以维护的“第二业务系统”。

小型系统可先不单独部署网关，而在 AI 服务内部保留清晰的模型客户端适配和配置边界。当模型来源、调用方或治理要求增加时，再下沉为独立网关。

### 6. 模型副本和负载均衡

模型副本是同一个模型版本在不同进程、GPU 或机器上运行的多个实例：

```text
                -> 模型副本 A
负载均衡器 ->  -> 模型副本 B
                -> 模型副本 C
```

它们带来三类价值：

1. **容量**：多个副本可以同时处理更多请求。
2. **可用性**：一个副本故障时可把新请求转向其他副本。
3. **发布能力**：可以先启动新版本少量副本，再逐步切流。

负载均衡策略并不只是轮询。模型请求的耗时差别大，简单轮询可能把多个长上下文任务恰好送到同一副本。更先进的策略可能参考：活跃请求数、排队 token、GPU 利用、预计完成时间、会话粘性、模型能力、租户优先级或区域。

但不要过度承诺“最聪明”的调度：这些指标有采样延迟，预计输出长度难以准确知道，跨节点状态同步也有成本。实践中先使用可靠、可解释的策略，再按指标逐步优化。

### 7. 什么时候需要会话粘性（session affinity）

若每轮请求都完整携带历史消息，并且各副本没有跨轮缓存依赖，那么不同轮落到不同副本通常是可以的。这有利于均衡流量。

但以下情况可能希望一定程度的粘性：

- 推理引擎在单副本内维护可复用的前缀 Cache；
- 服务端保存会话状态而非每次携带完整历史；
- 某些长连接、交互式工具会话需要保持同一执行上下文；
- 多轮过程依赖副本内短期资源。

粘性的代价是流量更难均衡：热点会话可能持续压在一个副本上，副本故障时状态迁移也更难。设计时应先问“这个状态是否真的必须在模型副本内”，能放到外部存储的状态尽量外置。

### 8. 同步交互、异步任务和批处理应走不同路径

不是每个模型任务都应该由网页请求同步等待。

#### 8.1 同步交互路径

适合聊天、短问答、简单分类、少量工具编排：

```text
用户请求 -> 业务服务 -> 模型服务 -> 流式/完整响应 -> 用户
```

关注 TTFT、P95、取消、超时、并发和清晰失败提示。

#### 8.2 异步长任务路径

适合长文档解析、批量 Embedding、大文件摘要、深度研究、多步骤长 Agent 任务：

```text
用户提交任务 -> API 快速返回 task_id
                 |
                 v
             消息队列 / 任务表
                 |
                 v
             Worker 执行模型任务
                 |
                 v
         数据库 / 对象存储保存结果与状态
                 |
                 v
     用户轮询、SSE、WebSocket 或通知获取进度
```

这避免浏览器和网关长时间持有同步连接，也让重试、断点、并发控制和任务审计更清晰。

#### 8.3 离线批处理路径

适合周期性生成评估、知识库全量重建、历史数据标注、报表总结：

```text
调度器 -> 任务分片 -> 批量 Worker -> 结果存储 -> 质量检查
```

它更重视成本、总吞吐、可恢复性和数据一致性，不必追求交互级 TTFT。把它与在线客服请求隔离，能避免夜间大任务抢占白天用户体验。

### 9. 队列：削峰和背压，不是无限等待室

队列可位于网关、应用层、推理服务内部或消息中间件中。它的价值是当瞬时进入速率超过处理速率时，避免立即压垮下游。

但队列必须有边界。若每秒进来 100 个请求，系统每秒只能完成 20 个，队列会持续增长。单纯排队只是在推迟失败，最终表现为长时间等待、内存耗尽或任务过期。

因此队列设计需要配套：

- 最大长度或最大 token 预算；
- 等待超时和过期策略；
- 优先级和租户公平性；
- 拒绝或降级响应；
- 排队长度、等待时长、丢弃量告警；
- 上游背压，即告诉调用方“请稍后再试”而不是继续接收。

对于模型服务，按“请求数”限流有时不够，因为一个 20 Token 问题与一个 50,000 Token 文档的资源消耗差异巨大。更成熟的策略会考虑输入 Token、预期输出、并发和模型类型。

### 10. 存储组件在模型架构中的位置

#### 10.1 对象存储

对象存储适合大而不频繁修改的二进制或文件类数据：模型权重、量化文件、Tokenizer、用户上传文档、解析结果、大型离线输出、评测数据集快照。

模型副本启动时可能从对象存储或本地缓存加载权重。这里会产生冷启动问题：权重很大，下载、校验、解压和加载到 GPU 都需要时间。

#### 10.2 关系型数据库

适合保存结构化、需要事务或查询关系的数据：用户、租户、任务状态、模型配置、Prompt 版本、评测记录、工单、审计元数据等。

数据库通常不应承载每个 Token 的原始流式片段，也不应被当作模型权重仓库。应根据读写模式选择合适存储。

#### 10.3 Redis 或类似内存系统

常用于短 TTL 缓存、限流计数、会话临时态、任务进度、分布式协调或队列。它很快，但内存昂贵，并且必须明确持久化和故障恢复策略。

不能因为 Redis 速度快，就把所有聊天历史、完整 Prompt、长文档和审计数据无限堆入其中。

#### 10.4 向量数据库与搜索系统

RAG 的向量索引、元数据过滤和可能的关键词检索属于检索层。它们一般不与模型副本强绑定：模型服务负责生成/Embedding，检索服务负责候选召回，AI 应用负责权限、拼装上下文与答案责任。

### 11. 健康检查、就绪检查与预热

将“进程还活着”当成“可以接流量”是部署中的常见错误。

#### 11.1 存活检查（liveness）

回答：进程是否已经卡死或不可恢复？若持续失败，平台可能重启它。

#### 11.2 就绪检查（readiness）

回答：当前实例是否已经具备接收真实业务流量的条件？例如：

- 模型权重是否加载完成；
- GPU 初始化是否成功；
- Tokenizer 和关键配置是否可用；
- 依赖的密钥或模型文件是否就绪；
- 当前是否处于优雅下线状态；
- 是否已经超过安全队列/显存阈值。

模型进程刚启动时，可能端口已监听但模型还在加载。此时存活检查通过、就绪检查应失败。负载均衡器不应把新请求送进来。

#### 11.3 预热（warm-up）

模型第一次真正推理可能触发 CUDA 上下文初始化、内核编译/选择、内存池建立、缓存初始化等额外开销。预热请求可以在实例正式接流量前完成这些准备。

预热要使用无敏感数据、可控长度的测试输入，并与业务质量评测区分开。它验证的是运行路径，不是回答质量。

### 12. 优雅停止：为什么不能直接杀掉模型实例

模型请求可能持续数秒到数分钟，流式连接正在向用户输出。如果直接终止进程：

- 当前用户看到的流会突然中断；
- 正在运行的异步任务状态可能不一致；
- 已分配但未写入的结果可能丢失；
- 负载均衡器还未及时摘除实例，可能把新流量继续送进来。

优雅停止的一般思路是：

```text
标记实例不再就绪
-> 负载均衡停止发送新请求
-> 等待活跃请求完成或到达最大宽限时间
-> 保存/清理必要状态
-> 退出进程
```

对无法等待的长任务，应有取消、可恢复 checkpoint 或任务重领机制。优雅停止不是“保证所有任务永远不受影响”，而是把影响变得可控、可观测、可恢复。

### 13. 发布与版本：模型版本不是只改一个字符串

模型上线可能变化：

- 权重或量化版本；
- Tokenizer、聊天模板、系统提示；
- 推理引擎版本和启动参数；
- GPU 驱动/运行时；
- 安全策略、工具 Schema、RAG 检索配置；
- API 字段或默认采样参数。

这些变化都可能改变输出质量、成本、上下文长度、工具行为和性能。因此模型版本管理应至少能回答：

- 这次请求实际使用了什么模型、什么模板、什么配置？
- 新版本是否通过离线评测和关键业务回归？
- 出问题时能否把新流量切回旧版本？
- 同一会话是否需要固定在某一版本？
- 版本切换造成的缓存失效和冷启动怎么处理？

常见发布方式：

- **滚动发布**：逐步替换旧副本；
- **蓝绿发布**：新旧两套环境并存，切换入口流量；
- **金丝雀/灰度发布**：先让少量流量进入新版本，观察指标和质量；
- **影子流量**：复制部分真实请求到新版本做不影响用户的对比，必须特别注意隐私、成本和副作用隔离。

选择哪种方式取决于成本、容量、可回滚性和风险级别。对生成式 AI，除了 HTTP 成功率，还要观察业务质量、拒答率、结构化输出合法率、工具调用异常和成本变化。

### 14. 故障域与隔离：不要让一个问题拖垮全部服务

**故障域（failure domain）**指一个故障可能共同影响的范围。例如同一 GPU、同一机器、同一可用区、同一网络出口、同一供应商、同一模型版本都可能成为共同故障点。

常见隔离思路：

- 在线交互模型与离线批处理使用不同队列或资源池；
- 高优先级租户与普通流量使用配额/隔离；
- Embedding、Rerank、聊天生成各自独立限流和扩缩；
- 关键模型至少有不同副本或替代路径；
- 云模型与自部署模型可形成受控的混合降级，但要评估数据政策；
- 将模型服务、数据库、向量库的故障和告警分别观察，避免“一处慢，全链路都说模型慢”。

隔离不是为了让架构图更复杂，而是为了让故障影响范围与业务优先级匹配。所有流量共用一张 GPU、同一个队列、同一份资源时，低价值批任务也可能挤掉高价值用户请求。

### 15. 降级策略：提前决定“资源紧张时保留什么”

模型服务不可能保证永远无限容量。降级策略应在故障发生前设计，而不是线上临时拍脑袋。例子包括：

- 优先保留登录用户、付费租户或关键业务流程；
- 从高成本模型切到质量较低但可用的备用模型；
- 缩短允许的最大输出；
- 暂时关闭非必要的多轮反思、扩展检索或复杂工具链；
- 将长文档任务改为异步；
- 返回模板化兜底或提示稍后重试；
- 暂停低优先级批任务。

降级必须透明且可审计。尤其涉及事实性、医疗、金融、客服承诺或写操作时，不能因为备用模型能力较弱就悄悄给用户低可信结论。业务层需要知道当前是否发生降级，以决定如何提示、是否要求人工处理。

### 16. 容量规划：从 SLO 和请求分布出发

容量规划不是只问“要几张卡”。可采用以下思路：

1. 定义服务目标，例如 P95 TTFT、P95 总时延、成功率和最大排队时间。
2. 收集输入/输出 Token 分布、峰值到达率、流式比例、模型类型和用户取消率。
3. 在目标硬件和模型配置上做压测，得到不同并发下的 TTFT、吞吐、显存、队列和错误率。
4. 选择满足 SLO 的安全运行区间，而不是压到刚好 OOM 前。
5. 考虑 N+1 或至少单副本故障后的容量：一个副本失效后，剩余副本是否仍能承担关键流量？
6. 为发布、预热、峰值、缓存失效和外部供应商波动预留余量。

一个粗略但有用的直觉是：当到达速率持续接近或超过服务完成速率时，排队延迟会以非线性方式变坏。看平均 CPU/GPU 利用率不够，还要看队列长度和 P95/P99。

### 17. 可观测性：部署是否健康，不能只看容器绿色

模型服务架构至少需要跨层关联：

```text
用户请求
-> 业务 Trace
-> RAG / 工具阶段
-> 模型网关
-> 具体模型副本
-> GPU / 推理引擎指标
```

建议关注的指标类别：

- **流量**：请求数、Token 输入/输出、流式连接数、租户/模型分布；
- **延迟**：网关耗时、排队时间、TTFT、TPOT、总时延、P95/P99；
- **资源**：GPU 显存、GPU 利用率、CPU/RAM、磁盘、网络、Cache 使用；
- **可靠性**：错误率、超时、429、OOM、重启、取消率、健康检查失败；
- **质量**：结构化输出失败、工具调用失败、RAG 无引用、人工转接率、评测分数；
- **成本**：每模型 Token、每租户、每任务、缓存命中、云 API 用量；
- **安全**：鉴权失败、异常大请求、策略拦截、敏感数据告警。

指标必须能回答行动问题。例如“TTFT 变差”后，你要能区分是入口网络慢、队列变长、长 prefill 争抢、GPU 利用不足、某版本回归，还是外部供应商抖动。

### 18. 三种成熟度架构示例

#### 18.1 学习与 PoC

```text
本地 AI 应用 -> 本地/云模型 API
```

重点：快速验证模型质量、协议、基础安全和成本估算。

必要的最低保护：密钥不进源码、请求超时、基本错误处理、明确开发环境边界。

#### 18.2 小型内部系统

```text
内部用户 -> 业务 API -> AI 服务 -> 云模型或单副本自部署模型
                         |-> 数据库 / 向量库 / Redis
```

重点：用户鉴权、权限过滤、日志、基础限流、备份、健康检查、可重复部署。

可以先不引入复杂多区域、多集群控制面，但要能清楚地恢复服务和定位问题。

#### 18.3 面向生产的多副本服务

```text
入口/网关 -> 多个业务/AI 服务副本 -> 模型网关 -> 负载均衡 -> 多模型副本
                  |                          |                 |
                  +-> DB/Redis/向量库/对象存储/队列/观测/密钥系统
```

重点：隔离、弹性、容量、灰度、回滚、审计、成本、SLO 和故障恢复。

这不是“最终唯一架构”，而是一类问题规模增加后的自然演进。不要在只有一个内部用户的阶段就照搬全部组件，也不要在有真实关键流量时仍停留在单进程手工启动状态。

### 19. 架构设计中的一组关键问题

面对一个具体 AI 系统，可按下面顺序追问：

1. 谁会调用？公网用户、内部员工、其他服务，还是离线任务？
2. 每类请求是同步还是异步？最长可等待多久？
3. 哪些数据敏感？可否发给外部模型？
4. 当前和未来模型来自云 API、本地还是混合？
5. 峰值请求和 Token 分布是什么？
6. 哪些任务必须高可用，哪些可稍后重试？
7. 一个模型副本、一个 GPU、一个区域或一个供应商失效时怎么办？
8. 如何做身份、权限、配额和审计？
9. 如何升级模型、Prompt、RAG 索引和推理引擎，如何回滚？
10. 如何知道系统慢在哪里、贵在哪里、答错在哪里？

如果这些问题没有答案，直接讨论“选 Kubernetes 还是 Docker”“要不要上多卡”通常没有意义。部署技术是实现手段，架构问题先来自业务和运行目标。

## 常见误区

### 误区 1：模型能通过 `/health` 就说明可以接业务流量

纠正：端口可访问或进程存活不代表模型加载完成、GPU 可用、队列健康、依赖齐全或容量充足。需要独立的就绪检查和关键路径验证。

### 误区 2：增加模型副本一定能让每个用户更快

纠正：副本提高总容量和可用性。只有当原先存在排队/负载不均且路由有效时，才可能降低用户等待；单请求的模型计算、长输入 prefill 和网络延迟仍然存在。

### 误区 3：队列可以无限吸收流量高峰

纠正：若平均进入速率持续超过处理能力，队列只会无限增长。必须有限流、背压、过期、优先级、扩容或降级策略。

### 误区 4：模型网关可以承担全部业务逻辑

纠正：网关适合共性的接入和治理，不能替代领域权限、订单规则、RAG 数据过滤、工具确认和业务审计。否则它会变成难以维护的单体。

### 误区 5：模型服务是无状态的，所以可以随时随地重启

纠正：跨请求可以近似无状态，但执行中的流、KV Cache、队列和长任务都是短生命周期状态。重启会中断用户体验，因此需要优雅停止和任务恢复策略。

### 误区 6：所有模型任务都适合 HTTP 同步等待

纠正：大文件处理、批量 Embedding、长研究任务应走异步任务与结果存储路径，避免长连接、超时和资源占用影响交互服务。

### 误区 7：容器化等于高可用和可运维

纠正：容器解决的是打包和运行环境一致性的一部分。多副本、网络、存储、密钥、观测、扩缩、发布、恢复和安全策略仍需独立设计。

## 本节练习

### 练习 1：区分同步和异步路径

以下任务分别更适合同步、异步还是离线批处理：用户问一句订单状态；上传 500 页 PDF 并建立知识库；每天凌晨重新评估 10 万条客服回答；用户要求生成一段 200 字的邮件。

答案：订单状态问答通常适合同步交互，必要时可流式返回；500 页 PDF 入库适合异步任务，因为解析、切分、Embedding 和写入可能耗时且需要可恢复；每天凌晨的大规模评估适合离线批处理，关注吞吐和可恢复；200 字邮件一般适合同步或流式交互。实际还要看服务目标、数据量和用户体验要求。

### 练习 2：分析模型副本故障

有三个相同的模型副本，负载均衡器将请求平均分给它们。副本 B 因 GPU OOM 崩溃。为了避免新请求继续打到 B，部署系统至少需要哪些机制？

答案：至少需要健康/就绪检查让负载均衡器识别 B 不可接流量；负载均衡器根据检查结果摘除 B；监控和告警通知故障；进程/容器编排机制按策略尝试重启或替换 B；剩余副本或降级路径要能处理关键流量。还要考虑 B 崩溃时正在处理的流式请求如何向用户说明或恢复。

### 练习 3：解释冷启动

为什么模型服务的新副本刚启动时不应立即接收全部流量？

答案：模型权重下载/读取、CPU 内存加载、GPU 显存加载、运行时初始化、Tokenizer 准备、内核选择或编译、缓存建立都可能尚未完成，首批请求会异常慢甚至失败。应通过就绪检查和预热确认关键路径可用后再接流量。

### 练习 4：设计一个降级例子

某客服系统的高峰期 GPU 队列快速增长。请设计一个按优先级的降级思路，至少包含三项动作。

答案：例如优先保留已登录用户的订单查询和人工客服辅助；将低优先级的长文档总结改为异步并暂停新的批处理；对非关键闲聊限制最大输出并使用较轻量备用模型；当队列超过阈值时快速返回“当前繁忙，请稍后重试”而非无限排队；记录降级标记和指标，恢复后复盘。具体策略应结合业务风险，不能让低质量备用模型悄悄做高风险决策。

### 练习 5：判断责任边界

“用户 U 是否有权限读取订单 A1001”应该由模型服务、模型网关、业务/AI 应用服务中的哪一层决定？为什么？

答案：应由业务/AI 应用服务或其调用的业务授权服务决定。该问题依赖用户、订单、租户和领域规则；模型服务只负责推理，模型网关只适合通用调用治理。授权结果应在数据检索和工具执行前生效，不能交给模型用自然语言自行判断。

## 自测题

### 自测 1：为什么要区分存活检查和就绪检查？

答案：存活检查判断进程是否卡死或需要重启；就绪检查判断实例是否已经具备接收真实流量的条件。模型进程可能活着但权重未加载、GPU 初始化失败、正在下线或队列已超安全阈值，此时应存活但不就绪。

### 自测 2：模型权重、KV Cache 和用户会话分别是什么类型的状态？

答案：模型权重是大而相对稳定的只读模型资产，可在副本内长期共享；KV Cache 是请求执行期间的短生命周期运行状态，通常在特定模型实例/GPU 内；用户会话是跨请求的业务状态，通常应持久化或放在外部共享存储，而不应依赖某个模型副本内存。

### 自测 3：消息队列在模型架构中解决什么问题，又不能解决什么问题？

答案：它可以让生产者与消费者解耦、削峰、承载异步任务、提供重试和任务状态基础。它不能凭空提高持续处理能力，也不能保证任务语义正确；若进入速率长期超过处理能力，仍需要背压、扩容、降级或拒绝策略。

### 自测 4：为什么模型部署要考虑故障域？

答案：同一机器、GPU、网络、区域、模型版本或供应商可能让多个组件同时失效。识别故障域后才能合理安排副本、隔离在线/离线任务、设计备用路径和评估单点故障，而不是误以为“有三个容器”就天然高可用。

### 自测 5：一个模型版本发布需要观察哪些维度？

答案：至少包括 HTTP 成功率、错误率、TTFT/总时延、吞吐、显存与队列、成本/Token 用量、结构化输出和工具调用成功率、关键业务评测质量、安全拒绝行为以及用户反馈。只看服务是否启动或 200 比例不足以判断发布成功。

## 本节小结

模型服务部署架构的关键在于分清职责和请求路径：边缘入口保护网络，业务/AI 服务处理用户、权限、RAG 与工具语义，模型网关处理跨模型治理，负载均衡和模型副本承载推理容量，数据库/缓存/对象存储/队列各自存放不同生命周期的数据，可观测系统帮助定位端到端问题。

生产化不是把所有组件一次堆齐，而是随着流量、风险和团队能力增长，逐步解决健康检查、冷启动、队列背压、故障隔离、版本发布、容量规划和降级问题。一个好架构应让每类请求在资源紧张和组件故障时仍有清晰、可解释的行为。
