# M12 第 12 节：企业级 Agent 系统设计

## 本节定位

M12 前 11 节分别学习了高级 Agent 的适用边界、任务状态机、Agent Loop、记忆、Checkpoint、异步队列、人工参与、Sandbox、角色分工、Multi-Agent 和 Browser/Computer-use。它们如果各自孤立存在，仍然只是许多技术点；企业级设计的难点在于把它们组合成一个边界清楚、可演进、可运维的系统。

一个真正可用的企业 Agent 系统，不是“接入更强模型 + 调几个工具 + 做一个聊天页面”。它至少要同时回答：

```text
用户能提交什么目标？
系统如何把目标变成可追踪任务？
模型能看到什么、提出什么动作？
谁执行工具，谁决定权限和副作用？
等待、失败、重试、取消、重启后怎样恢复？
何时升级给人？
如何限制成本、数据泄露和错误影响？
如何评估质量、发现问题、发布改动和持续运营？
```

本节不会给出一种放之四海皆准的“标准架构图”。不同业务风险、团队规模、数据治理和任务复杂度都不同。这里要建立的是一套审视方法：先识别业务目标和风险，再逐层选择必要能力，避免架构不足，也避免为了名词完整而过度设计。

## 本节学习目标

学完后，你应当能：

1. 用分层视角描述一个企业 Agent 系统，而不是只列模型和框架名称。
2. 说明接入层、控制层、智能层、工具层、数据层、执行层和运营治理层分别负责什么。
3. 根据任务风险选择同步/异步、单 Agent/Multi-Agent、自动/人工、API/浏览器、内存/持久化等方案。
4. 将状态、权限、工具、记忆、队列、Sandbox、评估和观测放在正确边界。
5. 理解从原型到生产的渐进建设顺序。
6. 能识别常见企业 Agent 架构缺口与过度设计。
7. 能对一个 Agent 项目进行基本的设计评审，并提出优先级明确的改进建议。

## 一句话先讲透

> 企业级 Agent 系统的核心不是让模型拥有更多自主权，而是建立一个以业务任务为中心的控制面：模型负责受限推理和建议，系统负责事实、权限、状态、副作用、预算和审计，人类负责高风险判断；所有能力都能在故障、变更和攻击下保持可解释、可恢复和可收束。

## 基础知识铺垫

### 1. 什么是“企业级”，不是什么

“企业级”不是项目规模大、页面多、用了容器或接入了多个模型。它更关注系统能否在真实约束下持续运行：

- 多用户、多租户或多角色；
- 权限、隐私、合规和审计要求；
- 外部服务不稳定、网络不可靠、任务会中断；
- 需要控制成本、延迟、配额和容量；
- 需求、模型、工具、规则和文档会不断变化；
- 需要让开发、运维、业务和审核人员理解系统做了什么；
- 发生错误时能限制影响、定位原因、修复并防止回归。

一个小团队内部工具也可以具有企业级关键能力，例如最小权限、任务审计和可恢复性；一个功能很多的聊天应用，如果所有权限和副作用都由模型 prompt 控制，则不具备企业级可靠性。

### 2. Agent 是系统中的一个决策组件，不是整个系统

传统后端系统由接口、业务规则、数据库、消息、权限、日志等组成。加入 Agent 后，模型成为一个擅长处理自然语言、不确定路径和非结构化信息的组件，但它不应取代：

- 认证和授权；
- 事务性业务状态；
- 金额、库存、订单等权威事实；
- 数据治理和审计；
- 队列调度和故障恢复；
- 高风险审批和组织责任。

可以把 Agent 看成系统中的“受控决策和编排层”，它提出调查、解释、计划或下一步动作；真正的业务能力仍由受控服务和规则执行。

### 3. 从“聊天机器人”到“任务系统”的思维变化

聊天机器人常以一问一答为中心：

```text
用户输入 -> 模型回答
```

企业 Agent 更适合以任务为中心：

```text
用户目标
-> 创建 task
-> 状态、计划、事实、工具、审批、队列持续推进
-> 形成结果、等待、失败或人工接管
```

聊天界面可以是任务的入口和展示层，但不能代替任务模型。只有任务模型能承载长时间执行、断点恢复、多个参与者、异步结果、取消、审计和成本归因。

### 4. 功能需求与非功能需求必须同时设计

功能需求回答“系统做什么”：查询订单、回答政策、生成报告、创建工单。

非功能需求回答“系统在什么约束下做好”：

| 类别 | 典型问题 |
| --- | --- |
| 安全 | 是否越权、泄露、被注入或被滥用？ |
| 可靠性 | 进程重启、工具超时、重复消息后是否可恢复？ |
| 性能 | 高峰期响应、排队和吞吐如何？ |
| 成本 | 模型/工具/存储的预算如何控制？ |
| 可观测性 | 能否看到任务在哪一步、为什么失败？ |
| 可维护性 | 模型、工具、策略、知识库变更如何验证和回滚？ |
| 合规 | 数据保留、审计、删除、地域和人工责任如何满足？ |

Agent 系统尤其不能只做功能路径。因为模型和外部工具天然具有不确定性，非功能设计往往决定它是否能真实上线。

### 5. 先画“信任边界”，再画系统架构

很多架构图先画模型、向量库、队列，最后才想权限。更稳妥的顺序是先区分信任边界：

```text
不可信：用户输入、网页、上传文件、第三方内容、模型自然语言输出
受限可信：模型 API、外部工具回执（仍需校验）
权威可信：经过认证授权的业务服务、数据库事实、人工审批记录、受控策略
```

再问每个边界之间发生什么：

- 用户文本怎样进入 prompt，如何防注入？
- 模型 tool call 怎样变成服务端动作？
- 外部工具结果怎样过滤后成为 observation？
- 哪些数据可出现在日志、记忆和模型上下文？
- 哪些动作必须被人批准？

信任边界能帮助你避免“模型输出直接写数据库”“网页内容直接改变策略”“服务账号替所有用户做事”等高风险设计。

## 本节主题系统讲解

### 1. 企业 Agent 的分层全景

可以用七层理解一个完整系统。不是每个项目都要有独立服务，但每项职责都应有明确归属。

```text
1. 接入与体验层（Experience / API Layer）
2. 任务与控制层（Task / Control Plane）
3. 智能决策层（Agent / Model Layer）
4. 工具与业务能力层（Tool / Business Capability Layer）
5. 数据与知识层（Data / Knowledge Layer）
6. 异步执行与隔离层（Execution / Queue / Sandbox Layer）
7. 运营、评估与治理层（Operations / Evaluation / Governance Layer）
```

下面逐层说明。

### 2. 接入与体验层：受理目标，而不是把前端直接接到模型

这一层包括 Web/移动端、内部工作台、HTTP API、SSE/WebSocket、Webhook 等。它负责：

- 身份认证和会话建立；
- 输入基本校验、上传受理、限流；
- 将用户意图转换为受控任务请求；
- 返回同步结果或 `task_id`；
- 展示真实任务状态、进度、确认和最终结果；
- 让用户能取消、补充、确认、查看引用或转人工。

它不应：

- 将用户输入未经控制直接变成系统 prompt 和工具权限；
- 根据页面按钮直接执行高风险业务动作；
- 把 SSE 流或浏览器本地状态当成任务真实状态；
- 将内部错误、模型原始响应或敏感数据直接展示给用户。

体验层应让用户知道“系统当前在做什么”，但不能伪造进度或把后台不确定性包装成确定成功。

### 3. 任务与控制层：企业 Agent 的中枢

任务与控制层是 M12 大多数知识的汇合点。它管理：

```text
task_id、任务状态机、任务输入和目标
checkpoint、工作记忆、计划版本
执行租约、并发、预算、截止时间、取消
人工确认/审批、重试、等待、恢复
父子任务和结果聚合
状态转移和审计事件
```

为什么它是中枢？因为模型、worker、队列、UI、人工审核、回调服务都可能短暂失效或更换，而任务状态必须成为各方共同认可的事实。任何组件都不应只凭本地内存决定“任务已经完成”。

可把控制层理解为企业 Agent 的操作系统：它不负责回答每个自然语言问题，却负责让所有动作在正确状态、权限、预算和生命周期中发生。

### 4. 智能决策层：模型被放在受控位置

这一层包含：提示词、模型调用、Structured Output、Tool Calling 决策、Planner/Executor/Critic、模型路由、上下文构造、RAG 结果使用等。

模型适合承担：

- 理解用户自然语言目标；
- 将模糊表述映射为受限任务类型；
- 在允许工具中选择下一步调查或交互动作；
- 生成计划草案、结构化抽取、总结与解释；
- 辅助发现语义矛盾、回答质量问题。

模型不应承担：

- 认证与授权最终判断；
- 订单、金额、库存、权限等权威事实；
- 状态机转移合法性；
- 写操作执行权；
- 幂等、重试、队列 ack、租约；
- 审批和安全策略的最终裁决。

智能层输入应由控制层构造：最小、已授权、来源清楚、符合 token 预算的上下文。输出应是结构化、可校验的建议，而不是直接改变系统。

### 5. 工具与业务能力层：把业务能力封装成窄工具

这一层包含业务 API、领域服务、检索服务、文档处理、通知、支付、工单、第三方集成等。它的关键职责是：

- 提供明确、稳定、受版本控制的能力契约；
- 在服务端完成用户/租户/资源授权；
- 校验参数、业务状态和幂等；
- 返回最小必要、结构化、可追踪的结果；
- 对写操作提供可验证回执、查询或补偿机制。

Agent 不应直接连接数据库、任意调用微服务、拼装 SQL 或操作基础设施。更合理的是：

```text
Agent 提议：query_order_summary(A1001)
-> Tool Gateway/业务服务校验权限
-> 返回允许字段的订单摘要 observation
```

这使工具层既是能力提供层，也是策略执行点。

### 6. 数据与知识层：不同信息使用不同生命周期

企业 Agent 至少会接触四类数据：

| 数据类别 | 例子 | 正确治理重点 |
| --- | --- | --- |
| 业务事实 | 订单、账户、工单、权限 | 权威来源、事务、实时授权 |
| 知识数据 | 政策、手册、FAQ、PDF | 版本、检索、引用、权限、更新 |
| 任务数据 | checkpoint、状态、计划、调用账本 | 恢复、一致性、审计、TTL |
| 记忆/偏好 | 用户语言、历史摘要、已确认偏好 | 准入、作用域、删除、过期 |

不要把业务数据库当成 RAG、把向量库当成权限系统、把聊天记录当成审计、把模型记忆当成权威事实。每类数据的写入、读取、保留和删除规则都不同。

### 7. 异步执行与隔离层：让任务在不确定环境中持续可控

这一层包括队列、worker、调度器、延迟任务、回调处理、Sandbox、浏览器隔离、资源限制等。它负责：

- 将长任务从 HTTP 生命周期中解耦；
- 可靠地分发和重新领取任务；
- 限制并发、速率、成本和资源；
- 处理重试、结果未知、死信和恢复；
- 为代码、文件、浏览器等高风险工具提供隔离；
- 在取消/超时后回收资源。

这一层不是“性能优化附加项”。只要 Agent 有长时间运行、外部调用、文件处理、多步骤或副作用，它就是可靠性的基础层。

### 8. 运营、评估与治理层：让系统能长期改进

一个 Agent 上线后，模型版本、文档、提示词、工具、业务规则和用户攻击方式都会变化。运营治理层需要：

- 日志、指标、trace 和任务事件；
- 质量评估集、回归测试、Bad Case 管理；
- Prompt/模型/工具/知识库版本管理；
- 成本、延迟、成功率、人工介入率监控；
- 安全事件告警、能力撤销、审计查询；
- 灰度发布、回滚、变更审批；
- 数据保留、删除、访问控制和合规检查。

没有这层，系统只能靠用户投诉后手工猜测“模型为什么这么答”。企业 Agent 必须把运行结果转化为可测、可查、可修复的工程信号。

### 9. 一张端到端的任务流

以“用户咨询订单物流，必要时创建工单”为例：

```text
用户/前端
  -> 接入层：认证、输入校验、创建 task
  -> 控制层：PENDING、预算、权限上下文、审计
  -> 队列：投递执行消息
  -> Worker：领取 task，进入 RUNNING
  -> 智能层：基于允许工具与已验证上下文选择 query_order
  -> 工具层：校验用户/订单授权，返回订单摘要
  -> Worker：写 observation，继续查询物流
  -> 智能层：根据事实建议创建工单
  -> 控制层：规则判定需用户确认，转 WAITING_HUMAN
  -> 用户确认：绑定 task/action/version，恢复任务
  -> 工具层：以幂等键创建工单，返回 ticket_id
  -> 控制层：保存结果，SUCCEEDED
  -> 接入层：推送/查询最终结果
  -> 运营层：记录 trace、成本、工具调用、确认和质量信号
```

注意每一步的权力归属：模型提出建议；工具层产生业务事实；控制层决定状态和执行资格；用户/人工处理授权；运营层负责长期观察和改进。

### 10. 同步与异步的架构选择

不是每个 Agent 请求都需要队列。可按任务类型划分：

| 场景 | 典型执行方式 |
| --- | --- |
| 单次短问答、低风险检索 | 同步或 SSE 流式 |
| 多工具但预计几秒完成 | 同步受控 Loop，设明确预算 |
| 文件解析、批量 RAG、长报告 | 异步任务 + 队列 + 状态查询 |
| 等待人工/用户输入 | 持久化等待 + 事件恢复 |
| 高风险写动作 | 任务状态 + HITL + 幂等/对账 |
| 定时/批量任务 | 调度器 + 队列 + worker |
| Browser/Computer-use | 通常异步 + 强隔离 + checkpoint |

错误不是“所有任务都异步”或“所有任务都同步”，而是没有根据等待、风险、时长、并发和用户体验做判断。

### 11. 单 Agent、工作流与 Multi-Agent 的选择

再从系统设计角度复习一次：

| 条件 | 合理选择 |
| --- | --- |
| 步骤确定、规则清晰 | 固定工作流 |
| 有有限语义路径选择 | 单 Agent Loop |
| 不同领域需要路由 | Router + 领域 Agent/工作流 |
| 多个独立子任务可并行 | Fan-out/Fan-in Multi-Agent |
| 高风险业务决策 | 规则/HITL/业务服务优先 |
| 需要网页交互但无 API | 受控 Browser Agent 适配器 |

企业架构的成熟，不是每一项都使用最复杂方案，而是在每个边界选择**最简单但足以满足风险和目标**的方案。

### 12. 权限模型必须贯穿全链路

一个常见架构漏洞是：入口校验了用户身份，但后续模型、队列、worker、工具和 RAG 检索没有持续携带/验证租户与权限上下文。

企业 Agent 应保证：

```text
requester identity
tenant_id
roles/scopes
resource constraints
trace_id/task_id
```

在以下边界中不丢失、不被模型伪造：

- 创建任务；
- 进入队列和 worker；
- 调用工具和业务 API；
- 查询知识库和记忆；
- 人工审批和接管；
- Browser/Sandbox 会话；
- 日志、审计与结果展示。

更重要的是：服务端授权不应只相信任务里携带的 user_id 字符串，而应由经过认证的身份、签名令牌、服务间信任或权威权限服务进行验证。

### 13. 成本架构：模型成本只是其中一部分

Agent 的成本可来自：

| 成本项 | 示例 |
| --- | --- |
| 模型 | 输入/输出 token、多轮规划/评审、不同模型单价 |
| 检索 | embedding、向量库、rerank、文档解析 |
| 工具 | 第三方 API、搜索、OCR、地图、邮件等 |
| 执行 | worker、队列、浏览器/VM/Sandbox、存储 |
| 人工 | 审核、接管、标注、运维 |
| 失败 | 重试、重复调用、错误并行、无效循环 |

成本控制不应只在月底看账单。应在控制层成为实时预算：

```text
每请求、每任务、每用户、每租户、每角色、每工具
的调用次数、token、时长、并发和金额上限。
```

当预算接近上限时，系统可以结束、降级、转人工、延迟或要求用户确认，而不是让模型继续自由尝试。

### 14. 安全架构：从输入到副作用的连续防线

可用一条安全链路审视系统：

```text
用户/外部内容
-> 输入校验与 Prompt Injection 防护
-> 最小模型上下文
-> 结构化决策与工具白名单
-> 权限/业务/预算校验
-> HITL（必要时）
-> 最小能力凭据
-> Sandbox/网络/文件/资源隔离
-> 输出脱敏与结果验证
-> 审计、监控、告警和撤销
```

每个环节回答不同问题：

- 输入层减少恶意/无效内容直接进入系统；
- 上下文层减少不必要数据暴露；
- 工具层防止模型越权提出动作；
- 权限层防止业务越权；
- HITL 处理高风险价值判断；
- Sandbox 限制执行环境；
- 输出层防止泄露和错误传播；
- 运营层支持发现与响应。

没有一层能独立保证安全。企业设计追求的是多层故障不会叠加成严重事故。

### 15. 可靠性架构：接受不确定，而不是假装不会失败

模型、网络、队列、数据库、第三方工具和浏览器都会失败。可靠 Agent 系统不以“永不失败”为目标，而以：

```text
失败可分类
-> 状态可观察
-> 结果可确认
-> 可安全重试或恢复
-> 副作用不重复
-> 无法自动处理时可收束到人工/明确失败
```

关键机制回顾：

- 状态机和终态保护；
- checkpoint 和恢复；
- 幂等键与外部结果对账；
- 条件更新、乐观锁、租约；
- 队列 ack、重试、延迟和 DLQ；
- 取消传播和资源回收；
- 外部工具超时、熔断、降级；
- 版本兼容和灰度回滚。

可靠性不是某个中间件提供的单一功能，而是每个边界都明确“失败后下一步怎么办”。

### 16. 质量架构：把“回答得好不好”拆开测

Agent 质量至少可分为：

| 维度 | 例子 |
| --- | --- |
| 任务完成度 | 是否完成用户真正目标？ |
| 事实正确性 | 是否基于真实订单/政策/工具结果？ |
| RAG 质量 | 是否检索到正确资料，引用是否准确？ |
| 工具选择 | 是否选择合适工具，是否重复/越权？ |
| 安全合规 | 是否泄露、是否被注入、是否绕过审批？ |
| 交互质量 | 是否清楚说明不确定性、等待和下一步？ |
| 系统质量 | 延迟、成本、重试、失败恢复是否在目标内？ |

不能只用“用户喜欢/不喜欢”或“模型打分高/低”衡量全部。应建立包含正常、边界、对抗、失败、权限、长任务和人工流程的评估集，并维护 Bad Case 到回归测试的闭环。

### 17. 可观测性架构：日志、指标、Trace、审计各不相同

| 类型 | 核心问题 | 示例 |
| --- | --- | --- |
| 日志（logs） | 发生了哪些具体事件？ | 工具调用失败原因 |
| 指标（metrics） | 系统整体趋势如何？ | 成功率、P95 延迟、队列积压 |
| Trace | 一次请求跨组件走了什么路径？ | API -> task -> worker -> tool -> model |
| 审计（audit） | 谁因何授权/执行了什么影响业务的动作？ | 某审批人批准退款 |

它们相互关联，但不能互相取代。对于 Agent，推荐以 `trace_id`、`task_id`、`tool_call_id`、`approval_id`、`artifact_id` 等建立关联，让一次用户任务的模型、工具、队列、人工与结果可以串起来。

日志不要记录密钥、完整敏感 prompt 或所有原始文件；审计不要依赖可被普通用户篡改的消息文本；指标不要只看平均值而忽略尾部延迟与失败分布。

### 18. 版本与变更管理：Agent 系统一直在变化

可能变化的东西包括：

- 模型与模型参数；
- 系统 prompt、工具 schema、输出 schema；
- RAG 文档、embedding、rerank、chunk 规则；
- 业务工具 API 和权限规则；
- 任务状态结构、checkpoint schema；
- 审批阈值与安全策略；
- 浏览器适配器和 Sandbox 镜像。

因此应尽量为关键变更保留版本标识，并建立：

```text
离线评估
-> 测试环境验证
-> 小范围灰度
-> 线上指标观察
-> 快速回滚
-> Bad Case 复盘和回归
```

特别是长任务和 checkpoint：新版本上线后，旧任务如何恢复必须有兼容策略。不要让“发布新 prompt/代码”无意改变已经等待审批的任务含义。

### 19. 数据治理：从来源到删除的闭环

企业 Agent 可能处理用户输入、业务记录、文档、模型上下文、记忆、日志、截图和人工反馈。每类数据应明确：

```text
来源与权威性
用途与最小化原则
访问主体与权限
保存位置与地域（按要求）
保留期限与过期
删除/更正机制
是否允许进入模型上下文
是否允许用于评估、训练或分析
审计与合规责任
```

最容易遗漏的是派生数据：文档 chunk、embedding、摘要、RAG 缓存、Agent 记忆、截图、trace 中的 prompt。删除原始文件不一定自动删除所有派生物，需要数据地图和同步策略。

### 20. 典型架构缺口检查表

设计评审时，可以逐项问：

#### 任务与执行

- 是否有明确任务模型、状态机和终态？
- 长任务是否脱离 HTTP，并能在重启后恢复？
- 是否区分同步、异步、等待与取消？
- 是否有重试分类、幂等和结果未知对账？

#### 模型与工具

- 模型输出是否结构化、可验证？
- 工具是否窄能力、白名单、最小权限？
- 权限是否在工具/数据服务端强制，而非只在 prompt？
- 写操作是否有确认/审批、幂等、审计与业务回执？

#### 数据与安全

- RAG、记忆、业务数据是否有清晰作用域、版本和权限？
- 不可信网页/文件/用户文本是否与系统指令隔离？
- 代码、文件、浏览器、网络工具是否有 Sandbox 和资源限制？
- 敏感数据是否避免进入日志、模型上下文和长期记忆？

#### 运营与质量

- 能否通过 task_id/trace_id 重建一次任务路径？
- 是否有评估集、Bad Case、回归与发布策略？
- 是否监控成功率、成本、延迟、队列、人工介入和安全拒绝？
- 是否能快速禁用工具、模型版本或高风险能力？

若关键问题回答不清楚，通常说明不是缺一个新框架，而是基础控制面尚未建立。

### 21. 原型、试点、生产的能力差异

不是所有阶段都需要相同完整度。可用风险驱动的成熟路径：

| 阶段 | 目标 | 必须优先具备 |
| --- | --- | --- |
| 原型（prototype） | 验证用户价值和模型可行性 | 明确范围、无高风险副作用、基础日志 |
| 内部试点（pilot） | 小范围真实使用 | 身份/权限、受控工具、基础评估、人工兜底 |
| 生产早期（production） | 稳定交付核心流程 | 任务状态、审计、重试/幂等、监控、成本限制 |
| 规模化（scale） | 多租户、高并发、多场景 | 队列/背压、治理、灰度、SLO、隔离、运营闭环 |

关键不是阶段名称，而是风险变化。原型若操作真实付款或隐私数据，也应提前引入严格控制；生产系统若只做公开只读总结，某些复杂机制可按需简化。

### 22. 反模式一：模型直连数据库和内部系统

错误架构：

```text
用户输入 -> 模型生成 SQL/命令 -> 直接执行生产数据库
```

问题：模型输出不可信、权限不可细化、注入与误操作风险极高、审计与幂等困难、数据范围容易扩大。

替代方案：模型只提出窄工具调用；业务服务执行参数/权限/状态校验；返回最小 observation；高风险写操作走审批和幂等。

### 23. 反模式二：把 prompt 当作安全边界

错误架构：

```text
系统提示：不要泄露数据，不要执行危险操作。
模型：拥有所有工具、所有数据库、所有网络和管理员凭据。
```

问题：prompt 不能强制权限、不能抵御所有注入、不能阻止工具 bug 或错误配置。

替代方案：将安全规则落实在工具 allowlist、业务授权、短期凭据、Sandbox、网络/文件策略、人工确认和审计中；prompt 只作为行为引导的一层。

### 24. 反模式三：所有请求都走一个无限 Agent Loop

错误架构：

```text
收到请求 -> while true 调模型/工具 -> 直到模型说完成
```

问题：无状态、无预算、无等待、无恢复、无取消、容易循环和成本爆炸。

替代方案：任务状态机 + 有限执行片段 + 步数/时间/成本/风险边界 + checkpoint + 等待/人工/失败出口。

### 25. 反模式四：为了“企业级”一开始引入所有组件

错误架构：还没有一个稳定任务，就同时引入 Multi-Agent、向量库、工作流引擎、浏览器控制、多个队列、多模型路由、复杂审批。

问题：难以定位价值、调试成本高、团队无法维护、测试空间爆炸、风险反而上升。

替代方案：从一个高价值、边界清晰的任务出发，先建任务状态、受控工具、权限和评估，再根据真实瓶颈增加异步、记忆、专门 Agent、Sandbox 等能力。

### 26. 反模式五：只看模型回答，不看系统结果

错误架构：评估只让模型/人工给答复打分，却不检查工具是否越权、任务是否重复写入、审批是否被绕过、重启是否丢任务、成本是否超标。

替代方案：将质量评估扩展到端到端任务：正确性、证据、工具选择、状态转移、权限、安全、恢复、成本和用户体验。

### 27. 一个参考架构：中等风险业务 Agent

下面是一种概念参考，不是必须照搬的部署图：

```text
[Web / API / Internal Workbench]
        |
        v
[Auth + Rate Limit + Task API]
        |
        v
[Task Store + State Machine + Audit + Outbox]
        |
        +--> [Queue / Scheduler] --> [Agent Worker]
                                      |
                                      +--> [Context Builder]
                                      +--> [LLM / Planner / Critic]
                                      +--> [Tool Gateway]
                                      |        |
                                      |        +--> [Business APIs]
                                      |        +--> [RAG / Knowledge]
                                      |        +--> [HITL / Approval]
                                      |        +--> [Sandbox / Browser Adapter]
                                      |
                                      +--> [Checkpoint / Artifact Store]
        |
        v
[SSE / Notification / Human Workbench]

横向能力：
[Observability] [Evaluation] [Policy] [Secrets] [Cost Control] [Governance]
```

其中“横向能力”意味着它们不只属于某个服务：策略、密钥、观测、评估、成本和治理应贯穿各层。

### 28. 一个设计评审走读：智能工单处理 Agent

需求：用户描述问题，系统查询订单/知识库，给出建议；必要时创建工单；复杂或高风险情况转人工。

#### 目标与边界

- Agent 可解释和调查，不直接决定退款/权限变更。
- 查询必须基于当前用户/租户权限。
- 创建工单是写操作，需用户确认。
- 长时间工具或人工等待必须可恢复。

#### 最小架构选择

- 短咨询：同步单 Agent Loop + RAG/只读工具。
- 创建工单：任务状态机 + 确认 + 幂等写工具。
- 人工等待：`WAITING_HUMAN` checkpoint。
- 大文档/批处理：异步队列 worker。
- 工具：`query_order_summary`、`search_policy`、`prepare_ticket`、`create_ticket_after_confirmation` 等窄能力。
- 质量：检查引用、订单归属、未确认写操作、工具调用和用户反馈。

#### 不应一开始加入的内容

- 无必要的 Browser Agent；
- 每个问题都拆 Multi-Agent；
- 让模型直连数据库；
- 把所有聊天记录变成永久用户记忆；
- 在没有真实用例前引入复杂多级审批。

这就是“按风险选择架构”：不是组件越多越成熟，而是每个组件都解决一个已知问题。

### 29. 可扩展性如何理解

企业 Agent 的扩展性不是只指 QPS，更包含四个方向：

| 方向 | 问题 | 关键设计 |
| --- | --- | --- |
| 业务扩展 | 新增任务类型/工具/审批规则 | 任务类型、工具注册、策略版本、契约 |
| 用户规模 | 更多用户/租户/并发 | 队列、限流、隔离、缓存、容量规划 |
| 数据规模 | 更多文档、记忆、日志、artifact | 生命周期、索引、分层存储、删除同步 |
| 组织扩展 | 更多团队维护模型/工具/规则 | 责任边界、审计、配置治理、发布流程 |

真正的扩展性来自边界清楚：新工具不破坏旧工具，新任务不共享不该共享的数据，新模型不改变业务授权，新 worker 能从 checkpoint 恢复。

### 30. 从设计到落地的优先级框架

当你面对一个新 Agent 项目，可按以下顺序推进：

1. **业务目标**：用户真正要完成什么，成功如何判断？
2. **不该交给 Agent 的部分**：权威规则、权限、金额、不可逆操作在哪里？
3. **任务模型**：需要同步还是异步，状态、等待、取消和终态是什么？
4. **工具契约**：最小需要哪些窄能力，谁在服务端授权？
5. **数据与 RAG**：需要哪些知识、来源、引用、权限和版本？
6. **风险控制**：哪些动作需要确认、审批、Sandbox、网络隔离？
7. **可靠性**：超时、重试、幂等、checkpoint、队列、恢复怎么做？
8. **体验**：用户如何看任务状态、补充、确认、取消和理解失败？
9. **评估与运营**：怎样验证、观测、灰度、回滚和修复 Bad Case？
10. **扩展**：真正出现复杂度后再引入 Multi-Agent、Browser、更多模型或更强执行平台。

这个顺序能让技术选择服务于业务和风险，而不是被框架或热点牵着走。

## 常见误区

### 误区 1：企业级架构就是微服务 + 容器 + 多模型

这些可能是实现方式，但不能替代任务状态、权限、工具控制、可靠性、审计和评估。一个单体服务只要边界清晰、控制充分，也可以承载早期企业 Agent；反之组件再多也可能不安全。

### 误区 2：只要模型能力足够强，系统层可以简化

更强模型能改善理解和生成，但不能消除权限、状态一致性、幂等、数据治理、外部副作用和合规责任。模型能力提升反而可能扩大可行动范围，更需要系统边界。

### 误区 3：所有 Agent 都应该具备记忆、队列、Multi-Agent 和浏览器能力

这些都是按需能力。简单、短、只读任务可能只需受控模型调用与 RAG；高风险、长任务才需要更完整控制。按风险和真实瓶颈渐进建设。

### 误区 4：把业务规则写进 prompt 就能快速迭代

提示词适合描述语言行为和引导，但金额阈值、权限、状态流转、审批规则等必须可测试、可版本化、可审计，通常应在策略/业务代码中执行。

### 误区 5：上线后只监控接口错误率就够了

Agent 可能 HTTP 200 但给出无依据答案、重复调用工具、排队过久、超预算、审批积压或被策略拒绝。需要任务、质量、安全、成本和用户体验多维观测。

### 误区 6：人工参与代表系统不够智能

人工是高风险决策、责任分配和异常处理的合理边界。好的 HITL 会让人只处理真正需要判断的点，并将反馈用于系统改进，而不是让人替 Agent 做所有低价值工作。

### 误区 7：一次架构设计就能永久不变

模型、工具、规则、数据、用户规模和攻击方式都会变化。成熟系统依赖版本、评估、灰度、监控和回滚持续演进，而不是追求一开始画出“终极架构”。

## 本节练习

### 练习 1：分层归属

请将下列职责放到最合适的层：

1. 判断用户是否有权访问订单 A1001。
2. 保存任务等待人工审批的状态和确认 ID。
3. 依据当前事实决定要不要检索政策文档。
4. 限制一个代码分析任务最多使用 2 分钟和 1GB 内存。
5. 统计一周内哪些任务最常因工具超时失败。

答案：1 属于工具/业务能力层的授权与权威数据服务（入口也可做初检，但工具侧必须强制）。2 属于任务与控制层。3 属于智能决策层，但只在允许工具范围中选择。4 属于执行/Sandbox 层，控制层可提供预算。5 属于运营、观测与治理层，通过日志/指标/trace 汇总分析。

### 练习 2：识别架构缺口

某 Agent 系统流程是“前端把用户问题和数据库连接信息发给模型，模型生成 SQL 后服务直接执行并把结果显示给用户”。请指出至少四个企业级缺口。

答案：模型拥有过大能力且 SQL 不受控；数据库连接信息和可能的敏感数据暴露给模型/前端；缺少服务端细粒度用户/租户授权；没有参数/查询范围/成本限制；容易遭受 prompt injection 和 SQL 风险；没有任务审计、幂等、结果脱敏或高风险确认。应改为窄能力查询工具、后端授权、字段白名单、参数化/受控查询、审计与输出过滤。

### 练习 3：选择执行模式

请为以下需求选择同步、异步或“同步受理 + 异步执行”，并说明原因：

1. 用户询问一条退款政策的解释。
2. 用户上传 300 页扫描 PDF，要求 OCR、提取和建立知识库。
3. 用户提交一个需要主管批准后才能执行的退款请求。

答案：1 通常同步或 SSE 流式，前提是检索和答复在短预算内。2 应同步受理 + 异步执行，因文件处理耗时和资源波动大。3 应同步受理并创建任务，随后进入异步/等待审批状态；用户不应在 HTTP 连接中等待主管处理，批准后任务再恢复。

### 练习 4：设计最小生产化路径

一个团队已有“模型 + RAG + 两个只读工具”的原型，想让内部员工使用。请给出优先级最高的五项生产化补充。

答案：合理答案包括：1）接入认证、用户/租户/知识库权限过滤；2）工具服务端校验和字段白名单，避免模型直连数据；3）结构化输出、基础错误处理和工具调用审计；4）任务/trace 观测、关键指标和失败日志；5）评估集与 Bad Case 回归，验证答案引用、权限和工具选择。若任务会变长或有写操作，再优先加入任务状态、幂等、审批与队列。具体顺序随风险调整。

## 自测题

### 自测 1：企业 Agent 的“控制面”包含什么，为什么重要？

答案：控制面包含任务状态机、checkpoint、预算、权限上下文、工具策略、租约、重试、取消、审批、审计和父子任务编排等。它让模型、worker、队列、UI 和人工在同一权威任务事实下协作，使系统能在故障、等待和变更中保持可控，而不是靠某个进程内存或模型文本猜测。

### 自测 2：为什么模型不应直接成为业务事实和权限的最终来源？

答案：模型输出具有概率性，可能幻觉、误解、被注入或使用过期上下文；它也不具备业务系统的事务、身份和审计能力。业务事实应来自权威服务/数据库，权限应由认证授权系统在服务端强制，模型只能基于受控 observation 提出建议。

### 自测 3：企业 Agent 的数据层为什么要区分业务事实、知识、任务状态和记忆？

答案：它们的来源、权威性、生命周期、权限、更新和删除规则不同。订单状态需要实时权威查询，政策文档需要版本与引用治理，任务 checkpoint 需要恢复和审计，用户偏好需要准入和删除。混用会造成过期、越权、无法恢复和合规问题。

### 自测 4：从原型走向生产，为什么不应一次引入所有高级组件？

答案：每个组件都会增加状态、接口、运维和测试复杂度。应先围绕真实高价值任务建立任务边界、工具授权、评估和观测，再根据长任务、并发、风险、数据规模等真实瓶颈增加队列、记忆、Multi-Agent、Sandbox 等能力。这样更可维护，也更容易验证收益。

### 自测 5：请用一句话概括企业级 Agent 架构的核心原则。

答案：以可持久化业务任务为中心，让模型在最小、受控能力内推理和建议，把事实、权限、副作用、预算、恢复、审计和高风险责任放在可验证的系统与人工流程中，并通过评估和观测持续改进。

## 本节小结

企业级 Agent 设计不是堆叠模型、框架和中间件，而是围绕一个可追踪任务建立分层控制：接入层受理目标，控制层维护状态与生命周期，智能层做受限推理，工具层执行业务能力，数据层治理事实与知识，执行层提供队列和隔离，运营层负责质量、安全、成本与变更闭环。组件的选择应由任务风险和真实瓶颈驱动。
